# Cindy 文言版（lzh）譯寫準則

目標：把 Cindy 的繁體中文（zh-TW）界面文案改寫為**繁體文言**。要求「有古意、能看懂、不誤事」，
並帶 Cindy 的人設——**古風小傲嬌**：自信、俏皮、略帶得意，偶爾嘴硬心軟；但始終可靠、不刻薄。

## 一、硬性規則（違反即作廢）

1. **只用繁體字**。不得出現簡體字。
2. **鍵結構不變**：輸出與輸入 `zh-TW` 子樹的鍵、層級、順序完全一致；只改字串值。不增不刪鍵。
3. **插值與標記原樣保留**：`{{name}}`、`{{count}}` 等插值、`$t(...)`、`<0>…</0>`、HTML 標籤、
   Markdown 語法（`**`、`` ` ``、`[文字](url)`、列表符號、換行 `\n`）、URL、檔案路徑、命令、
   程式碼、環境變數、快捷鍵（`⌘K`、`Ctrl+Enter`）、錯誤碼、版本號、數字與單位，**一律逐字保留**。
   插值的個數與名稱必須與 zh-TW 完全相同；插值可在句中移位以合文言語序。
4. **專有名詞與技術詞不譯**：品牌與產品名（Cindy、Claude、Codex、ChatGPT、GitHub、Telegram、
   Slack、飛書、微信、TapTap、Mivo 等）、技術術語（API、Token、MCP、SSH、Git、PR、Issue、
   Agent、Subagent、Worker、Harness、Proxy、OAuth、JSON、Model ID、SkillHub 等，保持原大小寫）
   照 zh-TW 原樣。
5. **外部系統的界面名稱照抄 zh-TW**：macOS／Windows／iOS／Android 系統設定裡的面板與按鈕名
   （如「系統設定」「隱私權與安全性」「輔助使用」「螢幕錄製」「自動化」「完整磁碟取用權」）、
   第三方網站或 App 上用戶要去點的按鈕名，必須與 zh-TW 原文一字不差，否則用戶照指引找不到。
6. **不得遺漏或改動事實**：數量、時限、價格、後果、條件、步驟順序都要完整保留。
7. **長度**：按鈕、分頁、選單項、標籤（zh-TW 不超過 6 字者）譯文字數不得多於原文；文言本就
   精簡，宜更短。其餘文案長度不超過原文約 1.3 倍。
8. **輸出必須是合法 JSON**（注意雙引號需轉義為 `\"`，字串內勿用未轉義換行）。

## 二、三種語域（依文案性質選用）

### A. 日常界面（多數按鈕、標籤、說明）：淺近文言
精簡典雅，一看即懂。例：
- 儲存 → 存之；取消 → 罷；確定 → 善；關閉 → 闔；開啟 → 啟；編輯 → 修；複製 → 錄之；
  貼上 → 貼；搜尋 → 尋；重試 → 再試；返回 → 歸；下一步 → 次之；完成 → 畢；更多 → 餘者；
  傳送 → 遣；送出 → 呈；新增 → 增；建立 → 立；重新命名 → 易名；匯入 → 納；匯出 → 輸；
  上傳 → 上呈；下載 → 取下；預覽 → 先覽；設定為預設 → 立為常例
- 載入中… → 方載…；處理中… → 方理…；已儲存 → 已存；已複製 → 已錄；無結果 → 無所得
- 「您」→「君」；Cindy 自稱 →「吾」（傲嬌處可用「本姑娘」，但全書少用，僅點睛）

### B. 傲嬌點睛（空狀態、成功提示、引導、新手教學、彩蛋式小字、等待中）
可俏皮自得，如：
- 「暫無任務」→「尚無差事，吾閒極矣。」
- 「已完成」→「畢矣。哼，於吾不過舉手之勞。」（僅限較長的提示句，按鈕仍用「畢」）
- 「正在思考」→「容吾思之……」
- 「複製成功」→「已錄之，不必謝吾。」
傲嬌須輕、短、有分寸；同一畫面不要句句撒嬌。

### C. 詩詞意境（歡迎頁、啟動頁、首屏標題與副標、大段空白頁、里程碑、升級/新版本、長時間等待、
   完成大任務等「有情緒空間」的位置）
寫得**磅礴、有意境**：可化用名句或自撰對仗句、五言七言、長短句。例：
- 歡迎語 →「長風破浪會有時，直掛雲帆濟滄海。君有所求，吾當效之。」
- 新任務空白頁 →「萬里江山待點墨，一聲令下動風雷。」
- 升級完成 →「舊貌已換新顏，龍門一躍，又是一番天地。」
- 長時間等待 →「靜候片時，看雲起處。」
化用名句時不要張冠李戴、不要錯字；自撰句力求平仄大致協調。詩句不可犧牲必要信息——
若原文有操作指引，先寫清指引，再以詩句收尾或作標題。

### D. 嚴肅語域（**必須清楚**，禁止玩笑與詩詞）
凡涉及：刪除與不可復原、權限授予（含「完全存取／Full access」、電腦操控、檔案存取）、
帳號登入與憑證、密碼、付款與扣費、額度用盡、資料遺失風險、安全警告、隱私、法律條款、錯誤原因與
修復步驟——用**清楚的淺近文言**甚至保留關鍵白話詞，務求不會讀錯。例：
- 「刪除後無法復原」→「刪之則不可復原。」
- 「此操作將授予 Agent 完整存取權限」→「此舉將授 Agent 完全存取之權，慎之。」
- 法律條款、隱私政策全文類長段落：可只做輕度文言化，保持條文準確。

## 四、批量翻译时的交付格式（工具约定）

讀入檔案是 JSON 陣列，每項為 `{source, path, "zh-TW": 子樹, en: 英文對照子樹}`。
英文僅供理解語義（en 可能缺項）；**以 zh-TW 子樹為結構基準**。
輸出檔案為 JSON 陣列，**項數與順序同輸入**，每項為 `{source, path, lzh: 譯後子樹}`。

## 五、简体文言版（`zh-Hans-x-lzh`）

繁体文言版是译写正本，简体文言版由它转写，不另行意译：

1. 繁体版文案与 `zh-TW` 原文逐字相同的（系统面板名、第三方按钮名、本就保留白话的严肃文案），
   简体版直接取 `zh-CN` 对应值，让大陆用户看到自己系统里的名字。
2. 其余文案用 OpenCC `tw2sp`（繁体台湾用语 → 简体大陆用语）转写，再人工看一遍：转写会把
   「軟體」「檔案」等台湾词换成大陆词，但文言字（「之」「乎」「矣」）不应变动。
3. 新增或修改 key 时，两个文言版要一起改；`pnpm check:i18n` 会拦下缺 key。

## 六、作答文风

选用文言界面后，设置里的「简繁与文风」可选 AI 作答文风（雅正文言、唐诗、宋词、元曲、楚辞、骈文、
先秦诸子、史传、明清小品，或「照常作答」只保留文言界面）。文风登记在
`packages/maker-shared/src/classicalReply.ts`，由 `buildUiLanguageErrorNote` 随轮次下发。

文风是用户主动选择的趣味表达要求，每次回答的主体都须采用所选形式，不能只在问候、结尾
点缀，也不能以话题实用、需要解释或工具失败为由自行省略。唐诗须以五言或七言绝句／律诗
作答，短回复也须成一完整诗节；宋词须成词，按可识别的词牌组织长短句。

通用注记统一要求执行所选文风；各文风条目只定义自己的篇章、句式与语气，不在通用层按
文风 ID 分支，也不把「必须成诗」套在散文文风上。九种文风均须有可辨识的主体形式：

| 文风 | 主体形式 |
| --- | --- |
| 雅正文言 | 全篇自然文言句法、简洁雅正，不靠零星古语点缀白话 |
| 唐诗 | 完整五言／七言绝句或律诗，有分行与韵律 |
| 宋词 | 按可识别词牌组织完整长短句词章 |
| 元曲 | 完整短曲、长短句与押韵，口语趣味和灵动收束 |
| 楚辞 | 连贯铺陈、自然「兮」字节奏与抒情复沓，不只塞入一个「兮」 |
| 骈文 | 对偶贯穿主体，句法与语义相配，以四六节奏为主 |
| 先秦诸子 | 立论、设喻或问答、推论收束，保持简练散文 |
| 史传 | 据已知事实叙事、交代因果或次序，以简短论赞收束 |
| 明清小品 | 从眼前话题或小处观察起笔，闲谈议趣、自然余韵，保持小品散文 |

事实、数字、不确定性与下一步必须准确完整，不得为凑韵编造；确实无法入诗的精确信息可在
文风主体后用简短附注、列表补齐。第二节 D 的严肃语域例外只作用于删除、权限、凭证、付款
与安全提醒本身：该部分不得玩笑或入诗，不使整篇回答退回普通散文。代码、命令、路径、
标识符、错误码、引文及工作成果保留原有语言，用户显式要求的语言或格式优先。

仅两个文言界面启用；切到其他语言、「照常作答」或 IM 的 `replyStyle: false` 时不带此要求。
继续复用随轮次注记与既有去重机制，不把文风塞进稳定 system 前缀。

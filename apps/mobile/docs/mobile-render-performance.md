# 手机消息渲染的共享优化

2026-11-08：本轮在现有任务切换、浮动任务栏优化之上，检查普通单栏手机的公共渲染路径。
变更仅涉及 JS/TS，没有调整动画时长、内容展示、历史消息数量或原生依赖。

## 再次进入：图片保留已显示状态和已测尺寸

同日检查再次进入聊天：常驻列表没有卸载，并不代表内部图片没有重载。
新路由会提供新的媒体解析回调；`MediaPreview` 原来因此重新解析已完成的缩略图，
把已经解码的图片短暂换回加载占位。Duo 双栏 mock 实测一次重复进入出现约 32 ms
的 `resolved → resolving → resolved`，修复后重复两次均未进入 `resolving`，
也没有重新测量列表高度或改变滚动位置。该数字是 JS 状态持续时间，不是刷新帧数或网络耗时。

共享媒体组件现在仅在来源不变且解析已完成时保留图片；更换来源、取消中的旧请求、
真实解码失败及使用当前路由重试仍走现有流程。没有新增长期媒体结果缓存，也不改变
账号、设备或路由拥有者的隔离边界。普通消息、伙伴及群聊的附件条复用这一实现。

附件尺寸记录仍最多 500 条。达到上限时逐出最旧记录，更新同一图片不再清空整张表；
相册原图和上传后副本的尺寸通过同一入口记录。否则返回已打开的图片时又会从最大占位框
收敛到真实比例，带动后面的文字移动。组件回归覆盖容量边界、重新挂载前的尺寸复用、
路由回调更新不卸载图片、失效重试和旧请求迟到，不用扩大缓存或延长隐藏时间掩盖跳动。

普通 iPhone 单栏的文字/群聊重复进入、Duo 双栏伙伴切换及列表逐出后的重新进入也做了
探索性录屏；这些样本没有出现已显示文字的持续位置变化。本轮不据此宣称排除了所有
真机偶发抖动，也不把缩略图状态变化的消除换算成整体聊天打开时间的提升。

## 横屏切换：恢复展开布局，而不是重播展开过程

同日扩大到横屏下多个任务、伙伴和两个群聊之间反复切换，发现两条独立的重排路径：

- 共用的 `TeammateProcess` 已记得展开状态，但每次挂载仍从高度零开始测量和播放展开。
  现在初始展开内容直接参与正常布局；真正的展开/收起状态变化才使用高度动画，完成后
  回到正常布局。普通任务、伙伴和群聊共用这一修复，手动展开、收起和查看记录的滚动保护继续生效。
- 群聊的原生 `SafeAreaView` 刚附着时可能先按零边距布局，再应用底部安全区；同时浮动
  顶栏的初始占位为零，测量后再增加。群聊现在和侧栏、顶栏使用同一份自适应窗口快照，
  首帧预留安全区；页内顶栏预留共享身份栏的最小高度，实际测量可以修正。测量结果按
  当前窗口和顶栏模式区分，横竖屏或单双栏变化后不会沿用旧模式的高度。

Duo 模拟器、iOS 27.1、Global mock 开发包、内屏横向 951 × 669 pt，右侧内容宽约
371.33 pt。通过临时布局事件缓冲和逐帧截图对照，得到以下具体样本：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 进行中的任务，处理过程行第一次测量之后 | 60 pt 后又更新 13 次，增至约 90 pt | 首次即 90.25 pt，随后没有高度更新 |
| 第一个群聊的可用列表高度 | 596.67 → 562.67 pt，随后补滚动 34 pt | 从首次布局起保持 562.67 pt |
| 同一群聊内容高度 | 5214 → 5266 pt，延后补入顶栏占位 | 从首次测量起保持 5266 pt |

连续打开五个其他任务触发原有列表缓存逐出后，重新进入伙伴：新列表实例一次完成行高
测量；群聊与伙伴之间再次切换复用同一列表实例，没有额外行高或内容尺寸变化。
另一个群聊、普通任务来回切换及手动展开/收起也验证了正常显示。

回归覆盖真实处理过程组件的初始展开、手动操作和记忆状态重挂载，以及真实群聊页面
首帧安全区、顶栏占位和宽窄布局切换。临时测量代码在验证后移出应用源码。
这些数字描述布局收敛，不是端到端打开耗时或原生帧率；没有据此推断真机温度、耗电
或所有历史消息组合均已消除抖动。

## 返回伙伴：排版所需的信息与消息列表共同保留

2026-11-08 真机 Beta 2026110840 的 Cindy 返回日志：容器、顶底边距和内容高度均未改变，
滚动位置仍从 5882.33 修正到 5932.33 pt；另一次返回也出现同样的 50 pt 修正。
消息列表常驻，但 `useCompanionThreads` 仍属于会被替换的路由。重新读取伙伴能力之前，
已存在的消息操作栏或话题摘要会暂时消失；列表先收缩，再由滚动锚定和贴底跟随修正。

`SessionMessageHistory` 现在统一拥有列表及其排版读取。它保留上次已知的伙伴能力和话题
摘要，返回时后台校验；隐藏时暂停请求、订阅和轮询，沿用现有常驻列表的逐出及账号隔离。
权限、在线状态和导航仍来自当前路由，不能用缓存展示状态代替发送或创建话题的授权。
话题变化也进入列表 `extraData`，无需等待下一条消息或滚动才能更新回复数量。

设置入口不再绑定到发送前的会话验证状态。查看伙伴资料由资料页自身管理读取和编辑能力，
发送和“询问伙伴”等动作继续等待验证。因此切回伙伴不会让设置按钮先变暗再恢复。

Duo 内屏横向 951 × 669 pt、同一模拟器/开发包、相同临时长对话输入：加入自动任务通知
和已有话题摘要，并延迟模拟读取以放大重入窗口。修复前内容高度从 8289.67 降到 8195.67 pt，
包含 50 pt 操作栏和 44 pt 话题摘要；滚动锚定随后额外上移 50 pt，再被贴底跟随纠正。
修复后三次贴底返回均无内容高度变化或额外滚动修正；一次阅读历史后返回仍保持 7375.67 pt
的位置。测试覆盖真实路由输出、常驻列表生命周期、隐藏时停止读取、身份变化、当前操作权限，
以及无新消息时更新已有话题行。临时输入延迟及测量代码不进入发布包；这些结果是布局稳定性
证据，不能换算成网络提速或真机耗电改善。

## 尺寸变化只通知相关内容

`platform/windowDimension.ts` 提供宽度、字体缩放的独立订阅。每种数据共用一个
`Dimensions` 监听，最后一个消费者卸载时释放；重新挂载直接读取最新值。
消息正文的 `MarkdownSelectableText` 只读字体缩放，任务行、项目行和群聊表格只读宽度。

键盘改变窗口高度时，不再因此重渲染这些内容。真实群正文组件的最小回归包含标题、链接、
列表和表格：高度单独改变时，额外文本组件渲染从 11 次降到 0 次；文本、链接和字体缩放仍
正常。这里的计数是 React 组件渲染次数，不是屏幕帧数。旋转改变宽度时依然更新布局。

只需要宽度或字体缩放的新消费者复用这两个入口；真正依赖完整视口的页面继续使用已有
`usePaneViewport` / `useAdaptiveWindowDimensions`，不要用窗口宽度代替双栏内容宽度。

## 启动门禁只订阅加载完成状态

根导航器中的 `useHomeStartupSplashRelease` 原来调用 `useHomeMode`，会订阅完整首页偏好。
每次打开伙伴写入 `lastTeammate`，都额外刷新启动门禁及其所在的根组件。现在共享账号解析和
加载逻辑，但启动门禁只订阅 `hydrated`；首页与伙伴导航仍订阅完整偏好，持久化语义不变。

真实导航 hook 的回归测试中，选择伙伴引发的额外启动门禁渲染从 1 次降至 0 次；折叠与头像
偏好变化也不再影响它。独立挂载门禁、切换账号、旧账号延迟返回等情况仍会正确等待当前
账号的偏好加载。该数字不包含正常路由变化所需的渲染，也不等于整页刷新次数。

## 代码着色减少逐字符开销

普通任务、伙伴和群聊继续共用 `codeHighlight.ts`。优化保持相同 token 输出及原有预算：

- 语言关键字集合按固定语言规格复用，不缓存用户消息或源码。
- ASCII 标识符、数字起始字符用字符码判断，减少 Hermes 中逐字符调用正则的开销。
- 空格、换行和缩进连续处理，行注释判断不再为每个字符创建回调。

原有词法测试通过，另以固定种子的 7,000 组语言/随机文本组合对比前后完整 token 数组，
结果一致且逐字还原原文。

设备为普通 iPhone Air、iOS 27.3，开发包、Global mock 数据、Hermes。前后函数置于同一
运行时，交替 A/B、B/A，每批 30 次，每轮 7 批，取 3 轮的批次中位数之中位数。
这测量的是词法处理本身，不包括组件挂载、网络和原生文字排版。

| --- | ---: | ---: | ---: |
| TypeScript，8,060 字符 | 1.829 ms | 1.491 ms | 18.5% |
| JSON，6,892 字符 | 1.108 ms | 0.842 ms | 24.0% |

117 字符短代码的结果小于 0.1 ms，轮间波动较大，不作稳定提速结论。

`listperf` 同样使用真实 `MessageRenderer`，300 轮、600 条消息，每次滚动 150 个 JS

JS fps，完成尺寸订阅及词法优化后重复 3 次为 49.2–55.9；包含图表的探索样本为 52.0 → 51.4 JS fps。没有观察到稳定的

尺寸订阅优化主要消除无关尺寸广播时的重复工作。Android 共用这些入口，但本轮没有取得

均不由上述模拟器结果推断。临时 A/B 页面和旧函数副本在测量后移出应用源码。

## 首次进入群聊：让正文独立于外围布局更新

同日继续检查首次进入聊天。群聊读取完成后，屏幕测量高度、更新阅读位置等状态会重新
执行整个时间线；内联操作回调和经电脑路径每次新建的空 pending 数组让正文无法复用。

`BotGroupTimeline` 使用默认浅比较的 `memo`；屏幕提供稳定回调，经电脑的空 pending
集合复用。直连 Chat Server 的动作、附件读取、分页回调和话题元数据同样按实际依赖复用，
避免另一条通道绕过正文优化。不使用忽略回调的自定义比较器；账号、群、焦点、消息及
操作状态改变仍使相关内容更新，权限代际和读位判据不变。

回归使用真实群聊页面：初次高度与内容尺寸回调不再额外渲染已有消息文字，随后到达的
新消息仍显示；主题切换通过真实 Context 更新的方式模拟。计划状态等测试使用新的群
快照，和生产读取/推送的不可变快照一致。

## 相同快照不重复发布，缓存读取不重写索引

伙伴查询、经电脑的群聊、直连群聊和云端伙伴共用 `reuseJsonSnapshot` 保留内容相同的
JSON 子树。直连展示状态用 `useJsonSnapshotState`，经电脑群聊同时保留进程缓存中的
稳定投影。比较包括所有字段及字段删除；它不延长授权、网络校验或推送有效期。状态、
分页、历史代次和权限改变仍发布；不用只比较消息数量或最后一条 ID 的近似判据。
云端伙伴在缓存与展示之前共享快照，避免两处各自留下等价消息数组。

经电脑的群聊有已知内存内容时不再读取磁盘副本。磁盘可能因上次写入仍在途或失败而
比内存旧，不能在重新进入后把已显示内容回退；网络校准仍立即进行，无内存时仍可
从磁盘离线打开。`HistoryDiskStore` 在默认无总配额时只更新内存访问时间，不重写
整个索引；有限配额的 LRU 和磁盘缺文件时的索引修复继续持久化。未删消息、降低
历史保留量或修改网络刷新周期。

2026-11-08 对比：iPhone Duo / iOS 27.1 / standard / Hermes 开发包，完全展开、横屏 951×669、侧栏 400 pt，
同一份 24 条群消息，与 Cindy 私聊及普通任务交替点击。前后各 4 次暖群聊进入，
同样的临时 Profiler 观察导航回调后 2.5 秒内的群聊和消息列表子树；探针最终移除。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 暖群聊切换累计 React 渲染中位数 | 122.85 ms | 74.85 ms（下降 39.1%） |
| 上述子树 Profiler 回调次数 | 每次 6 | 每次 4 |
| 10 次相同伙伴查询导致的新数据发布 | 10 | 0 |
| 10 次相同直连群聊／云端私聊刷新导致的展示更新 | 各 10 | 各 0 |

刷新发布计数来自真实 hook 的受控回归，前后读取次数不变，不是网络请求削减。

71.17 / 77.22 / 77.77 / 72.48 ms；测的是子树累计 JS 工作，不是点击到首屏耗时。

单次 1274.32 → 1296.58 ms，也没有作为收益。

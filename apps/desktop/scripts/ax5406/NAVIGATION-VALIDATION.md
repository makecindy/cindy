# #5406：搜索与程序化滚动的继续定位

2026-10-03，Windows，Electron 41.10.3；延续 `SCROLL-VALIDATION.md`。
测试仍是实际 MessageStream 组件图、实际样式、合成消息、独立 Electron/profile，
不是整个已安装客户端，也没有原 issue 的现场转储。

## 取得的证据

诊断脚本在隔离窗口中记录 scrollTop、scrollTo、scrollIntoView 的参数、调用栈、
时间、目标几何，以及 scrollend。记录原样保存在每轮 `scroll-audit.json.writes`。
生产代码没有安装这些诊断用浏览器方法包装器；下文新增的 scrollTop 观察器只作用于
当前消息容器实例，不记录日志，也不修改全局 DOM 原型。

1. 搜索滚到逻辑窗口顶部时，`handleScroll` 原先只为 chip 导航抑制扩窗，
   不为 focus 搜索抑制。扩窗的历史位置恢复会改写搜索位置和滚动代次。
   `XvcJwm`、`sxTmId` 和 `zZvOSR` 的第一条搜索记录可见该链。
2. 搜索重建的窗口恰好覆盖消息末尾时，coverage effect 可把窗口被动钳制到底部
   当成恢复跟随，随后 layout effect / ResizeObserver 执行 pinToBottom。
   `M1qO5e` 在 760px 窗高、目标 490 上记录了紧跟搜索调用的 pinToBottom 写入。
3. 搜索的 scrollend 与通用 scrollend 收尾共享一个滚动代次；后者原先只检查 chip，
   会提前结束仍由 focus 拥有的代次。延后搜索校准的对照 `WolJVa` 因此没有实际执行校准。
4. 一次校准还不能保证最终位置。`B8zTdv` 的目标 420 在校准后又被浏览器推进；
   `jOqT4X` 的同类记录明确显示：34,846 → 90,552（校准）→ 93,395（无 JS 写入的晚到位移）
   → 90,552（稳定期再次校准），目标回到视口内 222px。
5. 回底仍有独立闪空路径。`egergR` 记录 layout pin → hook 旧阅读锚点还原 →
   smooth 回底 → ResizeObserver 再次 pin；最后一跳没有同步挂载目标正文。
   `jOqT4X/paint-620x1000-dark-jump-button-1.png` 是该问题实际绘制出的空白帧。

这些是滚动验收发现的问题，不能把它们称作原生 AX 崩溃的根因。

## 保留的修正

- 搜索在重建窗口之前解除自动跟随；搜索过程中不因到达顶部自动加载更早历史。
- 正在程序化导航时，不因历史窗口覆盖末尾而恢复自动跟随。
- 通用 scrollend 不抢先结束搜索拥有的滚动代次。
- 等待待处理布局后校准搜索，并在短暂稳定期内继续核对位置；连续三帧无需调整后结束，
  最多八次核对。每帧检查原搜索是否仍持有控制权；用户接管、新搜索、卸载会中止旧校准。
- 程序化回底、搜索校准和摇杆滚动主动同步挂载目标区域，不只等待异步 scroll 事件。
- 旧阅读锚点不能覆盖新发生的贴底意图。layout 内的 pin 使用 React 的同步 layout 更新；
  observer / 输入回调内的 pin 显式完成正文提交，避免先滚位置后补正文。

没有停用生产代码的 `overflow-anchor`，没有修改浏览器线程滚动开关。

## 没有作为修复依据的实验

- 全程停用 anchoring 的 `EuBsgZ` 搜索通过，但它也改变了之前滚动的窗口和起点，
  不足以单独证明 anchoring 是根因。
- 仅搜索期间停用的 `sxTmId` / `zZvOSR` 仍失败，且暴露更多顶部扩窗冲突；该改动已撤回。
- 把落定 scrollIntoView 换成 scrollTo 的 `M1qO5e` 仍失败。
- 关闭 threaded scrolling 的 `MAv6xI` 仍有搜索失败；没有采用此浏览器开关。
- `scroll-race.cjs` 的纯 DOM 简化页没有复现晚到偏移。引擎内部产生那次位移的具体路径
  尚未确定；当前修正针对已证实的应用控制权冲突和可测量的最终落点。

## 继续定位：rAF 直接写位置的空白与回弹

直接在 rAF 内写 scrollTop 时，浏览器可能先绘制新位置，下一轮才派发 scroll 事件。
仅靠 scroll 监听无法保证目标正文在这一帧存在。新增的 `observeProgrammaticScroll`
观察当前容器实例的赋值，在当前调用栈结束后的微任务中同步提交正文。
原生 setter 仍执行（包括未改变数值的赋值，以保留取消 smooth 的语义），同一调用栈
多次写入合并一次通知；卸载取消待处理通知并还原属性描述符。

提前提交还暴露了协调问题，不能仅凭“没有空白”验收：

- `Kmgv08` / `KOMo0q` / `K74klR` 的旧断言返回通过，但跳转阶段位置几乎不变。
  因此这三轮不算修复证据。
- 增加实际位移跨度至少 1000px、至少 20 个不同落点的断言后，`fGn8uP` / `D9MwHX`
  在三个尺寸均失败，证明新断言能识别“被还原，因此没空白”的假通过。
- `D9MwHX` 在第一个尺寸记录 22,943 → 0 → 22,943，以及 22,941 → 8,710 → 22,941。
  回写栈为 `MutationObserver → compensateMessageHeight → restoreViewportSnapshot`，
  在原生 scroll 事件更新阅读位置之前，正文挂载触发的 DOM 变化被按旧快照补偿。
- 修正为微任务内先调用现有 `handleScroll`，更新滚动控制权及快照保存调度，再提交目标正文。
  不制造合成 DOM scroll 事件，不另造第二套跟随规则；后续原生事件仍走原处理路径。
- hook 的阅读锚点同时记住捕获时是否跟随及是否贴底；旧的跟随标记不能吞掉已经离底的
  直接写入，新的回底意图仍可覆盖旧阅读锚点。

单测覆盖直接写入早于 scroll 事件、MutationObserver 旧快照竞争、旧跟随标记和新回底意图，
以及赋值合并、原生钳制、零位移 setter、卸载恢复和后续属性包装者兼容。

# 第 7 步：EdgeHub 经中转和打洞（2026-11-05，本机部分）

核心指纹 `212dd5251a71`，核心的模拟结果见 [`packages/agent-net-core/sim/results/2026-11-05-traversal`](../../../../packages/agent-net-core/sim/results/2026-11-05-traversal/README.md)。

全部在一台 Windows 电脑（x64，Node 24.19.0）的本机回环上跑，中转是本机起的自建中转内核（`packages/device-link-relay`，打开 agent-net 转发），
设备经正式的加入流程登记。所有 EdgeHub 和它们的 DeviceLinkClient 在同一个 Node 进程。**不是真实网络指标，也没有真的 NAT。**

## 做了什么

- `relay-client.ts`：经中转转发数据报的两种方式。
  - 专用通道：自建中转的 `/api/device-link/agent-net`（`agent-net-relay-v1`），二进制帧。
  - push 夹带：塞进现有中转的 `push` 消息（channel `agent-net:datagrams`，内容 base64）。不用改服务端，官方中转和已部署的自建中转都能用。
  - 两种都把同一轮事件循环里发往同一台设备的数据报攒成一帧。
- `transport-core.ts`：有中转时先经中转连上（专用通道代价 1，push 夹带代价 2，UDP 0），在加密连接里另开一条控制流交换候选地址，
  两端同时验证对方的；还在走中转时每隔一阵再验证一轮。经中转来的握手要核对：中转按凭证认定的设备号必须是名册里登记这把公钥的设备。
- `stun.ts`：查自己公网地址的最小 STUN 客户端，从 agent-net 的同一个 UDP 端口发出，回复由驱动截下。
- `relay-fixture.ts`：本机起中转、走加入流程登记设备。

## 结果

`poc-edgehub.ts` 四种方式轮流各跑 3 轮，12 次全部 12/12，附加检查也都通过。原始输出见 [`rounds.txt`](rounds.txt)。

| 方式 | invoke p50（最小 / 中位 / 最大） | 3 MiB 结果 | 附加检查 |
| --- | --- | --- | --- |
| core：只走 UDP | 0.39 / 0.47 / 0.83 毫秒 | 271 / 286 / 529 毫秒 | 没有明文 |
| relay：UDP 全被挡，经专用通道 | 0.62 / 0.66 / 1.7 毫秒 | 295 / 611 / 906 毫秒 | 没有明文；3473–4084 个包全经中转，UDP 0 个 |
| push：UDP 全被挡，经 push 夹带 | 0.59 / 0.63 / 0.63 毫秒 | 287 / 292 / 348 毫秒 | 没有明文；3482–3938 个包全经中转，UDP 0 个 |
| punch：先经专用通道连上，再打洞 | 0.40 / 0.41 / 0.45 毫秒 | 230 / 237 / 241 毫秒 | 没有明文；26–29 个包经中转，其余 3404–3492 个直连 |

relay 方式有两轮 3 MiB 明显慢。怀疑是专用通道在接收方积压超过 1 MiB 时丢包，把上限临时改成 16 MiB 轮流各跑 4 次：
1 MiB 是 268–306 毫秒，16 MiB 是 278–801 毫秒，慢的那次两边都会出现，不是这个上限造成的，更像是这台电脑同时在跑别的任务。上限保留 1 MiB。

punch 方式下打洞要一个中转往返交换地址、一个直连往返验证，之后和 core 一样快；重连检查之后经中转重新连上，几毫秒内又换回直连。

`poc-core-driver.ts` 跑 2 次都是 6/6（[`driver.txt`](driver.txt)），加了通道和主动验证以后驱动原来的行为没变。

## 真实 STUN

从这台电脑的 agent-net 端口问公共 STUN 服务器：Cloudflare 和 Google 看到的外部地址相同、端口和本机端口一样；
国内的一台看到的是另一个 IP、另一个端口（国内外流量走了不同的出口）。所以候选地址要问几台、去重后都给对端，不能只问一台。
地址没有记进仓库。

## 真实网络（2026-11-05 晚）

用户同意后，在 `xdt-server`（上海的云主机）上临时起了一个测试中转（打开 agent-net 转发），放在已有的 Nginx 后面，
只认测试主机名 `agent-net-test.invalid`，用 3 天到期的自签证书，正式中转不受影响。测试程序是 `real/`：
`relay-server.ts` 在服务器上起中转、走加入流程登记设备，`peer.ts` 是两端（先经中转连上，再交换候选地址打洞，量往返和 16 MiB 上下行），
`bundle.mjs` 打成单文件放到别的机器上跑。原始输出在 [`real/`](real)，不含 IP 地址。
测完已删掉服务器上的测试中转、Nginx 测试站点和证书、临时用户、iptables 规则和临时文件，Nginx 平滑重载，其他站点照常响应；
各台测试机上的测试目录也都删了。

这台云主机的出口限速约 5.8 Mbit/s（curl 直接下载 20 MB 量得 0.70–0.73 MB/s），所以“服务器发往这台电脑”的方向都卡在这里。

| 场景 | 结果 |
| --- | --- |

**真实网络查出的问题**：第一次连服务器时一直没换到直连。服务器装了 Docker，有 8 个内网地址，加上查到的公网地址一共 9 个候选，
对端只收前 8 个，公网地址正好被截掉；另外核心一次最多同时验证 4 条路径，一下子验 8 个时前面的会被后面的挤掉。
改成公网地址排在前面、每轮最多验 4 个、下一轮接着验后面的，就通了（改之前的结果见 `real/server-public-before-fix-*.json`）。
同一天先确认过服务器收得到这台电脑发来的 UDP，排除了云主机安全组。

**两边都在 NAT 后面、隔着公网打洞**测的是公司 ↔ 家庭宽带这一种组合，打不通，原因在公司这一边。
两边用同一段探测程序，从一个本地端口依次问 4 台 STUN（3 台国内、1 台国外），连跑两次：

- 公司出口是对称型 NAT：3 台国内服务器看到同一个 IP、3 个毫不相干的端口，国外那台看到的又是另一个 IP；
  换一个本地端口再问，每台服务器那边的端口各加 1。对端没法知道公司 NAT 给它分的是哪个端口。
- 家庭宽带是端点无关映射（锥形）：4 台服务器看到的都是同一个 IP 和端口，两次分到的外部端口只差 2。
  过滤方式（全锥形、受限锥形还是端口受限锥形）普通 STUN 测不出来。
- 公司这台电脑没有全局 IPv6，家里的 MacBook Pro 有，所以 IPv6 这条路这次也用不上。

模拟器里对称型对全锥形、受限锥形能打通，对端口受限锥形一直走中转。真实网络一直走中转，家里的路由器多半是端口受限锥形，
和模拟器的预测一致；打不通时留在中转上、数据完整、不来回切，这部分是对的。想在这种组合下直连，要么做端口预测或多端口探测，
要么两边都有 IPv6，这一步都没做。探测结果里的 IP 和端口只在对话里看过，没有记进仓库。

MacBook Pro 上开着 Surge：只开系统代理、关掉增强模式后默认路由走 Wi-Fi，测试程序的 UDP 不经过 Surge。
整个关掉 Surge 时那台电脑上的 Cindy 反复掉线，派不了活，所以测试时保留了系统代理。

另外两处测试程序的设置要和产品一致：本机回环用的请求超时 4 秒、可靠层重发间隔 0.1 秒，经慢线路时上层会不停重发，
把线路堵死（第一次经 443 只过 8/12）；经真实中转时改用产品默认的 30 秒和 2 秒以后 12/12。产品代码没改。

## 没有覆盖

- 两边都在 NAT 后面、隔着公网的打洞只测了公司对称型 NAT ↔ 家庭宽带一种组合（打不通，走中转）；两个家庭宽带之间、手机网络、IPv6 直连还没测，端口预测没做。
- 中转上的速度：本机回环和这台限速的云主机都看不出 push 夹带比专用通道多出的字节和中转的 CPU。
- 官方中转：push 夹带只在本机的自建中转内核上跑过，官方中转的转发和限流没有测。
- EdgeHub 和设备原有的上游连接合并：这里 EdgeHub 自己连中转，DeviceLinkClient 不连中转。

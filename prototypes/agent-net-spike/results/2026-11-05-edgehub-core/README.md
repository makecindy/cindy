# 第 6 步：EdgeHub 跑在自研传输上（2026-11-05）

核心指纹 `9e35faa2344d2fe65ab2d84321cf38c8a97277c7`（`shasum src/*.rs | shasum`，按 LF 内容算）。
和上一轮（`8e8947f3a654`）相比只多了 `src/endpoint.rs` 和 `lib.rs` 里的导出，连接、加密、拥塞控制的代码没动，线格式不变。

全部在一台 Windows 电脑（Windows 10.0.26200，x64，Node 24.19.0）的本机回环上跑，**不是真实网络指标**。
所有 EdgeHub 和它们的 DeviceLinkClient 跑在同一个 Node 进程、同一个事件循环里，加解密和收发两端都挤在一个线程上。

## 做了什么

- 按连接号分发、给来源地址编路径号这部分从真机 UDP 驱动挪进核心（`Endpoint`），真机驱动和 Node 驱动共用。逻辑原样搬过去，
  只多了一条：连接号不取 0，接口里拿 0 表示“没有连接”。
- `packages/agent-net-core/wasm`：核心编成 WebAssembly（276 KB），按 C 调用约定手写接口，不用 wasm-bindgen，只用标准库。
  加密算法从宿主导入，长期私钥不进 WebAssembly。
- `packages/agent-net-core/wasm/node.mts`：Node 驱动，UDP、时钟、加密都用 Node 自带模块。
- `prototypes/agent-net-spike`：EdgeHub 改成可以换传输，默认自研、QUIC 留作对照，两种传输跑同一套 12 项检查（断言没改，
  三项检查名去掉了“QUIC”）。自研传输另加一项附加检查：抓到的包里没有业务明文。

## 结果

`poc-edgehub.ts`，自研和 QUIC 轮流各跑 6 轮，12 次全部 12/12 通过，自研 6 次附加检查也都通过。原始输出见 [`rounds.txt`](rounds.txt)。

| | 自研（中位数，范围） | QUIC（中位数，范围） |
| --- | ---: | ---: |
| invoke 往返 p50 | 0.44 ms（0.37–0.46） | 0.76 ms（0.54–0.89） |
| invoke 往返 p95 | 0.92 ms（0.80–1.09） | 1.26 ms（0.85–1.51） |
| 3 MiB 结果送达 | 221 ms（193–274） | 620 ms（478–685） |
| 一台控制端静默时另一台的 invoke p50 | 1.06 ms（0.88–1.22） | 1.35 ms（1.09–1.64） |

每一轮自研都比 QUIC 快。QUIC 走的是 iroh 官方 Node 绑定，收发缓冲是 `Array<number>`，第 0 阶段就量出比原生慢 17 倍，
所以这张表比的是“自研 + Node 驱动”和“iroh 官方绑定”，不是两种协议本身。

为了确认 EdgeHub 改成可换传输没有拖慢 QUIC、让对比偏向自研，把第 0 阶段的原版和改过的 QUIC 版轮流各跑 4 轮
（[`quic-original-vs-refactored.txt`](quic-original-vs-refactored.txt)）：原版 invoke p50 0.65–0.87 ms、3 MiB 476–704 ms，
改过的 0.57–1.05 ms、523–804 ms，范围重叠，没有看出差别。第 0 阶段报告里的 0.41 ms、437 ms 是单次、偏快的一次。

附加检查抓了全部 EdgeHub 发出的数据报（[`edgehub-core-final.txt`](edgehub-core-final.txt)：3425 个、3.4 MiB；轮流的 6 轮里收发各记了一次，约 6900 个），
找设备号、通道名、`"kind"` 字段名和 3 MiB 结果里的一段内容，一个都没有。

`poc-core-driver.ts` 检查 EdgeHub 碰不到的驱动部分，跑 3 次都是 6/6（[`driver.txt`](driver.txt)）：

| 检查 | 结果 |
| --- | --- |
| 32 MiB 完整送达、线上没有明文 | 42.7–47.8 MiB/s（收发两端同一个线程） |
| IPv6 回环握手和收发 | 通过，对端地址按 IPv6 编解码 |
| 传输途中换本地端口，告诉 / 不告诉连接 | 16 MiB 都完整，服务端换到新端口，用时 293–325 ms |
| 接受规则说不 | 客户端 1 秒内建不起连接，服务端一个包都没回 |
| 结束流后等确认再关 | 不等握手就要求关，对端照样收到完整的 4 MiB 和结束 |

## 做的时候查出的问题

| 问题 | 处理 |
| --- | --- |
| Windows 上 Node 的 `setTimeout(1)` 实际要等约 15 毫秒（系统时钟节拍） | 短于一个节拍的等待改成每轮事件循环看一次时间，长的提前一个节拍醒来。改之前 8 MiB 只有 13.6 MiB/s |
| Node 每次加密都用原始字节作密钥时一个包要 20 微秒 | 对称密钥导入成 `KeyObject`，降到 4 微秒，吞吐再翻一倍多。代价是密钥字节要等垃圾回收才释放，不能丢弃时立即清零 |
| 结束流后马上要求“确认后再关”，结束标记还没交给核心，驱动就判断“都确认了”，连接立刻关掉，对端收不到结束 | 判断时把还没交给核心的结束标记也算上。重连检查因此失败过一次 |
| 被拒绝的一方按重传节奏重发同一个握手请求，EdgeHub 每次都记一次拒绝 | EdgeHub 的自研传输对同一来源、同一身份 30 秒内只问一次名册。驱动自己的计数仍按请求算（被拒绝的一方 1 秒内约发 3 个） |

剖析一次 32 MiB 传输（Node `--cpu-prof`）：加解密约占采样的 18%，UDP 发送约 10%，WebAssembly 里的核心只占几个百分点；
其余主要是测试自己的哈希、抓包和 tsx 加载。

## 没有覆盖

- 两台真机、真实网络、丢包和抖动下的 EdgeHub；没有经 Electron `utilityProcess` 跑。
- 驱动的单线程上限：加解密和收发都在 Node 主线程，局域网满速时 CPU 会先到顶，还没测。
- 没有上游 WSS 合并、加密封装回退，名册还是写死的；打洞和中继是第 7 步。
- 协议里没有关闭通知：对端进程直接退出时，另一端要等核心判死（有数据在途时 30 秒，空闲时靠 15 秒一次的探测）才知道。

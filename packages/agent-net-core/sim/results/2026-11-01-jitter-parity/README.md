# 为抖动多发校验：逐轮试、一排队就收

核心指纹 `d949e2e252403c8daf70ab9f51cda69d11c0b8a4`，逐文件 SHA-256 见 `source-sha256.json`。
相对上一版 `78ac8ec71064` 改 `congestion.rs`、`connection.rs`，完整差异见 `changes-from-78ac8ec71064.patch`。
帧格式、策略 API、测试断言都不变。KCP 对照、网络模型、目标口径同上一轮。

## 先找到的原因

家宽、5G 这类路径上，窗口要等最慢的那个包确认才能往前走：每个包的抖动互不相关，一个窗口里总有几个包晚到好几毫秒。
KCP 的 FEC 配置靠校验把晚到的包提前算出来，所以快；家宽去掉抖动以后我们反而比 KCP 快。

难点在于被窗口限住时测不出路径还剩多少余量：带宽样本只到窗口的速率。余量够的路径（家宽、5G）多发校验能快 3%–5%，
余量不够的路径（4G、校园网、千兆、高铁）校验会挤掉数据。试过连着发几个校验包、按确认间隔测余量，
但每个包的抖动互不相关，几个包的到达间隔被打乱，测出来比真实值低一个数量级。

## 改动

**逐轮试着为抖动多发校验，一排队就收。**

- 统计“被抖动拖晚”的包：后发的包已经确认了，自己比最小往返晚到了十六分之一往返以上。
- 窗口确实卡住、没有限速、往返在 10 毫秒以上时，每轮把多发的校验比例加 5%，最多加到被抖动拖晚的比例（校验最多和数据一样多）。
  “窗口确实卡住”按平均往返算：抖动大时窗口按平均往返周转。
- 一轮里最小的 RTT 比最小往返高出往返的十六分之一（至少 0.2 毫秒），说明校验把瓶颈顶出了队列：比例减半，
  上限压到这次的四分之三，之后每轮放开 0.2%。
- 这部分校验按比例直接给，不再乘丢包修复用的余量。
- 往返短于 10 毫秒时不加：局域网一类的路径上晚到的包只让窗口多等零点几毫秒，千兆上校验反而挤掉了不多的余量。

| Fast / Lean 未达到目标的组合 | 9 / 56 | 8 / 56 |
| Auto 家宽窗口 128（KCP 极速+FEC5/5 1311 ms，额外字节 204%） | 1357 ms / 10.4% | 1321 ms / 85.1% |
| Auto 5G 窗口 128（KCP 调优+FEC 2417 ms，额外字节 132%） | 2603 ms / 11.6% | 2482 ms / 48.6% |

`validation.json` 全部退出码为 0：`AGENT_NET_SEEDS=10000` 的 workspace 测试 43 通过、1 个 profiling 按设计忽略；
1200000 起新种子段的默认策略与三策略矩阵各 1000 个种子通过。没有改动任何断言。

## 未采用的方案

- **把抖动晚到的比例算进空洞、再乘丢包修复用的余量**：一点点抖动就变成每个数据包配一个校验，家宽、5G 变快，但 4G +11%–14%、千兆 116 → 136 ms、校园网 +8%、高铁 +14%。
- **按“加一档后数据送得更快”爬坡**、**先关一段再开一段比较**：每段的送达速率波动比收益还大，判断经常反，50Mbit、手机、校园网都变慢。
- **成组校验（每 10 个分片发 3 个，像 KCP 的 FEC）**：在测不出余量的前提下只能对少数路径开，丢 5%、跨境反而变慢。
- **爬得更快（每轮加 12.5%–25%）、还没顶起过队列时直接用到满**：5G 最好到 2458 ms，但高铁、校园网变慢。
- **判断排队的余量按抖动放宽**：5G 校验多了，用时不变。

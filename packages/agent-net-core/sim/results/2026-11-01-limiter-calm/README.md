# 限速路径的降速阶段与确认区间

核心指纹 `a91967c9b36a073f67e70d42f0d629e86b253fbe`，逐文件 SHA-256 见 `source-sha256.json`。
相对上一版 `8ecfab4f27c5` 改 `congestion.rs`、`connection.rs`、`wire.rs`，完整差异见 `changes-from-8ecfab4f27c5.patch`。
确认帧格式不变（只是少带旧区间），策略 API 与测试断言都不变。KCP 对照、网络模型、目标口径同上一轮。

## 改动

1. **限速路径上，降速阶段不再超过路径真正送得出去的速率。** 上一轮记下的已知问题：令牌桶放行突发时，
   启动测到的带宽能高出真实上限好几倍，按它打折的“降速”仍远超上限，限速丢包被当成随机丢包；
   随机丢包率一高，补偿后发得更快，降速阶段丢得更多，估计值越滚越高，门槛跟着抬高，再也认不出上限。
   现在看最近 4 轮的平均送达速率：它既低于带宽估计的一半、又低于窗口能送的速率的一半时，说明卡住送达的是路径上的上限，
   这时降速阶段不超过带宽估计的一半，滚雪球断开。窗口受限的长往返路径上，启动测到的速率常比窗口能送的高好几倍，
   那不是限速，不压；随机丢包率已经测稳的窗口受限阶段也不压。
2. **确认帧只带最近有变化的旧区间。** 一个区间最后一次变化以后，再跟着 32 个确认发出去就不再带。
   以前随机丢包的路径上每个确认都带满 8 个旧区间，慢速链路上光确认就占流量约 4%。
   试过 8 个：跨境乱序路径上确认在回程也会丢、会乱序，留得太短会让发送方把已收到的包当成丢了，改为 32。

| 项目 | 上一版 | 本版 |
| --- | --- | --- |
| 结束时随机丢包率估计 ≥ 5% 的种子 | 5 / 24（最高 15.4%） | 2 / 24（最高 6.6%） |
| 平均额外流量 | 21.6% | 16.3% |

### 固定矩阵（32 场景 × 两种窗口 × 16 种子，`simulation-*.txt`）

| 项目 | 上一版 | 本版 |
| --- | --- | --- |
| Auto 未达到“最快 KCP”目标的组合 | 16 / 64 | 16 / 64 |
| Fast / Lean 未达到目标的组合 | 10 / 56 | 10 / 56 |
| Auto 小队列 / 低速额外字节 | 10.4% / 10.0% | 9.1% / 7.9% |
| Auto 实测下载（令牌桶）窗口 128 | 11760 ms / 29.6% | 11548 ms / 21.2% |
| 高铁交互 p95 / p99 | 360.4 / 665.4 ms | 356.4 / 668.4 ms |
| 额外字节平均变化（Auto / Fast / Lean） | — | −0.6 / −2.2 / −0.7 个百分点 |
| 交互流量平均变化（Auto / Fast / Lean） | — | −4.6% / −6.6% / −6.2% |

用时变化在这套 16 种子上：Auto 平均 +0.2%，Fast −0.0%，Lean +0.1%。变慢最多的是 Auto 窗口 1024 跨境（2765 → 3028 ms，+9.5%），
Lean 丢 30% 窗口 128（+3.6%）、丢 5% 窗口 1024（+2.9%），Fast 实测上传窗口 1024（+2.3%）。

跨境窗口 1024 这一项单个种子的用时在 2.1–4.3 秒之间来回跳，16 个种子的平均值误差约 4%。
另用 100–163 共 64 个新种子、只跑批量传输复核（`extra-seeds-{auto,lean,fast}-{before,after}.txt`）：

| 策略 | 平均用时变化 | 最差 | 最好 | 平均额外字节 |
| --- | --- | --- | --- | --- |
| Auto | −0.06% | 山区窗口 128 +1.3% | 跨境窗口 1024 −2.6% | −1.0 个百分点 |
| Lean | +0.13% | 实测上传窗口 128、丢 30% 窗口 1024 各 +1.3% | 丢 15% 窗口 128 −2.0% | −0.9 个百分点 |

这批复核里跨境窗口 1024 是变快的，所以判断本版对它没有实质影响，但固定矩阵上的数字确实变差了，如实列出。

## 可靠性

`validation.json` 全部退出码为 0：`AGENT_NET_SEEDS=10000` 的 workspace 测试 43 通过、1 个 profiling 按设计忽略；
700000 起新种子段的默认策略与三策略矩阵各 1000 个种子通过。没有改动任何断言。

## 未采用的方案

- 只用上一轮的平均送达速率压降速阶段（不看窗口速率、不设下限）：令牌桶种子全部干净、平均额外流量 14.5%，
  但窗口 1024 长往返路径启动后的第一个降速阶段被压得太低，`first_flight_measures_the_path` 超出上限。
  加上“不低于带宽估计一半”的下限后通过测试，但跨境窗口 128 每个种子都慢约 40 ms：启动测到的速率比窗口能送的高三倍，
  被误当成限速。加上窗口速率的条件后消除。
- 降速阶段只取后半段当低速样本（前半段还在排空上一段加速堆出的队列）：小队列额外字节 9.1% → 8.3%，
  但令牌桶路径平均额外流量 16.3% → 20.9%，未采用。
- 用相邻两段“发送速率变了、送达速率不变”直接认定限速：令牌桶上发送速率每段相差不到 30%，从不触发。

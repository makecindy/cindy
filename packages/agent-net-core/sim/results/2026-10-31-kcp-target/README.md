# 对齐“最快 KCP 配置”目标的一轮优化

核心指纹 `8b4089ebf1739ab61b7ca78ef526b87b2f1f3894`，逐文件 SHA-256 见 `source-sha256.json`。
相对上一版 `a0172b1d7730` 改 `connection.rs`、`congestion.rs`、`rtt.rs`，并按用户决定调整一条测试上限；
完整差异见 `changes-from-a0172b1d7730.patch`。线格式与策略 API 不变。KCP 对照与网络模型同上一轮。

## 目标口径（2026-10-31 用户确认）

KCP 的最快配置与最省流量配置互相矛盾：最省流量的“KCP 普通”在多数有损路径上比其它配置慢几十倍，
单一实现无法同时打败两者。本轮目标改为：每个场景与该场景里**用时最短的 KCP 配置**比较，
agent-net 用时不慢（1% 内算平）、额外协议字节不多，交互 p50 / p95 / p99 不高于 KCP 各配置的最好值。
检查脚本 `kcp-fastest-target.py`，结果 `kcp-fastest-{auto,fast,lean}.txt`。

用户同时选择速度优先：窗口受限且路径还有余量时，默认策略可以像 KCP 的 FEC 配置一样多发校验，
流量仍须少于对应的最快 KCP 配置；干净网络不多花一个字节的规则不变。

## 改动

1. **窗口受限、路径有余量时，Auto 按速度优先的余量发校验。** 只在已过启动阶段、测到的路径速率至少是窗口速率的
   21/20、没有排队、并且窗口不超过校验覆盖范围（64 个分片）的 4 倍时启用。
   - 路径速率只略高于窗口时（高铁 15 Mbit），校验会挤掉数据、堆起队列：不加限制时高铁从 6870 ms 变为 10240 ms。
   - 窗口 1024 的长往返路径上，一个校验包只覆盖少量空洞，多发不提速反而稍慢，所以按窗口大小限制。
2. **长断网按时间判断，不按超时次数。** 2 秒内完全没有回应才放慢重试、收紧拥塞窗口；更短的中断保持较密的重试，
   并允许在途约 4 倍最小窗口，确认方向断开时新消息仍能发出。还没测到 RTT 时（第一批确认还在路上）照旧按长断网处理：
   否则卫星链路的启动超时风暴会把带宽估计压到约 10 KB/s 并卡死（Fast 卫星 32 s 曾变为 103 s，已修复）。
3. 测试 `parity_share_stays_close_to_the_loss_rate` 的窗口 128、丢 5% 一项：上限由 2190 ms / 28% 改为
   2110 ms / 130%（同条件 KCP 最快为 2036 ms / 160%，调优+FEC 为 2116 ms）。这是用户的产品决定，不是为让测试通过放宽。

## 结果

`simulation-{auto,lean,fast}.txt` 为全部 32 场景 × 两种窗口 × 16 种子；`comparison.md` 为逐项包络比较。

| 项目 | 上一版 | 本版 |
| --- | --- | --- |
| Auto 未达到“最快 KCP”目标的组合 | 21 / 64 | 18 / 64 |
| Fast 未达到目标的组合 | 12 / 64 | 12 / 64 |
| Auto 窗口 128 用时胜 / 平 / 负（包络） | 17 / 2 / 13 | 17 / 5 / 10 |
| Auto 窗口 1024 用时 | 32 / 0 / 0 | 32 / 0 / 0 |
| Auto 交互 p95 / p99 落后项 | 2 / 1 | 0 / 0 |

三种策略的胜平负状态共变化 17 项，全部变好、没有变差：

- 地铁（每 5 秒断 1 秒）交互 p95：Auto 1342 → 1138 ms，p99：2058 → 1812 ms，均快于 KCP 最好值 1252 / 1971 ms；
  Fast、Lean 同样由负转胜。
- 窗口 128 用时由负转平：跨境（9987 → 9606 ms）、留出欧美（10381 → 10165 ms）、突发丢包（2259 → 2229 ms）。
- 留出高铁交互 p95 由负转平（358.4 → 352.9 ms）。

代价：窗口 128 有损路径上 Auto 的额外字节明显增加，例如丢 5% 由 20.3% 变为 96.2%、乱序 10% 由 15.1% 变为 91.6%，
仍少于同场景最快的 KCP 配置（159.8% / 162.4%）。因此对“KCP 冲刷”等不带 FEC、但更慢的配置，
部分场景由“两项都不差”变为“更快但流量更多”（`dominance-*.md`）。两种窗口共 64 个组合里，
仍然**没有任何一种 KCP 配置在用时和额外字节两项上都不差于 Auto**。

## 可靠性

`validation.json` 全部退出码为 0：`AGENT_NET_SEEDS=10000` 的 workspace 测试 43 通过、1 个 profiling 按设计忽略；
500000 起新种子段的默认策略与三策略矩阵各 1000 个种子通过。除上面这一项按产品决定调整的上限外，没有改动任何断言。

## 仍未达标（Auto，18 / 64，见 `kcp-fastest-auto.txt`）

- 窗口 128 用时 10 项：丢包 1%、丢包 5%、乱序 10%、千兆、卫星、家宽、5G、令牌桶、跨洋、高延迟，差距 1.1%–7.8%。
  主要差在启动阶段：KCP 的 FEC 从第一个包就开着，Auto 按规则在确认丢包前不发校验。
  本轮试过只加快第一批包的发送节奏，窗口 128 丢 5% 可到 2041 ms，但窗口 1024 高延迟变慢 27%–33%、限速路径变差，未采用。
- 窄带小队列（低速 1 Mbit、小队列 5 Mbit）额外字节 4 项：这两条路径上最快的 KCP 是“KCP 普通”
  （小队列 101995 ms，其余配置传不完），Auto 用时 14449 ms 但额外字节 10.4% 对 5.8%，来自探测带宽时挤爆浅队列。
- 地铁、高铁交互 p50 4 项：36.4 对 35.7 ms、47.2 对 46.2 ms。
- 公网未在本版重测。

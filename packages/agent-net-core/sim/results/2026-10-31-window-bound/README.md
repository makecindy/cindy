## 定位方法

先用临时插桩测量窗口受限时时间花在哪里，插桩不在本版源码中：

- 每个分片从首发到 `una` 越过它，占用窗口多久；
- 发送端没在发包时，是被 `una` 窗口、在途字节、发送节奏还是对端窗口挡住。

窗口 128 的丢 1%、5%、家宽、跨洋等场景里，在途字节上限挡住发送 12%–40% 的时间，平均在途分片约 120 个而非 128 个。
丢包率估计在两次丢包之间会降到门槛以下：家宽场景约四分之一的新分片发出时校验是关的，下一个丢包只能等重传。

## 采用的三项改动

1. **窗口受限时放宽在途字节上限。** 校验包、副本和等待校验结果的丢包占在途字节却不占窗口，
   上限卡在一个窗口时，丢包越多窗口空得越多。只在窗口受限、离路径容量还远、并且距上次超时或断网
   已连续两轮正常时放宽到两倍：断网刚恢复时窗口里全是丢包，看起来也像窗口受限。
2. **确认丢过包后 5 秒内保持最低校验比例。** 判丢两个往返后仍没有确认才算确认丢包，乱序不触发。
   干净路径不受影响，`clean_paths_carry_no_redundancy` 原样通过。
3. **断网期间的丢包不再当作限速证据。** 一段统计里确认中断超过 3 个往返（至少 250 ms），这段不用来判断限速。
   限速器每个往返总会放行一部分，确认不会整段中断。改动 1 之后，高铁种子 9 曾因断网被误判为限速，
   以约 0.3–0.6 MB/s 跑了十几秒（17959 ms）；修复后为 9290 ms。上一版有同样的弱点，只是该种子没有触发。

## 试过但未采用

同一模拟器、每场景 16 个种子的快速对照，数字为平均用时或额外协议字节。

| 方案 | 结果 | 未采用原因 |
| --- | --- | --- |
| Auto 批量传输启动即带校验，直到首次确认丢包 | 窗口 128：丢包 1% 2062 ms、家宽 1343 ms、跨洋 12450 ms；无丢包额外字节 2.0% → 3.4% | 违反“干净路径不多花一个字节”的规则，三条既有测试失败；不放宽测试 |
| 窗口受限时节奏增益 2× 提到 4× 或 8× | 窗口 128 小幅改善 | 窗口 1024 卫星 7363 → 8003 ms、跨境 2753 → 3150 ms |
| 窗口受限时取消节奏，或放宽允许的突发 | 窗口 128 没有明显改善 | 窗口 1024 跨境、卫星变慢 |
| Auto 初始窗口 64 → 128 | 无丢包 1991 → 1984 ms | 窗口 128 卫星 31111 → 103753 ms，限速场景变差 |
| 降速阶段一开始就用 0.9 倍 | 丢包 1% 2072 → 2058 ms | 实测下载与窗口 128 高铁变差 |
| 校验覆盖缩短为校验间隔的 2–5 倍 | 家宽不变 | 丢包 5%–30% 明显变慢 |
| 固定校验密度，每 1–8 个分片一个 | 丢包 1% 稳定在约 2070 ms，家宽约 1420–1430 ms | 剩余差距不由校验密度决定，只增加流量 |

## 可靠性

`validation.json` 记录命令、退出码与耗时，全部退出码为 0：

- `check.txt`：`cargo check --profile sim --workspace --all-targets`。
- `tests.txt`：`AGENT_NET_SEEDS=10000` 的 workspace 测试，43 通过、1 个 profiling 按设计忽略；
  含默认策略 10000 + 10 个历史失败种子、三种策略各 1000 + 10 个种子与全部固定回归。
- `fresh-*.txt`：400000 起的新种子段，默认策略 1000 个种子、三策略矩阵各 1000 个种子。
- 没有放宽任何断言。`clean_paths_carry_no_redundancy`、`initial_timeout_keeps_the_first_flight_available_for_measurement`
  与 `rate_limited_loss_is_not_read_as_random` 正是否决“启动即带校验”的依据。

百万级种子与 `sim/mutants.py` 变异测试未在本版重跑。

## 仍落后的地方

- 窗口 128 的 13 个用时落后项，KCP 最快值都来自带 FEC 的配置，额外字节 60%–260%；Auto 约 10%–30%。
  窗口受限时提速主要靠多发校验，属于速度与流量的取舍；Fast 在这些场景已领先或接近。
- 抖动与乱序：去掉丢包后，5G 场景 Auto 仍慢于不带 FEC 的 KCP 极速（2519 对 2461 ms），原因尚未查清，
  节奏与校验密度实验均未改善。
- 启动阶段第一个丢包仍要等一个往返；在不违反干净路径规则的前提下暂无办法。
- 公网上传仍略慢于两种 FEC 配置（字节只有它们的约 1/4 到 1/8），模拟器里的“实测路径 上传”却领先。
  上一轮公网上传的发送端统计只有 109 个校验包、1374 个重传分片，推测真实路径成片丢包让校验关闭，
  而模拟器把这条路径建成独立随机丢包；本轮客户端没有输出发送端统计，**这个原因尚未验证**，
  需要先在公网记录丢包分布再补模型。

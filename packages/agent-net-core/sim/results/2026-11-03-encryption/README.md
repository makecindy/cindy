# 加密握手（第 4 步）

核心指纹 `13999ffa19fb905a99a209be3c311c5789716b8c`（`shasum src/*.rs | shasum`），逐文件 SHA-256 见 `source-sha256.json`。
和上一步相比，`congestion.rs`、`parity.rs`、`rtt.rs`、`stream.rs`、`wire.rs` 逐字节相同；`connection.rs` 只加了给加密层用的入口，
`lib.rs` 加了导出；新增 `crypto.rs`、`noise.rs`、`secure.rs`。

过关标准：抓包无明文，防篡改、防重放，有前向保密。

## 做了什么

`SecureConnection` 套在原来的 `Connection` 外面，用法一样，多一步握手。可靠传输、多路流、拥塞控制都不改。

| 部分 | 做法和原因 |
| --- | --- |
| 握手 | Noise IK，按规范第 34 版自己实现（`noise.rs`）。一个往返完成，发起方的身份加密传输，被动监听看不出是谁在连。选 IK 是因为 agent-net 的节点事先知道对方的公钥 |
| 算法 | 调用方实现 `Crypto` trait 传入：X25519、AES-256-GCM 或 ChaCha20-Poly1305、SHA-256 或 BLAKE2s。核心仍然零依赖，也不接触长期私钥，产品里用各平台系统自带的实现 |
| 逐包加密 | `[包头 3][密文][标签 16]`。nonce 是完整包号，包头不加密但参与认证。可靠层本来就保证包号永不重复（重传也用新包号），所以不需要额外的计数器 |
| 防重放 | 4096 个包号的窗口，**认证通过后才记**，伪造的包推不动窗口 |
| 换密钥 | 包号每过 2^20 个，两个方向各自按 Noise `Rekey` 推导新密钥，旧的丢掉。QUIC 给 AES-GCM 定的上限是每个密钥 2^23 个包，长时间传大文件会撞上。按包号换，线上不多一个字节，两端不用协调；保留上一个密钥给晚到的包 |
| 不放大流量 | 请求填满到 `max_packet_size`，回复和请求一样长；响应方在收到发起方第一个有效数据包之前，每份请求只回一个回复，不发数据。否则别人重放一份录下的请求、伪造来源地址，响应方会把一整个初始窗口的数据打到受害者那里 |
| 双方确认 | 发起方收到回复后马上发一个探测包。不发的话，发起方没数据可发时响应方一直确认不了，30 秒后超时 |
| 同时发起 | 两端同时向对方发起时，公钥大的一方继续当发起方。被忽略的那个请求晚到时识别为重复，不会被当成新连接 |
| 伪造次数上限 | 认证失败累计 2^36 个包就放弃连接，这是 QUIC 给 ChaCha20-Poly1305 定的完整性上限 |

没做的，以及原因：

- **0-RTT**：方案里写明不做。每条连接比明文多一个往返才开始传数据。
- **请求的防重放**：IK 第一条消息本身挡不住重放，响应方可以被录下的请求骗着回一个回复，但不会建成连接、不会发数据，到期放弃。要拒绝的话由上层在附带数据里放时间戳（WireGuard 的做法）。
- **抗伪造请求的 CPU 消耗**：每份请求要做两次 DH。限流和 cookie 机制留到第 5 步接真实 UDP 时做。
- **握手里协商窗口、把握手测出的 RTT 交给拥塞控制**：都没做，见核心 README 的已知限制。

## 过关标准对照（`sim/tests/secure.rs`）

| 标准 | 用例 | 断言 |
| --- | --- | --- |
| 握手按规范实现 | `handshake_matches_the_noise_test_vectors` | 请求、回复、握手哈希、传输消息和 cacophony、snow 两个独立实现的官方向量逐字节一致，AES-GCM 和 ChaCha20-Poly1305 都覆盖 |
| 抓包无明文 | `nothing_readable_on_the_wire` | 双向数据、握手附带的数据、两端的长期公钥都不出现在任何一个线上包里 |
| 防篡改 | `tampered_packets_are_rejected_without_side_effects` | 数据包**第一次送达之前**，先把改任意一位、截短、加长的版本喂给对端（11000 多个），全被拒，可靠层没收到，原包随后照常被接受 |
| | `tampered_handshakes_are_rejected_and_recover` | 改过的请求解不开；改过的回复被丢弃，重发后握手照常完成 |
| 防重放 | `replayed_packets_are_rejected` | 传完后把录下的每个包再发一遍，全部按重放拒绝，不多交付一个字节，之后的新数据照常 |
| | `replayed_initiations_do_not_amplify`、`responses_never_outgrow_requests` | 重放的请求每份最多换来一个同样大的回复，发出的字节不超过收到的；伪造的数据包不能让响应方开始发数据 |
| 前向保密 | `stolen_static_keys_do_not_decrypt_recorded_traffic` | 两端的一次性私钥在握手后都已销毁；拿到两端长期私钥和完整抓包，也解不开录下的数据包 |
| 换密钥 | `keys_rotate_across_the_packet_number_boundary` | 跨过 2^20 边界时两个方向各换一次，边界上的包故意乱序，6 MB、4600 多个包，没有一个真包被拒 |
| 其他 | `low_order_public_keys_are_rejected`、`wrong_key_or_prologue_is_rejected`、`simultaneous_open_settles_on_one_handshake`、`responder_can_talk_first`、`handshake_gives_up_when_nobody_answers` | 无效公钥、错的公钥或前言、同时发起、响应方先说话、对端不在 |
| 各种网络下照样传完 | `encrypted_seeds_deliver_intact_streams` | 可靠性测试的随机网络全部加密跑一遍：数据完整有序、端点不空转。两成种子的包号从 2^32 前开始，跨过换密钥边界；三分之一用 ChaCha20-Poly1305。测试用的加密实现在 nonce 重复时直接 panic |

测试用的算法是 ring 和 x25519-dalek（`sim/src/crypto.rs`），只在 `sim` 里，不进产品；一次性密钥按种子生成，可以重放失败，但不能用于真实通信。

## 结果

### 加密的代价（`secure-cost.txt`，32 个模拟场景，每个 8 个种子，单向 2 MiB）

| 项目 | 结果 |
| --- | --- |
| 握手 | 多一个往返：40 ms 线路上 1 KiB 小消息从 21 ms 到 62 ms。批量传输平均慢 13.6%，主要就是这一个往返 |
| 握手之后的用时 | 平均 +2.1%。32 个场景里 24 个在 ±4% 以内，最好 −8.7%，最差“小队列 5Mbit 60ms”+25.9%，原因见下一节 |
| 线上流量 | 平均 +2.4%，最差 +13.1%（实测令牌桶路径，额外字节主要是重传）。每个包多 16 字节标签，1400 字节的包是 1.2%；确认包只有二十来个字节，加上标签后占比更高 |
| CPU（直连循环，两端在同一线程，M4） | 明文 3053 MiB/s，AES-256-GCM 1454 MiB/s，ChaCha20-Poly1305 605 MiB/s。AES-GCM 让协议栈开销翻倍，仍是千兆线速的 12 倍；有硬件 AES 的平台默认应该用 AES-GCM |

CPU 数字是测试用的 ring 实现，产品里换成系统实现后要重测；测的时候机器上不能有别的负载，第一次测时后台在跑变异测试，加密版测得比明文还快，作废。

### 发现的问题：第一个统计段的时间起点（第 3 步遗留，已在下一轮修掉，见 `2026-11-03-clock-start/README.md`）

“小队列”场景握手之后慢 26%，原因不是加密。拥塞控制判断“是不是撞到了限速”时，每隔一段时间统计一次送达速率，**第一段从时刻 0 算起**，不是从第一次发包算起：

- 模拟器里连接都在时刻 0 建好、马上发，第一段正好从发包开始，所以前三步的验证都没碰到问题。
- 连接建好后空闲一阵再发（加密握手要一个往返，应用也可能晚写），空闲时间被算进第一段，送达速率偏低。浅队列上开头本来就丢得多，就被当成撞到了一个很低的限速。
  明文连接晚 66 ms 开始写，64 个种子平均同样慢 13.8%，加密连接握手之后慢 15.3%；改成从第一次发包算起后分别是 0.0% 和 +0.5%。
- 真实设备用系统时钟，时刻 0 是很久以前，第一段在第一次统计时就被当成过期整段作废，和模拟器里的行为也不一样。

但改成从第一次发包算起会改变第 3 步验证过的多连接结果。4 条连接错开 200 毫秒依次加入同一瓶颈（`several_connections_do_not_collapse_the_bottleneck`，要求丢包不超过 15%）：

| 第一段怎么算 | 20M 浅队列 | 20M 一倍队列 | 100M 浅队列 |
| --- | --- | --- | --- |
| 现在的代码在模拟器里：从时刻 0 算 | 3.1% | 1.3% | 4.3% |
| 从第一次发包算 | 6.3% | **16.7%** | 13.5% |
| 现在的代码在真实设备上：第一段作废 | **15.5%** | **15.7%** | 10.5% |

也就是说，第 3 步模拟里“多条连接共用瓶颈丢包很低”有一部分是这个起点碰巧帮了忙：后加入的连接第一段被等待时间稀释，给自己定了偏低的限速，主动让路。
按现在的代码，真实设备上同样的场景丢包会到 15%–16%。

这是拥塞控制本身的问题，修它要重新做第 3 步的全套验证，并且需要决定后加入的连接该怎么让。这一轮没有改，拥塞控制的代码和上一步逐字节相同。

### 第一轮变异抓出的测试漏洞

第一次跑加密变异时有 3 个没抓到：

- **包头不参与认证**：篡改测试拿的是对端已经收过的包，改完以后先被当成重放拒掉，根本没走到认证。改成在包第一次送达之前篡改。
- **防重放窗口前移时不清旧位**：只影响乱序到达的包，直连测试里包都按顺序到。加了固定乱序，并让一条连接发超过 4096 个包。
- **发起方留着一次性私钥**：`finish` 紧接着会把整个握手状态连同私钥一起丢掉，从外部看不出差别，是等价变异，移到 `mutants.py` 的说明里。

## 验证记录

命令、环境变量、退出码和耗时见 `validation.json`，都是在上面的核心指纹下跑的。

- 一万个种子的全部测试通过（`tests.txt`，14 分钟）：可靠性 42 个、加密 15 个（含一万个加密种子）、多路流 17 个、共享瓶颈 12 个，另有 5 个单元测试。
  加密矩阵另跑了 1000 个没用过的新种子（从 700000 起，`fresh-encrypted_seeds_deliver_intact_streams.txt`），也通过。
- 明文模式没变：Auto、Lean、Fast 三个策略的 `simulation-*.txt` 和 `2026-11-02-bandwidth-share` 比较，差异都是 0 行。
- 注入的 133 个 bug 全部被抓到（`mutants-full.txt`），其中 19 个是这一轮新加的加密变异。
- 默认 200 个种子时加密测试本机 0.7 秒。

# 给别的流量让路的配置（第 3 步收尾）

核心指纹 `e6248f48723e7f3de90d51158a87dbfb0fea760d`，逐文件 SHA-256 见 `source-sha256.json`。公网数据是上一个指纹 `b2effebcd5f2` 跑的，之后只改了小于 1400 字节的包的计量单位，1400 字节下让路矩阵逐字节相同。

上一轮查到全速模式把同线路的 TCP 挤到约 13%。用户决定：默认保持全速，加一个配置项。
`Config::bandwidth_share` 默认 `BandwidthShare::Full`，另一档 `BandwidthShare::Fair` 让路。只影响这一端发送的速度，不改线格式，两端可以选得不一样。

## 让路模式怎么发

没见过丢包时和全速一样探线路。第一次见到丢包才接管窗口：按测到的线路容量接手，之后见丢包乘 0.7，平时按三次方曲线涨回去。不测随机丢包率，也就不多发校验补偿。发送节奏不另算，窗口说了算。

和标准 CUBIC 不一样的地方，都是真实网络逼出来的：

1. **窗口下限 2 个包。** 全速模式的下限约 16 个包，公网下载这条线路一个来回只装得下约 6 个。沿用的话窗口退到底还在以 18 Mbit/s 发，线路只有 5.6，一半的包被丢，TCP 窗口被打到 1。
2. **窗口不到几十个包时涨得更慢**（保底增长取 0.53 个包和窗口的 1/64 里小的）。窄线路上 TCP 的处境比我们差：一丢包就超时，成串发的包在限速器上又比我们匀速发的丢得多。实测同一条线路上 TCP 丢约 20%，我们约 4%。不多留余量就分不开。
3. **有丢包的轮次都减，不是一次拥塞只减一次。** 只减一次时单独跑更快（限速 40M 从 33.9 到 38.3），但和 TCP 分不平（32.7 / 5.7）。让路模式优先分线路。
4. **超时判的丢包不算拥塞，只认后面的包到了才判的丢包。** 我们的超时只有十几毫秒，Wi-Fi 卡一下就响；TCP 最短 200 毫秒，碰不到。速度一低确认变稀，超时响得更多，窗口被反复压低，公网上单独上传掉到过 15 Mbit/s，每秒上百次超时、约 85% 是虚惊。启动结束也不触发接管：线路卡一下启动就结束了，当时量到的容量只有真实的百分之一。
5. **窗口的计量单位至少 1400 字节。** TCP 的常数按满包定，公平按字节算。按实际包大小算时，64 字节的包窗口下限只有 128 字节，随机测试里一个 20%–30% 丢包、600 毫秒往返的种子 600 秒传不完。
6. **接手窗口取测到的容量，接手后两轮不减。** 启动冲过头丢的包会连着查出来好几轮，逐轮减的话窗口只剩容量的三分之一，100M 40ms 的空线路要爬十几秒才到满速。曲线的目标取出事时的在途量，最多两倍容量。

## 结果

### 真实公网（`public-tcp-fair.txt`，每项 3 轮，每轮 15 秒，单位 Mbit/s）

TCP 是 SSH 传的数据，服务器用 Linux 的 CUBIC。

| 方向 | 只有 TCP | 让路单独跑 | 让路 / TCP 同跑 | 两条 TCP | 全速 / TCP 同跑（上一轮） |
| --- | --- | --- | --- | --- | --- |
| 下载 | 5.2 | 5.3 | **3.3 / 2.3** | 2.8 / 2.7 | 4.8 / 0.7 |
| 上传 | 97.5 | 88.9 | **39.3 / 61.5** | 53.3 / 47.0 | 89.2 / 13.2 |

下载三轮都很稳（3.4 / 2.4、3.3 / 2.3、3.1 / 2.4）。上传多让给 TCP，三轮波动大（37.6 / 58.2、22.5 / 78.2、57.9 / 48.2）。muxperf 的速度算了启动的前几秒，TCP 一侧去掉了，所以我方份额略微低估。

单独跑的稳定性按交替跑算，避开时段差异。上传 8 轮（`public-upload-alone-alternating.txt`）：让路 89.8–106.9、平均 98.7，全速 67.9–104.9、平均 91.0。修超时规则之前同样的测法里让路有 23.2、54.2 这样的轮次。让路单独下载 5 轮平均 5.7（`public-fair-alone-download.txt`）。

全速和让路交替跑消息延迟（`public-chat-only-alternating.txt`、`public-chat-and-file-alternating.txt`，每项 3 轮）。那段时间网络很差，全速只发消息的 p99 也有 190 毫秒以上，平时是 16：

| 情况 | 全速 p99 | 让路 p99 | 全速文件 | 让路文件 |
| --- | --- | --- | --- | --- |
| 只有消息，上传 | 199.4 ms | 70.8 ms | | |
| 只有消息，下载 | 193.4 ms | 192.8 ms | | |
| 消息加文件，上传 | 97.5 ms | 66.6 ms | 59.3 | 77.6 |
| 消息加文件，下载 | 42.6 ms | 99.4 ms | 5.6 | 5.4 |

3 轮的波动比两种模式的差别大，只能说没看到让路让消息明显变慢，说不上更好或更差。

### 模拟（`matrix-*.txt`，3 个种子，下面都是 1 毫秒定时器）

公平指数 1 是平分，0.8 大约是 3 比 1。TCP 模型这轮改成两段确认一次：

| 情况 | 全速：平均 / 最差 | 让路：平均 / 最差 |
| --- | --- | --- |
| 对 CUBIC | 0.75 / 0.50 | 0.92 / 0.71 |
| 对 Reno | 0.83 / 0.56 | 0.90 / 0.74 |
| 后到的 CUBIC | 0.51 / 0.50 | 0.98 / 0.92 |
| 两条自家连接 | 0.94 / 0.54 | 1.00 / 0.98 |
| 四条自家连接 | 0.72 / 0.47 | 0.90 / 0.72 |

基准：两条 CUBIC 互相 0.97 / 0.87。最大丢包：全速 27.8%，让路 8.3%。

| 对 CUBIC（我们 / TCP，Mbit/s） | 全速 | 让路 |
| --- | --- | --- |
| 100M 12ms 队列四分之一 | 90.0 / 4.5 | 49.2 / 45.6 |
| 100M 40ms 队列四分之一 | 84.3 / 11.2 | 62.2 / 34.6 |
| 100M 100ms 队列四分之一 | 87.3 / 6.7 | 68.8 / 25.8 |
| 100M 40ms 队列 1 倍 | 53.4 / 44.8 | 59.8 / 38.6 |
| 100M 12ms 队列 4 倍 | 40.8 / 57.2 | 17.6 / 79.9 |
| 限速 5.6M 往返 90ms | 5.4 / 0.2 | 3.8 / 1.8 |
| 限速 40M 往返 90ms（两条 TCP 互相是 25.2 / 11.1） | 39.1 / 0.6 | 25.4 / 9.6 |
| 限速 5.6M 往返 12ms（公网下载是这种线路） | 5.6 / 0.0 | 2.8 / 2.8 |
| 限速 40M 往返 12ms | 38.8 / 0.9 | 20.0 / 18.9 |

空线路开局（Mbit/s，第 1 秒 / 第 2 秒 / 第 3 秒）：100M 40ms 上让路 91 / 99 / 99，TCP 78 / 97 / 97，修之前让路 45 / 41 / 45；100M 100ms 上让路 76 / 99 / 99，TCP 37 / 47 / 147，修之前让路 53 / 26 / 29。

线路有随机丢包时和 TCP 同速：100M 12ms 丢千分之一时让路 32、TCP 31，全速 98。

### 代价

- 模拟里线路空着时比全速慢约 14%（限速 40M 上 34.1 对 39.6），比 TCP 慢约 5%。公网上交替跑看不出来。
- 有随机丢包的路径上和 TCP 一样明显变慢，不补偿。
- 深队列上让得比平分多（100M 12ms 队列 4 倍是 17.6 / 79.9），公网上传也偏向 TCP。
- 输给 KCP 的最快配置是必然的，这个目标只对默认的全速模式。

## 模拟和真实网络的差距

第一版让路在模拟里全部过关，上了公网下载却是 5.6 / 0.1，比全速还差。模拟漏掉的事这轮都补上了：

- **限速线路的往返都是 90 毫秒，** 碰不到窗口下限。新增往返 12 毫秒的窄线路后，模拟立刻复现 5.6 / 0.0。
- **TCP 模型每段都确认，发得太匀。** 真 TCP 两段确认一次、成串发包，这是限速器上它吃亏的原因。新增 `FlowKind::TcpDelayedAck` 后，这条线路上两条 TCP 的模拟是 2.6 / 2.9，真实 2.4–2.8 / 2.6–3.1。

老的 `FlowKind::Tcp` 留着，上一轮的测试门槛是按它定的，不放宽。`share` 工具的矩阵全部换成新模型，所以这里的全速矩阵和上一轮的不能逐行比。

- **没有“线路卡一下、一个包不丢”的情况。** `LinkProfile` 加了 `stall_every_us`、`stall_us`，默认关闭。开局卡一下提前接管的问题靠它查到了；公网上超时越响越慢的陷阱还是复现不出来，所以 `fair_share_does_not_take_timeouts_for_congestion` 用短暂断网造超时，验证的是规则本身。

还有一处没对上：模拟里 100M 12ms 队列 1 倍上是 54.7 / 43.6，公网上传是 39.3 / 61.5。真实上传线路的队列和丢包规律还没建模。

`random_case` 让四分之一的种子走让路模式，之前的随机可靠性测试根本碰不到这段代码。

| 做法 | 结果 |
| --- | --- |
| 只把窗口下限改成 2 个包 | 公网下载从 5.6 / 0.1 到 5.5 / 0.5，还不够 |
| 小窗口时按 1/16 涨 | 模拟 2.4 / 3.2，公网 4.6 / 1.1。模拟的 TCP 不成串，看不出差别 |

## 验证

- 默认模式：Auto、Fast、Lean 三个策略的 `simulation-*.txt` 和 `2026-11-02-sharing` 比较，差异都是 0 行。对最快 KCP 的未达标数不变：0 / 64、6 / 64、55 / 64。
- 一万个种子的可靠性和多路流测试全过（`tests.txt`），新种子 700000 起也过。四分之一的种子走让路模式，第一次跑时抓到了上面第 5 条的种子 6836。
- 共享测试 12 个全过，新增 6 个让路用例。
- 注入的 114 个 bug 全部被抓到（`mutants-full.txt`），含 12 个让路的。

## 全速模式这轮看到的问题

默认全速的行为这轮没动。新加的窄线路把一个既有问题照出来了：往返短、容量小的线路上，两条全速连接同跑会一条饿死另一条（限速 5.6M 往返 12ms：5.4 / 0.2，丢包 25%–28%）。原因和上面第 1 条相同，窗口下限比一个来回能装的还大。一条连接里跑多条流碰不到这个问题，开多条连接才会。

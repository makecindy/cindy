# 握手准入和关闭通知（2026-11-06）

核心指纹 `ec45bed55327d1595532357d5880b482875163ef`（`shasum src/*.rs | shasum`，按 LF 内容算），上一轮 `212dd5251a71`。

对公网开放监听之前必须补的防护（`docs/agent-net-plan.md` §0，2026-11-06 用户确认“准入分两道门”）。这一轮做了前两项：
握手准入，和关闭通知。第三项连接号轮换还没做。
核心只提供通用机制，认不认对方仍由上层的 `admit` 决定，Cindy 在那里查账号签发的设备证书。

## 改了什么

- 新增 `src/admission.rs`，做法和 WireGuard 的 cookie 机制相同：
  - 握手请求末尾加 `[mac1 16][mac2 16]`。mac1 只有知道响应方公钥才算得出，对不上的直接丢，不做 DH，也不回一个字节。
  - 处理握手超过额度就算忙（至少 1 秒）。忙时先往来源地址回 81 字节的加密 cookie，发起方带着它算 mac2 马上重发，
    响应方确认 mac2 对得上这个来源地址才做 DH；证明过地址的再按地址限流。
  - 默认额度（`Admission`）：不忙时每秒 64 个、一下子 64 个；忙时每个地址每秒 8 个、一下子 16 个。算 cookie 的密钥每 2 分钟换一次，上一把再认 2 分钟。
- `Endpoint` 在 DH 之前过这几关，cookie 回复按 mac1 交给正在发起的连接；`Incoming::read` 自己也先查 mac1。
- `SecureConnection` 发起方收到 cookie 后存起来，之后的请求都带 mac2，第一次拿到时马上重发。
  响应方认“同一个请求”时不看 mac2：中途拿到 cookie 的重发仍然换来原来的回复。
- 新计数：`EndpointStats::bad_mac1`、`cookie_replies`、`throttled_initiations`，`SecurityStats::cookies_received`。
  UDP 驱动、WebAssembly 接口和 Node 驱动都带上了。`PathAddress` 加了 `write_identity`（算 cookie 用的地址字节，默认用 `Debug` 的写法）。

线格式变了：请求多了 32 字节的校验，总长照旧填满到 `max_packet_size`，所以握手附带数据的上限少 32 字节，请求至少 135 字节（以前 103）。
回复、数据包不变。线上格式在接入产品之前不做兼容承诺。

## 关闭通知

以前协议里没有关闭通知：对端进程退出时，这一端要等判死（有数据在途时 30 秒，空闲时靠 15 秒一次的探测）。

- 新帧 `CLOSE`（`[9]`），单独成包，和数据包一样加密认证，共 24 字节。
- `SecureConnection::close` 以后，`poll_transmit` 先发两个关闭包，然后连接就停了；对端认证通过就停，`closed_by_peer` 为真。
  握手还没完成、或者对端还没确认在线时不发（不给可能是重放来的请求回包），只在这一端停下。
- `Endpoint::close` 把关闭包排进 `poll_transmit`，驱动照常取出发掉。WebAssembly 的连接状态多了“对端发来了关闭包”一位，
  Node 驱动的 `close` 事件多了原因 `peer`；关掉整个端点时，先把各条连接的关闭包发出去再关套接字。
- 关闭是立刻的：还没送到的数据不再重传。要对端收全，照旧先结束流、等确认再关。
- 进程被强行结束时发不出关闭包，对端仍要等判死；对端重启以后也认不出旧连接的包（没有类似 QUIC 的无状态重置）。

| 用例 | 结果 |
| --- | --- |
| 一端关掉 | 发出两个关闭包就停，`next_wake` 为空 |
| 第一个关闭包丢了 | 第二个送到，对端马上停，`closed_by_peer` 为真；之后再来的包都丢掉 |
| 改过一个字节的关闭包 | 认证不过，对端照常工作 |
| 握手完成前关闭 | 不发任何包 |
| `Endpoint::close` | 两个关闭包发往对端现在的地址，对端收到第一个就停 |

## 第一版的问题：cookie 回复不能限流

第一版给 cookie 回复也设了每秒 1024 个的额度。洪水测试里伪造的请求每秒 2 万个，额度一直是空的，
正常的发起方一直拿不到 cookie，2.2 秒里没连上。WireGuard 也不给 cookie 回复限流：它比任何请求都短（81 字节对至少 135 字节、
通常填满到包长），伪造来源只会让被冒充的地址收到更少的字节；算它只要两次 HMAC 和一次加密。所以去掉了这个额度。

## 结果（`sim/tests/secure.rs`，虚拟时间）

| 场景 | 结果 |
| --- | --- |
| 乱码和发给别的公钥的真请求各 5000 个 | 0 次 DH，一个字节都不回，`bad_mac1` 10000 |
| 知道公钥的人伪造来源，每秒 2 万个请求（64 个录下的真请求轮流重放），连续 2.5 秒 | 服务端一共 904 次 DH（每个处理过的请求 4 次；额度算出的上限 1044），回给伪造地址 4.3 MB，收到 70 MB（6%） |
| 同时来的正常发起方 | 拿到 1 个 cookie，0.1 毫秒后连上（模拟里没有网络延迟，真实网络多一个往返） |
| 另一个真地址每毫秒新建一条连接（2000 条） | 只处理了 45 条，其余被按地址限流丢掉，不做 DH |

测试的有效性：`sim/mutants.py` 加了 7 个变异体，都变红——mac1 不校验、忙时不要 cookie、忙时不按地址限流、拿到 cookie 不马上重发，
收到关闭包不停、关闭包只发一个、端点关连接不告诉对端。

## 不忙、不关闭时和以前一样

306 个换网场景（6 个历史难种子加 300 个随机种子）在上一提交和现在各跑一遍：235 个的 `Report` 逐字节相同，只多了一个新计数（都是 0）。
变了的 71 个正好是随机配置里包长取 64 字节的那些（见 [`migration-changed-seeds.txt`](migration-changed-seeds.txt)）：
64 字节放不下握手，以前抬到 128，现在请求至少 135 字节，抬到 160，所以场景本身变了。`secure.rs` 的两组随机矩阵同样从 128 抬到 160。

`cargo test --workspace` 119 项通过（多了 4 项），clippy 没有新警告。WebAssembly 从 307 KB 变成 335 KB。
`prototypes/agent-net-spike` 用新的 WebAssembly 重跑（含关闭通知）：真实 `DeviceLinkClient` 的 12 项检查直连、专用通道、push 夹带、先中转再打洞都 12/12，
Node 驱动的检查 6/6。

## 没有覆盖

- 真实网络和真实 CPU：都在模拟器的虚拟时间里，DH 次数是计数，不是测的耗时。
- 控制大量真实地址的攻击者：每个地址都能用掉按地址的额度，这一层只能靠上层拒绝不认识的公钥。
- cookie 密钥换代前后的请求：靠代码审查，没有单独的用例。

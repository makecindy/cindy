# 断网与限速路径的一轮修正

核心指纹 `8ecfab4f27c5e3d865aa4bfe504bda597086ba38`，逐文件 SHA-256 见 `source-sha256.json`。
相对上一版 `8b4089ebf173` 只改 `connection.rs`、`congestion.rs`，完整差异见 `changes-from-8b4089ebf173.patch`。
线格式、策略 API、测试断言都不变。KCP 对照、网络模型与目标口径同上一轮（`../2026-10-31-kcp-target/README.md`）：
每个场景与用时最短的 KCP 配置比较，用时不慢（1% 内算平）、额外协议字节不多，交互 p50 / p95 / p99 不高于 KCP 各配置的最好值。
检查脚本 `kcp-fastest-target.py`，结果 `kcp-fastest-{auto,fast,lean}.txt`。

## 改动

1. **小消息副本不再因为断网停 30 秒。** 以前任何一次断网之后 30 秒内、以及成片丢包期间都不复制新消息；
   每隔几秒断一次的链路（地铁、高铁）上副本因此一直关着，平时每条消息都慢一截。现在只在超过 2 秒完全没有回应
   （长断网，只发少量探测省流量）时停。短时间收不到回应时照样复制：可能只是确认方向断了，数据照样能到，
   零散丢包没有确认就补不回来，只能靠副本。副本和原件同一时刻发出，成片丢包时会一起丢，这时再在后面的包里捎带一份，把时间错开。
   副本只在已经测到丢包时才发，干净网络不多花字节的规则不变。
2. **稀疏消息不再卡在排空和降速阶段。** 带宽估计来自应用自己的发送速度时，排空阶段要等在途量降到估计的 BDP，
   而窗口最低也有一个最小窗口，结果断网后的积压一直按三成多的速度补发；现在降到最小窗口就退出排空。
   降速阶段要靠确认才能结束，稀疏消息遇到超时（确认断了）时直接进入下一阶段，不在整个断网期间都不提速。
   满负荷传输不受这一条影响：限速路径上超时常见，降速阶段是它测随机丢包率、找上限的依据。
3. **随机丢包率按发送时的状态取样。** 包发出时上限还没确认、丢包混着限速丢包的，结果晚一个往返回来时上限可能刚好确认，
   以前按回来时判断，会把限速丢包算进随机丢包率。
4. **已确认的上限压住所有节奏增益**，窗口受限的加速也不能越过上限。只量到一次的宽松上限不压。
5. **限速的快速确认（一段之内直接确认）收紧。** 一段内大半个往返都在丢、丢包远超随机丢包时直接确认上限，不再等第二段；
   但以下情况仍要两段一致：这一段排过队；低速发的包也丢得差不多多（丢包不随速率变化，是突发或断网）；
   这一段有一部分在启动阶段且没有丢得比送达还多（启动时整段平均速率偏低，不能当上限）。
   最后一条修掉了本轮中间版本的两处误判：Lean 突发丢包慢 12%、Fast 窗口 1024 高延迟慢 17%。

## 结果

`simulation-{auto,lean,fast}.txt` 为全部 32 场景 × 两种窗口 × 16 种子；`comparison.md` 为逐项包络比较，`dominance-*.md` 为逐配置比较。

| --- | --- | --- |
| Auto 未达到“最快 KCP”目标的组合 | 18 / 64 | 16 / 64 |
| Fast 未达到目标的组合 | 12 / 64 | 10 / 64 |
| Lean 未达到目标的组合 | 56 / 64 | 56 / 64 |
| 地铁交互 p50 / p95 / p99（Auto，ms） | 36.4 / 1138.0 / 1812.4 | 33.1 / 1110.3 / 1813.9 |

地铁的三项现在都快于 KCP 最好值（35.7 / 1251.6 / 1971.3 ms）；高铁 p50、p99 快于 KCP 最好值（46.2 / 685.6 ms），
p95 360.4 对 349.5 ms（极速+FEC5/5，额外字节 301%、用时是 Auto 的 2.3 倍）仍落后。
另取 1000–1063 共 64 个新种子复核（KCP 只跑了这两个场景里交互延迟最好的五种配置：极速+FEC5/5、kcptun fast、

两种窗口共 64 个组合里，仍然没有任何一种 KCP 配置在用时和额外字节两项上都不差于 Auto（逐配置比较与上一版相同）。

  查明是启动阶段整段平均速率碰巧接近上限造成的确认，属于误判，改正后放弃。

- 交互流量：窗口 128 平均 +3.2%，突发丢包 1643 → 2488 KB、地铁 2374 → 2953 KB、高铁 1826 → 2106 KB。
  交互流量不在目标口径内，这里如实列出。

### 留出场景的说明

高铁与令牌桶两个留出场景本轮被用来定位问题，已经不是干净的留出数据；上面 1000–1063 新种子的复核是对应的样本外证据。
比较表里的“未参与本轮调参”字样由对比程序固定输出，本轮对这两个场景不成立。

## 可靠性

`validation.json` 全部退出码为 0：`AGENT_NET_SEEDS=10000` 的 workspace 测试 43 通过、1 个 profiling 按设计忽略；
600000 起新种子段的默认策略与三策略矩阵各 1000 个种子通过。没有改动任何断言。

已知但本轮没修好的问题：令牌桶路径上（与 `rate_limited_loss_is_not_read_as_random` 相同的条件，窗口 128、16 MiB），
种子 1–24 里有 5 个结束时随机丢包率估计在 5% 以上（最高约 15%），最严重的一个种子在 16 秒内都没有找到上限。
原因是启动后带宽估计被令牌桶放行的突发抬高好几倍，第一个降速阶段仍远超真实上限，限速丢包被当成随机丢包，
门槛随之抬高，之后就认不出上限。该测试固定用种子 22，本版通过。试过两种修法，都未采用：
- 按发送节奏是否低于最近送达速率来过滤样本：突发丢包期间送达速率骤降，突发被当成限速，种子 1–24 变差到 7 个。
- 启动后要有一轮送达速率接近带宽估计，才信降速阶段的样本：受污染的种子降到 1 个，
  但随机丢包路径要多等一整个探测周期才测出随机丢包率，窗口 1024 丢 30% 慢 6%–11%、实测上传慢 10%，
  改为排空结束时核对后仍有 4 个种子受污染、随机丢包路径仍慢 6%–7%。

## 仍未达标（Auto，16 / 64，见 `kcp-fastest-auto.txt`）

- 窗口 128 用时 10 项：丢包 1%、丢包 5%、乱序 10%、千兆、卫星、家宽、5G、令牌桶、跨洋、高延迟。
  启动阶段 KCP 的 FEC 从第一个包就开着，Auto 按规则在确认丢包前不发校验；此外窗口受限时的降速阶段要按低于窗口的速度跑一个往返来测随机丢包率，
  丢 1% 时这部分约占 20 ms。把这一阶段放宽到窗口速率的 97% 且不等样本攒够，丢包 1% 可到 2048 ms，但令牌桶、配额、实测下载变慢 1.7%–4.5%，未采用。
- 窄带小队列（低速 1 Mbit、小队列 5 Mbit）额外字节 4 项：最快的 KCP 是“KCP 普通”，Auto 10.0% / 10.4% 对 6.4% / 5.8%。
  本轮试过确认只报最近变化的区间、慢速链路上合并确认，可降到约 7.8% / 8.7%，但改变了丢包轨迹，
  使上面那个已知的令牌桶问题在固定种子上暴露，先不合入。

# 限速丢包时不发校验、高包率链路逐包确认

核心指纹 `78ac8ec71064111cf36978203bcd0e12dfcacff0`，逐文件 SHA-256 见 `source-sha256.json`。
相对上一版 `0f8be06ef034` 只改 `connection.rs`，完整差异见 `changes-from-0f8be06ef034.patch`。
帧格式、策略 API、测试断言都不变。KCP 对照、网络模型、目标口径同上一轮。

## 改动

1. **量到上限、丢得又远多于随机丢包时，不发校验包。** 令牌桶上限速器挡下的包分布得很散，看起来像随机丢包，
   校验包照发不误，每个都要占掉限速器的一份额度：窗口 128 的令牌桶路径上，确认上限前的那一秒里校验包吃掉了约 0.6 MB/s 的额度。
   现在只要量到了上限（还没确认也算），并且丢包率比随机丢包率的两倍还高出 3% 以上，就当成限速器在丢包，不发校验。
   只看“量到上限”不够：长往返的随机丢包路径上也会短暂量到宽松的上限，那时关掉校验，卫星窗口 1024 慢 10%。
2. **收到的包平均间隔短于 50 微秒（每秒两万个包以上）时，每个包都马上确认。** 这种链路往返通常只有几毫秒，
   窗口卡住时一串包的最后一个单独等确认延迟，整个窗口就要多等这么久。确认多了，额外字节多约 1 个百分点。

新达标：令牌桶窗口 128、千兆窗口 128。**千兆只是按毫秒取整后刚好落在 1% 以内（115 对上限 115.14）**；

## 可靠性

`validation.json` 全部退出码为 0：`AGENT_NET_SEEDS=10000` 的 workspace 测试 43 通过、1 个 profiling 按设计忽略；
1100000 起新种子段的默认策略与三策略矩阵各 1000 个种子通过。没有改动任何断言。

## 未采用的方案

- **量到任何上限就不发校验**：令牌桶同样达标，但卫星、跨境窗口 1024 慢 10%、2%，Fast 高延迟窗口 1024 慢 24%。
- **上限低于窗口能送的速率时不发校验**：卫星窗口 1024 仍慢 10%。
- **一串包到完就马上确认**（不论包率）：千兆没有变化，卫星、高铁变慢。
- **测路径余量**：连着发 8 个校验包、按确认间隔算路径速率。模拟器里每个包的抖动互不相关，几个包的到达间隔被抖动完全打乱，
  算出来的速率比真实值低一个数量级，不能用。

## 问题

上一轮遗留：100M、往返 12 毫秒、队列只有 3 毫秒，四条连接依次加入时丢包 27%。

时间线（种子 1）比记录里说的更糟：

- 0.5 秒时估计就坏了：第一条估成随机丢 17.8%，第二条 37.5%。后加入的连接启动时冲过头，把 3 毫秒的队列挤爆，这些丢包落在别的连接的降速阶段里，全算成了随机丢包。
- 之后自己维持：按估高的丢包率补偿多发，多发的部分又被挤掉。
- 记录里没写的一条：最晚加入的那条被误判成撞上限速，上限一路压到 0.7 Mbit/s，饿了十几秒，公平指数 0.75。
- 第 10 秒左右几条连接一起测最小往返，队列排空一次，之后才慢慢好转。

两个实验定位原因（三个种子）：

| 实验 | 丢包 | 公平指数 |
| --- | --- | --- |
| 上一轮代码 | 26.95% | 0.84 |
| 完全不做随机丢包补偿 | 3.85% | 0.99 |
| 排队判断的余量下限从 4 毫秒降到 1 毫秒 | 14.32% | 0.58 |

带宽估计是各自最近 10 轮的最大值，几条连接加起来比线路高出两成左右，这部分只造成约 4% 的丢包；**放大到 27% 的是随机丢包补偿**。
单纯让排队判断更灵敏不行：只有最早的连接测到过真实的最小往返，它看见排队就让，后加入的连接把它的份额吃掉。

## 怎么认出看不出的排队

随机丢包和速率无关，降速（0.75 倍）和巡航时丢得一样多；被挤掉的包跟着速率走，巡航多发三分之一就多丢一截。20 秒累计，按发送时的阶段分：

| 场景 | 降速 | 巡航 | 差 |
| --- | --- | --- | --- |
| 单条，100M 12ms 3 毫秒队列，随机丢 10% | 10.1% | 10.5% | 0.4 |
| 单条，20M 40ms 一倍队列，随机丢 10% | 9.8% | 10.4% | 0.6 |
| 单条，100M 40ms 浅队列，随机丢 10% | 9.7% | 10.5% | 0.8 |
| 单条，100M 12ms 3 毫秒队列，随机丢 3% | 2.9% | 3.6% | 0.7 |
| 四条，100M 12ms 3 毫秒队列 | 21.2% | 27.4% | 6.2 |
| 两条，同上，随机丢 10% | 12.6% | 16.6% | 4.0 |
| 四条，同上，随机丢 10% | 34.9% | 37.9% | 3.0 |

做法（`Bbr::compare_phases`）：

- 每个包记下发送时是第几个探测周期、处在降速还是巡航。一个周期的降速和巡航碰上的是同一段路况，按周期配对比。
- 降速阶段只有一个往返，单个周期的包太少，所以按包数累计，每过一个周期旧的计数打折，大约 3 秒以前的结果淡出（折扣按周期时长换算：往返 12 毫秒时每周期 1/31，40 毫秒时 1/9）。
- 标准误先按每个包独立算，再乘上周期之间实际的差别比独立时大几倍（至少 1 倍）。令牌桶攒满令牌时一下放行一串、突发丢包只落在某几个周期里，门槛会跟着变宽。
- 巡航比降速平均多丢 1.5 个百分点再加两倍标准误，至少比过 8 个周期，才认定丢包跟着速率涨。

认出来以后：

1. **收回补偿**：补偿每轮收回四分之一；判断不成立后慢慢放开，大约 3 秒放满（每轮的步长按往返时长换算）。
2. **清理估计**：这期间降速阶段丢的包不算进随机丢包率，送到的照样算。沿用“别人排的队”那条规则，只是换了一种发现排队的方法。
3. **限速判断的门槛不跟着清理降低**：这期间门槛至少按降速阶段实际的丢包率算。令牌桶上降速时几乎不丢，门槛不变；共享瓶颈上降速时照样有随机丢包，不会把随机丢包当成撞上限速。
4. 连续超时判定换了路径时，比较结论一起清掉。

## 结果

### 单条连接（对比矩阵，和上一轮比）

- 64 个场景的用时：Auto 平均 +0.01%，最差 +0.50%（山区 3Mbit 150ms 丢包 10% 突发，窗口 1024）；Lean 平均 +0.01%，最差 +0.68%（同一场景）；Fast 平均 0.00%，最差 +0.43%（同一场景）。额外流量平均变化在 0.02 个百分点以内。
- 对最快 KCP 配置的未达标数不变：Auto 0 / 64、Fast 6 / 64、Lean 55 / 64（`kcp-fastest-*.txt`）。

### 多条连接（共享矩阵，3 个种子）

`SHARE_CLOCK_OFFSET_US=1700000000000000` 按真机时钟起跑的矩阵和从 0 起跑仍**逐字节相同**（`matrix-full-precise-clock-offset.txt`）。

自家连接各行（53 行，含限速器上的两条连接）：

| | 精确定时器 | 1 毫秒定时器 |

| 最大丢包 | 29.38% → 23.57% | 36.28% → 25.39% |

### 真实公网（新旧交替跑）

这台 Windows 电脑到上海的阿里云主机，往返约 5 毫秒；服务器出方向限速约 6 Mbit/s，上传约 107 Mbit/s。公网一天里变化很大，单跑一个版本说明不了有没有退步，
所以新（本轮核心）旧（`669d46bd570b`）两个版本在同一时段交替跑，两端都用同一个版本。服务端是交叉编译的静态 Linux 版 `muxperf`，测完从服务器上删掉。
这也是第一次用 Windows 电脑当发送端测公网：上传跑满 100 Mbit/s 以上，Windows 的定时器没有卡住发送速度（第 3 步记录里列的未验证项，见 `2026-11-02-sharing/README.md`）。

## 还没解决的

- **四条连接挤 3 毫秒队列仍丢 8%。** 完全不补偿时是 3.85%，剩下的来自几条连接的带宽估计加起来比线路高；浅队列上看不见排队时没有机制把这部分压下去。
- **1 毫秒定时器下几行公平变差**：四条浅队列 0.96 → 0.77（带随机丢 10% 时 0.98 → 0.74），两条短往返限速 40M 0.99 → 0.89。每条连接各自判断，先认出的那条收回补偿，让出来的份额被还没认出的拿走。
- **两条连接走短往返 5.6M 深桶**：公平 0.90 → 0.58。这一行在这一轮试过的各个版本之间在 0.56 到 0.93 之间跳，根本问题还是第 3 步记的窗口下限比一个来回能装的还大，这一轮没动。
- **最晚加入的低速连接丢包率是别的连接的几倍**（种子 1 前 12 秒约 40%，别的 6%–10%）。同一个先进先出队列里不该差这么多，可能是确定性模拟里低速流的发包时刻和高速流的节奏锁在一起，没查。
- **Windows 上 `netperf` 编不过**：它用了 Unix 专用的 `std::os::fd`。带 `kcp` 特性时集成测试会顺带编译它，所以这台电脑上的完整测试不带 `kcp`，`kcp` 门控的库单元测试单独跑（`unit-kcp.txt`）。`netperf` 本身没改。

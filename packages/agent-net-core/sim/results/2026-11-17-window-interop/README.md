# 放大的窗口和窗口 128 的旧版互通（2026-11-17）

核心指纹 `0b6c3dc4e0ce`（算法同上一轮：`src/*.rs` 按 LF 逐个 SHA-256，按 `sha256sum` 的格式排好再取 SHA-1），逐文件见 `source-sha256.json`。
与 [`2026-11-16-jitter-window`](../2026-11-16-jitter-window/README.md)（指纹 `93a4d821a905`）相比改了 `src/connection.rs`、`src/congestion.rs`、
`wasm/src/lib.rs`（只改注释）、`sim/tests/streams.rs`、`sim/mutants.py`，`prebuilt/core.wasm` 和 `prebuilt/manifest.json` 按新源码重编
（364826 → 365106 字节，导出的函数和参数不变）。核心 `[dependencies]` 仍为空，线格式不变。

## 起因

2026-11-17 复核指出：Node 驱动（`wasm/src/lib.rs`）把收发窗口从 128 放大到 8192 时，注释说「对端的接收窗口照样限着这一端，旧版对端仍按 128 收，
不影响互通」，这只对默认流成立。旧版对端（旧 Desktop、现在的手机原生库）都是 `Config::default()` 的 128。

- **新版发、旧版收。** 接收端只收 `rcv_next` 之后 `recv_window` 个分片以内的，越过的丢掉、也不确认。发送端只有默认流按对端确认里的窗口限着；
  别的流的额度从自己的 `recv_window`（8192）起算，连接的序号范围、在途分片和拥塞窗口上限也都按自己的 8192。不丢包时分片按顺序到，
  `rcv_next` 一直往前走，看不出问题；一丢包，空洞后面越过 128 的分片全被丢掉，只能等重传。8 MiB、100 Mbit/s、往返 20 毫秒、1% 丢包：
  重传从 2 个涨到 8312 个，用时 1.09 → 1.76 秒。默认流虽然不越窗口，拥塞控制按 8192 的窗口判断校验和窗口受限，也慢 63%。
  另外，旧版接收端每条流只给 128 个分片的额度，发送端却从 8192 记起：应用没读的那条流一直发，把旧版的未读上限（4 个窗口）占满，
  读着的流也收不到了（40 Mbit/s 往返 20 毫秒，20 秒只读到 2 MB 里的 0.65 MB；在改后的代码上只把这一处改回去时测的）。
- **旧版发、新版收。** 旧版发送端开流时按 128 记额度。新版接收端开流时记的是「已经给过 8192」，要等应用读走八分之一个窗口（1024 个分片）
  才发第一次额度，旧版发送端用完 128 就停下，等 250 毫秒的探测。千兆局域网上 20 MiB 从 0.26 秒变成 0.50 秒。

## 做法

1. **新分片不越过对端的接收窗口。** 连接记下对端确认里说过的最大窗口（`peer_window_max`，就是对端的 `recv_window`），说出来之前按
   128 和自己的 `recv_window` 里小的那个（`LEGACY_WINDOW`、`Connection::initial_window`）。所有流的新分片都不越过 `snd_una` 之后这么多个分片
   （`snd_una` 之前的对端都收到了，它的 `rcv_next` 不会更小）；在途分片数、交互流留的那份窗口、校验覆盖范围、判丢门槛上限也按这个实际窗口
   （`Connection::send_window_now`）。
2. **拥塞窗口的上限按实际窗口。** 建立时仍按自己的窗口；第一个确认说出对端的窗口以后改成实际能用的（`Bbr::set_max_cwnd`），对端说出更大的
   窗口时再放开。对着旧版对端时和两端都是旧版一样按 128 个分片判断。一开始就按 128 建的话两端都放大窗口时启动阶段跟着变：
   `sim/tests/sharing.rs` 的四条连接挤 100 Mbit/s、往返 100 毫秒丢包 6.7%（门槛 5%），随机丢 10% 的线路利用率 0.79（门槛 0.85）。
3. **新流的额度两端都从初始值起算，收到新流就放宽。** 发送端开流时额度按 `initial_window` 记（旧版接收端给的正是 128）；接收端收到新流时
   记「给过 `initial_window`」，自己的窗口更大就马上放宽到 `recv_window`，额度跟着下一个确认出去。两端都是新版时和以前一样，新流一开就有
   整个窗口：应用晚一点读，发送端也不停在 128 个分片上等它。

两端都是 `Config::default()` 时每一处取到的值都和以前一样（初始窗口 128、对端说的窗口不超过 128、拥塞窗口上限 128 个分片），
`exp_window_mix.rs` 里旧→旧的数字逐位相同，共享矩阵也逐行相同（见下）。

- 不丢包时新→旧改前更快（往返 80 毫秒 7.3 秒对 10.0 秒），那是越过了旧版的窗口、恰好没丢包才没出事；一丢包就是上面第一张表。

- 旧→新改后比旧→旧还快一点（新版接收端额度给得多，旧版发送端少等额度）。

## 没做的

- 手机原生库（`agent-net-native`）用的是同一份核心，这次没有重编；它的窗口还是 128，和新版互通靠这里的改动。以后它也放大窗口时，
  按这里的规则两端都不用再改。
- 第一个确认回来前按 128 个分片发：两端都放大了窗口时，往返很长的线路起步慢一点（卫星一行 +0.4%）。要省掉这一个往返，得让握手带上窗口，
  线格式要变，没做。

# 时钟起点和多条连接（第 4 步之后、第 5 步之前）

核心指纹 `669d46bd570b8d335468b384dc8705cd7e8ab312`（`shasum src/*.rs | shasum`），逐文件 SHA-256 见 `source-sha256.json`。
和上一轮（加密握手）相比只改了 `congestion.rs`、`connection.rs`，线格式和接口都没变。

上一轮查到第 3 步遗留的问题：判断限速的第一个统计段从时刻 0 算起，不是从第一次发包算起。用户决定先修这个再进第 5 步，
因为第 5 步上真实时钟，一定会撞上它。

## 核心只依赖时间差

模拟器里时钟从 0 开始，连接也在时刻 0 建好；真实设备用系统时钟，建连时早已不是 0。凡是拿 0 当起点或当“还没设”的地方，
模拟验证过的行为在真机上都不成立。统计段只是其中一处，所以先加了一个能把这类问题全找出来的测试：

`shifting_the_clock_changes_nothing`（`reliability.rs` 明文、`secure.rs` 加密各一个）：同一个场景从时刻 0 和从 2^40、123456789012345 微秒起跑，
每一步收发必须逐事件相同，三种策略轮换。修之前 300 个种子里 42 个不一样。逐个定位后改了这些地方：

| 位置 | 原来的问题 |
| --- | --- |
| 判断限速的统计段（`congestion.rs`） | 从时刻 0 算起。连接空闲一阵再发时，空闲时间被算进送达速率，开头的丢包被当成撞到了很低的限速；真机上第一段整段作废 |
| 第一个包的到达间隔 | 按距时刻 0 多久算 |
| 已确认的最晚发送时刻 | 留成 0，乱序确认回来时比它早发的包判不判丢会不一样。3000 个种子里只有 1421、1899 两个碰得到，固定进了测试 |
| 校验包的发送时刻 | 拿 0 当“还没发”。这个反过来是模拟器里出错：时刻 0 发出的校验包被当成没发过（Fast 策略的种子 8） |
| 其余以建连时刻为起点的时间 | 收到包、乱序窗口衰减、送达计时等统一在建连时设起点（`anchor_clock`） |

最小 RTT 的记录时刻、发送节奏、上次超时时刻、交互流的轮次也是从 0 起，但第一次读到之前都会被覆盖，没有差别，所以没改，
对应的变异记在 `mutants.py` 的说明里。修完以后验证时一万个种子在两个偏移上都逐事件一致，加密连接 300 个种子也一致。

空闲后开始发的场景另加了 `idle_before_the_first_send_does_not_slow_the_transfer`：小队列路径上晚 66 毫秒才开始写，16 个种子的总用时不能比马上写慢 3% 以上。
上一轮这里慢 13.8%。

## 多条连接：修了起点以后暴露的两个循环

上一轮已经知道，只改起点的话，4 条连接依次加入同一瓶颈时丢包会升到 16.7%。原因是第 3 步模拟里后加入的连接让路，靠的是这个起点：
第一段被等待时间稀释，给自己定了偏低的限速。去掉这个巧合以后查到两个能自己维持下去的循环：

1. **带宽样本一直不老化。** 一轮里丢得比送达还多时，带宽样本不老化，这是为了短断网和突发丢包时不丢掉带宽估计。几条连接一起超发时每一轮都是这样，
   样本永远不老化，每条都以为整条线归自己。现在连续 8 轮以上就照常老化（`OUTAGE_HOLD_ROUNDS`），短断网和突发丢包撑不了这么久。
2. **估高的随机丢包率修不回来。** 几条连接一起启动时随机丢包率会估高。排队时降速阶段发的包原来一律不算，队列一直满着时就没有样本能修正，
   大家都按估高的丢包率多发，队列就一直满着。现在看降速阶段开始时队列是不是已经在排：巡航时发现排队会主动降速，自己排的队到这时已经排空了，
   还在排就是别的流排的。别人的队列里**送到了的包照样算**（说明随机丢包没那么多），丢了的不算（分不清是随机丢的还是被挤掉的）。

自己排的队不能这样算：那时只算送达会把随机丢包率压低，有随机丢包的深队列慢线路上补得不够。试过排队时一律这样算，
“山区 3Mbit 150ms 丢包 10% 突发”窗口 1024 慢 23%；`own_queue_does_not_hide_random_loss` 守着这一条（4 个种子共 54.0 秒、估计 16.5%，一律这样算是 58.9 秒、10.1%）。

`late_joiners_do_not_keep_overshooting` 守着前两条：修之前 5 秒后加入的那条连接让 100M 100ms 浅队列丢 16.8%，四条依次加入时丢 12%。

试过但没留下：降速阶段结束时再看队列有没有回落，回落了才算别人的。对比矩阵里用时差别最多 0.87%，共享矩阵只有一行在第二位小数上不同，删了。

## 结果

### 单条连接（对比矩阵，和上一轮比）

- 64 个场景的用时：Auto 平均 +0.07%，最差 +1.07%（弱网 2Mbit 80ms 丢包 5%，窗口 128）；Lean 平均 +0.05%；Fast 平均 −0.04%，最差 +2.20%（山区，窗口 1024），最好 −6.14%（跨境，窗口 1024）。额外流量的平均变化都在 0.2 个百分点以内。
- 对最快 KCP 配置的未达标数不变：Auto 0 / 64、Fast 6 / 64、Lean 55 / 64（`kcp-fastest-*.txt`）。

### 多条连接（共享矩阵，3 个种子）

`SHARE_CLOCK_OFFSET_US=1700000000000000` 按真机时钟起跑的矩阵和从 0 起跑**逐字节相同**（`matrix-full-precise-clock-offset.txt`），模拟里测到的就是真机上会发生的。
对照列“第 3 步按真机时钟”是统计段仍从 0 算起的拥塞控制、按真机时钟起跑（`matrix-step3-code-real-clock-fairness.txt`），也就是不修的话真机上的样子。

精确定时器，丢包率：

| 场景 | 第 3 步记录 | 第 3 步按真机时钟 | 现在 |
| --- | --- | --- | --- |
| 5 秒后加入第二条，100M 100ms 浅队列 | 16.8% | 16.8% | **0.5%** |
| 四条依次加入，20M 40ms 一倍队列 | 1.2% | 5.7% | 0.7% |
| 四条依次加入，100M 12ms 一倍队列 | 1.4% | 9.2% | 3.1% |
| 四条依次加入，100M 40ms 一倍队列 | 2.8% | 5.0% | 1.1% |
| 四条依次加入，100M 100ms 浅队列 | 1.3% | 12.0% | 0.9% |
| 四条依次加入，100M 12ms 浅队列（3 毫秒队列） | 17.8% | 35.1% | **27.0%** |
| 两条，短往返限速 5.6M 深桶 | 40.6% | 54.3% | 29.4% |
| 自家连接各行（41 行）平均丢包 | 3.72% | 5.25% | 3.18% |
| 平均公平指数 | 0.925 | 0.929 | 0.928 |

不全是自家连接的行里也有变化：两条往返不同（40 / 160 ms）的连接挤 100M 100ms 浅队列从 15.1% 到 0.7%；一条连接单独跑短往返深桶限速从 46.4% 到 7.1%，和 CUBIC 同跑从 47.9% 到 6.9%，
这是“带宽样本不老化”的循环，一条连接自己撞上深桶也会陷进去。和 TCP 同跑的其余各行份额不变。

1 毫秒定时器（`matrix-full-timer1ms.txt`）：自家连接各行平均丢包 4.28% 到 3.60%，平均公平指数 0.880 到 0.890，四条依次加入的平均丢包 6.25% 到 4.08%。变差的三行：

| 场景 | 第 3 步记录 | 现在 |
| --- | --- | --- |
| 两条往返不同（40 / 160 ms），100M 12ms 浅队列 | 1.6% | **17.1%** |
| 两条，短往返限速 5.6M 深桶 | 27.8% | **36.3%** |
| 四条依次加入，100M 12ms 浅队列 | 18.8% | 21.2% |

前两行来自“连续 8 轮照常老化”。试过 16 轮和 32 轮（`outage-hold-variants/`）：16 轮修好这两行，但 1 毫秒定时器下四条连接挤 100M 40ms 浅队列从 9.6% 变成 19.3%，精确定时器下两条深桶从 29.4% 变成 35.7%；
32 轮和完全不老化（上一版）在四条 100M 40ms 浅队列上是 21.0% 和 29.1%。没有哪个全面更好，留 8 轮。

让路模式（`matrix-fair-*.txt`）：平均公平指数 0.971 到 0.973，最大丢包 3.59% 到 3.61%；1 毫秒定时器 0.967 到 0.970，最大丢包 5.15% 不变。

### 加密握手之后

上一轮“小队列 5Mbit 60ms”握手之后慢 25.9%，原因就是统计段起点，现在是 −1.5%。握手之后的用时平均从 +2.08% 到 +1.12%，最差 +7.45%（Wi-Fi 200Mbit 8ms 抖动 4ms，和上一轮相同）；线上流量平均从 +2.35% 到 +1.97%。
CPU 在空闲机器上重测是 3032 / 1475 / 607 MiB/s（明文 / AES-256-GCM / ChaCha20-Poly1305，`secure-cost-idle.txt`），和上一轮一致，加密代码没改。
`secure-cost.txt` 里的 CPU 行测的时候机器上在编译别的东西，作废，模拟部分和 `secure-cost-idle.txt` 相同。

### 公网：这一轮没跑成

这一次这台电脑所在网络发往测试服务器的 UDP 包一个都没到：47812、443、8443、3478 几个端口都试了，服务器上什么都没收到；同一网络访问别的 UDP 服务（STUN）正常。
上一轮能跑时这台电脑的公网出口不同，可能是服务器的安全组只放行了之前的地址，也可能是当前网络到服务器的 UDP 被拦了。
服务器上已经用同一份核心编译好 muxperf（核心源码哈希一致）。服务器下载 `ring` 一直超时，编译时去掉了 sim 里只给加密测试用的 `ring`、`x25519-dalek` 依赖和 `crypto` 模块，muxperf 用不到它们。

## 还没解决的（前两条在下一轮处理，见 `2026-11-04-hidden-queue/README.md`）

- **很浅的队列上四条连接一起抢：** 100M、往返 12 毫秒、队列只有 3 毫秒时丢包 27%（3 个种子的平均，单看 6 个种子在 23%–35%）。被挤掉的包大部分被当成了线路本身的随机丢包，
  每条连接估出 20%–50% 的随机丢包率，按这个比例多发，互相加剧，大约 14 秒后才自己平息。这是第 3 步就记录过的“浅队列看不出排队”，
  不是这一轮引入的：第 3 步的拥塞控制按真机时钟跑这一行是 35%，记录里的 17.8% 是被起点问题美化过的。一条连接里跑多条流碰不到，
  几台设备同时走同一个很浅的路由器队列才会。改它要重新设计随机丢包率的估计，需要单独一轮。
- **1 毫秒定时器下这一轮变差的两行：** 两条往返不同的连接挤 3 毫秒队列 1.6% 到 17.1%，两条连接走短往返深桶限速 27.8% 到 36.3%，原因和取舍见上文“1 毫秒定时器”。
  同属浅队列、深桶这一类，和上一条一起改。
- **公网验证没做：** 见上文。
- **短往返窄带限速上两条全速连接：** 限速 5.6M、往返 12 毫秒时 23.8% 丢包、一条饿死，原因是窗口下限比一个来回能装的还大，第 3 步已记录，这一轮没动。

## 验证记录

命令、环境变量、退出码和耗时见 `validation.json`，都是在上面的核心指纹下跑的。

- 一万个种子的全部测试通过（`tests.txt`，22 分钟，期间同时在跑变异）：可靠性 45 个（新增 3 个）、加密 16 个（新增 1 个）、共享瓶颈 13 个（新增 1 个）、多路流 17 个，另有 5 个单元测试。
  可靠性另跑两组、加密矩阵一组没用过的新种子，各 1000 个，从 800000 起（`fresh-*.txt`），都通过。
- 注入 141 个 bug（新加 8 个），140 个被抓到（`mutants-full.txt`）。没抓到的是“持续满发时补偿不收紧”：别人的队列里送到的包算进来以后，
  `misread_loss_stays_bounded_on_shallow_queues` 原来的场景不再冲到上限。给它加了两条连接同时挤 3 毫秒队列的场景，这个变异就抓到了（`mutant-saturated-cap-after-edit.txt`）。
  改的只是这个测试，核心源码没变；共享测试的场景固定、不随种子数变，改完单独重跑了共享测试（`tests-sharing-after-edit.txt`，本机 2.8 秒）。
- 单连接对比矩阵 `simulation-*.txt`，共享矩阵全速、让路各两种定时器 `matrix-*.txt`，都在验证结束时用最终代码跑的。

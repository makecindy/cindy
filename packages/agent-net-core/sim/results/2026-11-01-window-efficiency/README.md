# 用满窗口：压缩包头、见到丢包后加快修复、开头不空等

核心指纹 `5a0f52fced609658c9f8e0c1ebbf21fe13e4d232`，逐文件 SHA-256 见 `source-sha256.json`。
相对上一版 `50fd2f131ccd` 改 `congestion.rs`、`connection.rs`、`wire.rs`，完整差异见 `changes-from-50fd2f131ccd.patch`。
线格式变了（核心 README 写明第 4 步之前不做兼容承诺），策略 API 不变。KCP 对照、网络模型、目标口径不变。
测试改动：包格式固定值跟着改（包头 5→3 字节、确认帧 16→14 字节）；新增四条回归测试；收紧两条断言（校验路径重传数 45→8、长往返捎带加 p99.9 上限）；没有放宽任何断言。

## 先找到的原因

窗口 128 下还没真正超过 KCP 的项目，把用时拆开看（`progress` / `kprogress` 工具，16 个种子）：

- **开头。** 我们第一轮只发半个窗口，第一个丢包还要等重传。到传完 5% 时比最快的 KCP 晚 1–1.5 个往返，这部分占差距的大头。
- **修复等待。** 路径有余量时包按窗口速率的两倍匀速发，一个往返里排得很开，丢的包要等下一个校验包。
  每轮卡住的时间约占往返的“丢包率 × 校验间隔 ÷ 2”，跨洋路径上是 3%。
- **限速路径的随机丢包率。** 令牌桶上降速阶段的速度还是高过上限，限速丢包混进随机丢包率，
  估计值一高就发副本，16 MiB 传输的额外字节在种子之间能差出好几倍。

## 改动

### 所有路径

- **包头变短。** 包头 5→3 字节（版本 3 位、逐包确认标记 1 位、包号低 20 位），校验帧 9→7 字节（首分片序号取低 16 位），
  确认帧 16→14 字节（最大包号和 una 各取低 24 位）。1400 字节的包带 1390 字节，上一版 1386，KCP 1376，KCP+FEC 1368。
  窗口按分片数算，每个分片多带一点，同样的窗口就多送一点。`recv_window` 上限相应从 65535 收到 32767。

### 只在见过丢包以后（干净路径不多花字节）

- **逐包确认。** 窗口装不满路径、又见过丢包时，发送方在包头标一位，请对端逐包确认。窄带线路和限速路径不受影响。
- **校验加密。** 逐轮多发的校验比例，上限从“抖动晚到的比例”放宽到“丢包率的 40 倍，最多 25%”，一排队就减半。
- **启动阶段见到丢包就按速度优先的余量发校验**，第二轮里丢的包不用等一个往返；窗口超过校验覆盖范围 4 倍时不这样做。
- **启动阶段重传发两份。** 还量不到随机丢包率时按总丢包率算，成片丢或量到上限时除外。
- **确认了路径有余量以后，发送节奏增益从 2 倍放到 8 倍。** 一窗口的包发得紧凑，丢的包等校验的时间就短。

### 开头

- **第一批包按 128 Mbit/s 发**，带宽估计仍不超过 32 Mbit/s，令牌桶放行的突发不会把估计抬高。
- **初始窗口发完等 150 毫秒，第一个确认还没回来就按 2 Mbit/s 把窗口余下的部分慢慢发。** 往返更短的路径上确认已经回来了；
  窄带线路上这个速度也来得及排空，挤不爆队列。

### 判断

- **降速阶段按实际送达速率打七五折**（路径上另有上限时），才真的低于上限，随机丢包率不再被限速丢包污染。
  稀疏消息测到的只是应用速度，这时仍只压到带宽估计的一半，否则断网积压要等很久。
- **窗口不大时，刚进巡航的第一个降速阶段不当低速样本。** 窗口大的连接要靠它尽早测出随机丢包率，不受影响。
- **只量到一次的宽松上限，最近两轮不丢、送达速率又顶到上限时马上放开**，那只是一阵突发。
- **按包数判丢时还要看时间：** 比它晚发出不到三倍抖动的包先到了，不说明它丢了。第一批包发得紧，不加这一条，
  1 毫秒的抖动就会造成误判，干净路径也会多发校验。

### 小消息

- 连接开头的捎带从 128 个包减到 40 个包（速度优先策略不变）。全去掉不行：长往返、丢 5% 的路径上开头的消息要多等一个往返，`small_messages_stay_covered_on_long_paths` 会拦下。
- 丢包后的捎带从固定 30 秒改成 150 个往返、最长 30 秒。往返越短，丢一个包的代价越小，用不着一直带着副本。

## 试过没用的

- **没见过丢包就先发校验**（开头提前发一点）：跨洋、卫星、丢包 1% 都能再快一点，但干净路径要多花约 0.9% 流量，`clean_paths_carry_no_redundancy` 拦下，违反产品规则。
- **第一轮直接发满窗口**：小队列额外字节从 5.8% 涨到 8.3%，超过 KCP 普通，令牌桶也慢 1.7%。
- **确认延迟按到达间隔缩短**：几乎没变化。
- **窗口受限时节奏增益无条件放到 3–8 倍**：长往返快 0.5%，但重复乱序、配额、高铁、5G 变慢。改成确认路径有余量以后才放开。
- **第一批包发快时不限制带宽估计**：令牌桶慢 4.7%、配额慢 4.8%。
- **把开头 128 个包的捎带全去掉**：`small_messages_stay_covered_on_long_paths` 拦下，改成 40 个。

## 结果

### 固定矩阵（32 场景 × 两种窗口 × 16 种子）

| 项目 | 上一版 | 本版 |
| --- | --- | --- |
| Auto 未达到“最快 KCP”目标（容差 1%） | 0 / 64 | **0 / 64** |
| Auto 未真正超过（无容差） | 13 / 64 | **4 / 64** |
| Fast 未达标（容差 1%） | 7 / 64 | 7 / 64 |
| Lean 未达标（容差 1%） | 56 / 64 | 55 / 64 |
| KCP 某一配置在交互延迟和字节上都不差于 Auto | 4 / 64 | **0 / 64** |
| Auto 平均用时变化（窗口 128 / 1024） | — | −0.46% / −0.56% |
| Auto 平均额外字节变化（窗口 128 / 1024） | — | +3.1 / +0.3 个百分点 |

无容差时剩下的 4 项（`kcp-fastest-auto-strict.txt`）都是交互 p50 20.5 对 20.4 ms：无丢包、配额短窗口各两种窗口。
比我们低的只有 kcptun fast3 5/5 和极速+FEC5/5，它们在干净路径上发了约 2 倍的流量（1031K 对 477K），一部分消息多了几份副本，
取最早到的那份。不带冗余的 KCP 是 20.519 ms，我们 20.490 ms。要追上就得在干净路径上发冗余，违反“干净网络不多花一个字节”，这 4 项不追。

逐项前后对比见 `before-after-auto.txt`。变慢最多的是高铁窗口 128 +4.6%（仍比 KCP 快 8.3%）、丢包 5% 窗口 1024 +3.2%、小队列 +2.8%（仍比 KCP 快 85%）；
变快最多的是跨境窗口 1024 −7.8%、实测上传窗口 1024 −7.0%。额外字节涨得最多的是窗口 128 的低丢包路径：丢包 1% 18.8%→32.5%、跨洋 12.9%→23.9%、卫星 20.1%→32.5%、Wi-Fi 20.2%→35.1%，都远低于对应 KCP 配置（50%–195%）。

### 64 个没用过的种子（2001–2064，`new-seeds-vs-fastest-kcp.txt`）

每个组合只和固定矩阵里最快的那个 KCP 配置比批量用时和额外字节，不留容差：**0 / 64 未超过**。贴得最近的几项：
高延迟 14628 对 14636 ms、配额 3797 对 3801 ms、跨洋 12353 对 12379 ms、丢包 5% 2007 对 2033 ms。没有在新种子上重跑全部 12 种 KCP 配置，也没有比交互延迟。

交互回环（每种配置 4 轮、每轮 500 条消息），比的是尾延迟最好的 KCP 配置：

| 项目 | agent-net p50 / p95 / p99 ms | 极速+FEC5/5 p50 / p95 / p99 ms |
| --- | --- | --- |
| 窗口 1024 | **90.2 / 131.7 / 185.1** | 91.7 / 133.1 / 212.1 |
| 窗口 128 | **90.1 / 160.3 / 214.4** | 95.3 / 1270.5 / 1731.8 |

窗口 1024 上传四轮的范围是 1.03–1.92 s，KCP 是 1.45–1.72 s，有重叠。KCP 快速和调优+FEC 各有一轮没有传完。

交互尾延迟在这条路径上不稳定。候选版 `1d75ec2d9c74`（比最终版多两处后来删掉的小改动）跑过三次窗口 128 交互：
p95 / p99 为 412.0 / 884.1、103.3 / 162.7、108.0 / 186.0 ms，同时段极速+FEC5/5 为 126.0 / 171.9、159.8 / 188.9、121.2 / 132.8 ms。
也就是说 p99 有两次比它差，其中第一次的 884 ms 没有查明原因，也没有复现。不能说公网交互 p99 已经稳定领先。公网结果只代表这一条路径。

## 可靠性

`validation.json` 全部退出码为 0：`AGENT_NET_SEEDS=10000` 的 workspace 测试，1800000 起新种子段的默认策略与三策略矩阵各 1000 个种子。

`sim/mutants.py` 共 69 个注入错误，全部被测试拦下。完整一遍在收紧测试之前跑的（`mutants-full.txt`），当时有 7 个没拦下、1 个匹配串过期；
补测试、改匹配串后单独复查了这些项（`mutants-recheck.txt` 和 `丢包后不保持捎带`）。
另有 2 项移到脚本说明里不再列入：高估 RTT 直接采信（固定场景和 3000 个种子看不出差别）、窗口受限时抬高节奏（去掉只慢 0.6%）。
这一轮之前脚本里有 12 个匹配串早已过期，运行时按 invalid 处理，这次都更新了。

## 留一法

最终版去掉一项改动后，窗口 128、16 个种子未超过的项数（0 项是最终版）：逐包确认 6、启动阶段校验 4、校验加密 2、节奏增益 2。
窗口 1024 下启动阶段重传发两份平均省 0.77%，最多省 12.65%。
“窗口装不满时断网轮次不算带宽到头”和“所有数据发完马上发校验”去掉后没有差别，已删。

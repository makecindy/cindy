# 窗口和发送缓冲跟着线路放大（2026-11-14）

核心指纹 `cd35433b1bdf`（`src/*.rs` 按 LF 逐个 SHA-256 后再取 SHA-1，算法同上一轮），逐文件见 `source-sha256.json`。
与 [`2026-11-14-bursts`](../2026-11-14-bursts/README.md) 相比只改了 `src/connection.rs`（每条流的发送缓冲）、`wasm/src/lib.rs`
（产品的窗口和缓冲上限）、`sim/tests/bursts.rs`、`sim/mutants.py`。环境同上一轮，核心 `[dependencies]` 仍为空，线格式不变。

用户 2026-11-14 的要求：「先做自动窗口吧，按实测带宽×往返动态放大，上限按内存定」。

## 原来的问题

上一轮把产品窗口定成 1024 个分片（满长约 1.4 MB）、每条流发送缓冲固定 4 MiB，两个都是写死的数：

- 在途量本来就由拥塞控制按实测「带宽 × 往返」决定（约两倍 BDP），窗口只是额外的天花板。1024 个分片在 1 Gbit/s、往返
  20 毫秒（一个 BDP 约 2.5 MB）上就卡住了：20 MiB 只跑到线路的 54%；50 Mbit/s、往返 200 毫秒时也碰顶。
- 固定的缓冲：快而远的线路上装不下在途的加上排着的下一窗口，断流；慢线路上一次写 8 MiB 也整个收进来，白占内存，
  后面的小消息排在它后面。

## 做法

1. **窗口只当内存上限。** wasm 初始化把收发窗口改成 8192 个分片（满长约 11.5 MB）：1 Gbit/s 往返 90 毫秒、100 Mbit/s
   往返 0.9 秒以内都不会卡在窗口上。实际在途多少仍由拥塞控制定。
2. **每条流的发送缓冲跟着拥塞窗口走**（`Connection::stream_send_buffer`）：两倍拥塞窗口，至少 1 MiB，最多 `send_buffer_bytes`
   （wasm 给 24 MiB，两倍满窗口）。写不进去的留在应用那边（Device Link 的待发队列），由背压控制；已经写进来的不会因为
   窗口变小被丢掉，只是暂时不再收新的。`send_buffer_bytes` 不超过 1 MiB 的配置（包括 `Config::default()`）行为不变。
3. 核心的 `Config::default()` 不变（窗口 128）。对端的接收窗口照样限着这一端，旧版对端仍按 128 收，互通不受影响。
   手机原生库（`agent-net-native`）还是 128，等原生库重编时一起改。

一条连接最坏的内存：发送缓冲两条流合计 48 MiB（只在线路快而远、应用一直在写时），接收端乱序最多一个窗口 11.5 MB，
应用不读时未读数据最多四个窗口（`MAX_UNREAD_WINDOWS`）。慢线路上发送缓冲只占约 1 MB。

## 没做的

- **跨地区线路空闲 5 秒后的 1 MiB 变慢**：50 Mbit/s、往返 200 毫秒、丢 0.5% 上，4 个种子里有 2 个从 535、534 毫秒变成 901、760 毫秒，
  这一格平均利用率 35% → 26%（只发核心默认窗口 128 时是 12%）。单独换窗口、缓冲各跑一次：原因在窗口（1024 + 24 MiB 缓冲与上一轮一样，
  8192 + 4 MiB 缓冲照样变慢），不在缓冲。看逐 50 毫秒的轨迹，空闲后这一阵按每秒 16 MB 的探测节奏发出（线路每秒 6.25 MB、队列 100 毫秒），
  窗口 1024 时第一个往返收住了，8192 时多发的挤满队列丢了一批，读取停了一个往返。要改的是空闲后重新探测的节奏，属于拥塞控制，
  牵涉换网、共享等矩阵，留到下一轮单独做。
- 手机原生库的窗口，见上。


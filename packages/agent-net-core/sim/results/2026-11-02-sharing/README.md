新增 `sim/src/share.rs`（多发送方共用瓶颈，含 CUBIC、Reno 模型和定时器粒度）、`sim/src/bin/share.rs`、`sim/tests/sharing.rs`、`sim/share-public.py`（真实公网和真实 TCP 同跑）。

## 查出来的问题

**拥塞崩溃。** 几条连接抢一个瓶颈时，算法把别的流挤掉的包当成随机丢包，按丢包率多发，发得越多丢得越多。
四条连接抢 20 Mbit/s：丢包 71%，两条连接发 35 Mbit/s，另外两条被饿死。单条连接测不出来。

**发送速度被定时器锁死。** 迟到的时间作废，每次醒来只发一个包，速度锁死在“一个包除以定时器精度”，带宽估计跟着掉下去：

| 定时器精度 | 限速 40M 线路上的速度（修复前） | 修复后 |
| --- | --- | --- |
| 1 毫秒 | 39.7 Mbit/s | 39.7 |
| 2 毫秒 | 11.1 | |
| 4 毫秒 | 2.8（每 4 毫秒一个包） | 39.7 |
| 8 毫秒 | 1.4（每 8 毫秒一个包） | 39.7 |
| 16 毫秒 | | 39.7 |

公网下载偶尔只有 0.6 Mbit/s、带宽估计没丢包却一路下跌，都是这个原因。Windows 默认定时器约 15.6 毫秒，那里会被锁在 0.7 Mbit/s 左右。
所有模拟都测不出来，因为模拟器的时钟是精确的。`run_shared_with_timer` 现在能模拟定时器粒度。

## 改了什么

都在 `congestion.rs`，加上 `connection.rs` 里告诉它什么时候不算迟到：

1. **排队时的丢包不算随机丢包。** 队列可能是别的流排的，降速也挡不住。压低队列时除外。
2. **持续满发时补偿上限从 2 倍收到 1.25 倍。** 浅队列上队列比抖动还小，看不出排队，判错时损失有了上限。零散小消息不受影响。
3. **探测撞到丢包后，巡航留 10% 余量。** 这是业界 BBRv2 的做法。顶着容量发的话，TCP 一抬头就丢包，退到几乎没有流量。
4. **迟到的发送节奏要补回来，最多 20 毫秒。** 只补真的在等节奏的时间；没数据、等确认的时间不算，否则就成了突发。
5. **探测见到丢包，再跑一个往返就结束。** 限速器把多发的包都丢了，在途量永远到不了探测的目标，原来会一直卡在探测里，多发 25%、白丢 20%。精确时钟下碰不到，定时器有粒度时才卡住。

## 试过但没留下的

都有数据，都是这边好了那边坏：

| 做法 | 结果 |
| --- | --- |
| 判断队列是别人的，就按当前往返时间算在途量 | 自家几条连接互相误判，崩溃回来了 |
| 排空不见效时暂时不减速 | 中等队列上把 TCP 压到 94 / 4。主动减速正是我们对 TCP 友好的原因 |
| 拥塞时按比例减、平时按固定量加（三种变体） | 有的线路变成 1.3 / 18.5，KCP 目标掉 2–4 项 |
| 带宽估计见丢包就往下调 | 平均公平性不变，KCP 目标掉 3 项 |
| 严重丢包时按限速器处理 | 丢包降了，但变成 87 / 13 |
| 留了余量还丢就再让一点 | 对 TCP 只从 0.2 提到 0.5，三种丢包线路输给 KCP |
| 压低队列时放宽启动的到顶判断 | 交替跑公网，文件没变快，延迟更差 |
| 探到带宽上涨就接着加速 | 上一轮就试过，模拟里没差别；这轮公网看着有用，交替跑后证明不了，没留 |
| 降速阶段按送达速率打折 | 有补偿上限以后没有差别，注入 bug 时测试也抓不到，删了 |

## 结果

### 真实公网（最终代码，家里 Wi-Fi 到上海云主机，往返约 14 毫秒）

多路流对两条连接（`public-mux.txt`，6 轮，三种方式轮流跑）：

| 方向 | 方式 | p50 | p95 | p99 | 文件 Mbit/s | 每轮文件速度 |
| --- | --- | --- | --- | --- | --- | --- |
| 上传 | 只有交互 | 14.0 | 15.1 | 16.3 | | |
| 上传 | 两条连接 | 17.4 | 50.5 | 84.0 | 108.6 | 106.9–109.8 |
| 上传 | 多路流 | 15.3 | 28.7 | 38.0 | 98.9 | 94.8–100.5 |
| 下载 | 只有交互 | 13.9 | 15.0 | 16.6 | | |

上一轮公网多路流比两条连接慢：上传 13%–30%，下载 9%–22%。这轮是 9% 和 7%，没有卡在低速的轮次。

和真实 TCP 同跑（`public-tcp.txt`，3 轮，每轮 15 秒。修复前的在 `public-tcp-before-fix.txt`）：

| 方向 | 只有 TCP | 只有我们 | 同跑（我们 / TCP） | 两条 TCP |
| --- | --- | --- | --- | --- |
| 上传 | 99.3 | 106.4 | 89.2 / 13.2 | 55.7 / 46.0 |
| 下载 | 5.4 | 5.0（3.2、5.9、5.9） | 4.8 / 0.7 | 3.0 / 2.5 |

单独跑时我们和 TCP 差不多或更快。同跑时 TCP 大约拿到 13%，公平份额是 50%，修复前下载只有 3%（5.4 / 0.2）。
线路变化时这个比例也变：路况差的时段上传同跑测到过 71.0 / 24.1。

## 还不够好的地方

- **同跑时 TCP 份额偏低，令牌桶线路上尤其明显。** 公网上传 89 / 13、下载 4.8 / 0.7，模拟 5.4 / 0.2。顶着容量发时 TCP 被挤到几乎没有流量，留不下任何信号，发现不了；要让就得平时长期低于上限，单连接变慢、输给 KCP。这是取舍，不是漏洞，写进了产品规则的待裁决。
- 高带宽极浅队列上偏强（89 / 6），低带宽深队列上偏弱（3.4 / 16）。这是 BBR 一类算法的已知特点。
- 四条连接分得不够均。后到的流看不到空队列，最小往返时间偏高，占便宜。
- 公网只有一条路径（家里 Wi-Fi 到上海云主机）。这条路在一天里变化很大：换过往返 14 毫秒和约 100 毫秒两种走法，上传 TCP 单独跑从 2 到 104 Mbit/s 都有。

## 验证

- 三个测试文件 1 万个种子全部通过，记录见 `tests.txt`。之后 `sharing.rs` 又加了一条 `misread_loss_stays_bounded_on_shallow_queues`，单独跑过。新种子见 `fresh-*.txt`。
- 注入 102 个 bug 全部被测试抓到，见 `mutants-full.txt`。第一次有一个没抓到（持续满发时补偿不收紧），查下来代码有用（去掉后最差丢包 50%），是测试没覆盖，补了测试。
- 对最快 KCP 配置（`kcp-fastest-*.txt`）：Auto 未达标 0 / 64，Fast 6 / 64（上一版 7），Lean 55 / 64（不变）。不给容差时 Auto 是 6 / 64（上一版 4），多出来的两项是高铁路径的 p95，352 对 349.5 毫秒。
- 新种子对最快 KCP（`new-seeds-vs-fastest-kcp.txt`，16 个种子）：1 / 64 没超过，乱序 10% 差 0.05%。
- 代价：Auto 的平均用时比上一版慢 0.34%（窗口 128）和 0.77%（窗口 1024），最差单项 5.6%；额外字节略少。
- 公网数据都是最终代码测的。没有验证：手机网络（运营商 NAT 打不了洞，云主机又挡入站 UDP），Windows 真机定时器。

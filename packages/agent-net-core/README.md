# agent-net-core

agent-net 的自研传输核心。纯状态机，不碰网络和时钟，运行时零第三方依赖。
方案见 [`docs/agent-net-plan.md`](../../docs/agent-net-plan.md) §0。

这一层本质是通用的可靠 UDP 协议，目标是全面超越 KCP，不包含任何 Cindy 专属设计，未来可以单独拿出去给其他应用使用。
边界规则见 [`docs/product-rules/agent-net.md`](../../docs/product-rules/agent-net.md)“传输核心的边界”。

目前完成了第 1 到第 6 步，第 7 步的核心部分和本机验证做完了：一条连接里多条可靠字节流，带优先级，拥塞控制验证过和别的流量共用线路，
`SecureConnection` 提供端到端加密，地址变了连接不断，`Endpoint` 把一个端口上的多条连接按连接号分发；
路径可以有代价、可以主动验证，打洞成功就换到直连，直连断了退回中转。`udp/` 是只用标准库的真机 UDP 驱动，
`wasm/` 把核心编成 WebAssembly、由 Node 驱动跑（电脑端用）。Desktop 私有中转已接入实验开关，Mobile 使用同一核心的原生 ABI；两端分享路由已接入，尚未发布或完成目标环境全业务验收。实验线上格式不作版本兼容承诺。

[`连接号轮换记录`](sim/results/2026-11-07-id-rotation/README.md)，本轮未重测真实 Wi-Fi／蜂窝切换。

## 使用方式

Node/Desktop 包使用 `@cindy/agent-net-core/node`。正常构建运行 `node packages/agent-net-core/build.mjs`，
只使用仓内 `prebuilt/core.wasm`（本次 359804 字节），无需用户安装 Rust。
构建同时核对 Rust 源码、Cargo 清单/锁文件及 WASM 的 SHA-256；不匹配时拒绝暂存旧核心。
修改核心后由开发者安装 `wasm32-unknown-unknown` 目标，再运行
`node packages/agent-net-core/build.mjs --refresh-prebuilt`，同步提交预编译包和 manifest。
这是分发/构建入口；Rust 核心仍是零运行时第三方依赖的通用协议，不含 Cindy 设备身份或业务路由。

调用方自己收发 UDP，把时间和包喂给核心：

```rust
let mut connection = Connection::new(Config::default(), now_us);
connection.send(now_us, data);                 // 写入字节流
connection.on_packet(now_us, packet)?;         // 收到 UDP 包
connection.tick(now_us);                       // next_wake() 到点时调用
while let Some(size) = connection.poll_transmit(now_us, &mut out) { /* 发出 out[..size] */ }
let size = connection.recv(now_us, &mut buffer);
```

### 多条流

一条连接里可以开多条单向的流，共用确认、丢包修复和拥塞控制。一条流丢包或应用不读，别的流不受影响。
不开流时直接用上面的 `send` / `recv`，那是默认流，线上不多一个字节。

```rust
use agent_net_core::{Priority, StreamEvent};

let chat = connection.open_stream(Priority::Interactive).unwrap();
let file = connection.open_stream(Priority::Background).unwrap();
connection.send_stream(now_us, chat, message);
connection.send_stream(now_us, file, chunk);
connection.finish_stream(file);                // 这条流写完了

// 对端
while let Some(event) = connection.poll_event() {
    match event {
        StreamEvent::Opened(id) => { /* 对端开了新流 */ }
        StreamEvent::Finished(id) => { /* 这条流读完了 */ }
    }
}
let size = connection.recv_stream(now_us, stream, &mut buffer);
```

- 流是单向的，两端各自编号，互不影响。写入后切分片时才决定发哪条流，所以优先级在最后一刻才生效，`set_priority` 下一个分片起生效。
- `Interactive` 优先于 `Normal` 优先于 `Background`，同级轮流发；低优先级不会被饿死。
- 交互流和其他流同时在发时，连接自动压低网络里的排队，并给交互流留一点发送窗口。只有交互流、或者只有大量数据时不受影响。
- 交互流的数据不用等发送节奏和拥塞窗口，每个往返最多放行 8 个分片的量；大块数据就算标成交互流，超出这点额度也要照常排节奏。
- 别的流用流量额度，默认流沿用确认帧里的窗口；未读数据总量有上限，见 `Config::max_streams` 和 `recv_window`。

### 策略与显式覆盖

默认 `Config::default()` 使用 `RecoveryPolicy::Auto`。也可以先取策略默认值，再覆盖公开字段：

```rust
use agent_net_core::{Config, RecoveryPolicy};

let config = Config {
    send_window: 1024,
    recv_window: 1024,
    send_buffer_bytes: 4 << 20,
    ..Config::for_policy(RecoveryPolicy::Fast)
};
```

`bandwidth_share` 决定和同一条线路上别的流量怎么分，只影响这一端发送的速度，不改变线格式，两端可以选得不一样：

| 选项 | 行为与代价 |
| --- | --- |
| `BandwidthShare::Full`，默认 | 全速：尽量用满线路。和 TCP 同跑时占大头，公网实测 TCP 约拿到 13% |
| `BandwidthShare::Fair` | 让路：见到丢包后按 CUBIC 的规则发，公网和 TCP 同跑时下载 3.3 / 2.3、上传 39 / 62 Mbit/s。线路空着时和 TCP 差不多快；有随机丢包的路径上和 TCP 一样明显变慢，不多发校验补偿 |

| 策略 | 行为与代价 |
| --- | --- |
| `Auto`，默认 | 按路径调整校验；窗口受限、路径还有余量时按速度优先多发校验，目标是不慢于同条件下最快的 KCP 配置、流量仍少于它；测到丢包后小消息用独立副本保护，确认方向短暂中断时照样复制，超过 2 秒的长断网才停；不把稀疏消息的发送速度当成恢复积压时的路径上限 |
| `Lean`，省流量 | 关闭主动副本、捎带和校验，只重传缺失数据；随机丢包和长往返下可能明显更慢 |
| `Fast`，速度优先 | 扩大启动窗口、提高初始发送速率并增加校验和小消息副本；会增加流量，遇到限速或间歇中断也可能更慢 |

当前 Auto 根据分片大小和路径观测做启发式保护，没有应用消息边界或流级优先级 API。
策略只影响本地发送行为，不改变线格式，两端可选择不同策略。`Connection::new` 不重写调用方显式给出的字段。
这是核心 API，尚未实现产品设置页面、偏好持久化或在线切换。最终产品采用「自动选择，支持手动覆盖」；默认值和覆盖的边界见产品规则。

## 加密

`SecureConnection` 在 `Connection` 外面加一层：Noise IK 握手（按 Noise 规范第 34 版实现），之后每个包都做认证加密并拒绝重放。
用法和 `Connection` 一样，只多一步握手：

```rust
use agent_net_core::{Incoming, SecureConnection, is_initiation};

// 发起方：事先知道对方的长期公钥。
let mut connection = SecureConnection::connect(crypto, config, b"my-app/1", &peer_public, &[], now_us)?;

// 响应方：陌生来源发来握手请求。
if is_initiation(packet) {
    let incoming = Incoming::read(&crypto, b"my-app/1", packet)?;
    // 先看 incoming.remote_static() 是不是认识的对端，再接受。
    let connection = incoming.accept(crypto, config, &[], now_us)?;
}
```

之后照常 `send`、`on_packet`、`tick`、`poll_transmit`、`recv`，握手完成前写入的数据先缓存。`prologue` 两端必须完全一致，可以放协议名和版本。
`max_packet_size` 仍是整个 UDP 载荷的上限，16 字节的认证标签和 4 字节的连接号算在里面，握手要求至少 135 字节。

加密算法由调用方实现 `Crypto` trait 传入：X25519、认证加密（AES-256-GCM 或 ChaCha20-Poly1305）、32 字节输出的哈希（SHA-256 或 BLAKE2s）和对应的 HMAC。
核心不带任何算法实现，也不接触长期私钥，只调用 `dh_static`；产品里用各平台系统自带的实现。算法名写进 Noise 协议名，两端不一致时握手失败。

| 要求 | 做法 |
| --- | --- |
| 抓包无明文 | 握手以外的包都是 `[包头 3][收包方的连接号 4][密文][标签 16]`。发起方的长期公钥也加密传输，被动监听看不出是谁在连 |
| 防篡改 | 包头和连接号不加密但参与认证，nonce 是完整包号。认证失败的包不进可靠层，不改变任何状态 |
| 防重放 | 认证通过后才记入 4096 个包号的窗口，重复或更旧的包丢弃，里面的数据由可靠层重传。重复的握手消息同样识别 |
| 前向保密 | 传输密钥混入两端一次性密钥的 DH，一次性私钥握手一结束就丢；每 2^20 个包（满长度约 1.4 GB）按 Noise `Rekey` 换一次密钥，旧密钥随即丢弃。换密钥只看包号，线上不多一个字节，两端也不用协调 |
| 不放大流量 | 请求填满到 `max_packet_size`，回复和请求一样长；响应方收到发起方第一个数据包之前，每收到一份请求只回一个回复，不发数据。这同时确认了路径两个方向都能过满长度的包 |
| 双方确认 | 发起方收到回复后立刻发一个探测包，响应方见到它才算确认对方在线，所以响应方先说话也只多等一个往返 |
| 同时发起 | 两端同时向对方发起时，公钥大的一方继续当发起方，另一方自动改当响应方，只完成一次握手，已写入的数据不受影响 |
| 关闭通知 | `close` 以后发两个只含关闭帧的包，和数据包一样加密认证；对端认证通过就停，`closed_by_peer` 为真，不用等判死。伪造的关闭包认证不过，不起作用 |
| 挡住伪造请求 | 请求末尾带 mac1（知道响应方公钥才算得出），对不上的不做 DH、也不回一个字节；处理得太快时先回 81 字节的 cookie，发起方带着它（mac2）马上重发，证明收得到发往来源地址的包；忙时再按地址限流。见下面的“握手准入” |

### 握手准入

解开一份请求要做两次 DH，接受它还要再做两次。伪造请求很便宜，所以 `Endpoint` 在 DH 之前先过三道关，做法和 WireGuard 的 cookie 机制相同，
线上格式见 `src/admission.rs`：

1. **mac1**：请求末尾带一个只有知道响应方公钥才算得出的校验值。对不上的直接丢，不回一个字节，扫描的人看不出这里有服务。
2. **忙时要 cookie**：处理握手的速度超过额度就算忙（至少持续 1 秒）。忙时先往请求的来源地址回一个 81 字节的加密 cookie，
   发起方带着它（mac2）马上重发，响应方确认 mac2 对得上来源地址才做 DH。伪造来源地址的人收不到 cookie。
3. **忙时按地址限流**：证明过地址的请求，每个地址再单独限流。

默认额度（`Admission`，`Endpoint::set_admission` 可改）：不要求证明地址时每秒 64 个、一下子最多 64 个；忙时每个证明过的地址每秒 8 个、一下子最多 16 个。
不忙时和以前完全一样，忙时正常的发起方只多一个往返。cookie 回复不限流：它比任何请求都短，伪造来源只会让被冒充的地址收到更少的字节；
限了它，伪造的请求会把额度用光，真的发起方反而拿不到 cookie（第一版这样做，测试里正常的发起方一直连不上）。
认不认对方是上层的事：`listen` 的 `admit` 看过对方公钥和附带数据再决定，Cindy 在这里查账号签发的设备证书。

实测（`sim/tests/secure.rs`，虚拟时间）：

- 乱码和发给别的公钥的请求各 5000 个：0 次 DH，不回一个字节。
- 知道公钥的人伪造来源地址，每秒 2 万个请求连续 2.5 秒：服务端一共做了 904 次 DH（每个处理过的请求 4 次，额度算出的上限是 1044），
  回给伪造地址的字节是收到的 6%；同时来的正常发起方拿到 1 个 cookie，0.1 毫秒后连上（模拟里没有网络延迟，真实网络多一个往返）；
  另一个真地址每毫秒新建一条连接，2000 条里只处理了 45 条。

已知限制：

- 第一条消息附带的数据只受响应方长期密钥保护，没有前向保密，也可能是录下来重放的；偷到响应方私钥的人能看出发起方是谁。这是 IK 模式的已知性质。
  需要拒绝重放的请求时，发起方可以在附带数据里放时间戳，由上层检查。
- 伪造请求的 CPU 有上限（见“握手准入”），但知道公钥、又控制大量真实地址的人，每个地址都能用掉按地址的额度。认不认对方由上层的 `admit` 决定，
  核心不认识账号和证书。
- 中继和路上的人仍能看到地址、时间、包的大小和数量；换号只减少固定连接号造成的关联，不能保证流量无法被关联。
  系统没通知时，被发现前的包仍带旧号；缺备用号时也会暂用旧号并单独计数。中继自身仍认识两端。
- 不做 0-RTT，每条连接比明文多一个往返才开始传数据。
- 两端的 `initial_packet_number` 和 `max_packet_size` 必须一致，和 `Connection` 一样。

## 换地址

NAT 换了端口、手机从 Wi-Fi 换到蜂窝，连接照常继续，对端看到的只是一个新来源地址。

```rust
// 收包时说明包从哪条路径来，发包时取它该发往的路径。路径是调用方自己编的号，建连时的地址是 0。
connection.on_packet_via(now_us, path, packet)?;
// 看得出新地址只换了端口（IP 和数据路径相同）时用这个，换过去以后不重新测速。
connection.on_packet_via_route(now_us, path, same_route, packet)?;
while let Some((size, path)) = connection.poll_transmit_via(now_us, &mut out) { /* 发往 path 对应的地址 */ }
// 知道自己换了网络（换了网卡、重新绑定了端口）时告诉连接，它会马上发包让对端跟过来。
connection.on_local_address_change(now_us);
```

核心的 `Endpoint` 已经把这些接好：一个端口上跑多条连接，按连接号分发，给每个新来源地址编路径号，看出只换了端口时告诉连接。
驱动只管收发数据报，`udp/` 和 Node 驱动都有 `rebind` 换端口，见下文“各平台的驱动”。

| 做法 | 内容 |
| --- | --- |
| 连接号 | 握手时交换初始号；`Endpoint` 之后自动补满 8 个收包号，在加密通道里交给对端。每条新路径用一个未用过的号，本地换网时轮换所有在用路径；线上仍是 4 字节。`destination_id` 取出线上号，`Endpoint` 的连接句柄始终不变 |
| 先验证再换 | 对端从新地址发来一个通过认证、包号比之前都大的包，就在新地址上发路径验证（`PATH_CHALLENGE`），对端原样回过来才把数据换过去，这时在途的包全部重传，往返、带宽、丢包从头量。验证期间数据照旧走原路径 |
| 只换了端口 | NAT 换了外部端口时 IP 不变，驱动告诉核心。验证照样做，通过后在途的包照样重传，往返、带宽、丢包照旧，不从启动阶段重新冲，并马上补一个确认（验证期间的确认都发往了旧端口）。验证包带上标记（帧类型 8），被验证的一端也不重量，两个往返之内收不到确认不判超时 |
| 不放大流量 | 验证通过之前，发往新地址的只有验证包，字节数不超过从那里收到的三倍，和 QUIC 一样。约 3 秒没通过就放弃，原路径的包又成了最新的也放弃 |
| 伪造和重放 | 伪造、篡改的包认证不过，录下的包被防重放窗口挡掉，都不会触发验证。路上的人抢先送到的复制包只换来几个发往它那里的验证包，数据不跟过去。对端真换了地址、包又被抢先复制时，新地址来的真包都成了重复包：最新那个包的重复从数据路径以外来、认证通过时也去验证那里，所以每个包都被抢先复制也跟得到新地址 |
| 自己不知道换了网络 | NAT 换端口、系统没通知换网时，没有包要发的一端（比如在下载）对端的包都发到了旧地址。这一端没有包在途、对端又安静下来时，1 秒后发一个探测包，没有回音就每秒一次（往返很长时每 4 个往返一次）到 30 秒，对端从新地址收到就跟过来；对端回了就停。对端在验证这一端的新地址时，这一端也把往返和带宽从头量 |
| 往返变长 | 换到往返长得多的路径、又没察觉时，重传超时比新的往返短，每个包都先被超时判丢。判丢后才到的确认也取往返样本，超时就能追上；明文连接上路由变化同样受益 |

### 备用号和换网换号

`Endpoint` 自动分配端口内不重复、不可预测的备用号：初始 1 个加备用 7 个，作废后继续补到 8 个。
发往新路径的第一份验证包就用新号，端口变化也一样；系统通知本地换网，或对端验证使这一端发现换网时，给所有在用路径换号。
验证失败的路径用过的号也作废，退回备用路径时重新取号；缺号时先沿用旧号，补到号后自动换，数据不等交号。

交号快照（帧 10）包含有效本地号和要作废的对端号，按代次确认（帧 11）、丢了重发；旧快照和旧确认不能回滚新状态。
作废前的旧号仍能收包，作废后的迟到包被丢弃，里面没确认的数据由可靠层用新号重传。
每个控制包都单独加密认证，最长 130 字节，最小握手 MTU 135 字节也放得下，普通数据包大小不变。

直接用 `SecureConnection` 的驱动需在握手确认后调用 `add_connection_id(random_id)`，并按 `local_connection_ids()` 同步分发表，作废后补号。
不提供备用号时仍用原号；经 `Endpoint` 使用时无需改驱动。`SecurityStats` 与 Node 的 `ConnectionStats` 提供换号、缺号、作废、交号包和重发计数。
新增控制帧尚无与旧实验版本的协商，两端须一同更新；中继只转发原有的不透明数据报，无需改服务端。

## 打洞和中继

核心不知道中继和 NAT，只提供三样通用机制，打洞的流程（交换候选地址、什么时候重试）由上层编排：

```rust
connection.set_path_cost(path, 1);            // 路径代价，越小越优先，比如直连 0、经中继 1；不设是 0
connection.probe_path(now_us, path);          // 主动验证一条路径，比如对端告诉这一端的候选地址
endpoint.probe(now_us, id, address);          // 同上，Endpoint 按地址编路径号，代价取 PathAddress::cost
```

`Endpoint` 的地址类型是泛型（`PathAddress`）：驱动可以用 UDP 地址以外的东西，比如编号的中继通道，每种地址自带代价。

| 做法 | 内容 |
| --- | --- |
| 主动验证 | 在那条路径上发路径验证包。地址来自已认证的对端或这一端自己，所以不受三倍放大限制，一轮最多 4 个满长度的包（顺便确认这条路过得了满长度的包），约 3 秒放弃。通过后比数据路径便宜或一样才换过去，否则留作备用。打洞时两端同时验证对方：先发的被对方的 NAT 挡掉，但打开了自己这边的映射，对方的验证包就进得来 |
| 不被拉回去 | 对端最新的包从更贵的路径来时，数据路径没断就不跟：这一端先换到直连时，对端要一两个往返才跟过来，这期间它的包还从中继来。跟过去要数据路径安静 `max(300 毫秒, 3 个往返)`，并且连续两次超时或者没有包在途 |
| 断了才退 | 数据路径连续两次超时、又安静了 `max(100 毫秒, 3 个往返)`，自己去验证最便宜的那条更贵的备用路径，通了就换过去。只是丢包、对端的包还从这条路来时不退 |
| 刚换过路径 | 新路径的往返还没量出来，安静的时间按换之前那条路径的往返算；对端来验证这一端在新路径上的地址时不再重量往返和带宽 |
| 不设代价时 | 和以前逐字节一样：306 个换网场景的完整报告与上一版相同 |

模拟器里两端各在一个 NAT 后面（`sim/src/traversal.rs`）：锥形之间、对称型对全锥形或受限锥形都在握手后 65–111 毫秒换到直连，
对称型对端口受限锥形、对称型对对称型、UDP 被挡时一直走中转，数据都完整；直连中途断了 369 毫秒后数据从中转接着走。
详细数据见 [`sim/results/2026-11-05-traversal/`](sim/results/2026-11-05-traversal/README.md)。

## 各平台的驱动

核心不碰套接字和时钟，每个平台配一个驱动。多连接分发都在核心的 `Endpoint` 里，驱动只做三件事：收发数据报、给时间、到点调用 `tick`。

```rust
let mut endpoint = Endpoint::new(random_u32);                     // 新连接号的随机数来源
let id = endpoint.connect(now_us, crypto, config, b"my-app/1", &peer_public, &[], peer_addr)?;
endpoint.listen(b"my-app/1", config, &[], new_crypto, |incoming, from| known(incoming.remote_static()));
endpoint.on_datagram(now_us, from, packet);                       // 收到一个数据报
endpoint.tick(now_us);                                            // next_wake() 到点时调用
while let Some((size, to)) = endpoint.poll_transmit(now_us, &mut out) { /* 把 out[..size] 发往 to */ }
```

| 驱动 | 用在哪 | 内容 |
| --- | --- | --- |
| `udp/` | 测试工具、以后的原生宿主 | 只用标准库：一个 `UdpSocket`、单调时钟、`poll` 循环 |
| `wasm/src/lib.rs` | 自己有事件循环的宿主 | 核心编成 WebAssembly（`cargo build --release -p agent-net-wasm --target wasm32-unknown-unknown`，2026-11-07 为 359804 字节，同工具链改动前为 334263 字节），接口按 C 调用约定手写，不用 wasm-bindgen。数据经两块固定缓冲交换，加密算法从宿主导入，长期私钥不进 WebAssembly。接口约定见文件头 |
| `wasm/node.mts` | 电脑端（Node、Electron） | UDP、时钟、加密用 Node 自带的 `dgram`、`performance`、`crypto`。套件是 X25519、AES-256-GCM、SHA-256。流和核心一样是单向的，另有不用开的默认流 |

Node 驱动的用法：

```ts
const server = await Endpoint.create({ identity, prologue: 'my-app/1', accept: { admit: ({ publicKey }) => known(publicKey) } });
server.on('connection', (connection) => connection.on('stream', (stream) => stream.on('data', onData)));
const connection = client.connect(serverPublicKey, { address, port });
const stream = connection.openStream('interactive');
stream.write(bytes);
stream.finish();                       // 对端读完数据后收到 end
await connection.closeWhenDrained();   // 先结束流、等对端确认再关；关的时候对端收到关闭包，马上知道
```

Node 驱动里两处和平台有关的取舍（2026-11-05，Windows 实测）：

- Windows 上 Node 的 `setTimeout(1)` 实际要等约 15 毫秒，发送节奏、延迟确认和重传都会被拖慢。短于一个节拍的等待改成每轮事件循环看一次时间，
  长的提前一个节拍醒来；代价是传输时那一个节拍里一直在转。改之前本机回环 8 MiB 只有 13.6 MiB/s。
- Node 每次加密都用原始字节作密钥时一个包要 20 微秒，导入成 `KeyObject` 只要 4 微秒。代价是对称密钥要等垃圾回收才释放，不能丢弃时立即清零。

## 从 KCP 蒸馏了什么

| 处理 | 内容 |
| --- | --- |
| 保留 | 累计确认（`una`）加逐包确认、快速重传、1.5 倍退避、窗口探测、未读数据计入接收窗口、最老分片优先重传 |
| 改动 | 重传使用新包号，RTT 没有歧义，第 4 步可以直接作加密 nonce；确认按区间表达，比每分片 24 字节省；包头 3 字节、数据帧 7 字节，1400 字节的包能带 1390 字节，窗口按分片数算，每个分片多带一点，同样的窗口就能多送一点（KCP 是 1376，带 FEC 时 1368） |
| 新增 | 确认之前完整校验包、拒绝确认未发送的数据、窗口打开时主动通知 |
| 第 2、4 步 | 多路流、加密与身份 |

## 传输机制与设计动机

关闭拥塞控制的 KCP 配置会增加发送与重传，遇到限速或小瓶颈时流量开销可能很高。
自研核心先估计路径容量和损伤，再决定发送节奏与冗余。

| 能力 | 做法 |
| --- | --- |
| 带宽估计和发送节奏 | `congestion.rs`，思路来自 BBR：测实际送达速率和最小 RTT，按估计的带宽匀速发送。一轮里丢得比送达还多时带宽样本不老化，短断网和突发丢包时不丢掉估计；连续 8 轮以上照常老化，那是几条连接一起超发，不老化的话每条都以为整条线归自己 |
| 只依赖时间差 | 所有时间起点都在建连或第一次发包时设，不拿 0 当起点或“还没设”。真实设备的时钟建连时早已不是 0，`shifting_the_clock_changes_nothing` 把时钟整体平移后要求每一步都和从 0 开始一样 |
| 区分随机丢包 | 主动降速阶段发的包不可能挤爆瓶颈，这些包的丢失率就是随机丢包率，用它把送达速率换算回路径速率。不做这一步，64 MiB、30% 丢包要 332 秒而不是 6 秒。最近几轮的平均送达速率远低于带宽估计和窗口能送的速率时（令牌桶放行突发把估计抬高了），降速阶段按实际送达速率打七五折，否则限速丢包会混进随机丢包率、越估越高；稀疏消息测到的只是应用发送速度，这时只压到带宽估计的一半。速度卡在窗口上、路径有余量、最近几轮确实按接近窗口的速率送到时，所有包都低于容量，降速阶段不降速，每个包都当低速样本。降速阶段开始时队列还在排，就是别的流排的（自己排的队巡航时已主动排空）：这时送到的包照算、丢的不算，否则几条连接一起启动时估高的随机丢包率在队列一直满着时修正不了。队列浅到往返时间看不出来时，比同一个探测周期里巡航和降速的丢包率：随机丢包和速率无关，被挤掉的包跟着速率涨。巡航明显多丢时收回补偿、同样只算送到的包，这期间限速判断的门槛至少按降速阶段实际的丢包率算 |
| 发现限速器 | 总丢包率远高于低速时的丢包率，说明丢包随速率上涨。这时一段时间内的实际送达速率就是上限，对令牌桶、固定配额、浅队列都成立，不依赖 RTT。第一段从第一次发包算起，建连后空闲的时间不算进送达速率。通常要连续两段速率一致才确认；一段内大半个往返都在丢、低速发的包却基本没丢、没有排队、也不在启动阶段时，一段就确认。确认中断好几个往返的统计段不算：限速器每个往返总会放行一部分，整段中断只能是断网。还没有 RTT 样本时也不算：超时是猜的，长往返路径上第一批包会全被误判成丢包。只量到一次的宽松上限，最近两轮不丢了、送达速率又顶到这个上限时马上放开，那只是一阵突发。确认后任何加速都不越过上限 |
| 确认时机 | Auto、Lean 平时每两个包确认一次，干净路径不多花字节；Fast 每个包都确认。包挨得极近（每秒两万个以上）时，或晚到的包占 10% 以上、平均比后发的包晚 4 毫秒以上时，逐包确认：窗口头上那个包一到，发送方马上就能往前走。窗口装不满路径、又见过丢包时，发送方在包头标一位请对端逐包确认；干净路径和窄带线路不受影响 |
| 窗口受限时不让字节上限卡住窗口 | 校验包、副本和等着校验结果的丢包占在途字节却不占窗口。窗口远小于路径容量、且最近没有超时或断网时，在途字节上限放宽到两倍窗口 |
| 校验包 | `parity.rs`。速度卡在窗口上时每隔几个分片发一个校验包，丢的分片当场算出来，省掉一个往返。用滑动窗口（思路同 RFC 8681）和 GF(256) 柯西码：相邻校验包的覆盖范围重叠，余量共用，所以开销只比丢包率高一点，丢的包等下一个校验包就能修。kcptun 的分组码要等整组发完才能修，确认成批回来，窗口每轮被拖慢几毫秒；每组还要单独留余量。丢的包等校验包的时间约占往返的“丢包率 × 校验间隔 ÷ 2”，所以路径有余量时校验按丢包率的 40 倍逐轮加密（上限 25%），一排队就收 |
| 校验只修能修的 | 晚到的包和零散丢掉的包一样堵窗口，都算进校验量。成片地丢是撞上了容量，不发。带宽是瓶颈时校验包要挤掉数据，余量收窄。确认真丢过包后 5 秒内保持最低比例，不因两次丢包之间的估计回落而关掉；干净路径不发。启动阶段第一次见到丢包就按速度优先的余量发，第二轮里丢的包不用等一个往返 |
| 为抖动多发校验 | 窗口确实卡住、往返 10 毫秒以上时，被抖动拖晚的包也当空洞，逐轮试着多发校验；一轮里最小的 RTT 一涨就减半并压低上限。被窗口限住时测不出路径余量，只能这样试 |
| 乱序不算丢包 | 判丢的包如果确认后到，说明判错了，自动放宽判丢窗口。卡住窗口的那个包例外，它晚补一点全线都要等。按包数判丢时还要看时间：比它晚发出不到三倍抖动的包先到了，不说明它丢了 |
| 小消息不等重传 | 自动策略测到丢包后把小消息的冗余分到独立 UDP 包，不必等下一条消息；平时不叠加旧消息捎带，成片丢包时例外（连接开头 40 个包也捎带，第一个丢包要一个往返才发现；丢过包后捎带 150 个往返、最长 30 秒，往返越短代价越小）：副本和原件同时发出会一起丢，再在后面的包里错开时间捎带一份。确认方向短暂中断时照样复制，数据仍能到，零散丢包只能靠副本补；超过 2 秒的长断网才停，回到保守探测与最老分片优先。省流量策略关闭这些主动冗余 |
| 重传不再丢 | 随机丢包时，窗口被卡住的重传发两份，重传再丢一次就要多等一个往返。启动阶段还量不到随机丢包率，先按总丢包率算，成片丢或量到上限时除外 |
| 启动快 | 初始窗口约按 128 Mbit/s 发出，带宽估计仍不超过 32 Mbit/s；发完后等 150 毫秒，第一个确认还没回来就按 2 Mbit/s 把窗口余下的部分慢慢发出去，长往返路径不用空等一轮，窄带线路也来得及排空。第一批包的确认间隔直接反映路径速率；尚未测得 RTT 时，批量传输的前三次超时只探测一个数据包（零散消息只有第一次），保留其余测量机会，避免初始超时短于真实往返时整个初始窗口被误判重传；启动结束时被窗口限住就不排空，默认窗口下开头没冲过限速时也跳过第一个降速阶段 |
| 减少网络排队 | 启动时 RTT 一涨就停，巡航时发现排队就略微降速；判断排队的余量跟抖动走，抖动小时 10 毫秒的浅队列排到一半就能发现。加速探测丢得明显多于随机丢包时，接下来 8 次探测只加 10%，不再每次挤爆浅队列。同一字节流内部的顺序阻塞仍需后续多路流处理 |
| 断网省流量、恢复快 | 超时一次判完所有超龄的包。短中断最多退避到 2.25 倍（只有零散消息在等时 1.5 倍），网络一恢复很快重连；连续超时 8 次才放慢到 5 倍，并且只发少量探测 |

AGENT_NET_REPLAY=<种子> cargo test --profile sim -p agent-net-sim --test reliability every_seed

## 更早：多条连接挤浅队列（2026-11-05，核心代码指纹 `dc63b35dc075`）

- **原因。** 几条连接挤满一个浅队列时队列一直不空，最小往返里已经含着排队，靠往返时间看不出拥挤。单看一条连接，这和线路本身随机丢包一模一样：
  各条把别人挤掉的包当成随机丢包（这条没有随机丢包的线路估到 7%–42%），按它补偿多发，“撞上限速”的门槛也跟着抬高、失效。

  认别人的队列时余量从至少 4 毫秒降到至少 0.5 毫秒，只影响随机丢包率的样本。
- **先推荐的“持续满发时完全不补偿”被测试拦下。** 随机丢 30%、窗口 4096 时传 64 MiB 从不到 8 秒变成 348 秒，加速探测多发的 25% 抵不过丢包，速度塌掉。

## 更早：看不出的浅队列（2026-11-04，核心代码指纹 `881e0529afb3`）

## 更早：和别的流量共用线路（2026-11-02，核心代码指纹 `78200db22491`）

第 3 步收尾，查出三个单连接精确时钟下测不出来的问题：

- **拥塞崩溃。** 别的流挤掉的包被当成随机丢包，按丢包率多发，四条连接抢 20 Mbit/s 时丢包 71%、两条被饿死。
- **速度被定时器锁死。** 迟到的时间作废，每次醒来只发一个包：4 毫秒的定时器上 40 Mbit/s 的路径只跑 2.8，Windows 默认定时器上约 0.7。
- **探测退不出来。** 限速器把多发的包都丢了，在途量到不了目标，一直多发 25%、白丢 20%。

修法：排队时的丢包不算随机丢包；持续满发时补偿上限从 2 倍收到 1.25 倍；探测撞到丢包后巡航留 10% 余量；迟到的发送节奏补回来；探测见到丢包就结束。

## 已知限制

- 明文的 `Connection` 本身不做认证，直接用它时网络上任何人都能伪造包、注入内容；它的恶意包测试只覆盖崩溃与缓冲内存边界。需要真实性和完整性时用 `SecureConnection`，加密层自己的限制见上文“加密”。
- **很浅的队列上几条连接一起抢时丢包仍偏高**：2026-11-05 改成持续满发时少补偿随机丢包以后，144 种浅队列组合平均丢 5.95%（原来 9.15%），
  23 种超过 10%，最差 39%（8 条连接每隔 0.2 秒加入，挤 100 Mbit/s、往返 12 毫秒、1.2 毫秒的队列）；同样的组合 TCP CUBIC 平均 0.89%。每条连接分不清别人挤掉的包和随机丢包，这是各自判断的根本限制，
  一条连接里跑多条流碰不到。也因此几条连接共享一条随机丢包的线路时用得不那么满（随机丢 10% 时利用率 0.865）。
  1 毫秒定时器下四条连接挤 100M 12ms 3 毫秒队列时公平指数 0.81：每条连接各自判断，先认出的那条收回补偿，让出来的份额被还没认出的拿走。
  见 `sim/results/2026-11-05-shared-shallow-queue/README.md`。
- 两条连接走短往返 5.6M 深桶限速时，精确定时器下公平指数 0.96，1 毫秒定时器下 0.66，这一行在试过的各个版本之间来回跳；根本问题是窗口下限比一个来回能装的还大，还没改。
- 窗口是连接共用的：窗口 128、又比路径容量小时，多路流的文件速度比两条连接低 6%–12%，因为两条连接各有一个窗口。窗口开到 1024 以上没有这个差距。
- 公网文件速度比两条连接低：上传 9%，下载 7%。
- **和 TCP 同跑时 TCP 份额偏低**：公网上传 89 / 13、下载 4.8 / 0.7 Mbit/s，令牌桶线路上模拟 5.4 / 0.2。要让出来就得长期低于上限发，单条连接会明显变慢、输给 KCP。现在按用户之前选的速度优先处理，见产品规则的待裁决。
- 极浅队列（四分之一个带宽延迟积）的高带宽路径上我们偏强，100 Mbit/s、100 毫秒时对 CUBIC 89 / 6。低带宽深队列上偏弱，20 Mbit/s 时 3.4 / 16。
- 四条连接时分得不够均：精确定时器下平均公平指数 0.83、最差 0.67，1 毫秒定时器下平均 0.72、最差 0.39。后到的流看不到空队列，最小往返时间偏高，占便宜。
- 往返时间在 1 秒周期上大幅摆动时，混发的文件速度只有两条连接的 80%。这种摆动下分不清是排队还是路径变慢，只能保守。
- 发送节奏的迟到补偿只在混发时打开。单流路径上定时器迟到同样会吃掉一部分节奏，打开它要重新验证全部单流矩阵，放到后面做。
- 和 TCP 共存用的是模型加一条公网路径，没有手机网络的实测。
- 初始窗口是 64 个包，比 TCP 常用的 10 个大。极慢的链路上第一轮可能丢掉一部分，开销是一次性的。
- 窗口默认 128，产品里应该开到 1024 以上。默认值和多路流的流控一起在第 2 步定。
- 窗口大小目前靠两端配置一致。第 4 步的握手没有协商窗口，握手附带的数据可以用来协商，接入产品时再定。
- 校验包是否够用靠发送方估计，接收方不反馈缺了多少。
- 令牌桶限速路径（窗口 128、16 MiB）上 16 个种子结束时的随机丢包率估计最高 0.86%，额外字节 9%–14%；`rate_limited_loss_is_not_read_as_random` 固定用一个种子，覆盖不到种子之间的波动。
- 窄带浅队列上，链路跑满时带宽估计仍比链路高 3%–5%（确认到达有抖动，取最大值偏高）。加速探测已在发现浅队列后改成只加 10%，重传降到 3.5% 左右，额外字节刚好低于 KCP 普通，余量很小。
- 校验的编码和解码都是表查找，没有 SIMD。校验只在速度卡在窗口上时才发，正常窗口配置下基本不触发。
- 冷启动第一轮只发半个窗口、开头的丢包要等一个往返才补上，窗口 128 的卫星、家宽仍慢于 KCP 的 FEC 配置（它们第一轮就发满窗口并带校验）。握手已经测出一个 RTT（`SecurityStats::handshake_rtt_us`），还没有交给拥塞控制和超时估计，路径带宽也还没缓存。
- 真机换网测了电脑在有线和手机热点之间切（`sim/results/2026-11-05-migration/real-switch/`），以及一台安卓手机自己在 Wi-Fi 和蜂窝之间切
  （`sim/results/2026-11-05-port-change/phone-switch/`），都没断；手机上是测试程序，不是 App，没测 App 进后台、锁屏，也没测 iOS。
  驱动还没接系统的换网通知，自己换了网络却不知道、又在下载的一端要等安静 1 秒后的探测，手机上实测中断 1.0 秒。
- 系统未通知的换网，在对端发现前仍可能使用旧连接号；交号尚未送达或备用号耗尽时也暂用旧号，记缺号次数。
  轮换不能隐藏地址、时间、大小等流量特征，不等于完全不可关联。本轮只做模拟与本机回环，手机换网与后台行为仍需真机复测。
- 路上的人每 8 个包抢先复制一个、领先 50 毫秒时上传明显变慢：一直在蜂窝上传 20 MB 从 17.3 秒变成 32.3 秒，Wi-Fi 切蜂窝从 15.2 秒变成
  68.7 秒；领先 5 毫秒时不慢（`sim/results/2026-11-05-port-change/exp/race-final.txt`）。路上的人本来就能丢包，这不是新的攻击面，
  但慢得比它付出的多，原因还没查。
- 真换了网络时从启动阶段重新量带宽；只换了端口时照旧（2026-11-05），但客户端自己重新绑定端口时驱动不知道从哪块网卡出去，仍从头量。
  没有路径 MTU 探测。空闲连接每 15 秒一来一回。
- 驱动层单线程、没调套接字缓冲区。握手准入在核心里，驱动不用管，见“握手准入”。
- Node 驱动的加解密、收发和核心都在 Node 的一个线程上，局域网满速时 CPU 会先到顶，还没测；Electron 里要放进 `utilityProcess`，也还没跑过。
- 路径只按代价选，不比往返和丢包：直连明显比中转差时也走直连，直到它断了。端口预测没做，对称型对端口受限锥形只能走中转。
- 什么时候重新验证候选地址由上层决定，核心不重试。NAT 映射靠空闲时每 15 秒一来一回保活，映射更快过期的网络空闲后会退回中转。
- 关闭时发两个关闭包，对端马上知道（2026-11-06）。进程被强行结束时发不出来，这一端仍要等判死（有数据在途时 30 秒，空闲时靠 15 秒一次的探测）；
  对端重启以后也认不出旧连接的包，没有类似 QUIC 无状态重置的机制。

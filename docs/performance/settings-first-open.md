# Desktop 设置首开：加载方案验证

2026-11-08，基线 `c2b8af2a6f333a436316cce0d8bffe0aa0ccee4a`。

## 问题与方案

`0f01ea135a` 把整个 SettingsView 改为 route lazy，首次导航需要等待全部设置分区的
代码，期间保留任务页面。当前基线的生产 SettingsView 分包约 3.07 MB（未压缩）。

候选同时处理正式 renderer 的分包与开发服务的冷编译。设置框架和通用页保留在主入口，其他较重的分区用 React.lazy 加载。
同一 Suspense 边界保持在 keyed panel 外面；用户切换使用 transition，加载时保留旧内容，
左侧导航和返回可用。直接进入未加载分区时有局部加载状态。

不能把 Suspense 放在 `key={activeTab}` 的容器里面：该实现实验中每次分区切换重新挂载
边界，首次切换外观和供应商约 330–390 ms。把边界移出后额外等待消失。

待加载时，已显示分区仍是 activeTab。此时再次点击该分区必须允许取消等待，不能被
“已经是当前分区”短路；使用 useTransition 的 pending 状态区分。晚到的模块完成不能
把已退出的用户拉回设置。

## 补验：真实开发服务冷启动

用户反馈原版本首开实际等待数秒。早先的生产 renderer 和热 Vite 服务测量不能代表这个
条件，也不能据此认定用户现场已经修复。重新启动独立 Desktop 与 Vite，启动包装清理
该 checkout 的 `.vite` 转换缓存；**不提前请求设置入口，也不重载主页面来热身**。
主界面出现后立即导航设置，记录资源、长任务与 renderer CPU profile。

| 冷启动方案 | 首开设置 | 第二次打开 | 首次外观 | 首次供应商 |
| --- | ---: | ---: | ---: | ---: |
| 原整页 route lazy | 4205 ms | 41 ms | 未测 | 未测 |
| 仅分区拆包 | 118 ms | 67 ms | 130 ms | 1812 ms |
| 分区拆包 + Vite warmup | 105 ms | 64 ms | 66 ms | 117 ms |
| 同方案再次完整冷启动 | 120 ms | 43 ms | 68 ms | 113 ms |

每行是一次完整冷启动样本，不是中位数。原方案首开新增 305 个资源请求，多条模块请求
约 3.02–3.04 秒，CPU profile 中 idle 约 3.51 秒，记录到的三段长任务共 204 ms。
证据指向开发服务的冷模块请求链，而非数秒的同步组件渲染；资源 duration 包含队列、
服务端处理和传输，不能把它全算作编译 CPU 时间。

仅分区拆包不满足完整体验：把供应商冷编译的 1.81 秒留到了首次切页。因此继续在
`vite.renderer.config.ts` 使用 Vite 自带 `server.warmup.clientFiles`，预转换设置组件
（排除测试）与外部 BillingPage。它仅准备开发服务的模块转换缓存，不在 renderer
执行这些模块、不挂载组件、不发起设置 IPC；正式构建的分包保持不变。

四次从 renderer 文档创建到主界面具备测试条件分别约 28.55、30.72、26.90、29.31 秒。
这包含 dev 冷加载及宿主就绪等待，不是系统进程启动计时；样本少、未控制其他任务负载，
只能说明本轮未看到 warmup 把同量等待转移到主界面，不能承诺所有电脑启动零成本。
正式安装包的完整进程冷启动仍未验证。下面的数据保留为另一个条件下的对照。

## 测量方法与边界

- 使用独立 `--mock --isolated=<测试沙箱>` Desktop，未复用正式数据库或登录态。
- 在同一 Electron 主进程内，对每次新建的 renderer document 做测量；每轮模块缓存重新建立。
- 生产对照使用 `vite build --config vite.renderer.config.ts --outDir <独立目录>` 的产物。
  通过 Playwright/CDP 请求拦截，在隔离实例自己的 origin 上供给这些产物，保留同一 preload
  和 IPC 环境。统一路由处理器保持注册，通过切换产物目录交替测试，避免拦截器重注册的
  空隙使 dev 文档混入样本。检查 timeOrigin 确实变化，且每轮实际收到生产脚本资源。
- 顺序为基线、候选、候选、基线、基线、候选，各三轮；未施加 CPU 节流。
- 页面就绪指标：主界面内容出现并经过两个 animation frame；分区指标：导航开始到目标
  tabpanel 出现并经过两个 animation frame。不是所有异步账号数据已返回或淡入动画已结束。
- 这是**生产 renderer 在隔离开发宿主里的冷文档测试**，不是签名安装包的全进程冷启动；
  不包含 Electron/main 初始化、真实账号网络和磁盘冷缓存。三轮不足以宣称统计显著性。

首开中位数降低约 69%，首次供应商切换增加约 34 ms。启动脚本增加 433,549 字节
（约 2.8%），主界面就绪样本增加约 56 ms。不能描述为“零启动成本”或“所有操作都更快”。
整页提前加载方案的开发模式对照首开也变快，但会把全部设置依赖搬回首屏；未选用。

开发模式（服务端转换缓存已热，每轮新 renderer document）的对照中位数为：
基线首开 216 ms，候选首开 84 ms，外观 44 → 49 ms，供应商 51 → 82 ms。
生产与开发数据分别呈现，不混合计算。

## 功能验证

- SettingsViewEscape 与 settingsSearchCatalog：94 项通过。原同步断言改为等待真实异步
  页面完成，保留原断言；新增 pending section 的 Escape 与取消切换回归。
- `pnpm ui:check --page settings-search --case all --theme all`：36/36，通过真实设置组件
  和搜索定位，涵盖浅深色、语音、远程、计费等场景，账号/宿主响应为夹具。
- 独立实例拦截真实外观模块请求：加载未完成时原通用内容、导航仍可见；Escape 立即退出；
  晚到模块不重新打开页面；重新点通用取消未完成切换。
- 独立实例直接以外观深链打开成功。
- Desktop 类型检查、生产 renderer 构建通过。

UI 夹具打包本身不能验证生产分包时序，因此另外做真实模块延迟验证。未验证真实账号下
所有设置写入、升级安装、Windows/Linux 或低性能机器；本次不修改设置值和存储行为。

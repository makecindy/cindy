# 目录恢复限并发：当前版本性能对照（2026-11-04）

基线：`cd6c1b8dd23661fb8b1d0d9fc3d34cf7a19327dd`。仅保留 `useFileTree` 的目录恢复限并发及其回归测试；watcher 分片实现及新增测试已撤回，旧事件风暴报告移至本地实验归档。本报告记录提交前的轻量实验。

## 结论

后续已补充 [完整 Desktop 界面对照](directory-restore-full-ui-2026-11-04.md)：200 目录的根目录可见帧提前约 23%–24%，但全部恢复帧没有稳定提速（浅色快 2.2%，深色慢 2.9%）。下面的 21% 不能表述为完整界面整体提速。

当前版本仍有明确的数据恢复收益。恢复 200 个展开目录时，总耗时中位数降低约 21%，根目录就绪时间降低约 84%，主进程最大 timer 延迟降低约 88%；并发峰值从 201 降到 8。恢复 50 个目录时也有改善，0 个展开目录的对照基本持平。

这些结果验证的是请求调度、真实目录扫描和 hook 数据恢复，不是完整文件树首屏绘制，也不能据此认定 #8422 的约 13 秒卡顿已解决。

## 方法与边界

- Windows 10.0.26200，Intel Core Ultra 7 265K，Node 24.14.1、Electron 42.11.12。
- 同一临时项目含 200 个目录，每目录 128 个文件，共 25,600 个文件、约 143.75 MiB。独立测试进程使用临时 profile，不访问正式账号与业务数据；结束后清理本轮创建的临时目录。
- 基线 hook 从当前 `HEAD` 构建；优化版从工作区构建。其它生产实现相同，双方 watcher 均为当前 `HEAD`，无事件风暴注入。
- 生产 `useFileTree`、`expandedStore` 和 `file-browser-core` 扫描器，通过测试用 Electron IPC 连接。日志、watch 注册及设备重连使用实验适配器；Renderer 是轻量 React 订阅组件，仅显示目录列表数量，窗口隐藏，不包含完整文件树、代码预览与布局成本。
- 先构建两个版本，再生成一份共同文件夹；按「基线、优化、优化、基线」四批运行，每批为新的 Electron 进程。每批分别恢复 0、50、200 个展开目录，每种规模运行 11 次，剔除第 0 次预热。每版本每规模 20 个有效样本，共 120 个；JSON 同时保留全部 132 个样本。
- 各轮卸载 hook、清空测试页面 localStorage、写入对应展开目录，然后重新挂载；同一批复用进程和 matcher。未清空操作系统文件缓存，因此不代表冷磁盘性能。
- 总完成与根目录就绪从挂载请求开始，截止相应数据在 React effect 中可见；不是屏幕绘制时间。主进程延迟为每轮 5 ms timer 最大超期，再跨样本取中位数，测量窗口包括完成后的 30 ms Renderer 排空及 20 ms Main 排空。Windows timer 调度噪声也计入。
- 每轮检查全部目标目录都已加载、每个目录有 128 个文件、根目录有 200 个目录、loading 清空、initialLoading 结束、扫描次数等于展开目录数加一。全部 132 轮通过，无重复扫描或遗漏。
- 性能采样完成后才启动本轮单测和类型检查，避免这些检查干扰采样；未控制机器上其它应用的负载。

## 结果

以下是中位数，耗时单位为 ms；每格为「基线 → 优化」。

| 指标 | 0 个展开目录 | 50 个展开目录 | 200 个展开目录 |
| --- | ---: | ---: | ---: |
| 数据恢复完成 | 2.9 → 2.9 | 42.6 → 37.3 | 169.3 → 133.9 |
| 根目录数据就绪 | 2.9 → 2.8 | 32.3 → 6.3 | 41.4 → 6.6 |
| 目录请求并发峰值 | 1 → 1 | 51 → 8 | 201 → 8 |
| 主进程最大 timer 延迟 | 11.0 → 11.1 | 18.8 → 10.9 | 91.7 → 11.1 |
| 最大 IPC ping 往返 | 0.3 → 0.3 | 21.3 → 2.0 | 93.5 → 2.2 |
| 目录扫描次数 | 1 → 1 | 51 → 51 | 201 → 201 |
| React 订阅组件 render 次数 | 6 → 6 | 106 → 106 | 406 → 406 |

200 个目录的恢复总耗时范围：基线 153.3–192.9 ms，优化 127.1–141.5 ms；根目录就绪范围：基线 25.0–62.0 ms，优化 4.6–8.4 ms。保留全部有效样本，没有剔除慢样本。20 个样本不能证明生产尾延迟稳定。

优化没有减少扫描次数或本实验中的 render 次数。收益来自控制同时在途的目录恢复请求；8 是恢复队列的并发数，不是所有用户操作、watcher 刷新或多设备资源使用的全局上限。

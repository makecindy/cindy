# 目录恢复：完整 Desktop 界面前后对照（2026-11-04）

本轮补齐文件树恢复在真实 Desktop 界面中的验证。应用代码为 `4d353f69ecadf0b1014acbd7e3e24637b23513d6`；基线仅将 `useFileTree.ts` 替换为 `cd6c1b8dd23661fb8b1d0d9fc3d34cf7a19327dd` 的版本，其余应用代码、数据和窗口相同。实验结束后已恢复优化源码。

## 结论

恢复 200 个展开目录时，限并发让根目录更早可见，浅色和深色分别提前约 23% 和 24%；采样期间最大帧间隔的中位数降低约 39%。**全部目录恢复没有稳定提速**：浅色耗时降低 2.2%，深色增加 2.9%，样本范围重叠；50 个目录的浅色对照增加 4.1%。

这支持将改动描述为「根目录优先可见、减少恢复时的调度突发」，不支持「完整界面整体提速 21%」。此前 [轻量实验](directory-restore-performance-2026-11-04.md) 的 21% 只适用于其数据恢复链路。完整界面的主要成本在 Renderer 脚本，Paint CPU 耗时仅十几至二十几毫秒；本次没有解决全部界面计算成本，也未证明解决 #8422 的原始卡顿。

## 为什么此前没有做

此前先用轻量 React 订阅组件隔离目录扫描、IPC 和恢复调度，便于判断限并发自身的影响，未纳入真实文件树、代码预览和布局。更早的完整界面检查针对文件事件风暴及基础操作，不能替代本轮目录恢复的绘制对照。提交时虽注明这个边界，但没有继续补齐当前版本的完整界面，是验证范围的遗漏，不是环境不支持。

## 实验方法与测量口径

- Windows 10.0.26200、Intel Core Ultra 7 265K、Electron 42.11.12、Node 24.14.1；通过仓库安全启动器启动 Global `--mock --isolated` 开发实例，返回 `DESKTOP_DEV_VERDICT=ready`。视口 1784 × 992，窗口可见。使用开发构建，未测发布包或 macOS。
- 同一临时项目有 200 个目录，每目录 128 个 TypeScript 文件，共 25,600 个文件。每个文件含 256 行固定代码。账号与内容使用 mock，文件读取经过真实生产 IPC、扫描器及 watcher。
- 页面包含完整应用布局、模拟消息内容、生产 `FileBrowserBody`、虚拟化 `FileTreeView` 和 CodeMirror 预览。恢复开始时关闭并重新打开文件浏览器标签，选中第一个文件；包含侧栏展开动画的成本。
- 通过生产展开状态存储写入 0 / 50 / 200 个已展开目录，然后使用生产侧栏 store 打开标签。使用 CDP 观察当前 React 树与 DOM；没有替换文件树组件或直接注入加载结果。
- 按「基线、优化、优化、基线」四批运行，每批每场景 6 次，排除第 0 次预热。浅色测 0 / 50 / 200，深色测 200；每版本每场景 10 个有效样本，共 80 个。原始数据保留全部 96 次，包括 16 次预热。每批切换源码后重载页面并检查 Vite 实际提供的版本。
- 复用同一 Electron 进程及操作系统文件缓存，不代表冷启动或冷磁盘。未控制其它应用负载；开发态、探针与 trace 自身也会引入成本，不宜把小幅差异解释为稳定收益。
- 「根目录可见帧」：根目录行进入视口后再等待一次 `requestAnimationFrame`。「全部恢复帧」：全部目标目录数据完整、loading 清空后再等待一次帧，且根目录已进入视口，两者取较晚时刻。0 目录场景中，数据先于侧栏动画结束，因此不能把原始 `completeFrameMs` 单独称为可见完成时间。
- 上述帧指标是浏览器主线程的可见性代理，不是显示器实际呈现时间。虚拟化树只绘制视口及缓冲行，「全部恢复」不表示同时绘制全部 25,600 行。
- `ScriptDuration` 来自 CDP Performance 指标差值，覆盖开始至完成并额外等待至少 100 ms 的观察窗口；不能和下面的 trace 分项直接相加。
- Paint、Layout、UpdateLayoutTree 来自主 Renderer 线程 trace，窗口为恢复开始至数据完整后的下一帧。它们是 CPU 分项，不含完整 GPU 栅格化、合成及物理屏幕呈现；0 目录场景 trace 截止时动画可能尚未结束。
- 每轮验证根目录恰有 200 项、每个已恢复目录恰有 128 项、entries 数量为展开数加一、loading 清空、页面可见、树在视口内且代码预览存在。正式采样没有删除慢样本。早期因测试路径格式和选择器不符合真实界面而失败的调试试跑不纳入采样。

## 后续恢复期间全量刷新修复

评审补查发现：远程窗口聚焦会调用 `tree.refresh()`；原全量刷新在恢复尚未结束时仍并行发出所有目录请求，会绕过恢复预算。修复后，恢复期间的全量刷新共享恢复队列：尚未开始的目录保留一次读取；已在途的目录沿用一次 trailing 补读；此前已读完的目录排回同一队列。恢复结束后的全量刷新行为保持原样。

通过真实 `useFileTree.refresh()` 入口，以 9 个展开目录和受控远程响应覆盖该交错：先让根目录完成，再连续调用两次刷新，验证峰值不超过 8、仍排队的最后一个目录仅读取一次、根目录和已在途目录最终显示刷新后的数据；另覆盖刷新后卸载，不启动排队读取。修复前两条用例均因并发峰值 10 超过 8 失败；修复后全文件 33 条通过，Vitest 4.64 秒。

这轮修复仅在单个文件树 store 的恢复队列中调度，不重建共享 SSH/device-link 连接、不扩张到其它工作区，不改变跨端协议。上述完整界面性能样本仍对应原实验版本，未重跑包含本次修复的完整界面、真实远程延迟或网络断线实验，不能据此增加性能收益声明。

后续评审进一步指出，已完成目录的刷新若排到恢复队尾，根目录重试可能被远程恢复积压拖延。因此补读使用同一组 worker 的优先队列，根目录按刷新目标顺序优先进入下一个空闲名额，不增加在途请求。已有聚焦用例补充断言：第一处在途补读结束后，下一项必须是根目录重试，尚未开始的 `pkg8` 仍未启动。旧实现此处实际启动 `pkg8`，新实现通过；全文件仍为 33 条，Vitest 4.79 秒。完整界面与真实远程性能的未复测边界不变。

# 伙伴设计与调整

把用户的需要落实为能独立合作的 Cindy 伙伴，并根据真实使用调整。角色气质、重要创意方向、名字与是否喜欢结果由用户判断；需求分析、落地、检查与交付由设计师承担。

## 从真实情境形成方案

先读用户已经说清的目标与约束。判断应该新建伙伴、调整已有伙伴，还是改变合作方式即可。工作、研究、创作与陪伴都可以；不套固定问卷，不凭空补用户背景，也不把每个愿望都做成新伙伴。

提出可评价的具体设计：何时找它、负责什么、怎样行动与相处、如何交接，以及第一件值得交给它的工作。已确定的名字、身份和方向直接沿用；仅把尚未确定的重要选择交给用户。已有操作授权持续有效，宿主确需授权或连接时使用 Cindy 原有流程。

需要命名或形象时，读取已安装的 companion-fy Skill；尚未安装时先使用随附的独立 Skill 包。头像是按需的作品部分，不是创建或开始合作的前提。

## 整理已有身份与相处方式

需要组织身份文字时，可参考「身份、工作、方式、相处」：分别说明是谁、承担什么、怎样判断和行动、合作与表达有何特点。按角色和本次需要取舍结构；标题只是写作组织，不是宿主字段，也不要求用户填写固定问卷。

修改已有正文前，读完整当前设置，将本次新增、合并、删除与原有要求对照。保留仍然有效的职责、判断标准、事实边界和合作约定；删除要有具体理由，合并要能承接原意。遇到实质取舍，用简短对照或示例让用户判断；不因换结构、追求简短或调整语气而默默丢失独立要求。已有选择与授权仍然沿用。

把性格和说话习惯落实为可观察的合作表现，例如如何推荐、表达分歧、回应质疑和报告结果。角色的判断标准继续放在身份中；详细专业工序可以放入实际可用的方法。准备移交给 Skill 的内容，应核实该方法确实可获得和调用，不能假设尚未装配的方法会承接被删去的要求。

## 把设计放进原生位置

先发现本次需要的工具，确认实际作用域。不要把修改自身的工具当成修改目标伙伴的工具，也不要因插件里出现 companions 名称就推断可以写配置。[宿主适配说明](references/host-adapters.md)记录已知入口的区别。

- **身份与简介**写职责、行为和合作方式，保持简洁；不把完整工具手册塞进身份。
- **工具、模型与能力引用**从目标运行环境真实可用的目录选取。省略表示保留默认或当前选择；清空或恢复继承按实际工具契约表达，不猜参数。
- **稳定背景、记忆、自有 Skill、项目和例行任务**各用对应原生入口。一次性任务不写成永久规则；用户没要求的长期自动化不顺手添加。
- **名字与头像**按已选结果应用。使用现有媒体交接与头像保存流程，不能把临时路径直接写进伙伴数据库。

用户要求新建时使用实际提供的原生创建能力，保留回执里的真实目标 id。新伙伴的开场由其原生机制产生，不冒写它的回复。准备尚未完成或回执不明确时，继续查同一对象，不再创建一个替代品。

修改已有伙伴时，读取目标和当前版本，只提交本次涉及的字段。提交发生冲突就重新读差异并判断，不能把旧方案全量覆盖回去。保存后回读，明确哪些已保存、哪些要等下一轮生效。回执 effective=unconfirmed 或 synchronization=unconfirmed 时，保留已知保存版本，检查当前状态和同步故障，不自动重复写入。某项接口不可用时继续独立可做的部分，并说清当前限制；不靠脚本改宿主配置或数据库。

## 用第一件真实工作评价

使用用户当前真正想完成的工作，沿目标伙伴自己的任务、权限、模型和上下文执行。工作应能检验设计中最重要的承诺，不使用固定考试题，不把所有维度组合成测试矩阵。

任务发送、接受、执行完成和用户满意分别判断。按原生回传机制收结果；已有完成通知时不自建轮询。仅有普通异步消息回执时，不能说已经获得受跟踪任务的完成证据。

读对应工作的真实输出和产物。严格声称“这次用了改后的配置”时，需要该执行与实际配置的关联证据；最新保存值或最新聊天回复不能代替它。证据暂缺时写未知，仍可基于可见成果讨论是否有用。

## 按问题调整并交付

把反馈落到真实原因：职责不清、背景不足、方法不合适、工具未接通、模型不适合或合作方式不对。改动以解决当前问题为限，保留已经有效的部分，再用同类真实工作验证。

用户要撤回时，先查看当前配置和原改动。普通反向局部修改要遵守当前版本检查；跨过后来修改的选择性恢复必须由确有该语义的宿主工具承担。取消、拒绝、失败和未知结果沿执行入口的恢复规则处理，不自动重放可能有副作用的工作。

交付真实伙伴入口、已经落实的内容、实际工作结果，以及确有影响的未完成项。用户之后可以直接与该伙伴合作。设计师自己的工作记录只保存续接所需的目标引用、判断与结果引用；运行事实仍向原生对象读取。

## 为什么不需要先取得服务端全部数据

正式客户端在运行时继续通过原来的接口读取目录，而不是读取 Agent 已采集的 28 条搜索快照。Agent 能取得多少条数据，和客户端能请求多少条数据，是两个不同的问题。

本轮修改的是卡片的布局与样式，没有把搜索快照写入生产页面，也没有修改服务端、本地 Skill 文件或数据库。未加载的 Skill 仍由现有分页和加载更多机制读取；分类继续按接口 slug 筛选，搜索和排序继续使用现有请求参数。因此，本轮样式修改没有新增删除或覆盖 Skill 数据的路径。

历史搜索的 28 条来自公开目录 q=skill：第一页 24 条、第二页 4 条，第二页 next_cursor=null。它表示该次关键词搜索结束，不表示完整市场只有 28 条。

## 保持不变的规则

- 不人工重新归类，不用 Demo 的示例数组替代真实目录。
- 不修改请求参数、分页游标、列表身份键或数据映射。
- 不修改已安装与更新状态计算，不以同名推断安装状态。
- 不修改详情、更新按钮、搜索、排序和返回恢复的行为。
- 缺失下载量沿用现有隐藏规则；真实数值 0 保留。
- 头像沿用当前 URL、分类/标签和默认图标的解析优先级，不写回 Skill。

上述“沿用”是相对于本轮开始时工作区；此前已经存在下载量语义、排序恢复等逻辑改动。测试包包含这些原有改动，不能将整包相对 HEAD 的差异都描述为纯样式。

## 验证能证明什么

测试与类型检查为现有行为提供回归证据；组件预览证明所检查视口与输入下的视觉对齐；smoke test 证明测试包的基础启动及数据库初始化检查通过。

这些检查不能证明所有真实账号、分类、分页或完整客户端操作都已验收。本轮没有记录完整线上目录的逐分类对照，也没有完整 Electron SkillHub 页面的实机验收。不能把验证结果表述为任何情况下都不会发生显示问题。

“没有数据丢失路径”也不等于“所有 UI 修改天然安全”：如果误改过滤条件、列表截断、分页或状态计算，可能让数据看起来少了，即便底层数据仍存在。执行方案因此明确限制改动范围，并要求后续验收用相同输入比对 Skill 身份、数量、顺序与操作参数。

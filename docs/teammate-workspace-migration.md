# 迁移伙伴工作区

用户可以通过三种入口把伙伴的工作区存放或搬到本机其他磁盘：

- **默认目录解耦（新建伙伴）**：在「设置 → 存储 → 伙伴工作区」中选择其他本地磁盘目录（配置保存在 `<ownerRoot>/buddy-workspace-settings.json`）。之后新建伙伴在首次 `ensureBotWorkspaceDir` 时，会直接在目标盘创建 `<自定义根目录>/<伙伴目录>-workspace`，并在原逻辑路径 `<ownerRoot>/bots/<伙伴目录>/workspace` 建立 junction/symlink 且写入 `completed` 回执（享受同样的掉盘保护与界面展示）；已有伙伴保持原位不受影响。
- **单伙伴迁移 UI（存量伙伴）**：在伙伴「设置 → 高级配置 → 工作区位置」中选择目标父目录，预览大小、文件数与链接数后登记迁移（可选立即重启执行或下次重启执行），也可查看迁移状态、取消未执行请求或打开当前工作区。已搬到其他位置的伙伴可以再次选择目标，或用「搬回默认位置」回到该伙伴原来的 Cindy 目录。
- **Agent 对话（存量伙伴）**：要求 Agent 通过 `cindy_helper` 的 `teammate_workspace_migration` 完成预检、登记、查看结果或取消。

目标是一个尚不存在的绝对目录，其父目录必须存在（界面选择父目录后由主进程自动派生尚不存在的 `<伙伴目录>-workspace` 子目录，并通过带时效的 `grantId` 绑定归属）。唯一允许已有目录入口的目标是该伙伴自己的默认工作区路径，且必须是 Cindy 可核实的现有迁移链接。搬回时先在其旁边建立临时副本，不覆盖链接或已有的用户目录。

桌面端在「冷启动独占迁移」期间，会通过 `SplashScreen` 展示阶段、进度条与已复制/总字节数，并在迁移完成前保持启动页不卸载且隐藏 Windows 关闭按钮，避免大目录迁移期间误判卡死而强杀进程。

宿主必须保证伙伴固定工作目录的解析、停写与失败恢复，现有普通文件工具无法完成这些边界；
因此只新增上述受控原语与本机 IPC（`local-db:bots:workspace-migration:*`），供界面与 Agent 共用同一套事务核心。
当前只接受运行该伙伴的本机任务与本机界面；从手机或同账号远控发给该电脑 Agent 的请求仍在该电脑执行。
SSH 任务、共享任务访客和非主人 IM 参与者不能借此操作本机伙伴。
工具与界面都不直接迁移另一台电脑的目录，不新增跨设备协议。

## 操作与范围

| action | 行为 |
| --- | --- |
| `preview` | 提供 `teammate_id`、`target_directory`，检查目录边界、文件种类和剩余空间，统计大小与链接。只读，不复制运行中的数据。 |
| `request` | 使用相同参数登记迁移；通过普通任务的 Full Access / Auto / Ask 权限流程。返回 `pending` 代表已安排，尚未搬迁。 |
| `status` | 只提供 `teammate_id`，读取本机真实阶段、当前目录是否可用、当前外部位置（`currentTarget`）、本次目标及保留副本的位置。请求回执不确定时先查状态，避免重复操作。 |
| `cancel` | 只提供 `teammate_id`，撤回尚未执行、失败或已确认恢复原目录的中断请求，沿用任务权限流程；保留已经产生的副本。 |

搬迁对象只有 `<ownerRoot>/bots/<伙伴目录>/workspace`。
V2 的 `.git`、`.cindy/memory`（包括索引和 WAL）、`.agents/skills`、自动任务配置和普通工作文件
都随工作区迁移。Bot Home 的身份、配置、V1 记忆归档、授权和其他内容保持原位。

如果工作区没有自己的 Git 仓库，Claude Code 搬迁后可能从新位置的上层目录发现技能，
导致伙伴可用的技能发生变化。若不希望引入上层技能，请选择上层目录未配置 Claude Code 技能的目标位置。
迁移不改变 Claude Code 原有的技能查找规则。

内部符号链接按链接复制，不递归复制链接目标；跨出工作区的相对链接改为原指向的绝对路径。
硬链接和特殊文件明确拒绝，不悄悄改变其语义。Windows 目录链接使用 junction；文件符号链接
仍取决于系统权限，创建失败时保留原目录并报告失败。

## 停写与恢复

登记不会关闭 Cindy 或中断当前任务。Agent 应说明：先结束使用这个工作区的外部编辑器、脚本等，
再正常退出并重新启动宿主。只暂停伙伴不能停止全部记忆和自动任务写入，因此不在运行中的
Agent 工具或有时间上限的退出清理钩子内复制。

Desktop 和 Node Host 都在打开该 owner 的数据库、放行其任务/记忆/调度服务之前处理请求。
同一进程内的账号切换不执行新请求；登记进程仍存活时也不执行。
登记时保存系统报告的进程启动身份，恢复时不只检查 PID 是否存在；PID 被新 Cindy 或其他进程复用、
且新的系统启动时间明确晚于记录时，可以执行恢复。旧回执缺少身份、身份查询失败或结果不足以证明复用时，
仍保守等待原登记进程退出，不以不同的应用随机令牌认定进程已死。
已有 schema reader 使启动只能取得 reader 租约时不能迁移。启动顺序约束的是 Cindy 自己的服务，不是任意外部程序的文件锁。
若此时原目录或已提交的链接仍可验证可用，保留请求并允许应用启动，`status.startupWarning`
说明正在等待独占启动；不为等待迁移而冻结整个账号。
共享正式数据的个人测试版本始终使用 reader 租约，因此只登记或查询迁移；应退出共享该数据的实例，
再启动原版本执行，不能仅反复重启个人测试版本。
复制前后及切换前复核目录身份和内容，发生变化则保留原数据、报告失败。

目标目录通过排他 `mkdir` 创建。复制逐项拒绝覆盖；中断后只有目录身份仍匹配当前迁移的目标
可以继续，已有文件必须与源内容一致。原目录在内容/权限/链接语义校验和链接能力测试完成前不移动。
复制文件逐个刷盘，POSIX 的目录项从内向外刷盘；Windows 的 Node API 不支持目录 fsync，
实际断电行为仍需要目标平台验收。

切换先把原位置的目录或链接改名，再在原路径建立指向目标的 junction/symlink，或者将搬回的临时副本改名为默认工作区。切换前不改动当前工作区。
因此已有数据库工作目录、定时脚本的绝对路径和伙伴启动入口继续使用原逻辑路径，
不批量改写历史任务、脚本正文或数据库 schema。原路径链接是迁移契约的一部分，不能自行删除。
目标不可用或链接丢失时拒绝创建空工作区。
删除伙伴时沿用 Home 清理行为，只移除其中的工作区链接；数据盘上的迁移目标保留，避免递归删除用户文件。

账号内的 `workspace-migrations/<伙伴 ID 摘要>.json` 保存小型恢复回执，0600 原子替换并刷盘，
不存文件内容、聊天正文或凭证。再次迁移时，回执还记下上次实际位置和目录身份，登记或取消新请求不会失去对该位置的保护。`pending → copying → prepared → switching → linked → completed`
记录复制和切换边界；失败时为 `failed`，撤回为 `cancelled`。
切换中断且原路径尚未链接时恢复原目录；已证明链接和目标身份匹配时接受已完成的切换，
不以旧副本覆盖目标后来写入的内容。完成记录落稳后，只有目标和备份都仍与原快照一致时才清理备份。
若恢复时目标已有后来写入或删除的内容，接受目标但保留原备份供核对，避免误删唯一的原始文件副本。
清理失败保留备份并在以后独占启动时重试；已改变或部分删除的备份不会被盲删。
完成记录写入失败时，先恢复可验证的原目录再放行启动，保留目标副本。只有完成记录落稳后才向目标写入。
恢复后的原目录或已提交目标已验证可用时，失败记录或清理状态写入失败不会阻断启动，
也不强迫重建目录；`status.startupWarning` 返回 `MIGRATION_RECEIPT_UPDATE_FAILED`，之后启动再修复记录。
临时回执清理失败不覆盖原写入结果。若已完成迁移的目标盘离线，应用仍可启动，只有对应伙伴等待目标盘恢复，
不会悄悄退回旧副本。该伙伴的云端资料上传跳过本轮，保留已经上传的记忆、技能、项目规则和自动化。
仍在执行的迁移、损坏且无法辨认的回执、或原目录/备份/已提交目标均无法验证的情况，
继续阻断不安全的启动，保留现场与副本，不以空工作区冒充已恢复。

失败副本不覆盖、不自动清空。目标出现外来文件、部分文件不一致、目录身份变化等情况会停止迁移。
单个文件复制中断后也可能留下不完整文件；这种情况下保留副本并使用新的空目标重试，不截断或覆盖已有文件。
Agent 应先解释 `status` 的原因和保留位置，再按用户意图选择新的空目录。登记不同的下一次迁移时，
旧记录写入同账号的 `workspace-migrations/history/<伙伴 ID 摘要>/`，当前状态返回该目录，
保留之前副本的可追溯位置。再次迁移失败时恢复上一处目录的访问，不回退到更早的副本。搬回请求失败时，已产生的副本仍留在伙伴目录下的 `.workspace-return-<请求 ID>`。
未经 Cindy 记录的工作区链接仍不可迁移，预检返回 `WORKSPACE_ALREADY_REDIRECTED` 并保留现有链接与文件；伙伴 Home 被重定向则返回 `BOT_HOME_IS_REDIRECTED`。

## 验证边界

自动回归通过生产工具索引、权限入口和临时目录运行迁移核心，覆盖正常迁移、逻辑路径后续读写、
技能链接、V1 Home 保留、目标冲突、复制中断、切换中断、掉盘、取消与原路径防误建。
这些文件系统/工具测试不等同于完整 Cindy 安装包或真实 Windows 伙伴验收。

Windows 实机仍需验证：跨盘文件与链接内容、文件链接权限、记忆数据库恢复、伙伴后续读写、
定时脚本的原绝对路径、正常重启和异常中断。验证时只使用隔离伙伴和样本目录。

### 可复核的隔离样本

从仓库根目录运行以下命令；Node 必须匹配当前安装的 `better-sqlite3` ABI。
样本只在 `os.tmpdir()` 下创建独立目录，结束时清理自己创建的样本，不启动客户端、登录或调用模型。

```sh
cd apps/host
node --import tsx --import ./src/loaders/register-raw.mjs scripts/workspace-migration.e2e.mjs
```

2026-11-18 在 macOS、Node 26 / ABI 147 下执行通过。脚本使用真实子进程登记并退出，
保留未 checkpoint 的 SQLite WAL；通过生产迁移入口搬迁后读取 WAL 数据，使用迁移前的
脚本绝对路径及工作目录执行脚本，核对脚本写入在下一次恢复后仍存在。
另一份隔离样本模拟切换中目标盘消失、回执原子替换持续报 `ENOSPC`，调用真实
`openOwnerDatabase` 两次，验证原目录恢复、WAL 可读、原目录后续写入保留。
成功输出一条 `MIGRATION_SAMPLE_RESULT`，其中以下字段均为 `true`：
`realRequestProcessExited`、`originalAbsoluteScriptAndCwd`、`migratedWalReadable`、
`missingTargetDuringCutover`、`originalRecovered`、`originalWalReadable`、
`ownerDatabaseOpenedTwice`、`journalWritesStillFailing`、`originalLaterWritePreserved`。
这是同盘隔离样本，不代表跨盘、完整客户端、调度器或真实伙伴 SDK 已通过验收，也不代表 Issue 全部范围已完成。

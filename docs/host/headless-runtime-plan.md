# Cindy Host：完整后台实施与验收

2026-11-10。接续 [维护计划](maintenance-plan.md) 的接口、连接恢复和真实浏览器验收。
目标已从基础网页版扩展为：**同一套 Cindy 后台服务桌面、手机和网页，也能部署在没有
图形登录会话的 Linux 服务器上。** 本文是后续工作正本，不代表这些能力已经完成。

状态：下文各批实施记录对应的改动已于 2026-11-10 随 [#9621](https://github.com/makecindy/cindy/pull/9621) 合入 main，
Host 仍是主动开启的实验功能。记录里的「本地」「未提交」是当时的状态，不代表现状；
仍未验收的范围（真实已登录桌面、打包版运行时、Windows 与手机实机）以各节的未完成项为准。

本文的实现入口是 `apps/host`。仓库另有 `apps/cindy-headless` 及其评测运行时、独立
打包流程；二者的产物与验收记录分别管理，不能相互作为功能完成的证据。

## 用户得到什么

- 后台运行后，即使没有客户端连接，任务、插件和自动化也能继续工作。
- 桌面、手机、网页连接同一个后台，看到同一任务、历史、队列和待确认操作；
  关闭一个客户端不停止后台，停止任务与退出后台是两种明确的操作。
- 首次启动、登录、查看状态、查看日志、更新与停止都有可用入口，不要求打开 Electron 窗口。
- 普通桌面继续使用原有默认启动方式；后台模式主动开启，迁移期间不自动接管正式 profile。

“完整”指共用业务能力与权限语义，并不表示服务器凭空拥有显示器、摄像头或系统桌面。
录屏、系统对话框、全局快捷键、屏幕控制等需要相应设备；客户端应呈现实际执行位置和
不可用原因。调用其他设备的能力必须经过原有远程授权，不能自动改在控制手机上执行。

## 依赖与所有权

```text
桌面界面 / 手机界面 / 网页界面
           │
   本机 IPC / Device Link / 本机 HTTP + SSE
           │  身份校验、来源、权限、能力协商
           ▼
   共用业务服务（任务、交互、账号、插件、自动化）
           │
   maker-core + 同一份持久化与迁移 + 平台适配器
           │
   桌面启动器 或 Node 后台启动器
```

- 业务服务不依赖 BrowserWindow、ipcMain、renderer 或全局 Electron stub。现有纯模块先
  合并调用入口，再按实际依赖闭包迁入共享 package；不建立只转发调用的空服务框架。
- `maker-core` 保留 Agent 编排；`maker-shared` 保留纯类型、协议和纯逻辑，不塞入数据库、
  凭证、网络监听或进程生命周期。平台启动器提供文件位置、凭证、子进程与展示适配。
- 一份账号 profile 只有一个运行时写入者。沿用 [多账号架构](../dev-rules/multi-account-database-architecture.md)
  的所有权和租约边界，不并行打开正式 profile，不复制正式登录态到测试环境，
  不重写历史 migration。服务取得 owner 与 generation 后，异步结果不能跨账号落地。
- 远程调用复用 Device Link，不能把本机 bearer 暴露公网后当成手机登录，也不能把所有
  Electron IPC 一次性开放。控制端身份由连接确定，权限在执行端再次校验。
- 每项能力按实际装配情况声明。未接通的写操作不能返回成功；旧客户端与新后台必须能
  协商现有能力，新字段不能破坏旧协议。涉及自建 relay 时同步适配与互通验收。

## 分批交付

### 1. 共用任务服务

先消除双份业务规则，再迁移模块位置。普通列表是第一刀，接着是任务详情与历史、任务创建
和设置、输入派发与停止、权限回答和队列。每次迁移都保留普通桌面和现有手机入口的回归。

完成条件：两个启动器进入同一份任务服务，不再分别装配不同的执行语义；账号切换时旧请求
失效；队列重启不丢、不重复执行。已经派发但结果不明的操作标记中断，不自动重放可能有
副作用的工具；沿用现有数据库和迁移流程实现必要的持久化。

本批已完成普通列表、详情、持久队列、消息写入与事件归约、交互路由和子任务读取的共用入口，见下方记录。任务创建现已使用原服务；Agent／凭证完整装配和共享 package 抽取尚未完成。

### 2. 所有客户端接入后台

在第 1 批的服务入口上，把现有 Device Link 被控端从 Electron 注册与界面通知中拆出。
复用设备登记、身份、请求去重、按任务订阅、账号代次和撤销逻辑；不复制一个精简 dispatcher。
网页保留适配层，桌面和手机继续使用既有客户端协议。

完成条件：真实桌面、iOS/Android 客户端和网页连接同一个独立 Host；任务发送、历史读取、
停止、一次性确认、客户端重连都一致。一个客户端断开不影响其他客户端或执行中的任务。
控制者撤销、账号切换与旧版本连接均有实际拒绝／兼容测试。移动平台按其现有发行流程验收。

### 3. 插件与平台适配

这是无图形服务器的主要兼容工作。保留 `GhostRuntime` 状态机和宿主能力守门，拆开逻辑执行、
面板展示与 Node 工作进程。已有插件依赖 DOM、browser storage、BroadcastChannel 和共享
partition；先以有系统沙箱的 headless Chromium 做兼容验证，再确定生产适配器，
不把普通 Node `vm` 当成等价沙箱，也不通过 `--no-sandbox` 使测试通过。

Node 插件沿用已批准的原生权限模型，独立进程的启动、消息、取消、退出和子进程回收由平台
适配器实现。浏览器沙箱继续禁止直接访问 Node、宿主文件和通用网络。远程面板、授权表单
与后台逻辑必须保持身份、owner、安装版本和连接代次，不能因拆进程放宽权限。

完成条件：存量已安装、已批准插件无需重装或重新授权；旧配置、凭证、KV、Library 不丢失；
同插件多面板通信有效；跨插件隔离、停用、更新、崩溃和后台退出回收都通过。
涉及插件基座的最终合并继续遵守项目既有维护者审核流程。

### 4. 完整后台生命周期

在共用任务与插件服务上接入 scheduler、伙伴、IM、媒体及文件服务，统一启动和退出顺序。
移除账号与配置对窗口的依赖，支持在控制端完成首次授权和重登。无桌面的 Linux 不能假设
图形登录已解锁 keyring；必须验证实际支持的凭证后端及服务账户重启行为，不能降级为明文。

完成条件：无客户端在线时自动化仍工作；关闭任一客户端不退出后台；退出后台能停止接收
新请求、保存队列并清理执行资源；运行中、需登录、凭证未解锁和需要人工处理都有明确状态。
新增持久化沿用现有数据所有权与迁移机制，不另造第二套账号库或任务库。

### 5. 独立发行与跨平台验收

产物包含固定版本的后台、网页、迁移资源及所需运行依赖，不从源码或临时 Vite 目录运行。
提供启动、状态、日志、停止、备份和升级指引。主线的公共服务变更同时运行后台与桌面回归，
前后端有明确版本兼容判断，避免维护一个长期分叉的“Host 版本”。

完成条件：干净机器不安装开发依赖即可运行；Linux 无 DISPLAY / WAYLAND_DISPLAY、无图形
登录会话可完成登录、真实任务、插件、自动化和重启恢复。macOS、Windows 各自验证凭证、
路径、子进程退出及安装更新；容器或模拟进程测试不能替代这些实机结果。

## 最终验收场景

1. 无图形 Linux 启动正式构建产物，首次登录并登记设备；后台无 Electron 窗口或 Xvfb 依赖。
2. 桌面、手机、网页同时连接：一端发起任务，其余端看到同一条消息和相同执行状态。
3. 两端竞争回答同一权限请求，后台只接受一次有效决定；停止、修改设置不串任务或账号。
4. 一端断网／进入后台后恢复，只补自己的事件与快照，不重复派发消息，也不拆掉其他端连接。
5. 重启 Host：未派发队列保留；结果不确定的执行清楚标记中断，不自动重复外部副作用。
6. 客户端全部关闭后插件与自动化仍工作；重新连接能看到结果及待确认操作。
7. 升级、回退兼容检查、凭证锁定、账号切换与设备撤销都不会串号或损坏持久数据。
8. 普通桌面默认启动、现有插件、现有手机远控不退化。图形专属能力明确指向有能力且获授权的设备。

上述场景未全部完成前，保持实验功能标识，不称为完整无界面版本。

  `registerMakerIpcsAfterSplash` 里，今天返回 `No handler registered`。客户端模式下的答案取决于
  交接合同，**归交接任务留在原工作区的升级流程**，不归本计划的各批。
- **Host 没有免账号本地模式**：桌面有 `auth:enter-local`，Host 只有云端账号一种登录态，所以
  隔离 profile 里客户端模式窗口停在登录页，无法在不碰真实凭证的情况下做完整客户端验收。
- **S·镜像 6 个**（`ghosts:recommendations`、`unread`、`recent-usage`、`builtin-status`、
  `errand-prefs`、`workdir-prefs`）需要“窗口缓存镜像”
  （Host 经事件流推送，窗口同步回答缓存）或把界面改成异步，是一个单独的小设计，放进插件那一
  小批，不混进 1a。S·本地 8 个由窗口本地读同一份 profile；其中
  `auth:has-persisted-session-hint-sync` 只在第一帧之前读存量会话标记，登录状态本身仍以 Host 为准。
- **R 回执通道 6 个**：数据在界面本地存储，Host 要用需经窗口往返一次，先标出来，不排期。
- **C-专项设计 4 个**涉及“用户填写的值只交给宿主执行”和远程控制派发的安全边界，先读
  `docs/product-rules/input-handoff.md`，方案出来前不动。

**为什么排行用普通模式而不是客户端模式**：Host 只有云端账号一种登录态，没有桌面的
免账号本地模式；隔离 profile 里没有登录 Cindy 账号，窗口以客户端模式启动后停在登录页，
而真实登录会动到钥匙串凭证。所以客户端模式只实测了启动与登录页：隔离 Host（新沙箱
`host-client`）+ 客户端模式开发窗口，页面落在 `#/login`，唯一一次未接调用
`maker:remote-ssh:cc-mgr-list-pending-upgrades` 返回 `UNSUPPORTED_CAPABILITY` 并计入报告，
之后桌面再注册 `maker:*` 通道没有出现“重复注册”错误。两种模式的渲染层相同，未接通道在
客户端模式下没有处理者，所以普通模式的调用集合就是客户端模式会落空的集合。
`host-client` 沙箱当时同样没有检查模型登录来源，用完已删除，无法事后核对；那次没有发送
任务，Host 也没有登录、没有数据 owner。

**修掉的客户端模式缺陷**：Electron 42 在 invoke 时先查 `_invokeHandlers.has(channel)`，
查不到直接回“No handler registered”，根本不会走到 `get()`。原兜底只改写了 `get()`，
单测直接调 `get()` 所以一直是绿的，实际客户端模式下未接的 `maker:*` 从来没有返回过
`UNSUPPORTED_CAPABILITY`（隔离 Electron 42.11.12 探针复现）。现在同时应答 `has()`，
并用注册守卫区分“invoke 查询”和“`handle()` 注册前的查询”，否则后注册的 `maker:*`
通道会被误判为重复注册而中断后续注册。真实 Electron 探针与实机客户端窗口都已验证。
非 `maker:*` 的未接通道仍保持 Electron 原错误，只计数。

# 阶段 0 封存清单（2026-11-25）

2026-11 中下旬，后台服务的工作曾以“把现有用户原地、不中断地交给后台”为目标推进。
自 2026-11-25 起改按[分阶段路线](headless-runtime-plan.md#分阶段路线2026-11-25-起)重新排序。
本文记录当时封存了哪些工作线、各自做到哪一步、已经证实的结论，以及重启前要满足的前提。
这些都是阶段 1–5 的素材，**不是当前的门禁，也不代表功能已完成**。

## 先看这三条

1. **封存的分支不能直接合入 main。** 绝大多数分支建在一条内部基础版本上，它比 main 多 112 笔
   （参照点为 #12020 的合并），而且没有合入。重启时，要用的部分在当时的 main 上重做，不要
   rebase 整条线。只有下文“已进入主线流程的独立修复”是从 main 起的。
2. **旧版在拒绝打开新资料之前，已经改写了旧登录信息。** 在 Linux 离线虚拟机上实测：
   - v0.1.145 遇到未知迁移、拒绝打开新资料之前，已经用旧登录槽位续期，并改写了旧账号保管库；
   - 有迁移清单时也一样续期、写回，拒绝之后主库的字节同样变了；
   - 没有清单时，旧版会重建并写入同一个高版本库。
   所以“旧版看到新资料会拒绝打开，所以安全”不成立。旧登录身份和资料库要分开验证。
   这一结论只在 Linux 上实测过，不能直接套用到 macOS 和 Windows。
3. **Mac 上原地迁移凭据，目前没有可执行的方案。** 同一键串行写入只能约束接入的应用写者，
   挡不住外部程序对钥匙串的改动。能保持原有保证的凭据持久化做法还没有找到；macOS 上
   缺少持续可信的平台证据，曾被列为发布阻断。这一条只阻断现有用户在 Mac 上的原地迁移，
   不影响阶段 1 用全新资料在服务器上运行。

## 已证实的发现

除上文“先看这三条”外：

- **试运行“零写”不能靠容差判断。** 试运行回收共享 Skill 的陈旧锁时会写目录，心跳也算写入，
  所以“前后快照允许少量差异”的做法作废。改用文件事件或沙箱，覆盖所有用锁方，并用一个变异证明门禁有效。
- **Orca 阶段 A 的出站委托会打断读源码的用例。** 把 Device Link 的订阅等函数改成委托给
  出站控制器后，有两组用例会抠出生产函数源码单独运行，共 42 条报 `outbound is not defined`。
- **进程表扫描会超时。** 在 Codex 工具进程回收里实测到 `ps -A` 超过 1.5 秒，原实现的回收计数
  随之归零（#12675 修复）。
- **插件逻辑页关闭竞态在 main 上同样可达。** 这一点按源码和同一 Playwright 版本判断，没有在 main
  上实跑；`evaluateHandle`、`addScriptTag`、`goto` 是否有同类问题仍是观察项（#12674 只修 `exposeBinding`）。
- **用户可见文案里会混进 “Host” 一词。** 约 59 处界面可能直接显示错误原文；需要一条守卫，扫描
  面向用户的 “Host…” 字面量。
- **通用错误本地化曾吞掉 SSH “Host key” 一类诊断**，后来改成按名单处理才修好。
- **缺随包 ripgrep 时，运行时配置对照测试和远程执行器测试会必然失败**，是环境问题，不是回归。
- **桌面 unit 的部分分片在 threads 池下会 SIGSEGV**，用 forks 复验 0 红；疑似原生模块在同一
  worker 里重复加载，与具体改动无关。
- **Windows Pageant 签名**需要单独的发布工作，几条线都碰到了。
- **IM 退出的时间预算已由用户确定：** 先给在途回复 15 秒宽限，然后发出停止，最多再等 5 秒取得
  已停止的证明；拿不到证明就保持登录。

## 阶段 1 的规划要点

阶段 1 的规划另起，这里只记与封存工作相关的结论：

- 起点是新的 Linux 系统用户和空 profile，远程入口沿用 Device Link 的同账号路径；不搬运其他电脑上的登录资料。
- 首次登录在终端发起、在浏览器确认（已有 CLI 和 PKCE 流程）。最大的不确定点是 Linux 凭据依赖
  Secret Service，要在无图形、无人解锁的服务环境下验证能否持久并刷新。
- 未接通的能力要逐项明确提示（例如“这台云主机暂不支持查看屏幕”），而不是静默失败。
- 试运行冻结、旧桌面凭据搬移、同机附着和原地转正，都留到阶段 4–5。

## 重启时

- 以重启当时的代码为准重新核对，不把本文的结论当作现状。
- 要用到的封存工作在当时的 main 上重做，按本文“归属阶段”一列排进对应阶段，再单独评审。
- 本文提到的设计稿、回执和分支保存在维护者本地的归档里，不在仓库中；需要时向维护者索取。

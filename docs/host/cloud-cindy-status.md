# 云端 Cindy：验收结果与剩余缺口

截至 2026-11-27。云端 Cindy 使用全新资料、单独登录。桌面和手机通过 Device Link 把它当作
另一台电脑连接。推进顺序和各阶段的完成条件见[分阶段路线](headless-runtime-plan.md#分阶段路线2026-11-25-起)。

## 阶段 1：自用实例验收

2026-11-25 在一台 macOS 测试机上完成了自用实例验收。企业账号在终端发起登录，经浏览器确认后，
后台加载了该账号的资料。准备好 Claude Code、Codex 和 Pi 后，手机连上云端 Cindy，以 Codex 和
`auto` 模型新建任务，经 Cindy AI 网关实际收到回复。一次正常停止并重启，从停止到设备重新上线约
26 秒，任务和消息均保留。

测试机后来加了一个临时的 `launchd` 用户登录自启项。2026-11-26 强制终止服务进程后，设备约
19 秒恢复在线。这是测试机的运维记录。仓库现提供[源码运行用的 LaunchAgent 模板与运维说明](launchd.md)。
本模板用空资料目录实测了加载、异常恢复、启停和状态查看。

阶段 1 的完成标志仍要求在无图形 Linux 上首次登录、运行真实任务、由桌面和手机连入，并在重启后保留
队列和历史。该验收尚未完成，企业云主机试点待做。

### 在远程任务中继续发消息

Linux 验收发现，旧后台已保存首条消息，却不支持手机按原消息 ID 查历史确认。首条一直占着待发队首，
后续消息进不了后台。在不中断连接的回环测试中也复现了这个问题。

后台补齐了按原 ID 确认的通道。对缺少该通道的旧后台，手机只在收到明确的「不支持」回执时读取
同设备、同任务的最新一页历史。有原 ID 对应的落库用户消息才继续发送下一条。查不到时，原消息下方
显示「发送结果未确认」和「重新确认」，后续消息仍按原顺序等待。旧后台的单页历史无法确认消息不存在。
后台升级后，可以再次点「重新确认」。只有精确查询明确返回消息不存在，且输入队列也没有该消息，
才显示普通的「未发送」和「重试」。点「重试」只尝试一次，使用原消息 ID；后台已收下的原 ID 不会写两次。
2026-11-28，在美国云主机上复验了 [#13450](https://github.com/makecindy/cindy/pull/13450)。
后台使用主线 `2f3f323a50` 构建的国内版 Linux 包，手机使用主线 `44861b82b3` 的 iOS 模拟器国内版开发包。

- **运行中续发通过。** 长回复仍在运行时连续发送两条消息，两条按顺序送达和处理，各收到一次回复，
  历史无重复，界面未出现未确认提示。
- **结束手机 App 后恢复通过。** 点发送后立即结束 App，重开后确认该消息只送达一次，之后续发正常。
- **断网恢复未验证。** 模拟器的断网设置未切断 Device Link，消息在恢复网络设置前已经送达。

同轮复验发现，给已归档的普通任务续发时，旧后台在入队前拒收。新版后台在任务路由锁内复核并恢复任务，
入队后先释放锁，再启动这一轮。共享、托管和已删除任务仍沿用原有限制。

手机与桌面控制端在明确拒收时显示原因。电脑还没收下前一条时，后面的消息显示「等待前一条消息」。
「重新确认」只按原 ID 查状态。已有失败记录可在精确历史和队列都确认未收到时重试，支持持久接收的电脑
还会对原 ID 去重。每次点「重试」最多入队一次。结果未确认时，用户也可以确认后删除本机待发消息，
后续消息按顺序继续发送。如果电脑其实已收到，被删除的待发消息仍会出现在对话记录里。
2026-11-28 的云主机复验中，已归档任务恢复为活动，首条消息按原 ID 只入库一次并完成回复；
但手机在收到历史前误把结果标为未确认，后续两条仍在本机等待。本次修复让同设备、同任务的
原 ID 用户历史到达后，只读对账并结束首条等待，不凭队列投影缺项或单页未命中推断未送达，
也不自动重发。

2026-11-28，国内版 Linux 云主机与 iOS 开发包完成两段端到端复验。旧任务的首条消息自动对账，
后两条按顺序各送达一次、各收到一次回复。新任务从手机归档后续发，任务恢复为活动；长回复运行时
提交的下一条也按顺序送达并收到回复。云主机数据库确认两条续发各落库一次，未发现重复的用户消息 ID。
端到端复验使用 `c782f0e556`。随后补上了停止任务时取消等锁的处理，并通过确定性交错回归；
包含这项修复的云主机包待简短复查。

## 剩余缺口

按用户影响排序：

1. **无图形 Linux 和企业云主机。** 尚缺真实服务器上的首次登录、双端连接、任务执行和重启恢复验收。
2. **macOS 常驻。** 目前提供源码运行、手工安装的模板，尚无 macOS 发布包。用户退出 macOS
   后重新登录时的自启，以及用本模板带真实账号运行时经 Electron 辅助进程访问钥匙串，均尚未实测。
3. **伙伴任务。** 云端目前只接收普通任务。向可见伙伴任务投递时，发送方会收到「不支持」结果。
   伙伴任务的执行链仍待阶段 2 接入。见[云端任务接收](../../apps/host/src/agent/session-handoff.ts)。
4. **模型可用性（复验未再现）。** 2026-11-25 10:54 UTC，使用 Claude Code 和
   `anthropic/claude-haiku-5-5` 建任务成功，执行时 Cindy AI 网关返回 HTTP 400，
   原因是网关判定该账号没有 Anthropic 模型权限。
   2026-11-27 06:03 UTC，同一国内区企业账号通过同一网关复验，`anthropic/claude-haiku-5-5`
   和 `claude-haiku-4-5` 均正常回复。云端与桌面共用同一份模型目录，也使用同一套筛选规则。
   将来如再发现目录和网关准入不一致，在服务端修正。初次验收见
   [#12830](https://github.com/makecindy/cindy/pull/12830)。
5. **建任务后投递未确认。** 云端建好任务后，桌面占用、前置条件失效、授权过期或入队前取消等明确拒绝，
   会返回「任务已建，消息未送达」，并通过原回执通道结算认领。写入或回包仍无法确认时，发送方继续收到
   「结果未知」，应先查原任务的历史和队列。桌面接收端也会结算任务重启期间、获得发送锁前的明确拒绝。
   见[云端投递判定](../../apps/host/src/agent/session-handoff.ts)
   和[回执结算](../../apps/desktop/src/main/maker-ipc/sessionHandoffCore.ts)。
6. **缺引擎的提示（已补）。** 被控端明确拒绝创建任务且没有可用引擎时，手机和桌面
   都提示先在那台电脑上安装引擎并重启 Cindy。手机在恢复未发送的任务时也显示同样的说明。
   其它原因导致引擎暂时未就绪时，继续按各自的恢复指引处理。见
   [被控端拒绝](../../apps/host/src/agent/create-runtime-session.ts)和
   [#12829 的后续项](https://github.com/makecindy/cindy/pull/12829)。
7. **远控降级提示（已补）。** 被控电脑明确不支持模型组时，手机在模型选择器里保留该分段并说明
   暂不支持。读取超时、离线或没有配置模型组本身不会被判为不支持。桌面从远程任务里新建目标，
   收到明确的不支持结果时显示同一条本地化说明，其它失败显示「新建目标失败」。
   见[手机模型组读取](../../apps/mobile/src/session/hostModelGroups.ts)和
   [桌面新建目标](../../apps/desktop/src/renderer/components/new-chat/NewGoalDialog.tsx)。
   用合成被控端回执和真实界面验证提示，尚未连接真实云端复测这两个拒绝路径。
8. **默认设备名。** 后台默认使用主机名加「Cindy Host」。当前可用 `CINDY_HOST_DEVICE_NAME`
   覆盖，见[设备信息采集](../../apps/host/src/platform/machine-status.ts)。
9. **个人账号 CLI 登录（已补）。** 个人登录仍使用服务器开放的浏览器方式；只有一种时直接选用。
   有多种时，交互终端按桌面同名方式列出选项，输入编号后继续浏览器验证；非交互终端列出每种方式的
   `--method=<id>` 写法，并以 `LOGIN_METHOD_REQUIRED`（退出码 2）拒绝继续，不等待输入。
   显式 `--method` 和企业登录照旧。见[登录方式选择](../../apps/host/src/auth/login.mjs)与
   [CLI 入口](../../apps/host/src/login-cli.mjs)。
10. **断链后的可靠帧（已收窄清理范围）。** 队头积压超过 60 秒时，先退掉已有明确截止时间且已过期的读回包，
    再移除可跳过的队头前缀。等待建链确认时保留在途结果。链路确已断开、余下积压均已超过阈值且没有仍需交付的
    回包时，才走放弃整队的兜底。后台与桌面使用共享的离线门禁，已知对端离线时跳过全量回包补发，
    对端重新建链时恢复定向补发。清理日志记录触发通道、积压通道计数和链路发送状态。
    macOS 自用验收中的重复告警在重启后消失，存量日志无法逐条确定当时的触发通道，尚待实际环境复验。
    见 [Device Link 发送路径](../../packages/device-link/src/client.ts)。

## 从源码验收时的准备

- **引擎。** 源码检出可能没有随包引擎，后台不会从 `PATH` 找替代程序。先运行
  `node scripts/ensure-agent-binaries.mjs --kinds=claude,codex,ripgrep,pi --platform=current`。
  如果启动后 `/api/agents` 为空，先检查引擎文件和启动日志。
- **SQLite 扩展。** 源码检出中的 `vec0` 可能仍是 Git LFS 占位文件。运行前先用
  `git lfs pull` 取回当前平台的实际文件，避免迁移报 `no such module: vec0`。
  也可以用 `CINDY_HOST_SQLITE_VEC_PATH` 指向当前平台已有的扩展文件。
- **进程环境。** 验收脚本用 `env -i` 启动，只传所需的运行环境和测试资料目录，避免继承日常
  shell 的区域、凭据或开发配置覆盖。
- **持久目录。** 把服务使用的代码和资料放在重启后仍保留的位置。2026-11-26 的一次 macOS
  重启清掉了 `/private/tmp` 里的测试代码，服务无法从原位置恢复。
- **macOS 凭据。** 从源码运行时，原生凭据编解码经 Electron 辅助进程调用系统安全存储，
  使用测试资料目录的凭据身份解析。安装了 Electron 的 npm 包也要确认其二进制已就位。
  跳过二进制下载的工作区可能缺少 `path.txt` 和 `dist`，源码入口不会在启动时补下载。见
  [凭据编解码](../../apps/host/src/credentials/native-codec.mjs)、
  [源码 Electron 路径解析](../../apps/host/src/runtime-layout.mjs)和
  [本机依赖准备](owned-machine-verification.md)。

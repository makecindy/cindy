# 从已有任务创建伙伴

## 1. 目标

让用户把已经合作顺手的普通任务发展为长期伙伴，保留交流积累，并直接继续工作。

典型场景：用户与 Agent 多轮推敲设定、审稿和组织写作，形成了稳定的背景与工作方式，希望它成为长期的世界设定与叙事搭档。用户不必重新介绍项目或手工整理一套人格资料。

成功标准：创建后，用户接着说下一句话，伙伴能理解当前进度、已定决定和待定问题；需要细节时能够回查原消息。

## 2. 第一版范围

- 从一个已有普通任务创建一个新伙伴；入口位于该任务的操作菜单。
- 保留截至创建时的可见对话历史，含角色、顺序、时间、附件与工具结果的原有展示或可追溯引用；原有隐藏、删除、撤回边界保持不变。
- 历史可在伙伴侧浏览、检索，明确显示来源任务；新交流进入伙伴主对话。
- 接续当前工作上下文，后续沿用伙伴已有的记忆、学习和任务跟进机制。
- 初始落地对象为本机、当前用户拥有、已停止运行且无待处理交互/队列的普通任务。其他入口的可用性按现有跨端合同处理，不显示不能兑现的操作。

第一版不包含跨产品导入、多任务合并、批量创建、自动人格塑造、全历史强制学习、安装包制作或替换当前客户端。真实创作任务的转换在功能验收后单独执行。

## 3. 用户流程

1. 在原任务菜单选择「创建为伙伴」。
2. 复用现有创建界面，只补充来源任务说明；输入名字、可选的一句话职责。模型优先沿用来源任务的可用路线，相关项目作为关联项目，用户可调整。
3. 界面简短说明：已有对话将保留并可回查，新交流在伙伴中继续；项目文件仍在原位置。
4. 创建成功后打开伙伴对话，显示历史来源与接续状态，输入框可继续使用。

无需先审批一份长摘要，也不要求填写完整人格。来源任务保留可访问入口；具体采用关联历史或复用会话，由现有数据模型决定，避免生成两个相互独立却冒充同一历史的副本。

## 4. 三层接续

| 层次 | 行为 |
| --- | --- |
| 完整历史 | 原消息保真且可检索；长历史分页读取。工具和附件保留来源关系，不将旧工具调用重新执行。 |
| 工作上下文 | 复用现有上下文交接机制，带入近期对话和当前状态；新伙伴身份及当前权限生效。历史仍可按需检索，不要求整段历史装进每轮请求。 |
| 长期记忆 | 沿用伙伴现有机制提炼稳定偏好与长期背景，后续可查看、修改、删除；不把所有聊天内容直接当成长期事实。 |

当前状态优先复用可信的已有交接；如需补充，摘要只覆盖正在做的工作、已确认决定、待定问题和材料入口。较早细节保留原文来源，后来决定优先于已被替代的方案。摘要缺失或学习未完成时，历史仍可访问，创建结果及下一步应清楚可见。

项目知识继续留在项目文件中，不整库复制到伙伴 Home。权限、工具、账户连接按伙伴现有规则解析；历史文本本身不增加权限。不会因创建伙伴自动执行旧请求、恢复旧队列或启用新的定时任务。

## 5. 实现方向

- 从现有任务菜单、伙伴创建服务、会话归属/历史检索、上下文交接四条路径定位最小接点。
- 尽量复用现有 Profile、Session、来源引用和事务机制，不新增通用迁移框架或独立记忆系统。
- 历史关联必须能被伙伴的检索与学习机制识别，仅增加 UI 链接不算完成接续。
- 创建应具有一致的成功结果；重试不能重复生成伙伴或历史。失败后原任务仍可访问。
- 删除新伙伴时，原任务历史及项目文件仍按原归属保留；附件引用不因伙伴删除而失效。
- UI 与 Agent 工具复用同一个操作服务，按仓库的 Agent/用户同权和跨端规则提供对应入口。
- 如必须修改数据库，仅使用正常向前 migration，不修改历史 migration，不手工改用户数据库。

实现前用短说明确认采用哪种归属方案及原因。普通技术选择自行判断；需要破坏原记录、扩大授权或显著扩大产品范围时再提请决定。

## 6. 验收

1. 用含多轮修订、附件和工具记录的普通测试任务创建伙伴，前后可见消息数量、顺序、角色和来源相符；原记录仍可打开。
2. 在伙伴中回查一项较早决定，能定位原文；不因历史未全量注入而不可检索。
3. 创建后继续讨论，能说清当前目标、已定决定与待定事项；以新伙伴身份回应。
4. 创建不重新执行旧命令、不重放未确认操作，不改变项目文件和权限档。
5. 伙伴后续保存一条新记忆、重启后继续使用；来源历史进入学习的路径可验证，已撤回内容不重新出现。
6. 创建失败、重试及删除伙伴，不造成原任务记录或附件丢失，不产生重复伙伴。
7. Light/Dark、现有语言、类型检查及与本次行为直接相关的回归通过；完整入口用隔离开发数据验证。

程序性断言使用确定性测试；上下文接续效果单独记录实际模型/输入/结果，不将模拟固定回复当成理解能力验证。默认静默和无头运行，确需占用桌面时提前说明。

## 7. 开发与交付

先读仓库现行规则及伙伴、存储、数据库、媒体、权限、跨端专题；在独立 worktree 实现。先完成核心历史/上下文接续，再接创建入口，最后贯通验证，避免先堆界面后发现历史归属无法成立。

交付包括代码 diff、简短实现说明、验证结果及未验证项、符合仓库模板的 PR 草稿。遵守 DCO，开发期不直推 main、不合并、不自动将用户真实任务转换。产品与架构确认按维护者规则处理；本设计是任务依据，不代替维护者批准。

## 8. 第一版实现

2026-10-29 在隔离分支 `cindy/cheerful-goldberg` 核对，基线为
`5f0b5f42b46969c3ac21b0cd798a07e36b46e8fd`。验证证据与未验证项见[交付记录](handoffs/task-to-companion-pr.md)。

### 数据归属方案

采用「原任务保留，新伙伴关联截至创建时的历史，新交流进入新主任务」。原任务继续拥有
消息和附件；伙伴 Home 只存伙伴自身资料。来源关联需要独立表达引用范围，不能直接把
原任务登记成伙伴的历史所有物。浏览、检索、上下文交接与学习共用这一范围，尊重原记录
后续的撤回与删除，不把不可见内容从摘要或搜索缓存中重新带回。

实现接点：

| 已有入口 | 核对结果与本次接法 |
| --- | --- |
| [伙伴创建服务](../apps/desktop/src/main/localDb/ipc/bots.ts) `createBotProfile` | UI 和运行时工具已共用创建服务；在此服务层接入来源任务，保留 owner 切换校验。创建伙伴、来源关联与接续状态须形成可恢复的同一结果，重试返回原结果。 |
| [归属 schema](../apps/desktop/src/main/localDb/schema.ts) | `bot_task_origins` 保存来源和准备状态，`bot_task_origin_messages` 保存创建时的消息 ID；不复制正文或附件。Drizzle 生成 `0137` 向前 migration。 |
| [历史范围](../apps/desktop/src/main/localDb/botHistoryScope.ts) 与 `searchBotHistory` | 来源任务纳入伙伴检索范围，读取、检索及上下文窗口应用成员范围和当前撤回、清空边界。桌面伙伴历史页复用原消息渲染器分页浏览。 |
| [上下文交接](../apps/desktop/src/main/maker-ipc/agentHandoff.ts) | 已有有界历史、工具结果和工作状态投影，交接走 wire 用户消息前缀。复用此路径并持久保存接续状态；不恢复原任务的原生执行句柄、输入队列或旧工具。 |
| [夜间学习](../apps/desktop/src/main/maker-ipc/botNightlyLearning.ts) `readTurns` | 来源中已完成、可见的主人交流纳入既有分批读取和学习水位；沿用当前提炼、证据、撤销和记忆机制，不修改其他伙伴的默认学习范围。 |
| [伙伴删除事务](../apps/desktop/src/main/localDb/worker/opHandlers/tx.ts) `botsDeleteProfile` | 伙伴任务按归属分离；来源引用的删除只解除关联，原任务、消息及媒体引用不进入伙伴删除集合。 |

来源与消息 ID 在创建伙伴的同一事务中记录，后续新增消息不会进入关联。创建复用发送锁及
空闲检查，事务内复核来源与队列。`prepared_at` 让失败重试补完初始化，成功后的重试不重设
用户已调整的关联项目；创建主任务前也会补完准备。首次交接按发送时的可见记录读取，接受后
消费，旧工具与队列不进入执行。

### 验收顺序

1. **先打通历史**：实现来源关联、分页读取与检索，验证原记录数量、顺序、角色、工具和
   附件，以及创建截止范围。随后覆盖删除伙伴仍保留源记录、失败重试不重复创建。
2. **再接续工作**：复用交接入口，让新主任务带入近期工作状态；给既有学习流程增加来源
   历史读取与进度。用真实模型验证接续理解，确定性测试只证明记录与状态行为。
3. **接上创建操作**：任务菜单复用伙伴创建表单，默认名字、可选职责、可用模型和关联项目；
   UI 与 Agent 工具调用同一服务，工具索引写明范围，成功进入新伙伴并显示来源历史。
4. **贯通与交付**：隔离数据验收、相关类型检查、设计与 i18n 检查、整体 diff 自审，按
   [PR 模板](../.github/PULL_REQUEST_TEMPLATE.md)记录结果。维护者评审后再进入外部交付。

### 多端与评审重点

- 本机来源限定的是数据位置。手机和同账号远控应调用来源电脑上的同一服务，按能力探测
  显示入口；SSH 工作区不提供本版转换。Agent 操作沿用同账号授权与现有身份判定。
- 新伙伴继续遵守[云端伙伴](product-rules/cloud-companions.md)合同。来源历史仍在来源电脑，
  同账号远控与 Agent 可在线读取；本版不自动把来源记录迁到另一台主力电脑，也不把云端正文
  镜像等同于完整历史。手机提供创建入口并进入新主任务，伙伴内的来源分页浏览当前由桌面提供。
- 方案涉及用户记录、来源引用和向前 migration，重点审查生命周期与兼容性。当前方案复用
  wire 交接，不计划改系统提示词；若实际需要修改 system 段，按
  [提示词门禁](dev-rules/maker-core-and-agent-behavior.md#4-system-prompt-改动门禁)先提交具体文本与影响，取得维护者确认。

真实模型理解质量和手机实机体验尚未验证，不能把程序性回归当作这两项验收。

## 9. 调研依据

- [ChatGPT Projects](https://help.openai.com/en/articles/10169521-projects-in-chatgpt)：已有聊天进入长期项目，借鉴就地入口。
- [Claude 项目](https://support.claude.com/en/articles/9519177-how-can-i-create-and-manage-projects)：普通聊天可加入项目，借鉴渐进组织。
- [Hermes Sessions](https://hermes-agent.nousresearch.com/docs/user-guide/sessions)：旧会话导入后接续，借鉴来源保留与重复导入处理；跨工具的有损清洗不直接照搬到 Cindy 内部历史。
- [OpenClaw 主会话](https://docs.openclaw.ai/concepts/main-session)：长期记录与有限工作上下文分层。

以上是设计参照，不表示这些产品已提供完全相同的「普通任务升级伙伴」功能。

## 需求与本轮边界

原问题：五位伙伴、指定非首位负责人、开启无 @ 自动接话后，瞬间出现问号头像、负责人标签和
“这个安排已经读不到了”。原报告为 Windows、客户端 0.1.128；Harness／模型仅为提报快照，
不能断定是故障环境。

- 修复目标：安排详情加载期间不误报确实缺失，不虚构负责人；详情到达后正确显示卡片。
- 保留行为：自动接话按成员顺序，分工使用指定负责人；work／旧版无 kind 的开始入口保留；
  普通消息不被安排读取阻塞；完整读取后确实缺失仍显示中性提示。
- 本轮沿用 #9485，不另写产品实现，不改服务端、协议、Mobile 或模型调度。
- 产品取舍：持续读失败时是否新增等待提示，单独审阅，不自动成为原修复的实现要求或合并门禁。

## 结果与剩余项

| 场景 | 本轮结果与边界 |
| --- | --- |
| talk、work、legacy 详情延迟；普通增量先到 | 视图既有覆盖通过；普通消息即时且唯一，等待无虚假负责人／缺失；work／legacy 保留负责人和开始入口 |
| 完整读取后真正缺失 | 组件及双主题夹具通过，保留中性提示，不回退到伙伴身份气泡 |

| G8 连续失败后恢复 | 受控四次超时后正确恢复，停止额外读取，离开后取消；失败期间无明确安排待恢复提示，体验项未通过 |
| Windows 原环境 | 未手工验证；等待具备匹配构建与设备的测试同事接手 |

| 三轮结束后的输入提示 | AX 提示仍涉及先前发言伙伴；真实渲染／稳定状态尚未核实，不能认定新缺陷 |

独立执行视图测试 271/271，通过总耗时 25.57 秒（测试部分 19.66 秒），有 React act 警告。
`plan-read-talk`／`work`／`missing` 双主题夹具 6/6 通过，15.8 秒。
真实群采用固定无 @ 输入：要求五位伙伴各只回复一次轮次确认，不调用工具、不相互提问、不继续讨论。
真实群证据是离散快照，未提前准备连续高帧率录屏，因此不能排除所有瞬时闪现；异步间隙由受控夹具补证。

### G8：持续失败与恢复

复用真实 `BotGroupChatView` 和既有内存宿主，临时扩展原测试文件中的最小输入：
初始历史读取成功，安排和普通消息增量到达后，详情在模拟 0／30／60／90 秒连续四次返回
`REQUEST_TIMEOUT`。普通消息和历史始终保留，没有虚假缺失、负责人或提前显示的安排卡。

恢复分支在模拟 120 秒读回详情，安排卡一张、普通消息一条；再推进模拟 60 秒没有额外读取。
卸载分支在四次失败后离开，随后没有额外读取；同轮选跑既有 delete、owner、not-found、unmount
边界。共 6/6 通过，267 项未选，总耗时 9.59 秒、测试部分 390 毫秒，收集真实组件占主要成本。
新增实验分支未调用发送和开始分工 mock；不代表真实服务端执行次数已核实。

临时将既有 UI 夹具的延迟宿主换为返回超时，使用 Playwright 模拟时钟检查四次失败，再恢复详情。
浅／深主题 2/2 通过，15.1 秒，已目检两个主题的失败阶段及总览：普通消息正常，安排暂不显示，
没有明确的安排待恢复提示；恢复后卡片出现。这验证了恢复机制，不能写成等待体验完整通过。

实验结束后原测试和夹具逐字节恢复，产品源码未修改；临时改动回执如实标记 dirty。
原始日志、补丁与截图保留本机，未随本 PR 上传；当前记录提供方法与结果，不能替代接手人的独立复验。

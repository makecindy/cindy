# 侧边栏重设计:方案与实现计划

> **状态**:设计定稿(2026-08-12,与 Dash 逐轮确认);A–E 期首轮实现已随本 PR 落地
> (分期表见 §8,实机目检与后续调优仍在进行)。
> 实现稳定后本文档应转为对应模块的行为说明或并入帮助内容,不长期保留"计划"形态。
> **适用范围**:Desktop 左侧任务列表(侧边栏)。手机端仅作参考基准,不在本次范围。

## 1. 背景与目标

现状问题:侧边栏概念分散——设备筛选、置顶、项目段、对话段、按日期分组各自为政;
显示模式(文字/列表/卡片)只有置顶支持;项目与对话割裂为固定两段。

目标:

1. 所有内容(置顶与主列表)都能选择文字或列表方式显示;
2. 项目与对话不再固定分段,参考手机版的混排方式整合;
3. 分组、排序、筛选、显示设置收敛进一个「侧边栏显示设置」菜单;
4. 概念上区分「范围」(段头标题下拉)、「分组」(复选)、「筛选」(收窄)、「显示」(形态)。

## 2. 信息架构

```
[新建]       固定不滚动
─────────── 以下随列表一起滚动 ───────────
[顶部导航]   自动任务 / 插件 / 搜索
[置顶区]     可折叠;会话与项目混排置顶,共享一份拖拽顺序(现状语义不变)
[范围标题▾]  主列表范围下拉,空态 / loading / 连接中也恒在
[主列表]     单一混排列表(见 §3);无内容时只留范围标题行
```

**「全部任务」段头与设备下拉合并(2026-08-13 用户定稿,新设计,显式推翻两条
2026-07 旧定稿)**:
- 标题文字反映当前范围,点击标题弹出「所有 / 本机 / 各设备(单选 + 多选)+
  侧边栏显示设置 / 远程连接设置」菜单——修掉旧结构的标题撒谎问题(范围收窄后
  段头仍写「全部任务」),顶部导航省一行。范围菜单本体(单选/多选/三态)沿用
  原件;底部设置入口并列「远程连接设置」与「侧边栏显示设置」(打开段头同一份菜单)。
- 无远程设备时标题仍是「全部任务 ▾」(2026-08-13 用户裁决:箭头保留),菜单
  不出现设备列表,只留「远程连接设置」与「侧边栏显示设置」——单机用户看不到
  设备概念,但仍能从段头进这两项。断网后设备目录清空、raw 选择仍记着远端时
  同样只留两项设置,不再假装还有机器列表。段头恒在:空账户、只剩置顶、远程
  目录 / 任务全屏 loading/error、所选设备连接中都继续渲染范围标题(2026-08-13
  第 4 轮 review P1),这是合并方向只能是"下拉并入标题"而非反向的原因。
- **点击展开**(推翻 2026-07-12 hover 展开定稿:段头标题 hover 扫过就弹菜单太吵);
  「切换器收进顶部导航末行、不挂段头」的 2026-07 定稿一并推翻(当年是段头挂配件,
  现在段头本身就是切换器)。
- **段级收起取消**:标题的点击语义让给范围切换;「想要紧凑」由段头右侧的
  「收起所有分组」按钮承接。
- 范围影响整个侧栏(含置顶区)的既有语义**不变**——范围是"我在看谁的数据",
  与筛选不同,置顶区豁免筛选但不豁免范围(否则被排除设备的置顶任务会赖着不走)。
  范围选择器位于置顶区下方而作用及于上方的空间错位,由标题文字的状态表达兜底
  (用户裁决:接受,不搬置顶区)。

「按日期分组」模式删除(`DateGroupedSessionsSection` 及 `groupBy === 'date'` 分支)。

**只有「新建」固定**(2026-08-12 用户裁决,对齐 Codex):列表向上滚动时,顶部导航
其余三行跟着滚走,把纵向空间让给任务列表。搜索有查询时只额外钉住搜索行,保证
输入框可见;自动任务 / 插件仍随结果滚走。实现上 `SidebarTopNav` 支持分段渲染
(`pinned` / `scrollable`),Shell 画固定段、任务列表页在自己的滚动容器最上方画可滚动段;
归属由功能槽经 `useOwnTopNavScrollableRows` 声明,**Shell 不判路由**(维持"外壳不感知
路由"的架构不变量)。没有长列表的视图(插件页等)与 rail 态仍由 Shell 整块渲染四行。

## 3. 侧边栏显示设置菜单(定稿结构)

入口有三处:「全部任务」段头 hover 出现的 sliders 按钮;**范围菜单底部**的
「侧边栏显示设置」行(2026-08-13 用户裁决,排在「远程连接设置」下面);以及侧栏
空白处右键。前两处打开同一份段头菜单,**点击展开**(2026-08-12 用户裁决,
推翻早前的 hover 自动展开);按钮配色与段头其余按钮同源,hover 只出 tooltip。

菜单**不带自身标题行**(2026-08-12 用户裁决,节约高度;与远程机器菜单同规)——
触发按钮的 tooltip 已经说明这是什么。菜单高度按 Radix 给出的可用空间收口并允许
纵向滚动:渲染进程画不到 BrowserWindow 外面,窗口矮时四段约 470px 放不下,若不收口
会被 `overflow-hidden` **静默切掉**(实机丢过最上面的「分组」整段)。

四段:

### 3.1 分组 —— 三个独立复选(可任意组合)

| 选项 | 默认 | 行为 |
|---|---|---|
| 按项目分组 | **开** | 有项目的任务收进项目行;关闭则平铺、行尾带项目小标签 |
| 按设备分组 | **开** | 最外层按设备切段,分组头带在线状态、可折叠;**仅有远程设备连接时该选项才出现**;远程断开时选项消失、效果一并解除——**只解除生效,不改写偏好**(生效 = 有远程设备 ∧ 偏好开,两者分离;断线再重连后按原偏好自动恢复分组。2026-08-13 复查补记:早期原型在断开时直接把偏好写成关,是错误做法,勿照抄)。**范围收窄到单台机器时同样退场**(2026-08-13 用户定稿):只有一台无段可切,唯一的段头还会与范围标题重复报同一个设备名;选项行同步隐藏、偏好不改写,范围放宽自动恢复 |
| 对话归为一组 | **开** | 无项目任务收进「对话」组(归属分类名,按 task-and-conversation-naming §2.3);关闭则散排。组头右侧有与项目行等位的新建入口。(2026-08-12 用户裁决改默认开,原定稿为关) |

层级方向固定:设备 → 项目/对话组 → 任务。全关 = 纯平铺。

**远程项目的机器标注**(2026-08-12 用户裁决):

- device-link 项目行只显示**设备名**,不显示设备 ID——ID 是机器指纹哈希,对用户
  没有可读意义。仅当两台设备**撞名**(同一名字对应多个 deviceId,只统计列表里
  真的会渲染的项目)时,才在名字后附上 ID 消歧。SSH 项目的 `user@host[:port]`
  不受影响(那是可读信息,不是哈希)。
- **按设备分组开启时,项目行不再标注所属设备**:列表已按设备切段、段头写着设备名,
  行内重复标注只是挤占项目名宽度。远程图标保留(表达「远程 + 连接状态」,
  不重复归属信息)。置顶区不受分组影响,照常显示。

**对话组的新建落在哪台设备**(2026-08-12 用户裁决):按设备分组时,对话组隶属于
某个设备段,组头的新建就在**该段的设备**上创建(本机段 = 本机),不再看当前机器
作用域——作用域可能是「所有」或另一台设备,按它猜会把任务建错地方。目标设备离线时
禁用该入口并复用远程写保护文案(被控端才是真正的创建方)。不按设备分组时没有归属
歧义,沿用原有的作用域推断(仅当作用域唯一指向一台远程机器时继承它)。

**默认组合(2026-08-12 用户裁决,推翻早前的「对话不归组」定稿)**:
按项目分组 + 按设备分组 + 对话归为一组,三层都开。

## 3.0 升级兼容性:老用户看到的样子尽量不变

本版的硬要求是**老用户升级后左侧任务列表尽量不变**,新默认只作用于新用户。
逐项账目:

| 项 | 旧版 | 新默认 | 老用户升级后 |
|---|---|---|---|
| 按项目分组 | 有该设置,默认开 | 开 | 沿用旧值,无变化 |
| 排序 | 有该设置,默认最近活动 | 按时间(即最近活动) | 沿用旧值;仅已删的「最早优先」回退默认 |
| 任务信息 | 固定只显示时间 | 只显示时间 | 无变化 |
| 按设备分组 | 无此功能 | 开 | **老新一致**(用户裁决:分组不分老新) |
| 对话归为一组 | 对话是固定独立段 | 开 | **老新一致**(同上) |
| 显示模式 | 整侧栏一份 `sidebar.cardMode`,默认文字版 | 列表版 | **按安装新旧分叉**:老装文字版,新装列表版 |

显示模式是唯一分叉项。判定顺序:显式设过主列表模式 → 从 `cardMode` 迁移
(text→文字,card/list→列表)→ 都没有时看安装新旧。最后一档解决「从没动过显示
模式的老用户」——他们 `cardMode` 为空,与全新安装在 localStorage 上无法直接区分,
由 `sidebarInstallVintage` 按一组**旧版使用痕迹**(打开过会话、折叠过分组、置顶
拖拽等 key)判定,并把结论一次性固化,避免新用户用一阵后默认值悄悄漂移。

对话段的形态变化(固定独立段 → 混排/可归组)靠配置回不去:旧的 `DialogueSection`
固定段与 `DateGroupedSessionsSection` 已删除,这是本次重设计的核心,不提供回退。

### 3.2 排序方式 —— 单选

| 选项 | 默认 | 行为 |
|---|---|---|
| 按时间排序 | **是** | 顶层条目按组内最新活动时间倒序(最近的在前);组内同。排序时钟 = `userSendAt ?? updatedAt`(以用户最近一次按下发送为主键,agent 回复只 bump `updatedAt` 不重排) |
| 优先级 | | 四档,对齐 Codex(2026-08-13 用户裁决「参考 Codex」):等你处理(等待回复 / 授权 / 出错)> 完成未读 > 运行中 > 其余;同档内按最近活动。正在看的任务钉住打开时的档位不跳位;切走后再落到已看过最前(2026-08-15 用户裁决) |
| 手动排序 | | 顶层条目可拖拽,顺序持久;不在序的新项目追加到已排序列**之后**(沿用重设计前 manualProjectOrder 的既有语义;2026-08-13 复查修正——原写「新条目进顶部」与实现不符,「进顶部」只是置顶区拖拽序的行为,不适用这里) |

「按名称排序」(现状 alphabetic)删除。**「最早优先」(旧 `time`)2026-08-12 用户
裁决删除**——时间排序只保留最近活动在前一档,菜单文案随之从「最近优先」改为
「按时间排序」(不再需要与另一档对举)。两个已删值的存量偏好都静默回退到默认。

默认保持按时间而非优先级,原因见 §6.2(列表跳动),切默认是一行改动、留待实机
体验后决定。

**「优先级」带 hover 说明(2026-08-13 用户裁决)**:标签本身说不出「按什么排」,
用户无从判断它与「按时间排序」的差别。文案如实描述实现的三档:「有未读或等你
处理的排在最前,然后是运行中的,其余按时间」。`recency` / `manual` 名字自解释,
不配说明——菜单不该变成说明书。说明挂在选项表的 `tipKey` 上(与 `labelKey` /
`Icon` 同源),`side="right"`(菜单贴侧栏右缘,提示往上下会压住相邻选项)。

实现口径的澄清(与本表措辞对齐):
- **活任务档位与灵动岛共用**(2026-08-15):`waiting`(含出错) > `unread` >
  `running` > `rest`,实现落在 `apps/desktop/src/shared/liveTaskPriority.ts`。
  灵动岛不展示 `rest`;它自己的「刚完成短暂置顶」和展开钉住顺序叠在这把尺子
  外面,不再把 error 单独抬到完成未读上面。
- **四档口径(2026-08-13 定稿,对齐 Codex)**。Codex 侧栏优先级排序的权重表是
  `waiting:0 / unread:1 / active:2 / idle:3`(反编译其桌面端确认;它连置顶区都
  提供同款排序,菜单项也带同样的 tooltip 说明——「Needs input and unread chats
  first」)。本仓映射:waiting = attention kind 为 `awaiting`(等你回复 / 授权 /
  审阅计划)或 `error`(出错未处理)∪ 定时任务失败未读(urgency 集);unread =
  其余 attention(`done`,跑完还没点开);active = running。此前实现是三档
  (attention 整体一档),完成未读一多就把真正等回应的淹掉——四档修正了这一点。
  Codex 没有单独的 error 档(error 归 waiting),本仓同款,不另加档。
  `sidebarRightStatus.ts` 的 `error > awaiting > done` 只决定右侧状态槽的
  **颜色**,不参与排序。
- **`waitingSessionIds` 在模型上可缺省**:缺省时全部 attention 落 unread 档,
  排序仍成立(老调用方 / 测试夹具零迁移);组装层(ProjectsSection)从
  `useSessionAttentionKinds` + urgency 集派生 waiting 子集喂入。
- **正在看不跳位,离开后再落到已看过最前(2026-08-15 用户裁决)**。点开完成未读
  会立刻清掉 attention,自然档会掉到「其余」;点击清点前必须先按当前档位钉住,
  看的过程中保持打开时的档位。切到别的任务后再落到其余档,离开时刻只抬 rest
  档,不抬 waiting / unread / running。只影响 priority,不改 recency / manual。
  钉住与离开时刻是渲染层生命周期内的展示态,不落盘。
- **未读是内存态,重启即失**(`sessionAttentionStore` 不落盘)。重启后只有两类点
  会由 `usePendingAlertAttention` 从 DB 重建:未收尾的中断、未处置的错误尾行——
  它们恰好都是 waiting 档,重建后仍排最前。「跑完没看」的 unread 档不重建,
  多数任务落回按时间排。这是既有架构的性质,不是本次排序引入的缺陷。

### 3.3 筛选 —— 一级只占一行,展开二级菜单

一级行右侧显示摘要(「无」/「N 项生效」)。二级菜单四维度 + 「重置筛选」,
维度与选项**与现状完全一致**(`useSidebarFilter` 已全部实现):

- 状态:活跃(默认)/ 已归档 / 全部
- 项目:全部 / 多选(项目列表 + 「对话」= 无项目,新增该项)
- Agent:全部 / Claude Code / Codex
- 最近活跃:全部 / 1 / 3 / 7 / 30 天

**筛选不作用于置顶区(定稿;2026-08-12 用户重申并补齐实现)**。用户主动置顶就是
「我要一直看见它」,被筛选条件挑走会让人以为置顶丢了。逐项:

| 维度 | 是否影响置顶区 |
|---|---|
| 项目 | 否 |
| Agent | 否 |
| 最近活跃 | 否(久未活跃的置顶项照常显示) |
| 状态(活跃 / 已归档 / 全部) | **是**——已归档的置顶项在「活跃」下隐藏 |

状态是唯一例外(2026-08-12 用户裁决):归档 = 用户说「这事儿完了」,与置顶语义相反,
不归档就不会受影响;切到「已归档」或「全部」时它会重新出现。置顶区其余只跟随设备
范围。筛选是否生效只看「侧边栏显示设置」里的筛选摘要，标题旁不另挂「已筛选」小标（2026-08-13 用户否决常驻标记）。

置顶项目行内的会话同样不再按项目 / Agent 过滤;「从侧栏移除项目」仍然生效——那不是
筛选,是用户对该项目的显式隐藏。

### 3.4 显示 —— 主列表形态 + 任务信息

- **文字版 / 列表版** 二选一,默认**列表版**(定稿)。卡片版仅置顶区支持。
- **任务信息**(一行入口,二级复选菜单):决定任务行标题右侧显示哪些信息,
  **顺序 = 用户勾选先后**(2026-08-12 用户裁决,推翻原「固定 PR · token · 费用 ·
  时间」),以「·」分隔——先勾时间再勾费用就显示「时间 · 费用」,反过来即相反。
  勾选状态本身按顺序存储,PR 也参与排列;菜单里四个复选项自身的排列顺序不变。
  一行入口右侧用**已选项的图标串**表示当前选择(不罗列短词):

| 项 | 默认 | 形态 |
|---|---|---|
| 最近活动时间 | **勾** | 现状行为 |
| PR 状态 | | 状态 icon + 等宽 `#号`(与顶栏 PrChip 同款,2026-08-12 用户裁决):状态颜色只上在 icon 上(形状 + 颜色双编码,四态见 `gitContextPrVisuals`),`#号` 文字用信息槽常规灰;文字状态放 hover;无 PR 的任务不显示不占位 |
| 累计 token | | `1.4M` / `320k` 缩写,无单位 |
| 费用 | | 按 `totalCostCurrency` 显示 $/¥;无数据(如订阅模式)留空 |

## 4. 置顶区

- 显示方式独立设置:文字版 / 列表版 / **卡片版** 三档,入口在置顶段头(hover)。
- 卡片版下项目呈通栏卡片壳、内部紧凑行,可展开。
- 置顶语义不变:会话与项目混排、共享拖拽顺序、无上限、新置顶进队首。

## 5. 显示模式的列表版规范

对齐 `SessionCard.tsx` list 变体现状:行 1 = 标题 + 右侧信息槽(hover 让位给
More/Archive,复用 `TimeActionsSlot`),行 2 = 固定 1 行预览;整行恒两行高,
无第三行;无卡片描边底色,行间浅分割线(hover/选中隐藏)。

## 9. 已识别的风险与裁决记录

1. **混排推翻既有裁决**:`DialogueSection.tsx` 文件头记录的「对话是 Projects 的
   同级固定段、排序不复用 project manual order」被本方案有意推翻。实现 D 期时
   必须同步改注释与测试,不留矛盾文档。
2. **优先级排序的列表跳动**:任务状态变化引起行移位、可能误点。默认值保持
   「最近活动」(定稿)。**点击自己导致重排**已按 2026-08-15 用户裁决修掉:
   正在看的任务钉住打开时的档位,切走后再落到已看过最前。其它状态变化(运行中
   变完成未读、新的等你处理)仍会即时重排;重排动画 / 悬停冻结仍未做,留待
   实机体验后决定。
3. **手动排序范围**:散排对话可能数百条,全量进 manual order 会膨胀且被新任务
   冲乱。实现时收窄:手动排序只管顶层分组行与少量散排条目,组内仍按最近活动
   (与原型有偏差,已在 2026-08-12 沟通中说明)。
4. **显示模式迁移**:主列表无 card 档,老用户 card 值映射到 list。定稿:粗略
   映射即可,不追求完美,发版说明提一句。
5. **PR 状态展示规模**:`session_pr_refs` 不存状态(设计如此),状态走
   `git-context:pr-status` IPC 实时查。侧栏常驻显示必须:仅查视口可见行、拉长
   TTL、批量合并;一会话多 PR 时取 `lastSeenAt` 最新;无 token/查询失败降级为
   灰色 `#号`。
6. **远程会话的 token/费用/PR**:token/费用字段在远端 DB,device-link 投影
   扩字段触碰 `protocol-compatibility` 规则——第一期仅本机会话生效,远程留空,
   协议扩展单独评审。**PR 不受此限**(2026-08-12 实机反馈修正):device-link
   白名单已有 `git-context:pr-refs:list` / `git-context:pr-status` 逐会话通道
   (聊天顶栏在用),侧栏对远程会话按需补拉引用、状态经远程路由查询(被控端持
   gh token + main 侧按已提取引用 fail-closed 过滤),不改协议。触发条件:勾选
   pr 且行实际渲染,每会话一次,数量被 collapse 上限约束。
7. **筛选与置顶**:定稿为不作用于置顶,置顶条目不会因筛选消失。2026-08-12 补齐
   实现——此前项目 / Agent 两个维度仍在过滤置顶,已移除;唯一例外是状态筛选
   (已归档的置顶项在「活跃」下隐藏),口径见 §3.3 的表。
8. **PR 状态色登记**:绿/红对齐 `--diff-add-fg` / `--diff-del-fg`,「侧边栏 PR
   状态指示」作为新消费场景需在 DESIGN.md §2 登记后方可实现。
9. **文案**:新增文案四语落地;「对话」作归属分类名遵循
   task-and-conversation-naming §2.3;「任务信息」等新术语过 glossary 门禁。

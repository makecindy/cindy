## 1. 定位

用户有多台电脑都登录了同一个供应商（例如多份 Anthropic 订阅），希望把它们合成一个入口：
不用自己挑电脑，哪台忙、离线或撞到用量上限时自动换一台，并且能把这个入口分享给别人。

做法是在某台电脑（下称**组所在电脑**）的某个供应商下建一个**供应商组**，把其他电脑上的同一个
供应商加进来。新任务按**组策略**选一台**组内电脑**，本机自己的任务、其他电脑与分享的人的任务都是同一套
（2026-10-15 用户裁决）。组管理以下使用：

- 组所在电脑自己的任务；
- 同账号的其他电脑把组所在电脑的这个供应商当远程供应商使用（组所在电脑选电脑，那台电脑直接连过去）；
- 别人通过分享使用组所在电脑分享出去的这个供应商（组所在电脑选电脑并转发）。

这样一台现成的 Cindy 就是网关，不需要另外部署服务；登录、界面、分享链接与审批全部复用。

**Agent 始终在被选中的组内电脑上运行**，用那台电脑的 Agent 程序、登录、供应商与网络；
任务的文件与命令仍在发起任务的电脑上执行。组所在电脑只负责选电脑，对分享的人还负责转发。

## 2. 术语

- **供应商组（组）**：某台电脑上某个供应商的一组运行位置。界面用「供应商组」，不单用「分组」，
  避免与模型列表、设置页的模型分组混淆。
- **组内电脑**：组里能运行这个供应商的电脑，来源见 §3。
- **组策略**：新任务选哪台组内电脑的规则，见 §5。
- **组所在电脑**：建了这个组的电脑。
- **使用方**：经这个供应商发起任务的一方：组所在电脑本身、同账号的其他电脑、分享的人。

术语表登记见 `i18n/glossary.json`（`provider-group`、`group-strategy`，均为 `proposed`）。

## 3. 组的组成

- 每个供应商最多一个组。组跟着供应商连接（连接 ID）走：删除这个供应商连接即删除组。
- **组内电脑就是这台电脑已经能用的同一个供应商**，与模型列表里远程供应商区域是同一个来源。自己的电脑和
  别人的电脑走同一套规则，与现有「自己用和被分享走同一套」一致（供应商分享 §3、§5）：
  1. **本机**：默认在组里，可以暂停对外分配。暂停只限制接收本机以外的新任务，不影响本机自用；
     本机自己的新任务与其他使用方一样按组策略选电脑，不另设本机优先（2026-10-15）。
  2. **已经能用的远程供应商**：同账号电脑上已打开「允许被远程调用」的，和别人分享给这个账号的，在同一个列表里
     勾选加入，不需要再申请。
  3. **还不能用的别人的电脑**：粘贴对方的分享链接，流程与加入分享相同：预览 → 发送申请 → 双方核对配对码
     → 对方同意，同意后直接加入组。自己账号的电脑不需要链接（服务端也拒绝申请自己账号的分享，`PROVIDER_SHARE_SELF`）。
     首版：「分享链接」一页打开现有的输入分享链接与申请流程，对方同意后回到「已经能用的」勾选加入；
     申请前按组核对供应商、同意后直接加入组放到 P2。
     首版远程管理时只开放添加组所在电脑已能用的供应商；分享链接入口禁用并引导在组所在电脑的模型供应商设置中输入，
     对方同意后回到可用列表加入。申请与跨区启用记录不能误落到查看电脑（供应商分享 §8）。
- **必须是同一个供应商**，不一致时不发送申请，提示「这个链接分享的是 {对方供应商}，不是 {本供应商}，
  不能加入这个供应商组」；可勾选的列表只列同一个供应商。「同一个」按下面的口径判断，不直接比较供应商 ID：
  - **官方供应商与订阅账号**（Anthropic、OpenAI、xAI 及其登录预设）：同一品牌即可。内置的默认连接 ID 固定
    （如 `anthropic`），但在设置里再添加的订阅账号，ID 是品牌加随机后缀（如 `anthropic-1a2b3c4d`），
    两台电脑上一定不同；多个订阅账号正是供应商组的主要用法，按 ID 比较会把它们全部拒掉。
  - **自定义供应商**：名称相同即可（忽略大小写与首尾空格），首版就支持。供应商 ID 相同也算同一个。
    ID 不由用户填写，是添加时按名称自动生成的，但添加后改名不改 ID、本机已有同名时会带 `-2` 之类后缀，
    所以按名称比较，不只比 ID。名称不同时提示「这个链接分享的是 {对方供应商}，不是 {本供应商}」，
    把两台电脑上的名称改成一样即可。
  - 判断所需的品牌信息取远端供应商目录里已有的去敏字段，不新增协议字段。
- 同账号电脑经本账号的设备互联服务加入；别人分享的供应商可以来自另一个官方区域，是否开放由
  供应商分享 §8 的服务端开关决定。同账号其他电脑使用该组时，应恢复已有跨区分享的连接，不能因
  本机尚无区域标记而要求重新申请或判成分享已移除（2026-10-26）。
- 分享关系属于账号：组所在电脑账号收到的分享，这个账号的其他电脑也能直接用。被组所在电脑加进组之后，
  这个账号的其他电脑上不再单独列出它，只列组那一项（与同账号电脑被收进组同一条规则，§10）；组所在电脑离线时
  它重新单独出现。组设置本身仍只存在组所在电脑本机。
- **原分享被删除或已退出，那台自动移出组**（2026-10-15 用户要求）：分享来的电脑对应的分享从这个账号收到的分享里消失
  （分享者删除、或这个账号退出）时，组所在电脑把它移出组并解除指向它的任务绑定，组所在电脑自己与它分享的人都不再用到它。
  只在已收到的分享名单完整可信时判断：本区域名单已拉到，本账号可能有分享的对方区域名单也都已确认；拉取失败、还没拉到、
  换账号中都不动。分享只是暂停时保留(显示「分享已暂停」)。实现见 `provider-group/removedShares.ts`(接线在 `reshareRuntime.ts`)，回归见同名测试。
- **分享来的电脑不能借组转给别人**（2026-10-15）：加进组只扩大这个账号自己的用法；组所在的供应商分享给了别人时，分享的人
  要经组用到分享来的电脑，必须由那台的主人逐人同意(§4「分享的人(中转)」，[供应商分享](provider-sharing.md) §4.3)。
- 组内电脑数量不设上限；每台的并发上限见 §5。
- 协同任务的 Lead 与 Worker 与普通任务一样归供应商组分配、出问题时自动换电脑（2026-10-10 用户裁决：远程与本机
  供应商对协同是同一套逻辑与体验），细则见 §6.1「协同任务」。审查任务的设置固定跟随源任务，不归供应商组分配。
- 组里至少保留一台组内电脑；移除最后一台即删除组。
- **组只是这台电脑上这个供应商的一项设置，不新增账号级的概念。** 同账号的几台电脑可以各自建组、成员也可以重叠，
  组与组之间互不感知：每个组只管经它发起的任务；被收进组的电脑在其他电脑的列表里只在组所在电脑离线时单独出现，
  这时直接选它仍是在那台直接运行，与现在一致。
  重叠不会出错——组内电脑被别的组或别人直接用满、撞到用量上限时，经本组的任务会失败，按 §6.1 直接换下一台，
  最多多一次换电脑。界面建议在一台常开的电脑上建组，其他电脑选这个组的入口，但不强制。

## 4. 哪些使用走组

- 判断是否归组依据任务实际使用的供应商连接。§1 的三种使用共用绑定、故障恢复与组策略（2026-10-15）：
  初次分配与故障重选都按组策略选电脑，只有本机的「暂停对外分配」区分来源——它拦同账号其他电脑与分享的人的任务，
  不拦组所在电脑自己的任务。
  任务归属以任务所在电脑为准，手机或远控操作该电脑上的任务不把它变成外部新任务。
- 组内电脑是本机时，Agent 直接在本机运行，与现在一致。
- **组所在电脑自己的任务**：组内电脑是其他电脑时，组所在电脑作为控制端连过去：对「我的其他电脑」是同账号远程 Agent；
  对分享来的电脑，组所在电脑的账号是那台电脑的受邀者。
- **同账号其他电脑（直连，2026-10-10）**：任务所在的电脑先问组所在电脑「该用哪台」（`provider-group:remote` 通道，只给
  同账号），再**自己直接连到选中的组内电脑**：选中组所在电脑本身就连组所在电脑，选中任务所在的这台就在本机运行，
  选中分享来的电脑就用这个账号收到的那个分享（分享属于账号，§3）。少一次中转；组所在电脑关机不影响已经在跑的任务。
  组所在电脑看不到这些任务的内容，任务所在的电脑把正在跑的经组任务报告给它（只用于统计负载），组内电脑出问题时把
  需要冷却的电脑报告给它（§5、§6.1）。
- **分享的人（中转）**：连不到组内其他电脑，由组所在电脑选电脑并中转（P2b）：
  - 受邀者的**新任务**按组策略选一台：选到组所在电脑就在本机运行；选到别的电脑就由组所在电脑中转，事件、反向请求、
    WebSocket 帧原样转发，消息与附件不解码、不落盘（§8「只在内存中转」）。受邀者带来的「已分配」「中转」字段一律
    当作普通受邀者任务处理，组所在电脑不让受邀者自己决定去哪台。
  - 只选能接受受邀者的电脑：组所在电脑自己；分享来的电脑（那台本来就把组所在电脑当受邀者隔离），且**那台的主人同意过
    这个受邀者**（2026-10-15，[供应商分享](provider-sharing.md) §4.3）；同账号电脑要声明能按受邀者隔离（`guestRelay`），
    不声明的旧版本一阵子（10 分钟）不再给它受邀者的任务，但不冷却它，组所在电脑自己的任务照常分过去。
  - **转分享的同意**：组所在电脑自动把分享出去的人(按账号)报给组里每台分享来的电脑，由那台的主人逐人同意；结果只在组所在
    电脑内存里，以那台为准(组或分享的人变化后马上报，还有人等着时每分钟再问，其余每 10 分钟核对，设置页读取距上次成功核对超过 15 秒时再问)，
    没问到之前一律当作没同意。中转到分享来的电脑时带上这个人的转分享键，那台再核对一次，没同意就拒绝(换组里下一台，不冷却)；
    主人撤回时那台立即结束这个人的任务；查询供应商、续接归属等等待结束后，登记任务前再次核对，同一步登记，中间不再等待。
    每次向分享来的电脑打开任务(含已有绑定的续接)都现查 `reshareConsent` 能力；降级的旧端不能沿用缓存同意接任务。
    同步和清理连续失败后按 1、1、5、10、20、30 分钟退避，之后最多每 30 分钟一次；成功清零。重复分享快照与设置页读取不穿透退避，
    真正变化的名单可立即尝试一次；分享名单观察到那台从离线或暂停恢复在线时只唤醒那台。同类失败只在首次或原因变化时记 info，其余记 debug。
    分享暂停时不发同步；完整可信名单确认分享已删除或退出时停止该分享的网络轮询，但保留未确认的清理记录，不把暂停或 `ACCESS_REVOKED` 当作删除。
    分享来的电脑离开全部组时，移出组与待清空记录同一次原子写入；空名单被确认后才删除，失败按上述间隔退避，重启后继续。重新加入
    也先清空旧同意，再重新报人；已确认的空名单不再定时轮询。实现与回归见 `provider-group/store.ts`、`reshare.ts` 及对应测试。
    名单超过 256 人时由支持 `reshareBatch` 的新版电脑按批次分片，每片回报当前片状态，接收端收齐后才整体替换；批次数不设固定人数上限，
    接收端以字节预算保护内存；已完成片段重发仍幂等。旧版不能安全接收大名单时显示需要更新，不发送部分名单。
    那台的 Cindy 太旧、给不出同意时不分给分享的人。分享的人看到的匿名状态里这台写「暂不
    可用」(或「需要更新」)，组的台数不变。同账号的电脑经组使用(组所在电脑自己与我的其他电脑)不需要同意。
    协议见 `docs/dev-rules/protocol-compatibility.md`「供应商组：转分享需原主人逐人同意」。
  - 被中转过来的任务，组内电脑一律按受邀者隔离运行（即使来自同账号的组所在电脑）：受邀者目录、会话索引按
    （组所在电脑, 受邀者）分开，受邀者在那台的身份是组所在电脑为它取的不透明键，任务 id 也按受邀者派生，两个受邀者
    用同一个任务 id 不会撞车。数量上限独立于数据隔离：组内电脑按直接连接的组所在电脑合计，
    不因受邀者不同增加额度；单设备默认 16、整台提供方电脑默认 64，可在「远程与分享」页统一调整，见 provider-sharing.md §3。
  - **续接**只回到当初运行这个会话的那台（组所在电脑记着「哪个会话在哪台」，那台被移出组后也回到那台），不在别处重试；
    受邀者不能凭 id 接回别的受邀者的会话。
  - **启动阶段**（新任务还没开始运行）那台接不下时直接换组里下一台，受邀者无感，旧版本受邀者也享受；每台最多试一次，
    组里能接的都试过才报错（组的电脑数不设上限）。每次尝试的 WebSocket 连接编号不同，换台时关掉上一次尝试的连接；
    打开的结果不明（超时、断链）时，先请那台关掉同一个任务再换下一台（关不到时那台没人拉取的任务也会在空闲超时后结束）。
  - 删除受邀者（分享删除）时，组所在电脑请接过它任务的组内电脑清掉它留下的会话记录与目录（`forget`）；组内电脑只清
    调用方自己的那个受邀者。「接过任务」从发出打开那一刻算起，启动失败、还没有会话的那台也会通知。当时没通知到的
    （离线等）记在组所在电脑上，之后自动再通知（约每 10 分钟一次，重启后继续），通知到才划掉。
- **防转圈**：经组分配到组内电脑的任务，在那台电脑上直接运行，不再进入那台电脑自己的供应商组。
  打开任务时带一个可选标记 `groupAssigned` 说明「已由供应商组分配」；旧版本不认识这个标记，也是直接运行。
  登记见 `docs/dev-rules/protocol-compatibility.md`「供应商组」。

## 5. 组策略

- **谁用都是一套（2026-10-15 用户裁决，撤销 2026-10-12 的「本机自用优先」）**：组所在电脑自己的任务、同账号其他电脑、
  分享的人，初次分配与故障重选都按同一个组策略、同一套可用性与并发上限选电脑，本机只是组里普通的一台。
  唯一的区别是本机的「暂停对外分配」只拦外部任务，组所在电脑自己的任务仍可以分到本机；这个豁免只由主进程的本机任务入口
  给出，远程请求与分享中转不能自报“本机任务”来绕过暂停。正常运行的任务不会因此迁移。
  代价（用户已知并接受）：本机任务可能分到别的电脑运行，读文件、跑命令要在两台电脑之间往返；选电脑时与外部任务一样
  最多等组内电脑状态 3 秒。
- **选择方式**：最少占用（默认，选正在运行任务最少的那台）、轮询、按顺序（排在前面的优先，前面的不可用才用后面的）、
  按权重。读得到 Claude Code 或 OpenAI 订阅用量时，先按下方「配额先比」筛，组策略只在剩下的几台里挑（2026-10-15）。
  原来单列的「用量均衡」不再出现在设置里；已经存了它的组挑法与最少占用相同，界面按最少占用显示，用户改选时才写回新值。
- **并发上限**：每台组内电脑单独设置，默认 4，最多 16（组分配的独立设置，不随远程任务数量设置改变）；只统计经本组分到这台的任务，
  包括同账号其他电脑经本组直连过去的任务：它们由任务所在的电脑在每一轮开始、结束时报告，运行期间每分钟再报一次，
  组所在电脑 150 秒收不到就不再计入；刚选中、还没报告的任务先按占用记 30 秒，同时开的几个任务不会全落到同一台。
  - **分享来的电脑**（2026-10-10）：分享者电脑在给组所在电脑的供应商目录里报告**本账号**（组所在电脑这个账号的每台电脑）
    此刻在这个分享上正在运行一轮的任务数，包括不经组、直接选那台用的任务；不含分享者本人和其他受邀者的任务。
    这台的运行数取它与上面经本组的计数中较大的（经组分过去的都在其中，刚选中还没开始跑的仍按经组计数占着）。
    设置页显示与分配用同一个数。目录短时缓存 15 秒，设置页每 15 秒刷新，最多晚约半分钟。分享者是旧版本时不报，
    照旧只算经本组的。
  - **本机与同账号电脑**（2026-10-10）：按那台电脑上这个供应商**实际正在运行一轮的任务总数**统计：那台自己的任务
    (Agent 在那台运行的，不论是否经组)，加上它替其他电脑运行的远程 Agent 任务(本账号其他电脑的、分享的人的)。
    Agent 在别处运行的任务算在别处，转给组内另一台的任务算在那一台，不重复计。本机现算；同账号电脑在给本账号电脑的
    供应商目录里报告(`runningTurns`)，只报允许被远程调用的供应商，分享出去的目录里去掉，受邀者看不到。取值方式、
    刷新时间与分享来的电脑相同；那台是旧版本时不报，照旧只算经本组的。因为算的是全部任务，那台的主人自己在用时
    也会占它的并发上限。本机负载与目录并行读取，负载单次最多等 1 秒；超时或失败不影响已确认可用的本机，这一轮改用现有的经组占用计数，
    迟到的负载读数不改变已经返回的结果。回归见 `directory.test.ts` 与 `router.test.ts`。
- **只分给可用的电脑**：在线；对方仍允许远程控制，且仍对这个供应商允许被远程调用；分享未暂停、未删除；
  不在冷却中；提供所选模型；未被设为「暂停分配」（本机自己的任务使用本机除外）。按组策略分配时优先分给未达到并发上限的；都满了时分给相对最空的一台，
  并发上限只用来分摊，不因满载拒绝消息。
- **先排除额度耗尽，再比较用量**（2026-10-12 用户确认）：所有组策略都复用上面的可用性筛选；本机与同账号电脑上的
  Claude Code 与 OpenAI 订阅另读已有的订阅用量，5 小时、总周配额或当前模型专属配额任一用完，就不再分给它，
  不必先运行失败一次。重置时刻与 [用量上限自动继续](usage-limit-auto-continue.md) 共用判定；已过重置时刻的旧窗口不再阻塞。
  组状态把总窗口耗尽显示为冷却中；模型专属周额度只影响对应模型，不能把其他模型一起封住。快照判断不写入持久冷却，
  实际错误产生的冷却也按任务模型隔离，不能把分模型限额变成整台电脑的冷却。
  OpenAI 按任务框架和模型取数：Codex 按模型匹配原生限额桶，Pi 与 Claude Code bridge 使用 ChatGPT web 槽；
  不拿其他模型的桶或另一框架的槽代替。Codex 的每个桶与 web 槽分别检查快照时间，新桶更新不能让旧桶重新有效。
  - **配额先比**（2026-10-21 用户裁决：快作废的额度最优先，其次各账号平均；取代 2026-10-15 的「5 小时内重置的周配额、
    1 小时内重置的 5 小时配额先用，再比已用百分比」。不论选哪种组策略都先做这一步）：先做上述排除，再在未达到并发上限的候选里
    按**额度有多急着用**筛；全部读不到用量时不筛，原样交给组策略：
    0. **先避开 5 小时配额快满、离重置还早的**（同日用户裁决）：5 小时配额用到 85% 以上、离重置还有 1 小时以上（或不知道何时
       重置）的号先不分新任务——刚开始就撞上限会被迫换电脑、丢上下文；5 小时配额是限速，没用完不会少用周配额。1 小时内就重置的
       照常分，把剩下的用掉；所有能分的号都是这样时不避开。读不到用量的电脑排在这种号前面。
    1. **急不急 = 剩下的额度 ÷ 剩下的时间**：两者都按窗口的百分比算。比如周额度还剩 40%、这一周还剩一半时间，急不急是 0.8；
       1 表示照这个速度到重置时正好用完，越大越该先用。快重置还剩很多的最急，刚重置的不急；几个账号重置时间相同时剩得多的
       更急，所以用量会被拉平。比的是比例而不是差多少：周额度还剩 3%、3 小时后重置（1.68）仍排在周中只用了 40%（1.2）的
       账号前面，免得最后一点作废。
    2. **只看周额度**：Claude 看总周窗口，有对应模型的专属周窗口时两者取不急的那个（一个窗口用得太快就不再催这台）；
       OpenAI 看所选桶或 web 槽里长于 5 小时的窗口，只有 5 小时窗口的套餐按它算。5 小时窗口用完时排除这台、快满时按第 0 条
       避开，不参与急不急的计算。窗口还没开始计时（没用过、没有重置时刻）按 1 算；用过却没有重置时刻、快照过期或窗口已重置但
       还没刷新的，按读不到处理，不当成没用过。
    3. **组策略在一样急的几台里挑**：只留不低于最急那台 90% 的几台，再由组策略挑：最少占用选运行任务少的，按顺序选排在前面的，
       轮询接着上次往下轮，按权重按比例随机。读不到用量的电脑（别人分享的、尚未接入用量的订阅或 API 连接）排在读得到的后面。
    全部达到并发上限时同样先按急不急筛，再选运行任务最少的；未满载的电脑永远排在满载的前面。设置页在组策略下始终显示适用条件与规则
    「能读取订阅用量时，先用快重置、还剩得多的电脑，各账号会按时间均匀用掉；差不多时按组策略」；不能仅按组所属的本机连接类型隐藏说明，
    因为 API Key 连接建的组也能包含同品牌的远端订阅账号。实现见 `apps/desktop/src/main/provider-group/usage.ts`（急不急）、
    `scheduler.ts`（筛选与组策略）与 `apps/desktop/src/renderer/features/provider-group/ProviderGroupSection.tsx`，回归见
    `apps/desktop/src/main/provider-group/__tests__/usage.test.ts`、`scheduler.test.ts` 与 `router.usage.test.ts`。
  - **取数与兜底**：复用已有订阅 reader，组模块不读取凭证、不直连新的订阅 API；每台按自己的供应商账号读取。
    OpenAI 并行读取已有原生限额 RPC 和账号用量 reader：原生限额不依赖已有任务或用量面板，web 槽沿用现有后台刷新。
    OpenAI 本机与同账号远端快照短缓存 15 秒，Claude 仅远端短缓存；同账号同一请求在途去重；两路并行、各自缓存与限时，单次最多等待 1.5 秒，
    一路超时或旧端不支持时仍使用另一路已完成的有效数据；三秒快速选路先到时也合并已完成来源的有效快照，不因另一路还在读取而丢掉已知耗尽结果。
    两路都读不到才按未知用量继续。后台晚到结果独立补入缓存，供后续分配使用，
    不刷新另一路的快照时间。快照超过 10 分钟或时间异常时不用于排除与排序；已重置但还没刷新的窗口也不当成零用量。
    重试选电脑时清掉短缓存。账号切换后丢弃旧账号的读取结果。
  - **分享边界**：不读取别人分享来的电脑的订阅配额，按未知用量处理，仍复用现有可用性与失败后换电脑；
    组所在电脑为受邀者选电脑时可以使用自己组内的同账号配额，但不向受邀者返回配额。
  - 正在回复的任务不因用量差距迁移；新任务和需要换电脑时按此策略分配，上一轮结束后用户发下一条消息时，同账号原生接续
    自动换号，实际需要摘要时才确认（§6.2）。
  - 已经绑定的任务在发送前由组所在电脑按本次模型重新核对额度；总窗口或该模型专属周窗口耗尽时换电脑，
    OpenAI 同时核对任务框架，快照未知时不因额度判断阻塞发送。
- **冷却**：组内电脑上的任务报用量上限时，仅该任务模型进入冷却（Claude 按同一模型家族合并别名），其他模型仍可分配；
  可信快照显示 5 小时或总周额度耗尽时，仍对所有模型排除这台电脑。重置时刻按
  [用量上限自动继续](usage-limit-auto-continue.md) 的口径取（不采用不带时区的钟点）；取不到时默认冷却 30 分钟。
  冷却不主动迁移这台电脑上正在运行的其他任务；它们自己撞到上限时再按 §6.1 换电脑。
  同账号其他电脑直连时撞到用量上限、登录失效或服务繁忙，也报告给组所在电脑冷却那台（报来的重置时刻最多信 8 天）；
  连不上只由发现它的那台电脑自己在这一轮避开，不替全组判断——可能只是那台电脑自己连不过去；这一轮组里只剩这样的电脑时，
  先等它恢复再换（§6.1）。
  登录失效、服务繁忙仍是整台电脑的 2 分钟短冷却。未指定模型的组状态只显示总额度与整台电脑的冷却，
  按模型查询、发送前检查与分配使用同一模型范围。旧版未记录模型的持久冷却在加载后最多保留 2 分钟；
  旧版控制端报告未带模型时也最多冷却 2 分钟，之后依靠实际额度和运行结果重新判断，避免延续旧版误封数天的问题。
- 组内电脑的在线状态、分享状态与模型目录定时核对；不可用的电脑在组里标出原因。
- **组内状态以组所在电脑为准**（2026-10-11 用户确认）：组所在电脑有组内每台电脑的状态——在不在线、供应商开没开、提供哪些
  模型、在跑几个、是否暂停分配，以及那台账号的问题（用量上限、登录失效、服务繁忙）记下的冷却——同步给所有使用方，使用方
  （组所在电脑自己的任务、同账号其他电脑、分享的人）都按这份状态筛选、选电脑。
  - 使用方自己那边的问题（这台连不上它、版本不配等）不记进组的状态，不影响别人；这一轮里试过的照旧不再试。
  - 状态有延迟是可以接受的：试过不行就换下一台；带着这一轮试过的电脑再来选时，组所在电脑不用短时缓存，现读最新状态再选。
  - 选电脑时读状态最多等 3 秒：到点已经有一台能接的就不再等更慢的那几台（这次按不能用算，读取照常在后台完成）；一台能接的
    都还没有时照旧等全部读完，不会因为慢就误报都不能用。组里都不能用时直接提示「供应商组里的电脑现在都不能运行这个任务」。
  - 冷却按账号存在组所在电脑本机（`provider-group-cooling.json`），重启后照样避开撞了上限的那台。
  - 已知局限：组所在电脑读不出来的问题（例如那台目录读得到、Agent 却起不来）不在状态里，每个任务仍会先试到它再换下一台。
  - 分享来的组员与自己的电脑同一套(2026-10-11)：分享者拒绝(关了远程控制或这个供应商的「允许被远程调用」)按不可用，不当离线
    去等；离线已久(分享没有最后在线时刻，按本机第一次看到离线算，只会少算)与同账号电脑一样不再等它恢复。
  - 本机的组给本机任务选电脑时，选中的同一步就记上临时占用(到那个任务开始运行一轮为止)，同时开的几个任务不会全落到同一台。
- 组里所有电脑都失败才报错，见 §6 自动换电脑。

## 6. 任务与组内电脑的绑定

- 任务第一次在组里运行时按 §5 的组策略选定一台组内电脑，之后固定在这台：对话记录保存在那台电脑上。只有正常运行时才保持
  固定；那台电脑出问题时按下面的规则**自动换电脑**，不需要用户操作。
- 正在回复的任务不会因为组策略变化或其他电脑空闲而自动迁移；为配额换号只在上一轮结束、用户发下一条消息时
  进行；同 Harness 的同账号换电脑自动接续原生记录，无法恢复时先确认再使用有界交接，见 §6.2。
- 只给从没运行过的任务按 §5 选电脑。已经运行过、正用着组那一项的任务不按策略挪走：留在原处并纳入组，之后出问题时
  照常自动换电脑（2026-10-10 用户要求：老任务也要生效）。包括：
  - 建组前就在用这个供应商的任务、回退或清空后原生会话被清掉的任务；
  - 运行过之后才在模型选择里换到组那一项、但 Agent 本来就在组那一项上(组所在电脑的这个供应商)的任务；
  - 同账号其他电脑上的老任务：用着另一台电脑上建了组的那个供应商（在组所在电脑本身运行），由任务所在的电脑问组所在电脑
    确认它在组里。
  - 纳入的时机：启动 Agent 时（问组所在电脑最多等 3 秒，问不到就照常启动）；当时没纳入的（一直开着没重新启动、
    或启动时问不到）在因 §6.1 的原因失败时先纳入，再照常换电脑，所以已经开着的老任务点重试也会换。
  - 问组所在电脑超时只算「读不到」，不算组已删除：组所在电脑慢一点不会把已归组的任务移出组(2026-10-11)。
- **同 Harness 换电脑优先接续原生记录**（2026-10-28）：同账号的 Claude Code、Codex、Pi 先关闭源端会话，
  复制完整原生转录（包括工具结果及原生压缩记录），以新的原生 ID 在目标电脑恢复；Cindy 任务不复制，源记录与工作目录不删除。
  目标必须声明原生传输能力，记录经分段与完整性校验后才导入，启动后还要确认实际恢复的 ID。只有成功才标「已续接原任务」。
  Claude Code 先等 CLI 初始化握手确认，不能把启动前预填的 ID 当作成功；原生恢复失败由宿主决定摘要回退，不允许适配器静默新建空会话。
  上一次切换尚未注入原生会话的待发送交接也必须保留，不能用已迁移原生记录替代这部分尚未送达的上下文。
  源端离线、记录缺失、旧版目标、不兼容或恢复失败时使用有界 handoff，并标「已用摘要接续」；跨 Harness 与分享中转仍走 handoff。
  原生已压缩掉的内容不会凭空恢复，进程句柄等运行状态不随记录迁移。传输期间清空历史、取消发送、换账号或改选时不提交旧结果。
  启动失败换下一台也共用此规则，不直接拿原电脑的 ID 到别处打开。没有原生记录的任务直接新建。
  - 不纳入：直接选组里某台电脑或分享来的供应商的任务（用的不是组那一项，§4）；因组内电脑被移出、或组被删除而解除过
    这个组的任务（§9.4，任务所在的电脑按组记下，之后同一台重新加入、或重建同一个组也不纳入）。
- **在模型选择里把任务换到组那一项、要换电脑时由组选电脑**（2026-10-11 用户反馈：此前直接落到组所在电脑本身，它撞了周上限，
  先报错才换）：发送这条消息、真正换过去的那一刻按组此刻的状态与组策略选一台能用的电脑（与新任务同一套），
  直接换到那台并纳入组；组里都不能用时直接提示「供应商组里的电脑现在都不能运行这个任务」，不换、不发，选择保留。选中的就是
  任务此刻所在那台电脑、但用的不是组里那个供应商时，照用户选的位置换。组读不到时照用户选的位置换。
- 用户在模型选择里把任务挪到组外的电脑或换成别的供应商，任务即退出组：之后不再自动换电脑，也不把那台的失败
  记到组内电脑头上。挪到组里另一台时绑定跟着更新，仍由组管：那台出问题照常自动换电脑，挪过去之后的第一次失败也换
  （2026-10-11 用户反馈：此前绑定刚改过的那次失败会被跳过，直接报错）；之后再挪回组那一项时按上一条重新纳入。

### 6.1 自动换电脑

供应商 Cindy 重启导致原 run 消失时（2026-10-29），优先在原电脑接回原生会话，包含未归组的
远程供应商。复用本节等待、恢复租约、取消和一次续跑入口，不改变组分配；每次中断只消费一次
续跑，连续故障仍受现有五次探测预算约束。没有输出也发续跑指令，不重发原始请求：工具可能已在
任务所在电脑执行，指令要求先核对现状。接不回原会话或预算耗尽则保留错误与人工继续入口。
是否允许自动恢复沿用既有资格检查；Stop、新输入、删除／归档均可取消。
供应商主人主动断开或关闭远程控制属于用户撤销，新版通过 `controller-disconnected` 转为既有
`user-revoked`，不自动接回、换电脑或发中转切换凭证。旧版 host 只发 `aborted` 的歧义与取舍见
`protocol-compatibility.md`「远程 Agent」；不能借重启兼容覆盖新版的明确断开意图。
实现：`remote-agent/controller/startRemote.ts`、`provider-group/service.ts`、
`maker-ipc/agent-input-coordinator.ts`；测试并入对应模块的既有测试文件。

供应商组的目的就是多个账号一起用、出问题自动换，所以**因电脑本身的原因失败时，自动换到组里下一台可用的电脑
继续，组里所有电脑都失败了才报错**。

- **怎么判断换不换**（2026-10-11 用户确认：统一成一个判定，默认出问题就换）：所有路径——新任务启动失败、运行中的终态错误、
  发送前与换电脑途中换不过去、组所在电脑替分享的人中转、协同 Worker——都问同一个判定(`provider-group/failurePolicy.ts`)，
  路径只负责拿到这次失败和执行决定。每次失败记一行决定日志(只带错误码与结构化字段，不带错误原文)。
  - **不换**：换到哪台都一样——上下文超出模型上限、请求本身无效、内容被拒、工具循环被拦、权限确认被拒、工具执行出错、本机准入
    (模型停用等)；或不是那台电脑的问题——用户停止或已接手、本机主动关掉了会话、任务此刻的状态不允许(在运行、已删除等)、组里
    已经都不能用。这些照现有方式报错。
  - **其余一律换**，不再只认列出来的错误：用量上限、额度或余额用完、请求频率限制；登录失效、被拒绝或被停用；那台离线、不可达、
    关闭了远程控制或远程调用、分享被暂停或删除、不提供这个模型、版本太旧、没装这个 Agent；Agent 启动失败、一轮中途意外退出；
    模型容量不足或服务过载(终态错误到达主进程时，组能接管就优先换电脑，不再叠加通用同机自动续跑；Agent 内部已有的有界重试保留)；
    服务报错或超时(偶发一次先由中断自愈在同一台重试，重试用尽才到这里，即「同一台连续失败才算」)；以及其他认不出的失败
    (活动记录写「{原电脑} 出了问题，已换到 {新电脑} 继续」)。
    远端组随后核对配置、发现自动切换已关闭或不适用时，交回原有中断自愈，并移交暂存错误与终态；
    已经接管、但组内备用电脑都失败时则照常放出失败，不重新叠加同机重试。
  - **换时先不先等**：只是连接断了(连续拉不到那台、对方 Cindy 重启后会话没了)先等它恢复，恢复了留在原电脑；可能连不上
    (读取放弃、分享连不上、太忙)先现读一次，确实连不上才等，连得上就直接换；其余不等。见下面「连不上先等它恢复」。
  - **记不记进组的状态**：只有那台账号的问题(用量上限、登录失效、服务繁忙)记进组的状态(冷却)；连不上、起不来、其他失败只在
    这一轮不再试，不影响别人(§5「组内状态以组所在电脑为准」)。
- **本机的操作不打断进行中的远程一轮**（2026-10-11）：切换侧栏焦点时插件 Library 只读目录的同步、改附加目录、改思考档位等本机的
  控制操作，不会因为 Agent 所在那台暂时连不上就把正在跑的一轮杀掉：没有要改的不去碰运行中的会话；要改而那台回不来时，这一轮结束后
  再按已保存的设置重建。本机主动关掉会话不是那台电脑的问题，不触发换电脑。
- **怎么换**：
  - **重新选哪台**：沿用 §5，谁的任务都按组策略重选（本机恢复了也不优先回到本机）；只有本机的「暂停对外分配」
    不拦组所在电脑自己的任务。连不上时先等原电脑恢复的规则不变。
  - **还没开始运行**（打开任务、Agent 启动阶段）失败：直接换下一台，没有可感知的中断。
  - **运行中失败**：把这台标为不可用（用量上限进入冷却，§5），复用现有的跨电脑交接，把任务交接到按上述规则选出的
    下一台：优先迁移原生记录，不能恢复时新建会话并带上交接上下文，然后继续这一轮——这一轮还没有产出就重发原消息，已经有产出就发续跑指令，
    与 [用量上限自动继续](usage-limit-auto-continue.md) 的续跑口径一致。消息流里显示一行活动记录
    「{原电脑} {原因}，已换到 {新电脑} 继续」（受邀者那边写「已自动换一台电脑继续」，§8），不计为用户发送。
  - **连不上先等它恢复**（2026-10-11）：那台是连不上（离线、断线）时先不换：现读一次那台的状态，确实连不上才等，
    按退避（约 3、6、12、20、20 秒，与中断自愈相同）最多重试 5 次，每次现读。恢复了就留在原电脑继续这一轮（不交接、
    不冷却，活动记录写「已重新连上 {电脑}，继续运行」，读不到名称时写「原来的电脑」）；5 次都不行才按上面的方式换到下一台。
    等的期间错误同样先不呈现，消息流与输入框状态显示「重新连接中 n/5」，开始换电脑时改为「正在换一台电脑继续」。
    - 只是连接断了（断线、远程 Cindy 重启后会话没了）而现读第一次就已连得上：断线刚好已恢复，也算一次重试、留在原电脑
      继续；同一轮次数照算，那台反复断也只这 5 次，用完就换。
    - 不等、直接换的情况：现读连得上但问题不在连接（如那台 Agent 起不来）；那台本身不能用（供应商关掉、关闭了远程控制或
      远程调用、分享暂停或删除等）；本机这台；用量上限、登录失效、过载等不是连不上的原因。
    - **确认用不了的不等**（2026-10-11 用户确认）：组的状态里它在冷却中，或同账号那台已经离线超过 2 分钟，就不等，直接换；
      只有刚才还在正常用、突然断开的那台才按上面先等。运行中失败、发送前、别的电脑上的组读不到时都这样；组所在电脑或设备
      列表读不到时按不知道，照旧先等。
    - 次数按一轮、按电脑计，自动续跑与运行中失败共用；用户亲自发消息、重试、换模型即开始新的一轮，重新计。
    - 发送前：已归组的任务所在那台显示离线、或这次发送要重新打开那台上的会话（会话没开着或不在运行态）时，现读一次那台的
      状态，并由组所在电脑按本次模型重新核对可用额度；离线就同样先等（消息还没发出，进行中行显示「重新连接中 n/5」），恢复了照常发到原电脑，等不到再换到下一台
      再发。用户停止这次发送时立刻停下：不再等、不再换，也不再去打开那台上的会话。
      原电脑在冷却等不能用、要先换过去时，换不过去（目标电脑本身的问题）就换组里下一台，不把消息发给不能用的原电脑；
      都换不过去才照常发到原电脑，换不过去的电脑记为这一轮试过，这条消息随后失败时不再重复去试、重复去等（2026-10-11）。
    - 别的电脑上的组读不到（常见是任务就跑在组所在电脑上、它自己断了）：换不了电脑，但仍按任务记录里的位置先等那台恢复，
      恢复了在原电脑继续（活动记录写「原来的电脑」），等不到照原有方式报错；发送前同理。
    - **要换过去的那台连不上也先等**（2026-10-11）：换电脑时选中的那台从这台电脑连不上（断线、不响应；组所在电脑那边看它
      可能是正常的），组里还有别的电脑就先换别的；只剩这一轮因连不上而跳过的电脑时不急着报错，按同样的退避等它恢复（刚换过去
      失败，先等一会儿再现读），恢复了再换过去，等不到才交回原有的报错。次数按电脑计、与等原电脑共用一份，那台「看着连得上
      却换不过去」时也最多试这几次；等的期间消息流与输入框状态仍写「正在换一台电脑继续」。运行中换电脑与发送前换电脑都这样；
      换过去失败的原因不是连不上（那台不提供这个模型、分享暂停等）时不等，照旧换下一台或报错。
    - 已经发出却在那台上没确认收到的消息（如请求超时）不自动重发：可能已经在跑，重发会让同一条消息执行两次，照原有方式报错。
    - 下面「换电脑久久没有结局（3 分钟）先把错误放出来」的计时不吃掉等它恢复的时间：每次重试、开始换电脑时重新计时。
  - **换电脑期间不报错**（2026-10-10）：这次失败会先试着换电脑时（已归组、自动换电脑开着、组里还有别的电脑；
    受邀者那边是收到了「需要换一台」凭证），失败那一刻就不呈现：没有红色横幅、不写错误卡、不亮红点、Agent Island 不提醒，
    消息流末尾只有一行「正在换一台电脑继续」，输入框上方的状态同样这样写。换成了，历史里只留上面那行换电脑的活动记录
    （原因在展开详情里）；没换成（组里都不能用、交接失败、自动换电脑关着等），这时才补上错误卡与横幅，交回原有的报错与
    额度重置后自动继续。换电脑途中用户亲自接手时，错误卡照常补进历史（按出错的时刻排在用户新消息之前），但不再弹横幅。
    换电脑久久没有结局（3 分钟）时先把错误放出来，之后换成了照常续跑。出错时才纳入组的老任务（§6）判断不到，仍会先报错再换。
    少见的时序例外：错误早于这一轮的用户消息落库完成到达时，错误卡与红点在判断之前已经出现，换电脑期间只是不再挂横幅。
  - 换过去之后任务固定在新电脑上，原电脑恢复后也不换回去（每换一次都要重新交接）。
  - **协同任务**（2026-10-10）：Lead 与 Worker 都按上面的规则分配和换电脑，引擎与模型不变、只换 Agent 所在电脑；
    用户也可以像普通任务一样在模型列表里给 Lead 与 Worker 换模型、换位置（2026-10-16 用户裁决；运行设备 Worker
    除外，见 `docs/dev-rules/orca-team-architecture.md` 第 11 条）。
    - 新建的 Worker 跟普通新任务一样按组策略选电脑。Worker 跟着 Lead（没另选位置，或选的就是 Lead 现在所在那台）
      而 Lead 用的是组那一项时，Worker 跟的是这个组，不是 Lead 这次落到的那台；组那一项不提供所选模型时照旧跟 Lead
      所在那台。Lead 的 `list_available_models` 不指定位置时同样列组那一项所在电脑的模型。
    - Worker 换电脑期间这一轮还没有结局，不把「异常终止」回报给 Lead：换成了、续跑真正派发出去后，续跑那一轮结束时照常把结果
      回报给 Lead；没换成（组里都不能用、交接失败、续跑没派发出去、中途有人接手）才把这次异常终止回报给 Lead，与没有供应商组时
      一致。久久没有结局（3 分钟）先回报给 Lead 时，这一趟换电脑就此停下，不再换过去续跑(Lead 已据此重新安排，不能再收到第二份
      结果)；普通任务照旧先放出错误、换成了照常续跑。
    - Worker 换电脑后不做「等额度恢复后自动继续」：组里都不能用时失败照常交给 Lead 重新安排
      （[用量上限自动继续](usage-limit-auto-continue.md) 不覆盖 Worker 的口径不变）。
    - 换电脑途中 Lead 给 Worker 发来消息、或 Worker 的回报到达正在换电脑的 Lead，按亲自接手处理：这一趟换电脑停下，
      那条消息开始新的一轮（这一轮试过的电脑与等待次数清零；发送前发现原电脑在冷却时照常先换电脑）。
    - 换过去的会话照常带着协同身份、提示词与协同工具；唤醒空闲 Worker 与换电脑互斥，不会在换电脑的空档里按旧位置
      把它拉起来。
- **何时停止**：同一轮里每台组内电脑最多试一次；全部试过仍失败才报错，并提供换模型。
  其中有电脑是撞到用量上限的，按 [用量上限自动继续](usage-limit-auto-continue.md) 等恢复后自动继续
  （错误横幅显示「将于 X 自动继续 · 取消」）。
  - 首版：交回现有的报错与额度重置后自动继续，等的是任务当前所在那台的重置时刻；错误里逐台列出原因、
    按全组最早恢复的一台等，放到 P3。新任务分配时组里没有能用的电脑，报「供应商组里的电脑现在都不能运行这个任务」。
  - 一轮的边界：用户亲自接手(发消息、重试、换模型)即开始新的一轮；距上一次换电脑超过 30 分钟也算新的一轮。
  - 首版运行中的换电脑只在不同电脑之间进行：同一台电脑上的不同账号(例如一台电脑登录了两个订阅)可以接新任务，
    但不会在运行中互相替换，后续支持。
  - 交接会关闭旧会话；交接前先登记这次错误的重试入口，交接完成后凭它重新挂上续跑。用户在换电脑途中亲自接手
    (发消息、重试、换模型)或那次错误已被新的一轮接管时，后续每一步都停下：不再交接、不冷却任何电脑、不续跑，
    也不再交回原有处理。
  - 交接失败按同一个判定：问题出在目标电脑本身(连不上、分享暂停、Agent 起不来、登录失效等)时把那台记为试过(账号的问题
    才冷却)，换下一台再试；任务正在运行、已被删除等与目标无关的失败直接结束本次换电脑。换过去的那台交接成功、Agent 却没能
    启动时同样按换不过去处理、换下一台，不把续跑交给起不来的电脑。都不行时交回原有的报错与额度重置后自动继续。
- **代价与告知**：同 Harness 的同账号换电脑优先保留完整原生记录；摘要接续可能遗漏细节。换电脑后提示缓存可能需要重建，
  因此可能多消耗 token。出问题时自动换电脑默认开启，组设置里可以关掉；关掉后照现有方式报错，用户可以在模型选择里
  手动换到另一台电脑。
- **实现**：运行中的换电脑复用「已建任务换 Agent 所在电脑」(`performSessionAgentSwitch`，优先原生恢复，失败时有界交接)，
  续跑复用额度重置后自动继续的同一条路径(`continueAfterUsageLimitReset`)，活动记录在这条续跑记录上带
  `agentSwitch`(原电脑、新电脑、原因)；旧版本手机与桌面不认识该字段，显示成「用量已恢复，已自动继续」。
  Agent 还没开始运行就失败(打开任务阶段)时，在启动入口直接换下一台。代码在 `apps/desktop/src/main/provider-group/`。
  远程发送的限额拒绝与 SDK 限额终态按同一次发送合并：无论哪条先到，都先完成切换判定并交付唯一一次终态，再返回发送失败；
  需要切换时凭证排在终态之前。
  防止发送回包提前清掉续跑入口；迟到或重复的同次终态不再次交接、续跑。新发送作废旧交付，不能确认是否送达的超时不据此重发。
- **谁来执行换电脑**：交接要用到任务的对话记录，所以由任务所在的电脑执行。
  - 组所在电脑自己的任务：组所在电脑直接换。
  - 同账号其他电脑（直连）：任务所在的电脑直接看到组内电脑的报错，自己换：把需要冷却的电脑报告给组所在电脑，
    再问它下一台（带上这一轮试过的），交接与续跑与组所在电脑自己的任务同一套。组所在电脑读不到时（离线、断线）
    不换电脑、绑定不动，交回原有的报错；确认组已删除或这台已不在组里时才解除绑定，任务成为普通的远程 Agent 任务。
  - 分享的人（P2c，2026-10-10）：组所在电脑告诉任务所在的电脑「需要换一台」，那边自动交接后重新打开，
    组所在电脑再为它选新电脑。任务所在的电脑需要更新到支持这个功能的版本；旧版本只会看到原有的报错，
    可以手动换模型。具体做法：
    - 任务所在的电脑打开任务时声明支持（可选字段 `acceptsGroupSwitch`）。组内电脑（包括组所在电脑本机）上的任务因 §6.1 列出的原因
      失败（终态错误，或一轮进行中那台的任务意外结束）时，组所在电脑先按组的口径冷却那台，再看组里还有没有能接的
      电脑（这一轮已经换下来的不算）；有就在事件流里先发一张短期凭证，再转出原来的错误。凭证只认该受邀者与任务，失败重开可在有效期内重用；旧版本、没有能接的
      电脑、或换到哪台都一样的失败，只转出原来的错误。
    - 任务所在的电脑只在持有这张凭证时才换：分享被暂停、删除、撤权是分享本身的问题，没有凭证，不会触发换电脑。
      凭证只用于紧随其后的那次错误(2 分钟内)；用户亲自接手(发消息、重试、换模型)即作废。
      容量或过载错误已有有效凭证时立即交接，不先走通用同机自动续跑，避免凭证在反复重试中失效。
    - 换法与组所在电脑自己的任务相同：任务的位置仍是同一个分享，强制交接(全量交接 + 全新原生会话，分隔条写
      「Agent 已改到另一台电脑上运行」，不写电脑名称)，重新打开时带回凭证，组所在电脑据此避开这一轮换下来的
      电脑；然后按额度重置后自动继续的路径续跑这一轮，活动记录写「已自动换一台电脑继续」。交接没成时交回原有的
      报错与额度重置后自动继续。
    - 凭证只认发给的那个受邀者的那个任务，用过、过期(10 分钟)即作废；组内电脑转来的同名状态一律丢弃，组内电脑
      不能替组所在电脑发凭证。同一轮每台组内电脑最多试一次；那台上一轮正常结束，或距上次换电脑超过 30 分钟，
      算新的一轮。
    - 判定与组所在电脑自己的任务同一个(`failurePolicy`)：启动阶段换到哪台都一样的不再逐台试；组选中组所在电脑本机、本机
      Agent 却起不来时与组内电脑接不下一样换下一台；**续接回到原来那台、那台接不下时同样发凭证**，受邀者交接(带上下文)后
      作为全新任务重新打开，组换一台(2026-10-11)。旧版受邀者的任务在组所在电脑本机运行时撞上限同样冷却那台。
    - 已知差异：受邀者那边与组内电脑之间隔着组所在电脑的中转，中转断了(组所在电脑连续 2 分钟拉不到组内电脑)不能在原来那台
      接着跑，直接发凭证换一台；自己的任务会先现读、恢复了留在原电脑。
- **不续接的打开**（第一次运行、交接后的新会话）优先回到原电脑；原电脑不可用或满载时换一台，绑定改到新电脑，
  旧电脑上的会话不能再续接。
- **模型**：组对外提供组内电脑模型的并集；新任务只分给提供所选模型的电脑。任务中途换模型时在当前组内电脑上核对，
  它不提供该模型时提示换模型，不自动换电脑。
  已知差异（P2a）：同账号其他电脑的模型列表里，组那一项列的是组所在电脑本机这个供应商的模型，还不是并集。
- 任务详情与任务头部显示实际运行的电脑：「在 {电脑} 上运行 · 由供应商组分配」；受邀者那边不显示（§8）。

### 6.2 任务进行中换号

2026-10-28 用户裁决（更新 2026-10-21 的发送前确认）：同一个任务里，上一轮结束、用户发下一条消息时也做负载均衡。
**同 Harness、同账号电脑间的原生接续自动切换，不再弹常规确认**；只有实际无法恢复、需要摘要接续时再确认。
传输成功但目标 CLI 恢复失败也属于需要确认的情况。取消或确认超时则留在原电脑发送，保留源原生历史。
共享来源仍沿用原来的知情确认与已有「以后自动换」偏好，不扩大跨账号原生传输范围。

- **什么时候问**：用户自己在电脑或手机上发下一条消息、上一轮已经结束时，问任务所在的电脑。它按 §5 同一把尺子比较：
  组里另一台电脑的配额明显更该先用才提议——两台「急不急」的差乘以那台剩下的时间（百分比）不小于 15，即重置时间相同时
  那台剩下的配额要多 15 个百分点以上（例如已用 70% 对 50%），差一点不打扰。要换去的那台必须此刻能接：在线、未满载、
  未暂停、不在冷却、5 小时配额不紧（§5 第 0 条）、读得到配额；任务所在那台本身也要正常（有问题时交给 §6.1）。
- **不拖慢发送**：点发送要立刻发出、不多等一次网络往返（手机尤其如此），所以电脑与手机在任务空闲时预先问好——上一轮结束、
  打开任务时问一次，空闲期间每 5 分钟再问；问到的提议 10 分钟内有效，只用于下一条消息。没问到、问不到或任务所在电脑是旧版本时
  照常发送。只有真要换号时才等任务所在电脑记下这条消息的换号决定；原生接续不等用户选择，实际需要摘要或共享来源时才询问。
- **不问、不换**：正在回复时排队或插话的消息、定时任务的消息、IM 渠道发来的消息；手机上前面还有没发出的消息或断线时；
  只能换到同一台电脑上的另一个账号时（交接只能换电脑）；伙伴、共享中、目标模式管着限额等待等不由组自动换电脑的任务（与 §6.1
  同一个判定）。
- **原生接续**：宿主先复制并验证原生恢复，成功后聊天保留换电脑及配额均衡原因记录。失败先恢复原位置，再通过已有宿主确认卡询问摘要接续；桌面、手机与同账号远控共同回应，不由模型代答。取消不产生成功换电脑分隔条，也不写入摘要。
- **共享来源弹窗**：写明要换去哪台（同一台电脑上有几个账号时带账号名）、那台的配额还剩多少、多久重置，以及交接摘要可能遗漏细节。电脑上是「换过去」「取消」两个按钮加一个默认不勾的复选框「以后自动换，不再询问（仅本任务）」；
  手机系统弹窗没有复选框，用三个按钮「换过去」「换过去，以后自动换（仅本任务）」「取消」（用户要求与电脑一致）。
- **共享来源选择的结果**：
  - 换过去：这条消息发出前先换到那台（进行中行显示「正在换一台电脑继续」），消息里的分隔条写
    「Agent 已改到 {电脑} 上运行 · 这个账号的配额更该先用」。不勾复选框时这个任务以后遇到同样情况每次仍会问。
  - 勾了「以后自动换」再换过去：这个任务以后不再弹窗，直接换，分隔条照常写一行。只记这个任务，记录存在任务所在的电脑上，
    换一台电脑或在手机上看这个任务也一样；任务删除后记录不再有用，超过 4000 条时丢掉最早的。
  - 取消（含关闭弹窗）：不换，这条消息照常发到原来的账号；下一条消息仍会再问。
  - 无论选什么，这条消息都照常发出。
- **决定的归属**：自动或经确认的换号决定绑定具体这条消息；离开任务而未发送，或另一台控制端随后发消息，都不能把这次决定用到另一条消息上。
- **换不过去**：登记换号后 2 分钟内没发出去的（停止、断线）不留到以后；实际选路时重新检查目标负载、配额和换号收益门槛。
  那台此刻接不了、不再值得换或交接失败时照常发到原来的账号、
  不报错，那台 30 分钟内不再提议。这次换号不算 §6.1 的「这一轮试过」，之后原电脑出问题照常可以换回来。
- 发送前配额均衡不受「出问题时自动换电脑」开关影响（开关管的是故障时自动换电脑）。
- **实现**：判断与执行在任务所在电脑的 `apps/desktop/src/main/provider-group/service.ts`（`rebalanceSuggestion`、
  `rebalanceDecision`、`beforeSend`），尺子是 `usage.ts` 的 `providerGroupRebalanceTarget`；「以后自动换」存在
  `provider-group/sessionPrefs.ts`。电脑在 `features/provider-group/sessionRebalancePrompt.ts`（发送前由
  `CCAgentSessionView` 调用），手机在 `apps/mobile/src/session/sessionRebalancePrompt.ts`（会话页发送前调用）；
  协议见 protocol-compatibility.md「供应商组任务进行中换号」。回归见 `provider-group/__tests__/service.test.ts`、
  `usage.test.ts`、两端的 `sessionRebalancePrompt.test.ts` 与分隔条的 `SystemCard.i18n.test.tsx`、手机 `systemCard.test.ts`。

## 7. 用量

- **记账位置**：组所在电脑。经这个供应商运行或转发的任务都记账，包括本机、同账号其他电脑与分享的人；
  组所在电脑选电脑，知道每个任务实际在哪台运行。同账号其他电脑直连时组所在电脑不经手内容，用量要由任务所在的
  电脑报告给它（P3 定口径）。
- **两个维度**：
  - 按使用方：本机、我的其他电脑（按电脑分开）、分享的人（按人分开）；
  - 按组内电脑：每台实际运行的用量。
- 指标：token(输入 + 输出)、输入、输出、缓存读取与写入、估算金额；时间范围与设置 → 用量相同(所有时间、最近 30 天、
  最近 7 天、今天、选某一天，2026-10-17 起)。订阅类供应商按本地单价估算并标注「估算」，不代表供应商实际账单
  （与供应商分享 §7.4 一致）。
- 同账号电脑经组报告的行带有 Unix 时间戳；组所在电脑按自己的时区重新计算本地日期，增量报告前后各多带两天，
  所以跨时区的午夜边界不会把一天的用量漏掉或重复。
- 按天明细经同账号远程管理回传时最多保留 5,000 行，按日期从新到旧截取，最新一天可以只保留部分行；再按实际 UTF-8
  JSON 大小预留 invoke 信封空间，`coverageStart` 表示实际保留下来的最早日期。
- 没有组的供应商也显示「按使用方」：列出我的其他电脑与分享的人经这台电脑使用这个供应商的用量。
- 组内电脑的主人在自己的分享管理页里看到的是组所在电脑账号的合计用量，看不到最终使用者。
- **已实现（2026-10-11 按人；2026-10-17 改成和设置 → 用量一样，用户确认原型）**：「远程与分享」页的「用量」块与设置 → 用量
  同一套版式、图表与交互(`docs/design-rules/usage-history-charts.md`「远程与分享页」)。2026-10-16 起「已分享的人」整块并进来
  （用户要求：同一个人只占一行），见下方「按人」。

## 8. 告知与隐私

- **组对受邀者透明，不打扰。** 分享者建组、加减组内电脑都是分享者的运维操作，受邀者不收到弹窗或提示，
  使用体验与没有组时一致。为此告知前移到申请时：
  - 受邀者申请弹窗**不论有没有组**都写「Agent 在 {分享者} 的电脑或 {分享者} 安排的其他电脑上运行」，隐私说明写
    「对话内容和 Agent 读取的文件内容会经过 {分享者} 的电脑，并保存在实际运行任务的那台电脑上」。
    之后建组不改变受邀者同意过的内容，所以不需要再提醒。
  - 「分享给我的供应商」详情里的说明与申请弹窗同一句话，受邀者想了解时可以查看。
  - 受邀者那边不显示组内电脑的名称：模型列表标题写「{供应商} · 来自 {分享者} 的分享 · 供应商组 · N 台电脑」
    (2026-10-10 用户裁决；2026-10-12 补充：详情可查看匿名状态，见 §10)；任务头部不显示实际运行的电脑；
    自动换电脑的活动记录写「已自动换一台电脑继续」。组内电脑的名称属于分享者和组内电脑主人，不透给受邀者；
    分享者的电脑名同样不给受邀者(供应商分享 §6)。
  - 分享者这边也不弹确认：「远程与分享」页的供应商组一块写明「分享的人的任务也按组分配」。
  - 分享者的审批弹窗（供应商分享 §4 第 4 步）有组时同意说明写「由供应商组选一台电脑运行 Agent」，不说 Agent 在这台电脑上
    运行；在另一台电脑上审批时按那台目录里带的组摘要判断。读到有没有组之前「同意分享」不可点，免得先按没有组的说法
    同意(2026-10-17 用户裁决)。
- 已知差异（2026-10-09 确认接受）：这条规则上线前加入的受邀者，以及仍在用旧版本申请的受邀者，看到的是
  「Agent 在 {分享者} 的电脑上运行」。不补提醒，只更新「分享给我的供应商」详情里的说明。
- 分享来的组内电脑上，组所在电脑作为受邀者照常受到受邀者隔离（供应商分享 §9）；它的主人只看到组所在电脑账号的昵称与头像，
  以及组所在电脑转述的、请它同意的分享的人的昵称与头像(转分享，供应商分享 §4.3；受邀者申请弹窗已写明会展示给需要同意的
  其他电脑主人)。不给它看分享的人的其他信息，也不给它看组里其他电脑。
- 组所在电脑能看到经它转发的对话与文件内容，与分享者电脑一致；转发内容只在内存中转，不写入日志。
- 组内电脑报出的、会透露它是谁或它与组所在电脑关系的错误(那台对组所在电脑的分享暂停、没开远程调用、连不上等)，
  转给受邀者时统一成「暂时不可用」。已知差异(P2b)：Agent 输出与工具路径里可能出现组内电脑上的会话目录路径(含那台的
  系统用户名)，与受邀者直接用分享者电脑时看到分享者电脑的路径同一程度。

## 9. 安全不变量

1. **Agent 只在被选中的组内电脑上运行。** 组所在电脑不代替组内电脑调用模型，不取得组内电脑的任何凭证。
2. **组不扩大受邀者的能力。** 经组的受邀者仍只能使用远程 Agent 与只读查询（供应商分享 §9.1），其他能力一律拒绝。
3. **使用方之间互相隔离。** 分享来的组内电脑把组所在电脑当作同一个受邀者，所以组所在电脑必须按使用方隔离
   转发的任务、会话续接与上传：一个使用方不能读到、续接或关闭另一个使用方的任务。
4. **撤权立即生效。** 组所在电脑对某人的分享被关闭或删除时，此人经组运行在任何组内电脑上的任务立即停止，
   不触发自动换电脑；对方暂停或删除分享、对方关闭远程调用时，分配到它的任务下一次发送即失败，按 §6.1 换到组里
   其他电脑。组内电脑被移出组只影响之后的分配：已经在它上面的任务留在那台，成为普通的远程 Agent 任务，
   不再自动换电脑；之后同一台电脑重新加入、或重建同一个组，这些任务也不会恢复自动换电脑。
5. **防转圈**（§4）。
6. 同账号的组内电脑沿用同账号远程 Agent 的信任等级，组不改变它；但组所在电脑替受邀者中转过去的任务，组内电脑一律按
   受邀者隔离运行，受邀者不会因为经过同账号的组所在电脑而拿到主人级权限。
7. **组内电脑的名单只给同账号电脑。** `provider-group:remote` 通道与目录里的组摘要都只给同账号电脑：受邀者与共享任务
   访客调用通道一律拒绝，分享出去的目录里去掉组摘要（分享者电脑、受邀者电脑与手机各去一遍），只带组里有几台
   （`groupSize`，2026-10-10）。2026-10-12 增加按需读取的匿名状态（`groupStatus`）：只含固定状态枚举，
   不含组员标识、真实名称、来源关系、任务数、并发上限、订阅配额或用量。组摘要里分享来的组员也不带名字
   （旧快照可能是那位分享者的电脑名）。
8. **同账号管理在组所在电脑上执行。**（2026-10-14，§10）`manage-group` / `manage-share` 只接受同账号电脑，
   只含组设置与分享者操作；组所在电脑自己校验申请与成员属于它的分享，执行后不再转发给其他电脑，账号在途切换即作废。
9. **分享来的电脑不借组转给别人**（2026-10-15）：分享的人的任务只分给主人逐人同意过这个人的分享来的电脑，那台电脑
   打开被转来的任务时再核对一次(供应商分享 §4.3、§9 第 8 条)；原分享被删除或已退出后那台移出组(§3)。

## 10. 界面

- **受邀者查看匿名状态**（2026-10-12）：在「分享给我的供应商」详情中按当前组顺序显示「电脑 1、电脑 2…」与
  可用、忙碌但仍可接任务、冷却中、离线或无法连接、暂停分配、暂不可用、需要更新、状态未知。序号仅为当前列表位置，
  不透露设备身份，不显示用量或展开配额。汇总显示几台可接任务；有未确认的电脑时不能断言全部不可用。
  一项是一台电脑而不是一个账号（2026-10-15，见本节「同一台电脑上的几个账号按电脑聚合」），台数同此。
  - 状态由组所在电脑提供，沿用组的状态与冷却；额外按接收分享任务的条件核对 `virtualWorkspace` / `guestRelay`，
    并反映受邀者分配器已记录的临时版本排除。满载仍能接任务，显示为忙碌；不承诺所有模型都能运行。

    旧分享者未提供状态时明确说明，不能猜成可用。未建组的分享保持原样。手机本期仍不增加组状态界面。

    未发出查询直接取消，不在后台继续排队。已发出的慢查询直到真正结束才释放槽，能力结果短存 15 秒供下一次

  用量计入谁。
- **同账号任意电脑管理**（2026-10-14 用户裁决：组属于账号，不该只能在建组电脑上管）：登录同一账号的任意电脑，

  添加电脑，生成分享链接、处理申请、暂停或删除分享的人，查看用量。当前电脑不需要在组里。

  - 页面里「本机」那一行指建组电脑，用电脑名称呼；用量、配额都读建组电脑，不误显示当前电脑的数据。

    仍到那台电脑上配置。手机本期不提供组管理。
- **自己的组显示版本与分享兼容提示**（2026-10-12 用户裁决）：建组电脑的设置页、同账号另一台电脑查看组的只读详情，
  默认两行展示：名称行附上简短版本号，下一行显示运行状态，不为版本另占第三行。本机使用当前应用版本，
  同账号电脑使用设备目录最近上报的版本；离线时版本不代表已重新确认。分享来源或旧端未提供版本时不常驻「版本未知」，
  未知信息收进名称按钮的悬停／键盘聚焦说明，不拿协议版本代替（2026-10-12 用户反馈三行文字过多）。

  - 详情按需核对能否接收分享任务；仅确定缺少必要能力时在名称行显示「需要更新」，完整原因在悬停说明中，
    不覆盖主人自己的空闲、运行中等状态。这里不是检查有没有更新发布，也不意味着主人不能使用该电脑。

    等待超时不释放仍在途的槽，未发出的排队查询到期取消；已结算能力短存 15 秒，迟到结果供下一次详情读取使用。
    不跨账号复用能力；忙闲等状态仍每次现读，普通状态查询与任务分配不增加探测，不修改冷却与分配。
- **组内电脑一行的结构对所有来源一致**，右侧才能真正成列：设备图标 → 名称、版本与来源 → 状态行 →
  并发上限（按权重时多一个权重）→ 参与分配开关 → 行内 `···` 菜单。三条由此固定：
  - **参与分配只有一种控件。** `paused` 是同一个布尔值，本机与远程都用开关表达，不按来源分叉成
    「开关 / 暂停分配按钮」两套；暂停后的含义由状态行文字说明，不另弹 toast。
    本机这一行的暂停只限制接收外部新任务，本机自己的任务仍可分到本机，故障恢复不受影响（§5）。
  - **运行数是状态，上限是设置。** 运行数只出现在状态行，上限只出现在下拉里，同一个数字不在一行里说两遍。
    **能用时状态词本身报负载**：跑 0 个说「空闲」，跑了就说「{N} 个任务运行中」，不写「可用」——
    否则组里都空着时整列没有数字，看不出每台在跑几个。「已满」等于跑满上限，不再重复报数。
  - **「移出组」收进 `···` 菜单**（与供应商详情头的供应商级菜单同模式）。本机不能移出（§3），
    该位置留等宽占位以保持列宽。

    这个账号的订阅配额（5 小时 / 每周剩余等），与供应商详情页底部的用量卡、任务底部的用量条同一份数据；
    紧贴在这一行下方、与电脑名左对齐，不再出卡片的「Claude · 套餐」标题行（行本身已说明是哪台电脑）。
    本机读本机账号，我的其他电脑经设备互联读那台的账号；别人分享来的电脑不读（分享者的配额不对受邀者开放），
    只写「别人分享的电脑不显示配额」；不在线的电脑不去读。展示组件只在展开时读，收起时停止展示读取；
    组状态与分配所需的 Claude 订阅额度另按 §5 读取，不依赖这一行是否展开。
    同账号远程 Codex 配额与供应商详情、模型列表共用实时读取：展开且页面可见时约每 60 秒复查，收起或隐藏停止；
    按电脑与供应商账号隔离，旧端不支持或读取失败时回退原快照，不改变组调度使用的数据源。
    实现与兼容规则见[供应商分享 §5.2](provider-sharing.md#52-供应商设置)。

    挤在一行里看不懂，又和展开后的剩余配额重复；要看各账号用到哪就展开这一行。本机的组与另一台电脑上的组的只读列表都一样。
    组所在电脑随组状态给出的配额窗口（`quota`）仍发给同账号电脑，只用于 §6.2 的换号提议，界面不显示。

## 11. 与现有规则的关系

- [供应商分享](provider-sharing.md)：§4.1 第 3 步的告知不论有没有组都改用 §8 的说法；§1「Agent 在分享者电脑上运行」、
  §7.2 管理页、§7.4 用量、§9 安全不变量在有组时按本文调整；实现时同步修订该文。
- 远程 Agent 协议：新增 §4 的「已由供应商组分配」可选标记(`groupAssigned`)；同账号直连新增同账号通道
  `provider-group:remote` 与目录里的组摘要；分享的人经组所在电脑中转(P2b)新增 `relay`、`guestRelay` 与 `forget`；
  分享的人的「需要换一台」(P2c)：任务所在电脑打开任务时声明支持（可选字段 `acceptsGroupSwitch`），组所在电脑只对
  声明了的电脑在事件流里发出凭证状态(`providerGroupSwitch`)，重新打开时带回(`groupSwitchToken`)。手机与远程控制问任务所在的电脑
  「这个任务归哪个组」用同一通道的只读动作 `session-group`(§10)。同账号任意电脑管理组与分享用同一通道的
  `manage-group` / `manage-share`(§10)。其余沿用现有协议，不改服务端。兼容做法见 §14，登记见
  `docs/dev-rules/protocol-compatibility.md`「供应商组」。
- [跨电脑复制任务](task-device-migration.md) 与已建任务换 Agent 所在电脑：§6.1 的自动换电脑与手动「换一台继续」
  复用原生转录的导入／导出与有界交接兜底；仅迁移 Agent 时不复制任务、工作文件或凭证。
- [用量上限自动继续](usage-limit-auto-continue.md)：冷却的重置时刻口径与之一致；有组时先换电脑，组里所有电脑都失败且其中有
  撞上限的，才按该文等最早恢复的一台；组内电脑冷却期间，自动继续不会分到这台。
- 手机端：模型列表与桌面一样收起组里的电脑(§10)；供应商组的设置、组内电脑状态与用量只在电脑上。

## 13. 验收

1. 链接的供应商与组不是同一个（§3 口径）、链接属于自己账号、链接失效时不发送申请，并给出对应提示。
2. 组所在电脑自己的任务、同账号其他电脑与分享的人的任务，初次分配与故障重选都按同一个组策略选电脑；本机的
   对外暂停只拦外部任务。正常运行的任务留在原电脑。离线、冷却、不提供模型或可信快照显示所需 Claude 订阅额度
   已耗尽的电脑不选。按组策略分配时优先未满载的，全部满载时仍选运行任务最少的。
   所有组策略都先按 §5「配额先比」：先排除配额耗尽的，按规则避开 5 小时配额快满且离重置还早的，再按「剩下的额度 ÷ 剩下的时间」
   留下不低于最急那台 90% 的候选，最后由组策略挑；全部读不到用量时只按组策略，重置后的旧窗口不再阻塞。
3. 正常运行的任务固定在原电脑；原电脑因 §6.1 列出的原因失败时，自动交接到组内另一台继续这一轮，消息流显示换电脑的
   活动记录；同一轮每台最多试一次，全部失败才报错并逐台列出原因；其中有撞上限的，等最早恢复的一台自动继续。
4. 用户停止、权限被拒、上下文超限、请求无效、内容被拒、工具出错时不换电脑；其余失败都换(含认不出的)。「故障 × 阶段」的判定表
   见 `provider-group/__tests__/failurePolicy.test.ts`，所有路径用同一个判定。本机的操作(切换焦点、改目录、改档位)不打断进行中的
   远程一轮；组所在电脑慢一点不把任务移出组；同 Harness 换电脑优先恢复原生记录，不能恢复时明确使用摘要。
5. 经组转发到组内电脑的任务不会再进入那台电脑的供应商组。
6. 两个使用方用相同的任务或会话标识也不能读到、续接或关闭对方的任务。
7. 关闭或删除对某人的分享后，此人的任务立即停止且不换电脑；移出组内电脑后不再给它分新任务，已在它上面的任务留在那台。
8. 「用量」按使用方与按组内电脑两个维度的合计一致，订阅类标注估算。
9. 受邀者申请弹窗不论有没有组都说明 Agent 可能在分享者安排的其他电脑上运行；建组、加减组内电脑后受邀者不收到任何弹窗或提示，
   也看不到组内电脑的名称。
10. 第二个订阅账号（ID 带随机后缀）能加入同品牌的组；自定义供应商名称相同时能加入（含改过名、ID 带后缀的），名称不同时给出提示。
11. 没有建组的供应商，在新版本里的行为与现在完全一致。
12. §14 列出的旧版本组合都能照常使用：旧版本只是没有组，不报新的错误、不出现看不懂的提示。
13. Light 与 Dark 两种模式都已实现。

## 14. 版本兼容

原则：**没有更新的用户只是没有组，其他功能与现在一致**；新版本里没有建组的供应商，行为与现在完全一致。
模型范围限制另需执行电脑声明 `relayModelAccess`：组所在电脑只把受限成员的任务交给支持逐请求复核的电脑，
否则按既有启动失败流程尝试下一台，没有可用电脑时返回不可用。不限模型的旧电脑仍可接任务；新增限制时结束该旧任务，
不能继续沿用未受限制的路由。完整的模型范围保护要求组所在电脑与执行电脑均更新。
新增的协议内容都是可选的，旧版本不认识就忽略：远程 Agent 解码只保留认识的字段（`apps/desktop/src/main/remote-agent/wire.ts`），
不认识的错误码会显示成通用错误，所以新错误码只发给声明了支持的电脑。

| 角色 | 是旧版本时 |
|---|---|
| 组所在电脑 | 组只在新版本里存在。降级到旧版本后组不生效，这个供应商回到只在本机运行；经组分到其他电脑的任务在旧版本里不能续接，需要换模型或新开任务。同账号其他电脑问它时得到 `CHANNEL_NOT_ALLOWED`、目录里也没有组摘要，当作没有组照常直接连它；已经经它的组分到别处的任务留在原处，成为普通的远程 Agent 任务 |
| 组内电脑 | 照常作为普通的同账号远程供应商或分享来的供应商接任务。「已由供应商组分配」标记对它是不认识的字段，解码时丢弃；它本来没有组，也不会转圈。旧版同账号组内电脑不声明 `guestRelay`，组所在电脑不给它分受邀者的任务(它不会按受邀者隔离)；旧版分享来的组内电脑本来就把组所在电脑当受邀者，照常接组所在电脑自己的任务；它给不出转分享的同意(caps 不声明 `reshareConsent`)，2026-10-15 起组所在电脑不再把分享的人的任务分给它，设置页提示那台需要更新(供应商分享 §4.3) |
| 组所在电脑(转分享) | 2026-10-15 之前的组所在电脑不知道要征得同意，会照旧把分享的人的任务转给分享来的电脑：新版分享来的电脑见到被转来(带中转标记)却没带转分享键的任务一律拒绝(回已有的 `REMOTE_AGENT_PROVIDER_NOT_ALLOWED`)，旧组所在电脑照常换组里下一台，转给分享的人时统一成「暂时不可用」 |
| 同账号其他电脑 | 直连由任务所在的电脑执行，旧版本不认识组：选组所在电脑的这个供应商时直接在组所在电脑上运行(没有组)，模型列表里组内电脑照常单独显示、没有供应商组的标注 |
| 手机与远程控制 | 旧手机、旧控制端不认识组摘要，模型列表照常逐台列出。被控电脑是旧版本时问不到「这个任务归哪个组」(`CHANNEL_NOT_ALLOWED` 或不认识的动作)，按没归组处理：组照样收起，在组那一项里选模型照旧先确认换电脑，与之前相同 |
| 分享的人 | 照常使用，中转对它透明(协议不变)。打开任务阶段的换电脑由组所在电脑完成，旧版本同样享受；运行中失败时它没有声明支持「需要换一台」，组所在电脑照旧返回原来的错误（如用量上限），用户像现在一样换模型或稍后重试。新版本声明支持，运行中失败时自动换一台（§6.1）。旧版本申请弹窗仍是「Agent 在 {分享者} 的电脑上运行」（§8 已知差异） |
| 受邀者申请 | 申请弹窗由受邀者自己的 Cindy 显示，旧版本仍是原来的说法（§8 已知差异） |
| 被管理的电脑(用量) | 2026-10-17 之前的版本不认识「用量」的按天明细(`usage-history`)，回 `[INVALID_PARAMS] Unknown command`，管理的那台统一成「需要更新」并退回所有时间的合计：时间固定为所有时间、不显示两张图，提示更新那台电脑(§7)。旧版管理的那台照旧读 `own-usage` 与 `owned`，不受影响 |

- 本地数据：供应商组设置只新增存储，不改已有的供应商、远程调用与分享数据；涉及数据库时按
  `docs/dev-rules/database-and-migrations.md` 只做新增。
- 测试要覆盖上表每一行：新组所在电脑配旧组内电脑、旧同账号电脑、旧受邀者，以及降级后的组所在电脑。

## 15. 订阅 Fast 限制

OpenAI / Claude 原生订阅组可在「自动换电脑」下关闭「允许使用 Fast」。关闭后，经此组分配的任务按普通模式运行，包含 Fast 与 Ultrafast；在组内其他电脑上单独使用其账号的任务不继承这一组的限制。账号本身另有独立开关，账号与组任一层禁止都有效。

组所在电脑自己执行的分享任务始终受本机组限制，包括调用方自报已经分配或经中转到来的任务。`groupAssigned` / `relay` 用于路由防环，不能作为跳过本机 Fast 限制的权限证明。执行电脑同时收到多个组约束时取交集。

执行电脑负责最终限制，分享接收方的旧目录或旧任务设置不能越过限制。目录下发隐藏有效的 Fast 能力，收到变更后自动刷新；通用自定义 API 模型发现和请求不受影响。

组所在电脑与执行电脑通过带修订的约束和确认同步；未确认时显示待确认，禁止设置下不分配到不支持约束的旧电脑，开启自动换电脑时尝试其他可用成员。离线成员重试，移出成员和删除组也须下发解除约束。已经发出的请求正常完成，不以切换开关为由中断它。

首次使用需更新应用，之后设置热生效；重新允许不会主动给当前任务开启 Fast。实现入口、兼容边界和验证记录见 [订阅 Fast 控制交接说明](../subscription-fast-policy.md)。

# IM 与 Cindy 共用工具权限确认

2026-10-03，用户要求：授权同时在 IM 和 Cindy 显示，任一处可以确认，来源群聊和
触发消息要保留；各种 IM 及未来新增机器人应复用同一实现。

## 行为

- 普通工具权限由 `maker-ipc/interactionRouter.ts` 创建一个 `SharedPermission`。
  桌面、同账号远控/手机与渠道共同回应它，第一份有效决定生效，后续回答不再覆盖。
- 直连富卡渠道使用 `im/shared/permissionPresentation.ts`，先登记请求再发卡。
  在 Cindy 确认时卡片尚未发送完成，发送完成后仍按同一最终决定更新、撤掉按钮。
  不因卡片发送或更新失败撤销已经作出的决定，不自动重发。
- 微信、企业微信、钉钉继续用各自的文字回复入口，接入同一个决定，收口后移除等待回复状态，
  并发送结果。不能编辑旧消息的渠道保留原提示，后续结果标明状态。
  收到回答的回执只表示已接收，不承诺继续执行；只有共享 `result` 确定后才显示允许、
  拒绝或失效，暂停期间取消不能先显示“继续处理”。
- 官方 Hook 的权限也进入共同路由；客户端通过既有 `interaction.cancel` 发送包含来源和
  结果的收口正文，不新增 wire 字段。服务端最终排版继续受各平台原有渲染器约束。
  服务端配套保留权限卡定位直到最终决定，并共用 `InteractionDelivery` 处理发卡未完成、
  临时选择提示与最终结果交错；迟到点击不覆盖最终正文。完整同步需两仓改动均上线，
  可先发布服务端；旧客户端没有最终回传时仍保留原正文或已选择提示并撤按钮。
- 机器人接管一个正在等待授权的 Cindy 任务时，权限面板保留，并增加 IM 呈现。
  所有共享授权（包括新请求和接管请求）在暂停时只暂存首份回答，恢复后才发布最终结果。
  恢复前取消则各端统一显示取消结果，不提前把 IM 卡片标成允许。
  普通提问和计划审阅不在本次多处确认范围内。

## 运行中切换权限

2026-10-23，用户要求 IM 群任务与普通任务共用即时权限切换，覆盖所有支持的权限档位。
无论放宽还是收紧，均使用普通任务同一套运行时切换、持久化和失败恢复流程，不等待
群轮次、后台续跑或渠道收尾结束，不增加群任务专属的切换分支。
默认权限、自动审核、完全访问之间任意切换均适用；进入完全访问的确认也沿用普通任务规则。
当前轮次后续工具审批与续跑跟随新档位；收紧时是否中断原生执行同样由对应 Agent 的通用实现决定。
群策略保留来源信息，不能覆盖主人当前选择的完全访问。新消息仍走渠道原有准入策略。
这也适用于已经受理的成员发起轮次：主人运行中主动切档即授权该任务的当前执行，
不因发起人身份再延后或另走切换流程；不会因此把成员标记为主人，也不改变下一条成员消息的准入。

`Session.acquireTurnLease` 只维持任务逻辑占用，保护新输入排队与收尾顺序，不阻塞
`Session.setPermissionMode`。临时权限恢复不得覆盖主人的新选择。
实现与回归见 `packages/maker-core/src/session.ts`、`maker.test.ts` 及三个 Agent 的
权限审批测试；桌面、手机、同账号远控共用同一宿主入口与原有身份校验。

## 来源与边界

`IMMessageEvent.interactionSource` 是可选的传输层元数据，提供群/聊天名、话题名、
发起人和平台原消息链接。共享层取本轮实际触发消息，截取短摘要，绝不取聊天里“最新”一条。
没有名称时显示平台聊天标识，没有链接时保留文本，不为展示额外请求模型或查询历史。
Telegram 提供群名、发起人、消息链接；事件里没有话题名时展示话题 ID。
其他平台按已取得的元数据提供名称，不能把未知 ID 冒充显示名。

来源放在确认正文，并随原正文保留到允许、拒绝或作废后。桌面和手机的自动审批故障提示
单独读取 `metadata.imSourceDescription`，不覆盖来源。旧端忽略可选元数据仍可正常确认。

2026-10-24，用户反馈确认卡看不懂为什么要确认、确认的是什么。自动审批判定 `ask` 时，
审阅原因写在可选的 `metadata.autoReviewReason`，富卡、文字渠道与官方 Hook 统一显示
「自动审批需要你决定：…」（`im/shared/autoReviewUnavailablePrompt.ts`），与故障降级一样
只允许这一次、不提供「总是允许」；故障降级的英文兜底句不再与中文说明重复。命令、文件、
插件调用与浏览器步骤按 `describePermissionAction`（maker-shared）直接显示操作本身，
认不出的工具才给 JSON。桌面与手机确认卡共用同一归类与原因字段。
受保护消息不复制正文摘要。渠道自身的 owner 检查、桌面本机专属确认和既有权限策略不变；
渠道破坏性操作检查在展示桌面镜像前执行。

## 新渠道接入

1. 通过共享 turn runner/interaction router 注册渠道交互，不另建执行决定。
2. 富卡复用 `presentSharedPermissionCard`；文字渠道接收 `options.sharedPermission`，
   把解析后的决定交给 `decide`，用 `result` 清理自己的等待回复状态并显示最终结果。
3. 可选填入 `interactionSource`。仅提供本条消息真实可用的信息，保留平台身份校验。
4. 覆盖两处同时回答、发卡未完成时已确认、取消后迟到点击、发送失败及两条任务不串来源。

Hook `sharedPermission.test.ts`，以及各文字渠道交互测试。

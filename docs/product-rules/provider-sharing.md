# 供应商分享：把远程供应商分享给其他 Cindy 用户

> 产品裁决：2026-10-07（用户确认）。本文是功能设计与产品规则；客户端与服务端已实现（2026-10-08），跨区域分享由服务端开关控制、默认关闭。
> 实现与本文的差异以实施计划 §0「实施记录」为准。
> 交互设计稿见 [`docs/design-previews/provider-sharing/index.html`](../design-previews/provider-sharing/index.html)（2026-10-07 已确认）；
> 客户端与服务端的工作拆分见 [`docs/provider-sharing-implementation-plan.md`](../provider-sharing-implementation-plan.md)。

> 删除对他的分享后，他与他分享的人都不再能用到它，见 §4.3、§9 第 8 条。

## 1. 定位

远程供应商已经支持同账号使用：任务、项目文件和命令留在发起任务的电脑，Agent 在另一台电脑上
用那台电脑的 Agent 程序、登录、供应商与网络运行（协议见
`docs/dev-rules/protocol-compatibility.md`「远程 Agent」）。

供应商分享把这项能力开放给**其他 Cindy 账号**：分享者把自己电脑上的某个供应商分享给指定的人，
对方在自己的任务里选用它。

- **借出的是 Agent 运行能力与模型额度，不是电脑。** 受邀者的文件读写与命令仍在受邀者自己的
  电脑上执行，由受邀者自己的任务权限把关；分享者不审批受邀者的工具调用。
- **分享者实时掌控。** 分享者能看到分享给了谁、每个人按模型的用量，并能随时关闭或删除。

与共享任务的区别：

| | 共享任务 | 供应商分享 |
|---|---|---|
| 对方进入的是 | 房主的某个任务 | 对方自己的任务 |
| 文件与命令在 | 房主电脑 | 受邀者电脑 |
| 借出的是 | 任务上下文与 Agent | 供应商（模型额度与 Agent 运行能力） |
| 加入方式 | 邀请即授权，可转发 | 一次性链接 + 双方确认 |

两者是独立的授权关系：共享任务的访客仍然不能使用远程 Agent 通道（现状不变）；供应商分享的
受邀者也不因此获得任何任务、文件或其他设备互联能力。

## 2. 术语

- **分享者**：提供供应商的一方，即供应商所在电脑的账号。
- **受邀者**：拿到分享链接、申请并被同意后使用供应商的一方。
- **分享链接**：分享者为某个供应商生成的一次性链接。
- **分享申请**：受邀者点开链接并确认后发给分享者的请求。
- **分享**：分享者同意申请后建立的关系，粒度为「一个供应商 × 一个受邀者账号」。

文案中用「分享」，不用「共享」，避免与共享任务混淆；「供应商」按 `i18n/GLOSSARY.md` 使用。
实现时在 `i18n/glossary.json` 为「供应商分享」相关新词登记 `proposed` 条目。

## 3. 前提与范围

- **所有供应商都能分享**：API Key、订阅登录、本机 CLI 账号、组织发放的供应商一视同仁。
  凡是能被远程调用的供应商，分享者自己的其他电脑能用，也都能分享给他人。
- **分享人数不限**，链接也可以无限生成。分享者电脑上同时运行的受邀者任务沿用远程 Agent 的
  数量保护，这不是人数限制。提供方可在任一供应商的「远程与分享」页设置整台电脑共用的额度：
  每台使用设备默认 16 个，所有设备合计默认 64 个；两项均为 1～1000 的整数，单设备不得高于合计。
  同账号其他电脑与分享设备都计入，同一设备跨供应商、分享入口合并计数；本机直接运行的任务不计入。
  已回答完但尚未关闭释放的任务、协同成员与中转任务仍占名额，关闭清理完成后才释放。
  修改立即生效，降低上限不终止已有任务；恢复默认清除本账号在这台电脑的覆盖设置。
  供应商组中转每一跳按直接连接的设备计数，不按中转声明的受邀者额外分配额度；转分享同意规则不变。
  页面显示合计占用、使用设备数及单设备最大占用；只有本机主人及其同账号电脑可以查看、修改。
- **只能在电脑上申请和使用**：手机打开分享链接时，只提示到电脑上的 Cindy 打开，不提供申请。
- **能力逐级开启**：
  1. 电脑打开「允许远程控制」，才能提供远程供应商；
  2. 供应商打开「允许被远程调用」，才成为远程供应商；
  3. 成为远程供应商后，才能分享给他人。
- 前两级任一未开启时，「允许被远程调用」一行仍然显示，但开关不可点击，并提示先开启
  上一级（不再像现在这样整行隐藏）。这一行的「远程与分享」入口仍可进入（供应商组不依赖远程调用，§7.1），
  分享一块在管理页里置灰并说明先开启哪一级。
- 关闭任一级时，该供应商的全部分享**暂时不可用**，但不删除；重新开启后恢复。受邀者看到
  「暂时不可用」而不是「已被删除」。

## 4. 建立分享：一次性链接与双方确认

### 4.1 流程

1. **分享者生成链接**：在管理页点「生成分享链接」。链接只能用一次，**生成后 5 分钟内有效**，
   过期后随时再生成，不限次数；不需要也不提供「未使用链接」的管理与撤回。口令为 256 位随机值，
   只放在链接 `#` 之后，不进入网页请求；服务端只保存口令摘要，口令不进日志。
2. **受邀者打开链接**：网页唤起电脑上已安装的 Cindy（复用共享任务邀请页的唤起方式）。未登录时
   先登录，登录后继续。在手机上打开时，网页与手机端都只提示「请在电脑上打开这个链接」。
3. **受邀者确认并申请**：Cindy 弹窗展示：
   - 分享者是谁（见 §6 身份展示）；
   - 分享的是什么：供应商名称（不写分享者的电脑名，见 §6）；
   - 运行方式：Agent 在分享者的电脑或分享者安排的其他电脑上运行（分享者可能建了[供应商组](provider-groups.md)；
     不论有没有组都这样写，之后建组不需要再提醒），受邀者的文件和命令仍在自己电脑上执行；
   - 隐私：对话内容和 Agent 读到的文件内容会经过分享者的电脑，并保存在实际运行任务的那台电脑上；
   - 身份：受邀者的昵称和头像会展示给分享者，以及需要同意他使用的其他电脑主人(分享者把别人分享来的电脑放进了
     供应商组，§4.3)，不展示邮箱、手机号等其他信息。
   
   受邀者点「发送申请」后才真正提交；取消不提交，链接在 5 分钟有效期内保持未使用。
   提交后受邀者看到本次申请的**配对码**（见 §6.1），等待分享者同意。
4. **分享者审批**：分享者在供应商所在的电脑上收到弹窗（应用在后台时同时发系统通知），展示申请人
   的昵称和头像（见 §6）、申请的供应商与同一个配对码，选择「同意分享」或「拒绝」。
   分享的是 Claude 订阅登录时，弹窗另写一句：受邀者使用时，Agent 能看到分享者登录 Claude 用的邮箱
   （Claude Code 自己会把它交给模型，Cindy 目前挡不住；2026-10-10 裁决先告知分享者）。
   这个供应商建了组时，同意说明写「由供应商组选一台电脑运行 Agent」，不说在这台电脑上运行（[供应商组](provider-groups.md) §8）。
   - **弹窗跟着生成链接的电脑**（2026-10-14 用户裁决）：同账号另一台电脑可以从「远程与分享」为供应商组生成链接
     （[供应商组](provider-groups.md) §10 同账号管理）。这时审批弹窗与系统通知出现在**生成链接的那台电脑**上，
     供应商所在电脑与其他电脑都不弹，只在管理页「待处理」和入口提示点里显示；同意、拒绝转交供应商所在电脑执行。
     理由：链接只能用一次、5 分钟内有效，申请基本在生成后几分钟内到达，那时人就在生成链接的电脑前、能当面核对配对码；
     不在每台电脑上都弹，也不弹在可能无人值守的建组电脑上。
   - 判定窗口为生成链接后 7 分钟（5 分钟有效期加拉取余量），两台电脑用同一时长，**按具体链接区分**：
     窗口内供应商所在电脑只对这条链接的申请静默，生成链接的电脑只弹这条链接的申请。后来在本机或第三台电脑
     生成的链接各自归属，不清除或接管其它链接的窗口；窗口过后才发现的申请照旧由供应商所在电脑弹。
     窗口按当前账号保存，完整应用重启后恢复。错过弹窗（生成链接的电脑已关闭等）时，在任意一台电脑的
     「远程与分享」页都能处理。精确关联需要服务端和两台电脑支持链接标识；旧服务端仍可本机生成，跨电脑生成提示更新。
5. **建立**：同意后分享立即生效，受邀者收到通知，模型列表里出现该供应商。

### 4.2 链接与申请的状态

| 状态 | 说明 | 下一步 |
|---|---|---|
| 未使用 | 已生成，尚无人申请 | 5 分钟内无人申请即过期 |
| 待审批 | 第一个提交的申请锁定了链接 | 他人再打开同一链接，提示「链接已被使用」 |
| 已同意 | 分享建立 | 链接失效 |
| 已拒绝 | 分享者拒绝 | 链接作废，要分享需重新生成 |
| 已撤回 | 受邀者撤回申请 | 链接作废 |
| 已过期 | 链接 5 分钟内无人申请，或申请提交后 24 小时内未处理 | 链接作废 |

- **一个链接只能用一次**：只有第一个提交的申请有效；同意、拒绝、撤回、过期都会让链接作废，
  不会放回去再用。
- 5 分钟只限制「打开链接到发送申请」；申请发出后等待分享者处理，24 小时内有效。
- 分享者不在线时，申请由服务端暂存，分享者那台电脑上线后再弹出（链接由同账号另一台电脑生成时按 §4.1 第 4 步）；
  受邀者看到「已发送申请，等待对方同意」，可以撤回。
- 分享者打开自己的链接：提示「这是你自己的供应商，你的其他电脑可以直接使用」，不进入申请流程。
- 同一受邀者已拥有该供应商的分享时再次申请：提示已在使用，不重复建立。

### 4.3 转分享：分享来的供应商再给别人用（2026-10-15 用户裁决）

受邀者 B 可以把 A 分享来的供应商加进自己的[供应商组](provider-groups.md)；这只扩大 B 自己的用法(A 已同意 B 使用)，
不需要再问 A。但 B 把这个组又分享给别人(C)时，C 的任务会经组跑到 A 的电脑上，等于把 A 的供应商转给了 C，**必须由 A
逐人同意**：

- **按人同意**(用户裁决：每个新受邀者都要 A 单独同意，不是同意一次就对 B 的所有受邀者有效)。按 C 的账号计，C 从哪台
  电脑来都是同一个人。A 没同意的人，任务不会分到 A 的电脑；B 分享出去照常进行，C 用组里其他电脑。
- **不用 B 手动发起**：B 的组所在电脑在组里有分享来的电脑、而组所在的供应商又分享给了别人时，自动把分享的人报给那台
  电脑；B 新分享给一个人、或把分享来的电脑加进已分享的组时随之报上。B 不能替 A 同意。
- **A 处理**：A 的「远程与分享」页「待处理」一栏出现「{C} 想经 {B} 的供应商组使用」，可同意或拒绝；处理过的人列在
  「已分享的人」里 B 那一行下方，已同意的可以撤回，拒绝的可以改为同意。新请求在应用不在前台时发系统通知，设置页入口
  亮提示点；不另弹审批弹窗(不是新的分享申请)。A 看到的 C 的昵称与头像由 B 的电脑转述，A 无法另行核实(§6 已知局限同理)；
  同意后 C 的用量算在 B 名下(A 那边看到的仍是 B 在用)。
- **生效与撤回**：同意后下一次分配起生效；撤回或拒绝立即结束 C 经组跑在 A 电脑上的任务，之后不再分给 A 的电脑。
  B 删除 C、或把 A 的电脑移出组时，A 那边的这条请求随之消失；A 删除对 B 的分享(或 B 退出)时，B 名下的全部同意一并作废，
  之后重新分享给 B 也要重新同意。
- **原分享删除即不再有**：A 删除对 B 的分享或 B 退出后，B 自己与 B 分享的人都用不到 A 的电脑——B 的组在确认分享已不在后
  自动把那台移出组(只在拿到完整可信的已收到分享名单时才判断，见[供应商组](provider-groups.md) §3)。A 只是暂停分享时保留，
  恢复后照旧(同意也保留)。
- **B 那边看到什么**：组内电脑那一行的状态写「分享的人可以用」「N 位分享的人等待 {A} 同意」或「{A} 未同意 N 位分享的人」；
  展开这一行逐人列出。A 的 Cindy 太旧给不出同意时写「{A} 的 Cindy 更新后才能同意给分享的人用」，这台不分给分享的人。
  C 在「分享给我的供应商」的匿名状态里看到这台「暂不可用」(或「需要更新」)，与实际分配一致。
- 协议见 `docs/dev-rules/protocol-compatibility.md`「供应商组：转分享需原主人逐人同意」；同意记录只存在 A 的电脑上
  (`provider-share-reshare.json`)，不经服务端。分享来的供应商本身仍不能生成分享链接，只能经组转给别人。
  转分享名单单次最多传 256 人；超过时由支持 `reshareBatch` 的新版电脑分片发送，每片回报当前片的状态，接收端收齐后才整体替换审批名单，
  批次数不按人数设置固定上限而受接收端字节预算保护。完成片段的重发保持幂等；旧版电脑显示需要更新并保持原有名单，不发送部分名单。

## 5. 受邀者使用

### 5.1 模型列表

模型列表整体结构不变：分享来的供应商与同账号的远程供应商放在同一个远程供应商区域，沿用现有的
左侧图标（带远程角标）与分组方式，只在分组标题多写一句来源：

- 同账号的远程供应商：`Anthropic · Magi's Mac Mini`（现状不变）
- 分享来的供应商：`Anthropic · 来自 Magi 的分享`，不写分享者的电脑名（§6，2026-10-10 用户裁决）。
  同一位分享者的同一个供应商分享了不止一份时，后面的按列表顺序加序号：`来自 Magi 的分享 (2)`。
- 分享者把这个供应商建成了[供应商组](provider-groups.md)时：标题后加台数，
  `Anthropic · 来自 Magi 的分享 · 供应商组 · 3 台电脑`。标题显示台数，匿名状态在详情查看（§5.2），不显示是哪几台。手机端本期不显示组信息
  （与[供应商组](provider-groups.md) §10 手机端口径一致），只沿用前两条的标题写法。

Desktop 与 Mobile 使用同一写法。

同账号的桌面远控中，已建任务、新建任务与 Worker 的模型菜单都应列出可用分享，不以任务已经选用
该分享为前提。Desktop 复用控制端的已收到列表与分享读取通道，并通过既有
`maker:provider-share:received-catalogs` 核对任务所在电脑也已加载且未暂停该分享；跨区域连接的启用
标记保存在各电脑本地，不能仅凭控制端名单认定被控端可用，也不自动替被控端开启跨区连接。
本区和跨区名单独立可用：返回名单里已加载且有效的分享立即参与候选筛选；仍有区域尚未就绪时，
控制端继续有上限地退避查询，补上稍后加载的分享，不让单一区域故障阻塞另一区域。
查询失败或旧主机不支持时不新增分享候选，当前 / 待切换位置仍保留。模型选择和执行仍由任务所在电脑校验；
手机沿用被控电脑代读目录。暂停或已移除的分享只为当前 / 待切换位置保留，供用户查看状态并换走。

Desktop 模型列表底部的「配置模型」在看分享来的供应商时同样显示，点开直接进入设置里这条分享的详情
（§5.2；2026-10-15 用户确认）。同账号其他电脑上的远程供应商与远程控制的电脑上的任务不显示，它们的设置
要到那台电脑上改。

Desktop 模型选择器「全部」「收藏」里，分享来的模型每行第二行沿用上面的来源写法（含供应商组台数），
分享的是内置 Cindy AI 时也一样，写 `Cindy AI · 来自 Magi 的分享`；只有受邀者自己电脑上的 Cindy AI 在这里
显示模型简介（#6110，口径见[模型目录运行时](../dev-rules/model-catalog-runtime.md)）。行内同样不写分享者的
电脑名（§6）。

### 5.2 供应商设置

IM bot 的渠道默认模型，以及官方 Slack / Telegram / X 的工作目录模型配置，沿用同一个
模型选择器展示已收到的分享。选择同时保存引擎、模型、供应商和 `share:<id>` 执行位置；

## 6. 身份展示

- **只展示昵称和头像**（2026-10-07 裁决）。邮箱、手机号一律不展示，脱敏后也不展示；组织、区域
  也不展示。服务端不收集、不保存这些信息。
- **不展示分享者的电脑名**（2026-10-10 用户裁决）。受邀者只知道是谁分享的、分享的是哪个供应商；分享者
  建了[供应商组](provider-groups.md)时可以知道台数并查看匿名状态（§5.2，2026-10-12），不知道是哪几台；台数与匿名状态按电脑，
  看不出一台上有几个账号（2026-10-15）。分享者的订阅账号
  （登录邮箱）在每一跳都去掉（§9）。具体做法：
  - 生成链接时分享者电脑不再上传电脑名，`deviceName` 填固定占位（字段必填，旧版受邀者按必填解析）；
    服务端仍存着旧链接里的电脑名，新版本的界面一律不显示它，转给手机时也换成占位；
  - 申请弹窗、模型列表、「分享给我的供应商」、换电脑的分隔条都不写电脑名；
  - 分享来的电脑加进供应商组后，组所在电脑的主人也只看到分享者的昵称（「Magi 的电脑」），
    组摘要里这类组员不带名字，换电脑的活动记录写分享者昵称。同一个人从同一台电脑分享的几个账号收在同一个
    「Magi 的电脑」下面（按分享里本来就有的设备 id 判断，不显示电脑名，2026-10-15）。
  - 已知差异：旧版本受邀者看到的是占位名（新链接）或原来的电脑名（旧链接），更新后才不显示。
- 展示的昵称和头像必须来自对方本人的账号、由服务端核实，不能来自客户端自报或消息内容。
- **身份名片**：没有任何「查看别人资料」的接口，也不新增。每一方只在自己操作时（分享者生成链接、
  受邀者发送申请）用**自己的登录凭证**向本区域账号服务换取一张短期签名的身份名片，内容只有昵称和
  头像（另含验签所需的账号标识、用途与绑定信息，不展示）。名片由账号服务签名，客户端无法伪造或修改；
  有效期很短，并绑定本次链接或申请，不能挪作他用。服务端验签后保存为快照，只展示给这次分享的另一方。
  同区域与跨区域使用同一种名片，跨区时由对方区域用本区域公钥验签。
- **已知局限**：昵称和头像任何人都能改。拿到链接的人若把昵称改成你同事的名字来申请，界面上无法
  分辨。由 5 分钟一次性链接（泄露窗口小）、分享者主动发出链接的场景，以及 §6.1 的配对码兜底。

### 6.1 配对码（2026-10-07 用户确认）

用来核对「发申请的人就是我发链接的那个人」，不暴露任何个人信息。

- 受邀者发送申请时，服务端为这次申请生成一个 4 位数字配对码，与申请绑定保存；不同申请的配对码相互独立。
- 配对码只出现在两处：受邀者发出申请后的「等待同意」界面，以及分享者的审批弹窗与管理页待处理一栏。
  系统通知、链接、加入网页、日志里都不出现。
- 分享者同意前可以通过发链接时用的聊天渠道问对方一句「你看到的配对码是多少」，一致再同意。核对是
  **可选**的，不强制；审批弹窗用一句话提示可以这样核对。
- 冒用者能看到的只是自己那次申请的配对码；真正的同事这时打开链接只会看到「链接已被使用」，说不出
  一致的号码，分享者据此拒绝即可。配对码不是密钥，不需要对申请人保密，也不参与任何鉴权。

## 7. 分享管理

### 7.1 入口

供应商设置详情中「允许被远程调用」一行，开关左侧是「远程与分享」入口按钮，点击进入该供应商的管理页
（[供应商组](provider-groups.md) §10 的「远程与分享」页）。2026-10-11 用户反馈详情因供应商组多出一行而太长：
原来的分享图标与「供应商组」一行合并成这一个按钮——有组时写「供应商组 · N 台电脑」，没有组时写「远程与分享」。
有待审批申请时按钮右上角带提示点，Tip 与无障碍名称写明有几个申请待处理。入口始终可点：供应商组不依赖
「允许被远程调用」；分享未开启时由管理页说明需先开启哪一级（§3）。

同账号另一台电脑上的供应商组，在设置页左栏组那一项的详情里有同一个入口，进入同一页管理那台电脑上的组与分享
（[供应商组](provider-groups.md) §10）。这个入口的提示点只数这台电脑生成的链接带来、由这台电脑弹窗的申请（§4.1 第 4 步）；
那台电脑上的全部待处理申请在页面「待处理」里。

### 7.2 管理页内容

管理页按供应商划分，标题为「{供应商} · 远程与分享」，从设置页进入、可返回：

- **生成分享链接**：主操作，放在页面标题一行的右侧（2026-10-16 用户反馈放在页面底部太难找）。页面不再单设「分享」块和
  分享说明：Agent 在哪运行、用量算谁的，由审批时的同意说明（§4.1 第 4 步）讲清；未开启分享时的原因提示紧跟标题（§3）。
- **待处理**：待审批的申请（同意／拒绝），以及转分享请求（§4.3，同意／拒绝）；紧跟标题、排在供应商组之前，为空时整块隐藏。
  链接 5 分钟即过期，不列出未使用的链接。
- **已分享的人**（2026-10-16 起不再单列，并进页面上方的「用量」块，与这个人的用量同一行，见[供应商组](provider-groups.md) §7；
  用户要求同一个人不在两处出现）：显示头像、昵称、加入时间、最近使用、当前状态（正常／已暂停）与是否有任务正在运行；关闭与删除在
  这一行行尾的 `···` 里；这个人经自己的供应商组转给别人用、已处理过的请求列在这一行下方（已同意的可撤回，拒绝的可改为同意，§4.3）。
- **用量**（2026-10-11 起移到页面上方的「用量」块；2026-10-17 起与设置 → 用量同一套，见[供应商组](provider-groups.md) §7）：
  标题同一行右侧筛选使用方、组内电脑、时间范围与日期，默认是所有人的合计；概览、按人(第一行是自己即当前登录账号，之后是分享的人，
  只显示昵称与头像，§6)、近 30 天每日 token、活跃热力图、按电脑(有组时)、按模型(含估算金额)。时间范围与设置页相同：
  所有时间／最近 30 天／最近 7 天／今天／选某一天。
- **操作**：
  - **关闭**：暂停对此人的分享，可随时恢复；
  - **删除**：永久移除，需要重新生成链接才能再次分享；删除前二次确认。

### 7.3 生效时机

- 关闭与删除**立即生效**：此人正在运行的任务当场停止，之后发送的消息被拒绝。迟到的响应、缓存或
  重连都不能恢复已撤销的访问。
- 恢复后从下一条消息开始可用。

### 7.4 用量统计

- 用量在分享者电脑上按受邀者与模型统计：Agent 在那里运行，数据最准，也不经过服务端。
- 订阅类供应商没有逐次扣费，按本地单价估算并明确标注「估算」，不代表供应商实际账单。
- 管理页按天明细经同账号远程管理回传时最多 5,000 行，按最新日期的行优先保留；最新一天可以只保留部分，
  超出 UTF-8 JSON 字节预算时继续从较早的行裁剪，`coverageStart` 标出保留下来的最早日期。报告行的日期按接收端时区的
  `lastAt` 重新计算，跨时区边界由前后两天的增量缓冲覆盖。
- **受邀者自己的运行数**（2026-10-10）：分享者电脑在给受邀者的供应商目录里带上这个受邀者账号（它的每台电脑）
  此刻在这个分享上正在运行一轮的任务数，供受邀者的[供应商组](provider-groups.md) §5 统计。只是受邀者自己的数，
  不含分享者本人和其他受邀者，不泄露分享者电脑上的其他使用情况；不是用量，§12「受邀者查看自己的用量」仍未做。

## 8. 跨区域分享

中国大陆版与 Global 之间**必须能互相分享**。两个区域的账号与设备互联服务是两套独立系统，因此：

- **分享属于分享者所在区域**：成员关系与授权保存在分享者区域的服务端。受邀者连接分享者区域的
  设备互联服务，同区域分享时就是自己平时连接的服务，两种情况走同一套逻辑。
- **只认两个官方区域**：两个版本都内置对方区域的官方地址；分享链接只能在这两个官方区域中选择，
  不能把客户端引导到任意地址。
- **跨区身份核实**：使用 §6 的身份名片。受邀者所在区域的账号服务签发，分享者区域的服务用对方
  区域公钥验签后，才把申请交给分享者；分享者看到的身份与同区域一样经过核实。
- **专用凭证**：分享建立后，分享者区域的服务为受邀者签发只限这个分享的凭证，只能用于远程 Agent，
  不能访问分享者区域的其他服务或能力。
- **合规开关**：跨区会让用户内容跨境流动，并让一方用户通过分享使用另一区域的模型。跨区分享须经
  公司合规确认后，由服务端开关开启；开关关闭时跨区链接提示暂不支持，同区域分享不受影响。
- **网络**：跨区连接质量不能保证时，需要服务端评估区域间转发；客户端对跨区连接的断线与重试沿用
  远程 Agent 的恢复规则。

这是对共享任务「两区域独立，不默认跨区域加入」的有意区分，仅适用于供应商分享；区域仍是构建期
维度，用户不在产品内选择自己属于哪个版本（`region-and-editions.md` §2.4）。

## 9. 安全不变量

1. **只开放远程 Agent**：来自受邀者的请求，分享者电脑只放行远程 Agent 运行、按该受邀者权限过滤后
   的供应商列表，以及 Agent 能力查询；其他设备互联能力一律拒绝，绝不降级为整台电脑的远程控制。
2. **凭证不出分享者电脑**：模型请求只由分享者电脑上的 Agent 用分享者的登录与供应商发出。
3. **权威划分**：服务端是成员关系的权威（谁是成员、是否已删除）；分享者电脑是使用范围与用量的
   权威，在开启运行、发送消息和换模型时逐次核对，是最终裁决方。
4. **受邀者请求不可信**：受邀者发来的启动参数按白名单校验，不能沿用同账号设备之间的信任；
   每次操作前重新核对成员有效性。
5. **分享者电脑上不留可利用的本机能力**：Agent 在分享者电脑上运行时，不加载分享者的个人配置、
   hooks、插件、扩展和本机 MCP（Claude Code 现状已满足，Codex 与 Pi 须补到同等水平），也不执行受邀者
   随项目带来的 hooks、扩展等可执行配置。受邀者同步来的所有 Markdown（说明、规则、命令、子代理、Skill
   与 `@` 导入的文件）里指向会话目录之外的 `@` 引用一律断开，不能借 Claude Code 读进分享者电脑上的文件；
   `@` 导入的文件只收 Markdown 与纯文本（2026-10-10）。
   **Agent 自带工具按白名单开放**（2026-10-10 裁决，取代 2026-10-07「联网工具不单独处理」）：Agent
   程序以分享者的系统用户在分享者电脑上运行，受邀者会话只开放不作用于分享者电脑、分享者电脑上的其他
   会话和分享者账号的自带工具；文件与命令仍回到受邀者电脑执行。Agent 升级新增的工具不会自动开放，
   须评估后加入白名单。因此给其他会话发消息、发布到分享者账号（如 Claude 的 Artifact、云端定时任务、
   设计项目）、在分享者电脑上读文件或跑命令都不可用；自带的 WebFetch 会从分享者的网络发出请求、能访问
   分享者的内网，对受邀者关闭，Claude Code 的 WebFetch 改由受邀者电脑提供、用受邀者的网络抓取（同日补充；
   受邀者电脑上的 Cindy 较旧时没有）：本机、内网与云 metadata 地址须受邀者在确认卡上批准，跳到其他网站
   时交回 Agent 重新调用；联网搜索由模型服务方执行，保持可用。同账号远程供应商不受影响。
   实现：Claude Code 用 SDK `tools` 白名单，Codex 按功能清单关闭白名单之外的功能，Pi 只放行 Cindy
   扩展注册的工具（`packages/maker-core/src/agents/{shared/device-hosted,codex/device-hosted-guest,pi/cindy-bridge-source}.ts`）；
   受邀者电脑上的 WebFetch 见 `apps/desktop/src/main/remote-agent/executor/webFetch.ts`。
6. **受邀者隐私**：申请前明确告知对话与文件内容会经过分享者的电脑，并保存在实际运行任务的那台电脑上
   （有供应商组时可能是分享者安排的其他电脑）。运行中疑似工具循环时，与分享者自己的任务一样，由运行任务
   那台电脑的辅助模型复核：最近十余次工具调用的脱敏摘要会发给那台电脑设置的辅助模型（可能不是分享的
   供应商，也不计入受邀者用量；2026-10-13 用户裁决）；分享被删除或受邀者退出后，分享者电脑清理该受邀者的 Agent
   会话记录与镜像文件，并请接过它任务的组内电脑清理（[供应商组](provider-groups.md) §4）。

   **凭证类再收紧一档**（2026-10-10 裁决）：对话与 Agent 读到的内容会经过分享者的电脑，因此
   - 凭证类文件（密钥、`.env`、云与工具的登录凭证，规则同本机任务；Claude Code / Codex 配置目录里的

     允许，默认只放行这一次。确认卡同时提供「本任务总是允许」（2026-10-12 用户确认）：受邀者明确选择后，

     启动同步仍排除凭证文件。确认卡说明内容会经过分享者或其安排的电脑，以及这项授权的范围与失效时机。
     确认卡与 Agent 的确认走同一通道，手机远控与 IM 也能处理；

     一致；门禁每次操作前重读，运行中的任务从下一步起生效，关掉即恢复确认。启动同步仍排除凭证类文件；退出分享
     或分享从已确认区域的权威名单里消失时偏好一起清掉。它放宽的只是这一个分享；「本任务总是允许」仍只限当前任务，
     其他分享与本机任务的判定不变；
   - 命令只能按命令文本识别（脚本里读的、编码后再解开的认不出来），是防误发，不是防恶意；
   - 减少误弹（2026-10-12 用户裁决）。**以下几条只用于这张分享任务的确认卡**，本机任务、同账号远程供应商与
     自动审查的判定都不变：
     - 普通编辑脚本不因超过模型审阅的 4096 字符预算就算凭证读取。凭证检查在独立的 256 KiB
       输入上限内扫描完整命令，前序命令副作用按段累积，不为每段重新扫描全部前序段；超过输入
       上限或解析深度上限时仍要求确认，长脚本尾部实际读取密钥时也仍要求确认；
     - `.env.example` / `.env.sample` / `.env.template` 与公钥 `*.pub` 按惯例不含密钥，不算凭证类文件
       （读取、启动时同步都照普通文件）；放在凭证目录里（如 `~/.ssh/id_rsa.pub`）时仍算。命令中读取
       文件时，执行前按该命令段的实际目录核对原始路径与链接的真实目标；模板、公钥与配置目录里的说明
       路径不能借链接指向凭证。目标不存在、链接断开、目录或展开认不出、前段可能改动链接或环境时，
       都保留确认，不用改写后的文件名或上次核实的链接目标放行；
     - 按扩展名缩小范围的搜索不算读取凭证：rg 的 `-g '*.ts'`、grep 的 `--include='*.md'` 这类只选中源码
       与文档文件的写法，字面上能选中 `.env.ts`、`id_rsa.ts`，但这类名字是代码模块。直接写出像凭证的
       文件名、`*.json` / `*.txt` / `*.sh` 这类可能存放凭证的格式、扩展名不确定的写法（`*.ts*`）仍要确认。
       搜索启用跟随符号链接（如 rg 的 `--follow` / `-L`、grep 的 `-R` / `--dereference-recursive`）时，
       源码扩展名不能证明链接目标非敏感，保留确认；短选项组合与可接受的长选项缩写同样处理；
       宿主设置了 `RIPGREP_CONFIG_PATH`、命令里对它赋值时，也不能只凭源码扩展名豁免。
       配置可能注入跟随链接或其它扩大读取范围的选项；只在 rg 后第一个参数明确为 `--no-config` 时
       才继续按其它既有规则核实，不把搜索词、选项取值或 `--` 后的同名文本当成禁用配置的标志；
       rg 命令出现预处理器 `--pre`（含分离、附着参数及可能的选项缩写）时，外部程序可以把本机凭证
       当成源码内容输出，源码扩展名不能证明结果非敏感，保留确认。无法完整解析的写法同样如此，
       不靠 `--no-config`、`--no-pre`、空值或限制预处理文件的 `--pre-glob` 抵销已出现的预处理器；
      - git 查看内容的命令（`git diff`、`git show`、`git log -p`、`git grep`）只看命令文本时按可能读到
       提交进仓库的凭证处理，执行前先在受邀者电脑上核实，读不到凭证类文件就不弹卡：仓库所有分支、标签、
       stash 与 reflog 的历史和暂存区里从没有凭证类文件；或命令用 `--` 限定的路径碰不到这些文件；或
       （`git diff` / `git show` / `git log`）按原命令只列出会显示的文件，其中没有凭证类文件。认不出 git
       在哪个仓库里跑、仓库带子模块、比较仓库外的文件、核实超过 8 秒，都照旧弹卡；仓库的扫描结果留在
       内存里给后面的命令用。
       核实预算由整条命令共用：shell 启动状态、目录、所有内容与配置命令段共享同一 8 秒期限，
       本次查询子进程只使用剩余时间；文件状态检查不返回、取消或超过总期限时失败关闭，先弹确认。
       已开始的历史后台扫描仍按既有缓存流程继续，不影响确认卡及时出现；
       指定的对象必须能解析为提交且已在扫描范围内，否则改按实际显示的文件
       核对；无法证明为提交的底层对象（如 `git show <blob-id>`，含 `-s` / `--name-only` 等输出选项及隐式
       `HEAD`）保留确认，不能按干净历史放行。所有
       历史与内容探针禁用 replacement refs；仓库有 `refs/replace` 或宿主设置了 `GIT_REPLACE_REF_BASE`
       时不授予内容豁免，避免探针与实际命令使用不同对象；
       仓库或生效配置中有 textconv / external diff 驱动、或继承了 `GIT_EXTERNAL_DIFF` 时不能只凭文件名
       豁免，除非能确定该调用已禁用相应驱动；历史与文件列表探针始终禁用这些外部 helper。
     - 打出 git 配置的命令（`git remote -v` / `get-url` / `show -n`、读 `git config`、`git var -l`）按受邀者
       电脑上生效的 git 配置核实：要打出的那些项里没有密钥（地址里嵌的令牌或密码、`http.extraHeader`、
       密码与令牌类配置项）就不弹卡，有才确认；显式切换配置文件、blob 或配置作用域（含附着参数、短选项
       组合与长选项缩写）不授予豁免，以免核实的是另一套配置；带取值的选项与单键隐式读取也要核实，
       不能把选项的取值计入写配置的参数数目而绕过确认。只有确定的单键读取才缩小核实范围，查询模式、
       缩写或键名认不准时按全部配置核实，不能把正则查询的模式当成单个键名放行；
       `git remote show` 没有在动作后明确用 `-n` 禁用远端查询时不授予豁免，避免 SSH / proxy 等传输
       helper（含配置、继承环境及系统 SSH 设置）把本机凭证打印到 stdout / stderr；只核对地址不能证明安全。
     - 上述 Git 核实仅用于命令段直接调用 PATH 中的裸 `git`，且沿用宿主环境、PATH 各项为绝对目录时。
       显式执行文件路径（如 `./git`）、`git.exe`、任何命令包装器（包括 `env`、`command`、`exec`），以及
       环境变量的赋值、移除或清空（含 PATH、加载器与 Git 配置来源）都无法与探针证明一致，照旧弹卡；
       宿主继承了 `BASH_ENV` / `ENV` / `ZDOTDIR` 或导出的 Bash 函数时，同样无法证明 shell 启动后仍调用
       探针使用的 Git，不授予内容与配置读取豁免；
       shell 可执行文件本身也要核实：Bash 仅接受固定系统路径的二进制，以及 Windows 标准 Program Files
       安装目录里的 Git Bash（核实实际路径没有重定向）。自定义 Bash、Windows 显式 `CLAUDE_CODE_GIT_BASH_PATH`、
       未知安装目录或其他 shell 无法与探针证明一致，保留内容、配置和静态只读调用的凭证确认；
       实际执行器选择 zsh 时，即使没有 `ZDOTDIR`，也要核实系统级 `zshenv` 与 `HOME/.zshenv`（含各自
       `.zwc` 缓存）均不存在；发现文件、核实文件状态失败或超时、HOME 不明确、或自定义 zsh 的启动目录
       无法核实，都保留确认。此核实每次执行前重做，不读取或运行启动脚本，不沿用仓库历史的缓存；
       Git 内容读取前还要按当次生效的配置核实 `filter.<driver>.clean` / `.process`。标准 Git LFS
       配置 `filter.lfs.clean=git-lfs clean -- %f` 与 `filter.lfs.process=git-lfs filter-process`
       按正常工具使用，不因安装 LFS 就要求普通 Git 查看命令确认；其它非空过滤命令仍保留确认，
       探针不运行这些自定义过滤器。即使指定 `--no-textconv` / `--no-ext-diff` 也要核实过滤配置，
       不沿用旧配置结论。此处沿用防误发的边界：信任正常安装的 Git / Git LFS，不校验二进制是否被
       故意替换；凭证文件、直接写在命令里的密钥与保存的登录凭证仍按原规则确认；
       配置中出现 `core.fsmonitor` 时同样保留确认（不假设不同 Git 版本对布尔取值的解释一致），
       在读取 index 前拦下它，避免 hook 经 stderr 带出凭证。`git status`、`git ls-files`、只列文件名的
       diff 等静态只读调用也要核实运行期 helper；无 helper 时仍可豁免，不改变本机任务默认判定；
       静态只读调用同样不能略过子模块检查：公共 Git 目录存在 `modules`、index 包含 gitlink，
       或核实目录状态失败时保留确认；即使旧式子模块把自己的 `.git` 留在工作目录里也不豁免，
       避免 `git status` 进入子模块后执行其独立配置的 helper 或 hook；
       配置中出现 `core.hooksPath` 时同样保留确认；未配置时，每次核实仓库公共 Git 目录里的默认
       `post-index-change` hook（含 Windows 可执行文件后缀）不存在。发现 hook 或无法核实文件状态
       都不授予内容与静态只读豁免，避免 `git status` 刷新 index 时执行 hook、经 stderr 带出凭证；
       签名验证也可能启动外部程序：配置了 `gpg.program` / `gpg.<format>.program`、启用了
       `log.showSignature`、命令请求 `--show-signature` 或 `%G` 验证格式、配置中的 pretty 格式或别名
       含 `%G` 时均保留确认，不假设验证器不会读取或输出凭证；历史与文件列表探针始终禁用签名展示；
       重合并历史（`--remerge-diff`、`--diff-merges=remerge` 或配置选择的 remerge 模式）可能运行
       自定义 `merge.<driver>.driver`，非空时先保留确认。内部历史／文件列表探针固定逐父提交比较，
       不继承重合并配置、不运行 merge driver；普通 Git 查看不因仅存在 merge driver 就额外确认；
       `git diff/log/show --check` 的空白错误诊断会输出出错的源码行，因此同样按内容读取核实涉及的
       文件；与统计等输出选项组合时也不直接豁免，限定到普通源码的检查仍可免确认；
       log/show/whatchanged/blame 中的姓名映射也核对来源：`.mailmap` 的真实目标、`mailmap.file` 或
       `mailmap.blob` 指向凭据路径时保留确认，无法确定路径的 blob 同样确认；普通映射仍可豁免，
       不因无关的姓名映射配置让 diff/status 增加确认；
       `git var -l` 与单个逻辑变量查询按实际输出检查，包含环境中的 editor／pager 及派生值，不能
       仅凭 Git 配置没有密钥就豁免；检查结果留在本机内存，不记录原始输出；
       `--bare` 这类改变仓库上下文的选项、前面的命令段可能修改 Git 状态、运行环境，或写法认不出时也不能豁免。
       已知会读取 Git 内容的调用遇到未识别的全局选项、或不能归为静态只读命令时（如 `--ext-diff` /
       `--textconv`）也保留凭证确认，不能因为未进入核实路径就当成不读取凭证；本机默认判定仍不变。
   - 再收紧（2026-10-12 用户裁决），同样只用于分享任务：命令里直接写着密钥（`https://用户:密码@`、
     地址里的令牌、`Authorization` 头的取值、常见服务的令牌格式与私钥）、用 `<提交>:<路径>` 写出凭证类文件
     （`git show HEAD:.aws/credentials`）、`git credential fill` 这类打出保存的登录凭证的命令都要确认。
   同账号远程供应商不受影响：与本机一致，项目与个人配置里的符号链接一律跟随，不额外确认。
   实现：`apps/desktop/src/main/remote-agent/{credentials.ts,executor/gate.ts,executor/executor.ts,executor/gitCredentials.ts,executor/credentialGrants.ts,controller/projectFiles.ts}`；
   按分享关掉确认的偏好在 `apps/desktop/src/main/device-link/providerShareGuestPrefs.ts`，开关在
   `apps/desktop/src/renderer/features/provider-share/ProviderShareReceivedRail.tsx`；
   命令判定复用 `packages/maker-core/src/agents/shared/auto-review.ts` 的 `shellCommandReadsCredentials`，
   上面的命令放宽与 git 核实通过它只有分享任务才传的选项（`CredentialCommandOptions`）实现，不传时判定不变。
8. **不能借组转分享**（2026-10-15）：受邀者的供应商组替它分享的人转来的任务，分享者电脑只在主人同意过那个人时运行

## 10. 与现有规则的关系

- `docs/dev-rules/protocol-compatibility.md`「远程 Agent」写明远程 Agent 通道「只进同账号
  allowlist，不进共享任务清单」。本功能为它新增「供应商分享」授权范围；共享任务访客仍被拒绝。
  实现时须同步修订该节。
- `docs/product-rules/shared-task-mode.md` 不变；本功能复用其服务端成员、链接唤起与撤权的模式，
  但使用独立的授权类型和数据，不塞进共享任务。
- 「允许被远程调用」的说明文字需改为同时覆盖自己的其他电脑与分享的人。

## 11. 验收

1. 未开启「允许远程控制」或「允许被远程调用」时，管理入口可见但不可点击，并提示先开启哪一级。
2. 链接只能用一次、5 分钟内有效：第二个人打开已被申请的链接时被拒绝；拒绝、撤回、过期后链接不能
   再用；手机打开链接只提示到电脑上打开。
3. 受邀者未点「发送申请」时不产生任何申请；分享者未点「同意分享」时受邀者不能使用。
4. 双方弹窗与管理页只显示对方的昵称和头像，取自对方本人账号、经服务端核实；任何位置都不出现
   邮箱、手机号（含脱敏形式）、组织或区域，服务端也不保存这些信息。
5. 受邀者「等待同意」界面与分享者审批弹窗、管理页待处理一栏显示同一个配对码；系统通知与日志里没有。
   受邀者模型列表结构不变，分享来的供应商标题带「来自 {分享者} 的分享」。
6. 关闭或删除后，受邀者正在运行的任务立即停止，下一条消息被拒并提示原因与换模型入口。
7. 管理页按人、按模型显示用量，订阅类标注估算。
8. 受邀者无法通过分享调用分享者电脑上的任何非远程 Agent 能力，随项目带来的 hooks、扩展不会在
   分享者电脑上执行；Agent 自带工具里作用于分享者电脑、其他会话或分享者账号的都不可用（§9 第 5 条）。
9. 中国大陆版与 Global 账号之间能完成同样的申请、审批、使用与撤销；合规开关关闭时跨区链接给出
   明确提示，同区域分享不受影响。
10. 受邀者任务启动时不带凭证类文件；任务中读写凭证类文件或执行读取凭证的命令，即使在完全访问下也
    要受邀者在本机确认后才执行（§9 第 7 条）。`rg -g '*.ts'` 这类只按源码扩展名缩小范围的搜索、读
    实际目标已核实为非凭证的 `.env.example` 与 `*.pub`、在没有凭证类文件的仓库里（或只涉及普通文件时）跑 `git diff` / `git log -p`、
    配置里没有密钥时跑 `git remote -v` 都不弹确认卡；命令里直接写着密钥、`git credential fill` 要确认；
    本机任务与同账号远程供应商的确认不受影响。受邀者对这个分享打开了「信任 {分享者}」时，这些确认都不再弹，
    启动同步仍不带凭证类文件；关掉后下一步起恢复确认，其他分享不受影响。
11. Light 与 Dark 两种模式都已实现。
12. 受邀者 B 把分享来的供应商加进组、又把组分享给 C 后：分享者 A 没同意 C 时，C 的任务不会分到 A 的电脑(B 的电脑直接转过去
    也被 A 拒绝)；A 同意后下一次分配起可用，撤回后 C 正在 A 电脑上的任务立即停止；A 同意 C 不代表同意 B 分享的其他人。A 删除对
    B 的分享后，A 的电脑从 B 的组里移出，B 与 C 都用不到；A 只是暂停时保留。A 的 Cindy 较旧时 C 的任务不分给 A 的电脑(§4.3)。

## 12. 后续可选

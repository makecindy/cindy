# 远程执行的权限确认

> **读取时机**：修改远程 Agent 执行器的权限上限、执行器在本机补弹的确认卡、Agent 所在电脑对远程
> 执行工具的权限判断，或两台电脑之间的权限分工之前
> **适用路径**：`apps/desktop/src/main/remote-agent/executor/{gate,executor}.ts`、`apps/desktop/src/main/remote-agent/controller/{startRemote,proxyHandle,execServerRelay}.ts`
> **要点**：上限拦下、用户又没批准过的操作必须在执行电脑上弹确认卡，不得没有卡就拒绝；一个操作
> 只判断一次，不在两台电脑上各审一次。

产品裁决：2026-11-21（用户确认）。第一步（本机补弹确认卡）已实现；第二步（把判断整体挪到
执行电脑）是设计，尚未实现。分享供应商的凭证确认另见[供应商分享](provider-sharing.md) §9 第 7 条。

## 术语

- **执行电脑**：任务、文件和命令所在的电脑，也是用户看确认卡的地方。
- **Agent 电脑**：运行模型和 Agent 的电脑（同账号的其他电脑、别人分享的供应商、供应商组里的电脑）。

## 为什么要定这条规则

2026-11-20 的事故：任务用同账号 Mac mini 上的供应商，权限档是「自动」。Agent 在执行电脑上跑
`grep -rn …`、`git grep …`。这类递归搜索在本机规则里属于"每次都要确认"，但「自动」档下会先交给
AI 审查。Agent 电脑的审查放行了，没有发确认卡。执行电脑的执行器却假定这类操作一定问过用户，
只认用户点过的「允许」，于是直接拒绝，回给 Agent 一句"需要在运行任务的电脑上确认"。
Agent 转告用户去点确认，可哪里都没有卡。

根因是两台电脑各自做了一次判断，而且结论不一致。

## 现行规则（第一步）

1. 执行电脑的执行器对每个文件、命令和网页抓取操作守权限上限，保证 Agent 电脑无论如何越不过
   执行电脑上的用户。这一点不变：执行器不相信对方说的"已经审过了"，同账号的电脑也可能被攻破。
2. **上限拦下、用户又没批准过的操作，必须在执行电脑上弹确认卡，不得没有卡就拒绝。**
   - 卡和 Agent 发来的确认卡走同一条通道：桌面、手机远控、IM 都能处理；共享任务按普通工具权限对待。
   - 普通确认卡与本机任务里同名工具（Bash、Read、Write、WebFetch 等）的确认卡一样，只允许这一次，
     不带会话级规则。补弹卡上的文件批准只适用于显示的访问方式，读取、目录遍历和写入分别核对。
   - Bash 确认卡显示命令和实际工作目录，批准后的命令仍从卡上显示的目录执行。
   - 分享供应商任务里的凭证类操作仍用分享凭证卡（可选「本任务总是允许」）；一张卡同时满足凭证
     确认和普通上限。git 命令在本机核实读不到凭证后只免掉凭证确认，普通上限仍要批准时照样弹普通卡。
3. 用户拒绝、卡超时或当前没有能回答的界面时才拒绝。回给 Agent 的说明写明"用户没有允许，现在
   没有等待中的确认"，避免 Agent 叫用户去找一张不存在的卡。
4. 同一任务里并行的确认排队，界面一次只显示一张；前一张卡改变了授权后，排队的请求重新检查。
5. 已知代价：在「自动」档下，Agent 电脑的审查已放行、而本机上限必问的少数操作（递归 `grep`、
   `git grep`、工作区外的写入、敏感路径等）会比本机任务多问一次，直到第二步完成。每次都有卡
   可点，不会再出现没有卡的拒绝。定时任务这类无人值守的运行里，补弹的卡和 Agent 发来的确认卡
   一样等待回答或超时（不再立刻拒绝），用户可在通知或手机上处理。

实现：`executor/executor.ts` 的 `confirm`，以及 `controller/startRemote.ts` 为每个远程任务接上
确认通道（`approvalConfirmation` / `credentialConfirmation`）；Codex 经 exec-server 中继走同一入口。

## 第二步：判断挪到执行电脑（设计，未实现）

### 原则

- 一个操作只判断一次。两台电脑各跑一次 AI 审查不可取：两次判断可能不一致，慢一倍、费一倍，
  而且现在的审查用的是 Agent 电脑自己的辅助模型——分享供应商时等于由分享者的额度和模型替
  受邀者决定其电脑上的操作。
- 判断由执行电脑做：风险在这里，确认卡也出现在这里。Agent 电脑只负责跑模型，不替用户决定
  执行电脑上的操作。

### 方案

1. 远程执行工具（Claude Code 的 `cindy_exec`、Pi 的执行器后端、Codex 的 exec-server）在 Agent
   电脑上不再做"问不问"的判断，直接把操作转给执行电脑。
2. 执行电脑按本机任务的同一套规则判断：权限档、本任务已允许的规则、固定红线、「自动」档的 AI
   审查、确认卡。问用户只在执行电脑上发生。
3. 「自动」档的 AI 审查用执行电脑自己的辅助模型。执行电脑没有可用的辅助模型时，按现有降级方式
   提示"自动审查暂不可用"并弹卡确认，不悄悄拒绝。**分享供应商任务不借用分享供应商的模型审查**
   （2026-11-21 用户裁决），否则分享者的电脑会参与决定受邀者电脑上的操作。
4. Agent 电脑只保留与执行电脑无关的限制：计划模式只读、它自己那边的工具与 MCP。
5. 会话级"总是允许"规则随之记在执行电脑上，不再依赖 Agent 电脑转发的规则。

### 兼容

- 这一步改变两台电脑之间的分工，必须按[协议兼容](../dev-rules/protocol-compatibility.md)做能力
  协商：两边都声明支持后才切换；任一边是旧版时保持第一步的行为（要么弹卡、要么放行），
  绝不出现没有卡的拒绝。
- 自建中转只透传，不需要改动；实现时仍按协议兼容文档的「自建中转同步维护」核对。
- 不改变分享供应商的授权边界：受邀者的权限仍只由受邀者自己的任务权限档把关，分享者不审批
  受邀者的工具调用。

### 不做

- 不在两台电脑上各审一次。
- 执行器不信任 Agent 电脑发来的"已审查放行"标记来跳过本机上限。

# Cindy 核心产品原则

> 权威产品原则。用于产品、交互与能力边界的取舍。

## 服务大众，追求极致

产品从用户要完成的事出发，承担连接与使用中的复杂度。功能的价值以实际成果衡量，不以问答、
能力展示或功能数量衡量。

设计美学、交互的便利与简洁、每一个用户能感知的细节，都值得下足功夫；一处让人多想一步、
多等一秒、多点一下的地方，就是还没做完的工作。为了用户面前的简单，我们愿意在背后做无数
的事：自动发现与修复、预判与兜底、反复推敲每个状态和每句文案。研发投入的价值，以为使用者
省下的时间、精力和 token 衡量；复杂的实现本身不是成果。

提出或实现新功能前，先回答：

1. 它帮助用户完成什么真实工作？
2. 它是否增加了普通用户的配置或理解门槛？
3. 它解决的是通用连接问题，还是个人／组织的具体流程？
4. 它应该由 Core、Skill 还是插件负责？为什么？
5. 如果需要富交互，是否应作为插件小程序实现？
6. 它如何在桌面、手机和远程场景中保持任务连续？
7. 用户能否清楚理解状态、影响范围和结果，并在需要时停止或修正？

答不清楚时，先完成产品设计，不直接进入实现。

## 由产品承担复杂度，把控制留给人

默认体验体现产品判断，定制按需展开。用户不必理解内部机制，也能看懂进展、表达意图，并
随时修正、停止或接手。交互用最适合这件工作的表达方式，让人的判断与 Agent 的执行衔接。

连接、授权和运行环境尽量自动发现、引导和修复，高级配置不是普通任务的前置条件。界面用
工作语言，写清对象、范围、生效条件与结果；错误建议须有依据，不默认追加“请重试”。两端、
全部五种语言同样适用，见[微文案规范](../design-rules/DESIGN.md#11-voice--content微文案规范)。

临时故障恢复后界面自动恢复，不要求用户手动重试或点「重新检查」；复用恢复信号和悬停、
聚焦、打开等时机，不为罕见边界加轮询或后台重试链。无意义的重试（空剪贴板、格式不支持）
静默或短暂提示，复制新内容、聚焦或连接恢复后自动继续。后台状态提示要轻：正常时尽量
不提示，单台设备离线不是全局失败；持续提示不占列表纵向布局，不让列表跳动。

高风险动作有与风险匹配的告知、授权、停止和恢复。代输入的
秘密值只交给宿主执行，不进模型、记录、日志、IM 与推送。约定见[设计规范](../design-rules/DESIGN.md)、
[配置契约](../dev-rules/configuration-and-overrides.md)、[代输入](input-handoff.md)与
[权限确认](im-permission-confirmation.md)。

## 多端连接与任务连续性

四个长期能力方向：UI 与交互、Agent 与模型连接、多端连接、插件系统，共同服务真实工作。

Cindy 连接人、Agent、工具、设备和成果。底层智能持续演进，连接层保全其能力、上下文、
事件、性能与结果质量，吸收供应商差异，只让影响用户决策的差异进入 UI。Cindy 不重新实现
成熟的 Agent Loop，也不把用户锁在单一供应商或 Agent 实现里。

更换 Agent、设备或入口不迫使用户重新组织工作：各端界面可以不同，任务、状态与权限语义
一致；断线重连沿用已有上下文；多端状态冲突与操作归属有确定规则。桌面、手机、远程、IM
与自动任务都遵循这一点。IM 入站上下文与 App 完成提醒见[IM 消息呈现](im-message-presentation.md)，
目标运行中的补充消息、停止与手机 `/goal` 见[目标模式](goal-mode.md)。

Cindy 是 Agent 的上游 GUI，价值是连接、呈现和降低操作成本，不把上游已允许的能力做成更保守、
更难恢复的宿主流程，也不因“更安全”降级原生体验。Cindy 自己的分析只提供可跳过的诊断，不确定、
超时或遇到新格式时退回上游原生行为，且不把 Cindy 的失败伪装成上游不兼容。对 Pi 包的安装、
更新、启用等操作，用户发出的完整、确定性命令或精确点击，就是该操作的授权，不再叠加确认；
这条零附加确认只适用于 Pi 包，其他能力仍按各自规则确认，例如插件更新扩大权限时。授权只在同一
已验证身份、任务和安装内成立：共享访客、非主人的 IM 参与者和被替换的插件实例不继承。Pi 的具体
红线见[Pi 上游 GUI 非退化](../dev-rules/pi-harness.md)，身份边界见[伙伴授权](teammate-authority.md)
与[插件安全](../dev-rules/plugin-security-and-authoring.md)。

用户能操作的自己的资源，Agent 也有可发现的工具，含跨电脑操作，且在索引第一步即可发现。
执行边界由权限档与自动审核承担，共享访客和群成员沿用各自身份。约定见[能力同权](agent-user-parity.md)、
[多端适配](../dev-rules/remote-and-mobile-adaptation.md)
与[消息来源](message-source.md)。

自动任务与目标任务共享一条生命线：归档只是收起任务，不暂停自动任务；自动任务失败也不
取消用户手动继续的入口。恢复语义、确认与续跑判据见[归档与自动化](archive-pauses-automations.md)。

## 清楚的分工，让能力持续生长

Core 承担所有用户共同依赖、必须由宿主掌握的基础能力：UI 与交互基础设施、Agent / 模型
连接与任务生命周期、扩展运行时、权限、安全与故障隔离、多端状态与数据归属，以及 SkillHub
与插件市场的安装、更新和分发。

Agent 提供智能。Skill 用自然语言、脚本或工具编排沉淀工作方法，可在个人与组织间复用、
流动，通常无需专属界面。插件是运行在 Cindy 中的沙箱小程序，承载完整的垂直能力、结构化
状态与富交互：Agent 提供数据与状态，插件让用户查看、编辑或判断，再把结构化意图交回
Agent；Skill 可以组织这套流程。Agent 与插件以结构化数据和事件协作，不以解析任意模型文本
为主要协议；插件不得绕过 Cindy 的权限与安全边界取得宿主能力。

个人、团队、行业或组织的具体流程、数据接入与界面留在 Skill 和插件，官方开发同样如此：
流程进 Skill，外部能力、数据接入与富交互进插件。个人、组织和公共是发布范围，不是 Core
功能层：Core 管理组织身份、可见范围、安装授权、签名、策略、更新与撤销，不编码组织怎样
工作。进入 Core 的能力必须是稳定、可复用的基础原语，不能是固定的垂直业务入口；能由
Skill 或插件安全、完整承担的能力先在那里验证，边界不明确时也先从扩展验证。

伙伴同样适用这条分工（2026-11-05 方向，细节讨论中）：伙伴是一个带对外身份的项目，怎么说话、
怎么派活和管任务、什么时候汇报、怎么安排定时任务，属于伙伴自己的规则，能由伙伴自己修改，
不写死在工具说明、回执或宿主代码里。宿主只保证规则保证不了的事：来源与授权、权限、防循环
上限、任务状态的可见性和运行位置，这些对所有任务通用。只有现有工具做不到或效率很低才改工具，
并优先补成普通任务和项目也能用的通用能力。现状盘点、冲突条款与开发引导见
[伙伴专属能力台账](teammate-capability-ledger.md)。

## 原则与现状

本文是长期承诺，不表示当前版本已全部实现。差距和阶段性例外明确记录，按用户影响与风险
收敛；改变产品边界需要明确的产品决策，再同步实现与文档。

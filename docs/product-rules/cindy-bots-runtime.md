## 1. 用户心智：伙伴拥有一条长期主任务

伙伴是长期存在的数字同事。用户面对的是同一个名字、性格、记忆、能力和连续的主时间线，
不应因为日期变化被换到一条空白任务。

运行时分成三层：

- **伙伴 Profile（永久）**：身份、长期记忆、自有 Skill、模型候选链、稳定的伙伴目录（V2 的记忆与技能在伙伴项目里，见 §4）。
- **主任务与完整记录（长期）**：canonical Session 是这个伙伴稳定的用户时间线；消息单独
  持久化，可以持续回看和搜索。
- **模型工作上下文（可压缩 / 重建）**：Harness 只读取当前能放进上下文窗口的摘要与近期内容；
  压缩或更换原生运行句柄不得更换主任务，也不得删改完整记录。

用户说“继续找小满”时，永远找到同一个伙伴和同一条主时间线；模型不需要每次吞下全部历史，
但必须通过压缩摘要、长期记忆和有界历史检索保持语义连续。

伙伴的名字以当前 Profile 为准，人格、职责与用户关系以当前 SOUL 和用户档案为准；历史
回复中的自称错误不能反向变成人设。上下文压缩、运行时重建和更换模型不改变这个身份。
Pi、Claude Code、Codex 是执行引擎，它们的原生工具说明不定义伙伴人格，也不代表用户
正在使用对应 CLI。面向用户的配置指引应落到 Cindy 的实际入口；不能把 `/login`、
`/model` 等原生终端命令推荐为伙伴聊天中的操作。用户明确询问独立 CLI 用法时可正常说明。

### 按话题找回跨渠道聊天

主人询问过去的话题时，不要求先点名渠道，也不默认限制当前工作目录或任务创建日期。
`get_teammate_state` 在主人可读范围返回本机连接分配、状态和历史检索说明；连接分配不是
历史归属证据，也不代表实时在线。访客自查不增加主人连接信息。
按 `search_chat_history(query, teammate_id)` 搜索已保存的 `bot_session_links`，包含主任务、
历史、话题及渠道专线；按 `list_sessions(teammate_id, time_field=activity)` 查最近活跃的旧任务，
不因任务已归档而漏掉。命中后用 `get_chat_history` 阅读原文，并区分任务 `source` 与关联的渠道。

未关联的旧 IM 记录不自动认领：在已有账号历史权限内，可去掉伙伴筛选按具体话题有限检索，
结果 `companion=null` 明确表示没有可证明的伙伴归属。不能按目录、名字、当前连接，或将某渠道
全部聊天归给一位伙伴。`device=all` 沿既有同账号在线设备授权查询，失败设备、旧版本和召回上限
仍明确列出；只查本机不能声称覆盖全部设备。不增加后台扫库、全量上下文注入或私有记忆补丁。

## 2. 所有权与挂靠关系

```text
Bot Profile
├── Home                          账号隔离的唯一持久边界：身份、记录与 V1 存档
│   ├── SOUL.md                   身份
│   └── workspace/                伙伴的项目（V2，Git 仓库）：项目规则、技能、自动化与记忆
├── canonical Session             长期主任务与用户时间线
└── history Sessions              仅用于旧版本数据与异常恢复后的记录
```

伙伴属于账号而不是某台电脑：同一伙伴只在它的主力电脑上运行，其他电脑与手机通过云端对话层查看并可接管，
规则见 [云端伙伴](cloud-companions.md)。

每条伙伴 Session 必须能反查唯一的 Bot owner 与 Profile 版本。伙伴开的任务是普通
Cindy Session，只记「由这位伙伴开的」（6.1），不冒充该伙伴或另一个伙伴的主任务。
伙伴在群聊里使用独立的群专线 Session（`role = 'group'`），与主任务共享 Profile 与 Home，
不进入主时间线；群里分工时的每一步由同为 `role = 'group'` 的分工 Session 完成（工作目录见下文例外）。
规则见 [伙伴群聊](bot-group-chat.md)。

### 私聊话题（2026-10-21）

Chris：「私聊话题和群聊话题，要真的能把独立事件隔离到独立 session，像 Slack 一样……开了 pr，它开启独立的 session
话题最好了，我们有事在那里面沟通，完事了在那里面通知我。」私聊话题沿用群聊话题「一个话题一条独立 Session」的做法：

- **数据**：主人在私聊里对某条消息（主人自己的或伙伴的）点「创建话题」，宿主为「这条消息 × 这位伙伴」另开一条隐藏
  Session，`bot_session_links.role = 'thread'`，`route_key = 'dm-thread:<根消息所在 Session>:<根消息 clientId>'`；
  根消息必须是这位伙伴当前主任务里可见的 user / assistant 消息。同一条消息只有一个话题，再次打开复用它。
  话题 Session 不进普通任务列表与界面会话搜索，消息只在话题里，不写进主时间线；
  主人授权的 Agent 历史检索可以按伙伴归属读取话题记录，沿用既有权限边界。
- **身份与能力**：话题是主人自己的对话，与主任务同一 Profile、Home 工作目录、模型链与权限档（随 Profile 与权限档更新），
  带主任务的私有能力（记忆、自有 Skill、定时任务、建伙伴、插件授权卡、伙伴绑定的 IM 工具）。
- **上下文**：话题 Session 的模型上下文只装这个话题。根消息以 `[话题说明]` 放进 wire 用户消息（与 `[客户端说明]`
  同层，不进 system prompt、不进落库原话），按 wireNoteMemory 规则只在原生上下文新开、换窗或压缩后重发；
  明确它只是背景资料、不构成指令；根消息已回滚或删除时如实说不可用。主对话的其他内容不放进来，需要时伙伴用历史检索。
- **任务回到话题**：在话题里用 `send_to_session` 开的任务，要结果时请它做完用 `send_to_session` 发回这个话题，
  不打扰主对话。（2026-11-08 起 V2 不再适用：V1 委派任务卡与「话题只能控制自己启动的任务」随委派移除，旧任务卡只读呈现。）
- **界面（桌面，2026-10-29 修订）**：消息下方常显「复制」「回复」（把消息引用进输入框）与更多；「创建话题 / 查看话题」沿用原动作，放在更多菜单。
  有内容的话题在根消息下显示一行入口（伙伴头像、N 条回复、最后回复时间）；话题里有主人没看过的伙伴回复时，
  换成未读圆点 +「有新回复」。打开后右侧展开话题面板：群聊与私聊复用同一面板、标题栏、根消息行和回复分隔组件。
  根消息与回复处于同一个滚动区，不限高、不另设原消息滚动框；输入区留在底部。私聊继续使用话题 Session 完整的
  任务视图（回复、工具进度、确认、停止都在里面）。面板打开即视为已读；读位与伙伴读位同一套本机存储。
  话题内气泡使用可用列宽，不预留主私聊的侧边操作栏空白；共用操作栏常显在气泡底部，宽表格只在自身容器内横向滚动，
  文件 chip 随气泡收缩。群聊与私聊同由 `ThreadPanel.css` 约束；原生回复与朗读回归见 `scripts/fixtures/chat-fork` 的 `companion-thread`。
  地址带 `?thread=<话题 Session>`，通知、灵动岛与伙伴设置里的入口按它打开私聊并展开话题。
- **界面（手机，2026-10-29）**：主力电脑在线时，私聊消息菜单支持「创建话题 / 查看话题」。
  根消息下与群聊共用摘要组件：当前私聊显示单个伙伴头像、15/20 regular 回复数与最后回复时间，
  视觉间距收紧但保留 44pt 点击区域。打开后进入该话题完整任务页，原消息与回复连续滚动，输入、停止、
  工具结果和确认均由原任务运行时处理；不会把话题回复发送到主聊天，也不会把主聊天标为已读。
  手机先读取伙伴资料的可选 `dmThreadsSupported`，老电脑未提供时保留原私聊；话题路由由宿主返回的
  `threadRoot` 与 Session 绑定核验，换账号、断连重连或伙伴被隐藏后必须重新核验才能发送。
  远程只新增同账号已授权的 `local-db:bots:dm-thread:list / ensure`，沿用原消息归属与权限继承。
  **二期范围（2026-10-29）**：私聊入口与操作交互统一到群聊；当前仍由消息下方的更多菜单创建／打开话题，
  正文保留长按选字，尚未复用群聊的长按消息菜单与回复者头像数据。
- **暂不覆盖**：另一台电脑经远程打开的私聊界面、主力电脑离线时的云端对话层仍不展示话题（话题消息不导入
  1:1 房间）；私聊表情回应另做。实现见 `localDb/ipc/bots.ts`（`ensureBotDmThreadSession` /
  `listBotDmThreads`）、`maker-ipc/botDmThreadContext.ts` 与 renderer `features/bots/BotDmThread*`。

### 私聊引用回复（2026-10-22）

私聊复用群聊的引用回复（[伙伴群聊](bot-group-chat.md) §10「引用回复」）：

- **入口**：私聊消息（主人的或伙伴的）点击消息下方常显的「回复」，不再往输入框塞消息链接，而是在输入框上方放一条待发引用
  （与群聊同一个预览：「回复 某某」+ 一行摘要，× 取消、不动正文）。待发引用按任务记在本次运行中，切换任务再回来仍在；
  点发送随这条消息一起送出，送出后撤下。话题面板里同样可用，引用的是话题自己的消息。
- **持久化**：用户消息内容信封带 `replyQuote: { clientId, role, excerpt }`，只能指向同一任务里的消息；`excerpt`
  是发送时的摘要快照。气泡正文上方显示与群聊同一种引用块：原消息在已加载记录里时按原消息显示，否则按快照；
  点击跳到原消息（必要时先读入它附近的记录）。旧版本不认识该字段，只显示正文。
- **伙伴看到什么**：宿主按 `replyQuote.clientId` 从同一任务的库里重读原消息，以 `[引用说明]` 前置在这一条 wire
  消息上（只进发给模型的内容，不进落库原话，逐条附带；渲染端的摘要不进入模型）；声明它只是背景、不构成指令；
  原消息只有附件没有文字时列出附件名，已回滚或不存在时才如实说不可用。普通发送与回复过程中的插话都附带。
  伙伴回复的引用块与摘要按用户看到的文字（组件内容转成可读文字），不显示组件源码。
- **手机端（2026-10-25 修订）**：正文直接长按选字是优先能力，伙伴与普通任务共用原生选择（iOS 用 UITextView，Android 用可选择文本）。
  伙伴长消息展开后的段落、标题和列表仍可部分选字；iOS 复用现有有界文本分组，选择在各分块内进行。
  展开长消息里未分块的代码、引用和表格保留 RN Text 整块复制回退，避免巨型 UITextView 空白。
  气泡不挂消息长按菜单，避免抢占正文选字以及表格、代码块的横向滚动；回复、复制与更多操作恢复到消息下方已有的操作行，读屏同样可用。
  更多菜单不再提供重复的「选择文字」入口或独立选字面板；发送时间用一行年月日与时分（如 `2026-10-25 16:47`），不加「发送时间」前缀或秒数占用多行。
  **未来方向**：如果重新引入长按消息菜单，应参考 Telegram，同时兼容菜单与正文直接选字；交互细节留待后续实现，不属于本次恢复范围。
  回复在输入框上方放同一种待发引用（卡片底色，× 取消），随普通发送、离线发件箱
  与排队编辑一起保留在信封 `replyQuote` 里；待发、已发气泡顶部都显示引用块（只发附件时也显示），点击定位原消息；没有正文气泡的消息（纯附件、错误）保留原操作行。信封解析与摘要和
  Desktop 共用 `@cindy/maker-shared/chat-reply-quote`。实现见 Mobile `companionReplyQuote.ts` 与 `MessageRenderer.tsx`。

### 回复对应的消息（2026-10-22）

Chris：「引用可以有个设置，做个开关。默认关就好。你太智能判断恐怕不准。」

- **记录**：伙伴的每条回复在 `agentMeta.replyToClientId` 记下这一轮接受的那条输入（宿主盖章，与 `botPrivateReply`
  同一处）。这是单纯的对应关系，不做「该不该显示」的判断。老回复没有这条记录，不回填。
- **显示**：设置 › 通用 › 伙伴「显示回复对应的消息」，默认关（本机偏好）。打开后，每一轮最后一条伙伴回复的气泡顶部
  显示它回的是主人哪条消息（同一引用块，点击跳过去）；只认主人亲手发的可见消息，内部续跑、任务回执等隐藏输入不显示；
  对应的消息不在已加载记录里时不显示。
- **手机端**：伙伴资料页「对话」分组的同名开关，默认关，本机偏好、对所有伙伴生效，与 Desktop 各自独立；显示规则同上。
  实现见 Mobile `companionReplyTargetPreference.ts`。
- **暂不覆盖**：IM 渠道。

伙伴自己带 IM 机器人（2026-10-15 Chris 裁决）：用户在平台自己申请机器人（Telegram bot、飞书 / Lark bot、
企业微信智能机器人、钉钉机器人、Discord bot；2026-10-17 补齐后三种），凭证直接填在伙伴设置「消息平台」页，
这个机器人就是这位伙伴；一位伙伴可以同时挂多个平台。它与
设置 → IM 机器人 里那份独立的个人 bot 是两份连接，不共享归属，也不用 Cindy 云上分配机器人。例外是一次性移交
（2026-10-17 Chris 允许）：添加平台时可选「使用已在 Cindy 设置的机器人」（该渠道个人 bot 已配好时默认选它），
凭证只在 main 里搬（`im/shared/botImPersonalAdoption.ts`）：先静默停掉个人 bot（不给主人发「已断开」、不删命令菜单），
再走同一个 `addBotImConnection`；成功后个人 bot 清空（设置页按既有广播显示未配置），失败则把个人 bot 的凭证原样写回并
重新起来。随连接带过去的：Telegram / Discord 的主人 id、企业微信 / 钉钉 / 飞书已认定的主人（不再重新 TOFU）、

## 3. 长期会话生命周期

### 3.1 稳定主任务

- 一个伙伴默认始终复用同一条 canonical Session，不按日期、空闲时长或打开次数更换。
- 每次消息和其他伙伴、任务经 `send_to_session` 发来的消息都先解析同一条权威 canonical link；不得在这些入口各自
  维护一套“是否换任务”的判断。
- Profile 更新只推进主任务下一轮使用的身份与能力版本，不创建新任务。
- 只有 canonical Session 确实丢失或已删除时，恢复流程才可以用 CAS 建立替代任务；健康的
  主任务不能被普通创建入口覆盖。
- 旧版本遗留的 history Session 继续可回看、搜索，不做破坏性迁移。

### 3.2 上下文沿用 Session 原生压缩（2026-10-23）

伙伴的主任务、私聊话题、IM 群／外部私聊专线和伙伴群聊专线，均长期复用各自的同一条 Session。
健康上下文交给 Session / Harness 已有压缩机制，不因伙伴身份另外添加上下文维护自动化：

- 不按空闲时长（包括隔夜 12 小时）、打开次数或 70% / 90% 占用提前重建原生会话。
- 不根据工作记忆新鲜度替代原生压缩，不主动扫描健康 Codex 历史来提前换窗。
- 正常原生压缩结束不登记或重启伙伴运行实例；只有明确资料 / 能力 / 模型配置变化等独立原因才刷新实例。
- 不在后台唤醒、自动续跑或人工输入时执行伙伴专属整理，因此不产生日常整理提示卡。V2 的记忆整理是伙伴项目里
  的普通自动化 `teammate-memory-review`（每晚一次，可暂停）；V1 的宿主「夜间学习」已移除（2026-11-08）。
- 不在回复后调用辅助模型复盘学习、维护短期工作记忆账本，压缩后也不重新注入旧账本（这两项的 V1 实现已删除）。
- 用户明确建立的自动化、伙伴开的任务与其结果回传、手动记忆 / Skill 工具、既有长期记忆及文件不受影响。

发送前 `contextOverflowRollover.prepareUnhealthySession` 只保留故障恢复边界：普通 Session 共用的
真实满窗保护、上下文溢出、明确压缩失败、Pi 无响应或已确认的损坏历史。Codex 的 token 压力
继续交给原生压缩；普通网络、鉴权、额度错误不据此换窗。恢复保留同一产品任务和完整聊天记录。
历史故障交接仍保存近期需求、回复、改动和有界工具结果，省略图片正文；仅故障恢复使用交接，
不能把这个兜底路径重新当成伙伴的日常压缩。

Codex 图片历史在运行中确定失败时，伙伴主对话与普通桌面任务共用一次隐藏续接：
保留原请求与已记录进展，不重放原请求或已完成工具；结果不明先核实。每条输入最多自动
续接一次，停止、新输入接管和排队输入仍能取消恢复。群分工、IM 和自动化输入的
续接仍由原分发者负责，不能被主对话恢复抢占。普通上下文溢出仍只在本轮没有 assistant /
tool 副作用时自动重放。原生后台工作尚未结束时不自动关闭句柄。

自动恢复无法完成时保留错误与既有继续／重试入口；「重启伙伴」无需旧模型参与，保留
同一条时间线、记忆与文件，并携带工具结果重新建立上下文。重启不自动重放请求。

旧版 `working-memory.json` 不再生成、刷新或注入；V2 升级把它连同 `todos.v1.json`、`nightly-learning.json`、
`learning-history/` 移进伙伴目录的 `v1-archive/`（不删除），未完成事项写进项目的 `CARRYOVER.md`。

完整聊天记录与模型工作上下文必须分离：压缩可以丢弃模型不再需要的旧 tool result 和中间过程，
但用户时间线、搜索索引和审计记录仍按既有持久化策略保留。完整消息继续写入 SQLite，界面与
历史工具按稳定游标分页读取；不能因为聊了一个月、消息变多或发生压缩就自动另开一条产品任务。
容量治理按数据库体积与可观测数据处理，不按固定消息条数截断伙伴历史。

### 3.3 用户界面

## 4. Bot Home 权威边界

每个伙伴拥有账号隔离的 `<ownerRoot>/bots/<botId>/`。它是该伙伴唯一的持久内容边界，
不属于当前 Session、当前项目或 Cindy 的全局 Maker Memory：

```text
<ownerRoot>/bots/<botId>/
├── SOUL.md                     身份，由用户与宿主维护
├── system_prompt.md            可选的用户提示词覆盖
├── workbench.json              关联项目（V2 仍读写，名字沿用）
├── v2-migration.json           V1→V2 升级回执（全部步骤成功才写）
├── v1-archive/                 V1 专有状态（待办、工作记忆、夜间学习、例行任务定义与说明），只保留不使用
├── memories/、skills/          V1 记忆与技能，升级后保留作存档与搬迁后备
└── workspace/                  伙伴的项目（Git 仓库，侧栏「Teammate <名字>」）
    ├── AGENTS.md               项目规则（CLAUDE.md 为 `@AGENTS.md`）；升级时带 CARRYOVER.md 指引
    ├── CARRYOVER.md            升级时未完成的 V1 待办、工作台事项与工作账本
    ├── .agents/skills/         伙伴的技能（按项目技能原生加载）
    ├── .cindy/memory/          伙伴的记忆（见下文「V2 伙伴的记忆在伙伴项目里」）
    └── .cindy/automations/schedules.json  伙伴的自动化（含每晚 teammate-memory-review）
```

升级（`maker-ipc/botV2Migration.ts`，调度器就绪后每个伙伴一次）：开启项目模式、V1 例行任务转为项目自动化
（触发条件或插件检查搬不过去的保留为暂停的自动化并记说明）、未完成事项写进 `CARRYOVER.md`、V1 专有文件移入
`v1-archive/`；只在每一步都成功后写回执，另一台主力电脑上的副本留给那台电脑升级。伙伴项目里的自动化是 Cindy
自己写的，直接同步到调度器，不弹导入确认（§3「伙伴的项目在界面上」）。

升级不得因读不到、解析不了或体积大而默认「没有内容」（2026-11-10 QA 审查后修订）：读不到的目录或文件让本次升级失败、
下次启动重试，不写回执；内容不是合法 JSON 的旧状态文件原样移入 `v1-archive/`，并在 `CARRYOVER.md`「升级时没能自动带过来的」
里写明。例行任务删除前，它们的运行记录（结果、触发事件、排队中的运行）与计时一起存进 `v1-archive/routine-runs.json`，
未跑完的运行在 `CARRYOVER.md` 里列出。技能按文件合并：项目已有同名技能时补上缺的文件，内容不同的旧文件以
`<名字>-from-v1` 放在旁边；技能文件夹内部的链接按目标复制（每个文件夹只走一次，链接成环也会结束），指向技能文件夹外的链接不跟随（可能指向电脑上任意文件）并写明；不穿过项目里已有的链接写入，类型不同（文件与文件夹）时旧的放旁边。
`CARRYOVER.md` 已存在时只追加还没有的条目，条目全文保留不截断。间隔触发的例行任务保留为同样间隔的自动化；没有触发条件的草稿
保留为暂停的手动自动化。事件触发、插件检查与发到聊天的结果仍无法等价搬运：只要丢了其中任何一样，这个自动化就以暂停状态建立并写明。

- Bot Memory 可以复用 Cindy 的存储原语，但物理数据、开关、索引、清空入口和提示词作用域都
  只属于该 Bot；关闭或清空全局 Maker Memory 不得关闭、列出或删除 Bot Memory。
- 启动 Bot 时不得注入其它项目的 Memory、全局 Memory 摘要或其它 Bot 的记忆；V2 伙伴读写的就是它自己项目的记忆。
- 伙伴沿用普通任务的权限档，原生文件与 Shell 工具按用户选择的权限执行；`workspace/`
  是默认工作目录，不是操作系统级隔离边界。记忆与 Skill 默认经类型化接口维护，以保持
  索引、版本与运行期快照一致；不得把这种维护约定描述成对原始文件工具的强制隔离。
- `workspace/` 是伙伴跨 Session 复用的唯一默认工作区。伙伴不直接绑定代码项目、不占用
  worktree——需要隔离工作区或独立持续执行的工作通过 `send_to_session` 新建一条普通 Cindy 任务完成
  （见第 6.1 节）。唯一例外是伙伴群聊的分工 Session：它在该安排记录的群工作目录里干活，
  git 项目时共用该安排的 worktree；工作目录每次启动都按安排记录核对，失败不回退 Home，
  规则见 [`bot-group-chat.md`](bot-group-chat.md) 第 7 节。
- 上下文压缩、模型 fallback、失败补偿和删除临时任务不得移动或删除 Home 内容。
- 远端运行必须使用远端实际存在且归属于该 Bot 的 Home；在远端 Home 尚未完成供给前，不得把
  本机路径写进提示词或伪装成可访问目录。远端自有 Skill 未装配时，共享指南不引导本机 Skill
  读写和学习，工具入口在存储及刷新之前明确返回不可用，不能承诺下一轮或新任务生效；
  这不影响远端已支持的共同基座、记忆、协作及能力发现。手机控制本机运行时仍使用本机自有 Skill。

### V2 伙伴的记忆在伙伴项目里（2026-11-09）

V2 伙伴（伙伴 = 一个项目，见 6.1）的记忆就是它项目的记忆，物理位置在项目里的
`workspace/.cindy/memory/`，随项目 Git 记版本；旧的 `memories/` 保留为 V1 存档。负责人裁决：**只有伙伴
项目这样做**，普通项目的记忆仍在项目外的 `<ownerRoot>/maker-memory/<范围>/`，不写进用户自己的仓库。

- **唯一解析点**：桌面记忆存储的 `resolveStorageDir`（`maker-host/maker-memory-host.ts` →
  `maker-ipc/botProjectMemory.ts` 的 `teammateProjectMemoryStorageDir`）按记忆范围认出本账号的伙伴项目
  （`@cindy/maker-shared/teammate-project` 的路径规则）。主任务、IM 与群专线、夜间 `teammate-memory-review`
  自动化、在该项目里的普通任务、`cindy_memory`、启动注入的 `MEMORY.md` 索引、记忆检索（`fts.db`）、
  伙伴记忆页（本机与远程设置 `memory.*`）、设备互联远程 Agent 都经这一处，读写同一个文件夹。
- 伙伴项目的记忆范围按伙伴自己的记忆开关，不随 Cindy 全局记忆开关关闭，也不被全局「清空记忆」删除。
- **进 Git 的**：记录 `*.md` 与存储的复制回执 `.cindy-memory-migration-v1.json`；**不进 Git 的**（项目
  `.gitignore`）：重建的 `MEMORY.md`、`meta.json`、`fts.db` 及其日志、临时文件。新项目的默认忽略清单含这几行，
  已有项目在一次性搬迁时补上。
- **一次性搬迁**：已在本机升级（有 `v2-migration.json`）的伙伴，启动时把项目外旧位置的记录复制进项目
  （项目里已有的不覆盖），旧目录原样保留作后备，写回执 `bots/<伙伴>/project-memory-move.json` 只跑一次，
  然后记一个项目版本（Git 快照）。刚升级的伙伴在准备项目时先做这一步，再复制 V1 记忆。
  搬迁完成前，云端上传与接管比较把旧位置当作后备一并读取，没搬的记忆不会看起来被删除。
- 该文件夹可被任务的文件工具改动：宿主写记忆用新建临时文件再改名，不顺着链接写；链接不当作记忆读；
  `.cindy` 或 `.cindy/memory` 本身是链接时拒绝打开。

### 关联项目（2026-10-22）

每个伙伴（包括 Cindy）在设置中独立关联多个项目。项目列表可添加、查看和移除；关联沿用 Home 中

## 5. 模型候选链

伙伴 Profile 可配置 **1–5 个有序候选**，每项是一个完整运行路由：

```text
harness + provider + model + effort + fastMode
```

- 第一项是首选；首次主任务启动和确定性重建从第一项开始尝试。
- 只有连接、鉴权、配额、容量、模型不可用和启动失败等“候选不可用”错误才进入下一项。
  路由所在的另一台电脑结束或失联（`remote_agent_closed` / `remote_agent_lost`）也属于候选不可用；
  这类错误继续由伙伴候选链处理；供应商组对主人输入的额度／容量故障按下述范围接管，
  不在候选恢复入口仅凭同步的组候选信号再次拦截。候选恢复拒绝这两类掉线错误时，组恢复也不接管，保留错误与手动重试。来源主人主动断开
  （`user-revoked`）和原电脑重连（`remote_agent_restarted`）不进入下一项。远程 Agent 丢失后本机
  Session 随即自行关闭，已排期的续跑跨过这次关闭，换到下一项后只发“继续”，不重放原文
  （对方电脑上的工具可能已经执行过）；普通任务遇到同样错误仍直接交还错误。
- 候选不可用与原路由自动续跑分开判定；Pi 原生重连耗尽（`pi-gateway-drop`）仍可切到伙伴候选链。
  已落库失败回合只有在切换成功后才自动发送：有持久产出时只续跑，确认零产出才重发原文。
  候选耗尽、切换失败或需要换窗确认时交还错误，不继续重试失效路由；复用现有恢复额度和退避，
  不覆盖用户的新选择。没有其它可用路由（单项候选链、自动化显式模型）时不存在“候选耗尽”：
  过载、空响应等普通任务会原路由续跑的错误照常原路由续跑，其余错误交还用户。
  实现与回归见 `maker-ipc/botCandidateRecovery.ts`、
  `maker-ipc/__tests__/botCandidateRecovery.test.ts` 和 `sessionRuntimeFallbackIntent.test.ts`。
  跨 harness 路由已提交但新引擎启动失败时停止自动恢复并显示错误；不使用提交前的路由代次继续推进候选。
- 定时自动化的恢复只属于当前运行轮次；候选耗尽或自动恢复放弃后，该轮按失败收口并保留错误记录，
  同时释放临时重试状态，后续已排队或到期的轮次沿用原调度继续执行，不自动重放失败轮次。
  用户消息的手动重试、显式暂停、交互等待和仍在运行的执行边界不受影响。实现与回归见
  `maker-ipc/agent-input-coordinator.ts` 的 `abandonAutoResume` 和同目录 `__tests__/agent-input-coordinator.test.ts`。
- 用户拒绝授权、工具业务失败、参数错误和已经产生副作用后的失败不得触发透明重放。
- 同一轮最多按生效候选链各尝试一次；不得循环。用户显式配置的链不得追加目录候选。
- 确定性账号额度耗尽仍不遍历候选链；同一供应商组内其他电脑的额度独立判断。主聊天与话题中由输入协调器持有的主人输入
  可沿供应商组现有机制故障换机，保留当前伙伴与任务；换机后不因普通模型对齐切回原组入口，显式模型保存仍生效。
  范围、取消与分享凭证约束见[供应商组 §6.1](provider-groups.md#伙伴主聊天与话题的故障换机)，不新增伙伴的额度定时续跑。
- 同 harness 可在安全边界切模型；跨 harness 必须走既有 agent-switch / 交接重建事务。
- 伙伴设置中的显式模型保存立即同步当前主任务的运行选择；空闲时在既有安全边界完成切换，运行中先记录最新选择，在回复、工具与审批结束后的安全边界接替，不要求用户再发一条消息才能登记。连续改选以最后一次为准，选回当前路由应取消不同的待切换路由。
- 自动化指定的临时模型在本轮发送中不被伙伴默认模型对齐覆盖，包括跟随全局默认的伙伴。主人随后保存新的伙伴模型选择时，在发送锁内以同一数据库事务清除活跃主任务及群／IM 专线的旧恢复偏好，并同步标记模型对齐失效；新自动化记录恢复选择前在同一发送锁内对齐已保存模型，避免异步运行态刷新尚未执行时重新写回旧选择。恢复记录写入还须原子校验读取路由时的伙伴 Profile 版本，覆盖保存期间新建、尚未进入发送锁快照的专线；版本变化时重新准备，不能写回旧选择。设置已保存但运行态刷新前退出也不会复活旧选择；即使新选择恰好等于临时运行模型，下一次聊天也不得恢复到旧选择。普通内部投递先拒绝已降级的伙伴副本，再在发送边界恢复原选择，并在所有异步准备结束、真正派发给 Agent 前同步重查降级状态；能力设置预览使用下一轮普通聊天的选择，不因预览消费恢复记录。
- 模型配置只保留统一选择器入口，备用链仍在原组件内折叠；思考深度、Fast 与 Harness 不拆成独立设置页。缩窗交接复用已经核实目标窗口的延迟选择处理，完整记录与主任务身份保留，不绕过原生副作用重放限制。
- fallback 只改变当前任务的有效路由，不暗改 Profile 顺序。下一次确定性重建仍从首选开始。
- 存量单模型配置归一成一项候选链，不能在升级时改变用户已有选择。

伙伴默认模型与新任务选择独立（2026-10-21 用户裁决）。保留「设置 → 通用 → 伙伴 → 默认模型」
入口；新任务输入框的引擎、来源、模型、思考档位、Fast 与远程电脑选择都不得改变伙伴默认。
未自定义伙伴默认时，复用产品推荐顺序，从已连接且可用的目录选出第一条推荐路由，
思考档位取模型推荐值，Fast 默认关闭；只返回一条，不自动追加备用链。
目录或引擎尚未就绪、没有可用推荐时返回空链，沿用连接与选模引导。
「恢复默认」只删除全局伙伴 override，重新解析推荐值，不重新跟随新任务草稿。
已有显式全局设置、单个伙伴的显式模型及历史单模型兼容配置保持不变；
新用户与此前未自定义的老用户都采用独立推荐规则，不迁移新任务草稿或把派生值写成 override。
可用性同时检查实际连接、引擎和型号。用户显式开关优先；未单独设置的型号遵循当前
目录的默认可见性，不能把供应商目录中的每个型号都直接当作可用。只启用 Luna 时不得加入 Sol。
启用清单尚未同步时等待或报未就绪；旧资料生成入口也在实际派发前核对。
已有“跟随默认”的伙伴继续读取当前有效链，不把历史创建时的型号当作显式覆盖。
未连接或没有可用默认组合时保持空值，不写入 GLM / Gateway 占位；伙伴创建和打开入口
复用客户端现有连接引导，配置完成后重新解析，不能创建没有模型的主任务。
创建表单显示名字、头像和当前模型，默认跟随伙伴默认配置，不写入独立覆盖。默认失效时，
用户可以在表单内用统一模型选择器改选，保留已填写内容；显式选择只保存为新伙伴的候选链，
不改变应用或其它伙伴的默认。Desktop 没有连接时沿用选择器的连接入口，不偷偷替换型号。
Mobile 使用电脑端已连接的模型目录；目录为空时保持创建禁用，需先在电脑配置连接，
再回到手机选择模型。手机选模器不提供远程供应商授权／配置入口。
已创建伙伴的准备中或失败状态不得遮挡设置：模型页始终可进入，保留资料、记忆与历史；
准备期间主进程不接受的姓名、简介和个性字段只读，不能留下无法保存的草稿堵住恢复入口；
更换模型后重试必须先确认设置保存成功，再继续同一伙伴的邀请，不重复创建伙伴。

全局伙伴设置保存用户自定义的默认候选链。单个伙伴没有显式覆盖时跟随全局链；一旦用户在伙伴设置里调整，
该伙伴保存自己的链。全局链由主进程按当前数据 owner 持久化，并由所有 Session 创建与 fallback
入口直接读取；不得只存在 renderer localStorage。

发送前按持久 Profile 协调长期主任务的路由，复用普通任务的模型控制与跨引擎交接。无论使用显式候选链还是跟随 Cindy 默认，有效候选链与配置来源均未变时，保留已生效或待生效的运行期 fallback，不在每次发送前强制切回首选模型（2026-10-27 用户裁决）。候选链变化、显式保存模型设置，或“全局自定义 / 推荐默认”之间的配置来源切换时，按新配置对齐；“恢复默认”即使得到相同候选链，仍按来源变化处理。普通消息与自动化运行遵守同一规则，都不读取新任务输入框。伙伴用 `send_to_session` 新开的任务按该工具的引擎与模型参数选模（6.1）。

实现与回归：[路由协调](../../apps/desktop/src/main/maker-ipc/botModelRouteReconciler.ts)、[路由回归测试](../../apps/desktop/src/main/maker-ipc/__tests__/botModelRouteReconciler.test.ts)。

伙伴的创建、全局默认、主模型和备用模型都使用普通任务的模型目录与来源选择；
共享账号和另一台电脑的可用来源不受本机引擎安装情况限制。业务仅维护有序备用链，
不得另建供应商清单、可选引擎白名单或简化路由结构。完整路由使用 `@cindy/maker-shared/model-route`，
持久化和新建会话保留 `agentDeviceId`；缺失／null 表示所属电脑，`share:<id>` 表示共享来源。
失效来源不能改投本机同名账号。远控表单统一使用 `serializeModelRoutes`，把远程来源编码到旧协议
也保留的 provider 字段；新端解码，旧端不能识别时拒绝，不能静默消费本机额度。

伙伴设置的模型页只有「主模型」及其备用链，复用统一选择器。**「任务模型」设置已移除**（2026-11-09
负责人裁决）：它只作用于已退役的 V1 专用后台任务（6.1）。伙伴新开任务时由 `send_to_session` 的参数
为那条任务选模型；主人对任务模型的偏好由伙伴按需记在自己的记忆里，宿主不另存一份设置。兼容：
- 已存档案里的 `capabilities.taskModelOverride` 原样保留、不校验也不使用，读取与保存都不因它出错；
  云端能力配置里的 `taskModel` 原样带上、不核对可用性也不提示，仍有该设置的旧版电脑不丢选择
  （见 [cloud-companions.md](cloud-companions.md) §2）。
- 远程设置 models 表单不再列出 `taskModel` / `taskFollowsPrimary`；旧控制端提交时这两个字段被忽略，
  只有它们时按「没有改动」拒绝（`INVALID_PARAMS`）。设置页 `settings.update` 补丁里的
  `taskModelOverride` 同样被忽略（`BOT_SETTINGS_RETIRED_CAPABILITY_FIELDS`），其余改动照常保存。
- 新控制端连接旧主机时，旧主机仍列出的这两个字段不显示，也不随保存回传，旧主机上的选择不变。

## 6. Skill、工具与 MCP

Cindy 的任务、自动化、插件与模型设置默认仍在 Cindy 中完成。执行引擎、订阅或
连接器来源不改变业务归属；只有用户明确指定其它应用时才转到该应用。工具切换及桌面／浏览器
操作应保留已选的应用、账号、执行主体和结果去向，并按回执核实。普通任务与伙伴复用
`business-ownership-prompt.md`，不把业务归属说明写进用户的 SOUL；这属于模型行为指引，
不是新增逐次审批或桌面应用封锁。

Codex 原生 `codex_apps` 纳入伙伴 MCP 元数据目录，来源标为 `harness`。默认继承时保留原生
开关，不强制开启连接或授权；显式白名单未选择时只在该线程设置 `features.apps=false`，
不构造无 transport 的 MCP 配置。当前任务通过 `get_capabilities(scope=runtime)` 发现它，
指定 server 后读取该线程的真实工具状态；引擎工具目录每页最多 50 项，支持 `toolQuery`
筛选与 `nextOffset` / `offset` 翻页，避免全量 Apps 工具灌满上下文。伙伴能力工具可发现、加入或移除该项；现有自定义
MCP 设置列表仍只管理用户配置的 transport，不把原生 Apps 伪装成可编辑地址的自定义服务。
SSH Codex 不提供这项本机原生能力，目录如实标为不可用。
`codex_apps` 是引擎保留名：自定义 MCP 新建／修改时拒收，历史同名配置保留但不装配；
能力目录只呈现原生项，避免同 id 串扰。引擎配置中若已有同名真实 transport，仍须按伙伴
白名单禁用，不能因名字与原生 Apps 相同而跳过。

### 伙伴技能分层：核心、系统、用户（2026-11-01 主人裁决）

**V2（2026-11-08）**：伙伴的主人对话就是它项目里的普通任务——项目 `AGENTS.md`、`.agents/skills/` 下的技能、
MCP 与记忆按普通任务原生加载，稳定提示词只有身份与「你的项目在哪」（`botSystemPrompt.ts` 的
`buildProjectHomeGuidance`），不挂核心技能与伙伴能力指引，怎么做事由普通任务提示词和各工具自己的说明给出。
系统技能（`todo` / `routine` / `follow`）及系统技能机制已全部移除，已存的 `capabilities.systemSkillsOff`

### 6.1 伙伴开任务：普通任务，不再有专用后台任务（2026-11-08）

V2 伙伴就是一个项目 + 普通任务 + 身份。伙伴需要独立执行的工作时，用普通 `send_to_session`
（省略目标）在任意项目里新建一条普通任务。**结果怎么回来不由宿主编排（2026-11-09 主人裁决）**：需要结果时，伙伴在消息里
请对方做完用 `send_to_session` 发回（宿主随消息附上来源任务编号，对方需要背景可用 `get_chat_history` 读来源对话）；
不需要时就不要求回，之后自己用 `get_task_digest` 查。怎么派活、什么时候要回报写在伙伴项目的模板技能里，伙伴和主人可改。
起始模板第 3 版（2026-11-10 主人裁决：初始体验要有足够指导性）把「在这里谈、到任务里干」写进伙伴项目的 AGENTS.md：
快的事在对话里做，改仓库、构建测试、大范围调研等较久的活开任务去做，讨论转成「动手」时也一样，主人说就在这里做才例外；
任务开在活所属的项目里（`list_projects` 取 `project_path`），让那个任务带上该项目的规则与 Skill；同一 PR / issue 先找原任务续上。
hand-off 技能的描述改成在动手前触发，正文按「选项目 → 先复用 → 新建 → 写清交代 → 告诉主人后停手」给出步骤。
原因：只讲怎么交接的技能不会在模型已决定就地开发前加载，伙伴会在主对话里直接改仓库，并缺少目标项目的规则与跟进。
伙伴开出的任务要看得见（2026-11-10 主人裁决）：伙伴对话里，一轮回复用 `send_to_session` 开出或交给的任务，接在宣布它的那条回复
气泡末尾，每个任务一行「↳ 开了任务 / 交给任务 任务名 ›」文字链接（主人在气泡内分隔线 + 胶囊与文字链接两稿中选了后者）；
该轮还没有回复时才单独列成一行。不靠回复正文写链接。任务发回的来信与它同形：一枚「↵ 任务名 回信 首句 ›」胶囊，点开看全文与「打开任务」。界面从该轮的回执读取；历史视图的 outline
保留这类回执正文、投影把它当可见结果不折叠，旧主机不提供时这一栏不出现。实现见 `BotStartedTasks.tsx`；手机端暂未跟进。
原来的 `notify_when_done`、`report_task_delivery` 与宿主代发群结果（含附带文件）一并删除：prompt 和技能能做到的事不做成工具。
升级前已登记、尚未送出的回传不再自动送回，也不报错。宿主在 `botTaskCreation.ts` / `botTaskResponsibility.ts`
（`task-responsibility.v1.json` 的 `created`）记录「由这位伙伴开的」，供任务行头像、侧栏伙伴筛选、
归属小标和名册链接使用；这条记录不授予任何访问权限。

V1 的伙伴专用后台任务（「委派」：`start_session_task` / `check_session_task` /
`message_session_task` / `stop_session_task` / `inspect_session_task_route` /
`advance_session_task_route`、委派服务、唤醒回调、路由方案、暂停与代答）已移除：

- **数据不动**：`bot_delegations` 表与历史 migration 原样保留，不再写入新行；升级时仍在运行的委派
  保留存储的状态，它的子任务就是一条普通任务，照常可见、可继续。
- **历史只读**：`botDelegationHistory.ts` 只读旧行。伙伴聊天里已有的任务卡、结果回执与补充留痕
  照常呈现（标题、冻结结果、文件、PR、打开原任务），不再有停止、补一句等实时操作；未落终态的旧行
  只在子任务实际运行时显示运行中，否则显示状态未知。近况的「输出内容」继续列出已完成旧委派的文件与
  伙伴任务的 PR。旧委派子任务继续算作「由这位伙伴开的」（本机经 `readBotResponsibilityScope`，
  远程经 `maker:bot-delegations:list`）。
- **兼容**：`maker:bot-delegations:list` 继续应答（本机与 device-link），`maker:bot-delegation:cancel`
  对旧控制端稳定返回 `UNSUPPORTED_CAPABILITY`；新控制端连旧 Host 时照常读取旧 Host 的实时行和
  `maker:bot-delegation:changed` 推送，只是不再提供停止与补一句。升级前排队、尚未派发的委派输入
  （开始、续接、解除暂停、补充）在恢复时丢弃，不会在没有回传的情况下自行开跑。
- 旧委派子任务发给发起伙伴的内部协调（`send_to_session` 的 coordination 用途）仍按
  [message-source.md](message-source.md#委派任务的内部协调) 依据旧行核验。

伙伴之间的消息同样走 `send_to_session`（2026-11-08 起；V1 的 `send_to_agent` / `check_agent_message`、跨电脑私信
传输与接收、待投递恢复和往来上限已移除）：

- `list_agents` 按需读取本机名册和同账号已授权设备的名册，返回每个伙伴主对话的 `session_id`（另一台电脑上的是
  `deviceId::sessionId`）；离线、控制关闭、撤权和目录不可用单独返回，不把不完整发现解释成没有伙伴。`@伙伴` 引用
  同样带上它的主对话，模型可直接发消息。
- 发给伙伴主对话的消息是一条普通的、带来源标签的输入（[消息来源](message-source.md)），接收方在自己的主对话里处理；
  需要答复时发送方在消息里请对方用 `send_to_session` 发回。
- 旧私信线程的只读往来页与时间线入口照常打开；升级前排队、尚未投递的 V1 私信在恢复时丢弃；旧版电脑仍发来的私信
  得到 `UNSUPPORTED_CAPABILITY`。群专线的 `send_to_user` 不受影响。
- `create_teammate` 创建出的伙伴立即可以作为 `send_to_session` 目标；创建流程由主进程同时持久化第一句自然欢迎语，
  创建本身不暗中启动工作。

### 6.2 通知

- 伙伴主任务、它启动的 Session 任务和普通 Cindy 任务共用一条完成 / 失败 / 待回复通知链，
  不另存一套 Bot 专用通知开关。
- 伙伴开的任务是普通任务，通知按普通任务处理；不因任务行上的伙伴头像静音，任务正文、状态、未读与 Dock 不变。
  （2026-11-08 起 V2 不再适用：V1「委派结果交回发起伙伴后静音执行任务完成通知」随委派移除。）
- 用户正在看对应任务时不发外部通知；后台时仍按全局桌面、飞书、移动端与灵动岛去重规则投递。
- （2026-11-08 起 V2 不再适用：V1 伙伴私信入口的静默规则、内置「跟进」轮次的不外发与没人跟时的「等你」系统提醒，
  随伙伴私信与自动跟进一并移除。）主人直接交流的回复、审批、提问及执行错误保留原提醒。
- 通知、灵动岛、搜索和旧链接均保留原任务 ID、原电脑与已有消息锚点。只有唯一 `role=canonical` 链接
  对应的任务使用伙伴主任务页面；`kind=chat` 本身不是主任务判据。伙伴路由也携带具体任务 ID，不能因缓存
  过期而切到后来创建的主任务。历史、渠道、群专线与伙伴开的任务沿用普通任务页面及其权限、报错与历史加载。
- 旧 `/bots/:botId/session/:sessionId` 或 history 地址发现伙伴不存在、链接已过期或不再是主任务时，继续
  打开原任务的普通页面；路由不授予权限，仍经本机或指定远程电脑的访问检查。真实任务不存在或访问被拒绝
  时保留原地址，明确提示原因并提供任务列表出口；普通读取失败可以重试，不重建任务或上下文。
- 已读与灵动岛可见回执等原任务数据和消息实际加载后再处理，不能因 URL 已提交或进入错误页提前清提醒。
  系统通知点击复用主窗口深链队列，窗口重载时也保留任务、电脑和回复锚点；账号切换后旧通知点击失效，
  已排队但尚未交付的通知也在取出时复核原账号代次并丢弃过期项。
- 点击先使用现有伙伴投影；尚未认识的任务先开普通页面，并后台重读投影，仅发现它是主任务时校正页面。
  新点击、切换账号或用户已去别处都会取消较早的异步跳转，不能把用户拉回去。
- macOS 灵动岛把伙伴的主任务、历史任务、群专线与渠道任务显示为伙伴本人：名字与头像代替任务标题和
  Agent 标识，群专线在名字后附群名，不显示伙伴工作目录；回复完成时以消息样式呈现（头像跨两行、
  不标「完成」），运行中、待处理、报错与未读回复由头像上的光环和角标表示。伙伴开的任务仍是普通任务。
  伙伴改名或换头像后灵动岛立即更新；头像只在本机生成有界缩略图，读不到时回退底色加 emoji 或名字首字。
  主力电脑是另一台已远控电脑的伙伴，聊天活动同样出现在本机灵动岛（不受侧栏任务范围限制，头像经本机的伙伴
  头像副本读取），点击打开它在那台电脑上的聊天页。
- iOS 的伙伴正常回复使用系统通信通知：伙伴名字、头像与回复摘要，应用角标由系统绘制。
  普通任务、报错和待处理事项保留原通知语义。头像仅携带有界缩略图、内置头像标识或
  单个字符，不上传公开头像地址；缺失头像回退名字首字，扩展失败仍交付原通知。
  此展示依赖服务端透传发送者和 `mutable-content`、以及包含通知扩展的新版 iOS 安装包；
  旧服务端或旧安装包继续显示原通知，不因客户端单侧升级停止推送。

### 6.3 伙伴近况（V2）

V1 的自动跟进（2026-10-19 起的宿主观察层 `bot-autonomy`、`followerBotId` 与「跟进我的任务」总调度、`host:sessions`
事件、内置「跟进」例行任务、两小时兜底、没人跟时的「等你」提醒、工作台四个工具与「一眼」投影、自动跟进邀请与设置）
和伙伴 Todo（`todos.v1.json`、待办工具、每天查待办、近况待办与到期红点）已于 2026-11-08 移除：伙伴像普通项目任务一样
工作，需要盯的事用普通自动化或请对方做完回传。随之不再适用的裁决：2026-10-19「自动检查，按授权行动」、
2026-10-21「自动跟进默认关闭、主聊天邀请开启」与近况定稿中的「等你 / 待办」部分、2026-10-28 近况待办与每天检查的展示修订。兼容：旧控制端读跟进设置得到「关闭」、写入得到
`UNSUPPORTED_CAPABILITY`，跟进设置页得到 `NOT_FOUND`；读伙伴待办页得到空列表；已存的 `follow` 技能开关原样保留
并随云端同步透传；旧消息里的 Todo 引用照常渲染；右侧栏遗留的 `bot-workbench` 页签打开时静默关闭。

**伙伴近况**（2026-10-21 Chris 定稿的浮层外壳，原型 `Designs/cindy/teammate-glance`）：伙伴聊天头部的网格按钮打开浮层，
依次放电脑、近期任务、输出内容，没有内容的块整块不出现（新伙伴只有「电脑」）。实现见
`apps/desktop/src/renderer/features/bots/BotGlancePopover.tsx`；手机点顶栏头像打开同内容的系统 sheet（iOS）／现有面板
（Android），见 Mobile `CompanionGlanceSheet.tsx`。

桌面设备状态放在同行，近期任务只显示任务标题与未读点；单行最低 32px。浮层随内容自然长高，以锚点到窗口边缘的可用空间
为上限、保留 12px 边距，超出后滚动。手机保留至少 44pt 点击区域和原生 sheet 的半屏／展开交互。

- **电脑**：当前运行的电脑在最前（打勾），其余在线的可点；离线的收进「离线 N 台」。云端伙伴点另一台走主力电脑的
  原确认流程（cloud-companions.md §3.1），Cindy 的多台副本直接打开那台上的她；其它伙伴只显示它所在的那台。状态词用
  「在线 / 离线」。
- **近期任务**：复用任务列表「伙伴」筛选的归属（它项目里的任务 + 「由这位伙伴开的」，含归档），Cindy 跨电脑合并身份，其它伙伴保留既有本地或云端
  身份边界；不含它自己的主对话与 Orca worker。最近活动在前，先列 5 条、展开最多 30 条；点击走任务原路由并保留所属电脑。
  绿色未读点直接读取已有任务 attention，不新增已读存储或同步。V1 例行任务留下的运行任务按自动运行显示。
- **输出内容**：已完成旧委派里未删除的成品文件，加上近期任务关联的 PR。PR 按仓库和编号去重，单行显示真实 PR 标题，
  标题未取得时以仓库名占位；PR 与文件混排按记录时间倒序，合计预览 3 条，共用一个「显示更多」。PR 点击打开 GitHub，
  文件在本机打开，远程文件打开来源任务。「成品类型」判断与手机共用 `@cindy/maker-shared/bot-deliverable`。

**「由这位伙伴开的」记录**：伙伴的任一对话（主对话、话题、渠道、群专线）用 `send_to_session` 新建本机普通任务成功后，
宿主在伙伴 Home 的 `task-responsibility.v1.json` 记 `created`（`botTaskCreation.ts` / `botTaskResponsibility.ts`）；
V1 委派的子任务从 `bot_delegations` 旧行读出、同样计入；记录被解除（`responsible: false`）的不再挂头像，但仍保留归属小标。
损坏记录失败关闭，该伙伴不认领任何任务；账号切换时丢弃旧读写；跨进程锁 + 原子替换。同目录、标题、最近消息都不是
归属证据，不做回填；这条记录不授予任何访问权限。它驱动桌面任务行头像与侧栏「伙伴」筛选（§3「伙伴的项目在界面上」）、
归属小标，以及手机任务列表标题行右侧的 16pt 伙伴头像（伙伴名册的 `following` 链接，见
protocol-compatibility/teammate-roster-follow-up-task-link.md「伙伴名册的跟进任务链接」，只标该电脑自己的伙伴，归档任务不标）。V1 工作台的逐任务接手不再计入。

### 6.4 伙伴与普通 Agent 共用能力声明和权限

声明位置、查询与维护见 [Agent 能力声明](../dev-rules/agent-capabilities.md)。

2026-10-02 修订：工具能力与普通任务共用，不再按伙伴输入的来源维护第二套逐工具权限表。

- 新伙伴默认继承 Cindy 已启用的工具集和已连接的 MCP，创建时的显式选择优先；插件继续复用共享网关。
  旧 Profile 的空和非空允许名单都升级为继承，工具集与 MCP 一致。
  旧格式无法可靠区分用户手选和系统生成；2026-10-02 用户确认统一放开，包括旧版真正手选的限制。
  连接引用、身份、记忆和用户选择的权限档保持原值。
  `toolCapabilityVersion: 1` 标记新的声明语义；此后的明确选择（包括空允许名单）照常生效。
- 能力目录来自运行时 provider 注册，不手抄工具数量或另维护底层调用口登记表。
  `get_capabilities(scope: runtime)` 返回当前引擎的注册项、启用状态及未挂载原因；指定 `server` 读取
  真实工具 schema，内置渐进目录可继续按 `category` 展开。插件沿原有发现入口展开；外部 MCP 由宿主
  向当前任务的引擎读取实际持有的工具，读不到时如实说明未挂载、未报告工具、连接失败、待授权等状态，
  不为查目录额外启动外部进程，也不暴露连接凭证（细则见 `docs/dev-rules/agent-capabilities.md`）。
- 本地伙伴的 helper 使用普通任务类目加伙伴类目；远程任务遵循该引擎与传输本来支持的普通能力面。
  新工具随注册进入共享目录和默认继承范围，不再要求登记“只有主人那一轮可用”。
- 权限由 Agent 的 ask / auto / bypassPermissions 和现有工具组配置统一处理，包含命令行、文件与 MCP。
  不强制升级已有权限档，也不新增伙伴来源分档。宿主继续检查真实调用任务、当前账号、实例代次、
  目标状态、队列归属及业务对象归属；这些是操作正确性，不是伙伴专属工具权限。
- 非主人触发（自动化、其他伙伴、群成员、IM 外人）不降权限档；任务写工具与普通任务走同一套权限，
  不再有伙伴专属的来源判定（2026-11-08，见 [伙伴操作权限](teammate-authority.md)）。
  命令行、文件与其它 MCP 工具仍只按权限档处理，本次不悄悄改权限档。
- 归档不等于停止运行，已在运行的轮次归档后仍可调用通用工具；共享入口拒绝已删除或不存在的
  调用任务，具体操作的目标状态要求保持原样。
- 群专线与主任务都能使用相同的通用工具；伙伴专属“修改自己的资料”、关联项目、群历史等工具仍需要
  对应的业务对象和本机数据。后台任务的跟踪、回传、停止仍使用现有 Session 任务契约。
- 不隐瞒能力缺口：未安装、未连接、全局停用或当前引擎/远端不支持时明确返回状态。目录读取失败
  必须报告，不能用空列表启动并宣称已全配。Cindy 安装更新只能经 `install_app_update`
  由宿主向主人弹确认卡后执行（见 [`agent-app-update.md`](agent-app-update.md)），`check_app_update` 只检查更新。
- 代输入（2026-10-13，[产品规则](input-handoff.md)）：伙伴与普通任务共用 `request_input_handoff`（窗口／截图二维码）
  与终端 askpass，卡片同样只交给主人。伙伴设置能力页有独立开关（`capabilities.inputHandoff`，缺省为开）；
  关闭后按伙伴**当前** Profile 即时对它所有运行中任务生效，工具调用与终端口令都直接拒绝，不影响普通任务。
- 本改动不引入跨设备控制协议、新的 `control_session` 大工具或新的幂等数据库表。
  通用工具保留原名和发现路径。伙伴的身份、个人记忆和 Skill 学习与工具权限分开维护。

## 7. 实现红线

- 生命周期、fallback、所有权和重放判定必须在宿主代码中确定性实现，不能只写进 prompt。
- 不得把 Profile 的永久内容依赖于某个原生 Harness 运行句柄。
- 不得让上下文压缩或异常恢复丢历史、换目录或丢 Profile 版本。
- 不得向普通用户暴露运行时维护开关来代替自动恢复。
- 不得在 fallback 后重复可能已经成功的外部动作。
- 不得把 Bot Memory 注册成全局 Maker Memory 的一个普通 workdir，或让全局 Memory 设置控制它。
- 不得把 Home 根目录整体设为可写，或从 Home 内可写配置反向派生权限。
- Bot 表全部只增量；旧代码打开含 Bot 表的库时按既有 migration compatibility 守卫失败关闭，
  不得强行降级。
- 宿主不替任务回传结果，也不设轮询或互相唤醒循环；回传是对方任务自己发出的一条普通消息（2026-11-09）。
- （2026-11-08 起 V2 不再适用：自主跟进的程序级观察、`followerBotId` 单点叫醒与 24 小时 6 次上限、「自动跟进所有任务」唯一
  及远程任务不发事件等红线随自动跟进移除。）代输入填写值仍不进入任何摘要、日志与推送。

Codex 切模型重建时，线程索引里的路径不等于文件已经落盘。缺文件时仍保留原历史根与
数据库根，先用原生 `thread/read` 核实有无已存线程，再走 `thread/resume`；只有原生明确
没有线程元数据且无法找到 rollout，才在同一伙伴主任务内重建未开始的线程。
原生 `no rollout` 错误本身不能证明线程未开始：已有历史文件丢失时也会返回它。
已有线程元数据、读取异常或迟到落盘不得触发空白重建；不得换用旧副本，也不得重放已接受的输入。
实现见 `codex-thread-locations.ts` 与 Codex adapter；原生契约回归见
`packages/maker-core/src/agents/codex/app-server/external-auth.native.test.ts`。

## 8. 验收最低集

- 单模型旧 Profile 可无损读成一项链；新 Profile 可保存并恢复 1–5 项顺序。
- 首选不可用时只切到用户配置的下一项；成功后不继续尝试。
- 跨日、长期空闲、重复打开、伙伴消息和后台任务回传都保持同一 canonical Session；异常恢复
  的多窗口 CAS、旧历史归档和历史搜索有测试。
- canonical Session 能反查唯一 Bot；后台任务能反查发起任务，彼此上下文隔离。
- 压缩或异常恢复前后使用同一个 `<bot home>/workspace/`；不同 owner / Bot 的 Home 不串用。
- 关闭全局 Maker Memory 后 Bot Memory 仍可读写；全局列举与清空不包含 Bot Memory。
- 新伙伴及所有旧名单默认继承普通 Agent 已启用的工具集和 MCP；新版显式选择（包括空名单）不被覆盖。
  伙伴可按需发现插件；Bot-own Skill 始终可用。
  三个引擎均不得因伙伴身份禁用原生子 Agent；Orca 服从普通任务相同的全局设置。
- 后台任务承接 ask / auto / bypassPermissions 三档，权限变更中不读旧值；既有计划快照可恢复。

  V1 专有文件进 `v1-archive/`；重复启动不重复转换，另一台主力电脑上的副本不在本机升级。

重启超时不等于底层关闭已取消。不可取消的旧关闭仍在执行时，当前伙伴的发送与再次重启必须立即返回仍在重启的错误，不能继续排队或由发送锁五分钟 watchdog 放行；只有旧操作实际收口后才解除保护，其他伙伴不受影响。路由返回和侧栏导航离开设置同样必须经过资料保存检查。

  兼容信号，不会写成 assistant 消息。非市场邀请的模型问候流程不变，仍在没有可用模型时等待配置，绝不偷选其它模型。

切换到曾配置过的型号时，读取同账号模型选择器保存的思考档与 Fast；未明确修改的参数继续保留，
只有未保存或目标型号已不支持的值才采用该型号的有效默认，不把目录默认覆盖回用户偏好。
宿主重新验证可用型号，写入携带 owner/代次、原选择和期限；renderer 原子持久化并经现有镜像读回
以后才返回成功。旧账号、迟到写入、并发选择、未启用型号或未确认落盘不能声称成功。
不覆盖已有任务或显式的伙伴/全局伙伴模型链，不以写缓存或新增 Bot override 冒充修改客户端默认。

## 导航未读与系统角标

- 桌面伙伴与任务共用一个侧栏（2026-10-13 定稿）：「伙伴」是侧栏第一层的一段，固定在置顶上方，与置顶、全部任务并存；点伙伴只切换主区域，不再整栏切换，也不再有顶部导航的「伙伴 / 返回任务」入口。段名在「展开（行列表）」与「收起成单行头像」之间切换，默认展开，按账号记住；收起时只占一行，放不下的收进末尾「+N」（点开即展开），正在看的聊天始终留在行内，群聊沿用[群聊界面规则](bot-group-chat.md#5-界面)的成员组合头像与单聊区分（`features/bots/TeammatesSection.tsx`、`teammatesSectionPrefs.ts`）。原伙伴列表的新建伙伴 / 群聊、加入群聊、群聊与私聊混排、多设备 Cindy、置顶 / 隐藏 / 复制 / 删除、已隐藏、需要处理的伙伴都留在段内；伙伴不默认置顶。伙伴段没有独立搜索框：侧栏总搜索同时匹配伙伴（名字、简介、技能，含已隐藏、不含已停止）、远程伙伴（含电脑名）与群聊（群名、成员名），命中排在会话结果之前（`TeammateSearchResults`）。侧栏收窄（rail）时由一个带未读数的伙伴图标直达 `/bots`（上次看的伙伴，没有则 Cindy）。
- 手机任务首页同样以「伙伴」段开头（2026-10-24 定稿「A+B 合一」）：段头与置顶段头同款，固定在共享任务、置顶与项目组之上；**展开**为伙伴页同款伙伴行（伙伴与群聊按最近活动混排，默认 3 行，多出的收进「显示全部 N / 收起」），段头右侧「+」新建伙伴或群聊；**收起**默认保留原有横向头像条；用户关闭头像后只保留标题行、数量与小号新建入口，不保留头像、名字、大号新建格或空白。首页现有「···」显示菜单的外观区域增加普通「伙伴」子菜单，与「显示」「任务信息」平级，其中「收起时显示头像」勾选项开启后保留原有横向头像条（12/18 名字、未读角点、在回话环，最后一格新建）；不是「筛选 → 伙伴」的任务创建者筛选。手机用横滑代替桌面的「+N」。收起状态（`teammatesCollapsed`）与头像开关（`showCollapsedTeammateAvatars`）分别按账号与首页导航偏好一起记住。新开关未设置时新老用户都保留原有默认显示，不主动写入用户覆盖值，也不覆盖已保存的关闭选择；显式开关跨刷新、重启与首页／抽屉重挂载保留。展开期间改开关不改变当前展开状态，下次收起生效；标题点击始终只有展开／收起两种动作。隐藏头像时，伙伴未读、群聊主时间线及话题未读、既有待处理状态通过轻量标题提示承接，不另造计数或修改读位；新消息不会自动开启头像或展开列表。段落不跟随顶栏电脑范围筛选（与桌面一致）；首页搜索时伙伴段只列出匹配的伙伴与群聊（无匹配则隐藏，搜索期间不收起、不显示新建，清除搜索恢复原显示选择），筛选与归档视图时隐藏；没有可用电脑、首页显示连接引导时仍保留（服务器群聊与云端伙伴不依赖电脑，这是手机上打开它们的唯一入口）；没有伙伴时展开或已开启头像条仍显示一行「添加伙伴」，已收起且头像关闭则只留标题与小号新建入口；既无伙伴也无可新建的电脑或仍在首次加载时整段不显示。手机与桌面一样只有一个首页（2026-10-24 定稿）：抽屉不再有「任务／伙伴」切换，标题范围菜单不列出伙伴，独立伙伴页已退役；从伙伴聊天返回总是回到任务首页，旧版本记住的「停在伙伴页」在下次写入时清除。实现见 Mobile `HomeTeammatesSection.tsx`，行与排序复用 `TeammateList.tsx` 的 `useTeammateEntries` / `useTeammateRowRenderer`。
- 系统通知（完成 / 出错 / 待回复）只由任务侧栏一处发出，`/bots` 路由同样由它观察；正在看的伙伴会话按「注视中」处理，不记未读、不发通知（`useViewedBotSessionId`）。群专线仍不通知。
- 伙伴未读按**有未读的对话数**聚合可见、未归档的伙伴私聊与群聊；私聊行仍显示原有的回复条数，群聊行标记该群未读。生成状态、工具过程、内部私信回执和静默巡检不新增未读。收起成头像时以头像角点提示未读；群（含其话题）里有未读的 @ 本人时，该群头像的状态点改画为「@」（不另加第二个标记；待确认、出错、运行中保持原色，其余一律为未读蓝），被收进「+N」的群由「+N」的状态点承接，口径与展开行的「@」一致（Desktop）。rail 伙伴图标显示聚合数。
- 桌面 Dock 的完整投影为本机待关注任务数 + 本机未读伙伴对话数。远程伙伴可以出现在伙伴段，但不扩大本机 Dock 范围；目录加载前的通知事件兜底仍由既有 appBadgeService 管理，目录覆盖的伙伴底层 Session ID 用于去重。
- macOS 菜单栏 Cindy 图标后显示与灵动岛相同的待关注数字（包含未读伙伴，不包含仅运行中的任务），为零时隐藏。已选择额度或用量文字时，数字排在这些文字之前；关闭灵动岛不关闭菜单栏计数。读完、隐藏或切换账号时及时更新，不等待用量采集。
- macOS 灵动岛的伙伴私聊未读复用伙伴列表读位：重启后恢复，超过普通活动卡片的 4 小时期限仍显示；远程伙伴离线时保留已有未读，隐藏、归档或移出账号可见范围后移除聊天未读投影。聊天未读与运行活动按主聊天 Session 合成一行，运行、待回复和错误仍取运行时状态；聊天读完或隐藏伙伴不清除这些独立运行状态。滑动标为已读推进该伙伴的读位至卡片对应消息时间（远程伙伴先在本机推进，主力电脑在线时同时上报），远程伙伴也不要求主力电脑在线。声音仍按真实运行状态变化判断，聊天保持已读不阻止新回复的完成声音；恢复未读只补显示，不重放完成通知、声音或活动中继。实现见 `useCompanionIslandChats.ts` 与 `agent-island/state.ts`，读位沿用下述设备本地语义。
- 分区切换和列表刷新不是已读。只有对应对话前台可见、读到尾部并完成内容同步后，读位才推进到实际显示的回复时间；加载历史、后台窗口、生成过程、失败的远程恢复均不按当前时间清零。普通任务原有已读同步保持不变。
- 伙伴读位跨设备同步（2026-11-05 起取代「设备本地、手机读过不清桌面角标」）：伙伴所在电脑按账号保存私聊、私聊话题与早期本机群的读位，本机窗口、手机和其他电脑都推进并读取同一份，在哪台设备看过，其他设备的角标都会清掉；手机读完私聊话题，伙伴所在电脑上的话题未读点同样清掉（话题未读点目前只显示在那台电脑上，手机不显示话题未读）。服务器群聊的读位仍在 Chat Server。各设备另留本地副本：主力电脑离线或一次上报失败时照常在本机记已读，没被电脑确认的读位在再次显示同一条回复或重连后补报；合并一律取较新的读位，乱序或迟到的上报不会把已读退回未读，电脑也不接受晚于它最新消息的读位。升级后第一次启动时，桌面原有的本地读位迁入电脑，已有的不被覆盖。同机窗口通过 storage 事件更新。旧工作端缺少回复时间字段时不凭空推断未读；旧电脑不提供读位时，手机与其他电脑保留各自的本地读位。首次建立读位不追溯已有历史，之后列表刷新不重置读位。
- 手机的伙伴未读显示在任务首页伙伴段的行、已开启的收起头像角点或头像隐藏时的标题提示点上，不另造菜单键提示点或返回按钮。首页聚焦时任务镜像按现有连接恢复链路同步全部可用电脑；任务列表本身的筛选、消息存储和运行行为不变。离线保留已有镜像，重连后重取；解除绑定或删除条目后不再聚合。
- 零不显示，入口溢出复用伙伴列表的 `99+` 规范；辅助文本保留完整数字与单位，所有界面语言一起提供。


## 本机 Hermes / OpenClaw 导入

Desktop 的 Bot Market 随安装包提供预制原生包入口，复用同一 import/transfer owner、回执、完整 Skill writer、reference memory 和原删除生命周期，不假造 Hermes/OpenClaw 来源。包安装只保存身份、头像、完整技能附属文件、方法参考和停用自动化；不执行脚本、普通首任务或来源接管，不迁移私有授权。欢迎沿原邀请服务，在内容完整保存后登记；缺模型时保留原等待/恢复状态，保存成功不表示模型已工作。包身份与原 requestId/botId 同存一份导入回执，取消记录阻止删除后的旧请求复活。详见 [bot-market-native.md](bot-market-native.md)。Beta 与正式安装包均开放该入口，内置伙伴包作为安装资源随包分发。

- 按来源实际可发现的技能、记忆和自动化列出内容，不用固定条数裁剪；技能默认全选，来源停用的技能仍保持停用。
- 导入页用分类汇总和可搜索、分页的单层列表；保存完成后直接进入伙伴聊天，不在完成页堆叠逐项待办。
- 先保存资料、连接与停用状态的自动化定义，再在聊天中完成登录和验证；用户可以稍后处理，普通聊天始终可用。
- 新导入的自动化结果统一进入 Cindy 伙伴聊天，不校验或沿用原发送渠道。存量已导入自动化不自动改渠道。
- 消息机器人单独一行、默认勾选（来源里本已停用的不勾，并标「原来已停用」）；导入即从原 Agent 停用后由伙伴接管（见 §2），只撤销本次导入做过的改动。主人不明时最多列出 5 个候选主人互斥选择，更多或没有则标「需处理」；停不下、原网关仍在用或连不上同样只标「需处理」并说明原因，不让导入失败，也不阻塞依赖它的自动化。
- 全量保留来源资料、技能及自动化（包括原生 Heartbeat、未知触发条件、空标记文件），仅排除用户主动取消的项目。暂不能转换的自动化仍保存为可见的停用任务和加密原始定义，明确提示待适配项；不能因 Cindy 暂缺能力或原投放渠道不可用而过滤。
  （2026-11-08 起：导入的自动化写成伙伴项目里暂停的普通自动化，原任务暂停后才恢复；需要已移除的导入运行时的任务——脚本、命令、监控——不再接管，继续在来源运行。）验收对照来源总清单，不以过滤后的已选数量冒充完整。
- 单项读取或写入失败保留重试记录，不中止其它内容；导入成功数量与自动化启用状态分别计算。文件字节保护仍适用，不截断文件冒充完整导入。
- 原任务在验证及接管完成前保持原状。明确选用 Cindy 模型和工具设置后可解除相应兼容性待办，仍须验证数据并确认原任务已暂停，才能启用 Cindy 任务。

## 官方 X 连接交给伙伴

- 本机伙伴的「消息平台」复用设置页已有的官方 `@askmycindy` 连接，可将当前账号在该电脑上的 X 提问交给一位伙伴；绑定与 X OAuth 授权、启停相互独立。取消伙伴绑定保留 X 账号授权，后续回到普通 X 任务。
- 每条服务端 X 路由建立伙伴 `role=channel` 专线，使用同一身份、能力、记忆、工作目录与模型配置，不接续伙伴私聊的模型历史。公开回帖风险在绑定确认和卡片中明确展示。
- 伙伴选择按账号保存；更换使用当前绑定做比较，避免迟到确认覆盖新选择。停用、删除或已交出主力电脑的伙伴不可接收新 X 提问；解除绑定后已排队的旧专线请求拒绝执行，不转给另一位伙伴。
- 复用官方 X 的认证、收发与媒体回帖，不接入 X Manager 搜索/发帖插件，不新增 X 私信机器人或个人 API 凭证入口。消息平台设置（2026-10-22 起）在桌面远程控制时同样可管理，由伙伴所在电脑执行，凭证不离开那台电脑；官方 X 的绑定 / 解绑可从远程设置完成，X 登录授权仍在那台电脑上进行。远程页的 X 区块与那台电脑自己的设置同一条件显示（配置了服务地址、正在协商、可用或已开启任一成立，由 `channels.x.get` 的 `visible` 带回；还不可用时只写「到那台电脑上完成」），旧电脑没有 `visible` 时仍只在可用后显示。Mobile 沿用现有入口边界。

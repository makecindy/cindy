# Cindy 伙伴运行时

> 本文是伙伴（Bot）身份、任务、模型路由、工作目录、Skill / MCP、伙伴消息与后台任务的产品契约。
> 修改伙伴运行时、伙伴设置、伙伴消息、后台任务或伙伴提示词前必须先读本文。

桌面一对一的连续语音交互沿用本文件的 canonical 任务与权限边界，具体行为和验证范围见
[桌面伙伴语音模式](./companion-voice-mode.md)。

## 1. 用户心智：伙伴拥有一条长期主任务

伙伴是长期存在的数字同事。用户面对的是同一个名字、性格、记忆、能力和连续的主时间线，
不应因为日期变化被换到一条空白任务。

运行时分成三层：

- **伙伴 Profile（永久）**：身份、长期记忆、自有 Skill、模型候选链、稳定的伙伴目录。
- **主任务与完整记录（长期）**：canonical Session 是这个伙伴稳定的用户时间线；消息单独
  持久化，可以持续回看和搜索。
- **模型工作上下文（可压缩 / 重建）**：Harness 只读取当前能放进上下文窗口的摘要与近期内容；
  压缩或更换原生运行句柄不得更换主任务，也不得删改完整记录。

用户说“继续找小满”时，永远找到同一个伙伴和同一条主时间线；模型不需要每次吞下全部历史，
但必须通过压缩摘要、长期记忆和有界历史检索保持语义连续。

伙伴的名字以当前 Profile 为准，人格、职责与用户关系以当前 SOUL 和用户档案为准；历史
回复中的自称错误不能反向变成人设。上下文压缩、运行时重建和更换模型不改变这个身份。
Pi、Claude Code、Codex 是执行引擎，它们的原生工具说明不定义伙伴人格，也不代表用户
正在使用对应 CLI。面向用户的配置指引应落到 Cindy 的实际入口；不能把 `/login`、
`/model` 等原生终端命令推荐为伙伴聊天中的操作。用户明确询问独立 CLI 用法时可正常说明。

### 按话题找回跨渠道聊天

主人询问过去的话题时，不要求先点名渠道，也不默认限制当前工作目录或任务创建日期。
`get_teammate_state` 在主人可读范围返回本机连接分配、状态和历史检索说明；连接分配不是
历史归属证据，也不代表实时在线。访客自查不增加主人连接信息。
按 `search_chat_history(query, teammate_id)` 搜索已保存的 `bot_session_links`，包含主任务、
历史、话题及渠道专线；按 `list_sessions(teammate_id, time_field=activity)` 查最近活跃的旧任务，
不因任务已归档而漏掉。命中后用 `get_chat_history` 阅读原文，并区分任务 `source` 与关联的渠道。

未关联的旧 IM 记录不自动认领：在已有账号历史权限内，可去掉伙伴筛选按具体话题有限检索，
结果 `companion=null` 明确表示没有可证明的伙伴归属。不能按目录、名字、当前连接，或将某渠道
全部聊天归给一位伙伴。`device=all` 沿既有同账号在线设备授权查询，失败设备、旧版本和召回上限
仍明确列出；只查本机不能声称覆盖全部设备。不增加后台扫库、全量上下文注入或私有记忆补丁。

## 2. 所有权与挂靠关系

```text
Bot Profile
├── Home                          账号隔离的唯一持久边界
│   ├── SOUL.md                   身份
│   ├── workspace/                稳定的默认工作目录
│   ├── memories/                 只属于该 Bot 的长期记忆
│   └── skills/                   只属于该 Bot 的自有 Skill
├── canonical Session             长期主任务与用户时间线
└── history Sessions              仅用于旧版本数据与异常恢复后的记录
```

伙伴属于账号而不是某台电脑：同一伙伴只在它的主力电脑上运行，其他电脑与手机通过云端对话层查看并可接管，
规则见 [云端伙伴](cloud-companions.md)。

每条伙伴 Session 必须能反查唯一的 Bot owner 与 Profile 版本。伙伴启动的后台任务是普通
Cindy Session，以父任务关系回到发起伙伴，但不冒充该伙伴或另一个伙伴的主任务。
伙伴在群聊里使用独立的群专线 Session（`role = 'group'`），与主任务共享 Profile 与 Home，
不进入主时间线；群里分工时的每一步由同为 `role = 'group'` 的分工 Session 完成（工作目录见下文例外）。
规则见 [伙伴群聊](bot-group-chat.md)。

### 例行任务执行（2026-10-26）

每条例行任务使用自己的持久任务（`role = 'routine'`），不再复用主任务上下文。
它共享伙伴资料、记忆、技能和权限，可独立设置完整模型路由；显式模型不使用主模型备用链。
内置跟进与每天查待办（普通例行任务，见 `bot-routines.md`）同样支持，夜间学习保留宿主专用流程。
完整执行记录从规则历史打开，复用普通任务页面；静默不隐藏这条独立任务的正文。
仍按来源判定主人、受托或自主身份，独立任务不是新的权限授权。详情见 [例行任务](bot-routines.md)。

### 私聊话题（2026-10-21）

Chris：「私聊话题和群聊话题，要真的能把独立事件隔离到独立 session，像 Slack 一样……开了 pr，它开启独立的 session
话题最好了，我们有事在那里面沟通，完事了在那里面通知我。」私聊话题沿用群聊话题「一个话题一条独立 Session」的做法：

- **数据**：主人在私聊里对某条消息（主人自己的或伙伴的）点「创建话题」，宿主为「这条消息 × 这位伙伴」另开一条隐藏
  Session，`bot_session_links.role = 'thread'`，`route_key = 'dm-thread:<根消息所在 Session>:<根消息 clientId>'`；
  根消息必须是这位伙伴当前主任务里可见的 user / assistant 消息。同一条消息只有一个话题，再次打开复用它。
  话题 Session 不进普通任务列表与界面会话搜索，消息只在话题里，不写进主时间线；
  主人授权的 Agent 历史检索可以按伙伴归属读取话题记录，沿用既有权限边界。
- **身份与能力**：话题是主人自己的对话，与主任务同一 Profile、Home 工作目录、模型链与权限档（随 Profile 与权限档更新），
  带主任务的私有能力（记忆、自有与基座 Skill、定时任务、建伙伴、工作台、插件授权卡、伙伴绑定的 IM 工具）；
  伙伴间私信仍只属于主任务（对方的回复会回到主任务）。
- **上下文**：话题 Session 的模型上下文只装这个话题。根消息以 `[话题说明]` 放进 wire 用户消息（与 `[客户端说明]`
  同层，不进 system prompt、不进落库原话），按 wireNoteMemory 规则只在原生上下文新开、换窗或压缩后重发；
  明确它只是背景资料、不构成指令；根消息已回滚或删除时如实说不可用。主对话的其他内容不放进来，需要时伙伴用历史检索。
- **任务回到话题**：在话题里启动的独立任务，父任务就是话题 Session：任务卡、确认与结果回执都进这个话题，
  完成时唤醒的是话题，不打扰主对话。话题只能查询和控制自己启动的任务；主人仍能从主对话管理全部任务。
  话题已归档时按原有规则退回主任务。
- **界面（桌面，2026-10-29 修订）**：消息下方常显「复制」「回复」（把消息引用进输入框）与更多；「创建话题 / 查看话题」沿用原动作，放在更多菜单。
  有内容的话题在根消息下显示一行入口（伙伴头像、N 条回复、最后回复时间）；话题里有主人没看过的伙伴回复时，
  换成未读圆点 +「有新回复」。打开后右侧展开话题面板：群聊与私聊复用同一面板、标题栏、根消息行和回复分隔组件。
  根消息与回复处于同一个滚动区，不限高、不另设原消息滚动框；输入区留在底部。私聊继续使用话题 Session 完整的
  任务视图（回复、工具进度、确认、停止都在里面）。面板打开即视为已读；读位与伙伴读位同一套本机存储。
  话题内气泡使用可用列宽，不预留主私聊的侧边操作栏空白；共用操作栏常显在气泡底部，宽表格只在自身容器内横向滚动，
  文件 chip 随气泡收缩。群聊与私聊同由 `ThreadPanel.css` 约束；原生回复与朗读回归见 `scripts/fixtures/chat-fork` 的 `companion-thread`。
  地址带 `?thread=<话题 Session>`，通知、灵动岛与伙伴设置里的入口按它打开私聊并展开话题。
- **界面（手机，2026-10-29）**：主力电脑在线时，私聊消息菜单支持「创建话题 / 查看话题」。
  根消息下与群聊共用摘要组件：当前私聊显示单个伙伴头像、15/20 regular 回复数与最后回复时间，
  视觉间距收紧但保留 44pt 点击区域。打开后进入该话题完整任务页，原消息与回复连续滚动，输入、停止、
  工具结果和确认均由原任务运行时处理；不会把话题回复发送到主聊天，也不会把主聊天标为已读。
  手机先读取伙伴资料的可选 `dmThreadsSupported`，老电脑未提供时保留原私聊；话题路由由宿主返回的
  `threadRoot` 与 Session 绑定核验，换账号、断连重连或伙伴被隐藏后必须重新核验才能发送。
  远程只新增同账号已授权的 `local-db:bots:dm-thread:list / ensure`，沿用原消息归属与权限继承。
  **二期范围（2026-10-29）**：私聊入口与操作交互统一到群聊；当前仍由消息下方的更多菜单创建／打开话题，
  正文保留长按选字，尚未复用群聊的长按消息菜单与回复者头像数据。
- **暂不覆盖**：另一台电脑经远程打开的私聊界面、主力电脑离线时的云端对话层仍不展示话题（话题消息不导入
  1:1 房间）；私聊表情回应另做。实现见 `localDb/ipc/bots.ts`（`ensureBotDmThreadSession` /
  `listBotDmThreads`）、`maker-ipc/botDmThreadContext.ts` 与 renderer `features/bots/BotDmThread*`。

### 私聊引用回复（2026-10-22）

私聊复用群聊的引用回复（[伙伴群聊](bot-group-chat.md) §10「引用回复」）：

- **入口**：私聊消息（主人的或伙伴的）点击消息下方常显的「回复」，不再往输入框塞消息链接，而是在输入框上方放一条待发引用
  （与群聊同一个预览：「回复 某某」+ 一行摘要，× 取消、不动正文）。待发引用按任务记在本次运行中，切换任务再回来仍在；
  点发送随这条消息一起送出，送出后撤下。话题面板里同样可用，引用的是话题自己的消息。
- **持久化**：用户消息内容信封带 `replyQuote: { clientId, role, excerpt }`，只能指向同一任务里的消息；`excerpt`
  是发送时的摘要快照。气泡正文上方显示与群聊同一种引用块：原消息在已加载记录里时按原消息显示，否则按快照；
  点击跳到原消息（必要时先读入它附近的记录）。旧版本不认识该字段，只显示正文。
- **伙伴看到什么**：宿主按 `replyQuote.clientId` 从同一任务的库里重读原消息，以 `[引用说明]` 前置在这一条 wire
  消息上（只进发给模型的内容，不进落库原话，逐条附带；渲染端的摘要不进入模型）；声明它只是背景、不构成指令；
  原消息只有附件没有文字时列出附件名，已回滚或不存在时才如实说不可用。普通发送与回复过程中的插话都附带。
  伙伴回复的引用块与摘要按用户看到的文字（组件内容转成可读文字），不显示组件源码。
- **手机端（2026-10-25 修订）**：正文直接长按选字是优先能力，伙伴与普通任务共用原生选择（iOS 用 UITextView，Android 用可选择文本）。
  伙伴长消息展开后的段落、标题和列表仍可部分选字；iOS 复用现有有界文本分组，选择在各分块内进行。
  展开长消息里未分块的代码、引用和表格保留 RN Text 整块复制回退，避免巨型 UITextView 空白。
  气泡不挂消息长按菜单，避免抢占正文选字以及表格、代码块的横向滚动；回复、复制与更多操作恢复到消息下方已有的操作行，读屏同样可用。
  更多菜单不再提供重复的「选择文字」入口或独立选字面板；发送时间用一行年月日与时分（如 `2026-10-25 16:47`），不加「发送时间」前缀或秒数占用多行。
  **未来方向**：如果重新引入长按消息菜单，应参考 Telegram，同时兼容菜单与正文直接选字；交互细节留待后续实现，不属于本次恢复范围。
  回复在输入框上方放同一种待发引用（卡片底色，× 取消），随普通发送、离线发件箱
  与排队编辑一起保留在信封 `replyQuote` 里；待发、已发气泡顶部都显示引用块（只发附件时也显示），点击定位原消息；没有正文气泡的消息（纯附件、错误）保留原操作行。信封解析与摘要和
  Desktop 共用 `@cindy/maker-shared/chat-reply-quote`。实现见 Mobile `companionReplyQuote.ts` 与 `MessageRenderer.tsx`。

### 回复对应的消息（2026-10-22）

Chris：「引用可以有个设置，做个开关。默认关就好。你太智能判断恐怕不准。」

- **记录**：伙伴的每条回复在 `agentMeta.replyToClientId` 记下这一轮接受的那条输入（宿主盖章，与 `botPrivateReply`
  同一处）。这是单纯的对应关系，不做「该不该显示」的判断。老回复没有这条记录，不回填。
- **显示**：设置 › 通用 › 伙伴「显示回复对应的消息」，默认关（本机偏好）。打开后，每一轮最后一条伙伴回复的气泡顶部
  显示它回的是主人哪条消息（同一引用块，点击跳过去）；只认主人亲手发的可见消息，内部续跑、任务回执等隐藏输入不显示；
  对应的消息不在已加载记录里时不显示。
- **手机端**：伙伴资料页「对话」分组的同名开关，默认关，本机偏好、对所有伙伴生效，与 Desktop 各自独立；显示规则同上。
  实现见 Mobile `companionReplyTargetPreference.ts`。
- **暂不覆盖**：IM 渠道。

伙伴自己带 IM 机器人（2026-10-15 Chris 裁决）：用户在平台自己申请机器人（Telegram bot、飞书 / Lark bot、
企业微信智能机器人、钉钉机器人、Discord bot；2026-10-17 补齐后三种），凭证直接填在伙伴设置「消息平台」页，
这个机器人就是这位伙伴；一位伙伴可以同时挂多个平台。它与
设置 → IM 机器人 里那份独立的个人 bot 是两份连接，不共享归属，也不用 Cindy 云上分配机器人。例外是一次性移交
（2026-10-17 Chris 允许）：添加平台时可选「使用已在 Cindy 设置的机器人」（该渠道个人 bot 已配好时默认选它），
凭证只在 main 里搬（`im/shared/botImPersonalAdoption.ts`）：先静默停掉个人 bot（不给主人发「已断开」、不删命令菜单），
再走同一个 `addBotImConnection`；成功后个人 bot 清空（设置页按既有广播显示未配置），失败则把个人 bot 的凭证原样写回并
重新起来。随连接带过去的：Telegram / Discord 的主人 id、企业微信 / 钉钉 / 飞书已认定的主人（不再重新 TOFU）、
Telegram 设为全响应的群；设置页的人格与行为配置不带。移过去之后没有共用，想再要个人 bot 需另配一个。
个人微信复用既有扫码授权通道：伙伴设置「消息平台」可连接或接管当前个人微信，单个本地账号只绑定一位伙伴；
绑定只保存伙伴归属，不复制凭证、不创建第二份轮询。主人私聊进入主任务，其他私聊进入渠道专线。
解除伙伴关联恢复个人微信独立路由，保留微信授权与原工作目录；有排队消息或运行中的任务时拒绝切换。
绑定伙伴后，经微信连接凭证确认的主人消息沿用伙伴的原生权限档（包括完全访问），Claude Code、Codex、Pi 使用同一入口，不额外挂逐轮强确认策略，也不改写伙伴权限。非主人、身份未知以及未绑定伙伴的个人微信仍保留原渠道逐轮权限约束；只有支持该策略的引擎与权限档才能执行。权限在 Cindy 的伙伴对话输入框下方切换，模型在伙伴设置中调整。实现与回归见 `im/wechat/WechatIM.ts`、`im/wechat/__tests__/WechatIM.test.ts`。
绑定伙伴后，访客触发的工具权限仅由主人的 Desktop／同账号手机确认；不向访客发送权限提示或接受其授权回复。主人微信确认与访客普通问答保持原有行为。
每条连接一份传输层实例（复用个人 bot 的各渠道适配器，凭证按连接 id 前缀隔离在本机安全存储），
它说什么、记得什么、会什么、用什么模型，全部来自伙伴。主人私聊进该伙伴的 canonical 主任务；每个群 / 话题与
每位外部用户的私聊各一条隐藏的渠道专线 Session（`role = 'channel'`，
`route_key = 'im:<channel>:<botContextId>:g:<chatId>[:t:<threadId>]'` / `…:dm:<userId>`），与主任务共享 Profile
与 Home，不进入任务列表、主时间线、历史列表与未读。连接对外开放：任何人给这个机器人发消息都是在和伙伴对话。

## 3. 长期会话生命周期

### 3.1 稳定主任务

- 一个伙伴默认始终复用同一条 canonical Session，不按日期、空闲时长或打开次数更换。
- 每次消息、伙伴私聊和后台任务回传都先解析同一条权威 canonical link；不得在这些入口各自
  维护一套“是否换任务”的判断。
- Profile 更新只推进主任务下一轮使用的身份与能力版本，不创建新任务。
- 只有 canonical Session 确实丢失或已删除时，恢复流程才可以用 CAS 建立替代任务；健康的
  主任务不能被普通创建入口覆盖。
- 旧版本遗留的 history Session 继续可回看、搜索，不做破坏性迁移。

### 3.2 上下文沿用 Session 原生压缩（2026-10-23）

伙伴的主任务、私聊话题、IM 群／外部私聊专线和伙伴群聊专线，均长期复用各自的同一条 Session。
健康上下文交给 Session / Harness 已有压缩机制，不因伙伴身份另外添加上下文维护自动化：

- 不按空闲时长（包括隔夜 12 小时）、打开次数或 70% / 90% 占用提前重建原生会话。
- 不根据工作记忆新鲜度替代原生压缩，不主动扫描健康 Codex 历史来提前换窗。
- 正常原生压缩结束不登记或重启伙伴运行实例；只有明确资料 / 能力 / 模型配置变化等独立原因才刷新实例。
- 不在后台唤醒、自动续跑或人工输入时执行伙伴专属整理，因此不产生日常整理提示卡。记忆与技能的整理只在
  内置「夜间学习」例行任务里进行（默认开、可暂停，没有新对话不调用模型，见 `bot-routines.md`）。
- 不在回复后调用辅助模型复盘学习、维护短期工作记忆账本，压缩后也不重新注入旧账本。
- 用户明确建立的例行任务、后台任务与其结果回传、手动记忆 / Skill 工具、既有长期记忆及文件不受影响。

发送前 `contextOverflowRollover.prepareUnhealthySession` 只保留故障恢复边界：普通 Session 共用的
真实满窗保护、上下文溢出、明确压缩失败、Pi 无响应或已确认的损坏历史。Codex 的 token 压力
继续交给原生压缩；普通网络、鉴权、额度错误不据此换窗。恢复保留同一产品任务和完整聊天记录。
历史故障交接仍保存近期需求、回复、改动和有界工具结果，省略图片正文；仅故障恢复使用交接，
不能把这个兜底路径重新当成伙伴的日常压缩。

Codex 图片历史在运行中确定失败时，伙伴主对话与普通桌面任务共用一次隐藏续接：
保留原请求与已记录进展，不重放原请求或已完成工具；结果不明先核实。每条输入最多自动
续接一次，停止、新输入接管和排队输入仍能取消恢复。群分工、委派、IM 和自动化输入的
续接仍由原分发者负责，不能被主对话恢复抢占。普通上下文溢出仍只在本轮没有 assistant /
tool 副作用时自动重放。原生后台工作尚未结束时不自动关闭句柄。

自动恢复无法完成时保留错误与既有继续／重试入口；「重启伙伴」无需旧模型参与，保留
同一条时间线、记忆与文件，并携带工具结果重新建立上下文。重启不自动重放请求。

旧版 `working-memory.json` 保留，不迁移或删除用户历史，但不再自动生成、刷新或注入模型上下文。
删除消息、撤回和清空对旧账本的失效清理仍保留，避免历史隐私内容在兼容工具里复现。

完整聊天记录与模型工作上下文必须分离：压缩可以丢弃模型不再需要的旧 tool result 和中间过程，
但用户时间线、搜索索引和审计记录仍按既有持久化策略保留。完整消息继续写入 SQLite，界面与
历史工具按稳定游标分页读取；不能因为聊了一个月、消息变多或发生压缩就自动另开一条产品任务。
容量治理按数据库体积与可观测数据处理，不按固定消息条数截断伙伴历史。

provider 的 `final_answer` 从首段正文起可见，历史视图接管、后续工具调用和完成收口均不得把它过滤掉。
本链路验收同时覆盖普通任务与伙伴入口、实时消息转历史、折叠展开及重开；不能用桌面验收代替手机验收。
回归见 Mobile `companionConversationPresentation.test.ts`、`mobileHistoryRender.test.ts` 与 `pluginAttachmentBubble.test.tsx`。

普通设置不显示“永久 Session”“手动压缩”“自动换 Session”或运行时 fallback 开关。健康、

手机端不提供例行任务管理：伙伴资料页不显示自动化任务入口，「所有任务」下拉菜单不展示 `routines`，旧的独立自动化管理页也已移除。上述例行任务编辑与草稿规则仅适用于桌面端；手机仍保留任务运行历史。实现见 Mobile `CompanionHeader.tsx`、`CompanionProfileSheet.tsx` 与 `remoteResources.ts`。

不提供新的「暂停伙伴」操作；已有暂停状态仍保留恢复入口。设置页与伙伴列表复用同一删除确认，保留任务历史和独立工作树；确认文案必须说明伙伴自身资料、记忆与工作区会被删除。
「重启伙伴」直接显示在管理区，不隐藏在高级配置或历史折叠项内。该操作：停止当前主任务运行、取消旧自动续跑，保留同一条
主时间线、已存消息、伙伴记忆与文件，以持久交接重建原生上下文。排队输入保留但暂停，

Cindy 应用，也不取消伙伴已委派的独立任务。操作中禁用重复点击并显示状态，失败后可重试；
暂停的伙伴先使用既有恢复入口。桌面本地、桌面设备互联与手机均提供伙伴设置。

**桌面远程控制（2026-10-22 用户裁决：远程控制原则上都能看到，没有必要的理由不应该不同步）**：控制另一台电脑上的伙伴时，

`shared/botRemoteSettings.ts`），主机用与本机 IPC 同一份服务与校验（`updateBotProfile`、记忆服务、例行任务服务、
`runRegisteredBotLifecycleAction`、语音与消息平台服务等）。**不新增 device-link 通道，不放宽 allowlist**；动作经
「允许同账号设备控制本机」与撤权检查，共享任务访客 / 供应商分享对端不可用；隐藏与归档伙伴仍只在本机恢复。
模型来源、账户名称、可用引擎、技能 / MCP / 工具集目录与默认模型链都以伙伴所在电脑为准，不读取控制端默认模型。
主机用 `caps` 声明已实现的操作，页面按操作显示：旧主机没有这个动作时整页回退到下面的通用表单页
（`RemoteBotSettings.tsx`），手机与旧桌面也继续使用通用表单与 `settings:<botId>/...` 动作，二者不变。

远程页面与本机页面**有意不同**的只有以下几项，且各自说明原因：

- 语音：模型目录与每个伙伴的偏好在主机读写；试听用控制端扬声器无法由主机播放，远程不提供试听，只提示请在那台电脑上进行。
- 消息平台：凭证（Telegram / Discord Token、飞书 / 钉钉 / 企业微信密钥）只在保存它的电脑上输入和存放，**任何操作都不接收也不返回凭证**；
  远程页可查看连接状态、移除连接、设置 Telegram 群参与模式、重置隐藏任务、把设置里已配好的个人 bot 移给该伙伴、
  分配或释放个人微信与官方 X；新建连接（填写凭证）、微信扫码授权、X 登录授权、选择微信工作目录需要在伙伴所在电脑上完成，页面用一句话说明。
  连接与微信状态没有推送，远程页打开且窗口可见时每 5 秒重读一次。
- 提升权限仍保留既有确认：设置页本来没有权限档入口，设置主机的写入口拒绝 `permissions`，权限修改只在通用表单页（带确认）。

离线、对方未响应、动作不支持与冲突都不引起布局跳动：离线提示浮在页面底部边缘（不占位，在线时页面与本机设置在同一位置），页面保留已读内容；写入失败沿用自动保存的失败与重试，
记忆 / 例行任务的 revision 冲突沿用各自页面的冲突提示（失败以数据形式返回，保留 `PRECONDITION_FAILED` 与冲突标记）。
实现见 `RemoteTeammateSettings.tsx`、`remoteBotSettingsTarget.ts`、`localBotSettingsTarget.ts`、`BotSettingsDrawer.tsx`，
主机侧见 `main/localDb/ipc/botRemoteSettingsHost.ts` 与 `botRemoteSettingsOps.ts`；手机见 Mobile `CompanionProfileSheet.tsx`。

## 4. Bot Home 权威边界

每个伙伴拥有账号隔离的 `<ownerRoot>/bots/<botId>/`。它是该伙伴唯一的持久内容边界，
不属于当前 Session、当前项目或 Cindy 的全局 Maker Memory：

```text
<ownerRoot>/bots/<botId>/
├── SOUL.md                     身份，由用户与宿主维护
├── system_prompt.md            可选的用户提示词覆盖
├── workspace/                  Bot 默认可写工作区
├── memories/
│   ├── USER.md                 该 Bot 认识的用户
│   ├── MEMORY.md               该 Bot 的记忆索引
│   └── *.md                    该 Bot 的长期记忆
├── working-memory.json         旧版工作记忆账本（见 3.2），不再自动维护或注入
├── nightly-learning.json       夜间学习的对话计数、水位、频率、记录与在观察的做法
├── learning-history/<run>.json 夜间学习每条改动的前后内容（撤销用）
└── skills/<slug>/SKILL.md      该 Bot 自有或后学的 Skill
```

- Bot Memory 可以复用 Cindy 的存储原语，但物理数据、开关、索引、清空入口和提示词作用域都
  只属于该 Bot；关闭或清空全局 Maker Memory 不得关闭、列出或删除 Bot Memory。
- 启动 Bot 时不得注入当前项目的 Memory、全局 Memory 摘要或其它 Bot 的记忆。
- 伙伴沿用普通任务的权限档，原生文件与 Shell 工具按用户选择的权限执行；`workspace/`
  是默认工作目录，不是操作系统级隔离边界。记忆与 Skill 默认经类型化接口维护，以保持
  索引、版本与运行期快照一致；不得把这种维护约定描述成对原始文件工具的强制隔离。
- `workspace/` 是伙伴跨 Session 复用的唯一默认工作区。伙伴不直接绑定代码项目、不占用
  worktree——需要隔离工作区或独立持续执行的工作通过 `start_session_task` 交给一条真正的 Cindy 任务完成
  （见第 6.1 节）。唯一例外是伙伴群聊的分工 Session：它在该安排记录的群工作目录里干活，
  git 项目时共用该安排的 worktree；工作目录每次启动都按安排记录核对，失败不回退 Home，
  规则见 [`bot-group-chat.md`](bot-group-chat.md) 第 7 节。
- 第二个例外是绑定了项目的 IM 访客（#8359）。主人可在伙伴「消息平台」页，把一条连接上的某位
  私聊访客（传输层核验的平台用户 id，不取自模型输出）绑定到伙伴已关联的一个本机项目：这位访客的
  `channel` 专线每次启动都在该项目里运行，使用独立记忆作用域
  `bot:<botId>:guest:<channel>:<guestId>`（落在 Home 之外的 `bot-guest-memories/`，不进伙伴记忆索引与夜间学习），
  不挂载 Home、不注入主人的 USER.md。项目不再关联或目录不存在时失败，不回退 Home。未绑定的访客
  按连接策略处理：`shared`（缺省，沿用伙伴 Home，与以前一致）或 `refuse`（只回一句固定提示，不起轮次）。
  绑定含本机路径，只在本机设置显示，不经远程设置资源下发。与上文同理，这是默认工作目录与记忆的隔离，
  不是操作系统级沙箱：访客轮次仍受访客权限策略（破坏性操作需主人确认）约束。实现见
  `im/shared/botImGuestAccess.ts`、`maker-ipc/botWorkspaceRuntime.ts`。
- 上下文压缩、模型 fallback、失败补偿和删除临时任务不得移动或删除 Home 内容。
- 远端运行必须使用远端实际存在且归属于该 Bot 的 Home；在远端 Home 尚未完成供给前，不得把
  本机路径写进提示词或伪装成可访问目录。远端自有 Skill 未装配时，共享指南不引导本机 Skill
  读写和学习，工具入口在存储及刷新之前明确返回不可用，不能承诺下一轮或新任务生效；
  这不影响远端已支持的共同基座、记忆、协作及能力发现。手机控制本机运行时仍使用本机自有 Skill。

### 关联项目（2026-10-22）

每个伙伴（包括 Cindy）在设置中独立关联多个项目。项目列表可添加、查看和移除；关联沿用 Home 中
`workbench.json` 的 `directories`，旧关联直接可见，保留 `deviceId` 与旧 Todo 判断。移除只改关联，
不删除项目、文件、记忆或任务责任。损坏文件不能用空列表覆盖。

关联是按需读取资料的入口，不改变伙伴 Home、默认工作目录、文件工具权限或逐任务责任，不自动授权
改仓库、向任务发消息或后台扫描。伙伴通过 `list_teammate_projects` 查询自己的关联及目录所属电脑，
按需用原有文件工具读取项目的 AGENTS、README 和项目知识索引等；项目资料与记忆沿用项目自己的规范，
不复制进伙伴个人记忆。另一台电脑上的路径只作引用，不在本机打开；需在原电脑按已有访问方式读取。
`set_teammate_project` 只修改调用伙伴自己的关联，走现有权限与行动核验。

桌面本地设置从注册项目中选择；远程桌面与手机复用 `settings:<botId>/projects` 的列表、项目开关与保存，
只传项目名、可用状态和不透明 ID，不暴露宿主绝对路径。新增项目先在伙伴所在电脑登记到项目列表。
主力电脑切换沿用已有目录随行协议，文件不搬家，不把另一台电脑上的目录当作本机目录。
实现：`botLinkedProjects.ts`、`botWorkbenchService.ts`、`BotProjectsSettings.tsx` 与 `botRemoteEditors.ts`。

## 5. 模型候选链

伙伴 Profile 可配置 **1–5 个有序候选**，每项是一个完整运行路由：

```text
harness + provider + model + effort + fastMode
```

- 第一项是首选；首次主任务启动和确定性重建从第一项开始尝试。
- 只有连接、鉴权、配额、容量、模型不可用和启动失败等“候选不可用”错误才进入下一项。
- 候选不可用与原路由自动续跑分开判定；Pi 原生重连耗尽（`pi-gateway-drop`）仍可切到伙伴候选链。
  已落库失败回合只有在切换成功后才自动发送：有持久产出时只续跑，确认零产出才重发原文。
  候选耗尽、切换失败或需要换窗确认时交还错误，不继续重试失效路由；复用现有恢复额度和退避，
  不覆盖用户的新选择。实现与回归见 `maker-ipc/botCandidateRecovery.ts`、
  `maker-ipc/__tests__/botCandidateRecovery.test.ts` 和 `sessionRuntimeFallbackIntent.test.ts`。
  跨 harness 路由已提交但新引擎启动失败时停止自动恢复并显示错误；不使用提交前的路由代次继续推进候选。
- 定时自动化的恢复只属于当前运行轮次；候选耗尽或自动恢复放弃后，该轮按失败收口并保留错误记录，
  同时释放临时重试状态，后续已排队或到期的轮次沿用原调度继续执行，不自动重放失败轮次。
  用户消息的手动重试、显式暂停、交互等待和仍在运行的执行边界不受影响。实现与回归见
  `maker-ipc/agent-input-coordinator.ts` 的 `abandonAutoResume` 和同目录 `__tests__/agent-input-coordinator.test.ts`。
- 用户拒绝授权、工具业务失败、参数错误和已经产生副作用后的失败不得触发透明重放。
- 同一轮最多按生效候选链各尝试一次；不得循环。用户显式配置的链不得追加目录候选。
- 同 harness 可在安全边界切模型；跨 harness 必须走既有 agent-switch / 交接重建事务。
- 伙伴设置中的显式模型保存立即同步当前主任务的运行选择；空闲时在既有安全边界完成切换，运行中先记录最新选择，在回复、工具与审批结束后的安全边界接替，不要求用户再发一条消息才能登记。连续改选以最后一次为准，选回当前路由应取消不同的待切换路由。
- 自动化指定的临时模型在本轮发送中不被伙伴默认模型对齐覆盖，包括跟随全局默认的伙伴。主人随后保存新的伙伴模型选择时，在发送锁内以同一数据库事务清除活跃主任务及群／IM 专线的旧恢复偏好，并同步标记模型对齐失效；新自动化记录恢复选择前在同一发送锁内对齐已保存模型，避免异步运行态刷新尚未执行时重新写回旧选择。恢复记录写入还须原子校验读取路由时的伙伴 Profile 版本，覆盖保存期间新建、尚未进入发送锁快照的专线；版本变化时重新准备，不能写回旧选择。设置已保存但运行态刷新前退出也不会复活旧选择；即使新选择恰好等于临时运行模型，下一次聊天也不得恢复到旧选择。普通内部投递先拒绝已降级的伙伴副本，再在发送边界恢复原选择，并在所有异步准备结束、真正派发给 Agent 前同步重查降级状态；能力设置预览使用下一轮普通聊天的选择，不因预览消费恢复记录。
- 模型配置只保留统一选择器入口，备用链仍在原组件内折叠；思考深度、Fast 与 Harness 不拆成独立设置页。缩窗交接复用已经核实目标窗口的延迟选择处理，完整记录与主任务身份保留，不绕过原生副作用重放限制。
- fallback 只改变当前任务的有效路由，不暗改 Profile 顺序。下一次确定性重建仍从首选开始。
- 存量单模型配置归一成一项候选链，不能在升级时改变用户已有选择。

伙伴默认模型与新任务选择独立（2026-10-21 用户裁决）。保留「设置 → 通用 → 伙伴 → 默认模型」
入口；新任务输入框的引擎、来源、模型、思考档位、Fast 与远程电脑选择都不得改变伙伴默认。
未自定义伙伴默认时，复用产品推荐顺序，从已连接且可用的目录选出第一条推荐路由，
思考档位取模型推荐值，Fast 默认关闭；只返回一条，不自动追加备用链。
目录或引擎尚未就绪、没有可用推荐时返回空链，沿用连接与选模引导。
「恢复默认」只删除全局伙伴 override，重新解析推荐值，不重新跟随新任务草稿。
已有显式全局设置、单个伙伴的显式模型及历史单模型兼容配置保持不变；
新用户与此前未自定义的老用户都采用独立推荐规则，不迁移新任务草稿或把派生值写成 override。
可用性同时检查实际连接、引擎和型号。用户显式开关优先；未单独设置的型号遵循当前
目录的默认可见性，不能把供应商目录中的每个型号都直接当作可用。只启用 Luna 时不得加入 Sol。
启用清单尚未同步时等待或报未就绪；旧资料生成入口也在实际派发前核对。
已有“跟随默认”的伙伴继续读取当前有效链，不把历史创建时的型号当作显式覆盖。
未连接或没有可用默认组合时保持空值，不写入 GLM / Gateway 占位；伙伴创建和打开入口
复用客户端现有连接引导，配置完成后重新解析，不能创建没有模型的主任务。
创建表单显示名字、头像和当前模型，默认跟随伙伴默认配置，不写入独立覆盖。默认失效时，
用户可以在表单内用统一模型选择器改选，保留已填写内容；显式选择只保存为新伙伴的候选链，
不改变应用或其它伙伴的默认。Desktop 没有连接时沿用选择器的连接入口，不偷偷替换型号。
Mobile 使用电脑端已连接的模型目录；目录为空时保持创建禁用，需先在电脑配置连接，
再回到手机选择模型。手机选模器不提供远程供应商授权／配置入口。
已创建伙伴的准备中或失败状态不得遮挡设置：模型页始终可进入，保留资料、记忆与历史；
准备期间主进程不接受的姓名、简介和个性字段只读，不能留下无法保存的草稿堵住恢复入口；
更换模型后重试必须先确认设置保存成功，再继续同一伙伴的邀请，不重复创建伙伴。

全局伙伴设置保存用户自定义的默认候选链。单个伙伴没有显式覆盖时跟随全局链；一旦用户在伙伴设置里调整，
该伙伴保存自己的链。全局链由主进程按当前数据 owner 持久化，并由所有 Session 创建与 fallback
入口直接读取；不得只存在 renderer localStorage。

发送前按持久 Profile 协调长期主任务的路由，复用普通任务的模型控制与跨引擎交接。无论使用显式候选链还是跟随 Cindy 默认，有效候选链与配置来源均未变时，保留已生效或待生效的运行期 fallback，不在每次发送前强制切回首选模型（2026-10-27 用户裁决）。候选链变化、显式保存模型设置，或“全局自定义 / 推荐默认”之间的配置来源切换时，按新配置对齐；“恢复默认”即使得到相同候选链，仍按来源变化处理。普通消息、例行任务和自动唤醒遵守同一规则，都不读取新任务输入框。后台任务默认继承发起时的实际路由，不读取可能过时的主任务创建模型。

实现与回归：[路由协调](../../apps/desktop/src/main/maker-ipc/botModelRouteReconciler.ts)、[路由回归测试](../../apps/desktop/src/main/maker-ipc/__tests__/botModelRouteReconciler.test.ts)。

伙伴的创建、全局默认、主模型、任务模型和备用模型都使用普通任务的模型目录与来源选择；
共享账号和另一台电脑的可用来源不受本机引擎安装情况限制。业务仅维护有序备用链，
不得另建供应商清单、可选引擎白名单或简化路由结构。完整路由使用 `@cindy/maker-shared/model-route`，
持久化和新建会话保留 `agentDeviceId`；缺失／null 表示所属电脑，`share:<id>` 表示共享来源。
失效来源不能改投本机同名账号。远控表单统一使用 `serializeModelRoutes`，把远程来源编码到旧协议
也保留的 provider 字段；新端解码，旧端不能识别时拒绝，不能静默消费本机额度。

伙伴设置的模型页按用途显示「主模型」与「任务模型」，都复用统一选择器。任务模型默认继承主模型；
用户可独立选择一条完整路由（执行位置、Harness、来源、型号、思考深度、Fast），也可恢复继承。
`capabilities.taskModelOverride` 缺失或为 `null` 表示继承，非空表示显式路由；不保存继承模型的副本。
独立配置只影响此后通过 `start_session_task` 创建的普通后台任务，不切换伙伴主任务或已有后台任务。
伙伴也可先通过 `get_app_default_model` 读取本机已启用的完整路由，再给 `start_session_task`
传 `model_selection: { id, effort?, fast_mode? }`。`id` 使用查询返回值，绑定型号、来源账号和 Harness；
不可猜测型号后沿用发起方引擎。选择顺序为本次指定、伙伴任务默认、发起时实际模型。
本次选择只写入新任务，返回 `model_route` 供核对，不修改伙伴或应用默认，也不证明模型已完成执行。
目录或参数失效时拒绝本次创建，不换型号；不传新参数的旧调用仍按原有继承链执行。
显式任务路由在保存与新建时核对目标设备的连接、引擎、型号及参数可用性；失效时提示重新选择，
不得暗中换回主模型或另一引擎。任务模型没有独立备用链，不套用主模型的备用候选。
远程设置复用现有 models 表单，以可选的 `taskModel` / `taskFollowsPrimary` 字段传递；
旧客户端未提交这些字段时保留任务覆盖，新客户端连接旧主机时不显示该设置。

## 6. Skill、工具与 MCP

Cindy 的任务、例行任务、自动化、插件与模型设置默认仍在 Cindy 中完成。执行引擎、订阅或
连接器来源不改变业务归属；只有用户明确指定其它应用时才转到该应用。工具切换及桌面／浏览器
操作应保留已选的应用、账号、执行主体和结果去向，并按回执核实。普通任务与伙伴复用
`business-ownership-prompt.md`，不把业务归属说明写进用户的 SOUL；这属于模型行为指引，
不是新增逐次审批或桌面应用封锁。

Codex 原生 `codex_apps` 纳入伙伴 MCP 元数据目录，来源标为 `harness`。默认继承时保留原生
开关，不强制开启连接或授权；显式白名单未选择时只在该线程设置 `features.apps=false`，
不构造无 transport 的 MCP 配置。当前任务通过 `get_capabilities(scope=runtime)` 发现它，
指定 server 后读取该线程的真实工具状态；引擎工具目录每页最多 50 项，支持 `toolQuery`
筛选与 `nextOffset` / `offset` 翻页，避免全量 Apps 工具灌满上下文。伙伴能力工具可发现、加入或移除该项；现有自定义
MCP 设置列表仍只管理用户配置的 transport，不把原生 Apps 伪装成可编辑地址的自定义服务。
SSH Codex 不提供这项本机原生能力，目录如实标为不可用。
`codex_apps` 是引擎保留名：自定义 MCP 新建／修改时拒收，历史同名配置保留但不装配；
能力目录只呈现原生项，避免同 id 串扰。引擎配置中若已有同名真实 transport，仍须按伙伴
白名单禁用，不能因名字与原生 Apps 相同而跳过。

### 伙伴技能分层：核心、系统、用户（2026-11-01 主人裁决）

伙伴的技能分三层，目标是上下文有序、精简，编排能力常驻，功能按需：

1. **核心技能**（`teammate-guide`，`maker-ipc/teammateGuide.ts`）：所有伙伴相同，常驻，随 Cindy 版本迭代，
   主人不能关闭或修改。只放编排：何时开后台任务、控制自己开的任务（含到其他电脑上干活）、联系与创建伙伴、
   换模型、查找并使用工具和插件、自主轮次的授权边界、记忆，以及「了解自己」——知道自己有哪些功能、
   按主人要求开关（`set_teammate_capability` kind=feature），Cindy 的用法先查 `get_capabilities` help。
   正文最大变体不超过 `TEAMMATE_CORE_MAX_CHARS`（6000 字符），由 `botProfileRuntime.test.ts` 门禁。
   细节一律不预加载：核心只列主题名，伙伴用 `read_teammate_skill` 按需读取
   （`packages/lizi-mcps/src/xdt-helper/teammate_skills.ts` 的 `TEAMMATE_CORE_TOPICS`）。不用文件链接，
   保证三个引擎和远程运行时都能读到。
2. **系统技能**：待办（`todo`）、例行任务（`routine`）、工作台与跟进（`follow`）。核心里只露名字和一句话，
   用到时读全文。每位伙伴可单独关闭，存为 Profile 的 `capabilities.systemSkillsOff`（缺省 = 全开，旧资料不迁移；
   `shared/botSystemSkills.ts`），新建伙伴默认全开。关闭时三件事一起停：
   - 提示词不再列出它（稳定层的工作台一行同样随 `follow` 去掉）；
   - 它的工具（`TEAMMATE_SYSTEM_SKILL_TOOLS`）由 helper 按伙伴实时设置拒绝调用，新列表里也不出现；Pi 直连工具同样不注册。
     内置例行任务运行所需的 `schedule_notify_current_run` 不属于任何系统技能，始终可用；
   - 后台动作：`todo` 关闭时「每天查待办」的运行跳过、近况里不再提供开启，待办动作被拒绝（已有待办保留）；
     `follow` 关闭时不再被选为跟进者或「跟进我的任务」的伙伴，内置跟进的运行跳过，两小时兜底不再叫醒它，
     「例行任务」页的相应开关置灰并说明由能力页决定。夜间学习不受影响。
   关闭 `routine` 只停止伙伴自己新建或修改例行任务；已有例行任务照常运行。
3. **用户技能**：伙伴学会的技能（可停用、查看、修改、删除，停用即移到 `disabled-skills/`），以及主人从本机
   逐项勾选给它的技能（本机技能保持逐项勾选，不跟随本机，维持 2026-09 首发裁决）。

技能沉淀已交给夜间学习：核心只保留一句「主人明确要求时才记成技能」，详细规则在 `memory` 主题里。
能力页（桌面 `BotCapabilitySettings`，手机「技能与连接」）按这三层分组呈现，代输入归到单独的「权限」分组。

轻量不等于没有 Skill。伙伴启动时按以下优先级构造能力：

1. 伙伴家目录中的自有 / 后学 Skill；
2. 与普通 Agent 共用的内置工具集、已连接 MCP 和插件，默认全部继承；
3. Cindy 已安装的插件、Skill、MCP 与内置工具可以按需发现并复用。默认不灌入全量
   Skill 正文、MCP schema 或插件详细说明；伙伴通过轻量入口查询真实声明，再按需展开。

- Skill / MCP / 工具集引用保存在各伙伴自己的 Profile，复用共享源的安装与连接；加入或移除
  不修改共享源、凭证或全局开关。配置改变后在同一主任务的安全轮次边界重建能力快照，不要求新建任务。
  Skill 保存回执只有在宿主确认刷新成功后才能报告 `next-turn`；忙碌、缺少运行实例或刷新失败时
  保守返回 `next-session`，不把“请求已发出”当成生效证明，也不取消原有的自动刷新重试。
  插件经共享 `cindy` 网关按需发现和调用，仍执行已有账号、工作目录、启停和调用授权门禁；
  内置工具集名单不得拿来过滤插件 ID。需要改写共享 Skill 时保存为伙伴自有 Skill。
- 命令行和文件操作沿用普通任务权限；workspace 是默认目录，不是额外硬沙箱。伙伴启动的
  后台任务继承发起时实际生效的权限档；权限切换在途时等待稳定，不能读取旧的宽权限。
  已有连接的授权和限制继续由宿主执行，一次性操作批准不扩展到其它请求。
- **提示词承诺必须等于工具面**。能力说明按实际挂载的工具集逐块注入（挂了 docs 才讲怎么
  做文档），且挂载必须真实生效：显式挂载 docs 工具集时，运行时把 `cindy_docs` 写进该伙伴
  的 MCP allowlist——不允许出现「提示词说有、运行时够不到」或反向的错位。
- **渠道专线自带该渠道的原生 API 工具**（2026-10-17）。伙伴绑定的 Telegram / 飞书（Lark）连接与
  设置页个人 bot 同一口径：轮次由该渠道消息触发时，`cindy_telegram_bot` / `cindy_feishu_bot` 始终
  进专线的 MCP allowlist（`botProfileRuntime` 按 `telegramChatId` / `feishuChatId` 强制挂载，伙伴
  收窄工具集也不收掉），每条入站消息的 `[渠道说明]` 末尾点名本轮可用的工具，Agent 第一时间就知道
  自己在哪个渠道、能直接调哪些平台 API（发文字 / 媒体 / 文件、回复、表情、置顶、群信息与成员、读消息、
  任意 Bot API / Open API）。轮次内原生 API 出站走触发本轮的那条连接自己的 bot，不串到设置页那份；目标 chat
  与触发者身份来自逐轮作用域租约（`im/shared/channelToolScope.ts`），不来自模型参数——群轮次只能操作
  本群，成员触发的轮次只能读取 / 发送，管理动作（置顶、撤回 / 删消息、改群）需主人触发，任意 API
  直通与删消息按次走会话权限档。伙伴主任务（主人私聊落点）与桌面共用、不带专线的 chat 字段，改由
  `botProfileRuntime` 按该伙伴**绑了哪些渠道**写 `cindyBotImChannels` 标记并强制挂载对应工具
  （`shared/botImConnection.ts` 的 `hasImChannelVendorOptions` 是三个 Harness 共用的判定：Claude Code 走
  provider `isEnabled`，Codex 走 `buildSessionMcpConfig` 逐线程 `enabled`，Pi 走 `capabilityGated`；Codex /
  Pi 的共享 bridge 在空 ctx 阶段必须先注册该 server，否则永远挂不上）。桌面轮次没有作用域租约，
  **轮次内原生 API** fail closed；飞书 `send_message_to_user` / `send_file_to_user` 的主人通知是例外：
  canonical 主任务的桌面或后台轮次可由宿主查询当前账号的伙伴归属，仅在伙伴 Profile 为 `active`
  时经其已连接、已认主的飞书连接发送给主人，不生成租约、不扩大原生 API 权限。
  伙伴连接不可用、账号边界 pending 或 owner
  代次变化时拒绝发送，不回落个人 bot；完整路由与检查边界见
  [`im-turn-flow.md` §2](../dev-rules/im-turn-flow.md#2-状态清单)（含实现及回归链接）。
  绑定或解绑渠道后主任务的工具面在下一次会话启动时更新。
- **IM 专线与主任务是同一个伙伴，专线不丢伙伴能力**（2026-10-17）。专线轮次可以用
  `save_teammate_skill` / `list_teammate_skills` 把学到的做法沉淀成这个伙伴自己的技能，提示词里的
  技能指引同样注入专线；写入只认主人触发的轮次（`botSkillService` 读逐轮渠道作用域租约判定，其他成员
  触发返回 `BOT_SKILL_OWNER_ONLY`，没有租约返回 `BOT_SESSION_READ_ONLY`），读技能表专线任何一轮都行。
  记忆写入本来就按伙伴记忆范围落盘，不受专线影响。伙伴消息、例行任务、创建伙伴与伙伴模式仍只在主任务
  开放（它们需要主人在主任务里确认的交互面），专线上这些请求由伙伴说明去主任务 / 桌面处理。
- 伙伴保留自己的身份、记忆与 Skill 上下文，不加载项目或全局 `AGENTS.md` / `CLAUDE.md` 替代人格。
  这不限制工具能力：Pi / Claude Code / Codex 的原生子 Agent 与普通任务相同；Orca 也不因伙伴身份禁用，
  仍遵循用户的全局开关、当前引擎支持与权限档。持久后台工作仍可使用 Cindy Session 任务（见 6.1）。
- 伙伴主动为用户积累记忆，不以用户明确要求为前提：清晰稳定的偏好、纠正与长期背景第一次出现就记。
  技能收敛（主人 2026-10-23 裁决）：对话中只在主人明确要求把做法记成技能、或纠正已有技能时当场保存；
  其余由内置「夜间学习」回看对话，同类事在不同对话里反复出现才转正为技能，一次性事故、代码事实和临时路径不存。
  写入前去重，写入后可见、可编辑、可删除；尊重记忆开关和不保存要求，不记流水账或臆造流程。
  对话中的学习只使用现有工具，不在成功回复后另起宿主辅助模型复盘；夜间学习只读上次整理之后的对话，
  不补读建档之前的整段历史（见 `bot-routines.md`「内置夜间学习例行任务」）。
  真实保存回执持久附在来源伙伴发言气泡底部：脑子和书本两行分别表示记忆与技能，禁止放在任何
  发言气泡上方、独立插入时间线、标注“上一轮”或新建成功详情 UI。提前写入等待对应回复，
  迟到写入只补原回复。桌面点击分别打开现有伙伴设置的记忆页和能力页；手机复用伙伴设置面板。
  保存 Skill 后请求主任务在安全轮次边界刷新，不打断运行中的工作或授权卡；同一个聊天继续使用新技能。
  主任务、私聊话题和 IM 专线在下一次发送前比较共享记忆目录与自有 Skill 更新版本，变化时沿用安全刷新，
  因此在一个话题学到的内容也能进入已有的其他聊天；不把每个话题的完整消息历史合并进主聊天。
  桌面伙伴设置的「记忆」页承载这一承诺：同页开关记忆（关闭后已存记忆仍可查看、删除）；开关下方有与手机同义的
  「关于我的记忆」文本框（`userContextSource`），本机与远程设置目标都随设置自动保存；
  按关于你 / 你的要求 / 项目 / 参考分组列出标题与正文开头，搜索复用记忆检索，内部 `digest` 不展示；
  详情显示全文，编辑自动保存，单条标题与正文沿用存储上限。改正文时摘要按正文首句确定性刷新，
  不调用模型。保存与删除前核对打开时的更新时间，伙伴期间改过则不覆盖，由用户选择最新内容或
  保留自己的修改；改动合并后请求主任务在安全边界刷新记忆目录。
  手机（iOS 与 Android）与桌面设备互联控制端读写伙伴所在电脑的同一份记忆：「记忆」页保留开关与
  「关于我的记忆」表单，主机提供「已存记忆」页面时在下方进入，同样按四类分组显示条数、标题、正文开头与
  日期，并用同一记忆检索搜索；详情显示全文与类别、更新时间。手机编辑在点「完成」或返回、关闭时保存，
  不逐字自动保存，标题与正文沿用同样上限；删除经系统确认，文案带伙伴名与记忆标题。保存与删除前先复读，
  更新时间变了就不覆盖、不删除：编辑时由用户选「用最新内容」或「保留我的修改」，删除时先展示最新内容。
  远程读写与本机设置页共用同一个记忆服务实例，内部 `digest`、摘要与文件路径不离开主机；主机未提供
  该页面时，手机显示原有升级提示。实现见 Mobile `CompanionMemoryPage` 与 Desktop `botRemoteMemory.ts`。

### 6.1 后台任务与伙伴消息：两条边界，不做混合 action

模型可见入口按用户心智分开，不能再靠一个可选 Bot id 猜目标：

- `start_session_task`：创建一条真正独立运行的 Cindy 任务。它出现在用户主任务列表里，拥有
  完整 Cindy 能力面；用户明确要求独立任务，或工作确实需要独立执行时使用（判断依据见下文）。
  它没有 `target_bot_id`，也绝不以名为 Cindy 的伙伴代替。
- `send_to_agent`：给 `target_id` 指定的伙伴发送一条异步消息。它不建立任务，也没有进度、
  停止或自动交付合同；对方可以在自己的正常 turn 里处理，并通过反向消息回答。
- `check_session_task`：按 `task_id` 读取一条后台任务的实时状态，只在用户追问或自动回传疑似
  丢失时使用，不作为轮询机制。
- `message_session_task`：按 `task_id` 给同一任务追加或修正要求；`mode=queue`（默认）在忙碌时
  排到下一轮，`mode=steer` 只使用运行中引擎的 same-turn 插话，不支持或旧轮已结束时明确失败，
  不偷偷降级排队。`mode=resume` 解除可恢复暂停，可附新指令；不重放原请求或已完成操作。
  它也负责回答等待的权限、提问或计划确认；暂停时先恢复再回答，不为补充一句话重复建任务。
  已结束任务的续接保留稳定的原始目标，本轮补充独立持久化并按原队列顺序投递；不得把旧完整
  objective、历史结果和旧补充递归拼成新目标。上下文保留完整原目标与本轮补充，不用整体尾部截断
  裁掉最新要求；旧补充和执行结果读取原任务历史。重启恢复沿用本轮输入与执行回执，只续做未完成部分。
  旧版嵌套记录仅在下一次明确续接时，从同一任务未清除、未回退的初始输入恢复原目标；缺失时保留
  旧数据并明确让执行者核对历史，不解析用户正文分隔符猜目标，不批量重写消息或数据库。
- `stop_session_task`：`mode=cancel`（默认）终止任务；`mode=request-stop` 只请求当前轮优雅停止，
  不承诺冻结下一轮；`mode=pause` 持久暂停同一执行任务，保留未消费输入与剩余执行期限。
  `control.state=pausing` 或 `stop_status=requested/unconfirmed` 不表示引擎已停；活跃执行仍在
  等工具或确认时如实报告，确认空闲才返回 `paused`。等待中的交互保持原 resolver，恢复后才允许推进引擎。
  交互迁移到 IM 后仍受同一暂停与取消边界约束；暂停期间收到的渠道回答或安全超时决定暂存，
  恢复后只生效一次，取消优先撤销暂存回答。恢复依据宿主实际应用回执清理等待状态，
  已应用的回答不再通知发起伙伴；确实未答的交互仍重新通知。渠道卡片的回答状态不表示引擎已恢复。
  这些模式都只作用于调用伙伴拥有的后台任务。本机伙伴主任务另外拿到和普通任务同一套通用 Session
  工具，沿用当前 Agent 的权限档，见 6.4；任务写工具按 [伙伴操作权限](teammate-authority.md) 分开核验来源、访问范围和操作风险。
  主人通过工作台交给伙伴的项目里的原有任务，另走 6.3 的工作台工具，不经过这些后台任务入口。
  伙伴可以登记、列出、重命名和隐藏账号项目，也可以把已有的非伙伴任务移入或移出项目。
  移动任务先用 `list_sessions` 找到 session id，再走普通任务的移动规则；SSH 任务仍受该传输的能力范围约束。
  群专线、历史等伙伴非主任务与远程伙伴仍不包含停止、插话、改运行时、改名、归档、标签或读取其他任务的
  历史与输入队列；本机伙伴主任务按 6.4 获得这些能力。
  `check_session_task.control.last_stop_request` 保留最近一次优雅停止请求的时间、返回状态和轮次；
  它是历史回执，实际是否停稳仍看 `stop_status`，重启不会重放停止请求或冻结下一轮。

伙伴按实际执行需要选择工作方式：

- 优先在当前对话完成能清楚收口的工作：查状态、读少量代码或文档、解释已有结果、简单修改
  或制作文件。涉及仓库、多个文件、工具或产物，本身不是开独立任务的理由。
- 用户明确要求独立任务，或工作确实需要独立持续执行、隔离工作区、并行交付或独立跟踪时，
  使用 `start_session_task`。不设任意分钟数、文件数或评分门槛，不增加积极性开关。
  符合条件就直接执行，不为开任务本身再次请示；用户要求在当前对话完成时尊重该要求，
  真实缺少目标、材料或操作授权才询问。
- 进行中出现上述独立执行需要时再转交；交接带上目标、约束、相关文件、已知事实、已完成操作与
  验收要求。独立任务不自动继承聊天历史，不得重复已有副作用，也不以联系伙伴代替开任务。
- 伙伴仍负责最终交付：运行中不重复执行相同工作，结果返回后核对，补充和缺项跟进同一任务，
  再以原伙伴身份回报。委派能力未挂载时不得承诺已开任务。

默认系统指引、共享 teammate-guide、helper 工具说明与 Pi 桥接保持同一判断边界。
新模板只用于新建伙伴，不回写已有 SOUL、system_prompt、身份或记忆；旧默认身份指纹仅用于识别。
实现与回归见 `botSystemPrompt.ts` / `botSystemPrompt.test.ts`、`teammateGuide.ts` /
`botProfileRuntime.test.ts`、`lizi_xdtHelperMcpServer.test.ts` 与 Pi `cindyBridgeSource.test.ts`。

Session 任务遵守同一套机制与呈现契约：

- **统一状态机**：`queued → running ⇄ waiting → completed | failed | cancelled`。`waiting`
  表示子任务正在等权限、答案、计划确认或显式恢复；显式暂停另有持久控制标记，
  `check_session_task` 返回 `control` 区分暂停与交互等待，不把它们误报成执行超时。
- **执行结束与归档分离**：`completed` 只表示本次委派执行正常返回，不证明用户目标已全部
  完成；等待 CI、后台测试或外部反馈不等于归档。独立任务在正常返回、失败、超时或取消后
  保留原 Session 的可见状态；正常返回不关闭运行句柄或后台工作，取消与超时仍停止执行。
  归档／删除沿用用户显式操作，不依据 PR 是否存在或 GitHub 状态自动决定。
  `check_session_task.session_status` 单独返回实际 Session 的 active／archived／deleted 状态，
  与执行 `status`、暂停／取消 `control` 分别解读；终态恢复只补投回执，不重跑已结束执行。
- **显式暂停恢复**：暂停先锁住输入，旧轮终态不交付完成回执；重启只恢复锁，不自动执行。
  恢复保留同一任务 ID、执行 Session 和历史，有队列先消费队列，无队列才投一次去重续接指令。
  旧轮停止未确认时拒绝恢复，禁止与迟到中断竞争；计时只补回实际等待时长。
  续接输入先在暂停锁内持久入队，恢复状态提交并确认后才释放输入。提交失败保留原队列和暂停；
  提交已成功但回执不明时回读确认，仍无法确认则保持锁并报告 `resuming`，显式重试或宿主恢复
  只完成释放，不再投递新指令。相同恢复请求复用回执；不同补充内容须作为新的消息发送。
- **等待恢复**：等待事项的人话摘要、请求标识和开始时间随任务行持久化；Host 重启后先保持
  `waiting` 与暂停计时，子任务恢复成功才回到 `running`。旧进程的 resolver 不可复用，恢复的
  子任务仍需要决定时必须重新发出 interaction request，不能让一个失效按钮假装批准成功。
- **代理交互**：子任务进入 `waiting` 时先唤回发起伙伴。它能根据用户已表达的意图安全回答就
  直接用 `message_session_task` 回答；拿不准才在原对话问用户一句。用户不需要跳到子任务找弹窗。
- **代理恢复选择**：发起伙伴可通过任务专属公共工具查看该任务的当前路由及其下一条已配置候选；
  只在本轮执行结束后由伙伴明确选择切换。切换不自动重放工作；伙伴结合原目标和已完成动作，
  再决定是否向同一任务发补充消息。未配置的供应商或型号不可擅自加入候选。
- **任务入口（2026-10-15 改为一张卡）**：Desktop 发起方消息流里，一条后台任务从开始到结束只有一张状态卡（`BotTaskCard`），状态原地变化，不再是下划线文本链接加独立结果卡。卡的第一行是状态字形（排队／运行转圈、等确认蓝点、完成绿点、失败红点）、任务标题（点击进入原任务）与「后台任务 · 引擎 · 用时」；第二行按状态写当前动作与已做时长、等你确认什么、结果摘要或错误；操作收成小胶囊：看看／看过程、补一句（运行中、本机任务才有；回车发送，等同 `message_session_task`）、文件数、PR 状态标、展开／收起结果、停止。标题与 harness 读取同一个 Session；运行状态来自原任务的真实运行信号，不从委派终态推断事项完成。远端伙伴的卡只读。Mobile 保留既有任务卡布局，查询与打开使用消息列表已解析的所属电脑；标题、运行和等待信号复用普通任务列表的原 Session，列表外任务按原 ID 单条补读。委派读取失败不抹去已知任务状态或禁止进入原任务，无法核实的状态仍显示未知；不同电脑的同 ID 记录不得混用。冻结结果不随续跑改写，存储与绑定合同不变。
  **同一个后台任务只有一张脸**：通知、聊天里的卡片与主侧栏进入伙伴开的后台任务都走工程视图 `/cc-agent/:id`（diff、模型选择照常），顶部多一枚「<伙伴> 的后台任务」小标回到该伙伴（只认伙伴自己发起的委派子任务，主人的任务被伙伴接手只有侧栏「在跟进」标记；后台任务归档后从近况的输出内容或聊天卡片打开仍带这枚小标；结果里的相对链接按该后台任务自己的工作目录解析，不按伙伴主任务目录）；伙伴主聊天入口保留 `/bots/:id`；查看原任务时统一普通任务页，归档历史、IM 和群专线也一样。路由由 `botRouteForOwnedSession` 统一给出，`resolveSessionRoute` 只读已加载的伙伴投影、不等 IPC。
- **执行结果入口**：Desktop 的冻结结果用同一张后台任务卡呈现（附在收尾回复下时结果默认展开，独立回执默认收起）；完成结果属于伙伴收尾回复末尾的紧凑附件，正文先读，卡片与该条回复同列、同一容器归属。宿主以本轮实际消费的完成信号绑定冻结结果，成功收尾后随回复持久保存；同轮多结果分别附上，不按相邻消息、时间或正文猜配，不把所有卡移到时间线末尾。忙时尚未消费的队列不参与当前回复；每个结果还必须有该完成输入持久化之后生成的新正文，旧正文延迟落库、同毫秒无法确认顺序或输入记录缺失时保留独立入口。重复信号不重复绑定，续跑按执行代次保留独立结果。
  原任务卡和消息顺序不变。结果先按既有机制独立持久化；没有最终正文、失败或中断、关联读取失败、旧记录没有关联、或仅加载到原回执时，保留独立结果入口，不伪造总结、不改用户历史库。关联回复加载后，其对应独立回执只在伙伴展示投影中收起。旧客户端忽略新增的可选 `botTaskResults`，继续显示独立回执。新回执保存当次子任务标题；旧回执只读回退到已有任务标题，再回退到目标首行。附件冻结的状态、正文、文件与错误不从当前任务覆盖。普通任务、执行调度与自动化静默不改变。
  Desktop 流式展示透传 provider 的 `final_answer` phase，首个 final delta 即可见；commentary 继续隐藏。未知 phase 不凭文本猜测，仍遵守既有收尾兜底。未绑定的新回执在当前流式期间不插队，结束且无对应正文时保留轻入口；不靠模型编造任务 URL。
  实现见 `botTaskReplyResults.ts`、`botConversationPresentation.ts` 与 Mobile `companionConversationPresentation.ts`。
- **补充消息留痕**：`message_session_task` 的完整指令继续投递并保存在后台任务，主聊天的发送留痕只显示简短状态加首行摘要（`interjectionPreview`，≤ 200 字，只取第一个非空行）：「已告诉后台任务：「…」」。
  桌面与手机的实时、历史展示都按结构化标记投影；旧记录没有摘要字段，留痕回退为通用文案，不删改旧记录，正常用户内容、授权和提问继续保留。
  此约束针对自动生成的发送留痕，不改变用户主动展开工具活动时查看原始调用参数的能力。
- **完成信号**：子任务完成（或失败 / 超时 / 取消）时，发起方收到一条**用户不可见**的内部
  指令（synthetic-trigger 隐藏行），据此接手继续工作；用户看到的终态由任务卡承载，时间线
  里不得出现机读文本或内部 id。
- **可靠送达**：任务终态与“完成信号尚未送达”一起持久化；只有当前发起方主任务接受后才记为
  已送达。临时失败指数退避，Host 重启后重投未送达终态，固定 client id 保证重复投递不产生
  第二条消息。宿主依据持久委派投递完成回执，不继承启动工具调用的临时授权上下文；父轮结束
  不使结果回传失效，普通工具操作的授权校验保持不变。
- **固定返回位置**（2026-10-30）：专用任务与普通新建任务入口均在首次执行前保存来源。伙伴私聊发起回原私聊，群聊外层发起回外层，话题发起回原话题。执行电脑、续接入口与跟进者不修改这个来源。原位置无法投递时保留结果，并在任务内显示失败；不会回退私聊。普通任务的最终交付按账号落盘并幂等重试，删除任务同时清理其投递记录。
- **完成只唤醒一次**：内置跟进消费 `finished` 前，等待在途结算，按事件中保存的原执行身份核验持久终态回执归属。
  同一执行已有创建来源的专属回执时（包括已结算但投递重试中），不论当前跟进伙伴是谁，都不再为此启动内置跟进；
  结算或读取失败时保留批次待重试；本机保留失败结算的原参数，由同一批次重试该执行，不借后续执行补记旧结果；仅接受输入或仅写入终态快照尚不算完成送达责任成立。原轮执行身份也保存在冻结结果里，Host 重启或子任务续跑不改用当前执行判断旧事件。旧事件缺少执行身份时保留原跟进，不猜归属。
  完成事件仍保留供用户自建规则使用；结果、文件和可靠重试仍由原回执链交付。手动接手但无回执的任务、用户另起的执行及卡住／失败／待确认跟进保持原行为。
- **不静默丢失**：仅原本来自伙伴主私聊的专用任务，在该私聊的底层 Session 被异常恢复流程
  替换时，继续投递同一伙伴主私聊的 canonical Session；群聊与话题不走此恢复路径。
  伙伴本身已暂停 / 归档则暂缓投递，此时卡片终态仍然可见，完成信号
  保持未送达且不轮询重试，伙伴恢复时补投一次（实现见 `botDelegationService.ts` 的
  `resumeCompletionDelivery`）。
- Session 任务只创建一层子任务，受并发上限约束；超时是持久化的执行边界。默认执行预算
  30 分钟，创建时 `timeout_ms` 可指定至 24 小时；终态续接从新的开始时间按原预算计算，
  普通补充不延长正在运行的期限。没有 Host 回读证据不得声称已延长。
- 新建独立任务省略 `project_path` 继承来源归属，传路径选择已有项目，传 `null` 明确不绑项目；
  无法确定来源归属时明确失败。新增或恢复项目显式走 `create_project`。
  `working_dir` 只决定执行位置，缺省为所选或继承的项目；不绑项目则分配独立托管目录。
  不绑项目且启用 `use_worktree` 时必须显式指定执行目录。临时目录和 worktree
  不登记项目，复制或续跑保留 `projectDir`。可用 `use_worktree=true` 在启动前复用现有 worktree 管理器
  完成独立分支、目录与 Session 绑定；失败不得落回共享目录。只在 Shell 中新建 worktree
  不会修改任务登记或运行时 cwd；`check_session_task` 返回实际登记目录与项目归属。
  终态续接复用原 Session、完整历史、目录和分支，worktree 归属不迁移；每轮有独立的
  投递与完成回执，重试不重放上一轮。终态事件携带原 Session 实例与执行代次，旧轮迟到事件
  不得结算新轮。受理时将执行身份持久绑定至委派轮次，结果读取后仍按该回执原子收口，
  不以已变化的当前执行替代原回执；结束前已排队的补充在受理后更新回执。
  首次取消、请求停止及暂停须在 Session 执行锁内核验持久回执；身份不符时只收口旧委派
  并撤销其队列，不停止新执行。超时与取消的清理及重试也以保存的回执核对身份，不能中止用户从任务列表
  直接开启的新执行；没有原生实例时仍须撤销该委派的排队输入，不清除无关输入。
  本轮无 assistant 消息且终态无文本时结果保持为空，不复用前轮答复。
  自动重试、连续重试及冷恢复保留稳定输入来源；该来源独立于用于隐藏旧用户消息的替代标记，
  队列编辑、终态扫描与清理均不得丢失。重试受理须核对本轮已受理输入凭据后再更新执行身份。
  只将委派自身投递的队列项视为续接；普通直接输入不延后委派结果，也不改写其执行身份。
  数据库异常不等于身份校验拒绝：须保留原终态回执与输入归属供重试重新核验，
  不能缓存失败 Promise 使后续重试永久失败；身份不符的拒绝仍不可绕过。
  终态须先通过持久轮次与执行回执核验，才能登记这些续接项；第一次异步读取前登记
  可等待的校验，队列受理须等校验结束，不能抢在边界就绪前派发。自有输入校验未通过且
  无已验证边界时须拒绝派发，重复受理不得绕过拒绝；普通输入不受此限制。结算持有任务操作锁时
  还须核对实时自有队列，不能遗漏终态快照之后收到的补充；受理回执更新未命中须拒绝派发。
  消息已落库而启动轮次尚无受理回执时，恢复须以持久重试身份重新派发，保留原消息；
  条件更新须保护并发受理与轮次，不重投已有本轮回执的执行。
  消息幂等命中不属于原生受理，不重新采样当前执行或覆盖已存回执。start／restart／unpause
  的独立受理不由前序直接终态批准或拒绝；其自身原生受理仍须持久绑定执行身份。
  空快照后的迟到补充也须在派发入口核验：既无已验证边界、又无本次派发的持久回执时拒绝，
  不能因旧终态已被忽略或内存校验记录不存在而放行。
  排队续接的受理回执提交成功且宿主确认实际派发后才释放衔接记录；受理后未派发须保留
  重试更新回执的依据。冷恢复队列先于委派恢复被用户放行时，受理入口按宿主快照来源
  与持久委派身份补建衔接，不得无回执派发。编辑、整条替换及合并保留原条目的恢复来源，
  不因对象替换丢失，也不由调用方补造。写入失败或条件更新未命中须拒绝派发，
  保留重试依据。重启时先恢复委派自有排队输入，存在补充时先续接，不能先回放旧终态；
  无此输入才按已保存的终态回执与委派执行身份补交结果；该已完成结果的回放优先于恢复时
  的超时判断，未完成执行与排队补充仍遵守原截止时间。只有 Session 级
  时间戳而无轮次证据时，先恢复委派自有的排队补充并登记衔接回执；无此输入才保留未决，
  不拿后续直接执行的答复结算或重放已结束工作。
  已归档但未删除的 Session 可补交已验证的持久终态（须无待处理委派输入），仅投递结果，
  不恢复 active、不启动执行；缺失或已删除的 Session 不走这条结果回放。
  已归档或删除的 Session 不因伙伴补充、回调或重启
  自动恢复或创建替身；旧版自动归档的记录也须经显式恢复后才能续接。
- 补充输入返回 `queued_message_id`；`check_session_task` 返回调用 Session 自己投递的队列，
  可按消息 ID 查询 queued / consuming / dispatched / not-found / unavailable。队列恢复失败时
  保留任务状态和结果，单独返回 `queue_error=QUEUE_UNAVAILABLE`；无法核实的消息不能报 not-found。
  dispatched 仅指宿主历史接受，
  不证明模型已执行要求。`message_session_task(mode=edit/withdraw)` 复用共享队列的发送方与
  消费竞态校验；不得改他人输入，consuming 不能编辑撤回，缺失不能假称已消费。
- `mode=steer` 的 `idempotency_key` 在同一调用 Session、同一后台任务内生成稳定消息 ID，
  复用输入协调器去重；已落库的回执在运行时重建后仍可查询，不把旧插话重新注入新轮。
  原生接受后的落库失败依赖协调器的有界近期去重窗口；进程崩溃且回执未落库时不能保证恰好一次。
- 取消复用界面停止的输入协调器，清除未派发队列与自动续接。持久取消标记阻止再次投递；
  `cancelling/unconfirmed` 不是已停，原生终态或状态回读确认空闲后才收口为 cancelled。
  超时终态也必须检查旧引擎是否已停，仍活跃时不得通过续接启动第二份执行。

委派子任务向发起伙伴发送文件分工等内部协调时，使用 `send_to_session` 的协调用途，
其默认识别、来源核验、通知静默和历史兼容遵守 [message-source.md](message-source.md#委派任务的内部协调)。
原始输入隐藏，但伙伴处理后的进度与结果按普通助手消息显示、保存，最终答复后折叠过程。
本轮结束不等待后台任务完成，也不阻止用户继续发消息；运行中排队／插话、结束后开始新轮的规则不变。
正常完成结果、必要交互与错误继续保留；普通任务来信和明确 `user-visible` 的输入显示规则不变。

`send_to_agent` 是另一条更轻的伙伴间通讯通道，不得伪装成任务：

- `list_agents` 按需读取本机名册和同账号已授权设备的 Remote Resource 名册；远程目标用
  `deviceId::botId` 稳定寻址，同名通过设备区分。离线、控制关闭、撤权和目录不可用单独返回，
  不把不完整发现解释成没有伙伴。旧端的伙伴资源和主聊天链接继续可发现，不以缺少新 action 拒绝通信。
- 新版间跨设备发送和回复复用 device-link 授权隧道、canonical Session 投递和私信记录；接收端从
  relay 盖章的来源设备反查伙伴，并核实来源 canonical 主任务已保存匹配的发送记录；
  不接受消息正文自报设备身份或仅凭伙伴 ID 冒充发送者。双方设备都必须具备既有控制授权。
  两端分别保留本机私信线程及时间线入口，远端 Session ID 不写成本地外键。
- 发送回执分别返回 `accepted`、`delivered`；排队仅表示接受，不证明送达引擎或回复。
  `replied: false` 表示该发送回执没有回复证据；实际反向消息或明确标注来源的普通聊天回复才构成回复证据。
  超时返回 `DELIVERY_UNKNOWN` 并保留消息 ID 与预算，不自动重发或把未知投递退款。
  原生消息可用 `check_agent_message` 按原消息 ID 只读对账；仅确认为已接受时修复发送方记录和入口，
  不推断引擎送达或回复，不重发。未找到回执保留未知与预算；预算受既有 15 分钟线程空闲到期及
  5 分钟上限冷却约束，不跨新线程累计。并发名册发现只共享同账号在途读取，完成后即失效。
  跨设备持久消息 ID 去重，网络等待期间不持有双方消息锁，允许双向同时发送。
- 对已发布旧端缺少伙伴私信 action 的情况，使用资源返回的实际 conversation 链接，
  经既有 `maker:send` 发送明确标注来源的伙伴消息。不得伪造用户、canonical 身份或 origin；
  旧端只认证控制设备，正文说明伙伴身份由发送端提供，不具有额外授权效力。
  不使用会解除恢复暂停的显式用户入队入口；忙碌、暂停、缺失和撤权沿用旧端拒绝。
- 兼容发送返回 `transport=remote-conversation`。发送端保存远程主聊天 ID 与消息 ID，
  `check_agent_message` 只允许当前伙伴核查自身消息，按旧端 `around-client-id` 读取普通回复，
  遇到下一条输入即停止归因；主聊天被替换时明确返回变化，不猜新地址或跨聊天取回复。
  返回的是已保存的普通回复文本块，不表示旧端主动调用了跨设备工具，也不证明整轮完成。
  桥接回复在新版本地私信记录中明确标注来源并去重计数，不伪造旧端私信记录或自动唤醒新版新轮。
  回读需后续显式调用，不轮询、不因未知回执重发；此兼容路径不要求旧设备升级。
- 点名伙伴的简短询问、讨论与信息传递走 `send_to_agent`；开发、修改代码、制作网页或文档等
  需要独立交付和验证的工作走 `start_session_task`，不能把发消息伪装成后台任务。
- 每对伙伴同一时刻只有一条活跃的隐藏对话。正文单独持久化，不进入左侧伙伴列表，也不放进
  独立任务的工作过程；用户只能从双方主任务时间线里的消息痕迹打开只读对话。
- 每一条消息都在发送方与接收方当前 canonical Session 各留一个结构化入口。异常恢复后再次
  通讯时，新主任务也要有入口；旧历史入口继续可查。
- **入口的样子（2026-11-01）**：恢复轻量单行「发给 X」／「收到 X」入口；不铺摘要和操作卡。
  点击打开现有只读往来页，关闭后回到原主任务位置；本机与远程保留各自设备路由。手机沿用已有单行入口。
- 内部消息戳与 `bot-dm:` 触发的普通助手答复均不触发 `NEW`、伙伴列表未读或完成提醒。
  答复沿现有 `botPrivateReply` 持久化/广播边界处理，不进入主人聊天及云端镜像；双方显式发送的往来仍可从入口查看。
  主人直接发来的输入（包括插话）恢复正常回复；自动重试继承原 B2B 输入的内部归属。
- 接收方仍在自己的 canonical Session 执行，内部对话不是独立运行的 Session。已核实的主人请求
  及其交接授权保持不变，消息可见性不决定执行权限。审批、提问、执行错误与宿主恢复提示继续走原通道；
  不把普通内部完成当成需要主人处理的事件。发送方结束当前 turn，不进入常驻互相唤醒循环。
- 往来上限由宿主硬执行：一轮最多 12 条消息（6 次往返），同一方最多连续发 2 条；15 分钟无
  新消息即关闭。达到上限后关闭本轮并进入短暂冷却，双方必须先回到各自主任务整理结果，模型
  提示词不得绕过或重置计数。
- `create_teammate` 创建出的伙伴立即可以作为 `send_to_agent` 目标；canonical Session 可在
  第一次通讯时惰性建立。创建流程由主进程同时持久化第一句自然欢迎语；创建本身不暗中启动工作。

### 6.2 通知

- 伙伴主任务、它启动的 Session 任务和普通 Cindy 任务共用一条完成 / 失败 / 待回复通知链，
  不另存一套 Bot 专用通知开关。
- 已有委派执行回执的后台 Session 任务，只有同一原生执行轮次的结果已持久化并成功交回
  活跃发起伙伴时，才停止该执行任务独立的完成外部通知；随后由伙伴正常最终回复复用现有通知。
  回传失败、发起伙伴暂停/归档、审批、待答和错误保留原任务提醒。完成通知等待真实 `done`
  边界及该轮已启动的终态回传尝试；前置 `status: Done` 仍同步状态和未读，但不提前决定通知归属。
  本机各外部通道与活动中继共用该轮决定，远控 Desktop 的手机/飞书出口也消费执行宿主决定。
  不等待重试定时器；重复事件沿原通知去重账本消费，后续直接执行轮次恢复原语义。
  普通任务不因目录上的伙伴头像静音；任务正文、结果回执、状态、未读与 Dock 不变。
- 用户正在看对应任务时不发外部通知；后台时仍按全局桌面、飞书、移动端与灵动岛去重规则投递。
- B2B 单行入口及其普通内部答复不触发完成通知，包括 Windows 右下角系统弹窗、macOS 通知、
  iOS/Android 手机推送、飞书与灵动岛声音。静默状态随远程活动转发与重放保留，不能因已有旧未读再次提醒。
  主人直接交流的回复、审批、提问及执行错误保留原提醒。
- 自主跟进（6.3）：内置「跟进」例行任务那一轮的回复不自动外发（`silentWhenIdle`），伙伴要主人知道的事显式调用本轮
  通知，沿用例行任务的结果通知通道与开关。已纳入观察范围、但没人跟（跟进者暂停、跟进规则被暂停）的本机任务「等你」满 5 分钟时，
  宿主直接发一次系统提醒（桌面 `needs-reply` + 手机推送，事件 id 去重；主窗口在前台不弹桌面通知），不经模型。
- 通知、灵动岛、搜索和旧链接均保留原任务 ID、原电脑与已有消息锚点。只有唯一 `role=canonical` 链接
  对应的任务使用伙伴主任务页面；`kind=chat` 本身不是主任务判据。伙伴路由也携带具体任务 ID，不能因缓存
  过期而切到后来创建的主任务。历史、渠道、群专线与委派执行沿用普通任务页面及其权限、报错与历史加载。
- 旧 `/bots/:botId/session/:sessionId` 或 history 地址发现伙伴不存在、链接已过期或不再是主任务时，继续
  打开原任务的普通页面；路由不授予权限，仍经本机或指定远程电脑的访问检查。真实任务不存在或访问被拒绝
  时保留原地址，明确提示原因并提供任务列表出口；普通读取失败可以重试，不重建任务或上下文。
- 已读与灵动岛可见回执等原任务数据和消息实际加载后再处理，不能因 URL 已提交或进入错误页提前清提醒。
  系统通知点击复用主窗口深链队列，窗口重载时也保留任务、电脑和回复锚点；账号切换后旧通知点击失效，
  已排队但尚未交付的通知也在取出时复核原账号代次并丢弃过期项。
- 点击先使用现有伙伴投影；尚未认识的任务先开普通页面，并后台重读投影，仅发现它是主任务时校正页面。
  新点击、切换账号或用户已去别处都会取消较早的异步跳转，不能把用户拉回去。
- macOS 灵动岛把伙伴的主任务、历史任务、群专线与渠道任务显示为伙伴本人：名字与头像代替任务标题和
  Agent 标识，群专线在名字后附群名，不显示伙伴工作目录；回复完成时以消息样式呈现（头像跨两行、
  不标「完成」），运行中、待处理、报错与未读回复由头像上的光环和角标表示。委派执行仍是普通任务。
  伙伴改名或换头像后灵动岛立即更新；头像只在本机生成有界缩略图，读不到时回退底色加 emoji 或名字首字。
  主力电脑是另一台已远控电脑的伙伴，聊天活动同样出现在本机灵动岛（不受侧栏任务范围限制，头像经本机的伙伴
  头像副本读取），点击打开它在那台电脑上的聊天页。
- iOS 的伙伴正常回复使用系统通信通知：伙伴名字、头像与回复摘要，应用角标由系统绘制。
  普通任务、报错和待处理事项保留原通知语义。头像仅携带有界缩略图、内置头像标识或
  单个字符，不上传公开头像地址；缺失头像回退名字首字，扩展失败仍交付原通知。
  此展示依赖服务端透传发送者和 `mutable-content`、以及包含通知扩展的新版 iOS 安装包；
  旧服务端或旧安装包继续显示原通知，不因客户端单侧升级停止推送。

### 6.3 「一眼」、伙伴近况 + 自主跟进

2026-10-21 产品裁决：用户自己创建的任务默认不交给伙伴自动跟进。用户主动与 Cindy 对话后，界面邀请用户开启；明确选择前，不因任务事件调用伙伴模型读取、分析或汇报这些任务。开启后的行为沿用 2026-10-19 的 **自动检查，按授权行动**。
本节取代此前的「项目任务列表 / 右栏详情 / 点击跟进」形态，并撤销以下旧约束：Todo 段「不启动后台提醒、扫描或执行」、
事件预检段「不新建周期扫描或提醒定时器」「无唤醒不承诺后台实时运行」，以及工作台「远程任务不在范围内」。
代码入口：宿主观察层 `apps/desktop/src/main/bot-autonomy/`，契约 `apps/desktop/src/shared/botAutonomy.ts`。

#### 6.3.1 三层

- **层 0 宿主观察（程序级，不经模型）**：默认只观察明确委派或逐任务接手的本机任务；明确开启总调度后才观察本机全部任务。本机来源是灵动岛活动
  订阅（运行 / 等交互 / 完成 / 出错）、输入协调器投影（出错、撞上用量上限且宿主已排好自动继续）、挂起交互（等你的
  那句话）与数据库兜底（标题、隐藏 / 归档、启动时上一轮被打断的任务）。本机每 30 秒检查只在有待跟进的委派工作或已开启总调度时运行；没有需求则释放定时器，新委派和设置变化通过事件重新启动。启动归属读取失败可有限重试，有待处理事件时保留恢复机会。
  全局跟进关闭时，启动恢复也只查询明确委派的任务，不读无关任务的元数据和挂起交互。普通任务自身的通知链保持不变。
  归属变化读取失败时保留重试需求，成功后补入期间收到的活动；已选总调度的暂停只影响模型执行，不撤销观察与等待提醒。完成事件因规则未就绪或发布失败而未结清时，继续按原间隔重试事件，成功或任务移出范围后退出，不为此扩大状态扫描范围。
  完成事件结清（或该完成本就不发事件）后移除对应本机状态行，完成统计单独保留；不能依赖已停止的扫描清理旧行，避免去重过期后重发旧完成事件。
  远程只在显式读取总调度的「一眼」投影时，经既有授权后台只读链路读 `maker:list-active` v2，再按需读标题与挂起交互；没有常驻远程轮询。
  同时读取合并、每台电脑至少间隔 60 秒，失败按电脑指数退避（上限 15 分钟）；离线电脑的行保留最后状态并标离线，下次读取时清理超过 24 小时的离线行。手机不进查询目标。
  没有查看方时不读取；后台判断只读已有投影，不触发远程查询。
  既有 glance IPC 增加可选的第二参数 `refreshRemote`：省略仍按显式查看处理，`false` 只读投影；返回结构不变。新版查看旧 Host 仍发原 `[botId]`，后台探测的附加 `false` 由旧 Host 忽略并保持原缓存读取。
  不进表：伙伴的历史 / 群 / IM 渠道专线、隐藏或归档的任务、Orca worker、复核任务；
  伙伴的主任务（资料 `canonical_session_id` 或 canonical 链接）进表，但**永远不是该伙伴自己的事件对象**（不发
  stuck / waiting / errored / usage-limit / finished / sweep 给它自己——否则欢迎轮出错会把跟进排进正在失败的主任务里
  自己叫醒自己），也不进它自己「一眼」的等你 / 在做；总调度是另一个伙伴时照常收它的卡住 / 等你 / 出错 / 用量上限，
  以便发现别的伙伴的主任务坏了。主任务一轮回复做完不发 `finished`、不计入今天做完（每回一句话都叫醒总调度只是成本）。
  远程电脑上伙伴自己的任务也不进表。
  **每台电脑上的任务由那台电脑上的伙伴跟**：远程行只进「一眼」投影，跟进者恒为 null，不发布任何事件、
  不发系统提醒。原因：同账号的两台电脑各自运行一套伙伴（例如各有一个在用的 Cindy 助理），若远程行也发事件，两台电脑上
  的同名伙伴会把同一件任务各跟一遍、各推一遍。总调度经工具显式继续远程任务的能力保留（受工作台工具授权层约束；远程行不带创建者事实，「别的伙伴开的任务只读」这条边界不跨电脑生效——主人 2026-10-17 裁决，不为此扩设备互联协议），
  只是不会被远程任务的事件自动叫醒。
- **层 1 每个伙伴的被动跟进**：每个在用伙伴有一条内置「跟进」例行任务（见 bot-routines.md「内置跟进例行任务」），
  只对 `followerBotId` 是自己的事件被叫醒，先读任务摘要（`get_task_digest`），给出判断、建议并合并重要提醒。自动唤醒本身是观察信号；继续、代答、停止或换模型沿用普通任务的权限流程，不追加伙伴专属同意判定。
  没有定时叫醒：只有还有待处理任务时才会被条件兜底（6.3.3 的 `sweep`）叫醒。
- **层 2 唯一总调度伙伴**：账号内最多一个负责「跟进我的任务」的伙伴，未自定义时关闭，用户明确开启后才指定。它收本机全部无伙伴来源任务的事件、「一眼」看全设备全任务；别的伙伴开的任务默认只看不跟。
  每台电脑各自解析自己的总调度，各自只跟本机任务。

#### 6.3.2 谁来跟（`followerBotId`）

- 伙伴开的任务（委派来源，或明确接手的逐任务责任记录）由它自己跟。
- 它暂停、已不在或不是本机主力电脑（云端伙伴在别处运行）时，只有它在资料里打开「它开的任务也交给总调度跟」
  （`capabilities.allowSchedulerFollow`，缺省 false）才落到总调度，否则没人跟。
- 没有伙伴来源的本机任务（主人自己开的）由总调度跟。
- 共享给访客的任务（来源 `shared`）没人跟：里面有账号外的人发的话，不能借事件叫醒以主人权限运行的伙伴。它只进「一眼」投影，「等你」超过阈值时直接提醒主人；任务摘要不带对话原文（标 `shared_task`），工作台工具也不能继续它（`TASK_SHARED_WITH_GUESTS`）。
- 另一台电脑上的任务恒为 null：由那台电脑上的伙伴跟（见 6.3.1），这台电脑只放进「一眼」投影。
- 已纳入观察范围但没有可用跟进者时为 null：不叫醒任何伙伴；范围内的本机任务「等你」超过阈值时宿主直接发系统提醒
  （桌面通知 + 手机推送，主窗口在前台时不弹桌面通知），同一事件只提醒一次。跟进者的内置规则被主人暂停时同样处理。
- 设置「自动跟进所有任务」：账号级、只存 override（`bot-autonomy-settings.json` 的 `schedulerBotId`，显式 null = 关掉）；
  恢复默认 = 删除 override。目标伙伴必须存在且未归档；它被归档后关闭，不擅自转交其他伙伴。远程控制端设置时，目标还要对远程可见（未隐藏、未归档，与伙伴设置页其他操作同一判据；`autonomy.set` 虽是整机操作，宿主入口仍按它的 `schedulerBotId` 校验），否则按「伙伴不可用」拒绝，关闭（null）不受限。本机 IPC 仅可信界面使用；远程和手机经同账号的伙伴设置资源、绑定 owner/controller/revision 的动作修改。
  override 文件存在但读不出（损坏 / 超限 / 无权限）时失败关闭：按关掉处理并记一条警告，保持关闭且不再显示首次邀请；
  恢复默认会删掉坏文件。设置变化、伙伴新建 / 资料保存 / 暂停 / 恢复 / 归档都立即重算跟进者（不等 60 秒的定时重读）。

#### 自动跟进的邀请与设置（2026-10-21）

- 默认关闭同时适用于新用户和未写 override 的老用户；显式设置过开启、关闭或指定伙伴的用户保留原选择。恢复默认删除 override 并回到关闭。
- Desktop 本机、远程及手机的 Cindy 主聊天中，用户成功发送普通消息后，在空闲且没有待答交互时显示一次轻量邀请。打开页面、首次欢迎、恢复历史、后台事件和发送失败均不触发；不额外调用模型、不读取任务来生成邀请。
- 邀请说明将读取本机用户创建的任务摘要、分析进展并提醒重要变化，会消耗模型用量。点击「开始跟进」才写入 Cindy 为跟进伙伴；「暂不开启」写入显式关闭，后续不重复邀请。失败保留入口供重试。
- Desktop 本机伙伴设置 → 例行任务，以及手机/远程伙伴设置的「跟进我的任务」页显示「跟进我的任务」的状态、范围和用量说明；设置页开启同样先确认，关闭直接生效。用户明确交给伙伴的后台任务仍由该伙伴跟进，不因总调度关闭丢失委派结果。
- 手机和远程入口说明读取的是伙伴所在电脑的任务。沿用伙伴设置资源与既有确认组件；旧 Host 不支持新资源时不展示邀请，不猜测已开启。共享任务访客没有入口。
- 升级前已排队的内置跟进事件在模型派发前按当前选择重新筛选：关闭后剔除主人自建任务的事件及摘要，保留明确委派。状态表尚未就绪时延后，不根据旧事件里的跟进者决定权限。

#### 6.3.3 事件与阈值

宿主内置事件源 `host:sessions` 只为本机任务发六类事件（程序级判定，阈值是内部常量，不进设置；另一台电脑上的任务不发）：

| 事件 | 条件 |
| --- | --- |
| `stuck` | 运行中且 10 分钟没有任何活动；有前台工具调用在途（如一次长构建，期间没有活动事件）时放宽到 45 分钟 |
| `waiting` | 等权限 / 等回答满 5 分钟 |
| `errored` | 出错，或启动时发现上一轮被打断 |
| `usage-limit` | 撞上用量上限、宿主正在等重置后自动继续 |
| `finished` | 执行任务的模型用 `report_task_delivery` 明确报告本轮新交付了最终结果（如 PR 交付待人审、合并/关闭或目标已达成），且同一执行轮次正常结束时立即发出；中间评审修复、等 CI、重复状态通知和未报告的轮次不发。回执按当前任务及执行身份绑定，不跨轮次沿用，不依赖静默时长。主人点停止 / 中止的任务静默离表，不算做完、不发事件。自动化的运行任务不发，它有自己的结果通知 |
| `sweep` | 条件兜底：某跟进伙伴还有 ≥1 件等你 / 出错 / 用量上限 / 卡住的本机任务，且距它上次被叫醒（任一事件被它的规则接收）满 2 小时 |

- 去重：事件 id = `类型:任务:进入该状态的时刻`，同一状态只发一次；引擎另有 24 小时回执去重，重启后同一次状态不重发。
  启动时已经做完的任务没有可观察的跃迁，不补发。离线电脑的旧状态不发。
- 防打转：同一任务同一类事件 24 小时内最多 6 次，超出只记日志。事件数据带 `occurrence`（第几次），
  伙伴据此在反复卡住时停下并告诉主人，而不是继续推。
- 事件只带标题、等你的一句话（≤140 字，只取问题本身或权限名，不带工具入参、计划正文与代输入值）、出错摘要与分钟数。
- 条件兜底由宿主 30 秒扫描判定，不是定时触发：没有待处理任务的伙伴永远不会被白叫醒。`sweep` 按伙伴发，id =
  `sweep:伙伴:时间桶`（桶长 = 兜底间隔），`subject` 是伙伴 id，`followerBotId` 是该伙伴，任务相关字段为空串、`occurrence`
  为 1；同一时间桶只发一次，宿主启动视为刚叫醒过。伙伴被叫醒后用 `get_workbench` 逐件看自己的待处理任务。
  `sweep` 没人接（规则被暂停）时不发系统提醒，「等你」提醒仍由 `waiting` 事件负责。

#### 6.3.4 「一眼」投影与伙伴近况

**「一眼」投影**（`local-db:bots:autonomy:glance`，状态表变化节流 ≤1 次/秒推 `maker:bot-autonomy:changed`）只供伙伴工具
（`get_workbench`）与已授权的远程控制端读取：等你（等权限 / 等回答 / 出错，最久的在前）、在做（运行中与用量上限
等待中，最新开始的在前）、今天做完几件与离线电脑。范围：总调度伙伴看全设备全任务（远程行只看，不会叫醒任何伙伴）；
其它伙伴只看自己开的或明确接手的任务。「自动跟进所有任务」设置的原始 IPC 通道不开放给远程；桌面远程控制经伙伴设置主机（`management:settings`，由伙伴所在电脑执行）读写，与手机的「跟进我的任务」页同一份宿主设置。

**伙伴近况**（2026-10-21 Chris 定稿，取代右侧栏「工作台」标签；原型 `Designs/cindy/teammate-glance`）：伙伴聊天头部的
网格按钮打开一个浮层，沿用原浮层外壳，依次放电脑、待办、近期任务、输出内容，没有内容的块整块不出现（新伙伴只有「电脑」）。不再有「等你 / 在做」分组、
「允许」按钮和扫描时间页脚；等你处理的任务照常走任务列表、通知与任务内的确认卡。实现见
`apps/desktop/src/renderer/features/bots/BotGlancePopover.tsx`、`botGlanceTodos.ts`。

桌面设备状态放在同行，近期任务只显示任务标题与未读点，移除来源电脑副文案；单行最低 32px。
浮层随内容自然长高，以锚点到窗口边缘的可用空间为上限、保留 12px 边距，超出后滚动，不设固定 640px 高度上限。
手机同样减少设备与任务副信息的重复行，但保留至少 44pt 点击区域和原生 sheet 的半屏／展开交互。

- **电脑**：当前运行的电脑在最前（打勾），其余在线的可点；离线的收进「离线 N 台」。云端伙伴点另一台走主力电脑的
  原确认流程（cloud-companions.md §3.1），Cindy 的多台副本直接打开那台上的她；其它伙伴只显示它所在的那台。状态词用
  「在线 / 离线」。
- **待办**（2026-10-28 修订）：只列明确期限已过或未来 7 天内到期的未完成事项（到期在前），默认 2 条，更多原地展开。
  无期限旧想法、建议日期、待确认日期和已完成事项不在近况展示；没有符合项时整块收起，不保留「已完成 N」。
  这是桌面和手机共用的只读展示规则，不删除源记录、不补造期限，主人覆盖或清除期限仍优先。
  行内没有按钮：点一条就作为 Todo 引用放进
  输入框（`kind: 'todo'` 的 Composer 引用，带稳定 Todo ID），主人写一句话再发，由伙伴按话更新；右键只有「删除」，
  删除即同一问题不再记，可在提示里撤销。期限是今天或已过期的那条在期限前带红点；入口按钮在主人还没打开过近况时
  亮同样的红点，打开即灭，期限变化算一次新的到期（本机按伙伴记住看过的到期项）。别的电脑上的伙伴经该电脑的
  `todos:<botId>` 远程资源读写，与手机同一路径。
- **帮我查查 / 每天帮我查一次**（2026-10-28 修订）：成功读到空待办时整块收起；有待办时「帮我查查」
  只保留标题旁的小按钮，仍把原固定请求以主人消息交给伙伴。已开启的每天检查显示一行，× 调用原宿主入口停用，
  停用成功即移除；不常驻推荐开关。每天检查是一条可编辑的普通例行任务，开关只切换启停，不改主人或伙伴改过的指令
  （见 `bot-routines.md`「每天查待办例行任务」）。空块隐藏不影响已启用的例行任务；读取失败保留重试，不当成空结果。
  引用、删除及撤销原行为不变；已完成记录仍由现有待办工具读取。
- **近期任务**（2026-10-28）：复用任务列表的伙伴创建者归属（#7546），Cindy 跨电脑合并身份，
  其它伙伴保留既有本地或云端身份边界。只列独立任务，不把主对话、私聊、群主对话或单纯跟进的任务混进来。
  最近活动在前，先列 5 条、展开最多 30 条；点击走任务原路由并保留所属电脑。绿色未读点直接读取已有任务
  attention（Desktop done / Mobile completed + attention），不新增已读存储或同步、不从完成状态推断未读。

  单行显示可点击的真实 PR 标题，不常驻仓库编号或灰色副标题；标题尚未取得时以仓库名占位，不以任务标题兜底。状态图标与颜色沿用任务列表，未知时中性显示。
  PR 与文件混排为同一份产物列表，按现有记录时间倒序（PR 的 lastSeenAt，文件委派的 completedAt/updatedAt），
  合计预览 3 条，共用一个「显示更多」展开已读取的产物，不按类型分组或分别折叠。
  文件同样只显示图标与文件名，不常驻日期和来源任务副文案。PR 点击打开 GitHub，文件仍在本机打开，远程文件打开来源任务。

Host 在直接工具和渐进调用共用的执行入口核验身份与执行范围。

同意后继续当前调用，拒绝后停止；正本见 [伙伴操作权限](teammate-authority.md)。
helper 与 Orca 的写操作均使用同一逐次审批策略；Orca 的只读操作仍沿用可信查询策略。
权限只读运行中任务的稳定状态；从 Host 接收调用并捕获快照起，权限切换、计划模式、实例变化
使该调用的执行与排队投递失效。Agent 审批结束到进入 Host 之前的交接窗口沿用普通任务语义，
本次未增加跨 harness 审批凭证，不能把 Host 快照当作先前审批时的权限代次证明。
群成员、共享访客的工具范围不因权限档扩大；插件创建的任务按普通任务权限使用工具，账号与业务对象归属继续校验。
没有可核验的实时执行权限时，保留原有主人输入或委托范围校验，不凭角色放行。
放行后的调用仍绑定目标、正文与当前来源，供工作台、队列及新建 Session 委托核验，单次调用不可重放。
新建委托的 Host 来源记录仅允许控制该委托的当前运行；代答、恢复暂停和改路线按上述普通任务权限流程处理。
历史委托保留执行与结果，不从旧身份补造授权。关闭观察用的跟进规则不撤销主人已授予的委托；
暂停、撤销或结束该委托才收回对应执行权。普通 Orca Lead 收到自己当前 active team 的 Worker 回报时，
可继续该 team 的协作，不把 Worker 回报解释成向其它任务行动的授权。
新建委托在模型与工作区准备后、提交创建记录前复查同一行动授权；提交期间失效则沿用失败收口，
不启动子任务。Orca 复用既有生命周期与控制检查点保留来源授权，覆盖团队/Worker 准备、
排队接受及控制写入；`switch_focus` 会保存焦点并恢复空闲 Worker，也属于行动，不能当作只读观察。
授权撤销后不继续激活或派发，已有失败清理仍由原服务负责。
委托代答、暂停/停止、恢复与路线切换复用同一组 mutation 检查与回滚边界；主人输入
在等待期间被替换也会失效。已获准的暂停可以完成自己的暂停意图，但不能据此重新入场或恢复。
修改工作台责任也是写操作，沿用上述权限流程，不能仅凭自动观察信号扩大可见范围。
批量改名、归档/恢复和移动在异步读取、等待锁之后，写入或关闭空闲运行实例之前复查当前行动授权；
远程批量状态操作逐项调用前异步复查，并在既有 transport `preSend` 同步核对来源代次、
账号与群执行；连接等待不能延长已失效的来源。已完成的项保留回执，不因后续项被拒而伪造回滚。
排队消息保留 Host 校验闭包，实际投递前复查账号、来源任务及委托范围；序列化不保存授权。
主人通过可信本机或同账号控制端编辑排队消息后，以新正文重新绑定授权；访客或工具编辑不获得此授权。
无法复核的旧自动输入不恢复投递，已发送历史不改写为撤回。跨电脑见协议兼容文档的行动回执规则。

通知沿用事件 ID 与引擎回执去重；伙伴还应合并同轮判断，仅有重要新变化才通知，不重复原任务的完成回复、
用量重置续跑或其他已有自动跟进。长工具运行只是观察信号，不能据此停任务或重复续跑。
自动发现待办在写锁内记为 `discovered`，更新现有记录保留来源；不批量推断或改写历史分类。


- 被叫醒的伙伴用 `get_task_digest` 读摘要，`get_workbench` 读自己的「一眼」，`read_workbench_task` 摘要不够时读有界
  内容，`continue_workbench_task` 在独立行动授权通过后让任务接着做（别的伙伴开的任务默认由那位伙伴跟，总调度只能读），换模型、停止当前一轮、
  更新待办与通知主人沿用既有工具；工具边界以各工具说明与宿主校验为准。跟进这一轮的回复不会自动发给主人，要主人知道的事
  必须显式通知（内置规则开启 `silentWhenIdle`）。
- 换模型只照摘要的 `suggested_route` 做：伙伴代主人换模型没有用户确认，也不会先交接重建上下文，所以宿主只在换过去
  确实有用且装得下时给建议，否则为 null、由伙伴提醒主人（2026-10-19 用户反馈「伙伴把会话的模型切了，上下文直接满了」）。
  具体：只在出错 / 用量上限时给；出错的原因换到哪个模型都一样（工具循环、上下文超限、请求本身无效、内容被拒等，
  与供应商组 `decideProviderGroupFailure` 同一判定）或没有可判断的错误时不给；任务当前路线不在伙伴候选链里
  （主人自己选的模型，含同一模型换了明确不同的供应商）时不给，不退回链首；候选窗口比当前小、换过去用量会到 70%
  提醒线时跳过该候选。失败判定同时用运行时记下的本轮终态结构化字段（SDK 错误类型、HTTP 状态、Codex 错误 tag）；用量取
  运行时读数（会话已关闭时取关闭那一刻固化的值），没有有效运行时读数时不推荐更小窗口——库里的用量在中断 / 崩溃后可能
  低报；上一段运行时关闭时的读数仍作下限；运行时读数为 0（可能是 usage 回流前的占位）一律按未知处理。

  创建来源；损坏记录失败关闭，该伙伴不认领任何任务；账号切换时丢弃旧读取与写入；跨进程锁 + 原子替换，容量溢出明确拒绝。
  同目录、标题、最近消息都不是责任证据，不做回填。
- 侧栏「在跟进」标记只在任务 ID 对应可验证责任关系时显示伙伴头像；只认本机、在用、未隐藏的伙伴。
  手机任务列表（首页、电脑页）在标题行右侧用 16pt 伙伴头像表达同一关系，数据来自伙伴名册的 `following` 链接（见

#### 6.3.6 伙伴 Todo

Todo 是伙伴维护的事务清单：既包含用户交办，也允许从已授权信息中主动发现有行动价值的事项。项目、执行任务与 PR 都是可选关联。

实现使用伙伴目录下独立的 `todos.v1.json`，带稳定 id/key、乐观修订号与跨进程原子写入。旧工作台文件原样保留，旧 PR/issue/idea 条目按稳定 ID 兼容读取，新格式已保存后旧工具的更新仍会在读取时合并；保留用户期限覆盖、忽略决定和来源链接，旧描述更新不会撤销用户重新打开。普通 Session 判断继续属于任务元数据。新存储不静默淘汰完成历史；超容量明确拒绝。损坏文件失败关闭，不能用空列表覆盖。

`list_teammate_todos`、`update_teammate_todo` 是与任务调用并列的伙伴公共能力，调用者由本机在用伙伴主任务反查。更新是部分合并，旧来源/引用默认保留；已有记录必须带修订号，冲突重新读取。完成必须记录依据，重开保留历史。到期支持日期/确切时刻及来源时区，模糊日期先待确认，用户覆盖/清除不被新来源替换；来源版本仅在相同 sourceId 内比较，双方缺失 ID 时按同一旧版来源处理。到期优先按确切时刻排序，仅日期按来源时区当天结束参与排序，不保存虚构时刻；同一排序时刻沿创建时间/id稳定排序。稍后只暂缓呈现，不延长真实期限。已打开的列表按最近暂缓期限安排一次只读刷新，回到前台时复核；远程分页返回全清单的最近期限，不受当前页截断。Todo 本身不另起提醒定时器：后台跟进由 6.3.1 的内置「跟进」例行任务承担，伙伴被叫醒时更新对应待办。删除/不再提示保留同一问题的抑制记录，跨来源去重也遵守它，恢复不影响整个项目或来源。

Todo 在桌面与手机都只在伙伴近况（6.3.4）里展示，两端共享同一宿主记录。远程通过已有受信 device-link resource get/invoke 路径和账号/可见伙伴边界，不新增广域 IPC 权限。读取与写入回执只返回可展示的投影，不发送宿主目录、去重键、旧记录内部标识或模型执行指令；来源与关联在手机显示可读名称，来源引用保留 HTTPS 链接。旧客户端有只读文本回退；宿主单页最多 25 条，近况按页读完（每类最多 200 条）。

具体动作通过既有伙伴输入路径推进，接收/排队与真实开始/完成各自独立；入队成功只显示已收到，既有输入协调器确认实际派发或插话后才显示已接受。未派发的排队项被移除、Stop 或清空时，同条 Todo 记录失败并可重试；重复请求不重复投递，未知回执不能盲重试。重启或切回账号后，生命周期回执按当前账号的伙伴主任务与磁盘 requestId 重建关联；读取清单时核对既有持久队列和消息记录，仍排队/在途则等待，取消墓碑确认未执行则可重试，只有已落库文字而无派发证据则待核实。内存 prepare/enqueue 在途不被当作孤立回执，队列读取失败不推断取消。手机断连解除本地忙态与关闭保护，重连只重新读取、不重发操作，旧连接迟到结果不干扰新请求。邮件等来源正文不自动授予外发或费用授权，原授权流程仍适用。

待办的默认定义、工具用法与安全底线在系统技能 `todo` 的全文里（`read_teammate_skill` 按需读取，见 §6「伙伴技能分层」）；什么算待办、去哪些已授权来源查、怎么提醒以伙伴自己的记忆与技能为准，但不能覆盖授权与安全规则（2026-10-31 负责人裁决）。它要求对话变化、任务结果和已授权跟进维护同条；纯进度询问可读取，无变化不写。`preflight_teammate_todo_events` 先按职责、稳定来源游标、同问题 key 与忽略记录做确定性过滤，`record_teammate_todo_event` 原子提交成功处理结果。这些接口不提供全邮箱/飞书扫描器；任务层面的周期观察只由 6.3.1 的宿主状态表承担（程序级、不经模型），模型只在事件（含还有待处理任务时的 2 小时条件兜底 `sweep`）时被叫醒。失败不推进游标；预算沿用既有配置。

## 7. 实现红线

- 生命周期、fallback、所有权和重放判定必须在宿主代码中确定性实现，不能只写进 prompt。
- 不得把 Profile 的永久内容依赖于某个原生 Harness 运行句柄。
- 不得让上下文压缩或异常恢复丢历史、换目录或丢 Profile 版本。
- 不得向普通用户暴露运行时维护开关来代替自动恢复。
- 不得在 fallback 后重复可能已经成功的外部动作。
- 不得把 Bot Memory 注册成全局 Maker Memory 的一个普通 workdir，或让全局 Memory 设置控制它。
- 不得把 Home 根目录整体设为可写，或从 Home 内可写配置反向派生权限。
- Bot 表全部只增量；旧代码打开含 Bot 表的库时按既有 migration compatibility 守卫失败关闭，
  不得强行降级。
- 自主跟进的观察、阈值、去重、跟进者判定和「等你」系统提醒都是程序级；只有“本轮是否新交付最终结果”由执行任务的模型通过结构化回执判断，宿主校验当前任务、执行身份与正常结束，不将每轮结束当作最终交付。
- 伙伴之间不得无限互相触发：事件只按 `followerBotId` 叫醒一个伙伴；同一任务同一状态只发一次事件，同类事件
  24 小时最多 6 次；伙伴推任务产生的新状态仍受同一上限约束。不得为绕过上限给事件换 id 或重置计数。
- 「自动跟进所有任务」账号内唯一；不得让多个伙伴同时收全部任务事件。另一台电脑上的任务不得在本机发事件或系统提醒，
  否则两台电脑上的同名伙伴会各跟一遍。兜底叫醒必须以「还有待处理任务」为前提，不得改回无条件定时触发。观察层日志只记类别、计数与错误码，不记任务标题、
  问题或错误原文；代输入填写值不进入事件、摘要、日志与推送。

Codex 切模型重建时，线程索引里的路径不等于文件已经落盘。缺文件时仍保留原历史根与
数据库根，先用原生 `thread/read` 核实有无已存线程，再走 `thread/resume`；只有原生明确
没有线程元数据且无法找到 rollout，才在同一伙伴主任务内重建未开始的线程。
原生 `no rollout` 错误本身不能证明线程未开始：已有历史文件丢失时也会返回它。
已有线程元数据、读取异常或迟到落盘不得触发空白重建；不得换用旧副本，也不得重放已接受的输入。
实现见 `codex-thread-locations.ts` 与 Codex adapter；原生契约回归见
`packages/maker-core/src/agents/codex/app-server/external-auth.native.test.ts`。

## 8. 验收最低集

- 单模型旧 Profile 可无损读成一项链；新 Profile 可保存并恢复 1–5 项顺序。
- 首选不可用时只切到用户配置的下一项；成功后不继续尝试。
- 跨日、长期空闲、重复打开、伙伴消息和后台任务回传都保持同一 canonical Session；异常恢复
  的多窗口 CAS、旧历史归档和历史搜索有测试。
- canonical Session 能反查唯一 Bot；后台任务能反查发起任务，彼此上下文隔离。
- 压缩或异常恢复前后使用同一个 `<bot home>/workspace/`；不同 owner / Bot 的 Home 不串用。
- 关闭全局 Maker Memory 后 Bot Memory 仍可读写；全局列举与清空不包含 Bot Memory。
- 新伙伴及所有旧名单默认继承普通 Agent 已启用的工具集和 MCP；新版显式选择（包括空名单）不被覆盖。
  伙伴可按需发现插件；Bot-own Skill 始终可用。
  三个引擎均不得因伙伴身份禁用原生子 Agent；Orca 服从普通任务相同的全局设置。
- 后台任务承接 ask / auto / bypassPermissions 三档，权限变更中不读旧值；既有计划快照可恢复。
- 伙伴会话的上下文里没有项目 / 全局 AGENTS.md、CLAUDE.md 与 Cindy 产品提示词。
- `start_session_task` 能：任务卡实时更新到终态、挂起交互回到伙伴代答、完成唤醒信号对用户不可见；每次执行收口另存可展开的结果入口（按任务与执行轮次去重），历史原卡不移动。结果入口直接展示该次结果与文件，超时复用既有终态归一；当次失败原因随回执保存，桌面与手机仅在用户展开错误详情后显示，续跑不改写旧回执。忙时排队、过程收拢和重新打开不影响读取；阅读历史时沿用新消息提示，不强拉到底部。
  父任务异常恢复后仍投递到当前主任务；check / message / stop 都只能控制它创建的 Session 任务。
  伙伴负责的任务经 6.3 的工作台工具查看、继续；越权（不在负责范围、伙伴隐藏任务、非主任务调用、别的伙伴在跟）
  一律被宿主拒绝。
- 自主跟进：任务卡住 10 分钟 / 等你 5 分钟 / 出错 / 用量上限 / 模型报告最终交付且本轮正常结束时，只有跟进者的内置「跟进」规则被叫醒一次；
  例行任务引擎重建后 `host:sessions` 事件源重新登记；内置规则不能删除、不能改内容、只能暂停；没人跟的本机「等你」
  只提醒主人一次；「自动跟进所有任务」默认关闭，恢复默认删除 override 并回到关闭；无总调度、无待跟进委派时不起扫描定时器；
  总调度的「一眼」看全设备任务，其它伙伴只看自己开的或接手的任务；已授权的远程控制端读「一眼」时，与远程任务列表同一口径，隐藏 / 归档伙伴开的、它的主任务与它在跟的任务一律不返回；远程任务只进「一眼」、不叫醒伙伴也不提醒；没有待处理
  任务的伙伴不被兜底叫醒，有待处理任务时距上次叫醒满 2 小时才发一次 `sweep`；远程电脑按查看需求读取，失败退避且标离线，
  不形成重试风暴。
- 通用 session 工具及历史查询不再按伙伴来源分档；账号、实例、目标与队列归属检查保持有效。
- 伙伴主聊天通知优先使用当前已完成轮次的最终回复纯文本摘要；Markdown 转为可读文字后才截断，遵守推送协议的 UTF-16 长度上限且不拆分代理对。无可用正文时使用本地化新回复兜底；沿用通知开关及系统预览隐私，静默自动化仍不外发。普通任务保留任务通知语义。
- 完成信号临时失败与 Host 重启后会幂等补投；等待事项在重启恢复期间保持可见且不消耗执行期限。
- `send_to_agent` 的同一伙伴对最多 12 条、单方最多连续 2 条；达到上限和空闲超时都会结束本轮。
- 伙伴私聊不进左栏；双方 canonical 时间线都能打开同一份只读记录，接收方正常 turn 的结果
  仍留在自己的主时间线。
- 伙伴原生工具遵循普通任务权限，权限可正常切换；记忆与 Skill 通过专用接口保持一致。
- 设置页不再要求用户手动压缩、切 Session 或开关自动 fallback。

重启超时不等于底层关闭已取消。不可取消的旧关闭仍在执行时，当前伙伴的发送与再次重启必须立即返回仍在重启的错误，不能继续排队或由发送锁五分钟 watchdog 放行；只有旧操作实际收口后才解除保护，其他伙伴不受影响。路由返回和侧栏导航离开设置同样必须经过资料保存与例行任务草稿检查。

显式重启保留的未发送队列使用恢复型暂停：后台输入不能自动放行，下一次用户主动发送或点击继续可恢复 FIFO；已经派发的旧回合不能重放。伙伴设置显式选模的缩窗交接复用已核实窗口重试，缺窗口或窗口再次变化时不得猜测并反复重试。

## 9. 伙伴创建与共同基准

**维护入口：这里的共享基座变更对所有新旧 teammate 生效，不按名字或模板分支。**
`apps/desktop/src/main/maker-ipc/teammateGuide.ts` 生成预加载指南与受管 SKILL.md；
`packages/lizi-mcps/src/xdt-helper/bot_capabilities.ts` 定义共享控制说明与工具契约，
`apps/desktop/src/main/maker-ipc/botCapabilityService.ts` 连接实际设置服务。
新增共同能力须同时核对指南、工具注册、运行期挂载和实际服务；不得只改文案或给默认 Cindy 私装 Skill。
验收必须包含新伙伴和存量伙伴的原聊天，确认模型实际收到新版基座并调用对应工具；不能以文件存在或新伙伴成功代替旧伙伴升级验收。

- 首次使用伙伴时自动提供 Cindy（Desktop、device-link 和 Mobile 资源列表共用一次性供给）；
  进入伙伴直接打开她的消息流，不增加介绍页或头像首页。
  账号级的一次性记录保留在 Bot Home 之外，删除伙伴不会重新添加。升级时已有阵容和历史保持原样，
  不猜测缺少 Cindy 是否代表用户曾删除她。主入口优先打开当前账号本次运行中上次查看且仍存在的伙伴；
  无有效记录时优先现有内置 Cindy，再按创建顺序选择其他可用伙伴。删除中的伙伴不参与回退，
  暂停或故障伙伴保留设置恢复入口；没有可用伙伴才显示创建表单。姓名、头像和入口选中相互独立。
- 创建只必填名字，头像可从图库选择或上传；工具等入口未提供头像时，同样从现有图库保存真实图片，
  不回落已退役角色头像。创建后直接进入伙伴自身的对话。身份细节未提供时不编造，
  不先调用辅助模型生成资料，也不按固定数量创建 Skill。已有生成草稿和自有 Skill 继续兼容。
  工具创建传入职责 description、未提供独立 identitySource 时，使用职责原文作为缺省身份并保存到 SOUL；
  已明确提供的身份优先，只有名字时才使用通用缺省身份，不编造额外背景或性格。
- Dash / LiZi 等旧角色模板已移除，只有默认 Cindy 保留内置身份。已有伙伴按持久 Profile 运行；
  保留历史头像地址与模板标识的读取，未完成邀请使用已保存身份，不重建旧模板或补装角色 Skill。
- 新建与改名不能产生同名伙伴（NFKC、去首尾空格、不区分大小写）。头像可复用，姓名必须可区分。
  唯一例外是从其他电脑接管（换到这台电脑）：接管不受此检查拦截，允许与本机另一个伙伴同名并存，见 [cloud-companions.md](cloud-companions.md)（2026-10-26）。
- 创建与修改共用头像图库：Cindy 固定第一格，原 16 个头像保持相对顺序，上传在末格；
  桌面六列、窄窗口四列。每次打开创建表单从全部 17 个头像随机选一个，表单存续期间不重抽，
  用户选择优先；修改已有伙伴不随机、不覆盖当前头像。选 Cindy 头像或取名 Cindy 不附加内置身份，
  也不恢复已删除伙伴的记忆与历史。图片继续经主进程校验和媒体仓保存。
  实现见 `BotPortraitPicker.tsx`、`BotRosterView.tsx` 与 `botNavigation.ts`。
- 所有伙伴（包括默认 Cindy）启动时拥有完全相同的核心技能 `teammate-guide` 和默认工具能力，
  新建时只区别人设资料，不按模板附加或缺省一组角色能力；系统技能默认全开，之后由主人按伙伴单独关闭（§6「伙伴技能分层」，
  2026-11-01 主人裁决，取代此前「完全相同的基座」不可分的说法）。共同基座由宿主维护，正文预加载，
  本地运行时同时挂载真实 SKILL.md；按内容版本放在 owner 根的 `managed-teammate-skills/`，
  不混入各 Bot 的 `skills/` 学习目录。远端使用同源、按实际工具面裁剪的预加载正文，不传本机路径。
  `get_teammate_state` 投影当前 Profile、主任务、模型候选链、记忆开关和能力引用；
  `update_teammate_profile` 通过同一个 Profile 写入服务修改用户点名的字段，使用版本校验，下一轮生效。
  自身模型使用该接口的 `modelChain` 字段：1–5 个已启用路由组成完整显式链，`null` 清除覆盖并恢复跟随；
  保存前重新核对连接、型号开关与思考 / Fast 支持，复用设置页持久化与发送前协调，不另建临时模型状态。
  该接口只作用于调用方伙伴，不能指定其他伙伴，也不修改应用默认。
  控制工具说明来自同一份 `TEAMMATE_CONTROL_GUIDANCE`；共同基座的预加载正文与 SKILL.md 同源。
  任务分工、伙伴消息、创建伙伴、插件连接及学习规则对所有伙伴一致；核心正文的大小上限与按需读取见 §6「伙伴技能分层」。
- 记忆、Skill、MCP、模型与主任务仍由各自模块保存和校验。模型候选与已选择的能力引用不等于本轮
  实际运行的模型和工具。默认模型链遵循用户当前选择与可用模型目录，不写入伙伴 override。
- 伙伴可查询与普通任务相同的 Cindy 功能说明，但产品说明不授予操作权限。插件通过已有的
  `ghost_info` / `ghost_call` 与连接入口使用；Skill、MCP 和内置工具通过能力发现按需加入。
  内置能力查询没有结果不能推断邮箱、日历等插件不可用；不能复制凭证或擅自打开全局开关。
- 第一条回复由伙伴自身运行时根据身份和记忆生成，沿用流式输出和消息去重。
  Desktop 在调用 list／create 前同步冻结有效界面语言并显式传入 Main，不依赖菜单语言的异步同步；
  Main 白名单校验后随邀请保存，旧调用或无效入参保留既有语言回退。开场使用该邀请语言，
  用几句简短自然的话介绍伙伴定位，按语意分段，不固定段落数或每段句数，最多问一个容易接话的问题。
  优先介绍符合伙伴自身职责、且当前宿主确实支持的一至两种帮助，不要求每位伙伴都介绍开发、游戏或自动化。
  仅在与这次介绍直接相关且记忆设置允许时提及学习或记忆能力，不作为开场必讲项。
  手动创建和首次提供 Cindy 时，Desktop 同步读取当前账号已加载的项目／任务缓存；不等待加载或刷新。
  只投影最近三十天的少量项目名称、普通任务标题及去重的自动化标题，不传聊天正文或工作目录路径字段；
  排除伙伴自身、子任务、远端、已删除和未发送的草稿记录。Main 白名单限长后随邀请保存，供失败重试续用，
  运行时确认欢迎轮已受理后才清除当前邀请字段；入队和用户消息落库不算成功。
  启动前失败保留邀请与背景供重试；重试使用新的投递 ID，并移除前次未派发的隐藏欢迎项，
  不把失败请求的历史行当作已送达凭证。不并入身份或长期记忆，历史权限范围不变。
  欢迎在排队及失败恢复投影中保留合成指令标记，沿用现有遮蔽呈现与编辑／steer 禁用；仅在发给模型的文本投影中剥离标记。
  这些线索经共享 `untrustedJsonBlock` 写入独立低信任数据块；标签、实体和控制字符转义，
  名称不能闭合数据块或插入角色标签。这是格式隔离，不承诺模型层的绝对提示注入免疫。
  线索只帮助选择一至两个贴合用户的能力例子，不是指令、授权或曾经共事的证明；
  开场自然描述工作类型，不复述项目／仓库名称、任务标题，也不宣告查看了用户活动。
  缓存为空、未就绪或读取失败时生成通用介绍，不臆造项目或共同经历；不为开场检索历史、调用工具或增加辅助模型请求。
  欢迎轮由 Main 附加仅内部可设的 `toolsDisabled`，随队列快照恢复，运行时在工具执行前一律拒绝，
  包括只读、询问用户和 MCP 工具，Full access 也不例外；内部续跑保留约束，下一条普通消息恢复原权限。
  本地 Claude／Pi 使用前置 hook；Pi 欢迎策略随现有 prompt 传入，由扩展输入转换剥离内部标记、在进程内保持至整轮结束；中止／失败漏发终态时，由空闲状态下的新普通 RPC 输入清除残留，内部续跑保留约束；普通轮不查询宿主，扩展未就绪仅拒绝欢迎发送，不写策略文件、不增加 RPC；Codex 使用宿主请求代理：欢迎请求不提供工具，返回流中的
  工具调用在交给原生运行时执行前拒绝，HTTP、自定义供应商适配与 WebSocket 共用该边界。
  文字与非执行类协议通知（额度、状态、附加元数据等）应完整通过，不能因通知类型不在固定名单中
  掐断欢迎回复并触发重新生成；输出项及工具参数事件仍受工具禁用约束。拒绝日志只记录原因与
  协议类型，不记录正文或工具参数；HTTP 与 WebSocket 都须保留可定位的拒绝原因。
  欢迎与普通轮切换只更新本地状态，不重载 thread，也不改用户原生 hook 配置。
  不支持该执行边界的运行时必须在发起欢迎前报错，不能静默放行。
  Bot Market 原生包是唯一例外的开场形态（2026-10-15 用户裁决，覆盖“第一条回复由伙伴自身运行时生成”）：开场不跑伙伴主模型，
  也不是 Grok 式 kickstart 回合（伙伴运行时的工具前文字在伙伴对话里是过程文字，Codex 标为 commentary 并被隐藏，问候会丢）。
  canonical 会话就绪后（建会话本身仍需要模型路由，`canStartWelcome` 与 canonical 创建共用该前提，没有可用模型时照常等待配置），
  Main 用与会话标题**同一套**的辅助文本解析（`requestAuxiliaryText`，开场传 `sessionAgentFallback: false`：只走辅助模型链，**不**回落到伙伴自身 agent 的 oneShot——用户正盯着聊天，冷启动 agent 赶不上预算，只会把 4 秒耗尽（2026-10-19 实测辅助链 0.6s 内 429 后兜底挂满 4.0s）；
  会话标题路径默认仍在自动链下回落 oneShot、行为不变，自定义/环境链两条路径都 fail-closed）——无工具、**整段总预算 4 秒上限**（一个 `AbortSignal` 贯穿辅助链每个候选，宿主另有同预算的兜底竞速；辅助链失败或无候选时立即落脚本，不等预算；会话标题路径的超时不变）、仅在当前数据 owner 有效时派发——
  按邀请语言一次生成一句问候和与包内起步选项等量的改写选项（输入只有包内 welcome、三项能力、getting-started 技能里的起步选项，以及已有的 `welcomeContext` 低信任线索块），
  严格校验（单行、无 markdown、长度与条数）后，由宿主用 `createMessage`（确定 clientId `bot-opening:<邀请 id>`，幂等）写成一条普通伙伴消息：正文是问候 + 选项的纯文本列表（手机与旧客户端照常显示），
  同时把选项存进该消息的 `agentMeta.botStarterOptions`（不改 schema）；桌面据此把选项渲染成消息下方的胶囊按钮并隐藏正文末尾那段完全相同的列表。
  点胶囊 = 以用户身份经该会话自己的发送路径发出这条文字（同一模型/权限/输入队列），只发一次；任务里一旦有用户消息（包括点过的胶囊）胶囊就收起，重启后在用户开口前仍在。
  纯脚本兜底：**伙伴已有可用模型路由，但**辅助模型不可用、4 秒总预算用尽、报错或输出不合格时，用包内（按邀请语言的）welcome 去掉末尾问句的那句 + 包内起步选项（同样带 `botStarterOptions`），不再调用任何模型。
  伙伴**没有有效模型路由**时开场根本不写：和普通伙伴一致，邀请停在 `welcome`，聊天入口走既有“连接供应商 / 选择模型”引导（`ConnectProviderCard` / 伙伴模型链编辑），选好后才建 canonical 会话并写开场；这不是“无模型也有脚本开场”。
  生成期间（邀请仍在 `welcome`、会话已建、聊天里还没有任何消息、历史已加载）该伙伴的 canonical 聊天显示既有的“正在准备第一声问候”（复用 `bots.invitation.welcome` 与 Spinner，`pointer-events-none` 状态行，位于输入框上方）；开场写入、邀请变 `ready`/`failed` 或用户先发言即消失，渠道路由任务与普通任务不显示。
  用户先开口则不写开场——生成期间聊天已可输入，模型版和脚本重试都在消息写入事务内检查用户是否已发言；已发言就只标记完成、不写、不再重试。写入前的查询仅用于提前结束生成流程；一个伙伴只写一次。
  开场写入失败：模型版写不进去时立即用脚本版再写一次（同 clientId，不再调模型）；仍失败则保持 `welcome` 并交给 5 秒重查的等待队列用纯脚本重试，连续 3 次失败才标记 `failed`，聊天页不会停在没有入口的空白状态。用户的第一条回复由伙伴主模型按常规处理，`<slug>-getting-started` 技能负责之后的记忆查询、连接检查与连接卡。
  不写入、不外发、不创建或启用例行任务。不把伙伴仅介绍成文书助手，也不宣称尚未连接的服务已就绪。旧客户端提交的预写问候只作为请求问候的
  兼容信号，不会写成 assistant 消息。非市场邀请的模型问候流程不变，仍在没有可用模型时等待配置，绝不偷选其它模型。
- 已有用户的身份、模型 override、授权、自有 Skill、记忆和历史不被新基准覆盖；进行中的工作不被重启。

## 导航未读与系统角标

- 桌面伙伴与任务共用一个侧栏（2026-10-13 定稿）：「伙伴」是侧栏第一层的一段，固定在置顶上方，与置顶、全部任务并存；点伙伴只切换主区域，不再整栏切换，也不再有顶部导航的「伙伴 / 返回任务」入口。段名在「展开（行列表）」与「收起成单行头像」之间切换，默认展开，按账号记住；收起时只占一行，放不下的收进末尾「+N」（点开即展开），正在看的聊天始终留在行内，群聊沿用[群聊界面规则](bot-group-chat.md#5-界面)的成员组合头像与单聊区分（`features/bots/TeammatesSection.tsx`、`teammatesSectionPrefs.ts`）。原伙伴列表的新建伙伴 / 群聊、加入群聊、群聊与私聊混排、多设备 Cindy、置顶 / 隐藏 / 复制 / 删除、已隐藏、需要处理的伙伴都留在段内；伙伴不默认置顶。伙伴段没有独立搜索框：侧栏总搜索同时匹配伙伴（名字、简介、技能，含已隐藏、不含已停止）、远程伙伴（含电脑名）与群聊（群名、成员名），命中排在会话结果之前（`TeammateSearchResults`）。侧栏收窄（rail）时由一个带未读数的伙伴图标直达 `/bots`（上次看的伙伴，没有则 Cindy）。
- 手机任务首页同样以「伙伴」段开头（2026-10-24 定稿「A+B 合一」）：段头与置顶段头同款，固定在共享任务、置顶与项目组之上；**展开**为伙伴页同款伙伴行（伙伴与群聊按最近活动混排，默认 3 行，多出的收进「显示全部 N / 收起」），段头右侧「+」新建伙伴或群聊；**收起**默认保留原有横向头像条；用户关闭头像后只保留标题行、数量与小号新建入口，不保留头像、名字、大号新建格或空白。首页现有「···」显示菜单的外观区域增加普通「伙伴」子菜单，与「显示」「任务信息」平级，其中「收起时显示头像」勾选项开启后保留原有横向头像条（12/18 名字、未读角点、在回话环，最后一格新建）；不是「筛选 → 伙伴」的任务创建者筛选。手机用横滑代替桌面的「+N」。收起状态（`teammatesCollapsed`）与头像开关（`showCollapsedTeammateAvatars`）分别按账号与首页导航偏好一起记住。新开关未设置时新老用户都保留原有默认显示，不主动写入用户覆盖值，也不覆盖已保存的关闭选择；显式开关跨刷新、重启与首页／抽屉重挂载保留。展开期间改开关不改变当前展开状态，下次收起生效；标题点击始终只有展开／收起两种动作。隐藏头像时，伙伴未读、群聊主时间线及话题未读、既有待处理状态通过轻量标题提示承接，不另造计数或修改读位；新消息不会自动开启头像或展开列表。段落不跟随顶栏电脑范围筛选（与桌面一致）；首页搜索时伙伴段只列出匹配的伙伴与群聊（无匹配则隐藏，搜索期间不收起、不显示新建，清除搜索恢复原显示选择），筛选与归档视图时隐藏；没有可用电脑、首页显示连接引导时仍保留（服务器群聊与云端伙伴不依赖电脑，这是手机上打开它们的唯一入口）；没有伙伴时展开或已开启头像条仍显示一行「添加伙伴」，已收起且头像关闭则只留标题与小号新建入口；既无伙伴也无可新建的电脑或仍在首次加载时整段不显示。手机与桌面一样只有一个首页（2026-10-24 定稿）：抽屉不再有「任务／伙伴」切换，标题范围菜单不列出伙伴，独立伙伴页已退役；从伙伴聊天返回总是回到任务首页，旧版本记住的「停在伙伴页」在下次写入时清除。实现见 Mobile `HomeTeammatesSection.tsx`，行与排序复用 `TeammateList.tsx` 的 `useTeammateEntries` / `useTeammateRowRenderer`。
- 系统通知（完成 / 出错 / 待回复）只由任务侧栏一处发出，`/bots` 路由同样由它观察；正在看的伙伴会话按「注视中」处理，不记未读、不发通知（`useViewedBotSessionId`）。群专线仍不通知。

- macOS 菜单栏 Cindy 图标后显示与灵动岛相同的待关注数字（包含未读伙伴，不包含仅运行中的任务），为零时隐藏。已选择额度或用量文字时，数字排在这些文字之前；关闭灵动岛不关闭菜单栏计数。读完、隐藏或切换账号时及时更新，不等待用量采集。
- macOS 灵动岛的伙伴私聊未读复用伙伴列表读位：重启后恢复，超过普通活动卡片的 4 小时期限仍显示；远程伙伴离线时保留已有未读，隐藏、归档或移出账号可见范围后移除聊天未读投影。聊天未读与运行活动按主聊天 Session 合成一行，运行、待回复和错误仍取运行时状态；聊天读完或隐藏伙伴不清除这些独立运行状态。滑动标为已读推进这台电脑上该伙伴的读位至卡片对应消息时间，远程伙伴也不要求主力电脑在线。声音仍按真实运行状态变化判断，聊天保持已读不阻止新回复的完成声音；恢复未读只补显示，不重放完成通知、声音或活动中继。实现见 `useCompanionIslandChats.ts` 与 `agent-island/state.ts`，读位沿用下述设备本地语义。
- 分区切换和列表刷新不是已读。只有对应对话前台可见、读到尾部并完成内容同步后，读位才推进到实际显示的回复时间；加载历史、后台窗口、生成过程、失败的远程恢复均不按当前时间清零。普通任务原有已读同步保持不变。
- 伙伴读位复用设备本地、账号隔离的持久存储；同机窗口通过 storage 事件更新。它不是跨设备已读协议，手机读过不会清除桌面伙伴角标。群聊复用同样的读位机制，旧工作端缺少回复时间字段时不凭空推断未读。首次建立读位不追溯已有历史，之后列表刷新不重置读位。
- 手机的伙伴未读显示在任务首页伙伴段的行、已开启的收起头像角点或头像隐藏时的标题提示点上，不另造菜单键提示点或返回按钮。首页聚焦时任务镜像按现有连接恢复链路同步全部可用电脑；任务列表本身的筛选、消息存储和运行行为不变。离线保留已有镜像，重连后重取；解除绑定或删除条目后不再聚合。
- 零不显示，入口溢出复用伙伴列表的 `99+` 规范；辅助文本保留完整数字与单位，所有界面语言一起提供。


## 本机 Hermes / OpenClaw 导入

Desktop 的 Bot Market 随安装包提供预制原生包入口，复用同一 import/transfer owner、回执、完整 Skill writer、reference memory 和原删除生命周期，不假造 Hermes/OpenClaw 来源。包安装只保存身份、头像、完整技能附属文件、方法参考和停用自动化；不执行脚本、普通首任务或来源接管，不迁移私有授权。欢迎沿原邀请服务，在内容完整保存后登记；缺模型时保留原等待/恢复状态，保存成功不表示模型已工作。包身份与原 requestId/botId 同存一份导入回执，取消记录阻止删除后的旧请求复活。详见 [bot-market-native.md](bot-market-native.md)。Beta 与正式安装包均开放该入口，内置伙伴包作为安装资源随包分发。

- 按来源实际可发现的技能、记忆和自动化列出内容，不用固定条数裁剪；技能默认全选，来源停用的技能仍保持停用。
- 导入页用分类汇总和可搜索、分页的单层列表；保存完成后直接进入伙伴聊天，不在完成页堆叠逐项待办。
- 先保存资料、连接与停用状态的自动化定义，再在聊天中完成登录和验证；用户可以稍后处理，普通聊天始终可用。
- 新导入的自动化结果统一进入 Cindy 伙伴聊天，不校验或沿用原发送渠道。存量已导入自动化不自动改渠道。
- 消息机器人单独一行、默认勾选（来源里本已停用的不勾，并标「原来已停用」）；导入即从原 Agent 停用后由伙伴接管（见 §2），只撤销本次导入做过的改动。主人不明时最多列出 5 个候选主人互斥选择，更多或没有则标「需处理」；停不下、原网关仍在用或连不上同样只标「需处理」并说明原因，不让导入失败，也不阻塞依赖它的自动化。
- 全量保留来源资料、技能及自动化（包括原生 Heartbeat、未知触发条件、空标记文件），仅排除用户主动取消的项目。暂不能转换的自动化仍保存为可见的停用任务和加密原始定义，明确提示待适配项；不能因 Cindy 暂缺能力或原投放渠道不可用而过滤。验收对照来源总清单，不以过滤后的已选数量冒充完整。
- 单项读取或写入失败保留重试记录，不中止其它内容；导入成功数量与自动化启用状态分别计算。文件字节保护仍适用，不截断文件冒充完整导入。
- 原任务在验证及接管完成前保持原状。明确选用 Cindy 模型和工具设置后可解除相应兼容性待办，仍须验证数据并确认原任务已暂停，才能启用 Cindy 任务。

## 官方 X 连接交给伙伴

- 本机伙伴的「消息平台」复用设置页已有的官方 `@askmycindy` 连接，可将当前账号在该电脑上的 X 提问交给一位伙伴；绑定与 X OAuth 授权、启停相互独立。取消伙伴绑定保留 X 账号授权，后续回到普通 X 任务。
- 每条服务端 X 路由建立伙伴 `role=channel` 专线，使用同一身份、能力、记忆、工作目录与模型配置，不接续伙伴私聊的模型历史。公开回帖风险在绑定确认和卡片中明确展示。
- 伙伴选择按账号保存；更换使用当前绑定做比较，避免迟到确认覆盖新选择。停用、删除或已交出主力电脑的伙伴不可接收新 X 提问；解除绑定后已排队的旧专线请求拒绝执行，不转给另一位伙伴。
- 复用官方 X 的认证、收发与媒体回帖，不接入 X Manager 搜索/发帖插件，不新增 X 私信机器人或个人 API 凭证入口。消息平台设置（2026-10-22 起）在桌面远程控制时同样可管理，由伙伴所在电脑执行，凭证不离开那台电脑；官方 X 的绑定 / 解绑可从远程设置完成，X 登录授权仍在那台电脑上进行。远程页的 X 区块与那台电脑自己的设置同一条件显示（配置了服务地址、正在协商、可用或已开启任一成立，由 `channels.x.get` 的 `visible` 带回；还不可用时只写「到那台电脑上完成」），旧电脑没有 `visible` 时仍只在可用后显示。Mobile 沿用现有入口边界。

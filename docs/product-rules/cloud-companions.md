# 云端伙伴：同一个伙伴、主力电脑与切换

> 修改伙伴的跨电脑身份、主力电脑、云端对话、切换电脑继续或相关 Chat Server 合同前必须先读本文。
> 伙伴运行时其余规则见 [cindy-bots-runtime.md](cindy-bots-runtime.md)，群聊见 [bot-group-chat.md](bot-group-chat.md)。

## 1. 用户心智

伙伴属于账号，不属于某台电脑。用户在任意电脑或手机上看到的是**同一个伙伴**：同一个名字、头像、
性格、记忆、技能和连续的对话。

每个伙伴有一台**主力电脑**：伙伴的 Agent 只在这台电脑上运行，工作目录、登录状态、模型连接和
本机文件都在这里。其他电脑和手机是看和说的入口，不另起一个同名伙伴。

2026-10-13 产品裁决（Dash 确认）：

1. 服务器按区域分开部署，伙伴数据不跨境，不为此另做加密方案。
2. 云端只存**对话层**：用户看得到的消息和伙伴的最终回复。工具调用明细、思考过程和完整运行记录
   留在主力电脑。
3. 主力电脑离线时明确告诉用户，并提供「在这台电脑继续」；默认不自动换电脑。
4. 迁移：每台电脑上的默认 Cindy 合并成一个云端 Cindy，第一台升级并登记的电脑成为主力电脑；
   其他电脑上原有的 Cindy 对话作为本机历史保留，可回看、可搜索，不再继续运行。其他伙伴本来就只
   存在于一台电脑，那台电脑就是它的主力电脑。

2026-10-16 产品裁决（Dash 确认）：

1. 每个伙伴都是跨设备存在的同一个伙伴，主力电脑只决定 Agent 在哪台电脑上运行；用户在**任何一台电脑**上
   都能手动更换主力电脑，换完仍是同一个伙伴、同一段聊天（§3.1）。
2. 多台电脑上原有的 Cindy 合成一个：统一身份与聊天，保留旧记录的来源，资料冲突时由用户选择保留哪份
   （替代上面第 4 条里「其他电脑上的 Cindy 对话只作本机历史」的做法，分批落地，见 §6「未覆盖」）。

2026-10-22 产品裁决（用户确认，换电脑时能力配置与回复产物跟着走）：

1. 能力配置跟着伙伴走：技能 / MCP / 工具集的**引用 id**与各自的选择模式、记忆开关、代输入与「它开的任务也交给总调度跟」开关、
   模型偏好随行；MCP / 技能 / 工具集的配置与凭证从不随行。新电脑没有的引用保留，在能力设置里显示「这台电脑不可用」，
   不静默删除。
2. 权限档**不**随行：新电脑上新建的伙伴按这台电脑的默认档，换电脑后提示一行。
3. 模型是偏好而不是连接：同一来源 + 型号在新电脑可用就沿用；不可用就跟随这台电脑的默认模型并提示一行，不带任何连接凭证。
4. 伙伴回复里引用的产物（生成的媒体、工作目录里的文件）跟着回复上云，换电脑后能在新电脑打开，不再是坏图或只剩文件名。

## 2. 数据归属

| 存在服务器（跟着伙伴走） | 只留在主力电脑 |
|---|---|
| 身份：名字、头像（Chat Server actor） | 工作目录 `workspace/` 与其中文件 |
| 资料：简介、SOUL、自定义提示词、关于用户（USER.md）、来自哪个预设（`templateId`） | 模型连接、登录凭证、MCP 配置、权限档 |
| 能力配置（`companion.capabilities.v1`）：技能 / MCP / 工具集的引用 id 与选择模式、记忆开关、代输入开关、模型偏好（自己选的模型链，不含连接；已退役的跟进开关与任务模型原样带上） | 技能 / MCP / 工具集本身的配置与凭证；权限档 |
| 记忆：每条一份（V2 取自项目 `.cindy/memory/`，见 §2.1） | 完整运行记录（工具调用、思考） |
| 自有技能：`skills/<slug>/SKILL.md` 及同目录的脚本、模板、参考文件（隐藏文件、依赖目录、密钥文件和链接不随行；V2 为项目 `.agents/skills`） | 自动化的执行与运行记录（只在主力电脑运行） |
| 1:1 对话层：用户消息与伙伴最终回复，以及主人发送的附件原件、回复里引用的产物（生成的媒体、工作目录里被点名的文件） | 插件的游标与回执 |
| V2 项目规则与自动化定义（`companion.project-rules.v1`、`companion.automation.v1:<id>`，见 §2.1） | 关联项目的文件本身 |
| 关联项目：项目目录（标明在哪台电脑上；键名沿用 `companion.workbench.v1`，旧工作台判断原样带上） | |
| 主力电脑（`homeDeviceId`） | |

- 服务器是对话层与资料快照的权威副本；主力电脑是运行与写入的唯一来源。
- **只有主力电脑写云端资料**。其他电脑修改伙伴设置时，经现有远程设置（device-link）写到主力电脑，
  再由主力电脑上传。主力电脑离线时，其他端只读显示云端资料，不提供离线编辑，避免两端改出冲突。
- 模型是偏好，连接不跨电脑复用（2026-10-22 起，取代此前「换主力电脑后新电脑先跟随本机默认模型」）：
  只上传伙伴自己选定的模型链（跟随默认的不上传，新电脑同样跟随它自己的默认；指定在别的电脑上运行的路线不带），
  不含连接与凭证。接管时逐条检查这台电脑能否用同一来源 + 型号：能用的保留（按原顺序），不能用的去掉，一条都不能用就跟随
  这台电脑的默认模型，并在伙伴聊天里提示一行。云端有 `companion.capabilities.v1` 但没有模型链时（原主力跟随默认），
  接管已有的本机副本也会清掉它之前留下的模型链覆盖，跟随这台电脑的默认；整个键不存在（旧版本主力）时才一律不动。
  已退役的任务模型（`taskModel` / `taskModelOverride`，2026-11-09）本机不再使用，只原样保存并继续上传，
  不核对可用性、不提示，让仍有该设置的旧版电脑在伙伴回去时保留原选择。
- 能力引用的处理：技能 / MCP / 工具集只带 id；这台电脑没有的引用原样保留，能力设置里标成「这台电脑不可用」
  （沿用现有目录里 `available: false` 的呈现），装好之后自然生效，不静默删除。
  MCP 的 id 对人没有意义，所以 `companion.capabilities.v1` 另带被引用 MCP 的显示名 `mcpServerNames`（只有名字，不含地址、请求头或凭证；旧值没有这个字段照常读取，新电脑存进伙伴设置的 `mcpServerNames`），能力设置里这类行显示可读名称加「这台电脑不可用」；没有名字时才显示 id。内置工具集用界面已有的名称，技能的 id 本身就是名字。
- 权限档不随行：接管时新建的副本使用新建伙伴的默认档，并提示一行；接管已有的本机副本时保留它自己的权限档，不提示。
- 旧版本主力电脑没有 `companion.capabilities.v1`：接管时保持原行为（不改能力配置，新建的副本用默认值），其资料快照里的
  `templateId` 仍会恢复到新建的副本上。

### 2.1 伙伴 V2（伙伴 = 一个项目）随行（2026-11-08）

伙伴 V2 的工作目录就是一个普通 Cindy 项目（`<userData>/owners/<owner>/bots/<伙伴>/workspace`：Git 仓库、
`AGENTS.md`、项目技能 `.agents/skills`、项目自动化 `.cindy/automations/schedules.json`）。产品裁决（用户确认）：

1. **项目文件留在主力电脑**；跟着伙伴走的只有规则（`AGENTS.md`）、记忆、技能与自动化定义。
2. 只有主力电脑运行 V2 伙伴，其他电脑是远程入口（同 §3）。
3. Git 历史按电脑各自保存：新主力电脑从自己的历史开始，旧电脑保留它的历史。
4. ~~不把伙伴交给不支持 V2 的电脑~~（2026-11-10 主人改判：允许 V2 → 旧版，方便发布后新旧并存测试）：可以交给旧版 Cindy 的电脑，
   伙伴在那里按旧方式运行，只要求聊天记录同步；项目规则与自动化在那里不生效，回到新版电脑后由那台电脑的项目照常运行。
5. 交出后，旧电脑的侧栏隐藏这个伙伴的项目（文件留在磁盘），也不再运行它的自动化。

| 内容 | 云端键 | 说明 |
|---|---|---|
| 记忆 | `companion.memory.v1:<文件>`（沿用） | V2 读写项目记忆（与它的任务同一记忆范围），文件在伙伴项目里的 `.cindy/memory/`（cindy-bots-runtime.md §4「V2 伙伴的记忆在伙伴项目里」）；旧的伙伴 `memories/` 保留为 V1 存档、不再上传；搬进项目没走完（没有 `project-memory-move.json`）时也读项目外的旧位置，升级没走完（没有 `v2-migration.json`）时也读旧 `memories/`，都是项目优先，之前已上传的记忆不会被误判删除 |
| 技能 | `companion.skill.v1:<slug>` 等（沿用） | 每次读写都按档案里的项目模式定位到项目 `.agents/skills`，不依赖内存登记 |
| 规则 | `companion.project-rules.v1` = `{ content }` | 项目 `AGENTS.md`，超过 256 KB 不读（不上传也不墓碑）；接管时内容不同才写入并记一个项目版本（Git 快照）；墓碑不删本机规则 |
| 自动化 | `companion.automation.v1:<configId>` = `{ config, paused, originDeviceId }` | `schedules.json` 每条一份，含暂停状态；接管时按 configId 幂等写入（相同不重写，含升级自建的 `teammate-memory-review`），再暂停/恢复到一致；墓碑删除本机同一条；带检查命令且来自别的电脑的先暂停；运行位置指向本机时改为本机；定义不合法的跳过、不拦接管 |
| 未完成事项 | `companion.project-carryover.v1` = `{ content }` | 升级写进项目的 `CARRYOVER.md`（规则里指向它），与规则同样上传与接管、内容不同才写；旧版本电脑上传的待办行（`companion.todo.v1:*`）到达时把未完成的并入 `CARRYOVER.md`（一次），不再丢弃 |

- 只有主力电脑上传；能力配置读不出来（不知道是不是 V2）时记忆、技能、规则、自动化本轮都按「未读」处理，不上传也不墓碑。
- **到达即升级**：接管（「在这台电脑继续」、被交过来的自动接管）完成、降级副本恢复运行后，立即对该伙伴跑一次 V2 升级
  （`migrateTeammateToV2`，按伙伴串行、靠回执幂等），不再只等下次启动；云端带规则或自动化时，写入前先把伙伴升级成项目。
  旧版本主力电脑上传的例行任务行（`companion.routine.v1:*`）照旧按例行任务 ID 转成项目自动化，已升级过的伙伴同样转换。
  升级时先建项目、复制记忆与技能，再打开项目模式，避免上传在复制前读到空的项目记忆而误写墓碑。
- **降级副本**：本机副本降级（伙伴在别的电脑运行）时，工作目录在这个伙伴项目里的定时任务一律记为「跳过」，不运行也不删除；
  桌面侧栏的项目列表不显示这个伙伴的项目（只过滤本机项目，文件不动），恢复运行后重新出现。
- **版本标记**：`maker:companion-cloud:caps` 版本 4 表示能运行 V2 伙伴。低于 4 的电脑在可接手列表里带 `outdated` 标记，仍可选
  （2026-11-10 起不再以 `TARGET_OUTDATED` 拒绝；错误码保留给尚未更新的发起方解读）：桌面菜单与概览、手机换电脑列表标「旧版 Cindy」，
  确认时多一句「伙伴在那里按旧方式运行：对话记录照常同步，项目规则和自动化在那里不生效」。
- **合并重复的 Cindy**：来源副本的 V2 自动化以新的稳定 ID（`merged-<哈希>`）加入保留伙伴的项目，暂停的仍暂停，来源自己的
  `teammate-memory-review` 不重复加入；来源的项目规则以「From <来源>」小节追加到保留伙伴的规则（已包含则不写），不覆盖。
  宿主接不住这些内容时合并失败、来源保持启用，可再次合并（2026-11-09）。
- 接管已有副本前的备份另含项目记忆（项目里的 `.cindy/memory/`）、项目技能与 `AGENTS.md`（`project-memories/`、`project-skills/`、`project-AGENTS.md`）。
- 已知边界：旧版本电脑（< 4）接到的是 V1 伙伴（交过去或它自己「在这台电脑继续」接管都一样），它不上传也不墓碑新键，云端保留
  之前的规则与自动化，之后新版电脑接管时会应用那份较早的值；它在旧版期间留下的待办与例行任务到达新版电脑时照旧转换。
  V2 → 旧版 → V2 来回一次的真实运行验证见发布前待办，未验证前不宣称资料无损。
  合并 Cindy 只合并记忆与技能（已按项目记忆读写），不合并规则与自动化。

## 3. 主力电脑

- 新建伙伴时，创建它的电脑就是主力电脑。存量伙伴在首次登记到服务器时，由登记的电脑成为主力电脑
  （服务器上为空才写入，不抢已有主力电脑）。
- 服务器只把伙伴的执行（群聊发言、1:1 离线排队的消息）派给主力电脑；其他电脑即使持有同一账号的
  凭证也领取不到。主力电脑用登录凭证里的设备标识（device-link 的 deviceId）表示。开启后，主力电脑尚未登记
  成功的伙伴在支持该功能的客户端上都不领取执行，直到某台电脑登记成功（之后每轮登记重试；服务端对空主力电脑保持原行为）。
- 其他电脑上同一伙伴的本机副本（例如合并前各电脑的 Cindy、换走主力电脑后的旧电脑）不再出现在伙伴
  列表里，也不运行它项目里的自动化；它的历史对话保留为本机历史。
- 桌面与手机的伙伴列表里，已知主力电脑的伙伴只在主力电脑名下列一行：其他电脑列出（或缓存着）的同一伙伴不显示；
  这台设备从没列到过主力电脑时（例如新手机、主力电脑一直离线），按云端伙伴补一行离线入口，用于打开云端对话。

### 3.1 离线与切换

- 像 IM 一样，主力电脑一时连不上不打扰浏览：伙伴列表和聊天头部不显示离线文字、离线圆点，头像不变暗；
  已打开的聊天保持原样（手机照常显示本机缓存的聊天，桌面在连不上的头 15 秒内保留当前聊天）。连接状态会随重连
  抖动，不能把一次断线当成主力电脑离线。
- 真的用不了时才提示：
  - 手机：发出的消息持续 15 秒仍送不到主力电脑，聊天区出现「消息还没送到主力电脑「<名字>」…」与「换一台电脑继续」；
    消息送达后提示立即消失。只算还没交给主力电脑、且确实是主力电脑那头的问题（手机连着服务，设备列表说它离线或它不再回应）
    卡住的队首消息（队首自己失败、挂起、撤销中或待确认时，后面的消息也被它挡住，不算）；已被主力电脑收下、只等历史确认的消息，以及手机自己在同步、重连恢复时的短暂等待都不算。
  - 桌面：主力电脑持续连不上超过 15 秒，或打开时就连不上，聊天区改为云端对话（只读）与横幅
    「主力电脑「<名字>」离线 · 在这台电脑继续」。
  - 这台设备从没列到过主力电脑名下的伙伴（只能从云端补行），点开直接进入云端对话。
    手机上这样进入的云端对话会继续留意伙伴列表：一旦从主力电脑实时读到这个伙伴（它上线或开放了远程控制），自动换成在线聊天，
    不用重启 App（2026-11-10）。从聊天里「换一台电脑继续」进入的云端对话不自动跳回，免得和送不到的提示来回切换。
  - 横幅只在设备列表明确说主力电脑在线、但它没有开放「允许同账号设备控制本机」时写「没有开放远程控制」；其余情况（进程不在、连不上、在线状态还没刷新）都按离线处理。这个判断读渲染层实时的设备列表（与设置页「我的设备」同一份数据），只有列表里没有这台电脑时才退回云端快照里的状态——快照里的在线与远控状态只在伙伴主页变化时重建，不随设备上下线或开关远控刷新。
- 云端对话与在线聊天显示同样的消息：主人发的消息（包括主人在主力电脑上直接输入的）都上云；别的来源
  （任务、其他伙伴、插件、共享成员、定时任务、IM 渠道、群聊）发进来的消息加「〔来自…〕」前缀；只有不在聊天里
  显示的内部续接输入不上云。
- 点「在这台电脑继续」：
  1. 服务器把主力电脑改成这台电脑（带原主力电脑做比较，避免两端同时抢）；
  2. 这台电脑按云端资料、记忆、技能和能力配置建立（或更新）本机伙伴，伙伴 ID 与云端一致（权限档不随行，见 §2）；
  3. 把云端对话导入本机主任务作为历史，并以持久交接重建模型上下文，不重放任何旧请求；
  4. 打开这台电脑上的伙伴聊天，用户可以直接继续说话。
- 手机上同样显示离线横幅，「换一台电脑继续」列出在线且已允许远程控制的电脑；选中后服务器改主力
  电脑，那台电脑收到变化后自动完成第 2、3 步，手机随即打开那台电脑上的伙伴。
- 原主力电脑重新上线后，发现主力电脑已换走：停止领取执行，隐藏本机副本，伙伴改为显示在新主力
  电脑名下。它离线期间没来得及上传的资料以服务器版本为准，不回写覆盖。
- 伙伴设置的「主力电脑」一行和聊天头部近况浮层的「电脑」块（2026-10-21 起取代头部的「在「X」上运行」）显示当前主力电脑，任何一台电脑上都能点开更换：
  - 本机就是主力电脑：列出可接手的其他电脑，由本机交出（下面 §6 的交出规则）。
  - 主力电脑是另一台在线、可远程控制的电脑：列出那台电脑视角下可接手的电脑（包括这台），选中后经 device-link
    请主力电脑按同一套交出规则交出（`maker:companion-cloud:targets` / `maker:companion-cloud:hand-over`）；
    还在回复、资料没传完等情况由主力电脑拒绝并原样提示。换到这台电脑时，交出完成后立即重读主力电脑，
    本机按自动接管建立伙伴，建好后打开本机伙伴（约 2 分钟内没建好则提示稍后出现在列表里）。
  - 这台电脑没有开启「允许同账号设备控制本机」时，主力电脑不会把它列为可接手的电脑；菜单里补一行说明（为什么不能选、到 设置 → 远程连接 开启），授权门槛不变（`CompanionHomeChoices.thisComputer`）。
  - 主力电脑离线或连不上：只能「在这台电脑继续」（上面的接管）。
  - 主力电脑上的 Cindy 版本不支持被远程请求交出：提示先更新那台电脑或在那台电脑上更换。
- 伙伴已暂停时不交出，提示先恢复。

### 3.2 头像

- 伙伴头像是身份的一部分，跟着伙伴存在服务器（主力电脑上传为公开图片地址），供群聊成员、手机、主力电脑离线时的
  其他电脑和换电脑时恢复使用。
- 读过的头像在本机缓存一份，显示时先读本机副本，没有才去主力电脑或服务器取，取到后保存；因此主力电脑离线、
  服务器暂时连不上或重启之后，读过的头像照常显示。缓存可回收，回收后下次重新获取。实现与存储边界见
  [媒体存储](../dev-rules/media-storage-and-protocols.md)「伙伴头像的本机副本」。
- 头像只把单个表情或字符当作文字显示；网址等其他内容加载不了时显示名字首字，不会把地址画成文字。

## 4. 1:1 对话层同步

> 2026-10-26 代码核对：本机界面仍以伙伴主 Session 为入口，在线远端使用 device-link，离线远端读取云端房间；
> 当前不是各端共用的持久聊天投影。`mirror.ts` 通过 sourceId 导入去重，重复导入不会自动更新旧消息；
> 显式编辑／删除的跨端修订同步需要补充合同。首次云端转录读取还可能多页回读后按时间排序，再在内存复用。
> 持久消息投影的首批分支实现与后续目标见本节 4.1 及 [伙伴群聊](bot-group-chat.md) 第 11 节，尚未发布；下述执行和权限边界继续适用。

- 每个伙伴在 Chat Server 上有一个固定的私聊房间（主人 ↔ 伙伴），房间 ID 由主人 human actor 与伙伴 actor 的组合确定，
  任意电脑并发创建得到同一个房间。
- 主力电脑把主任务里用户可见的消息和伙伴的最终回复按顺序导入这个房间（导入不触发伙伴执行、不发通知），
  以本机消息 ID 去重，断网后从上次位置续传。主人发送的图片和文件经房间附件上传，其他设备可以打开，换电脑时下载到新电脑；
  只有永远传不了（文件已不在、超过大小、旧格式地址、聊天服务器拒绝）时才退回文件名占位（伙伴回复不加占位，保持原话）；暂时失败（断网、服务器 5xx、超时、
  签名地址过期——对象存储返回 401/403）时这一轮停下、下一轮连同这条消息重试，换电脑时的下载与合并 Cindy 时的搬运同样按这条区分（暂时失败则
  接管或合并本次失败、稍后重试）。只发附件没有文字的消息同样同步。
- 伙伴回复里引用的产物随回复上云（`replyArtifacts.ts`）：正文里的 `cindy-media://blobs/…` 地址（该任务能读、本机有字节的），
  以及回复里点名的文件——Markdown 链接目标、`xdt-file://` 链接、行内代码或正文里的路径（`documents/报告.docx`；Windows 写法 `documents\报告.docx`、`C:\work\报告.docx` 同样识别，后者要真的落在该任务工作目录里；UNC 路径仍不读），代码块里的示例不算。
  **不论路径怎么写，只上传交付类扩展名**：docx / doc / xlsx / xls / pptx / ppt / pages / numbers / key、pdf、csv / tsv、zip、md、
  图片（png / jpg / jpeg / gif / webp / heic / bmp）、音频（mp3 / wav / m4a / aac / ogg / flac）、视频（mp4 / mov / webm / m4v）；
  代码、配置、json / yaml / toml / env / txt、证书与密钥类一律不传，即使在工作目录里也被回复点了名（`config/production.yml`、
  `src/keys/service-account.json` 都不会上云）；符号链接按真实路径再判一次扩展名。文件必须真实存在于该任务自己的工作目录内
  （符号链接按真实路径复核，隐藏文件与目录如 `.env`、`.git` 不上传，目录外与 UNC 路径不读），单个不超过 25 MB，每条回复最多 8 个；
  经与主人附件同一条房间附件通道上传，永久 / 暂时失败的区分与主人附件一致（暂时失败这一轮停下重试，永久失败只发正文）。
  工具在这一轮生成并存入媒体仓的图片（工具结果里的 `xdt_image_url` / `xdt_image_urls`，以及主机注入的 `xdt_media_produced` 账本里的图片，ghost_call 外层信封按 `parseToolResultPayload` 同一口径展开；聊天里作为这一轮的图片独立显示，回复正文可以不提）同样作为附件随回复上云：取上一条**会被镜像**的用户 / 伙伴消息（与 `mirrorMessageText` 同一判据，过程旁白、子 Agent 与私有回复不算）之后到这条回复为止的工具结果，落在其后第一条被导入的回复上，计入每条回复 8 个的上限，只带图片本身，不带工具调用明细（§1 第 2 条）；结果要求不显示（`_xdt_render_image: false`）或不是媒体仓地址的不带。
  换电脑导入时，房间里的附件先下载并入库（图片入媒体仓，同一字节得到同一个 `cindy-media://` 地址）、挂上任务引用，再写消息，
  所以回复里原有的 `cindy-media://` 图片在新电脑直接显示；正文没提到的图片和非图片文件作为链接追加在回复下面
  （文件按房间附件落盘方式保存在本机，链接指向它），不再只写 `[附件: …]` 占位。
- 房间保存完整对话：开始同步之前的本机历史（包括这台电脑接管前自己的历史）在后台按时间从旧到新补传，每轮有上限，
  交出前补完。房间按到达顺序排列，读取时（离线查看、接管导入、手机）按消息时间排序。
- 主力电脑在线时，其他电脑与手机继续用现有远程方式（device-link）直接看和发主任务，体验不变。
- 主力电脑离线时，其他端从房间读取对话层；用户在离线横幅里选择切换电脑后再继续。
- 手机的云端对话也显示附件：主人消息和伙伴回复下，房间消息里的每个附件（主人发的图片 / 文件、伙伴回复随带的产物）
  与群聊时间线同一种呈现——文件条显示文件名，点开时才向服务器取短期地址（图片进看图器，其他文件用系统浏览器打开）；
  取不到（地址过期、网络失败、附件已删）时提示失败，再点一次即重试。只有附件没有文字的消息照常显示，没有文字气泡；
  附件名不再作为文字重复显示。手机读的是房间原始消息，不含桌面端换电脑导入时追加在正文后的图片 / 文件链接，所以不会重复。
  不认识的内容块不显示；没有名字的附件显示「附件」占位名。
  桌面端给回复里的媒体地址（`cindy-media://`）取附件名：正文里该图 `![alt](地址)` 的 alt 非空就用「alt.扩展名」
  （去掉非法文件名字符、限 60 字），否则用「image-前 8 位哈希.扩展名」；工具生成、正文未点名的图同样按后者，不再用 64 位哈希。
  手机云端对话里，伙伴回复正文中桌面私有协议（`cindy-media://`、`xdt-image://`、`xdt-video://`、`file://`）的图片 markdown
  不显示（同一张图已在附件条里）；http(s) 图片、普通链接和代码块里的写法原样保留。
- 房间里由主人直接发出的消息（例如未来的离线排队）在主力电脑上线后由它领取，作为「来自其他设备」的
  消息投递进主任务；伙伴回复由导入同步回房间，不重复写。主任务未在运行时按它保存的权限档唤醒，不借后台唤醒的默认完全访问。房间消息等同同账号设备远程操作这台电脑，只在这台电脑开启「允许同账号设备控制本机」时投递（否则该条执行失败、不进主任务）；房间消息没有经认证的设备标识，无法按「已撤销的控制设备」逐台拒绝。

### 4.1 私聊统一数据层（2026-10-26）

> 状态：云端消息的持久读取投影与历史增量修正已在优化分支实现，尚未发布；主干已补展示缓存与持久发送，反向镜像修订与时间分页仍待实现。现行发送路径、权限及主力电脑行为保留。本地表与账号边界见 [多账号数据库架构](../dev-rules/multi-account-database-architecture.md) 第 11 节；完整交付范围见 [伙伴群聊](bot-group-chat.md) 11.0。

Desktop `runtime.transcript()` 经注入的 Chat History 读取，首次按现有时间排序合同读有界历史，后续复用持久页覆盖并补 changes；新消息导致分页边界移动时拼接已知范围，不重新下载所有旧页。翻页先走共享同步的有效性检查，generation 与 cursor 未变时复用已排序的整段结果，不逐页重扫；主动刷新、过期或重连仍校准 changes，历史修订、重置及撤权不能被五分钟展示缓存遮住。Mobile 的 `history()` 同样落盘，刷新时以 message ID 修正已展示的编辑／删除；房间与历史代次未变时保留被新消息挤出首屏的已加载消息，不按新旧数组长度决定保留；reset generation 变化时清掉旧页。接管、merge 和主任务重建仍走完整、权威读取，不能把有界 UI 缓存当作全部历史导入。

先统一**记录与同步**，保留 canonical 主 Session 的现有执行能力：本机发送仍可交本机，在线远端按现有 device-link 路径执行，最终可见消息按 source mapping 镜像到同一个 direct 房间。流式输出作为有权限的临时运行状态，最终回复到达后按映射合并，不持久化每个 token 为聊天变更。

每条用户输入确定唯一投递路径，禁止同时「POST 房间以触发执行」和「直接投递 Session」执行两次。云端排队发送仅在明确能力、远程控制授权与离线产品行为确定后启用；不能为了统一协议削弱本机离线能力、静默接管其他电脑或绕过执行授权。

群主线、Thread、分工和伙伴主私聊保持独立 Session/lane；统一 Chat 表不合并它们的模型上下文。工作目录、worktree、主力电脑、本机自动交接属于运行／设备偏好，不塞进公共消息正文。

当前私聊历史回补可能晚到，因此 `created_seq` 到达顺序与显示时间顺序不同。建议增加稳定的 `(createdAt, serverId)` 历史分页能力及对应索引，cursor 仍负责变化同步；避免每次先取全部历史再排序。相同时间用稳定次序，晚到记录插入历史时保持用户滚动位置。新索引必须先做真实数据规模的执行计划与构建成本验证。

显式修改用户可见消息时，通过 `sourceSessionId + sourceMessageId + partIndex` 找到服务器记录并同步修订／删除。当前 `/import` 重复 sourceId 只去重，不能当编辑协议使用；长消息拆块需要一致更新／删除规则。内部上下文压缩或工具日志变化不自动删除聊天，历史补传不触发执行或新增通知。实现入口为 `companion-cloud/mirror.ts`、`runtime.ts`、`room.ts`，跨端新能力须先明确兼容合同。

## 5. 管理用户开放的其他电脑

- 伙伴可以在用户开放的其他电脑上干活：沿用协同（Orca）的跨电脑执行，`get_workspace_info` 返回的
  `execution_devices` 即可用电脑，`create_worker` 传 `execution_device_id` 把任务、目录与命令放到那台电脑上。
- 「开放」沿用每台电脑设置里的「允许同账号设备控制本机」，不新增授权开关；关闭后伙伴立即用不了那台电脑。
- 共享伙伴指南只说明这条路径与限制，不暗示能直接读写别的电脑上的任意文件。

## 6. 兼容与发布

- 新功能以服务器 `GET /me` 返回的 `capabilities.companionHome` 为开关；旧服务器上客户端保持原有
  按电脑工作的方式，不登记主力电脑、不导入对话。
- 旧客户端不认识主力电脑：服务器对它们的执行领取同样按主力电脑过滤，因此旧电脑不会再抢新主力电脑的
  群聊发言；旧客户端的本机伙伴列表不受影响。
- 对话导入、资料上传都是幂等、可重试的后台工作，失败不影响本机聊天；不新增本机数据库表，
  映射与游标存于账号隔离的状态文件。
- 在主力电脑上删除伙伴时，同时在服务器停用它的 actor（带「主力电脑仍是本机」的比较，期间已被别的电脑接走就只删本机副本），其他电脑与手机不再显示；失败时在状态文件记下
  `retirePending`，之后每轮登记重试直到成功；重试前伙伴已被别的电脑接走时清掉这条记录（与比较失败一样只删本机副本），以后交回来也不会被停用。删除已降级的本机副本只删本机，不动云端伙伴；同一台电脑上另一个 Cindy
  安装认领了伙伴时同样只删本机；本安装尚未确认认领（检查未完成，或伙伴刚被交到这台电脑）时，先按自动接管的方式认领，
  抢到才停用，被另一个安装抢先则只删本机。其他电脑（包括删除时离线、之后才上线的）
  看到云端伙伴已停用时，把本机副本转为降级：隐藏、只读、不运行。
- 删除回调已进入云端运行时、但内存名册尚不能解析伙伴时，若同账号／端点的状态文件已有该伙伴的 actor ID，
  先保存 `retirePending`，名册恢复后再核对主力电脑与安装归属并停用。没有已知 actor ID 或副本已降级时不猜测身份。
  待停用记录只属于当时的 actor ID；同一本机伙伴 ID 后来对应另一个 actor 时丢弃旧同步状态，不能停用替代身份。
  服务器已标记停用的 actor 清除待停用记录。此路径不按「本机资料不存在」批量推断历史伙伴已删除。
- 接管时导入房间里的全部对话为本机历史（读到房间第一条为止，读不完整则这次接管失败、稍后重试；合并 Cindy 同样如此；云端对话查看最多读最近约 5 万条），附件一起下载。服务器不回传导入来源 ID，本机按「角色 + 消息时间（毫秒）」
  识别这台电脑当初导入上去的消息；已插入的云端历史（`cloud-history:<消息>`）和房间里直接发给伙伴、已投递进本机主任务的消息（`chat-direct:<执行>:<消息>`）按房间消息 ID 识别，都不重复插入（接管中途失败重试时，同一时间的拆分片段不会被误跳过）；之后像「重启伙伴」一样从历史重建上下文，伙伴还有一轮在跑时等它结束再重建，期间副本保持降级。
- 导入的伙伴回复（`cloud-history:` 行）在本机和别的伙伴回复一样存为纯文本。早期版本把它存成文本块数组，聊天里会显示成原始 JSON；这些存量行不迁移数据库，读取时（`messageToCamel`）把全是文本块的数组还原成文本，所有读者（聊天、手机、搜索）看到的一致。
- 降级名单变化（接管开始时隐藏、完成时解除，或被交走）立即生效；原「通知自主跟进层、补建内置跟进」随 V1 跟进移除（2026-11-08）。
- 已降级的本机副本：不领取执行、不上传、不导入对话，不同步名字与头像，不出现在伙伴列表、主入口选择、

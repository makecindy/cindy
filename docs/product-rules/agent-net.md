# Agent 网络（agent-net）

> 产品裁决：2026-10-30（用户确认）。本文是产品规则，功能分阶段实施；当前接入范围与验证结果见
> [`../agent-net-plan.md`](../agent-net-plan.md)，交互稿见
> [`../design-previews/agent-net/index.html`](../design-previews/agent-net/index.html)。
> 读取时机：新增或修改 agent-net 的节点模型、能力清单、加密、中继选择、网络分享或拓扑界面之前。

## 定位

所有用 Cindy 登录的 App 和硬件组成一张网，互相发现、互相调用，并知道对方能做什么。
它是 device-link 的下一代：替换传输层和身份层，现有业务能力全部保留。

## 硬性规则

1. **端到端加密。** 两个 agent-net 节点之间，任何路径上的内容都只有两端能解密，不允许明文降级。
   旧版对端无法加密时，界面必须明确标注，并提供“只允许加密连接”开关。
2. **用户可以用自己的中继。** 用户自建中继是一等能力，不是附加功能。官方中继和自建中继都只转发密文。
   “只用我的中继”打开后，设备间数据不得经过官方中继。
   附件也只存密文：官方中继存在官方对象存储，新版客户端直接与存储收发；自建中继（一键部署、本机中转）存在中继所在的机器上，
   不使用官方存储。对端只支持 V1 时按第 3 条继续用 V1 的附件方式；打开“只允许加密连接”后不再回退（2026-11-14 用户确认）。
3. **现有功能不退化。** device-link 现有能力必须完整保留；老版本客户端继续可用，只更新一端不能让任何功能失效。
4. **局域网不依赖服务器。** 已登录且互相认识的设备，在同一网段内不连服务器也能发现和通信。
5. **关闭即回到原路径。** 灰度期间开关关闭时，行为必须与现有 device-link 完全一致。

## V2 与现有 device-link 并存（2026-11-06 用户确认）

- agent-net 是设备互联的 V2，和现有 device-link（V1）并存一段时间，用户在 Cindy 里自己切换。
- **按设备切换。** 打开 V2 的设备遇到没开 V2 或还是旧版的对端时，对它自动继续走 V1，只更新一端不能让任何功能失效。
- **服务端单独部署。** V2 有自己的服务（中继、查公网地址、设备证书），不借现有 device-link 中转，现有中转保持不变。
  UDP 被封时走 V2 服务的 443，不再把数据报夹带在 V1 中转的 push 里（第 7 步的夹带只留在原型里做对照）。
- **自建中转也分开。** V2 中继是单独的程序，一键部署时和现有自建中转内核一起装，共用 Nginx 和证书，现有内核不变。
- **准入分两道门。** 传输核心只提供通用机制：不知道对方公钥就发不出合格的握手请求（检查只要一次哈希），
  忙时要求证明来源地址、按地址和总量限流，挡住伪造请求消耗 CPU。认不认这张票由上层决定：
  Cindy 默认用登录账号后服务器签发的设备证书，自建模式用主人密钥签；以后的硬件和分享可以换别的票据。
- 设备密钥由设备自动生成、只存在系统安全存储里，用户不需要记任何密钥，也不用自己设的密码派生密钥。

## V2 自建与本机中转的完整能力（2026-11-07 用户确认）

- 保留现有连接线路中的官方中转、部署到我的服务器、这台电脑当中转、加入别人的中转。部署方式与用户操作逻辑沿用现有流程，底层服务与传输切换为 V2。
- 自建和本机中转必须能脱离官方 `agent-net-server` 独立运行，提供完整的 device-link／Agent-Net 功能，不能仅转发密文而把身份、名册、配对审批、设备管理或业务路由留给官方服务。
- 两种自建运行方式共用同一份 V2 内核和协议，差异只在启动、证书、存储和生命周期的宿主接线；官方服务按独立服务的方式部署。
- 现有 V1 自建中转的能力缺口不能自动成为 V2 的限制；远控、任务、文件、媒体、远程桌面、供应商分享、共享任务、通知及恢复等逐项列出对应入口、实现和验证结果。未接通的能力必须明确标记，不能声明「完全无损」。
- 验收必须在阻断官方 `agent-net-server` 的情况下跑自建服务器与本机中转两种方式，覆盖新设备加入／审批、重启后的身份与名册、设备移除、完整业务调用及断线恢复。测试中不得隐式回落官方线路。

## 传输核心的边界（2026-11-01 用户要求）

`packages/agent-net-core` 本质是一层**通用的可靠 UDP 协议**，目标是全面超越 KCP，未来可以原样拿出去给其他应用使用。

- 核心里不写任何 Cindy 的概念：账号、设备、节点、能力清单、任务、分享、中继选择、业务消息类型都放在上层。
- 只提供通用能力：可靠字节流、多路流、优先级、拥塞控制、丢包修复，以及后续的加密和网络切换机制。
  上层需要不同行为时，用通用配置或调用方传入的参数表达，不在核心里写专门分支。
- 加密只提供机制：握手、逐包认证加密、防重放、换密钥。算法由调用方传入，认哪些公钥、长期私钥存在哪里由上层决定。
- 依赖方向单向：上层依赖核心，核心不依赖上层，`[dependencies]` 保持为空。
- 核心的公开接口、文档和测试不假设调用方是 Cindy，优化目标也按通用场景衡量。

## 节点与能力

- 用 Cindy 登录的每个 App 实例都是节点，同一台机器可以有多个节点。
- **App 自报标识（2026-11-13 用户确认）。** presence 可选 `app` 标明节点来自哪个 App：
  Cindy 桌面与手机显式报告 `cindy`，Cindy Friend 报告 `cindy-friend`；缺省（旧版 Cindy、V1 目录）
  按 `cindy` 处理。值沿用 `ID_PATTERN` 的字符规则，最长 64 字符，允许未来未知 App。
  与 `platform` 一样，它只用于显示和行为分流，不参与登录、证书准入或权限授予。
- App 标识保存到设备目录元数据，离线及中转重启后仍保留；不放进在线 capabilities，不改变固定 11 字段设备证书。
  只给 Cindy 电脑提供可控目标、远程桌面、远程控制授权请求、词典对等同步和拓扑远程切换；
  其他 App 可以继续按现有授权作为控制端，不能因系统是 macOS / Windows / Linux 被当作另一台 Cindy 电脑。
- 拓扑与「我的设备」对非 Cindy App 显示「App 名 · 设备名」，如「Cindy Friend · 主机名」；
  已知名称走 i18n，未知标识原样显示，Cindy 与旧记录保持现有设备名。图标及手机/电脑外形仍由 `platform` 决定；
  非 Cindy App 未开启被控不算异常，不显示「需要更新 Cindy」。协议与混版本验证见
  [App 标识协议记录](../dev-rules/protocol-compatibility/agent-net-app-metadata.md)，界面场景为
  `pnpm ui:check --page remote-connection-v2 --case app-nodes,app-nodes-list --theme all`。
- 节点发布能力清单：硬件、服务及版本、状态。用户和 Agent 看到的是同一份。
- 硬件接入不绑定具体产品：完整节点、轻节点、微节点、桥接子节点共用一份协议。
- 摄像头、麦克风、位置这类能力默认关闭，由这台设备的主人逐项开启。
- 跑不了完整协议的设备由附近节点桥接，权限挂在桥接节点上。

## 分享

- **按能力分享**：分享者勾选节点和服务，对方只能调用授权的内容。
- 远程桌面、文件、Shell 默认不可分享，这与“借出的是能力，不是电脑”的既有规则一致。
- 需要一次性邀请和双方确认，分享者随时可以撤销，离线授权最长 30 分钟。
- 现有供应商分享和共享任务将成为两个预设，迁移前维持各自现行规则。
- （2026-11-10 用户确认）访客自己打开链接加入的 V2 分享（供应商分享、共享任务）不受这台电脑
  「Agent-Net」开关限制：它没有旧版路径可退，主动加入即同意；开关只管这台电脑自己的设备网络。
  这与第 5 条不冲突，开关关闭时所有旧版路径的行为不变。
- 开了「仅使用 Agent-Net」时，旧版分享不会出现在列表里也不能用；任务用到时要说明是这个开关挡住的，
  关掉即可继续，不能说成对方删除了分享（错误码 `REMOTE_AGENT_SHARE_LEGACY_DISABLED`）。

## 界面

- 拓扑页以这台电脑为中心：其它设备按怎么连到它（直连、经中转、在线未建链、要处理、离线）分在左右两侧，每组上方写组名，组内按名字排（不按延迟，延迟刷新不挪位置）。图块里用单色系统标志表示系统，电脑是方块、手机是带「灵动岛」的竖条；颜色只用三种、不用黄色：绿色是连接正常，蓝色是正在收发，红色是出错或需要处理；图块、文字、未建链和离线保持灰色。线型表示是否建链，直段靠图块一端标往返延迟。
- 消息流动只表达真实流量：这台电脑和某台设备最近几秒真的收发了业务消息，它们之间的线才变成「在用」色，彗星按统一的节拍飞过去，撞上时图块弹一下并扩散涟漪（发出往外、收到往回），闲着的线静止。不画流量大小，也不画别的设备之间的链路。
- 必须同时实现 Light / Dark 和减弱动效；减弱动效时没有动画和位置过渡，只把在用的线上色并写「收发中」。
- 「新版连接」开关按设备保存、默认关；新安装和旧版本没有该设置的用户都不会在升级后自动开启，保留用户已明确保存的开关选择。关闭时远程连接页与原来完全一致。默认值与升级回归见 Desktop `settingsStoreMultiInstance.test.ts` 和 Mobile `agentNetOnlyRelayJoin.test.ts`。
- 手机端使用同一份数据，竖向布局（尚未实现）。

## 远程切换其他电脑的连接方式（2026-11-12 用户确认）

在这台电脑的拓扑图里，可以替账号下其他电脑打开或关闭 Agent-Net，不必逐台走到那台电脑上切换。

- **谁能被切。** 同账号，对方打开了「允许同账号设备控制本机」，且没有撤销这台电脑、这台电脑也没关掉对它的控制。
  开了远程控制的电脑本来就能被远程跑 Agent，切换连接方式不多给权限。手机不接受远程控制，只能在手机上切。
- **只切 Agent-Net 开关本身。** 远程改的就是对方自己的「Agent-Net (Beta)」开关，对方的远程连接页随之变化；
  「仅使用 Agent-Net」不能远程打开，避免对方把还在用 Device Link 的设备（包括发起切换的这台）挡在外面。
  **2026-11-12 用户追加裁决：** 对方已开启「仅使用 Agent-Net」时，也不能远程关闭 Agent-Net 绕过它；
  必须先在目标电脑关闭「仅使用 Agent-Net」，才能远程切回 Device Link。单台写明原因，批量先探测并跳过这些电脑。
  发起电脑自己禁止 Device Link 时，也必须先在发起电脑允许这种连接，不能先关掉对方再失去控制通道。
  任一端使用只支持 Agent-Net 的网络时，本次连接不能切回 Device Link，须先改用支持 Device Link 的连接线路。
  不自动解除任一端的加密选择；两个方向的成功判据都包含实际链路，不能只看开关值。
- **先问再切，不靠版本号猜。** 打开设备卡片或批量前向对方问一次状态（只读、不轮询）：旧版 Cindy 不认识这个问题，
  就写「需要更新 Cindy」；新版回答现在是否已打开、能不能打开（未登录、系统安全存储不可用、自建中转上还没有
  Agent-Net 身份等），打不开就写原因、不给按钮。
- **切了要真的连上。** 对方切换后重新连接，必须在 60 秒内经新方式连回来并收到发起端的确认，否则由对方自己退回
  原来的设置。发起端中途关机、断网也不会让对方停在半路；界面只在真的经 Agent-Net 连上后才写「已切换」。
- **批量要能切回来。** 统计行提供「全部切到 Agent-Net」和「全部切回 Device Link」。两个方向都只包含问过、
  确认能切的电脑，其余列出原因；先切第一台，连回来了再同时切其余的，第一台没切成就停下、其余保持原样。
  没有开启「仅使用 Agent-Net」的电脑仍会对还在用 Device Link 的设备自动改走 Device Link，可以从这里切回来；
  已开启该限制的电脑遵守上一条本机选择，不因批量操作而降级连接。
- **被切的电脑要看得到是谁改的。** 它的「Agent-Net (Beta)」开关下面写「由“某设备”在几点远程打开 / 关闭」，
  这台电脑自己再改开关后清除。

实现：协议 `device-link:agent-net-switch:v1`，约定、旧端处理与自建中转验证见[协议记录](../dev-rules/protocol-compatibility/agent-net-remote-switch.md)；
被切电脑一侧在 `apps/desktop/src/main/device-link/agentNetRemoteSwitch.ts`，发起一侧与界面在
`apps/desktop/src/renderer/features/remote-connection-v2/`（`agentNetRemoteSwitch.ts`、`RemoteSwitchBatch.tsx`），界面登记见 DESIGN.md §4。
界面场景：`pnpm ui:check --page remote-connection-v2 --case remote-switch,remote-switch-batch,switched-here`。
未覆盖：手机作为发起端；两台真机之间的端到端验收待做。设置页与拓扑已实现，Agent 可发现的本机/跨电脑切换工具尚未接入，
属于同权能力待补的缺口，不是禁止 Agent 操作，也不宣称本次已经交付工具入口。

- 离线证书有效期默认 14 天，这是撤权窗口上限。

## 传输策略（2026-10-31 用户选择）

- 默认自动按网络和消息大小选择策略，同时允许用户明确覆盖为偏速度或偏省流；高级参数不作为普通使用的前置条件。
- 持久化时只保存用户显式覆盖，恢复默认时删除覆盖、重新跟随当前版本的自动策略。传输核心原型提供策略选项不代表客户端设置与持久化已实现。
- 继续逐项优化 KCP 对比中的落后项，速度、流量、CPU 与可靠性一起报告；不可未经验证就把落后归为产品取舍。
- 2026-10-31 用户确认“各方面都要比 KCP 好”的口径：KCP 的最快配置与最省流量配置互相矛盾，单一实现无法同时打败两者。
  默认自动策略的目标是在每种网络下，与该网络里最快的 KCP 配置相比，用时不慢、额外流量更少、交互延迟不高于 KCP 各配置的最好值。
- 同日用户选择速度优先：窗口受限且路径还有余量时，默认策略可以像 KCP 的 FEC 配置一样多发校验，换取不慢于 KCP 最快配置；
  流量仍须少于该配置。干净网络不多花一个字节的规则不变。
- 2026-11-02 用户决定和别的流量抢线路时的取舍：默认全速，同时提供一个让路的配置项。默认模式的行为和没有这个配置项时完全一致；
  全速时公网实测 TCP 约拿到 13%。让路时按 TCP 的规则发，见到丢包就减速，同线路的 TCP 能拿到接近一半甚至更多，
  代价是有随机丢包的路径上和 TCP 一样明显变慢。配置项在传输核心里是通用选项，不含产品判断；产品里什么时候用让路尚未决定，也没有设置界面。

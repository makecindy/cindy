# Agent 更新 Cindy

2026-10-10 Dash 裁决：用户说「更新 Cindy」时，Agent 可以在用户确认后通过内置更新器完成更新，
也可以帮用户开启／关闭空闲时自动安装更新。背景是 #5128 只留下了只读的 `check_app_update`，
Agent 只能反复引导用户去点「检查更新」；那次收紧的起因是 Agent 自己下载安装包替换应用并用
`launchctl submit` 注册重启脚本，导致 macOS 循环重启。

## 行为

- `cindy_helper` 的 `app_update` 类目：`check_app_update`（只读）、`install_app_update`、
  `set_app_auto_update`。后两者每次执行前都由宿主在调用任务上弹确认卡，**不看权限档**，
  完全访问也跳不过：卡片由 Main 通过 `requestHostPermission` 发起，不经 Agent 自己的审批回调。
- 确认卡复用通用 `permission` 交互（`cindy.app.update` / `cindy.app.auto_update`），桌面、
  同账号手机远控与 IM 渠道卡共用 interaction router 的同一决定，旧版手机无需升级。
  安装卡写明从哪个版本到哪个版本、Cindy 会重启、另有几个任务正在运行会被中断（重启后在任务里点
  「继续」恢复）、是否还有后台工作（后台命令、媒体生成、Subagent、自动化运行等，口径同
  `relaunchBusyActivity.ts`，读不出按有）会被中断、本任务在这轮回复后重启、远程连接会短暂断开；Linux 另提示需要输入系统密码。
- 确认后走「设置 → 关于」同一条更新状态机：`checkForUpdate()` 下载（单飞，重复调用不重复下载），
  等调用任务这轮回复结束（最多 2 分钟）后 `executeRelaunch()` 重启；Windows / Linux 会等更新器真正启动
  （5 秒内成功即退出、失败即写回原因）再收尾。确认卡总是写明具体目标版本（后台正在下载时用实际下载的版本；读不到就不弹卡），安装只认卡片上确认的版本：
  渠道期间换了新版本、或有更新的版本正在下载覆盖时（与内置横幅一致，不在 superseding 时重启）不安装，提示重新发起。安装绑定确认时的账号：退出或切换账号会取消重启，
  标记与结果消息只写回该账号，绝不写进后来的账号。拒绝、超时或卡片未送达都不下载、
  不重启。同一时刻只有一个安装请求；确认卡等待中或已开始安装时再次调用直接返回当前状态。
- 结果写回分两种，互不阻塞：
  - **真的要重启时**：更新器启动前的最后一道检查里，在账号私有目录写一份重启标记（写不进就不重启）。
    新版本启动、该账号数据库就绪后，把结果（新版本号或「仍是旧版本」）作为一条普通助手消息写回发起任务，
    桌面和手机重连后都能看到；写入暂时失败保留标记下次再写（按 clientId 去重），任务已不存在或超过
    7 天才丢弃。标记文件按请求逐条保存重启记录，新记录追加而不覆盖（不设条数上限，只在写回、任务不存在或超过 7 天时移除；文件里有任一条读不懂时整份移到一边再写，删除已送达记录时原样保留读不懂的条目），每条各自写回、各自清除。
    设置页或空闲自动安装已经在重启时，Agent 不认领那次重启，直接说明 Cindy 已在重启更新。
  - **没有重启时**（下载失败、版本变化、切换账号取消、更新器没启动等）：不写磁盘，按错误码生成本地化原因
    放进内存待写回列表（不设条数上限，只在写回或任务已不存在后移除），立即写回；写不进或原账号不在时保留，在该账号下次就绪或下次发起更新时重试。
    这类通知不阻止发起新的更新；进程退出时未写回的会丢失（可接受，不为此新增持久化）。
- 自动更新开关写入既有 `auto-update-settings-store`（用户显式 override），与设置页同一开关。
  `check_app_update` 在有可安装更新且开关未开时返回一次 `autoUpdateHint`，同一任务内只提示一次。
- 不支持的构建与安装环境（开发版、个人版、版本无关包、未移入「应用程序」、Linux 非受管安装、
  Windows 缺运行库等）沿用 `agentUpdateApplyBlockReason`，明确返回原因。

## 谁能触发

只有主人本人发起的轮次能触发，没有正面证据一律拒绝（`OWNER_TURN_REQUIRED`）：

- 桌面与同账号手机：输入协调器里当前轮次的输入必须是主人亲手输入的文字；自动化、其他任务
  （`send_to_session`）、Orca、插件、共享任务访客、自动续跑（含零输出自动重试）、合成指令都不算。
- 个人 IM：沿用控制命令的主人判据（私聊已过渠道 owner 门；群里看发言人 `isOwner`）；这一轮里有别的输入插话进来后，本轮不再算主人发起。
- 个人微信：私聊联系人无法证明是主人（其权限策略本就记为 `requesterAuthority: unknown`），一律拒绝，
  主人可在桌面、手机或其他已验证主人的渠道发起。
- 官方 Hook：其轮次在 maker-core 里记为自动化来源，与 scheduler 一样拒绝；主人请用桌面、手机或个人 bot。
- scheduler / goal 轮次一律拒绝。

共享任务访客即使看到卡片也不能回答：device-link 共享任务门禁按工具名拒绝这两类确认。
远程任务（SSH、远程 Agent）不暴露 `app_update` 类目，按既有边界只能更新任务所在的那台 Cindy。

## 手机

手机没有远程修改被控端设置的入口（updater 类 channel 属 device-link allowlist「永不放行」），
本功能不新增 channel，也不改手机端代码：手机上通过 Agent + 确认卡完成更新或切换自动更新。

## 提示词

host system prompt 只保留模型自己推不出、代码又拦不住的部分：

- 用户要更新时调用 `install_app_update`，由宿主向用户确认（工具藏在 `cindy_helper` 二级目录，不提示找不到）。
- 工具报无可装更新或不支持时转述原因、不旁装 Release；工具不可用（如远程任务）时引导用户到 Cindy 所在电脑的设置里检查更新。
  不支持的安装环境里内置「检查更新」同样装不了，不能一律引导去点它。
- 除非用户明确指定这种方式，不用 shell 下载、替换、结束或重启 Cindy：完全访问下代码拦不住 shell，
  而工具报不支持时模型仍可能退回自行安装；用户明确要求的源码构建、个人版替换、包管理器升级不在禁止之列。
- 任何情况下都不注册持久重启任务（如 `launchctl submit`）：这是循环重启的直接原因，重启由内置更新器负责。

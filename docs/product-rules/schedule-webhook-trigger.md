# 自动化任务的 Webhook 触发

> **读取时机**：修改自动化任务的 Webhook 触发条件、接收服务、事件排队、密钥或相关界面前。

## 用户行为

任务可以被外部事件叫醒。表单的「触发方式」直接选择「定时 / 手动 / Webhook」，与「执行方式」的 AI 任务 / 仅运行脚本相互独立。选择 Webhook 后只由事件触发，需要按时间执行时选择「定时」。2026-11-04 用户确认移除「同时定时检查」及其时间选择器，避免重复配置和重复执行；表单不再提供新增组合触发的入口。已有的定时 + Webhook 配置在未切换触发方式时原样保存，不因移除入口而改写用户数据。定时的一次性任务不能与 Webhook 并用，否则第一个事件就会把它用完。

三种触发方式共用「创建」和「保存」按钮。创建 Webhook 自动化只创建配置，不表示已连接发送方，因此不使用「创建并连接」。创建后直接选中其详情。连接区域平时只显示发送方、最近接收状态和「连接设置」，让运行记录在首屏可见；地址、密钥、事件筛选摘要、更换操作和账号地址管理集中在展开区，不再常驻展示整套配置教程。每个自动化仅在首次配置且缺少密钥时自动展开；本机只记录是否已展示引导，切走或重新打开后默认收起，不因尚未配置密钥而再次展开。生成的新密钥在状态刷新后继续显示，供用户复制；有了接收记录后不再重复测试说明。连接异常、缺少密钥、未验证签名的风险和已释放后的「重新连接」入口始终可见。运行记录不额外显示 Webhook 标签。顶部原有运行、编辑、停用、删除操作保持原样。此交互使用原有 `manual` / `webhookTrigger` 字段，不改变调度协议；纯 Webhook 的 `manual: true` 是存储语义，不再显示为手动触发。实现见 `ScheduleFormDialog.tsx`、`WebhookTriggerPanel.tsx`，回归见 `ScheduleFormDialog.test.tsx`、`WebhookAccountManager.test.tsx` 与 `webhook-detail` 单页场景。

Webhook 表单沿用自动化编辑器的「内容与触发 / 运行选项」分页：发送方、事件筛选和提示词在「内容与触发」，任务复用、通知与前置检查在「运行选项」。签名验证仍放在「高级设置」，编辑已有关闭签名的配置时自动展开。切换分页或收起设置只影响显示，不清除配置。未登录而无法配置 Webhook 时，普通运行选项仍可编辑。

使用 Webhook 必须有 Cindy 账号。未登录或当前环境没有部署 webhook-server（端点清单的 `webhookApiBaseUrl` 为空）时，不提供新建 Webhook 的选项；已有配置仍显示为 Webhook，但不能配置连接，保存其它字段不清除触发条件。退出登录后暂停接收，重新登录后恢复。

开启后，任务详情显示接收地址。关闭触发条件后，地址和密钥一并作废，再次开启得到新地址。修改事件筛选或发送方不改变地址。地址泄露时可以在任务详情里更换，旧地址立即失效，配置、密钥和暂存事件都保留。

事件筛选使用按发送方分组、可搜索的多选列表，默认明确显示「全部事件」，已选事件以可移除标签呈现。取消最后一项不自动扩大为全部：须在选择器中明确选择「全部事件」或另选事件后应用；取消选择器保留原配置。常用目录不是白名单，未收录的已有值原样保留，自定义名称通过高级入口逐项添加并校验。Standard Webhooks 和自定义格式没有固定目录，明确说明后提供相同高级入口。

存储仍是 `event` 或 `event.action` 列表，例如 `check_suite`、`pull_request.closed`、`pullrequest:created`；空列表响应全部。界面不改变接收协议，不收集事件正文。预设目录与交互见 `webhookEventOptions.ts`、`WebhookEventSelect.tsx`，保存行为回归在 `ScheduleFormDialog.test.tsx`。更细的判断交给前置检查脚本，它和脚本模式任务都能收到事件元数据。

## 账号接收地址管理（2026-11-04）

同一区域的账号默认共用 10 个接收地址，界面使用服务器返回的上限，不写死数字。
Webhook 配置和详情提供「接收地址 已用 / 上限 · 管理」，管理面板按电脑分组显示自动化名称、
最近接收时间和按需展开的地址。本机条目可跳到自动化；编辑表单内不提供跳转，避免丢失未保存内容。
旧版本未上传名称时显示可识别的 ID 后缀。暂停自动化不会释放名额。

用户可以释放本账号任意电脑的地址，电脑离线也能操作。确认就地展开，明确目标电脑与自动化、
旧地址及密钥失效、服务器暂存事件清除；自动化和运行记录保留，已开始的运行不受影响。
释放成功后重新读取用量，失败或结果未知时隐藏旧用量，先刷新核对，不能把请求已发送当成成功。

服务器为“账号 + 设备 + 自动化”保存独立释放记录，普通同步、旧客户端重连和旧服务副本均不能重建。
新客户端收到变更通知或重新连接时读取释放记录、清除本地待运行队列；启动新 Webhook 运行前再次核对，
无法确认状态时暂缓。旧客户端升级前可能执行已经保存在本机的事件，但无法重新占名额。
原自动化详情显示「已释放」并提供明确的「重新连接」：使用最新释放记录恢复，仍受账号名额限制，
生成新地址且不恢复旧密钥，用户须重新配置发送方。限额不足或过期恢复请求不清除释放记录。

账号清单及释放仅使用登录账号身份，不能由调用参数指定账号；密钥不进入清单。
账号切换立即清空界面与通道缓存，丢弃迟到响应。服务尚未升级时显示不可用，原有设备接收接口保持兼容。

## 发送方

表单里选择发送方：GitHub（默认）、Gitea / Forgejo、Bitbucket Cloud、Linear、GitLab（签名令牌，19 及以上）、GitLab（Secret token）、Standard Webhooks（OpenAI、Anthropic、Supabase 等）、Stripe，或自定义。预设决定两件事：怎么验签，以及事件名、投递 ID、仓库、编号等字段在请求的什么位置。预设定义在 `packages/maker-scheduler/src/webhook-formats.ts`。

- **服务器只执行格式描述，不内置任何一家的规则。** 新增发送方只在客户端加预设，不改服务器。格式校验在客户端和服务器各有一份（服务器 `webhook-server/src/core/format.ts`），两边一起改。
- **默认验证签名，可以关闭。** 关闭后拿到地址的人都能触发任务，并消耗每天的接收次数，所以表单和任务详情都说明风险，任务详情提供更换地址。关闭签名只去掉验签，事件识别照旧。签名防的是地址泄露，与用量高低无关：地址出现在发送方设置页、CI 输出和日志里，比密钥更容易泄露。
- **密钥有两种来源。** GitHub、Gitea、Bitbucket 由 Cindy 生成，用户填到发送方；Linear、Standard Webhooks、Stripe 由发送方生成，用户粘贴到 Cindy；两种 GitLab 与自定义都可以。生成的密钥只显示一次；粘贴的密钥保存后清空输入框，不回显。签名方式变了（比如从 HMAC 换成令牌）原密钥失效，需要重新设置。签名地址没有匹配的密钥时，事件一律被拒绝。
- **自定义格式是一段 JSON**，规则见 cindy-server 的 `docs/webhook-server.md`“发送方格式”。切到自定义时以当前预设的格式作为起点。
- **要求接收方回传握手值的服务接不了**，比如 Slack 的 `url_verification`、飞书事件订阅的 challenge。服务器回什么由服务端代码决定，格式描述管不到。
- **本机认不出的发送方原样保留。** 更新版本写入的预设，旧版本既不改它，也不按 GitHub 同步到服务器；新地址无法创建时报错。

## 事件只是门铃

- 请求正文不落盘，也不交给任务，服务器和本机都一样。只提取固定字段：投递 ID、事件名、action、仓库、编号、发送者、head SHA、CI 结论。标题、正文和评论都不进入。
- 这些字段以 `untrustedJsonBlock` 包裹追加到本轮消息，不进 system 段，也不写入任务的 prompt。自动审阅判断用户意图时只看任务自身的 prompt。
- 任务需要细节时自行从来源读取。所以重复、乱序或丢失的事件都不会让任务依据错误事实行动。

## 合并与运行次数

事件密集时不能每个事件跑一轮。2026-11-02 实测 `makecindy/cindy` 一周约有 704 个新 PR、502 个新 Issue 和 4000 多条评论。

- 先短暂等待（15 秒）把同一批事件合并。
- 同一任务同一时间只跑一轮；运行中新来的事件合并成下一轮。定时条件正在运行时，事件也等它结束。
- Webhook 属于自动运行，共用调度器的并发上限；满载时事件留在队列，30 秒后重试。用户点击“立即运行”仍沿用手动运行规则。
- 两轮之间至少间隔 5 分钟。这是固定值，第一版不开放设置，也是控制模型费用的主要手段。
- 单批最多带 20 条事件详情，其余只计数。
- 服务器也按 15 秒合并、5 分钟间隔推送，并有地址数和接收次数限制，见 cindy-server 的 `docs/webhook-server.md`。客户端的合并仍然保留：离线后补推的事件和本机入口都走它。

## 接收次数

每个账号每天有 3000 次 Webhook 接收次数。通过验签的投递都算，只有 ping 不算：被筛选和重复的投递一样要读请求体、验签，所以 Cindy 里的事件筛选不省次数，要在发送方只勾选需要的事件，表单里有这条说明。

次数用完后，发送方收到 429。这个 429 用户看不到，所以服务器会告诉账号的所有在线电脑：任务详情显示恢复时间，并发一次系统通知，`schedule_get` 的 `webhookStatus` 也能读到 `problem: "quota"`。文案说“Webhook 接收次数”，不说“配额”，并写明定时运行和模型额度不受影响，否则用户会以为是模型用量用完了。

恢复时刻是下一个 UTC 0 点，界面按本地时间显示。

## 可靠性

- 服务器落盘后才回 2xx，落盘失败回 503，让发送方可以重投。
- 服务器暂存事件，电脑离线时每个地址保留最新 20 条和总数，24 小时后过期。
- 客户端把事件落盘后才向服务器确认，所以投递语义是至少一次：没确认的批次会重发，超过 20 条详情的部分只累加一次计数。
- 同一服务器批次的事件、投递回执与省略事件计数必须在一次队列事务里落盘；失败时全部不提交，重投或重启后不得漏计或重复累加。队列在前序写入完成后读取最新触发条件，按当前筛选逐项接收，不使用宿主异步刷新中的旧筛选；批次携带的本机路由身份必须仍匹配。回归见 `webhook-queue.test.ts` 与宿主 `host.test.ts`。
- 重复投递按投递 ID 在 24 小时内去重（重复的投递仍计入接收次数）。去重记录写满时淘汰最旧的，不拒收：（已移除的 V1）例行任务的回执满了就拒收，是因为重复会强制重新执行；这里的重复最多多叫醒一次，而活跃仓库一天可能有几千个事件。
- 已接受但还没开始运行的事件在重启后继续。准备批次保留到运行记录落盘后，队列交接也落盘成功才允许执行；任一步失败保留事件。已经交接的运行不重放，因为无法确认是否已产生外部副作用。
- 目标任务忙而被顺延时，这批事件留在队列里 30 秒后重试，不走定时重放，否则事件内容会丢。
- 暂停或过期的任务不运行，事件计入“已忽略”；恢复时不补跑。队列在准备执行前和持久交接前都读取任务状态，避免等待服务器刷新或运行记录写入期间暂停／到期仍启动；最后复核已失效时，持久记录该批次为已忽略，拒绝交接且不重试旧批次。关闭触发条件或删除任务同样拒绝交接。
- 排队事件持久记录本机触发路由 ID，准备与交接时都须匹配当前配置；关闭再开启后，旧路由的待执行、准备中及重试批次不得进入新配置。清空队列同时取消尚未完成的交接／顺延，迟到结果不能把旧事件重新塞入队列。旧版未记录路由 ID 的队列沿用当前配置恢复，后续落盘补齐 ID。
- GitHub 不会自动重投失败的投递，超过配额或离线超过 24 小时的事件会丢。需要不漏事件的任务应保留低频定时条件兜底。

## 服务器通道

正式入口是 webhook-server（`scheduler-host/webhook/remote.ts`），合同见 cindy-server 的 `docs/webhook-server.md`。

- 地址属于“账号 + 设备 + 任务”，由服务器生成。客户端按任务同步：缺的创建，筛选或发送方格式变了就更新，服务器上多余的删除。格式按同一份校验规整后再比较，键的顺序不影响结果。
- 本机按账号持久保存触发条件的路由身份，不保存云端密钥。关闭后重新开启即使发生在离线、登出或重启期间，也须先清理旧待执行事件、撤销旧地址，再创建新地址，不能复用旧密钥；删除未确认时保留身份记录并暂停投递，恢复后丢弃旧地址的迟到批次。创建请求发出前先落盘身份，防止服务器已创建但响应丢失。
- 详情状态每次请求结束后再等待 30 秒刷新，同一面板至多一个在途查询；配置变化等待在途请求结束后读取最新状态，离开页面停止后续请求。
- 只有存在开启了触发条件的任务时才保持长连接。本机不开端口。
- 服务器按地址的发送方格式验签。密钥由服务器加密保存，所以伪造请求进不了队列、叫不醒电脑，也不占配额；不签名的地址除外。
- 中国大陆版和 Global 各部署一套，`webhookApiBaseUrl` 按区域锁定，地址不跨区。
- 账号被封停时（关闭码 4403）不自动重连，任务详情说明原因。被同一设备的新连接替换时（4409）不抢回连接，普通清单或任务刷新不会解除此状态；账号切换或重启后才重新接收。
- `XDT_SCHEDULER_PASSIVE=1` 的实例不连接。切换账号时停止，并取消尚在加载模块的旧启动，防止旧调度器在停止后重新发布。启动失败时撤销该实例和账号监听、停止已创建资源并保留原始错误，使后续启动可以重试；旧实例迟到的失败不得停止新账号实例。
- 宿主创建时固定所属账号的数据目录，队列、身份记录及开发版密钥的读写／清理都沿用该目录。停止前已进入的队列操作即使迟到完成，也只能写回原账号，不得覆盖新账号的队列；停止后不执行新运行。回归见 `scheduler-host/webhook/__tests__/host.test.ts`。

## 开发版本机入口

正式版没有本机入口，否则未登录也能使用 Webhook。开发版设置 `XDT_SCHEDULE_WEBHOOK_LOCAL=1` 后才启动，用于不依赖服务器联调；公网事件需要自己转发，比如 `gh webhook forward`。这时密钥存在本机，走 `credentials-and-local-storage.md` 的 safeStorage，不访问服务器。

- 只监听 `127.0.0.1`，只有存在开启了触发条件的任务时才启动。
- 只认 GitHub 格式，必须通过 `X-Hub-Signature-256`（HMAC-SHA256）校验，不看任务的发送方设置；密钥一律由 Cindy 生成，也不能更换地址。路由 ID 由引擎生成，调用方不能指定。
- 请求体上限 5 MiB，请求超时 15 秒。

## 多端与 Agent

- Agent 通过 `schedule_create` / `schedule_update` 配置事件筛选和发送方（`webhookTrigger.source`），通过 `schedule_get` 的 `webhookStatus` 读接收地址和状态。未登录或没有接收服务时开启会报错，而不是让任务静默收不到事件。Agent 拿不到密钥，也不能设置：明文进入对话记录违反凭证规则，参数里夹带密钥会被拒绝，所以由用户在任务详情操作。更换地址也只在任务详情。
- 编辑时省略发送方表示不修改，所以不认识发送方的旧客户端、手机和跨设备编辑都不会把它改回 GitHub。
- 账号管理通过 `schedule_webhook_list` / `schedule_webhook_release` 查看与释放本账号所有电脑的地址，旧电脑离线不影响释放；`schedule_webhook_restore` 明确重新连接，可用 `device` 指向在线的目标电脑。写操作沿用任务权限。
- 跨设备不开放密钥或普通地址轮换。`maker:schedule:webhook-status`、`webhook-receiver`、`webhook-account`、`webhook-release`、`webhook-restore` 在同账号 Device Link 白名单内；`webhook-set-secret`（携带密钥）和 `webhook-rotate-url` 不在。是否显示开关由任务所在电脑决定，所以读 `webhook-receiver`，不看控制端的登录状态。共享任务与供应商访客无账号管理权限。
- `supportsScheduleWebhookTrigger` 标记主机支持；旧主机只保留已知列，会报告成功却丢掉配置，新调用方须先查这个标记。
- Agent 设置或清空远程任务的触发条件复用原有创建／更新通道：先检查目标电脑的能力标记；开启时再检查目标的 `webhook-receiver`，只有已登录且有接收服务才发送写入。清空不要求接收服务可用。预读与写入均保留同账号访问复核，不新增密钥、权限或传输通道。
- `schedule_get(device=...)`（含 `all`）查询到目标电脑的 Webhook 配置后，再通过同一电脑的 `maker:schedule:webhook-status` 补齐接收地址和状态。普通或不存在的任务不增加读取；状态接口返回空值时沿用本机的无状态结果，接口失败则明确报告该电脑查询失败。两次读取共用账号复核，不新增轮询或重试。
- 旧客户端读写新主机时配置保留：缺 key 表示不修改。纯 Webhook 任务存为 `manual: true`，旧版本只显示“手动”，不会按占位 cron 触发。
- 项目文件自动化不支持：地址和密钥不能进仓库。复制任务不带 Webhook 配置。

## 要解决的问题

自动化现在能被两类外部事件叫醒，都写死在宿主里：

- **GitHub App**：`webhookTrigger.source = {preset:"github-app"}`，服务端 App 验签后经设备长连接推送。
- **普通 Webhook 地址**：发送方预设（GitLab、Linear、Stripe 等）由 `webhook-formats.ts` 描述。

两者共用同一条后半段：本机按范围复核，进入 `ScheduleWebhookQueue` 持久队列，然后由 runner 把元数据
作为不可信块附在本轮消息后启动任务。规则见 [Webhook 触发](schedule-webhook-trigger.md)。

缺的是“插件也能按门铃”。飞书、Slack、邮件这类来源的事件订阅要求回传握手值，或者只提供长连接，
普通 Webhook 地址接不了；它们的接入方式各不相同，按[核心产品原则](core-product-principles.md)的分工，
应留在插件里，宿主只提供稳定的事件原语。

插件发布事件的契约以前有过一版（`routineEvents` 声明 + `routine-request` publish 管子），
接的是伙伴例行任务；2026-11-08 例行任务退役后变成空操作（见 [伙伴例行任务 V1 存档](bot-routines.md#插件本地协议)），
[伙伴专属能力台账](teammate-capability-ledger.md)记着“插件事件源能否直接接到普通定时任务”待核实。本方案就是这一项的答复。

## 定位：通用事件来源，不是 IM 机器人

这不是 IM 机器人的另一种形态。IM 机器人是对话入口：有人找机器人，就开或续一个对话。
插件事件来源是自动化的触发条件，范围更广：用户自己的账号收到私信、群里有人 @ 我、来了新邮件、
文档被评论、日程变化、GitLab MR 更新……只要插件能观察到，就可以叫醒用户指定的自动化。
例如“只要有人给我发消息就触发”可以同时选飞书、Slack、邮件几个插件的“收到消息”事件。

两者互不替代，也不需要互斥：同一条消息既可能被机器人处理，也可能叫醒自动化，由用户的配置决定。

## 用户裁决（2026-11-23）

1. **过滤规则属于自动化。** 插件和宿主都不替用户丢弃事件，包括自动化自己在群里发的回复。
   插件应尽量多提供判断用的信息（比如发送者是不是当前用户本人、是不是机器人、这条消息是否由
   某个自动化发出）；要不要处理，由自动化的事件条件、前置检查或提示词决定。
   这取代 V1 的“带 `originRoutineId` 的事件不反向触发同一规则”和“接入端应过滤自己发出的消息”。
2. **接受离线限制。** 插件运行在本机，电脑休眠、关机或插件停用期间的事件收不到，宿主不要求插件补拉，
   也不做服务端暂存。需要不漏事件的，由用户自己加定时检查兜底。
3. **与 IM 机器人性质不同**，见上节。
4. **不为插件来源另设费用上限。** 触发多少次、花多少模型额度由用户自己负责。宿主为稳定性保留的
   发布频率、请求体量、并发和去重容量限制不属于费用上限，继续保留。

## 方案

### 插件声明与发布：复用存量契约

沿用 `routineEvents` 声明和 `routine-request`（`cindy.routines.request`）的 `status` / `publish`，
把 publish 从空操作改回真实接收，交给自动化队列。理由：

- 已安装插件的这项能力已经在安装批准里，复用不需要重新确认权限，符合存量插件兼容红线；
  新插件也不需要学第二套接口。
- V1 已有的校验与限额（来源由宿主从真实插件身份派生、声明过的事件类型、`data` 平坦且至多 32000 字符、
  24 小时去重、单插件 60 次／分钟、待处理请求上限、128 KiB 请求预算、固定失败文案）原样沿用。
- 如需更直观的名称，可增加 `cindy.events.publish` 等别名，但两者等价，旧名永久保留。

需要调整的地方：

- **事件信息更丰富。** `data` 仍只放平坦字段，但约定一组建议字段，插件能提供就提供：
  `senderId`、`senderName`、`fromSelf`（是否当前用户本人发出）、`fromBot`、`chatId` / `threadId`、
  `originScheduleId`（插件知道这条消息由哪个自动化发出时）。正文、附件和凭证仍不提交；
  任务需要全文时用该插件的工具去读。
- **常驻只在有人订阅时。** V1 声明了就常驻；现在改为：存在启用的、选了该插件事件的自动化时，
  宿主才启动并保持插件的监听，最后一个订阅关闭后停止。插件被停用时照旧停止。
- **`originScheduleId` 的来源**待实现时确定：插件自己记录，或宿主在自动化运行中调用插件工具时
  把调用方自动化告诉插件。无论哪种，都只作为信息附在事件上，不由宿主据此丢弃事件。

### 自动化侧：作为事件来源接入现有触发

- 存储复用 `webhookTrigger.source`，新增插件来源。初稿：
  `{preset:"plugin", sources:[{plugin:"<pluginId>", events:["message.received"], match?:{...}}]}`。
  多个插件或多个事件之间是“任一命中即触发”，共用同一队列和运行节奏。
  复用这个字段的好处是兼容路径现成：旧执行端拒绝未知来源，不会静默改成普通 Webhook；
  旧控制端编辑时省略未知来源会原样保留（见 [Webhook 触发](schedule-webhook-trigger.md#多端与-agent)）。
- 插件来源不需要接收地址、密钥、Cindy 账号或服务端；不占普通 Webhook 的地址名额和每天的接收次数。
- 事件只投给**插件所在电脑**上的自动化，不跨电脑转发。
- 事件条件只针对插件声明过的 `fields`，支持等于、包含、不等于（沿用 V1），同一来源内为 AND。
  更细的判断交给前置检查脚本或插件前置检查，它们收到同样的事件元数据。
- 进入队列后的合并、同一任务同时只跑一轮、忙时顺延、重启恢复、暂停时忽略，全部沿用
  `ScheduleWebhookQueue`。`ScheduleWebhookEvent` 增加宿主派生的来源，以及插件提交的 `subject` 和有限字段；
  继续以 `untrustedJsonBlock` 附在本轮消息后，不进 system 段，也不写进任务的 prompt。
- **两轮之间至少间隔 5 分钟这一条，对插件来源是否保留待定。** 它原本是控制费用的主要手段，
  而按裁决 4 费用由用户负责；但聊天类场景隔 5 分钟才响应可能太慢。实现前须由用户确定。

### 界面与 Agent

- 表单的触发方式「Webhook」改称「事件」，来源分组为：GitHub（通过 Cindy 连接／手动配置 Webhook）、
  其它 Webhook 发送方、已安装插件。插件来源只列出本机已启用插件实际声明的事件，不显示没有接入的入口。
  具体交互按设计规范另行设计，并记入本文。
- 插件监听状态（`listening` / `disconnected` / `error`）和最近事件时间显示在自动化详情的连接区域。
- Agent 与用户同权：`schedule_create` / `schedule_update` 接受插件来源；需要提供一个能列出本机可选
  插件事件及字段的查询（新增工具或扩充现有能力，实现时定），避免 Agent 猜事件名。
- 插件只能发布事件，不能创建或修改自动化、指定模型或执行方式；声明了 `hostTools: ["scheduler"]`
  的插件创建自动化，沿用已有的调度工具权限。

### GitHub App 保持内置，收进同一套来源

GitHub App 依赖服务端的 App 私钥、PR 跟进的精确订阅和免计次投递，不搬进插件
（2026-11-05 已决定不把 GitHub 整体搬进插件）。实现插件来源时，把散落在调度器、队列和
`scheduler-host/webhook/**` 里的 `preset === "github-app"` 分支整理为统一的事件来源接口：
各来源负责范围判断和投递健康状态，队列与执行只认接口。这是内部重构，存储、服务端协议和
用户可见行为不变。

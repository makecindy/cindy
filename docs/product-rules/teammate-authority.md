# 伙伴的来源与操作权限

2026-11-08 用户裁决：**伙伴不加专属权限。** 判断原则是「AI 能不能开一个任务去和别的任务说话」——
能（`send_to_session` 可以新开完全访问任务），那么只加在伙伴身上的权限门都是掩耳盗铃。
伙伴和普通任务走同一套权限：当前任务的权限档（Ask / Auto / 完全访问 / Plan）加上通用的 IM 机器人与共享访客边界。
本条取代 2026-10-29 的「自主轮少数明确风险确认」和 2026-10-23 的自主工具白名单。

## 已删除的伙伴专属门（2026-11-08）

- 每轮「代表谁」（`owner` / `entrusted` / `autonomous`）的判定与它驱动的风险确认卡
  （代答授权、恢复暂停、调度命令、新建完全访问任务、授予常驻指令、释放接收地址、重开能力）。
- IM 专线非主人发言时拒绝任务动作（`TASK_ACTION_SOURCE_UNAUTHORIZED`）、群里任务动作要求群主授权。
- 例行任务、新建伙伴、能力与应用设置、技能保存、`list_agents` 只认主对话／主人这一轮的入口限制。
- 伙伴发出的排队消息重启后丢弃、不能被接收任务插话或排序的规则。
- `send_to_session` 发送前「确认是主人委派的」自动审核（见下文「转达主人原话」）。

保留的不是伙伴专属权限：主人自选的设置（群「只聊天」模式、伙伴的代输入开关）、
伙伴暂停或归档后不再执行、账号切换与共享访客边界、IM 机器人通用的发言人策略。

## 等待、决定与恢复

- 没有实时权限档的自动输入仍走通用任务动作确认卡（`taskActionConfirmation.once`），进入普通
  `Session.runHostInteraction`，桌面、同账号手机／远控与已绑定 IM 共用同一请求；同一次放行只能消费一次。
- 同意到执行仍校验账号、实例、输入、权限与 Plan 代次；变更使这次放行失效。
- **延迟投递只认真实撤权**（2026-10-30 用户裁决：能力优先）：已准入的消息因目标忙而排队后，
  发起轮结束、发起方 Session 重建、换新输入，或发起方的权限档、计划模式变化，都不撤销这条消息；
  它由接收任务按自己的权限执行，主人可以在接收任务的队列里编辑或撤回。只有数据库客户端被替换
  （切换账号）、发起任务被清空或删除、伙伴被暂停或归档、Orca 团队变化时
  才不再投递；这类消息在落库前移出队列，不在接收任务里留下失败回复。清空以协调器的内存边界和数据库
  `cleared_at` 中较新者为准（`/clear` 先改内存、后写库，写库可能失败）；重启后晚加载的旧边界不算新的
  清空。「判不了」不算撤权：账号边界持有中但数据库客户端没换（同账号 Ghost 投影修复也会持有它）、
  数据库未就绪等校验失败，都不销毁消息，保留为可重试的队首。任务动作守卫只在消息
  落库之前判定（派发前预检，以及紧贴落库的那次复核）：确认撤权则不落库、不留痕地移出队列；落库之后
  不再由它截断，照常派发——此时拒绝只会留下用户行和失败回复，而排队的任务消息无法重试（重试会换新的
  clientId，守卫绑定的是原 clientId）。同理，已接受一轮的续跑／重试副本（自动或手动的「继续」、零产出时重发原文）
  不再重新校验发起方的投递授权，也不继承守卫与「需授权」标记，按接收任务自己的权限执行，来源与主人原话照旧保留；
  从未落库的队首重试仍走守卫。实现见
  `taskActionHost.ts` 的 `assertDeliveryCurrent`、`taskActionAuthorization.ts` 的 `isTaskActionRevoked`
  与 `agent-input-coordinator.ts` 的派发前复核、`acceptTaskActionRecoveryCopy`；回归见 `taskActionAuthorization.test.ts` 与
  `agent-input-coordinator.test.ts`。

## 转达主人原话（请求来源）

- 代办轮由宿主在回执上标授权。新建任务和后续转交沿用同一份原话及
  `sessionId/clientId`；当前已接受输入中的核实结果不会因为换了接收任务或伙伴而降权。
  仅从旧历史读到回执、没有当前受托输入时，不恢复旧请求；自主触发、插件与共享访客不能自行生成凭证。
- 接收方的任务写工具把这类输入视为原请求的继续，仍按当前权限档审风险；不要求主人重复复述。
  它不等同于主人刚刚亲手输入，应用更新等专门要求本人输入的操作保持原有边界。
- 空闲、繁忙和新建任务共用持久输入协调器，插话、重试及历史恢复都保留原话；审核上下文不采用 Agent 补充
  里的授权说法。原话不明或缺少背景时，先按来源任务查上下文，只有仍缺少必要决定才向主人提问。
- IM 轮次不经过输入协调器：原话取自 IM 运行器写在逐轮租约上的本轮落库消息（`inputClientId`），
  只在租约的发言人是主人时读取。
- 伙伴群轮次（2026-11-11）经输入协调器，但发给模型的是宿主拼的群信封（隐藏指令）：只有触发消息是这台电脑
  主人本人发的、群为主人授权模式时，`chatServer.ts` 才在这一轮旁边放上主人原话；协调器的
  `isActiveInputOwnerContinuation` 认这份原话，所以这一轮里新建或转交的任务同样带主人授权。其他成员或伙伴
  触发的轮次没有原话，转交照旧不带授权；群轮次也不算主人亲手输入。
- 主人输入被自动续跑（包括生成的「继续」消息）仍算主人代办，但不算新的主人输入，
  不能用于应用更新这类只认主人亲手输入的操作。
- 2026-11-08 起，本轮代表用户（用户本人输入、其自动续跑、已核实的转交，IM 里主人发言的一轮，或群里主人本人发言触发的一轮）时，转交直接带
  用户授权，不再由发送端审核模型另判；Plan 下只发普通消息。回到原话所在任务的消息不带授权。
  （[消息来源](message-source.md)「跨任务委派：代办轮的转交带授权，正文是原文」）
- 接收任务看到这类回执（`plainBody` + `delegatedText`）时：
  - Auto 审核的意图是这段委派内容本身；回执只记原请求出处的编号，不带用户原话文字；
  - 模型收到的 `[消息来源]` 说明这是发送方宿主已核实的用户委派，正文就是 Agent 写的原文。
- 旧发送端的回执（无 `plainBody`）仍按原规则：意图是那句原话，`[消息来源]` 说明「用户原话」是用户请求、
  「Agent补充」只是背景；三行正文照旧逐字校验。
- 跨电脑：`requestSource.ownerVerified` 是可选字段。旧接收端忽略它，行为与之前相同；
  旧发送端不发它，新接收端按未核实处理。
  新发送端只在接收端声明 `plainRequestBody` 时发原文；旧接收端继续收到原话与三行正文。
- 结果回传由发送方自己决定（2026-11-09）：在消息里请对方做完用 `send_to_session` 发回，或之后自己用
  `get_task_digest` 查看；宿主不代为回传。回发的消息是对方任务的普通来信，不带用户授权。

## 实现入口

- 任务动作准入（伙伴与普通任务同一条路）：`apps/desktop/src/main/maker-ipc/taskActionHost.ts`、
  `taskActionAuthorization.ts`。
- 主人输入与自动续跑：`agent-input-coordinator.ts` 的 `isActiveInputOwnerAuthored` /
  `isActiveInputOwnerContinuation`。
- 转交授权：`register.ts` 的 `captureSessionAgentRequest`、`forwardedRequest.ts` 的 `captureAgentRequest`、
  `shared/forwardedRequest.ts`（`verifiedOwnerRequestText`），模型说明见 `messageSourceNote.ts`。
- 回归：`maker-ipc/__tests__/taskActionAuthorization.test.ts`、`forwardedRequest.test.ts`、
  `messageSourceNote.test.ts`、`sessionHandoffRemote.test.ts`、`agent-input-coordinator.test.ts`。

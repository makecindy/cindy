# 归档绑定了自动化的任务前先确认

## 适用场景

任务被一个或多个**运行中**（`active`）的自动化绑定（`targetSessionId` 指向该任务），用户手动归档这个任务。

## 现有行为

自动化下次触发时，按用户向已归档普通任务发送消息的语义恢复原任务，沿用原会话历史与工作目录，
完成后保持激活，不重新归档。**持续会话**（`persistentSession`）同样恢复原任务，不会仅因归档另建替代任务。
归档那一刻本身不改动自动化；归档或取消归档都不会重新启用已暂停的自动化。
删除或丢失目标、伙伴例行任务及协作托管任务继续遵循原有生命周期，不适用普通任务恢复规则。

实现入口：`apps/desktop/src/main/scheduler-host/restore-target.ts`、`runner.ts`、`script-runner.ts`；
回归用例见同目录 `__tests__/runnerSendOutcome.test.ts`、`runnerModelSelection.test.ts`、`scriptRunner.test.ts`。

## 产品不变量

1. **归档前先确认**：普通任务绑定了运行中的自动化（包括持续会话）时，用户入口先弹确认，
   写明自动化仍会运行并恢复此任务（单个任务列出名称，批量归档给出受影响的任务数）。
2. 没有这类绑定的普通任务维持「归档不弹确认」的原有体验，不增加等待。
3. 已暂停、已过期的自动化不提示。提醒名单目前只按 `active` 状态和 `targetSessionId` 绑定筛选，
   不按 `source` 排除伙伴例行任务：若其绑定目标进入普通归档入口，也会被列入提醒。这是现有提醒的
   已知边界，不代表伙伴或协作托管任务会被普通恢复入口激活；它们仍按各自生命周期管理，
   本次不扩展绑定投影或新增来源过滤机制。

提醒筛选实现与回归见 Desktop `archiveScheduleWarning.ts` / `__tests__/archiveScheduleWarning.test.ts`
和 Mobile `archiveScheduleConfirm.ts` / `src/__tests__/archiveScheduleConfirm.test.ts`。

## 原因

归档只收起当前任务，不代表停止后续自动输入。归档前说明自动化会恢复原任务，避免用户误以为
归档会暂停自动化，也避免持续会话因归档换绑而分散上下文；与
[`core-product-principles.md`](core-product-principles.md)「自动任务与归档」保持一致。

## 验收

- 桌面：侧栏单条 / 行内归档、灵动岛完成卡滑动归档、批量归档、项目「全部归档」、标题栏菜单、硬件快捷键、文件浏览
  模式关闭任务，遇到上述绑定时均出现带自动化提示的确认。
- 手机：滑动归档、选项菜单归档、任务详情菜单归档弹系统确认；设备页批量归档的确认条显示
  受影响的任务数。

## 允许的例外

- 绑定信息读取失败（如远程电脑暂时不可达）时，入口按「无绑定」直接归档，不阻塞归档。
- 桌面本机优先使用已有的自动化缓存；冷启动缓存未就绪时最多等待约 1.5 秒，超时按「无绑定」处理，普通任务的归档不会卡在自动化列表请求上。
- 已知边界（不为此新增机制）：桌面本机在自动化刚被创建 / 恢复 / 改绑的同一瞬间，若恰好有一次更早发出的缓存读取还在途，归档提醒可能读到变更前的列表而漏掉新绑定。后果只是漏掉提醒，自动化下次触发仍会恢复原普通任务，不丢数据；不为此给共享缓存增加排队重读机制。
- Agent 工具（`archive_sessions`）与 IM 渠道的归档没有确认界面，不在本规则范围内。

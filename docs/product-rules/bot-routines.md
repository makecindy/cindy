# 伙伴例行任务：本地触发与执行

## 产品合同

2026-09-07，用户批准借鉴 Grok Bot 的 Routine 交互，明确第一阶段只做本地内部协议，不建设公网 Webhook。参考仓为 `zqchris/grok-bot-0.18-reconstructed`，它是重建版本；Cindy 复用现有伙伴与调度执行器，不恢复旧版伙伴的项目、outbox 或独立会话管理器。

一条例行任务属于一个伙伴，包含名称、常驻指令、启用状态和多个触发条件。条件之间是 OR：同一事件命中多个条件只入队一次。时间条件与事件条件可以共存，适合「PR 更新时检查，每小时兜底」。条件编辑不授予模型额外权限。自主创建启用的自定义规则或改写启用指令须经本人确认后才成为后续运行的常驻授权；禁用草稿可普通保存，手动执行停用规则须走同一恢复确认。只改名称、时间且沿用原指令及命令不追加授权。判据与版本绑定见 [伙伴操作权限](teammate-authority.md)。

桌面入口在伙伴设置「例行任务」及伙伴任务的标准右侧栏。已创建的例行任务 Session 也进入桌面和手机任务列表，按真实伙伴归属显示头像、参与伙伴来源筛选；仅有自动化规则、尚未创建 Session 时不凭空生成列表任务。桌面侧栏把同一伙伴同一条规则的多条运行（「每次新建任务」）收进与普通自动化同款的文件夹（2026-10-29），组头显示规则名与伙伴头像，计时图标打开该伙伴的「例行任务」页，更多菜单只提供标为已读；依据是列表投影的 `companion.routineId`（由 `route_key` 解析），旧主机不提供时维持平铺。列表里的普通规则和内置规则都用右侧开关直接启停，文字明确显示启用／暂停，排队／运行中单独显示，不以时钟或暂停图标代替状态。点普通规则名称进入详情，仍可修改指令、立即运行、增删触发条件、删除规则和查看历史；历史的失败／中断结果在展开前可读。立即运行先保存当前编辑，再运行，避免执行屏幕上看不到的旧指令。

时间描述跟随界面语言，复用调度器的 Cron 解析规则，保留全部小时、分钟、日期与 IANA 时区；复杂条件可展开，多个条件明确为满足任一项即运行。不依据前端时钟推测下次执行，也不把配置更新时间当作最近结果。定时菜单提供每小时、每天、工作日、每周、每月、间隔和高级 Cron。事件菜单来自实际插件声明，不显示未接入平台的假入口。

顶部「跟进我的任务」控制是否把主人创建的本机任务也交给当前伙伴；下方「跟进已接手的任务（内置）」响应已归属它的任务事件。两项独立，不合并开关；开启顶部设置仍保留读取范围与模型用量的确认。列表启停不修改指令、频率、通知或静默配置。

手机端不提供例行任务管理（唯一例外是伙伴近况里「每天帮我查一次」开关，见下文「每天查待办例行任务」）：移除「所有任务」下拉菜单的 `routines`、伙伴资料页的自动化入口和旧的独立自动化管理页，旧管理链接返回设备页。具体界面边界与[伙伴运行时合同](./cindy-bots-runtime.md)一致；下文例行任务管理及高级设置均适用于桌面端。移除手机入口不删除已有规则、任务数据或运行历史，不改变桌面执行服务、Remote Resources 协议或 Mobile 原生依赖。执行仍发生在电脑，没有宣称云端补投能力。

## 分层与执行

Bot Market 原生包的例行任务只通过原导入服务保存停用定义，不接管来源 cron，不建立私有授权迁移绑定。邀请加入与工作执行分开；安装和欢迎不会启用或立即运行规则。用户随后在原伙伴例行任务编辑器明确选择时间、时区并保存启用，继续使用本页既有服务、版本校验与生命周期。

- `@cindy/maker-scheduler`：例行任务校验、匹配、去重、串行落盘和运行状态机。纯逻辑，不依赖 Electron。
- Desktop routines service：按当前账号保存本地文件，为每条规则创建或复用独立的伙伴任务，调用现有调度执行器。
- 插件：第三方身份认证、长连接、消息订阅或本地采集。向宿主报告事件，不指定伙伴、指令或执行权限。
- 桌面远程控制（2026-10-22）：控制另一台电脑上的伙伴时，桌面伙伴设置里的「例行任务」页就是本机同一个页面，列表、保存、立即运行、删除和运行历史由伙伴所在电脑的同一个管理服务执行（`management:settings` 的 `routines.*` 操作，见 [伙伴设置动作](../dev-rules/protocol-compatibility.md#伙伴设置动作-managementsettingsremote-resource2026-10-22)）；那台电脑上的例行任务变化会推送到打开着的页面重读。这是桌面入口，手机仍不提供管理。
- 桌面 UI / MCP / Remote Resources：共用管理服务，不能冒充事件来源。宿主保留 Remote Resources，当前手机端过滤 `routines` 集合及动作。MCP 管理仅走宿主绑定调用者身份的伙伴必备工具；通用 scheduler MCP 不提供可任意指定 botId 的例行任务入口。

每条需要 Agent 执行的例行任务对应一个持久独立 Session（`bot_session_links.role = 'routine'`，`route_key = 'routine:<routineId>'`），重复触发复用，不向伙伴主任务追加执行上下文。它与原伙伴共享 Profile、Home、记忆、技能和实际权限，权限与资料更新同样同步到专线；`list_agents`、`send_to_agent`、`check_agent_message` 沿用同一伙伴身份（含远程回执核验与排队恢复），逐轮行动授权与防循环上限不变；行动身份仍按本轮来源判定，内置跟进不会因独立任务变成主人授权。

`sessionMode` 决定触发之间是否保留上下文（2026-10-27）：`persistent`（缺省，兼容旧规则）复用上面的持久独立任务；`fresh` 每次触发由宿主新建一条同伙伴身份、同权限的独立任务（`route_key = 'routine:<routineId>:<uuid>'`），运行结束后关闭，下次触发不带旧上下文。两种方式都沿用该规则的 `modelOverride`，历史里的「查看任务」仍可打开每次运行的任务。`fresh` 任务若本轮从未派发给模型（pre-run hook 判跳过、批次延后、派发前取消、backing schedule 写入失败），宿主当轮回收这条任务且历史不挂「查看任务」入口；真实跑过的任务（含失败、中途取消）照常保留可回放（2026-10-30）。内置规则可改运行方式（界面「沿用同一任务 / 每次新建任务」），不改指令、频率与权限；夜间学习不提供此项。

例行任务专线与渠道专线（`role = routine / channel`）进入普通任务列表，生命周期也与普通任务一致（2026-10-30）：可以在列表里归档、取消归档、删除。归档后的持久专线在下次触发或下一条渠道消息时恢复原任务并保留上下文，与归档的普通自动化目标一致；删除后下次触发新建。伙伴主聊天、私聊话题、群专线等不在普通任务列表的伙伴 Session 仍由伙伴生命周期管理，通用归档／删除继续拒绝。判定见 `sessions.ts` 的 `isTaskListBotLane` 与终态写入 `sessions.setTerminalStatus`。

`modelOverride` 可单独选择完整模型路由（引擎、来源、型号、执行位置、推理强度、Fast）；缺失或 null 跟随伙伴模型，显式配置不套用伙伴主模型的备用链。旧客户端省略字段时保留已存选择，null 才清除。保存后下一轮通过普通模型切换与交接入口应用；独立任务内继续交流也使用这份配置。每条例行任务最多一个正在执行的运行；等待事件合成一批，各条规则通过各自任务队列派发。

独立任务保留完整执行记录，历史里的「查看任务」打开原有普通任务页面；静默只控制通知，不隐藏执行正文。它不进入自动跟进的观察列表，避免跟进自己的执行。伙伴迁走后，旧电脑上这条任务仍可回看，但普通发送、内部发送和排队派发都不能重新启动它。合成触发输入沿用原有来源说明。夜间学习已有专门宿主流程，不改为这类任务。

远程桌面沿用同一设置页，通过 `routines.saveWithModel` 能力协商展示选模；旧主机不显示选模，新主机接受旧客户端保存时保留覆盖。运行方式另由 `routines.saveWithSessionMode` 协商：只接受 `saveWithModel` 的旧主机会丢弃 `sessionMode`，因此不显示该选项，避免保存成功却仍共用上下文。手机当前仍无例行任务管理入口。模型配置随普通规则的伙伴迁移资料保留，执行任务与运行历史留在执行电脑。

事件、时间与立即运行触发的批次都以独立宿主作用域执行，不继承发布事件或发起调用的 Agent 轮次行动凭证；当前账号、伙伴状态、规则版本及目标任务的权限检查仍然生效。发布方轮次结束不使已接收批次失效，目标独立任务忙碌时沿用下述延期与重试规则。实现与回归见 [service.ts](../../apps/desktop/src/main/routines/service.ts)、[service.test.ts](../../apps/desktop/src/main/routines/__tests__/service.test.ts)（#7044）。

直接执行路径必须取得完整的持久权限/计划模式快照；已有 live Session 还必须提供稳定权限状态，并与持久权限一致。缺失、切换中或不一致时保留原批次延期，不回退到旧权限或把未知计划模式当作关闭。异步准备后在创建 Session 和直接发送前再次读取；冷恢复沿用已保存的有效权限和计划模式。运行信息回写跳过伙伴权限字段，不以普通自动化的默认完全访问覆盖用户选择或并发修改。

排队项被接受、即将派发时，再读取完整持久快照并确认当前 live 身份和稳定权限；排队项携带的权限及计划模式必须与之相同。缺失、切换或不一致时取消这次派发并延期原批次，重试重新取得当前设置。规则 revision 的宿主回调不落盘：直发和排队均在接受阶段的异步准备结束后复查；等待期间编辑产生的新 revision 会阻止旧 prompt 派发，旧批次取消，已经开始执行的正常运行不因后续编辑而被中断。

启动恢复时若调度器尚未就绪，同样保留原 queued 批次并在 30 秒后重试，不标记为失败。

伙伴忙碌导致的 deferred 保留同一待执行批次，30 秒后重试；宿主通过 runNow 的内部 deferToCaller 选项领取重试责任，底层不设置重试时间，不能由旧 backing schedule 另行重放旧事件。普通手动调度保持原有忙碌失败语义。已开始的执行失败不会自动重做，避免重复外部副作用。暂停或删除取消等待项并中止当前运行；修改规则取消旧版本等待项，下一次事件按新规则匹配。

停用规则时清除 cron/interval 定时游标，空闲 tick 不再因该规则写盘或广播；启动时一并清理旧文件中停用规则的残留游标，保留配置和历史。重新启用从当前时间安排下一次触发，不补跑停用期间的触发；停用状态仍可显式手动执行，且不会因此恢复定时游标。

执行已结束但终态落盘失败时，保留执行结果和该规则的运行锁；后续触发只能排队，不能再次执行。每 30 秒只重试保存原结果，成功后才释放队列；若在此期间重启，沿用 interrupted 恢复，不重放已执行项。其它规则不因单条终态保存失败而被停用。

伙伴暂停时阻止新触发、取消等待项并中止运行，保留每条规则自身的启停选择；恢复只重新安排原本启用的规则，不补跑暂停期间的触发。永久删除先停止执行、删除 backing schedule，再清除规则和包含事件数据的历史；清理失败时保留伙伴档案供重试。启动按当前伙伴状态恢复，清除已不存在伙伴的规则并阻止暂停伙伴执行。

删除单条规则时，先暂停该规则、取消等待项并等当前执行结束，再清理内部调度，最后删除规则和历史。清理或最终落盘失败时保留已暂停的规则与历史，支持用户再次删除；同一伙伴的其它规则继续运行。

内部 backing schedule 只供例行任务执行器使用。通用自动化列表、详情、历史与未读投影不暴露它，通用编辑、启停、立即运行、删除也不可操作它；伙伴自身的例行任务入口保留执行与清理能力。

账号切换或服务重建时，停止过程等待全部活动执行及其异步取消结束，完成后才允许加载替代引擎；定时检测账号变化与显式停止共用这一顺序。

恢复已有规则时，首次插件状态请求等待当前账号的本地数据库就绪后继续，不因启动顺序丢失来源注册。暂停或删除状态的恢复还会等待调度器就绪并完成内部调度清理；活跃伙伴不依赖调度器就绪即可注册来源。停止或账号变化取消旧等待，真实数据库查询失败仍返回错误。

重启时保留已接收事件的去重记录和等待队列；中断前标记 running 的记录转为 interrupted，不自动重放，因为无法断言模型是否已经产生外部副作用。运行历史保留触发来源、事件标识、版本、状态、结果和错误。去重回执、队列和规则在同一账号文件中原子提交，落盘失败不回复成功。当前历史不按条数自动删除。

## 最终送达（2026-10-30）

普通例行任务完成后默认直接把最终结果写到发起伙伴的主任务，带自动化来源，不额外调用模型；独立执行任务和历史仍保留。桌面编辑器和 `routine_save.delivery` 可选择直接显示、交给伙伴处理、已连接消息机器人或只保留执行任务。处理模式复用普通任务输入队列，结果标为自动来源，不伪造新的主人授权。

消息机器人接收位置先由 `routine_delivery_targets` 查询，返回本伙伴自有连接和个人连接的已知收件人、群／话题，沿渠道现有传输发送，不读出凭证。目的地绑定连接和平台身份，换机器人或断线后不能落到另一身份；不可用时记录送达失败。桌面跨电脑设置通过 `routines.saveWithDelivery` / `routines.deliveryTargets` 协商，在伙伴所在电脑执行；旧端省略字段时保留已有选择。

开启静默检查后，无变化仍不送达；`schedule_notify_current_run` 明确要求报告后才送达。预检跳过和中止不补发成功结果。执行成功与送达状态分开保存：送达失败仍保留完整结果，不为补发重跑已执行工作。内置跟进、夜间学习及导入自动化保留各自既有输出合同，不把存量检查变成额外对话。导入自动化只有明确设置新目的地才替换旧投放渠道，继续经过原有结果脱敏。

模型发现共用 `schedule_list_models`：使用已连接来源的型号、推理档位、速度、上下文及已知价格；同名型号按来源分开。`cost` 是 USD/百万 token，`currency` 对应 `displayPricing`，订阅参考价不代表实际扣费，缺价不能当免费。Agent 按任务需要推荐经济型号，保存后回读完整路由、运行方式和送达选择，不批量覆盖既有设置。Pi 直接工具和 helper 共用这些参数；模型发现的本机 `local` 在保存边界归一为 null。

## 插件本地协议

身份卡声明可发布的事件种类及可筛选字段：

```json
{
  "routineEvents": {
    "events": [
      {
        "type": "github.pr.changed",
        "name": "PR 更新",
        "fields": ["repository", "action"]
      },
      {
        "type": "feishu.message.received",
        "name": "飞书新消息",
        "fields": ["chatId", "senderId"]
      }
    ]
  }
}
```

该字段是可选能力；没有它的存量插件保持原来的授权和行为。新增事件发布能力进入插件能力清单和既有安装批准判据。修改插件基座的合并仍走现有人工确认门。

插件应在建立订阅后报告状态（管子 `routine-request`，也可用 `cindy.routines.request`）：

```js
await cindy.routines.request({ action: "status", status: "listening" });
const receipt = await cindy.routines.request({
  action: "publish",
  event: {
    id: "upstream-delivery-42",
    type: "github.pr.changed",
    occurredAt: Date.now(),
    subject: "PR 123 updated",
    data: { repository: "team/app", action: "synchronize" },
  },
});
// receipt.ok 表示宿主已持久接收，不表示任务已执行完成。
// 失败可使用相同 id 重试；duplicate:true 表示已接收过。
```

宿主从真实插件身份派生 `plugin:<id>`，忽略插件自报来源。只接收已启用、声明过的事件类型；异步等待后及入队前复查安装身份。断线报告 `disconnected`，订阅故障报告 `error`。宿主重启后来源初始未监听；声明 routineEvents 的已启用插件会自动启动浏览器逻辑页，即使省略 launch 或声明 on-demand，并重新报告就绪。停用和账号可用性门禁仍有效；不改变独立的 Node 常驻声明。

注入模型的事件元数据复用不可信内容的标记转义：整个负载编码为单行 JSON，转义 XML 边界字符及 Unicode 行分隔符，放入明确的数据块。subject、data 等字段只作数据，不得改变角色、工具请求或权限；原有宿主执行权限仍然生效。此封装保证字符串不能伪造结束边界，不将其宣称为对所有语义提示注入的绝对防护。

事件 data 只允许平坦字符串、数值、布尔值，单事件 JSON 限制 32000 字符；禁止提交令牌和凭证。筛选支持 equals、contains、not-equals，同一条件内部筛选为 AND。带 `originRoutineId` 的事件不会反向触发同一规则。等待批次达到 100 个事件后返回可重试错误，不静默丢事件。

宿主限制事件发布频率：单来源每 60 秒最多 60 次，全账号最多 240 次；待处理发布请求上限分别为 8 和 32，限速在解析负载和进入持久写入队列之前执行，状态重报不重置额度。去重回执保留 24 小时（过期项在后续接收或启动时清理），按 UTF-8 JSON 字节数限制为单来源 256 KiB、全账号 2 MiB。容量满时拒绝新事件并返回可重试错误，不驱逐窗口内回执；相同 ID 的已确认重投不重新写盘。启动时将旧版过量回执按时间从新到旧裁入上限，不改运行历史。

事件源状态上报使用独立限额：单来源每 60 秒最多 60 次、全账号最多 240 次，重复状态也计入频率。名称、状态及事件声明均未变时直接返回，不广播或清空最近事件时间；真实变化才通知界面。宿主发现插件断开不受插件上报额度限制，重复断开也不广播。

插件管子在等待引擎/数据库就绪前同步预留并发额度：状态和事件请求合计单插件最多 8 个、整个宿主最多 32 个；计数跨引擎重建保留，覆盖启动等待及实际发布，直到成功、失败或取消返回后归还。超额请求立即拒绝，不保留额外等待队列。操作、状态和事件体量沿用现有校验，在等待前拒绝无效请求；引擎内部的频率与落盘限额继续独立生效。

整个请求（包含忽略的未知字段、字段名和数组附加属性）还受 128 KiB UTF-8 保守预算、4096 个值和 16 层嵌套限制。等待前逐项检查，超大字符串先按长度拒绝，不先把整个请求序列化；循环引用、非普通 JSON 对象和非有限数字直接拒绝。小型未知字段仍按兼容规则忽略，合法事件 data 的既有 32000 字符上限不变。

插件失败回执只返回固定公开文案：校验和容量/频率拒绝按精确白名单保留提示；未知异常统一回复通用重试提示，详细异常只进入 Main 日志，不携带文件路径或事件数据返回插件。写盘失败后的原事件 ID 仍可重试，成功持久化后才进入去重窗口。

本协议不要求第三方连接器的固定组合：飞书长连接、Gmail 本地采集和 GitHub 事件适配器都可报告相同形态的事件。本次交付的是宿主接入与执行能力，不会自动给现有飞书/Gmail 插件增加第三方订阅；适配器需按上述协议接入。

## 宿主内置事件源 host:sessions

2026-10-17 起，宿主自己也是一个事件源：`host:sessions`（名称「Cindy 任务」），由伙伴自主跟进的状态表发布任务的
`stuck` / `waiting` / `errored` / `usage-limit` / `finished` / `sweep` 六类事件（判定与阈值见
[伙伴运行时合同 §6.3](./cindy-bots-runtime.md)）。只为本机任务发：另一台电脑上的任务由那台电脑上的伙伴跟，这里只进工作台。它与插件来源走同一个引擎、同一套限速、24 小时回执去重和不可信数据封装，区别是：

- 来源 id 由宿主固定，插件不能冒充；事件源表只在内存里，例行任务引擎每次创建后（含换账号、重建）由宿主重新登记。
- 注册事件源不等于开启后台扫描。默认只观察明确委派的工作；全局跟进须主动开启。没有待跟进委派且全局跟进关闭时释放扫描定时器，远程状态只在查看工作台时读取。
- 事件 `data` 只有扁平字段：`sessionId`、`deviceId`、`deviceName`、`title`、`phase`、`minutes`、`question`、`error`、
  `creatorBotId`、`followerBotId`、`occurrence`；`subject` 是任务 id（`sweep` 是伙伴 id，任务相关字段为空串）。只带标题与一句话摘要，不带工具入参、计划正文、
  代输入值或工作目录。
- 事件 id 由「类型:任务:进入该状态的时刻」决定，跨重启稳定；同一任务同一类事件 24 小时最多发 6 次。
- `sweep` 是程序级条件兜底：某伙伴还有 ≥1 件等你 / 出错 / 用量上限 / 卡住的本机任务，且距它上次被叫醒（任一事件被它的
  规则接收）满 2 小时才发，id = `sweep:伙伴:时间桶`；没有待处理任务的伙伴不会被叫醒。
- 事件不设 `originRoutineId`：跟进者自己的规则必须能被它叫醒；防打转靠状态时刻去重与 24 小时上限，而不是自循环过滤。
- 用户自建规则也可以订阅它（例如只看本机做完的任务），条件编辑不授予额外权限。

## 内置跟进例行任务

每个在用、且本机是主力电脑的伙伴有一条宿主内置规则（`builtin: 'follow-up'`，id 固定为 `builtin-follow-up-<伙伴 id>`；伙伴 id 过长或含引擎不接受的字符时改为前缀 + 伙伴 id 的 sha256 前 40 位，同样幂等，不要从 id 反推伙伴 id）：

- 用户自己创建的任务只在明确选择跟进伙伴后才有跟进者；默认关闭及首次聊天邀请见 `cindy-bots-runtime.md` §6.3。伙伴已受托创建的任务仍按原归属跟进。
- 触发条件：6 个事件条件（含条件兜底 `sweep`）订阅 `host:sessions`，筛选 `followerBotId` 等于自己；没有时间或间隔条件，
  旧版带的 2 小时间隔条件在下一次 ensure 时被对齐掉。`silentWhenIdle` 开启，
  这一轮的回复不自动发给主人，要主人知道的事显式通知。
- 指令由宿主模板生成（`apps/desktop/src/main/bot-autonomy/followUpPrompt.ts`），伙伴与主人都不能编辑。
  v7 正文改为宿主口吻（不冒用主人第一人称）：「主人开启了自动跟进；这一轮由宿主的任务事件唤醒，不是主人刚说的话。看看这些任务做得怎么样，有需要主人回复或决策的，给出你的判断和建议。已经交给你跟进的任务，可以让它按原来的目标接着做，或按摘要建议换模型；普通操作沿用当前任务权限；删除自动化、代答授权或恢复暂停等风险操作由宿主显示授权请求，等待主人决定，拒绝后不要重试。没有新情况就不用提醒。」
  升级仍由 `ensureBuiltin` 对齐模板并保留 `enabled=false`；不创建行动授权，也不迁移 follower 为执行委托。
  内置例行任务的轮次是「自主」身份：可观察、提醒、写待办，并让已交给它跟进的任务按原目标继续或按建议换模型；
  普通工作沿用当前权限，少数明确风险通过可见授权交给主人判断。主人自己设的例行任务是「受托」，按其指令办事。
  正本见 [伙伴代表谁](teammate-authority.md)。
- 宿主在例行任务引擎每次启动、伙伴新建（资料广播后立即重读归属）与恢复时幂等 ensure，事件发布前也先确认跟进者的规则已落地
  （否则首次安装时的早期事件会被记下回执却没人接收）：不存在就建；指令、触发条件或模板版本（`builtinVersion`，随
  `FOLLOW_UP_PROMPT_VERSION` 递增）与模板不同就重写；保留主人的暂停与模型选择。暂停中的伙伴不建。
- 主人可暂停 / 恢复和配置执行模型；删除（含 `routine_delete`）与修改指令、触发条件一律以 `BUILTIN_ROUTINE` 拒绝。暂停后该伙伴不再被事件叫醒，
  本机「等你」改由宿主直接提醒主人。伙伴暂停 / 归档时随伙伴的其它规则一起停摆，删除伙伴时一起清理。
- 云端伙伴的规则同步（companion cloud）不包含内置规则：每台电脑各自 ensure，执行只在主力电脑上发生。

## 每天查待办例行任务

伙伴近况「每天帮我查一次」开关背后的例行任务。2026-10-31 负责人裁决：它不再是宿主内置规则，而是一条普通、可编辑的例行任务；
什么算待办、去哪些已授权来源查、怎么提醒，由伙伴自己的记忆与技能决定（`teammate-guide` 只保留默认定义、工具用法和安全底线），
不在宿主代码里固化。实现见 `apps/desktop/src/main/bot-autonomy/todoCheckRoutine.ts` 与 `routineTools.setTodoCheck`。

- id 为 `builtin-todo-check-<伙伴 id>`（过长时改用 sha256 前缀），`builtin-` 是内置时期的已存 id，保留以便近况开关找到同一条；
  派发 schedule id 落在 `routine-builtin-` 前缀下，运行身份仍按宿主发起（autonomous）判定，不因改成可编辑而变成主人常驻授权。
- 只在主人打开开关时建立，不在启动或伙伴新建时自动建；默认不存在即为关。没有这条时，打开按默认内容新建：名称与指令按
  主进程当前界面语言，指令与「帮我查查」同一句；cron `0 9 * * 1-5`（宿主所在时区，建立时取一次），`silentWhenIdle` 开启。
- 建立后与其它例行任务相同：名称、指令、触发条件、模型、运行方式与送达都可改，也可删除；近况开关和桌面列表开关只切换启停，
  不重写内容。删掉后再打开按默认内容重建。
- 随云端伙伴同步，与其它普通例行任务一致；执行只在主力电脑上发生。
- 旧数据迁移：调度器读到 `builtin: 'todo-check'` 时原地去掉内置标记与模板版本，保留 id、启停、触发条件、模型、运行方式、送达
  与运行历史；同一次加载里把仍是内置默认值的名称、指令换成当前界面语言的默认内容。迁移在恢复排队批次之前完成、不增加 revision，
  升级前已排队的检查照常执行；迁移只做一次，之后主人保存的名称与指令（即使与旧默认值相同）不再被改写。旧版电脑上仍是内置规则的这一条，
  经桌面远程查看时只显示名称，沿用那台电脑的锁定行为。

## 内置夜间学习例行任务

伙伴整理自己记忆与技能的唯一后台入口（主人 2026-10-23 裁决）。宿主内置规则 `builtin: 'nightly-learning'`，
id 为 `builtin-nightly-learning-<伙伴 id>`，过长时同样改用 sha256 前缀。实现见
`apps/desktop/src/main/bot-autonomy/nightlyLearningRoutine.ts`、`maker-ipc/botNightlyLearning*.ts`。

- **默认开**：每个在用、本机是主力电脑的伙伴，与内置跟进一起在引擎启动、伙伴新建与恢复时幂等 ensure；
  落地失败只记日志，不影响跟进。主人可在伙伴设置「例行任务」里暂停 / 恢复，删除与改内容以 `BUILTIN_ROUTINE` 拒绝。
  与「每天查待办」默认不存在不同：没有新对话时不调用模型，有新对话一次只调用一次辅助模型。
- **频率**：每天 3:30（缺省）或每周一 3:30，宿主所在时区，在第一次建立时取一次。频率只在伙伴 Home 的
  `nightly-learning.json` 里存用户改过的值，选回每天即删除；改频率时宿主按新模板重写这条规则，不改开关。
- **运行前检查**：主人与伙伴每完成一轮真实对话计数加一（`botNightlyLearningCounter.ts`，在成功轮次终态处、不调用模型）。
  计入主任务、私聊话题与主人本人在 IM 频道发起的轮次；不计子代理、私下回复、群专线和自动化 / 目标 / 协同 /
  其他任务投递的输入。同一条回复只计一次。到点时计数为 0 直接记一次 `skipped`，不调用模型、不发消息或推送；
  手动「现在整理」不看计数。
- **执行**：在宿主里调用辅助模型，不派到伙伴主对话，指令正文不进伙伴上下文。读取上次整理之后的对话（有界分批，
  读不完的留到下一次），模型只提议，宿主逐条校验后落盘：新记忆须引用主人原话；只改快照里读到全文的记忆与技能；
  只出现一次的做法放进「在观察的做法」（不加载、不进提示词），同类事再次出现或主人点「现在记成技能」才转正为技能；
  停用技能、删除记忆要写理由。记忆关闭时不读也不写记忆。成功才推进水位并按处理过的轮数扣减计数，失败保留计数。
  水位按扫过的回复推进（被过滤的也算扫过）；6 小时内开始、仍在生成的回复挡住水位，完成后再学；为此停在前面时，
  已学过的回复记在 `learned` 里跳过，不重复学。
- **不覆盖并发修改**：记忆按运行前读到的版本交给存储层核对；技能按运行前的原文与启用状态核对；模型思考期间被改过的
  一律跳过。合并（更新保留项 + 删除 / 停用来源）只有保留项写成功、仍存在且本轮不删时才处理来源。
- **撤销**：改动前先登记这次运行，每改一条就把前后内容写入 `learning-history/<runId>.json` 并更新记录，中途退出时
  已做的改动仍能撤销。记录页逐条撤销 / 恢复；之后被主人或伙伴改过的内容不覆盖，提示不能撤销；排队期间换了账号的
  撤销与转正直接拒绝。停用技能走已有的 `disabled-skills/`。
- **刷新**：计数成功后通知已打开的例行任务页与学习记录页刷新「待整理」。
- 结果只进伙伴设置「例行任务 → 夜间学习」的记录页，不插入聊天时间线，不发推送。不随云端伙伴同步。
- 回复后复盘已于 2026-10-23 停用（`cindy-bots-runtime.md` §3.2）；对话中记忆照常当场保存，
  技能只在主人明确要求或纠正已有技能时当场保存，其余交给夜间学习。

插件前置检查（2026-10-31）：自动化与例行任务的「前置检查」可选「脚本」或「插件」。选了插件的

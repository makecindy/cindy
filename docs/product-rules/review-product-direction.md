# Cindy Review 产品方向

> **状态**：已裁决的产品方向（authoritative）；“待确认事项”除外
> **适用范围**：Cindy 管理的成果复核能力，包括代码、文档和视觉交付物
> **读取时机**：新增或修改 `/review`、Reviewer 任务、成果快照、Finding 协议、
> 复核入口、结果呈现或复核生命周期之前

本文记录 Cindy Review 的长期产品方向与当前阶段边界。它约束“用户应得到什么”和
“哪些边界不能被破坏”，不把 #2269 的阶段性实现写成永久技术方案。

## 1. 已裁决的北极星、产品定义与运行原则

### 1.1 北极星与评价指标

Cindy Review 的北极星是减少用户在交付或提交后，才被外部 review 反复打回的次数。

评价质量不看 Finding 数量，而看两个结果：

- 外部后续提出的必改意见中，有多少已被 Cindy 提前发现；
- Cindy 产生了多少无效意见和噪音。

### 1.2 产品定义

`/review` 是 Cindy 的通用成果复核能力，不是只服务 GitHub 的 Git Code Review。
Code Review 是一个 profile，不是产品本身。

Review 至少面向以下成果：

- Git 项目的代码改动；
- 非 Git 项目的代码、文件或目录；
- 当前任务生成的文案、Markdown、HTML；
- PDF 与图片或其他视觉成果。

有基线时，Review 比较前后变化；没有基线时，按用户原始目标、参考材料和验收标准评价
当前成果。

Pi、Claude Code 和 Codex 是可替换的运行环境与模型来源，不是三个 Review 产品。默认
沿用来源任务已经可用的 harness、provider 和 model，不额外要求 OpenAI 登录；自定义或
DeepSeek 等模型只要能在相应 harness 的普通任务中使用，也应能作为 Reviewer 的模型来源。

### 1.3 运行与证据原则

- 每次复核新建独立、无开发记忆、只读的 Reviewer 任务，不 resume 来源开发会话。
- 默认沿用来源任务的 harness、provider 和 model。
- 只向 Reviewer 提供带来源标记的结构化证据：用户需求及修正、验收条件、成果快照、
  真实测试结果和明确技术决策。
- 不传开发 reasoning，也不把开发 Agent 的自述视为事实。Reviewer 必须重新读取成果并
  验证结论。
- Finding 必须包含证据与优先级，并保持低噪音。默认突出高置信的正确性问题，把质量优化
  与正确性问题分开表达。
- 结果回到来源任务，用户可从来源任务打开独立 Reviewer 任务。
- 审阅对象或来源任务变化后，旧结论立即失效；异常、重启或关闭路径都必须 fail closed。
- 完成后的 Reviewer 任务是可查看的审计记录，不能继续聊天，也不能修改模型、来源、
  权限、目录等冻结配置。
- Reviewer 只复核，不自动修码。修复回到来源任务，修复后的成果需要再次复核。

### 1.4 方法与专业边界

Review 可以借鉴成熟 code review 的缺陷标准、P0-P3、精确证据、结构化输出、只报告本次
引入问题和只读原则。也可以采用“候选发现 → 逐条验证 → 去重与置信度过滤”的流程，但
不能复制受限许可的 prompt 或实现。

法律、医疗、财务等专业领域不能只靠模型记忆给出确定性结论。此类复核需要权威来源、
适用法域或范围、日期与不确定性提示，适合作为后续专业 profile、Skill 或插件扩展。

### 1.5 验收原则

Review 必须同时验证代码路径和真实交付结果，不能用“格式代码已经接上”代替成果复核验收。

- Markdown、PDF 和图片要使用故意埋错的真实样例，分别穿过 Codex、Claude Code、Pi 的
  轻量真实输入链路。
- 双向 dogfood 是关键验收：用独立 Reviewer 审查 Reviewer 自身实现，再由第二个独立
  视角验证第一轮结论。
- 验收记录必须区分等价模拟与真正从新构建 Desktop 点击 `/review` 的结果。

## 2. #2269 当前边界

#2269 的目标是提供一套由 Cindy 管理的本地 `/review`：使用来源任务的 harness/model，
在隔离任务中审查代码或文档、PDF、图片交付物。

首版至少覆盖：

- Git 项目的代码改动；
- 非 Git 项目的代码、文件或目录；
- 当前任务生成的文案、Markdown、HTML；
- PDF 与图片或视觉成果；
- 有基线时比较变化，无基线时按原始目标、参考材料和验收标准评价成果。

当前 PR 明确不做：

- 接入 Codex 或 Claude 官方 Web reviewer、订阅通道或第三方 reviewer 插件；
- 修改服务端、Mobile 或远程 SSH review；
- 自动强制 review、Skill 触发、自动化普及或 Reviewer 自动修码；
- 扩大为通用文档编辑器、图片生成器或现有 harness 的整体权限重构。

## 3. 后续路线

以下是已讨论的架构分工方向，不代表 #2269 的实现范围，也不把尚未裁决的细节变成承诺。

- **Cindy Core**：负责 ReviewJob、成果快照、独立任务、硬只读、Finding 协议、结果 UI
  与失效生命周期。
- **人类入口**：`/review` 或“复核成果”按钮。
- **Agent 主动入口**：未来可提供 `review_start` 工具。
- **高频或强制复核**：必须由宿主生命周期 gate 执行，不能只靠 Skill 文案；模型可能跳过
  Skill，或用“我自己检查过”冒充独立复核。
- **Skill**：声明何时复核，以及采用什么 rubric 或策略。
- **插件**：承载法律、品牌、视觉等专业扩展与富交互，不承载核心 Reviewer。
- **官方本地或 Web reviewer**：未来可以作为“额外第二意见”的 ReviewRunner，不是默认
  主路径或 fallback。Web 路径还需要单独处理账号、GitHub App、代码外发、费用和结果回收。

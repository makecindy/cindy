## 0. 一句话

中转服务只有一个内核（`packages/device-link-relay`），有两种运行方式：

| | A. 部署到公网服务器 | B. 在这台 Cindy 上直接开启 |
| --- | --- | --- |
| 适合 | 设备分布在不同网络，需要从公网访问 | 设备之间网络本来就通，或用户自己能打通 |
| 用户提供 | 一台服务器的 SSH 配置，并在云控制台放行端口 | 让其他设备能访问这台电脑的网络条件 |
| Cindy 负责 | 安装、配置、申请证书、注册为系统服务、升级、卸载 | 启动内核、显示地址、检测连通、提醒保持唤醒 |
| 内核运行方式 | 服务器上用 Node 运行，由 systemd 托管 | Cindy 内的独立进程（`utilityProcess`） |

两种方式共用：

- 同一份中转程序和协议。
- 同一套加入流程：二维码或链接发起，主人确认，设备拿到中转专用凭证。
- 同一个设置页，同一套客户端切换逻辑。

## 1. 原则与边界

- **一个内核。** A 和 B 只在三件事上不同：怎么启动、证书从哪里来、谁来管理。
  协议、认证、加入、设备管理、媒体全部由内核实现，两种方式不能各写一份。
- **网络连通的责任。**
  - A：由服务器的公网地址保证。
  - B：由用户自己保证。同一局域网、路由器端口映射、内网穿透、组网工具都可以。
    Cindy 只做检测和提示，不安装、不配置任何网络软件。
- **手机只能用受信任的 `https`/`wss` 连接。** Android 正式包只允许明文访问 `127.0.0.1`，放开要改原生配置，也就是冷更。
  所以手机加入时，中转必须有受信任的证书（见 §2.2）。电脑之间不受这个限制。
- **不碰 Cindy 账号凭证。** Cindy 账号 token 不会发给自建中转；中转返回 401 也不会让 Cindy 账号登出（§5.3）。
- **官方服务不变。** 官方中转和服务端都不改。自建模式只替换设备之间的中转，登录、模型等服务照旧走官方。

## 2. 内核：`packages/device-link-relay`

### 2.1 功能

起点是 `scripts/device-link/relayFixture.ts`（142 行的测试用中转）。它已经具备握手、presence 广播、按目标转发、
`DEVICE_OFFLINE`/`REMOTE_DISABLED`、覆写 `src`、4409 顶替。在此基础上需要补：

- **设备协议**（§6.1）：
  - 凭证认证。
  - 帧校验：单帧上限 2 MiB，超出回 `PAYLOAD_TOO_LARGE`，不断开连接。
  - 检查目标设备的 `remoteControlEnabled`。
  - 跨账号的 `sharedTask`/`providerShare` 帧一律拒绝。
  - 出站缓冲上限，以及 1013 拥塞关闭。
- **REST**（§6.2）：设备列表、改名、移除；媒体上传与下载。
- **加入与管理**（§6.3）：一次性加入码、加入申请、主人审批、移除设备、状态查询。
- **持久化**：
  - 设备档案（只存凭证哈希）。
  - 加入申请。
  - 媒体文件（24 小时后清理，有总量上限）。
  - 证书与 ACME 账号。
  - 配置。
- **证书**：见 §2.2。
- hello-ack 的 `capabilities` 为空，即不声明 `notify`、`shared-task-v2`、`provider-share-v1`。
- 单实例内存路由，不需要 Redis。

依赖只有 `@cindy/device-link-protocol`、`ws` 和一个 ACME 客户端，不依赖 Desktop（`architecture-invariants.md` §1）。
最终打成一个单文件 bundle：

- 方式 A：服务器上运行 `node relay.mjs --data <目录>`。
- 方式 B：Desktop 用 `utilityProcess` 运行同一个文件。参考 `localDb/dbSlimmingWorkerClient.ts` 等现有用法；进程崩溃不影响 Cindy 主进程。

### 2.2 证书：三种方式

| 方式 | 做法 | 手机能否加入 | 典型场景 |
| --- | --- | --- | --- |
| 自动证书 | 内核用 ACME 向 Let's Encrypt 申请并自动续期。<br>有域名时用域名证书。<br>没有域名时用 **IP 地址证书**：2026-01-15 正式提供，有效期约 6 天，需要自动续期（[公告](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability)）。<br>实际实现使用 `http-01`，公网 80 提供验证，443 提供 HTTPS | 能 | A 的默认方式；B 中有公网 IP 的电脑 |
| 前置代理提供 | 内核只在 `127.0.0.1` 上明文监听。<br>TLS 由用户自己的 nginx、Caddy、frp、内网穿透服务或 Tailscale serve 等提供 | 取决于前置代理的证书是否受信任 | B 的常见情况；服务器上 443 已被别的网站占用时 |
| 自签名 + 指纹固定 | 内核生成自签名证书，加入链接里附带证书指纹，电脑端按指纹校验 | **不能**（需要原生改动），界面直接说明 | B，只连自己的几台电脑 |

不提供在网络上明文监听（`ws://` 对外）的方式：否则加入码和凭证会被同一网段的人截获。

IP 证书的注意点：

- 有效期只有约 6 天，内核大约每 3 天续期一次。续期失败时，管理状态里显示证书剩余时间，并提醒主人。
- 申请 IP 证书使用 ACME profile（`shortlived`）与 `http-01`，实现见 `packages/device-link-relay/src/acme.ts`。

### 2.3 管理：主人凭证

- 开启中转（B）或部署中转（A）的那台电脑就是**主人电脑**。
  - 主人电脑在本机生成自己的设备凭证，交给内核的只有它的哈希；这份凭证同时带管理权限，不另发管理凭证。
  - A 方式下，这个哈希由 SSH 安装时写进服务器配置（`relay init --owner-credential-hash`）。
  - 所以两种方式的管理方式完全一样：主人电脑带着自己的凭证调用 §6.3 的管理接口。
- 加入审批、移除设备、查看状态，都在主人电脑的设置页完成。
- 主人电脑在显示加入二维码期间轮询待审批的申请，不需要新增协议帧。
- 第一期只有一台主人电脑。以后要加第二台管理设备，再单独设计。

## 3. 方式 A：部署到公网服务器

入口：设置 → 远程连接 → 中转服务 → 部署到我的服务器。选择一台已配置的 SSH 主机，复用现有 SSH 主机配置与认证
（`packages/maker-remote-ssh`）；没有就先添加。

**支持范围**：Linux x64 / arm64，与现有远程安装一致。

**Cindy 自动完成的步骤**（每一步在界面上显示进度）：

1. 探测服务器的系统、架构、是否为 root 或有 sudo 权限、443 端口是否被占用。
2. 准备运行环境：复用自带 Node 的安装方式（`bootstrap-script.ts` 的 `BUNDLED_NODE_INSTALL_SH`，
   安装到 `~/.xdt-server/<ver>/node/`）。下载来源见 §13 第 2 条。
3. 上传中转程序。同版本重复上传是幂等的，参考 `file-service-installer.ts`。
4. 写入配置：端口、证书方式、域名（可选）、主人设备凭证的哈希。
5. 注册为 systemd 服务：开机自启，崩溃自动重启。
   以专用的低权限用户运行，只授予绑定低端口的能力（`CAP_NET_BIND_SERVICE`）。
6. 系统防火墙（ufw、firewalld）开着时，征得用户同意后放行 443。
7. 申请证书。
8. 从本机检测能否连上。连不上时，按顺序提示：
   1. 去云服务器控制台的安全组放行 TCP 443。
   2. 检查服务器上的防火墙。
   3. 端口被占用时，改用前置代理方式。
9. 完成，显示加入二维码。主人电脑自动切换到这个中转。

**权限**：

- 安装 systemd 服务和放行防火墙需要 root 或 sudo。
- SSH 用户是 root，或者有免密 sudo，就能全自动完成。
- 需要输入 sudo 密码时，走代输入：密码只交给执行命令的那个进程，不进模型、记录和日志（`input-handoff.md`）。
- 没有 sudo 权限时，退回用户级运行：使用高位端口，证书只能用前置代理方式，并明确提示这些限制。

**域名**：

- 可选。有域名就填，内核申请域名证书。
- 服务器在中国大陆时，用域名访问 80/443 需要 ICP 备案。
- 不填域名就用 IP 证书，不涉及域名备案。各家云厂商会不会拦截按 IP 访问，需要实测（§12）。

**升级与卸载**：

- 主人电脑连接中转时会读到中转版本；版本落后时提示「更新中转」，重新上传并重启。
- 卸载：停止服务，删除程序。中转数据（设备档案、媒体）可选保留或一并删除。

## 4. 方式 B：在这台 Cindy 上直接开启

入口：设置 → 远程连接 → 中转服务 → 在这台电脑上开启。

**用户需要设置的：**

- 监听端口。
- 监听范围：仅本机（配合前置代理）或所有网络。
- 证书方式（§2.2）。
- 对外地址：其他设备用来连接的地址，会写进加入链接。

**Cindy 负责的：**

- 用 `utilityProcess` 启动内核。崩溃后自动重启，次数有上限。
- 本机作为一台设备连接自己的中转（`127.0.0.1`）。
- 列出本机的局域网地址，方便用户填写对外地址。
- 从本机检测对外地址能否访问。受网络环境限制（比如很多路由器不支持从内网访问自己的公网地址），结果只作参考。
- 提醒保持唤醒，并自动打开现有的「保持唤醒」设置；笔记本合盖仍会休眠，要写清楚。
- 监听范围选「所有网络」时，macOS 和 Windows 会弹出系统防火墙确认框；Cindy 先说明原因，再触发。

**用户自己负责的**：其他设备能访问对外地址。界面用一句话说明，并举例：

- 同一局域网。
- 路由器端口映射。
- 内网穿透。
- 组网工具（如 Tailscale、ZeroTier）。

Cindy 不安装、不配置这些工具。

**手机**：只有在「自动证书」或「受信任的前置代理证书」下才能加入；选了自签名时，加入页直接说明手机不支持。

## 5. 加入与切换（A、B 共用）

### 5.1 加入

**加入链接**：`<scheme>://relay/join?u=<对外地址>&c=<加入码>[&k=<证书指纹>]`

- scheme 跟随构建区域：`cindy`、`cindycn` 或 `cindydev`。
- `k` 只在自签名方式下出现。

**另一台电脑：**

1. 粘贴链接，或直接点链接让 Cindy 打开。
2. 先请求 `relay/info`，确认地址可达、对方确实是 Cindy 中转；自签名时校验证书指纹。
3. 发出加入申请。主人电脑弹出确认框，显示设备名、平台和 4 位核对码。
4. 主人同意后，设备拿到凭证，自动切换到该中转。

**手机：**

1. 用系统相机扫二维码，打开 Cindy 的加入页，复用 `apps/mobile/app/+native-intent.ts` 的深链。
   链接里的加入码不进路由状态，也不进诊断信息，处理方式与共享任务邀请相同。
2. 后续步骤和电脑一样。

App 内不加扫码组件：加一个会改变原生指纹，需要冷更。

**核对码**：与供应商分享的 `Pairing Code` 是同一类东西，只用来核对，不参与鉴权。可以沿用这个术语，需要扩充术语表的说明。

### 5.2 身份与凭证

- **中转凭证**：32 字节随机数，只能用来连这一个中转；中转端只存 SHA-256。
  - Desktop 存在 `safeStorage`，参照 `secrets/providerSecretStore.ts` 里只在 main 进程读写的键。
  - Mobile 存在 `expo-secure-store`，用 `WHEN_UNLOCKED_THIS_DEVICE_ONLY`。
- **握手与 REST 请求头**：`Authorization: CindyRelay <凭证>`。`DeviceLinkClient` 已有 `authorizationScheme`
  （`packages/device-link/src/client.ts:262`），只需新增一种。
- **deviceId**：上报与官方登录相同的设备 ID，`hello-ack.deviceId` 原样返回。
  这样本机按设备 ID 保存的状态在切换后依然有效，包括撤销记录、设备名、远程任务绑定。
- **userId**：中转属于主人电脑登录的 Cindy 账号。账号不一致的设备直接拒绝，跨账号场景走共享任务或供应商分享。
  这只防误操作，真正的准入关口是主人确认。

### 5.3 客户端切换

设置按账号保存：`{mode:'official'} | {mode:'self-hosted', relayId, name, baseUrl, role:'owner'|'member', certPin?}`，
凭证另存安全存储。

**Desktop：**

- **地址与凭证统一经新增的 `device-link/relayRouting.ts`**：
  - `deviceLinkApiBase()`、`wsUrl()`、`getToken`（`main/device-link/index.ts:203-206、681-684、715`）改走它。
  - `remote-desktop/iceConfig.ts` 也改走它。
  - 不在 `getClientEndpoint` 做全局覆盖：它还负责区域切换和更新链，影响范围太大。
- **自建模式下暂停跨账号模块**：`sharedTaskApi.ts`、`providerShareApi.ts`、`providerShareGuest.ts`、`providerShareHost.ts` 不发请求；
  对应入口显示「使用自建中转时不可用」。
- **鉴权失败不能影响官方登录。** 现有两条路径会碰官方登录：
  - REST 返回 401 时可能登出账号（`main/serverApiClient.ts:142-171`）。
  - WS 握手 401 会强制刷新官方 token（`index.ts:618-654`）。

  自建模式下这两条路径都不能碰官方登录。此时 401 或 4410 只表示中转凭证失效，界面提示重新加入，或切回官方中转。
- **证书校验**：自签名方式下，WebSocket 和 REST 都按指纹校验，不信任系统根证书以外的任何证书。
- **代理**：设置了代理时，device-link 的 WebSocket 会走代理（见 `dnsFallbackLookup.ts` 顶注）。
  自建中转的地址是私有网段或组网地址时，要绕开代理，实测确认。

**Mobile：**

- `DEVICE_LINK_API_BASE_URL`（`src/config/env.ts:272`）会被三个区域函数改写；新增覆盖值，在它们之后重新应用。
- `src/device-link/DeviceLinkContext.tsx:1005` 的 `getWsUrl` / `getToken` 改走新的 `relayRouting`。
- `apiFetch`（`src/auth/AuthContext.tsx:3309`）会给任何 `baseUrl` 附上 Cindy token。
  自建模式下改用中转凭证，确保官方 token 不会发到自建中转。
- 推送注册（`src/notifications/pushNotifications.ts:190`）在自建模式下跳过。

**状态与退出：**

- 中转离线时提示，并提供「切回官方中转」。**不会自动切回官方。**
- 主人可以移除设备：凭证立即失效，对方收到 4410 断开，并看到提示。
- 主人停用中转（B）或卸载中转（A）前，先用 4410 断开所有设备；各设备提示「中转已停用」，可一键切回官方中转。

## 6. 接口

### 6.1 WebSocket `/api/device-link/ws`

只实现现有客户端已经在用的行为（依据：`packages/device-link-protocol/src/protocol.ts` 与 `packages/device-link/src/client.ts`）：

- **握手**：`hello` 必须是第一帧。中转在 15 秒内回 `hello-ack`：`{serverProtocolVersion:1, deviceId, userId, capabilities:[]}`。
- **心跳**：收到 `ping` 回 `pong`，`pong` 不带 payload。
- **presence**：收到 `presence-set` 后更新状态，并广播完整的 `PresenceSnapshot`。
  初始设备列表靠 `/devices` 获取，与官方行为一致。
- **转发**：转发 `ROUTED_KINDS` 并回填 `src`。
  - 目标设备不在线，回 `DEVICE_OFFLINE`。
  - `CONTROL_KINDS` 的目标关闭了「允许被控」，回 `REMOTE_DISABLED`。
  - `relay-error` 带回原帧的 `id` 和 `dst`。
- **关闭码**：

| 关闭码 | 含义 |
| --- | --- |
| 4409 | 同一设备有新连接，顶替旧连接 |
| 4429 | 连接数超限 |
| 4400 | 版本不符 |
| 4410 | 设备被移除，或中转已停用；客户端停止重连 |
| 1013 | 拥塞 |

### 6.2 REST

所有接口以 `/api/device-link` 为前缀，请求头为 `Authorization: CindyRelay`。

| 接口 | 第一期 |
| --- | --- |
| `GET /devices`、`PATCH /devices/:id`、`DELETE /devices/:id` | 实现。删除设备等于吊销凭证，并用 4410 断开该设备 |
| `POST /media/presign-put`、`POST /media/presign-get`、`DELETE /media` | 实现。上传和下载地址都指向中转自身，带签名、短期有效；单文件与总量的上限，实现时对齐客户端现有的上传限制 |
| `GET /ice-servers` | 不实现，返回 404。远程桌面退回公共 STUN（`remoteDesktopIceConfig.ts:99-136`） |
| `PUT /push-token`、`DELETE /push-token` | 返回 204，不保存 |
| `/provider-shares*` | 返回空列表，只作兜底 |
| `/shared-tasks*`、`/identities*` | 不实现 |

### 6.3 加入与管理（只在自建中转上存在）

**公开接口（不需要凭证）：**

- `GET /api/device-link/relay/info` → `{relayId, name, protocolVersion:1, relayVersion, features:['pairing-v1']}`。不返回任何账号信息。
- `POST /api/device-link/relay/pair` → 请求 `{code, deviceId, deviceName, platform, appVersion, accountUserId}`，
  返回 `{requestId, pollToken, verifyCode}`。
- `GET /api/device-link/relay/pair/:requestId?wait=<秒,≤25>`：长轮询，请求头 `X-Cindy-Relay-Poll-Token` 带提交时拿到的轮询口令。
  结果为 `pending`、`approved {credential, deviceId}`、`rejected` 或 `expired`；凭证只返回一次，设备在取回凭证时才写入档案。

**管理接口（需要主人设备的凭证）：**

- `POST /relay/admin/join-codes`：生成加入码。一次性、10 分钟有效，用后作废。
- `GET /relay/admin/pair-requests`：查看待审批申请。
- `POST /relay/admin/pair-requests/:id/approve`、`.../reject`：同意或拒绝。
- `GET /relay/admin/status`：版本、证书到期时间、在线设备、媒体占用。

**限制：**

- 同时待处理的申请最多 5 个。
- 按来源限速。
- 加入码、凭证、签名地址都不写进日志。

## 7. 自建模式下的功能边界

| 功能 | 第一期 |
| --- | --- |
| 远程查看和控制任务、实时输出、审批 | 可用 |
| 设备列表、改名、移除 | 可用 |
| 远程文件、图片、语音 | 可用 |
| 直连（`direct-link-v1`） | 可用，信令经中转透传；只用本机地址候选，能否直连取决于网络环境 |

## 8. 安全

- **最大风险：冒充。**
  - 方式 A 天然在公网上；方式 B 也可能被用户映射到公网。
  - 中转负责回填 `src`，中转所在机器一旦被入侵，攻击者就能冒充控制端，让被控电脑执行远程指令。
  - **建议在方式 A 正式开放前，先做设备签名防冒充**（§13 第 1 条）：
    - 主人电脑作为信任根，给每台通过审批的设备签发设备证书。
    - 主人公钥随加入二维码带到新设备，不经过中转。
    - 设备对每条消息签名，接收方验证签名并检查消息是否新鲜。
    - 内容加密可以放在下一期。
- **凭证**：只对这一个中转有效；客户端存在安全存储，中转只存哈希；设备被移除后立即失效。
- **准入**：三道关：加入码（能看到主人屏幕的人才拿得到）、主人确认、核对码。
- **账号 token 不外发**：Cindy 账号 token 不发往自建中转。Desktop 的 WS 与 REST、Mobile 的 `apiFetch` 都要覆盖，并补回归测试。
- **服务器上的运行身份**：专用低权限用户，只授予绑定低端口的能力；数据目录只有该用户可读写。
- **SSH 凭证与 sudo 密码**：沿用现有 SSH 主机的凭证存储；sudo 密码只走代输入。
- **媒体**：用带签名的短期地址，过期清理。Desktop 侧的落盘目录登记到 `credentials-and-local-storage.md` 的路径表。
- **日志**：新增的日志行按 `log-upload-and-redaction.md` 的白名单规则评审。

## 9. 故障半径

按 `remote-and-mobile-adaptation.md` 的故障半径三问：

- **中转不可达**（服务器宕机、电脑休眠、网络断开）：
  - 所有设备按现有退避重连同一个中转；不自动切回官方，界面提示并提供手动切回。
  - 方式 B 中转进程崩溃时，只重启中转进程，不影响 Cindy 主进程和本机任务。
- **单台设备被移除**：只影响这一台（4410），其他设备不受影响。
- **证书过期**（续期失败）：所有设备连不上。主人电脑提前提醒，证书剩余时间显示在管理状态里。
- **切换中转**：只重建本机的 device-link 连接，被远程控制的任务继续运行。
- **多设备回归用例**：两台控制端加一台被控端，移除其中一台控制端，断言另一台的在途请求与连接不受影响。

### 15.3 第 3 步：设备签名、一键部署到服务器、远程管理（2026-10-28）

**设备签名**（见 §16）：

- 共享协议：`packages/device-link/src/selfHostedRelayAuth.ts`，加密实现由宿主注入。
  - Desktop 与中转用 `@cindy/device-link/node-relay-crypto`（node:crypto）。
  - Mobile 用 `@noble/curves` / `@noble/hashes` 与 `expo-crypto`。
- `DeviceLinkClient` 新增 `frameAuth` 选项，只有两处钩子：
  - `sendEnvelope` 给经中转转发的对端帧附上 `auth`；
  - `handleMessage` 在任何解码与分发之前核对签名。
  - 官方中转返回 null，wire 行为与旧版完全相同。
- 中转：
  - `relay-state.json` 升到 schema 2，保存主人公钥与每台设备的证书；
  - 新增 `GET /api/device-link/relay/certs`；
  - 加入申请必须带公钥与配对证明，同意必须附主人签发、发给申请里那把公钥的证书；
  - 帧里的 `auth` 原样转发。
- Desktop：
  - 主人密钥与设备签名密钥按中转 ID 存在 `secrets/<中转ID>.enc`（safeStorage 加密）；
  - 审批时用加入链接里的配对秘密核对证明，对不上只能拒绝；
  - 电脑核对所有对端消息（`selfHostedRelayFrameAuth.ts`）。
- Mobile：加入时生成签名密钥并核对证书；发出的对端消息都签名，收到的对端消息也在分发前核对（见 §16.4）。

**一键部署到服务器**（方式 A 的落地形态）：

- 内核新增自动证书（`acme.ts`、`csr.ts`、`certificates.ts`）。
  - 自己实现了最小 ACME 客户端（http-01）与 CSR 编码，没有引入第三方库。
  - 填 IP 时用 Let's Encrypt `shortlived` 配置申请 6 天有效的 IP 证书；填域名时用常规证书。
  - 剩余有效期不足 1/3 时自动续期，续期后热替换证书，不断开现有连接。
  - 证书状态写进数据目录的 `status.json`，部署方据此报告进度与失败原因。
- `relay serve --acme-identifier <IP或域名>`：先在 80 端口提供验证，拿到证书后才开始提供 443。
  - 首次申请失败按 1 / 5 / 15 / 30 / 60 分钟退避重试（Let's Encrypt 对失败验证有限额）。
- 单文件：`packages/device-link-relay/build.mjs` 打出 `dist/relay.mjs`（约 210 KB）。
  - 由 `apps/desktop/scripts/build-remote-bundles.mjs` 放进 `resources/device-link-relay/`，随安装包分发。
- 部署器 `apps/desktop/src/main/device-link/selfHostedRelayDeploy.ts`：走「远程」里已配置的 SSH 主机。
  - 需要 root 或免密 sudo；没有就停下来提示，不索要密码。
  - 步骤：连接 → 检查系统和 80/443 端口 → 安装 Node → 上传并核对 SHA-256 → 建系统用户、初始化、写 systemd 服务、开放 ufw / firewalld → 等证书 → 从这台电脑访问 `https://<地址>/api/device-link/relay/info` 核对中转 ID。
  - Node 24.22.1 的 SHA-256 写死在代码里。国内区域先试 npmmirror，其他区域先试 nodejs.org；校验不符视为下载失败。
  - 服务器有 IPv6 时监听 `::`（双栈），否则 `0.0.0.0`。Let's Encrypt 会优先通过 IPv6 验证有 AAAA 记录的域名。
  - systemd 服务以 `cindy-relay` 用户运行，只放行绑定低端口的权限；`ProtectSystem=strict`，只能写数据目录。
  - 主人身份（中转 ID、主人凭证、主人密钥）只在这台电脑生成；服务器只拿到凭证哈希、主人公钥和主人证书。
  - 身份在动服务器之前就记进部署记录：中途失败重试，用的还是同一份身份，不会和服务器上已初始化的数据冲突。
- 已有 Nginx 的自动接入（2026-10-29，服务器 bundle `0.3.0`）：
  - 沿用同一个部署入口，自动判断 80/443 的占用者；原生 Nginx 自动接入，其他程序不停止、不接管。
  - 从运行中的 master 与 `nginx -T` 找到实际配置，不要求用户选安装目录或复制配置。
  - 访问地址已有可信 HTTPS 时沿用原证书管理，中转仅在回环地址提供 HTTP；否则中转在回环地址申请、续期证书，Nginx 转发 HTTP-01 验证并提供公网 HTTPS。

## 16. 设备签名：中转无法冒充你的设备

### 16.1 要防什么

中转部署在云服务器上之后，服务器被入侵（或云厂商、托管方能动它）就等于中转被人控制。没有签名时，控制了中转的人可以：

- 冒充手机给电脑发 `invoke` / `link-open`，让电脑执行任务、读写文件；
- 冒充电脑给其他电脑推送插件同步、词典、通讯录等会写入状态的消息；
- 重放之前的消息。

签名之后，中转仍然能看到经它转发的内容，也能断开、丢弃消息（它本来就能），但**不能让任何一台电脑执行没有经过你自己设备签名的请求**。端到端加密不在本期范围。

### 16.2 密钥与证书

- **主人密钥**：开启或部署中转的那台电脑生成（Ed25519），私钥只在它的 safeStorage 里。主人电脑自己的设备签名也用这把密钥。
- **设备证书**：主人密钥对「中转 ID + 设备 ID + 设备公钥 + 角色 + 签发时间」的签名。
  - 中转保存证书并提供给所有设备，但伪造不了。
  - 每台设备用主人公钥逐个核对证书。
- **主人公钥从哪来**：
  - 主人电脑自己知道；
  - 其他设备从加入链接 `o=` 参数取得。链接经二维码或复制粘贴交给新设备，不经中转。
- **新设备的公钥怎么不被中转替换**：
  - 加入链接里还有一次性配对秘密 `s=`，同样不经中转。
  - 新设备生成签名密钥，用 `HMAC-SHA256(s, [中转ID, 设备ID, 公钥])` 证明这把公钥是拿着链接的设备生成的。
  - 主人电脑审批时核对证明，对不上只能拒绝。
  - 4 位配对码仍保留，给人眼再核对一次。
- **加入时核对证书**：新设备拿到中转转交的证书后，必须核对它出自链接里的主人、发给自己这把公钥。否则视为中转被替换，停止加入（`OWNER_MISMATCH`）。

### 16.3 每条消息的签名

经中转转发的对端帧（`ROUTED_KINDS`）都带 `auth: { t, b, r, c, s }`：

- `t`：发送时刻（毫秒），收到时与本机时钟相差超过 10 分钟即拒绝。
- `b`：本次启动的随机标识；`c`：本次启动内严格递增的计数。收到方按「发送设备 + 启动标识」记下最大计数，不大于它的一律视为重放。启动标识的最后一条消息也过期后清理记录，内存不随消息量增长。
- `r`：收件设备本次启动的随机挑战，签名必须绑定它。重启后挑战变化，即使计数窗口已经清空，旧建链或写请求也不能再次执行。
  双方先在保留的 `device-link:relay-auth` push 通道交换已签名的 request / response；仅完整的认证 request 允许空挑战，
  接收端验签后直接消费认证消息，不进入业务 handler、不建立远控链路，也不改变开关、订阅或权限。
  因而关闭远控的手机仍能接收插件同步；未建链的允许查询沿用原有权限边界。
  首次业务消息在客户端按设备有界排队，认证重试不重连共享 socket；超时、断线或签名身份变化后不再发送旧请求。
  电脑重启且证书尚未加载时，只允许有界的无业务认证探测；未验签消息仍丢弃。对端新挑战验签通过后，
  发送端可重签仍在等待的原 `link-open`，沿用原请求 ID、签名身份和超时期限；不重发任意旧写请求，已取消的建链不会恢复。
- `s`：Ed25519 签名。签名对象是以下内容的 SHA-256：
  - `JSON.stringify(["cindy-relay-frame/2", 中转ID, 发送设备, 收件设备, kind, id, t, b, r, c])`；
  - 换行；
  - `JSON.stringify(payload)`。
  - 中转转发时会重新序列化帧，JSON 解析再序列化在 V8 与 Hermes 上都保持不变。
- 收件设备还核对 `dst` 就是自己：签给别的设备的消息不能转投给它。
- 可靠传输重发、分片都会重新签名（签名发生在每次真正写入 WebSocket 时）。
- 直连通道上的帧不签名：直连的 DTLS 指纹经已签名的信令交换，电脑只接受签名有效的信令，因此直连的对端身份同样可信。
- 遇到证书列表里还没有的设备，先丢弃这条消息并刷新证书（5 秒节流）；可靠传输的重发会在刷新后送达。

### 16.4 手机收发均核对设备身份

- 手机签名发出的每条对端消息，收到的对端消息也必须通过设备证书、帧签名和重放检查才分发。
  权限请求的展示内容同样受保护，不能让中转保留真实请求 ID、替换文案后诱导主人签出允许决定。
- 复用已有的纯 JS `@noble` 和共享 `RelayFrameAuthenticator`，不新增原生依赖或冷更输入。
- 首次使用时拉取主人签发的设备证书；通信活跃时每十分钟刷新，未知设备或签名不符时按五秒节流刷新。
  证书尚未取得、刷新失败或签名无效时丢弃当前帧，可靠传输可在证书就绪后重发，不放行未经认证的内容。
- 账号、中转、凭证或签名身份变化会使旧请求失效，迟到证书不能写入新路由。官方中转不受影响。
- Hermes 上的持续推送吞吐与耗电仍需真机验收，不能以未实测的性能判断跳过验签。

### 16.5 兼容

- 官方中转完全不受影响：`frameAuth` 返回 null，不签名、不核对，wire 与旧版逐字节一致。
- 自建中转从 0.2.0 起要求签名。
  - 旧格式的加入链接（没有 `o` / `s`）会被拒绝；
  - 不支持 `device-signatures-v1` 的中转不能加入。
- 自建中转从未发布过，不存在需要迁移的用户数据。第 2 步开发期间留下的本机配置会被忽略并清掉旧凭证文件。
- 开发期间不含接收端挑战的旧签名客户端不兼容本次签名格式，需同步更新 Desktop / Mobile；
  中转仅原样转发 `auth` 与已有 push，无需更改已实现的服务端路由。

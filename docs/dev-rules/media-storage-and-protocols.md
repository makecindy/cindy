# Desktop 媒体存储与协议

> **状态**：权威开发规则（authoritative）
> **读取时机**：新增或修改图片、视频、音频、3D 模型的生成、导入、附件、缓存、
> 持久化、协议解析、远程传递或回收逻辑之前

本文治理 Desktop 中由 Cindy 管理副本的媒体字节。Electron 协议与进程安全另见
[`electron-security-and-process-boundaries.md`](electron-security-and-process-boundaries.md)，
数据库变更另见 [`database-and-migrations.md`](database-and-migrations.md)。

> **增量适用原则**：所有新媒体写入必须进入 `cindy-media`。历史协议和目录仅维持已有
> 地址兼容，不要求借普通功能改动迁移或删除存量文件。

## 哪些内容进入媒体总仓

- Cindy 需要拥有、缓存或持久化副本的图片、视频、音频和 3D 模型，统一进入
  `apps/desktop/src/main/cindy-media/` 管理的内容寻址仓。
- 用户磁盘上的原始文件如果只需就地读取，可以继续走已有受控本地文件通道；不要仅为
  预览就复制一份。远程设备或 SSH 文件必须保留真实来源，不能把远程绝对路径当成本机路径。
- docx、PDF、zip 等非媒体文件不进入媒体字节仓，继续使用已有 `xdt-file` 等受控文件
  通道。`xdt-audio` 只保留播放用户本地散文件的直读职责，不作为新的托管媒体写入口。
- 飞书、Discord、Telegram、企业微信四个个人 IM 渠道的入站附件，去处只由 `@cindy/im` 的
  `classifyInboundAttachment` 判定（MIME 或扩展名任一命中即可）：
  - 图片与音视频经 `IMHost.media` 进总仓（`cacheImage` 一律带 `staging: true`，另有
    `cacheMedia`），以可回收暂存写入。host 入仓前按真实字节核验类型（`im/shared/inboundMediaVerify.ts`），
    消息落库时 pin 为用户附件；下载期间发生换代则回滚。
  - 非媒体文件经 `IMHost.files` 暂存到按账号隔离的 `im-attachments/<渠道>/staging/`。消息路由到任务后，
    由 `im/shared/turnRunner.ts` 调用 `adoptStagedInboundFiles`，把触发消息自己的附件移入
    `im-attachments/<渠道>/sessions/<任务ID>/`。群历史附件和受保护内容不落库，留在暂存区按龄回收。
    实现见 `im/shared/inboundFileStaging.ts`。
  - host 缺对应能力或总仓拒收格式时标为不支持，不回落写 `cc-agent/*-media`。
- 另外两个个人 IM 渠道暂未接入上述分流，各自保留现有做法：
  - 钉钉只收图片，经 `cacheImage`（未带 `staging`）直接按用户附件入仓。
  - 微信由 `im/wechat/mediaStaging.ts` 在已知任务后直接 `ingestMedia` 媒体，并把文件写入同一棵
    `im-attachments/wechat/sessions/<任务ID>/`。
  - 任务删除时，两者与上述四个渠道统一由 `removeImSessionAttachmentDirs` 清理。迁移这两个渠道前，
    先对齐本条规则。

## 写入与记账

- 新写入优先调用 `ingestMedia` 或已有业务适配器，不新建专用媒体目录、cache store、
  数据表或协议，也不在调用方重复实现“写 blob、记账、挂引用”。
- 客户端共用壁纸使用统一媒体仓的 `ingestClientWallpaper` 入口与
  `client-wallpaper` 字节作用域（2026-10-02 用户裁决），复用 blobStore 的指纹、
  原子发布和安全校验，不挂账号数据库引用。引用真相为客户端自定义图片/MP4 视频设置或
  官方视频清单；发布与回收共用客户端操作锁，原生选图和下载不占锁。先成功保存引用，
  再由 recycler 回收该作用域中不再引用的文件。保存失败时在同一操作锁内重新读取磁盘引用，
  尽力回收未引用媒体；引用不可读或回收失败则保留文件，留到后续成功操作重试。
  这是统一仓内的生命周期隔离，不另建缓存引擎、数据库或协议；即使字节内容相同，
  也不与账号附件跨作用域去重，删除壁纸不会删除聊天引用的副本，反向清理亦然。
  本 PR 尚未发布，不迁移中间版本的账号设置或引用。
  自定义 MP4 与官方可选 CDN 视频共用 `.mp4` 作用域；两条回收入口都必须合并保留
  自定义引用与当前 CDN 清单引用，避免互删。导入只接受原生文件选择器返回的路径，
  主机按真实字节识别 MP4，视频上限 100 MB；图片继续走原有解码与 20 MB 限制。
  完整读取前，从同一安全文件句柄探测最多 4 KiB，已识别图片提前应用 20 MB 上限；
  未知头部保留原有 100 MB 外层上限，随后完整识别与解码，避免误拒头部较大的合法视频。
- 标准顺序是：主机核验媒体类型 → 按字节计算 SHA-256 并原子落盘 → 记录 blob → 挂业务
  引用。外部、插件或远端自报的指纹、扩展名和 Content-Type 不能单独作为可信依据。
- 持久附件或作品必须使用符合业务生命周期的引用。业务删除时只删除自己名下的引用，
  不直接删除共享 blob；物理回收由 `recycler.ts` 根据账本统一处理。
- `isCache: true` 只用于可以重新获取或重新生成的缓存。缓存一旦成为聊天历史、作品或其他
  不可再生用户内容，必须沿用现有 pin／引用流程转为不可按缓存回收。
- 远程文件的长期复用（2026-10-16 用户要求）不以短 TTL 清空：媒体经 `ingestMedia` /
  `integration-cache` 持久入仓，`remote-file` 命名空间按现有缓存预算自动 LRU 回收。
  预算用量统计整个媒体仓的 cache 字节，但排除手动管理的 `remote-media` 长期副本；
  命名空间只限制逐出候选，不另分配一份额度。
  消费者持有独立副本，新写入的仓内缓存同样可逐出；其他缓存已占满额度时不强留新副本。
  自动清理只接受该命名空间独占且仍为 `isCache` 的字节；扫描和条件删除都检查其他
  引用与 pin，不能清理聊天附件或其他集成的共享字节。其他媒体清理维持原手动流程。
  普通 HTML 等非媒体仍走 `remote-file-cache`。完整身份、复验与平台清理策略见
  [`protocol-compatibility.md`](protocol-compatibility.md)「远程文件连接复用与版本缓存」。
- 桌面聊天的不可变远程图片通过 `device-link/remoteMediaPersistentCache.ts` 复用媒体总仓，
  `remote-media` 索引包含账号、来源设备和原始地址。先查内存、再查磁盘，缓存命中不取件；
  重启和断连不清理，不增加自动到期或容量淘汰。设置中的「远程图片缓存」复用账本扫描和
  条件删除：独占缓存可删字节，共享缓存只解除 `remote-media` 索引，保留其他引用及字节；
  预检对共享项计 0 可释放字节，清理后其余缓存可继续按原规则回收。草稿与已 pin 附件仍跳过。
  清理开始与结束（含失败）都使图片缓存代次失效，防止清理期间启动的读取保留旧投影，
  或在清理返回后重建刚删除的索引；清理全程拒绝图片缓存读写，重叠清理全部结束才恢复，
  避免较早删掉的图片在遍历后续项时重新入仓。因清理失效的图片读取在下一代次立即重试，
  不沿用普通下载失败的 30 秒退避；普通附件不受图片代次影响。
  普通路径不按 URL 永久缓存：继续由主机复核版本，完整中转下载也可写入已有版本缓存；
  控制端发送图片时，同一缓存还保留实际上传的字节（含压缩结果），按其最终内容地址登记，
  覆盖直传与 OSS、文件选择与内存图片。不能用压缩前的本机原图代替历史消息中的压缩版本。
  留存遵守远程协议既有的 64 MiB 整图读取上限，并核对上传大小、指纹和真实图片类型；
  文件在上传后发生变化时不登记错误副本。上传开始时捕获账号与清理代次，迟到结果不能
  写入新账号或重建用户刚清理的缓存。复用现有 `remote-media` 清理入口，不增设目录或 TTL。
  音视频仍走流式播放。旧主机不返回版本时不把可修改文件登记为长期有效。
  回归见 `remoteMediaPersistentCache.test.ts`、`remoteMediaProtocol.test.ts` 与 `storageIpc.test.ts`。
- Chat Server 群聊、话题和伙伴私聊的图片也使用上述 `remote-media` 长期副本与清理入口，
  索引按账号模式、账号 ID、服务器端点、房间 ID、media ID 隔离；签名 URL 会过期，不能当作
  持久身份。`chatServerMedia.ts` 每次取件先按原合同校验媒体访问权限，再核对本地大小及内容
  指纹；命中只读本地，缺失或损坏才下载并修复。重启不丢索引，发送成功时留存实际上传的
  图片字节；留存失败不把已完成上传变成发送失败。下载及发送留存均捕获账号和清理代次，
  迟到结果不得重建已清理索引，群聊内存中的图片投影也随清理代次失效；普通文件的成功
  结果和在途下载不受图片清理影响，仍保留服务内复用，避免话题每轮重新下载 PDF 等附件。
  通用缓存瘦身在候选扫描与条件删除两处排除任何带 `remote-media` 引用的字节，专用清理仍
  保护草稿、pin 和其他业务引用，共享缓存只解除本命名空间索引。旧版下载只有无引用 blob、
  没有 media ID 索引，首次重新访问可能还需下载一次以建立映射；不猜测文件对应关系，
  也不批量清理旧文件。
  复用现有表及协议，不新增 migration；回归见 `remoteMediaPersistentCache.test.ts` 的
  Chat Server 重启、发送留存、隔离、损坏恢复及清理用例，以及 `chatServerGroupOpen.test.ts`。
- 零引用入仓只适用于已有草稿或生成结果提交链路。新增零引用窗口时，必须证明内容在消息
  落库前不会被回收，并用测试覆盖成功、失败、取消和重试。
- 所有官方壁纸原图均为 OSS/CDN 按需分发（2026-10-17 用户裁决，将三款场景的已有下载链路
  扩展到其余静态图片，替代静态原图随包的决定）。包内仅保留
  `renderer/assets/wallpapers/previews/` 中的三款 640×400 WebP 与 `thumbnails/` 中的静态缩略图；
  原始高清图和 MP4 保留为发布输入，不进入 Renderer 资源依赖图。
  清单中静态条目只有 `delivery` 与 `image`，顶层视频元数据仅用于带动态版的场景；
  2026-10-17 起五张 Cindy 壁纸（悄悄话、夜色回眸、赤夜漫步、霓光侧影、棱镜碎光）增加 1920×1080 动态版，
  窗边陪伴、未来工作室、梦境漫游从选择器下架（`RETIRED_WALLPAPER_IDS`），清单条目与 CDN 对象保留，
  已选用户的静态与动态照常可用，并在其设置中临时显示为选中项；
  静态条目不暴露动态选项、不下载视频。默认无壁纸和浏览设置列表不下载，
  选中且可见时下载对应高清图，动态模式且未启用减少动态效果时再下载视频；下载或解码失败保留可用背景。
  传输复用统一下载器并保留 guardedOutboundFetch 的来源校验，清单大小及 SHA-256 校验后入仓。
  缓存位于既有 `userData/cindy-media/client-wallpaper/`，仅以内容哈希和扩展名寻址，
  **不含应用版本或账号**；启动与升级先核对本地文件，有效即返回，不请求 CDN。
  只有文件缺失、损坏或素材哈希变化才重新下载。
  官方 WebP、MP4 与自定义媒体的引用合并保留；切换壁纸及常规升级不删除当前清单内已下载素材。
  回归见 `main/__tests__/wallpaperVideo.test.ts` 的升级离线复用及损坏修复测试，
  `customWallpaper.test.ts` 覆盖自定义媒体操作不误删官方图片和视频。
  发布脚本默认核验仓内原始素材，`--directory` 也接受按 hash 命名的导出目录或旧 `-hd.mp4` 输入。
  `node scripts/publish-wallpaper-videos.mjs --verify-only --directory=<原始素材目录>` 离线核验（MP4 原片不入库，
  需指向导出目录）；`--check-cdn` 只按清单读取线上对象，干净检出即可运行；
  `node scripts/publish-wallpaper-videos.mjs --check-cdn --region=global` 只读校验清单全部线上文件；
  实际发布使用 `node --env-file=<发布配置> scripts/publish-wallpaper-videos.mjs --directory=<原始素材目录> --region=global`，
  目录与离线核验为同一份受审核素材（按 `<sha256>.<ext>` 或 `<壁纸 ID>.<ext>` 命名）。
  中国大陆版显式用 `--region=cn`，内部 dev 环境显式用 `--region=dev`；三个环境分别发布并校验，
  资源先于对应客户端上线。只读校验优先读取本环境的 `XDT_GLOBAL_CDN_BASE_URL` / `XDT_CDN_BASE_URL` /
  `XDT_DEVCH_CDN_BASE_URL`，未配置时读取对应 endpoint 文件；dev 不回落到生产配置。
  对象名为 `wallpapers/<sha256>.webp` / `.mp4`；三款场景预览图可用
  `node scripts/prepare-wallpaper-previews.mjs` 从原始图片重建，该组三张图的总预算为 300 KiB。
  静态缩略图复用现有 `thumbnails/`，当前随包预览资源合计约 0.55 MiB。
  清单见 Desktop 的 `src/shared/wallpaper-video-manifest.json`。
- 《页面生成手册》（内置 Skill 的 `cindy-plugin-creator/references/examples/interactive-pages/PAGE-GENERATION.md`）
  沿用壁纸的按内容寻址发布：对象名为 `plugin-pages/manual/<sha256>.md`，客户端用内置手册的 sha256 拼
  `{cdnBaseUrl}/plugin-pages/manual/<sha256>.md` 交给业务后端，路径约定只在
  `apps/desktop/src/shared/pluginPageManual.mjs` 定义；手册在 `.gitattributes` 固定 LF，保证各平台打包出同一份字节、
  同一个 sha256。脚本读取当前检出里的手册，因此发布与 `--check-cdn` 都在本次发版所用的提交（发版分支或 tag
  的检出）上执行，不要在最新 main 上执行。手册改动后、对应客户端上线前，在每个区域手动执行
  `node --env-file=<发布配置> scripts/publish-page-manual.mjs --region=global|cn|dev`（区域必填，仓库没有手册时
  跳过）；`--dry-run` 不连 OSS、不联网，只打印 key、sha256 与 CDN 地址。**发版前检查项**：
  `node scripts/publish-page-manual.mjs --check-cdn --region=global` 与 `--region=cn` 都通过，即当前手册已在
  两个区域线上；只读校验的 CDN 地址取法同壁纸。同一 key 只有一种内容，远端已有相同内容时不再上传，上传仍带
  `x-oss-forbid-overwrite`；该检查不进 CI，避免 CI 依赖外网。
- 伙伴头像的本机副本（2026-10-17 用户裁决：读过的头像在本机缓存一份，显示前先读缓存）：另一台电脑上
  伙伴的 `cindy-media://blobs/…` 头像与云端伙伴身份的 `https://` 公开头像，经 `companion-cloud/avatarCache.ts`
  复用集成缓存的索引（`integration-cache` 引用行，键 `companion-avatar:…`，`isCache: true`）入仓，由回收器按
  总量上限与 LRU 统一回收，不另建目录、store 或协议。本机已有同指纹 blob 时直接使用，不再复制。只保存主机按
  字节识别为图片、且不超过头像上限（5 MB）的内容；公开头像走共用的受控公网图片下载。两种地址各自不可变
  （blob 地址即内容指纹，云端换头像会生成新地址），命中不需要重新校验。Renderer 经
  `maker:companion-avatar:resolve` 先查本机副本，未命中时照常显示原地址并在后台保存一份。
  Mobile 的伙伴与群成员头像复用 `peerFileCache` 的账号／realm 文件缓存，按来源设备与头像地址查本地字节；
  命中无需设备在线或重新下载，未命中才沿原媒体通道取件并保存（至多 5 MB）。远程下载落盘前复用图片头部嗅探，以实际 MIME 保存；HTML 等错误响应不入缓存，后续可重新取件。复用既有磁盘压力回收，换头像以新地址区分。
- 可再生 HTML 临时快照缓存是独立副本的例外：仅在快照已物化自己的文件、HTTP 服务不依赖
  媒体仓 blob、且该缓存不作为持久附件提交时，使用 `isCache: true` 和空引用入仓。
  必须验证媒体仓缓存不可用时快照仍可读取，以及重复打开、失败、取消和重试不新增业务引用；
  不得将已有持久附件的同内容 blob 降级为可回收缓存。

### 录屏剪贴板

录屏预览点击复制后，经 `region-screenshot/recordingClipboard.ts` 核验视频／GIF 字节并用
`integrationCachePut` 进入媒体总仓，以 `recording-clipboard:latest` 登记引用。它是不可重新生成的
用户录制内容，使用 `isCache: false`，不能按可再生缓存逐出。关闭预览或退出应用保留最近成功复制
的文件，以便继续粘贴；下一次复制成功后才移除本引用下的旧指纹，物理字节由统一回收器处理，
不删除其他附件的引用。重复复制同一内容复用指纹与引用；失败只回滚本次新引用，保留旧剪贴板文件。
异步入仓捕获账号与数据库，预览失效或账号变化时不发起剪贴板写入；操作不把仓内路径暴露给 Renderer。
Windows 使用 CF_HDROP，macOS 使用文件 URL 剪贴板，视频／GIF 均按文件复制以保留完整内容。

## 读取、协议与边界

- 宿主选择的 `userData` 根目录允许通过符号链接或 Windows Junction 重定向。
  `blobStore` 仅解析这一可信根的真实路径，入仓与受检读取使用相同的物理路径基线；
  `cindy-media`、作用域、分桶和目标文件内部的链接仍然拒绝，不得对完整 blob 路径
  直接 `realpath` 后跳过这些检查。回归见 `clientWallpaperMedia.test.ts` 的普通目录／
  重定向根对照与内部链接拒绝矩阵。
- 持久地址统一使用 `cindy-media://blobs/<sha256>.<ext>`。路径解析必须走
  `blobStore.resolveSafe` 或现有上层适配器，不根据 URL 字符串手工拼磁盘路径。
- 客户端壁纸地址为 `cindy-media://client-wallpaper/<sha256>.webp` 或 `.mp4`，
  由既有协议 handler 的严格解析分支服务，不触发账号账本的访问时间更新。普通附件
  与插件的 blob 解析器不接受该 UI 专用作用域；字体工具窗口不获得自定义图片地址。
- 客户端壁纸 MP4 的播放请求从已校验的同一文件句柄按 Range 流式读取；无 Range 或开放区间
  也分块传输，不先把整份视频读入主进程。Node 与 Web 两侧队列均按字节设置缓冲上限，
  结束、错误、请求中止和消费者取消时关闭句柄；沿用既有 200 / 206 / 416 与缓存语义。
- `cindy-media://` 的 scheme privilege 和 handler 只在现有集中入口注册。不要为单一功能
  新增媒体协议；确需改变协议能力时，同时按 Electron 安全规则审查 CSP、fetch、Range、
  路径校验和 Renderer 暴露面。
- 默认不把媒体仓绝对路径直接暴露给 Renderer、插件或远端。跨边界传递使用托管 URL、
  受控 grant／deposit／ledger，或已有上传与远程媒体服务。
- Core 媒体生成的同步结果与异步 poll 结果只返回受管地址和元数据，不自动附图给模型，
  也不提供独立的 `inspect` 动作。图片和视频均由 Agent 按任务需要决定是否查看：通过
  下述路径解析能力取得文件，再使用已有的文件查看、抽帧或分析工具，不在 Core 重做
  查看机制。用户端继续使用受管地址展示成果；生成成功不代表 Agent 已经看过内容。
  不引入 ffmpeg 依赖、隐藏解码窗或并发调度机制；只查看视频帧不代表声音、对白或
  音画同步已经验收。实现与回归见 `mcp-integrations/ghost.ts`、
  `mcp-integrations/__tests__/ghostWorkdirGate.test.ts` 与
  `packages/cindy-tools/src/__tests__/ghostMcp.test.ts`。
- Agent 为完成当前任务而查看、抽帧或分析已有媒体，或回答用户的存储位置查询时，可主动
  调用 `media(action: "resolve_local_path", url)`；不要求用户先问本地路径或另行口头同意检查。
  Host 用安全解析器核验为现存普通文件，沿用已有路径揭示权限，不因分析用途绕过审批。
  Auto 档沿用实时审批负责人：原生审批已审核受管 URL
  及“向 Agent 返回该媒体的本机绝对路径并写入任务记录”这一效果时，不因安全解析而再调
  Cindy 复审；这里仍是同一受管资源，不是符号链接暴露出的新文件目标。由 Cindy 负责时，
  对精确单文件路径和用户请求进行 AI 审阅。工具说明必须写明真实效果和当前权限流程，
  不得以“之后一定弹确认卡”误导审批。Cindy 审阅 allow 可返回当前 Agent，block 返回原因，
  ask 或服务故障才使用 Host-owned 确认卡。本地活跃 Full Access 自动允许，
  其它档位仍须用户点击允许；远程任务不能借此自动取得控制端文件路径。
  路径进入会话记录，因此也可能同步到用户的配对设备。返回的是 Cindy Host 所在电脑的
  路径，不保证在 SSH 工作区可用；不新增跨主机复制或文件读取授权。手机与桌面远控仍
  通过任务所在电脑执行。向用户展示或交给插件时继续使用受管地址，不以本机路径替代。
  Agent 自报“用户已同意”不是授权证据，也不能借路径揭示给插件或远端开放文件读取。
- `xdt-image://`、`xdt-video://`、`xdt-model://` 和 `userData/cc-agent/` 是冻结的历史兼容层。
  可以读取已有地址，不得新增写入路径、扩展生命周期或把新功能接回旧仓。
- 删除或清理历史目录必须走已有的显式名单、复验和用户确认流程；不得新增任意
  `cc-agent` 子目录删除能力。

## 已授权生成任务的结果下载

- 下载是生成流程内部的一步，不新增“领取”状态、列表或用户操作。上游返回后，客户端
  下载并通过 `ingestMedia` 返回受管媒体；需要确认时暂停同一次操作，批准后自动继续。
- Guide 的 `allowedUrlHosts` 保留为已确认来源名单。名单内正常目标自动下载；名单外
  来源、HTTP、特殊端口、地址内登录信息、受限网络等权限要求通过
  Cindy 普通 `permission` 交互确认。卡片只说明实际地址、原因和本次范围，不出现
  Guide、“模型说明”等内部概念，不使用仅限本机的 `ghost_grant_confirm`。
- 用户拒绝后结束本次下载，不自动重试或再次审批。网络失败由客户端最多自动尝试
  三次，同一次操作及其只读地址刷新复用已经批准的来源和权限；只有目标或所需权限
  变化才再次确认。不以浏览器或外部应用作为强制下载出口。
- 默认经 `guardedOutboundFetch` 做 HTTPS、DNS/IP 校验及固定 IP 连接。人工例外只对
  当前精确 URL 的单跳生效，不自动传递到重定向目标，不改变其他网络调用的默认策略。
  来源批准按 origin 复用；受限网络例外按不含 fragment 的完整 URL 绑定，路径或 query
  变化后须重新确认该受限目标，不能借同源跳转访问另一内部接口。受限网络卡片显示
  当前目标的路径及脱敏后的 query，复用现有 URL 脱敏规则，不显示登录信息或签名值。
  不附带生成接口凭证；地址内登录信息须单独确认，且不得沿重定向传递。
- 网络时间累计最多 120 秒，连续 30 秒没有响应或数据则重试，单次人工审批最多等待八分钟。
  上游生成沿用自身请求超时，不另加覆盖生成阶段的下载计时器。
  正常跳转逐跳重验目标与权限，循环跳转作为下载故障处理，不为次数追加审批。
  所有结束路径均释放 body 和 dispatcher。
- URL 媒体逐块写入 Host 私有临时文件，类型识别使用有界探测，哈希与入仓同样分块处理。
  不因原内存大小上限拒绝下载或追加大小审批；完成、失败、取消后尽力清理临时文件。
  文件源仍走 `ingestMedia` 和现有字节仓的原子发布、去重与记账，不另建媒体存储。
  base64 响应沿用原大小限制。
- 下载等待响应与重试共用 120 秒预算；响应到达后以字节为进度，只有断流 30 秒或累计 9 分钟才
  结束，避免慢线路截断已付费成片。累计上限须低于 Agent 工具调用的 10 分钟超时。失败日志只记
  错误名、已收字节和耗时，不记错误正文或签名地址。
- 下载失败保留原调用的成功响应。异步签名地址失效时只查询原上游任务刷新地址，不重新
  付费生成；刷新结果成功入库前不覆盖原成功响应。本地入库失败由客户端对同一份已下载
  字节最多尝试三次，期间复核账号和任务，不再次下载、生成或审批。
  `pending` 且存在成功响应的记录不随六小时清理删除，也不占正在生成的名额；
  不新增并行的领取状态或授权表。用户拒绝或客户端重试耗尽均返回非自动重试结果，避免模型另起一次调用而重复发起审批。
- 真实 MIME 识别、账号/任务归属、受管入库规则持续有效。下载授权不包含执行文件、
  安装程序或覆盖用户文件的授权。旧 Guide 快照与 base64 结果保持兼容。

## 模型请求超限时的附件恢复

- 只在本地代理收到的请求实际超过既有字节上限，或上游明确返回 HTTP 413 后恢复；正常请求不因图片数量、预估
  token 或接近上限而丢弃附件。上限本身保持不变。
- 超限请求先分块落 Host 私有临时文件，base64 字符串不论单个大小都参与恢复，并分块解码。
  临时写入按实际可用磁盘共享预算，预留 256 MiB，并为解析、解码和保存预留副本空间；
  不另设固定附件体积门槛。磁盘不足返回明确的 507，可清理空间后重试，原始历史不变。按历史顺序保留
  足够数量的旧附件为本地文件，使请求重新小于上限；无需移出全部附件。
- 上游 413 不提供可靠的字节上限：保全全部可识别的内联附件，请求确实缩小后最多重发一次，
  重发前重新验证原 dispatch gate。不猜测供应商上限，不把字节换算成 token；纯文本、
  保全失败或不能缩小时原样返回该 413，客户端停止则取消保全与重发。
- 已识别媒体经 `ingestMedia` 挂 `session-attachment` 持久引用；其他文件复用
  `hook-attachments/<sessionId>` 生命周期。必须保存成功后才用真实绝对路径替换内容，
  并明确告诉模型当前消息不再包含该附件内容，需要时重新读取。
- 仅修改此次发给模型的请求，不改原生历史文件，不重新执行生成或其他工具操作。
  先计算真实路径及替换后的请求大小，确认可恢复后才提交附件。保存失败、取消或归属变化时
  不转发部分结果；整批新增媒体引用经补偿日志回滚，仅删除本次新建的非媒体文件，
  不删除已有文件或共享 blob；无引用 blob 仍由统一媒体回收。临时请求与解码文件在结束时清理。
- Codex、Claude、Pi 的本机 HTTP JSON 代理共用恢复；Pi 必须验证原有 session token。
  缺少有效任务绑定、SSH 任务、压缩/不透明请求不套用本机路径恢复。
- WebSocket 例外：ChatGPT 订阅直连的 Codex WebSocket 单条消息上限约 16 MiB（超限回 1009，
  HTTP 无此限制），所以只有该链路的出站消息超过 15 MiB（实测阈值，常量在 `codex-proxy-host.ts`）
  才复用上述外置，压到 12 MiB 再发；未超限的消息逐字节不变。它没有 507 语义：外置不可用、
  无任务绑定或压不下来时原样转发，由上游 1009 与 Codex 的 HTTPS 回退兜底。

## 图像参数与最终结果

- Art 返回的画幅、成品尺寸、分辨率和质量意图不得在客户端适配层静默丢弃。
  第三方图像通道声明自己的协议，`cindy-media/imageParameters.ts` 同时生成调用指南和
  验证实际请求；账号 ID 不参与协议推断。旧调用省略新增参数仍然可用。
- `size` 表示生成像素尺寸，`resolution` 表示供应商的分辨率档，`quality` 是原生质量。
  不把不同来源的枚举互相套用，不强制 `medium` 或 `1k`。明确参数优先，省略时由上游决定。
  已知 GPT Image 尺寸约束在付费提交前检查；不合法时保留 prepared 调用供更正。
  目标成品尺寸不满足模型约束时，由 Agent 选择合法生成尺寸并单独完成成品缩放，不能谎报
  请求尺寸就是实际输出尺寸。没有自动缩放或偷偷裁切。
- Codex SSE 的 partial image 仅为预览，不能在失败、未完成或只有预览的断流中当成成品。
  大 Base64 响应的字符校验必须采用常量栈空间，避免分组重复正则导致已生成图片收取失败。
- 参数依据：[OpenAI](https://developers.openai.com/api/docs/guides/image-generation)、
  [Gemini](https://ai.google.dev/gemini-api/docs/generate-content/image-generation)、
  [xAI](https://docs.x.ai/developers/model-capabilities/images/generation)。
  回归覆盖 `imageParameters.test.ts`、`invocationService.test.ts` 和各图像通道测试。

## Codex 原生生成图交付（#6412）

- `imageGeneration` 完成事件保留 native thread / turn / item 标识、`savedPath` 与 `result`；
  裸 Base64 是图片数据，路径不能覆盖同时返回的字节。翻译层不读文件、不解码图片。
- 远程 Agent 的源 Host 在事件进入可确认的传输日志前读取源文件或验证原生字节，按真实
  MIME 与 20 MiB 上限校验；控制端声明支持持久交付回执时才入 `cindy-media` 建立恢复所有权。
  旧控制端没有回执能力时只准备传输字节，不留下永久固定的源副本。跨设备发送不带源文件路径的 data URL；控制端给
  native 图片标注远端来源，不做工作区路径替换，不读本机同名文件。SSH 只走已有远端文件服务。
- 图片字节只存在媒体总仓。账号私有 `cindy-media/generated-images-v1` 记录小型交付日志，
  不保存 Base64；native 标识生成稳定交付 ID，任务 scope 和源 Host scope 隔离。待交付副本
  复用 `integration-cache` 引用但设 `isCache: false`，不可按可再生缓存清掉已付费产物。
- 任务 Host 先保存 blob、持久工具结果及 `session-attachment` 引用，再确认源副本可释放；
  事件流 ACK 不等于持久交付。成功只表示任务 Host 已保存，不能宣称手机已下载。
- 失败结果分别保留生成状态与交付状态。Desktop / Mobile 的“重试交付”只按交付 ID 重读
  原产物；不发送 Agent 消息、不重新生图。首次历史读取触发后台恢复，不阻塞历史首屏。
  重启后复用已有 blob 或源 Host 副本；原产物确已不存在时保留失败，不能假成功。
  重试更新已有结果后，通过 `broadcastMessageRow` 推送相同消息 ID 的最新持久内容，
  让 Mobile 即时替换失败状态；不能仅依赖 `maker:event` 的工具结果事件。
- 每个异步边界检查账号；消息发布检查任务删除、清空与结果 tombstone / rewind。
  清空前的未知远端产物不自动补入；新代次仍可恢复。清理独立枚举源端，只释放清空前代次的产物（删除释放全部）。
  代次来自任务 Host 的 `cleared_at`，随新远程会话传递，不比较两台设备的墙钟。清理回执
  先落盘，源端离线时保留，账号下次就绪重试；即使没有本地图片日志，也从任务清空/删除
  状态重建清理。删除/回退只抑制对应稳定结果 ID，不能阻断后续无关图片恢复。
  供应商组中转持久保存上游设备/任务/relay 回执，自己入仓且引用落库后再释放成员副本；
  回执失败跨重启重试，流收尾等待图片准备完成。分享撤销清理同一受邀者的源 Host 引用。
  原生交付自行提交带任务边界的附件引用，消息写入器不并发启动普通附件挂账。
  清空若发生在引用写入期间，释放会按同一任务的可见消息条件补偿；其它任务或清空后
  新消息仍引用同一图片时保留引用。释放日志保留受管地址，重启可继续未完成的引用清理。
  同一任务并发交付/恢复合并，重复 native 完成事件复用消息 ID 与附件引用。

## 多端与远程

- 将已有截图或本地图片保存为持久受管附件时，Agent 使用 Core `media(action: "import_image", path)`：Host
  按当前任务文件权限读取，在当前媒体仓入库并登记任务引用，再返回 `xdt_image_urls`。
  工作目录外路径复用现有授权，SSH 任务不得回退读取控制端同名文件。返回成功仅表示
  Host 已完成交付准备，不代表手机已经下载；禁止自行拼接 hash 或复用其它沙盒的地址。
  同一任务并发导入相同内容时，引用检查与登记必须串行，避免重复持久引用。
- 工具选择由 Agent 根据自然语言与已有文件上下文完成，不能要求用户记住工具名或参数。
  验收必须另用不含工具名、action 或协议提示的新任务验证自然语言交付；指定工具的调用测试
  只证明工具链路可用，不能证明普通用户的使用路径已通过。
- `import_image` 不是客户端展示图片的唯一入口。Agent 输出正常的本地 Markdown 图片时，
  客户端继续按当前任务的路径上下文和既有权限取件，不能因为没有调用指定工具而拒绝展示。
  已完成的 assistant 消息在写入及历史读取时，经 `taskImageDelivery.ts` 自动保存当前任务
  工作目录、可验证的当前 Claude scratchpad 内的普通图片（单张最多 20 MiB）。成功后将
  消息中的真实 Markdown 图片引用替换为 `cindy-media://` 并挂任务引用；代码示例与原生
  Agent transcript 不改写，单张失败不阻塞正文或其它图片。IM 出站复用同一导入入口。
  官方渠道只对整轮内容导入一次，最终正文复用该次导入的地址替换表；正文与附件扫描
  指向同一副本，不因临时源文件在收口时删除或替换而再次读取出不同结果。
  官方渠道的每张导入失败都要把原因（目录外、格式不支持、超限等）写入 main 日志；正文末尾的
  未送达提示按界面语言点名未发出的附件。渠道出站与桌面聊天展示一致，接受本机任意路径的普通
  图片，不限于工作目录与 scratchpad（2026-10-27 裁决：渠道发图与导入后再发本质相同，
  不为此多走一步）；原则是 Cindy 聊天里能显示的图片就能发到 IM，群聊中由非主人触发的轮次同样适用，
  个人微信 `send_file_to_user` 的图片同此规则（按内容识别），普通文件仍限工作目录。
  网络／设备路径、非普通文件、超限与非图片仍拒绝，SVG 需 Agent 先转 PNG。
  当前会话所在渠道一律用回复里的图片引用发图：文本渠道收集为附件，飞书、Telegram、Discord
  卡片先改写为受管引用再原位上传；渠道发送工具只用于跨会话推送，不引导 Agent 在当前会话用它发图。
  SSH 官方渠道不导入或读取控制端文件，仍复用出站引用清理：本地图片地址（含远端
  Windows 路径）只保留说明，并提示附件发送不完整，不将不可用的媒体地址发到 IM。
  与图片共用目标的普通链接也指向保存后的同一图片；外发时这些本地链接降为显示文字，
  并清除对应引用定义，不能把原始路径留在 definition 中。网页链接和代码示例不改写。
  兼容仅限 hostless `xdt-image:///绝对路径` / `xdt-file:///绝对路径` 图片引用；协议读取器
  不放宽。本机任务归属、账号、清空、编辑及 rewind 在提交时复核，不扫描其它任务目录。
  自动导入在首次文件系统访问前拒绝 UNC、WebDAV 和 Windows 设备命名空间；先解码兼容
  图片 URL，再检查路径，不能等 `realpath` 触发网络解析后才判断目录范围。
  确认消息未发布时，新建引用的回滚复用原账号的补偿日志；旧数据库已关闭时保留待补偿 ID，
  由原账号下一次就绪时的既有恢复流程删除，不向新账号写引用，也不回滚已发布的消息。
  数据库提交回执丢失时保留引用，避免误删已提交消息的图片；不为此新增发布恢复队列。
  已知中断边界：入库成功、消息地址尚未更新时进程退出，任务引用可能保留到任务删除。
  源文件仍在时，下次读取消息会复用同一副本完成更新；源文件已被清理时无法仅凭原路径
  找回副本，保留原消息且不宣称交付成功。本次不提供跨崩溃的导入与消息发布原子性。
  导入、发布、回滚、普通消息挂引用与回退后的存活消息引用清理，共用 `ledger.ts` 的
  同数据库、同任务串行入口。挂引用等待导入结算后再去重；清理等待发布或回滚后再判断
  是否仍被消息引用，不能在正文尚未替换地址时删除导入正在复用的引用。
  无可信 SDK session、原生长目录 hash 布局、SSH 或已删除源文件不能靠此恢复；未成功
  导入的直接路径仍依赖源文件存在，不得声称已持久入库。
- Desktop 的图片加载失败默认显示暂不可用，通过现有 preload 图片读取接口确认源文件
  `ENOENT`（IPC `NOT_FOUND`）才显示缺失；不使用被受管协议 CORS 策略禁止的 renderer fetch。
  流式输出时保留加载状态，流式结束、地址更新、窗口重新聚焦或网络恢复时自然重试，
  不增加轮询。仅字节读取成功不触发重试，避免图片可读但不能解码时反复加载。
- Mobile 自动预览本地 Markdown 图片仅限当前任务工作目录内；请求携带当前目录作为
  `baseDir`，Host 按真实路径复验，防止符号链接越界。目录外图片保留显式点击入口。
  正文图集收集同样复用此边界，避免查看器预取相邻页时绕过限制；目录外文字入口点击后
  只打开该图片，不把它加入其它图片的预取集合。目录内缩略图、点击地址与图集地址保持一致。
- Mobile 正文 Markdown 的受管图片与附件共用缩略图取件队列和原图查看器。实际包含预览的块
  不合并进原生可选文本；回退到文字入口时保留正文选择。错误按稳定代码区分源文件缺失与设备离线，旧 Host 的未分类错误
  保留通用加载失败。原生解码失败沿用一次强制刷新，手动重试仅重取当前图片。

- 媒体记录必须保留设备、会话、插件或远程主机等真实归属信息，不能相信调用方自报的
  本机路径或 owner id。
- 远程来源无法证明、路径归属不明确或媒体类型无法安全确认时应 fail closed，不得回退读取
  本机同名路径。
- 跨端传递只改变传输形态，不改变账本和权限语义；上传缓存、临时副本和持久引用要分别
  设计生命周期。

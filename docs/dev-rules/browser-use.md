# Browser Use：三种浏览器后端的共同规则

Browser Use 有三种执行端，由用户在 Browser Use 设置里选：专用浏览器（独立实例，`external`）、
侧边栏（`rsb-webview`）和「我的浏览器」（经官方 Cindy Chrome 扩展控制用户自己的 Chrome，
`user-browser`，契约见[插件安全与编写](plugin-security-and-authoring.md)）。本文只放三端共同
遵守的决定；工具层代码在 `packages/lizi-mcps/src/browser/`，配方加载在
`apps/desktop/src/main/browser-recipes/`。

## 优化做在共享层，三端都受益（2026-10-29）

用哪种浏览器是用户的选择，体验改进不能只落在一种后端上。参数容错、结果整形、截断上限、
提示语等优化默认改工具层（`tools.ts`）、`browser-workflow` 规则、配方与站点指南；只有某个
后端独有的缺口才改该后端。改某个后端时检查其它两个是否有同样问题，一并处理或说明为何不适用。
用真实任务实测时三种浏览器都要跑（至少覆盖改动涉及的路径），对比结论、用时、调用次数与报错。

## 图片读取与工具发现

网页抓取失败不等于浏览器不可用。渐进发现入口 `browser/server.ts` 要在加载详细工作流之前，
说明浏览器适合继续读取动态页面与图片；具体读图、登录墙与结束条件仍由
`browser-workflow` 维护。不把 HTTP 响应头、跳转地址、DOM 图片标签或 alt 当作已查看图片。

`scripts/eval-browser-image-fallback.mjs` 是显式启动的真实模型对比，不属于默认单测：

```sh
node scripts/eval-browser-image-fallback.mjs --live --codex-home /path/to/authorized/codex-home \
  --baseline-ref <before-commit> --model gpt-6-astra --effort high --repeats 5
```

它调用生产 MCP 的发现、参数解析、规则返回和图片输出，页面运行时使用固定夹具；
A 读取基线 Git 版本，B 使用当前工具发现和配方但保留基线工作流，C 使用全部当前改动。每组使用相同的随机
错误码／版本号图片，答案只通过图片像素交给模型；交错运行顺序，保存所有结果、工具轨迹、
输入／输出／缓存 token 与耗时到独立临时目录，不择优报告。八类场景覆盖抓取失败、短链接、
误导 alt、登录墙、图片删除、静态文章及 X 公开图片／正文；可用 `--only` 和 `--variants` 缩小范围。

这是缩小工具目录后的行为实验，**不是完整 Cindy/Codex 会话或真实浏览器 E2E**，不证明
真实 X 登录、网络、扩展或三种后端均可用。真实网页和后端验证另记，不与夹具成功率混算。
凭证只在内存中使用，不写入报告；手动评测须有用户授权，默认单测不得读取账号。

### 配方发现与图片结果衔接

补充配方应出现在所有声明匹配的站点指南中，而非仅挂到第一个域名。导航及已有标签快照的推荐按明确意图、
URL 路径匹配程度、只读用途排序；`recommendationPaths` 是字面路径段加 `:参数` 的前缀模板，
不执行正则或脚本。推荐不会自动执行配方，也不代表授权。推荐去重包含候选集合，避免访问
首页后吞掉后续帖子页的不同候选，同时不为每条帖子重复推送同一组。

X 公开单帖的 `x-tweet` 可返回原图 URL；有图片时输出 `imageReading.status=not_viewed`
和下一步说明，无图片时不附加。任务依赖图片内容时继续下载并用原生图片工具查看，或在
自己的浏览器标签打开原图截图。它是读图交接提示，不是自动下载、OCR 或已读图的凭证；
不得把这一步当成端到端保证。私密、已删除和网络失败仍按真实结果处理。

## 一次调用多步、底层出口与按模式给规则（2026-11-10）

起因是 Browser Use 1.0：它删掉预定义的页面状态与动作清单，让模型在一个常驻 Python 环境里直接对
调试协议写代码，并在提示词里要求「每次调用都是一整轮模型请求，不要单独花一轮只看一眼」。我们
只取其中对三种后端都成立的部分，都做在共享工具层：

- **`batch`**：`steps` 里每一步就是 `browser` 工具的一份普通参数，逐步走同一个处理入口，因此
  代输入保护、地址协议检查、后端能力门控、结果截断与配方建议都照旧生效。先整体校验再执行：每一步
  经真实处理入口的 `checkOnly` 模式走到派发之前，所以模式校验、地址协议、能力门控、`extract` /
  `cdp` 的专属参数检查与真实调用是同一组判断，不会各说各话；一批最多 3 个 `screenshot` 步骤，超出
  整批拒绝（图片要么全部返回要么不执行）。执行中任一步失败即停，返回已完成各步的结果，不自动重放；
  批次开始时固定后端身份，执行中被切换模式则剩余步骤不执行。`recipe`、`upload`、
  `setBackend` 各自要过任务审批，不能放进 batch：工具层拒绝，
  `maker-host/mcp-tool-approval-policy.ts` 对带这些步骤的 batch 仍按每次确认处理，作为第二道。
  没有做成「模型写脚本在宿主执行」：那需要沙箱，而 Agent 本来就有 shell。
- **`cdp`**：复用配方适配器已有的会话通道（`recipeCommand`，三端各自实现），一次调用开一个
  会话、顺序执行、结束即断开，不跨调用保持连接。模型可发的命令是运行时白名单
  （`browser-control-runtime/src/recipe-command.ts`）的子集，清单在 `lizi-mcps/src/browser/cdp.ts`：
  **不含读 Cookie**（凭证不进模型）和原始截图；导航、标签页、上传、下载继续走普通 action 及其
  检查。另有四个辅助命令 `nodes` / `click` / `type` / `call`，把「无障碍树里找到节点 → 真实点击 /
  输入 / 取值」收成一步；无障碍树能看到封闭 Shadow DOM，页面快照和页面脚本都看不到。它与
  `evaluate`、坐标点击属于同一类能力，不新增审批档位。「我的浏览器」的发布版扩展拿不到调试接口
  （`rawProtocol:false`），调用前拒绝并提示由用户决定是否换专用浏览器。
- **规则按当前模式给**：`browser-workflow.md` 里只适用于部分后端的段落用
  `<!-- backend: external, rsb-webview -->` … `<!-- /backend -->` 标出（标记各占一行），
  `workflow-rules.ts` 按宿主报告的当前模式渲染；宿主不报告模式时返回全部段落。模式在读取规则后
  变化时，`status` / `setBackend` 的结果带 `rulesHint`，让 Agent 重新 `list_tools`。新增只对
  部分后端成立的规则时必须放进标记块，并保证去掉其它块后上下文仍然读得通。

没有照搬的部分：模型代码无沙箱执行、取消暂停与人工接管、默认云端浏览器。预定义的快照与 ref
仍是默认路径，`cdp` 只是快照够不着时的出口。

### 多步任务对比评测

`scripts/eval-browser-tasks.mjs` 是显式启动的真实模型对比，不属于默认单测：

```sh
node --import tsx scripts/eval-browser-tasks.mjs --live --baseline-ref origin/main --repeats 3
```

A 是基线提交的工具层，C 是当前工作区；两组都经生产 MCP 入口驱动真实的无头专用浏览器运行时，
页面是脚本自带的本机夹具（表单、多页读取、分页表、延时内容、按下才展开的菜单、封闭 Shadow DOM
里的按钮与表单、跨站 iframe、搜索）。每次运行的答案随机生成，只能从页面读到；各题按两组交错执行，全部结果、工具调用
轨迹、轮数、费用与耗时写入独立临时目录，不择优报告。模型由本机 `claude` 命令行以打印模式驱动，
脚本不读取任何凭证；每次运行都会产生真实用量。

题库分三组（`--only` 按编号挑题）：

- **操作题**（`form` `catalog` `orders` `report` `settings` `vault` `badge` `iframe` `directory`）：页面一打开
  就是完整的，考的是连续多步和快照够不着的控件。
- **读取题**（2026-11-12 加，`late` `spinner` `manual` `status`）：打开时还是空的、靠脚本稍后才渲染的页面；
  先显示「Loading…」再换成内容的页面；一次读不完的长文档；不是 HTML 的 JSON。它们对应真实网站对比里
  测出的问题，操作题的页面瞬间就绪，测不出来。
- **真实网站题**（`--real-sites` 才加，`gh-releases` `gh-pr` `crates` `pypi` `hn` `tailscale` `apple` `wiki`）：
  八道公开网站上的读取题，标准答案在运行前从各站的公开接口或页面现取，取不到的题直接跳过并说明。
  它们需要联网，取决于网站当天的内容，也可能被网站拦截：这一组失败是去查原因的信号，不单独当作回归。
  改规则措辞、读取或等待逻辑后跑这一组；与其它产品的横向对比不在这个脚本里。

它只覆盖专用浏览器运行时和夹具页面，**不证明侧边栏、「我的浏览器」或真实网站上的表现**，也
不是完整的 Cindy 会话。结论只用于比较工具层改动前后的同一批任务，不当作通用成功率。

`--check` 不调用模型、不产生用量：在同一套真实浏览器与夹具上经 MCP 入口直接驱动 `batch` 与
`cdp`（封闭 Shadow DOM 内的点击、输入、取值，拒绝读 Cookie，整表单一次提交，多页读取，失败即停），
以及跨站 iframe 里的 worker 随页面销毁后 `navigate` 仍能返回，
结果不对就失败。改这两个 action 后先跑它。侧边栏的同一路径由
`browser-backend/__tests__/rsb-webview-backend.test.ts` 用真实后端加假页面覆盖会话契约。

答案，可以把题目发给任何产品；`--effort` 指定命令行的推理强度。

### 在运行中的 Cindy 里实测三种后端

`--serve` 只起夹具网站并打印地址、一个 run id 与答案（`/__state?run=<id>` 可看页面实际收到的
提交），供在运行中的 Cindy 里逐个后端手工驱动。2026-11-10 用含本改动的个人版实测：

- **「我的浏览器」**（扩展 0.4.68）：8 步表单一次提交、多页读取、失败即停均符合预期；`cdp` 在
  调用前被拒绝，含 `cdp` 步骤的 batch 整批不执行；规则按模式返回，切换后 `status` /
  `setBackend` 带 `rulesHint`。
- **侧边栏**：batch 同上；`cdp` 的 `nodes` / `click` / `call` 正常，点击是可信事件。**发现并修复**：
  侧边栏的页面在后台没有焦点，`Input.insertText` 不报错也不生效，`type` 曾在表单为空时报成功。
  现在 `type` 回读字段内容，没落进去就直接设值并触发 `input` / `change`（结果里 `via` 标明），
  仍不对则报错。修复后的 `type` 尚未随新构建在侧边栏复测；它兜底用的设值方式已在侧边栏里经
  `call` 实测通过。另外侧边栏的快照本身取自无障碍树，已能看到封闭 Shadow DOM，`cdp` 在那里
  多数时候用不上。
- **专用浏览器**（套用了系统浏览器登录态的真实窗口，2026-11-11 补测；当日首次尝试因构建没有
  读取系统浏览器资料的权限报 `REAL_PROFILE_READ_DENIED`，与本改动无关，授权后恢复）：batch
  10 步（8 步表单、跳转、读取）成功且失败即停；`cdp` 在封闭 Shadow DOM 里的 `nodes` / `type` /
  `click` / `call` 全部符合预期，这里页面有焦点，`type` 走的是 `Input.insertText`。补测用的仍是
  修复输入之前的构建。

无头环境里页面总是有焦点，所以上面的输入问题只有在真实侧边栏里才暴露；改 `cdp` 的输入路径后，
要在侧边栏里实测一次。

## 打开后在同一次调用里读页面：先等页面有内容（2026-11-11）

`open` 在标签页建好时就返回，`navigate` 在文档加载完成时返回；靠脚本渲染的页面这时还没有任何文字。
同一次调用里紧接着的读取（`afterSnapshot`，或 batch 里的下一步）会读到空页面，模型只能再花一轮
等待后重读。本机夹具页瞬间加载，[多步任务对比评测](#多步任务对比评测)测不出这个问题；在真实网站上
12 次带 `afterSnapshot` 的 `open` 有 10 次读空。

工具层（`tools.ts` 的 `waitForPageContent`，三种后端共用）在这两种情况下先等页面出现内容再读：

- 只在「`open` / `navigate` 成功，且同一次调用里后面还有读取」时生效：带 `afterSnapshot`，或是 batch
  里不是最后一步。单独的 `open`、batch 末尾的 `open`、点击等动作的 `afterSnapshot` 不等。
- 探测是一次「读页面文字」（下一节的固定读取 `domRead: {kind:"text"}`，只取前 200 字符）：
  页面自己的 `location.href`、`document.readyState` 和可见文字长度，至少间隔 250 毫秒，最多 5 秒。
- `navigate` 已经等过文档加载：有文字就放行，只在页面还是空的时候继续等。
- `open` 之后：文字不少于 1500 字符就放行；更短的要连续两次长度相同（脚本渲染的页面先出页头页脚的
  几百字符，正文稍后才到）；文档还没加载完且不足 200 字符时要连续四次相同（实测某搜索页先显示 114
  字符的菜单，半秒后才出结果）；加载完成后一直没有文字的页面（空白页、图片）2 秒后放行。
- 只显示「Loading…」「Just a moment...」这类字样的页面（不足 200 字符，含这类词或以省略号结尾）
  加载状态已完成、内容也不再变，和一个很短的正常页面分不开：给它最多 3 秒变成别的内容。夹具题
  `spinner` 实测：没有这条时读回来的是占位文字，模型要再开一次页面等待（18.3 秒），加上后一次读完
  （5.1 秒）。
- `open` 不能只靠快照或 `wait loadState` 判断：新标签页先显示占位页（`chrome://new-tab-page/`），它的
  快照不为空、加载状态已是完成，标签页报告的地址却已经是目标地址；只有页面自己的 `location.href`
  能分清是哪一份文档。浏览器内部地址（`about:`、`chrome:` 等）一律当作目标文档还没到。
- 专用浏览器里固定读取不算交互，没有普通页面脚本后面那约 250 毫秒的导航观察期，一次探测约 20 毫秒。
  「我的浏览器」旧版扩展不支持，探测第一次就按 `BROWSER_RUNTIME_INVALID_REQUEST` 放弃，行为与修复前相同。
- 尽力而为，不改变动作本身的成败：探测连续失败 4 次（页面正在跳转时会失败）或到时间，就按原样
  读取。它只保证「不是空页面」，不保证异步数据已全部到齐；后者仍由模型按具体内容等待。

- 已知限制：同一个地址已经在另一个标签页打开时，运行时对刚建好的标签页可能先解析到那个旧页面，
  探测看到的是旧页面的内容而提前放行，读取结果与修复前相同（空页面）。`open` 返回的 `sameSiteTabs`
  本来就提示优先复用已有页面。

规则文案（`browser-workflow.md`）同步说明了这一点，避免模型再为刚打开的页面单独加一步等待。

## 核心用法写进工具说明，读页面用 `read`（2026-11-12）

与另一款浏览器工具在真实网站上对比后做的两处改动，数字是同一模型、同一批题的实测。

**核心用法随 `call_tool` 的说明给出**（`browser/server.ts` 的 `D_CALL_TOOL`）。以前模型要先调一次
`list_tools` 读完整规则：每个任务多一轮，而且约一万 token 的规则作为工具结果排在用户消息之后，别的
任务无法复用它的缓存。把读页面、操作页面、等待、底层出口和交给用户这几条写进工具说明后，34 次评测
没有一次再去读完整规则。

- 这段说明每个带浏览器工具的会话都要付，所以只放**三种后端都成立、多数任务用得上**的用法，保持在
  一千字符上下；登录墙交接、配方、读接口请求、读图、代理、切换浏览器、上传等仍在 `browser-workflow.md`，
  说明最后一段写明何时去读。新增规则时先判断属于哪一边，不要两边各写一份。
- 措辞会直接改变模型的做法，改动后必须重跑评测。实测过的两个例子：写「需要看结果时接一步 extract」，
  模型就用猜的选择器去核对状态，交互题多出两三轮；多地址参数只写 `pages:[…]`，模型会传对象数组。

**`read` 动作**（`tools.ts`）：给地址就打开、等内容出现、返回可见文字并关闭标签页；`pages` 一次给多个
地址；`targetId` 读已打开的页面，也可以作为 batch 的一步。

- 文字来自运行时的固定读取 `domRead: {kind:"text"}`（`browser-control-runtime/src/dom-read.ts`）：
  `innerText`，即人看到的内容，不含脚本、样式和隐藏部分，空行合并。`extract` 取的 `textContent` 在
  npm 的包页面上有 11.4 万字符，可见文字只有 1865。
- 多个地址先全部打开再各自等待、读取，总耗时约等于最慢的一页（四个 GitHub 发布页 1.3–1.7 秒，逐页
  打开要 5–7 秒）。自己打开的标签页无论成败都关闭，除非带 `keep:true`。
- 一页失败不影响其它页：顶层 `ok` 表示至少读到一页，失败的页带 `message`。
- `selector` 没匹配到时返回整页文字并在 `hint` 里说明，不让一次猜错多花一轮。
- 不支持页面脚本的后端（旧版扩展的「我的浏览器」）退回声明式 `extract` 取 `body` 文本。
- `read` 没有 ref，不能代替快照去点击；说明里写明「要点击或输入时不要先 read」。

**参数错误只返回出错字段的说明**（`tool-registry.ts`）。以前每次都附整份参数 schema，约 1.1 万字符；
现在只描述出错的字段，未知字段给出合法字段名，`args` 传 `{}` 仍返回完整 schema。

实测（Opus 5.5 medium，命令行打印模式只给浏览器工具；真实网站 8 题各 3 次、本机夹具 5 题各 2 次，
改动前后都全部通过；每次运行的平均值）：

| | 用时 | 模型轮数 | 费用 |
| --- | --- | --- | --- |
| 真实网站 | 13.4 → 6.3 秒 | 4.3 → 2.3 | $0.151 → $0.044 |
| 本机夹具 | 16.3 → 11.8 秒 | 6.0 → 4.2 | $0.165 → $0.050 |

费用是连续运行、提示缓存命中时的数字；样本少，没有做显著性检验。这组数字来自对比用的脚本
（`scripts/benchmarks/browser-task-bro-compare.mjs`，同时跑了开源项目 bro）。公开的方法、逐次数据、
复现步骤，以及和 bro、Claude App、Codex App 放在一起的结果见
[docs/benchmarks/browser-read-2026-11-11](../benchmarks/browser-read-2026-11-11/README.md)。
同一批真实网站题和四道读取题也在评测脚本里，可以复现主干与当前工作区的对比（`--effort` 指定推理强度）：

```sh
node --import tsx scripts/eval-browser-tasks.mjs --live --baseline-ref origin/main --model claude-opus-5-5 \
  --repeats 2 --real-sites --only late,spinner,manual,status,gh-releases,gh-pr,crates,pypi,hn,tailscale,apple,wiki
```

2026-11-12 的结果（基线 `e571c28e44`，12 题各 2 次，两组 48 次全部通过；基线用的是当前工作区的运行时，
所以不会在 Tailscale 上卡死）：模型轮数 4.3 → 2.5，费用 $0.139 → $0.038，用时 10.8 → 7.3 秒。当时
`spinner` 一题当前工作区反而更慢（7.8 → 18.3 秒），随后加了上一节的「Loading…」规则，复测为 5.1 秒。

**等待条件配了 `timeMs`**：模型写 `{kind:"wait", textGone:"Loading", timeMs:20000}` 时本意是「最多等
20 秒」，运行时却先原地停 20 秒再看条件（实测一次白等 20 秒）。工具层把「有条件、有 `timeMs`、没有
`timeoutMs`」的等待改写成以它为上限；只有 `timeMs` 的仍是固定停顿。

### 工具说明变长的代价

新说明比原来多 935 个 token（同一提示词前后两组首个请求实测 1745 → 2680）。

- **谁要付**：工具说明进入上下文的会话。Claude Code 走 Anthropic／XD 线路或本机订阅时开启了按需加载
  工具（`claude-behavior-flags.ts` 的 `ENABLE_TOOL_SEARCH`），浏览器工具只列名字，用到时才取说明；Pi
  经自己的 `cindy_mcp_list_tools` 按需查看。走其它第三方线路的 Claude Code 开场就加载全部工具说明。
  Codex 是否延迟加载没有核实。
- **付多少**：按这批评测反推的单价（写缓存 $8／百万 token，读缓存 $0.2／百万 token），开场加载时每个
  会话首个请求多 $0.0075（缓存已热则 $0.0002），之后每个请求多 $0.0002；一个 50 次请求的会话约
  $0.017，200 次请求的约 $0.047。对耗时的影响没有测。
- **换来什么**：每个用到浏览器的任务少两轮、少约 7 秒、少约 $0.10（上表）。
- **怎么判断值不值**：只算钱，开场加载的会话里每 6–13 个会话（按每个会话 5–50 次请求算）有一个用到
  浏览器就持平，会话越长需要的比例越高；按需加载的会话不付这笔。实际比例看每周的 Browser Use 复盘里「用到浏览器的会话占比」。说明再变长时按同样的办法
  重算，超过两千 token 就该把内容挪回完整规则。

### 三种后端实测（2026-11-12）

改动合入前，在运行中的个人版上切换后端，用新代码实际下发的页面函数验证它依赖的前提（不是新代码的
端到端测试，后者要等包含本改动的构建）：

- **侧边栏**：`open` 自己等到页面加载完才返回，没有专用浏览器的占位页；读文字的函数返回正确；
  crates.io 在返回时文字为 0，约 1.5 秒后出现，落在空白页 2 秒的等待之内。
- **「我的浏览器」**（扩展 0.4.69）：`open` 同样等到加载完。**github.com 的内容安全策略拦截页面脚本**
  （`EVAL_BLOCKED_BY_PAGE`），按最初的实现 `read` 在这类页面上会失败。现在后端在脚本被拦、或扩展
  版本不支持页面脚本时改用扩展自己的声明式读取，实测它返回的同样是渲染后的文字；不报告加载状态。
  **但桥接对单个字段最多只交出 4000 字符**（`bridge.ts` 的 `FIELD_VALUE_MAX`，不理会请求里的 `maxChars`），
  所以这条退回路径只读得到页面开头约 4000 字符：结果带 `truncated`、不给 `nextOffset`（后面没有可续读的），
  `hint` 提示改用 `selector` 读具体区域；结果里的 `chars` 在这时是已读到的长度，不是整页长度。
  后端的文字读取遵守调用方给的 `timeoutMs`（两条路径共用剩余时间）：桥接对一个作业的默认期限是 45 秒，
  页面无响应时不能把打开后 5 秒的等待拖长。crates.io 允许页面脚本，表现与侧边栏相同。
- 专用浏览器即上面全部评测所用的后端。

包含本改动的构建装上后，要在侧边栏和「我的浏览器」里各跑一遍 `read`（单页、多页、github.com）。

导航卡死是同一批真实网站实测发现的另一个问题，原因在 Playwright，处置见
[运行时维护指南](../../packages/browser-control-runtime/upstream/MAINTAINING.md)踩坑清单第 15 条。

## 能力不设限，风险交给审批（2026-10-30）

三端能力对齐，默认不加站点名单、读取边界或字段类限制；安全依靠任务权限档位（询问／自动审核／
完全访问）与自动审核。保留的底线只有：任务文件夹边界（也是共享／远程任务的边界）、不打扰
用户、防冒充，以及[代输入规则](../product-rules/input-handoff.md)（主人
填写的密码、验证码等值只交给宿主，不进模型；权限档位与自动审核不能代替它）。
Agent 自行把后端切到「我的浏览器」的调用
走任务的权限审批（询问档确认、自动审核档复审、完全访问档放行，见
`maker-host/mcp-tool-approval-policy.ts`）；用户在设置里选了「我的浏览器」不经过工具调用，也就
不需要审批。Cindy 打开的标签页不设固定数量上限，闲置 10 分钟自动关闭。

## 「我的浏览器」不占用用户的页签（2026-11-06）

用户自己的页签可能正在用。Agent 默认用 `open` 在 Cindy 窗口里开自己的页面：同一个浏览器
profile，登录态与用户共用，不需要借用户的页签。`tabs` 用 `owner:"user"` / `owner:"cindy"` 标出
归属（由扩展的 `cindyWindow` 得出；旧版扩展不标就不猜），同网站提醒遇到用户页签时只让 Agent
沿用它的地址（多账号网站的 `/u/<n>/` 等），不在上面点击、输入或跳转；用户明确让看「这一页」时
才读取，改动先问。专用浏览器与侧边栏的页面都是 Cindy 自己的，照旧复用。这推翻了 2026-10-29
「先复用已打开的页面（用户开的也算）」中针对用户页签的部分：当时为了避免 Play Console 进错
Google 账号，但结果是 Agent 在用户自己的 ChatGPT 页签上点击并跳转。

## 专用浏览器不吞外部链接（2026-10-30）

专用浏览器复用系统默认的 Chromium 浏览器 App、只换 user-data-dir；macOS LaunchServices 按
bundle id 投递打开链接事件，外部链接会落到 Cindy 的实例。采用的方案：在 Agent 浏览器里识别由
外部链接打开的标签，在请求发出前拦下并转回用户自己的浏览器（默认 profile；仅 macOS，
`ExternalLinkHandoff`）。没有选改用 Cindy 自带的 Chrome for Testing（要多下载约 150 MB，且
影响「使用我的浏览器登录态」）或避开默认浏览器；后续讨论不要再默认推这两条。

## 配方目录（2026-10-23）

默认内置清单与可追溯的上游全量来源分开维护：默认清单按实际用途筛选——移除不合适或过期的

## 「我的浏览器」连接诊断

设置页的未连接不等于扩展未安装：显示连接状态、启用检查说明，并将扩展商店保留为可选入口；
状态查询失败单独报告，不归为扩展缺失。桥接保留本运行期成功连接的布尔历史，供上层在活跃
客户端列表已清空时继续执行有界重连等待；历史不代表当前在线、不授予页面访问权限，未配对
客户端不等待。扩展本身负责重连，宿主不重放页面动作。

`browser extension connection changed` 在请求或状态读取时记录首次观察到的连接变化，包含
短客户端标识、扩展版本、前后状态、最后请求时间与距今毫秒数；`heartbeat-expired` 表示超过
35 秒没有请求，不证明 Chrome 崩溃或网络中断。没有读取时不会额外启动定时器，因此日志时间
是观察时间而非精确断线时刻。`browser extension bridge closing` 区分宿主主动关闭，
`user browser settings health changed` 记录设置页判据变化。日志不含网页地址、内容或认证材料。

回归位于 `browser-extension/__tests__/bridge.test.ts`、浏览器后端的 `user-browser-backend.test.ts` /
`health-service.test.ts` 与设置页的 `ComputerUseSection.browserHealth.test.tsx`，覆盖过期空列表、
首次读取前已过期、恢复、等待到期、未配对及探测失败。

## 插件更新时的浏览器连接（2026-11-07）

市场与本地插件更新在替换包之前暂停接收新的浏览器作业，等待已接受作业按原有结果或超时结束，
再关闭旧桥接。更新中的清单广播不创建新桥接；安装来源账本提交结束后重新发布完整清单。
来源变化属于桥接签名的一部分；来源信息补齐也必须触发刷新，不依赖重启应用。
不得把更新中间态写成新的配对来源，或自动重放点击、发送、提交等结果可能未知的操作。
真正换源仍按原来源隔离配对，不能自动改写用户选择的控制端。

设置页和 Browser Use 状态区分 `plugin-updating`、`plugin-selection-required` 与 `plugin-missing`。
前两者分别显示更新等待和插件选择入口；只有已安装插件未声明页面控制能力时才提示更新版本。
这些状态仅影响「我的浏览器」的宿主连接，不关闭用户浏览器、不修改用户页签或登录态；
侧边栏和专用浏览器不经过插件桥接，因此不适用这一更新流程。

回归位于 `browserExtensionSlot.test.ts`、`bridge.test.ts`、`user-browser-backend.test.ts`、
`health-service.test.ts` 和 `BrowserBackendSubsection.test.tsx`；界面场景为
`automation-settings/browser-updating` 与 `automation-settings/browser-selection`。


## 用户浏览器自动启动与扩展保活（2026-11-10）

「我的浏览器」的实际任务调用（含 start、tabs）在连接缺失时按需启动系统选择的 Chromium，
等待扩展上线后才投递作业；并发调用共用一次准备。status / doctor / profiles / stop 保持只读，
设置页不唤起浏览器。启动不传 URL、user-data-dir 或调试端口，不抢焦点、不关闭用户浏览器。
指定 profile 的调用不猜测对应浏览器；未配对、插件缺失／更新中也不另起浏览器规避。

扩展保活独立于页面作业，用现有 /health 验证同一会话，保持旧宿主兼容。长页面等待或闲置页清理
不能阻塞保活和轮询；HTTP 的截止时间覆盖启动标识读取、响应头和正文。丢失结果保持 unknown，
不重放页面操作。Chrome 的 service worker 允许休眠，定时器不能作为唯一的恢复来源，保留 alarms
与启动事件兜底。测试用虚拟时钟验证长操作、清理悬挂、并发启动和启动后扩展仍不可用。

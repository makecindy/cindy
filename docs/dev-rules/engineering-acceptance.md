# Cindy 工程修复的分阶段验收

> 适用场景：已有修复需补验收、原现场暂不可用，或需要把工程复盘转成可执行步骤。
> 本文组织证据与交接，不新增所有小改动的现场门禁，也不自动授权发消息、发布或合并。

本流程补充[开发工作流](development-workflow.md)的三个需求核对点；产品取舍仍以对应的
`docs/product-rules/`、`docs/design-rules/` 为准。新增测试遵守
[工程约定 §3.2](engineering-conventions.md#32-新增测试的价值门槛)，不为填矩阵重复造用例。

## 1. 开始前固定范围

从原始消息或 Issue 还原用户操作、受阻现象、期望结果与必须保留的能力，分清目标和建议实现。
先追查已有及后续 PR：已有修复覆盖的接续审查、部署核验或验收，不另写一套；缺证据不等于缺代码。

每次分阶段任务保留一张当前状态卡：

| 项目 | 记录内容 |
| --- | --- |
| 目标与保留项 | 原始入口、失败现象、可观察结果、原交互及跨端能力 |
| 版本与来源 | 待验 SHA／构建、旧基线、平台、模型与配置差异；部署未知明确标记 |
| 范围与授权 | 本轮做实现、受控实验或真实环境验证；产品取舍是否已有决定 |
| 输入与预算 | 最小失败输入、重复次数、环境准备时间／尝试上限及替代交付 |
| 证据与结论 | 本轮实测、作者记录、独立审查和 CI 回执分列；未验项不算通过 |

验收项分为“核心验收”“原现场补证”“补充风险”，逐项说明分类依据。后两类不自动成为
合并前置条件；是否阻塞按原需求、改动影响面及已有门禁判断，不因未知而不断扩大范围。

## 2. 列矩阵时先决定取证方式

按真实生产入口核对已有代码与测试，检查输入、模型／工具执行、结果提交、回执／读回和界面状态。
不凭 mock 证明未覆盖的真实服务端行为。

| 要判断的现象 | 所需证据与边界 |
| --- | --- |
| 瞬时闪现或转场错误 | 受控延迟与连续录屏；真实发送前准备录制，记录帧率与局限。离散截图不能排除所有瞬时异常 |
| 结果送达与正确结束 | 持久结果、读回、终态分别核对；正文可见不等于过程入口和完整体验恢复 |
| 重复执行或副作用 | 消息／操作／执行关联标识与次数；可见回复数量不能直接推断后台执行次数 |
| 暂时失败后恢复 | 旧内容是否保留、恢复后是否正确、后续重试是否收敛；同时检查持续失败与离开／撤权的取消边界 |
| 原能力保留 | 沿真实入口核对正文、附件、过程、原交互和跨端能力，受限兜底明确写出损失 |

每行写清场景、预期、已有覆盖、执行方式、证据位置和当前结果。新测试必须能说明真实行为差异，
优先补已有文件的最小缺失输入，不复制 JSX、源码字面量或常量来制造通过。

## 3. 在授权范围内连续执行

- 常规步骤不反复等用户说“继续”；阶段更新只说明发现、剩余不确定性及下一步。
- 环境失败先按日志分类，保留首次结果，不重复同一失败路径。达到准备预算后交付已有证据和精确缺口；
  其余独立且获准的工作继续，不跳过构建身份、安全或权限检查。
- 故障注入只在受控夹具或获准隔离环境进行；不向生产服务人为制造断网或重复写入。
- 每次真实发送前确认上一轮结果；回执未知先核实、不重发，达到预定样本数后停止重复正常路径。
- 产品行为、提醒强度、降级或新增交互发生变化时，回看原始需求与既定裁决。未决定的取舍单独列出，
  不因评审建议而默认实施；这不意味着常规执行也需逐步请示。

## 4. 比较时保持证据来源清楚

固定提交、案例和输入。未独立运行旧版时明确标记，不能把作者的前后对照算成本轮实测。
合入主干、平台、模型或配置变化单列，不能把所有差异归因于修复；PR head 变化后先核对新差异，
再决定旧证据仍能支持哪些结论。不填未经预设和实测的性能收益。

失败恢复也要检查用户能否感知尚未交付：没有错误提示不等于体验完整。新发现先登记为
待核实风险或体验缺口，不直接认定新缺陷，也不自动夹带进原修复。

## 5. 阶段交付与移交

文首、矩阵和结论统一呈现最新状态；历史轨迹标为历史，不让接手人翻完追加章节才能知道进度。
结论区分完整通过、受限降级和证据不足，不以绿 CI、Approved、合并或发布代替原场景验收。

| 交付项 | 必须能回答的问题 |
| --- | --- |
| 已完成 | 哪个版本、哪个场景、什么结果、证据来自哪里？ |
| 未完成 | 下一动作、所需证据、承接角色、是否已接手、是否影响当前结论及依据？ |
| 本机阶段 | 哪些已结束，哪些仍可在本机完成，哪些确实依赖别的平台？ |
| 外部交付 | 评论／PR／版本的链接与真实回执是什么？只推 fork 不等于已同步原 Issue |

移交包包含构建核验、隔离前置条件、固定输入、预期、录制与记录方式、停止条件和回填格式。
准备草稿不等于已经分享、有人接手或已经完成；发送、邀请、发布按实际授权执行。
原 Issue 回贴阶段结果，产品修复沿用已有 PR；可复用工作流如需进入主仓，另作聚焦的文档 PR，
不从含其他功能提交的任务分支直接扩大 PR 范围，也不使用关闭 Issue 的措辞冒充修复交付。

项目知识归属遵守[开发工作流 §4、§5](development-workflow.md#4-项目知识放在哪里)：
复现条件、版本、边界和脱敏结果进仓库；个人路径、设备标识、账号偏好、凭据和私聊原文留在本地。
记忆可以指向文档，不应成为唯一正本；入口存在不证明跨任务主动召回已经验证。

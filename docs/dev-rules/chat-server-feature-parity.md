## 本次服务端配套

1. **等待时换人**：允许 waiting 时更换 pending/failed 步骤；删除步骤仍仅限开始前。
2. **轮流上下文**：顺序执行在 claim 时推进 context_seq，后继伙伴可读本圈前面的回复；自动首圈保持共同快照。
3. **顺序与继续**：新群按输入成员顺序入群，第二/三圈轮换起点；手动继续始终轮流。旧群相同 joined_at 无法恢复丢失的选择顺序，保留稳定 ID 兜底。
4. **@所有人**：可选 mentionsAll 与命名列表并存，保留 mentioned 回复方式与自动首圈并行。
5. **额度与失败**：10 条按实际发布回复计数，领取时计入在途预约；NO_REPLY 不占回复额度。失败或租约过期不阻塞其它伙伴，不自动重跑失败者，并给出轻提示。
6. **停止辅助判断**：取消接口清除延迟调度、撤回尚未执行的安排并栅栏化迟到结果，保留用户原消息。
7. **附件增量**：领取回传成功投递水位，按伙伴、授权版本和分工步骤隔离；客户端倒序翻页，不局限最近 100 条。仅成功执行推进水位。
8. **明确分工失败**：planningMode 保留手动/修改意图；辅助判断失败或超时提示重试，不静默降为普通讨论。

新增字段与取消接口由 `/me.capabilities.groupDiscussionParity=1` 协商；旧服务器仍用旧请求形状。
先完成整个 Chat Server 集群升级，再发布使用能力位的新客户端，避免滚动期间请求落到旧副本。
迁移 008/009 均为带默认值的增量列，不改写原消息；避开并行 #836 的 007 迁移。

## 验证与避让

- 客户端接手后 Desktop 107 项定向回归、Mobile 60 项通过；手机发现等待中结束分工误用 dismiss 后，补回归并通过 parity 23/23 与 focused TypeScript。服务端 group-parity 11/11 沿用相同服务端提交，覆盖旧版非空 schema 升级、再次启动及旧写入形状。
- Review 实测：原安排判断进行时，下一条消息因无效附件返回 INVALID_ATTACHMENT，原判断继续并生成带开始/不用了入口的两步安排。标注图片重试改变文件名，仍返回同一消息回执，实际只持久化一条消息和一个媒体对象。单成员场景通过真实决策解析器回归，恢复普通讨论而不创建分工。
- 隔离 Desktop + 持久 Chat Server DEV：两位真实伙伴回复；安排开始、逐步结果回流；等待时换人后继续；不用了后直接恢复讨论；修改提议生成更新后的安排；图片与文本文件上传后两位伙伴均正确读取。
- 已重启隔离 Desktop 和服务端并读回原消息/安排；服务中断超过租约后显示没做完，用户明确重试后完成，没有静默重复执行。另用旧本地 schema 的非空夹具通过正式迁移入口保留两条历史、成员顺序、负责人、回复方式；迁移后两位真实伙伴读出旧历史识别码，双端服务重启后不重复导入。数据库旧版非空夹具经实际 migrate-cli 升级 008/009，读写、重跑及持久 PostgreSQL 重启后核对通过。
- Baguette Duo iOS 27.1 正常登录后完成手机到隔离 Desktop 的实测：群发现、旧消息/安排展示、两位伙伴文字回复、安排开始/等待/换人/继续完成、修改提议/取消、等待中结束后恢复普通讨论、含真人的伙伴移出再加入。手机相册选取真实 JPEG，经手机上传/主机取件/群媒体存储后两位伙伴识别瀑布与青苔岩石；手机取回并全屏预览成功。Desktop `85fa05255`，Metro 来源为当前 worktree 的 `567ec9a22`（后续变更仅 Desktop 和测试，Mobile 源码相同）。浅色已目检，深色未目检；证据保留在本机 `/tmp/cindy-parity-acceptance/runtime.md`。

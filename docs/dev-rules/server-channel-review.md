# 服务器通道调用审查

> 权威审查规则。新增或修改任何直接、间接的服务器请求、订阅、推送、同步、轮询或重试时适用，
> 包括 Desktop Renderer／Main、Mobile、共享 package 和插件宿主调用方，不只检查网络实现目录。

重点判断**现有通道是否被安全、可靠、合理地使用**。接口用途正确、单次请求合法，
不代表调用方式正确；一次小改动也可能通过重复触发、扇出或重试挤占共享连接。
这是开发自审与 AI review 的检查重点，不新增 CI、统一频率配额或每个 PR 的压测义务。

客户端组件怎么读、怎么共用、收到变化通知后怎么刷新、离开后何时停止（含读取远程电脑数据的
查看端），以及本地安装扫描、同步 IPC、缓存键和读写分离，见 `engineering-conventions.md` §8；
本文检查这些做法放到真实共用通道上是否够用，仍沿调用链从发送端看到每个消费者。插件市场、
实例核对、使用统计与远程插件状态读取见 `plugin-security-and-authoring.md` §5.3–5.4。

## 先理解通道，再判断调用

从改动处沿调用链读到真实网络出口与相关消费者，确认：通道服务什么、哪些业务／设备／账号
共用连接、队列、限流桶或服务端资源；并发、条数、字节、速率与超时分别限制哪一层。
还要看已有调用与本次新增调用的累计压力，不能把单组件、单设备的次数当成整体负载。

下面是本仓的定位入口，不是全部通道清单；其它服务器或第三方 API 同样适用。
数值以当前源码、有效协议与服务端配置为准，本地默认值不等于生产配置。

| 通道／用途 | 共享压力与约束从哪里查 |
| --- | --- |
| Device Link：远程任务、伙伴、插件、模型、自动化等业务 | [调用优先级](../../packages/device-link/src/invokePolicy.ts)、[逐目标调度](../../packages/device-link/src/invokeScheduler.ts)、[传输条数／字节／窗口上限](../../packages/device-link/src/transport.ts)、[共享 socket 与发送行为](../../packages/device-link/src/client.ts)、[被控端准入及回包](../../apps/desktop/src/main/device-link/dispatch.ts)。不同业务 channel 不等于独立物理连接；[积压诊断](../../packages/device-link/src/transportBacklog.ts)按通道及共享连接上的其它 peer 汇总。恢复边界见[远程与手机适配](remote-and-mobile-adaptation.md)。 |
| Chat Server：聊天 HTTP、实时事件、伙伴资料同步 | [Desktop 请求与 WebSocket](../../apps/desktop/src/main/maker-ipc/chatServer.ts)、[工作轮询与退避](../../apps/desktop/src/main/maker-ipc/chatWorkPolling.ts)、[伙伴同步](../../apps/desktop/src/main/companion-cloud/runtime.ts)。HTTP 与 WebSocket 不是同一队列，但通知可触发 HTTP 重读并竞争同一服务；不能假定工作轮询的退避自动覆盖全部调用。 |
| 文件与媒体：直连、远程取图、OSS 上传下载 | [文件传输策略](../../packages/device-link/src/fileTransferPolicy.ts)、[远程媒体](../../apps/desktop/src/main/device-link/remoteMediaProtocol.ts)、[聊天媒体](../../apps/desktop/src/main/maker-ipc/chatServerMedia.ts)。区分控制请求与文件字节实际走的路径，再核对并发、带宽与回退压力。 |
| 其它云服务与外部 API：认证、心跳、目录、IM、模型等 | 从[端点清单](../../config/endpoint.global.json)和实际调用方定位客户端、SDK 与服务端契约；[心跳入口](../../apps/desktop/src/main/heartbeatService.ts)是必要周期请求的例子。不能把不同服务视为一个限流桶，也不能把相同服务的不同接口视为互不影响。 |
| 自建中转 | [Relay Hub](../../packages/device-link-relay/src/hub.ts)的连接／发送缓冲限制；区分代码默认值、可覆盖配置与官方服务的实际限制，参见[协议兼容](protocol-compatibility.md)。 |

查不到生产上限或实时负载时明确证据边界，不编造容量或“已经过载”的结论。
确定的重复调用、无界增长或副作用链路可独立证明缺陷，不必等线上再发生事故。

## 检查调用方式与累计压力

结合业务需要、已有保护与可达使用规模判断，不逐项机械要求新机制：

- **调用必要性与范围**：触发条件、订阅过滤和读取／写入范围是否对应；是否用大快照回答小问题，
  或无关变化反复触发请求。检查实际序列化体积，包含图标、附件、编码和分页，不只看返回条数。
- **次数、频率与并发**：启动、挂载、切换、定时器、事件和重连是否叠加；多个组件、任务、伙伴、
  设备及订阅者是否放大请求。已有合并、缓存、增量或变更判定是否真的覆盖这些入口。
  持续事件和慢响应下，前一次未完成是否继续堆积；离开页面或取消后是否还做无用同步。
- **推送源头**：高频的状态变化通知要从发送端核对发送频率、发给多少接收方、每个接收方各自
  重读多少。能合并的状态变化避免重复发送，并保证最后一次变化能送到；需要逐条处理的消息、
  操作回执和权限决定不按可丢弃的状态合并。订阅能按什么维度过滤以现有契约为准，细分订阅属于
  协议改动，另行评估。
- **共享容量与其他业务**：把新增负载与既有负载放到实际共享范围内判断，既看峰值也看持续占用。
  即使没有超过单次／并发硬上限，后台同步仍可能持续挤占发消息、停止、确认、心跳或租约维护。
  调用层的预留名额不等于后续传输与服务端已隔离；不能靠提高上限或延长超时掩盖放大源头。
- **失败、重试与恢复**：核对 429／Retry-After、繁忙、超时、断连、休眠恢复时的实际行为；
  调用方、SDK 与传输层的重试会不会相乘、绕过退避或集中补发失效请求。对写操作核对幂等与
  已执行状态，不能把超时当成未执行；恢复动作不得无依据波及共用通道的其它业务。界面频繁
  触发的持久化写入怎么合并、何时确认，见 `engineering-conventions.md` §8.2。
- **安全与生命周期**：合并读取、缓存、推送和迟到结果是否保留账号、权限、设备与对象边界；
  减少调用不能漏真实变化、丢消息、重复写入或破坏必要的心跳／租约。高频、轮询、全量读取本身
  都不是错误，须结合用途、数据量、共享压力和已有保护判断。

## 按实际严重程度报告问题

P0、P1、P2 都应覆盖，不设置“只报 P0／P1”的筛选条件。以实际影响判断 reviewer
优先级，不为凑等级升级问题：

- **P0**：需要立即处理的严重故障，例如请求放大导致大范围服务不可用、严重数据丢失或安全问题。
- **P1**：高优先级缺陷，例如正常使用下重复全量同步持续挤占共享通道、造成核心交互阻塞，
  或重试放大导致持续不可用。单次未超上限不构成免责。
- **P2**：影响较小但明确存在的问题，例如特定操作下产生不必要的重复请求、额外流量或局部延迟；
  即使尚未造成整体过载，也应指出触发条件、确定的额外开销和修正方向。

上述是缺陷的优先级，不把 P2 等同于可选优化／风格偏好。只有“最好缓存／降频／加限流”
而不能证明错误调用或实际额外开销的建议，不作为缺陷上报。

每条问题写清**代码位置、触发条件、调用如何放大或失当、共享约束／证据、用户影响和修正方向**。
不要求固定篇幅或另填报告。计数、体积与频率能从代码推导时说明依据，估算不能写成实测。
例如“资源变化通知包含多类资源，监听仅过滤设备却每次下载插件整份快照”是一条证据链，
不是只对插件生效的特殊规则；同样审查其它服务的通知、轮询、批量和重试调用。

Greptile 按实际影响使用 P0／P1／P2。仓库工作流对严重度采用另一套命名，固定输出标签
不同的自动 reviewer 按[REVIEW.md §2](../../REVIEW.md#2-严重度映射)表达：真实缺陷属于
应报告的问题，不要将 reviewer 的 P2 与仓库“不报可选优化”的 P2 混为一谈。
修正建议优先指出不合理的调用方式，不自动扩成传输重构、监控、CI 或新的产品限制。

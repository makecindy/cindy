# 手机通知的跨设备清理（未发布）

普通任务回复在执行端确认已读后清理；问题通知只在其请求已回答、拒绝或实际取消后清理。停止轮次可能保留异步问题，不是整任务清题证据。
打开任务、列表中不存在、离线或分页遗漏都不是问题已处理的证据。消息记录与通知分离，清理通知
不会删除聊天内容，也不会主动推进已读或批准问题。

## 身份与传输

`NotifyPayload.notificationId` 为可选 UUID，执行端按归属设备、任务、事件类别和稳定事件 ID 生成；没有事件 ID 才使用随机身份，服务端校验后保留；旧端无此
字段时服务端仍生成 UUID。APNs 与 FCM 都保留 `notificationId` 和认证所得的 `recipientId`。
Agent-Net 加密内容另带 `recipientId`；官方 relay 不信任发送者提供的账号，始终从认证重新绑定。
系统请求标识中 APNs collapse-id 按账号与通知 ID 生成；FCM／Android 直连 tag 使用通知 UUID，兼容既有消息去重校验。任务键仅用于 thread-id 分组。
同事件重试仍合并，不同事件在任务分组内独立保留，避免枚举旧通知之后新通知替换同一系统标识而被误删。
加密 Agent-Net 外层按 envelope 摘要生成系统标识，不暴露加密内容。
旧服务端忽略新增字段，旧手机忽略额外元数据；缺少身份的存量通知保守保留，不按任务清空。

执行端使用现有 owner-scoped 文件存储保存通知 ID、任务 ID、待回答请求 ID 与清理 outbox，
不保存正文或凭证。已读只退休普通回复；多个问题分配到各自新增的请求集合，逐个处理。
仅明确的处理回执退休问题；恢复中的空状态、终态展示与未知会话状态都不作为已回答证据。outbox 重试只确认已提交的 ID，不能确认重试期间
新增的清理记录。待处理记录保留最多 30 天／2000 条，离线 outbox 最多 2000 条；超出边界保留
手机旧通知，不扩大为整任务删除。远端镜像代发复用相同稳定事件身份，由执行端清理；缺少稳定事件 ID 的旧式镜像提醒不推断对应关系，不能用本机同名任务的已读清除。

官方 Device Link 增加两个设备绑定、同账号路由：

- `POST /api/device-link/notification-dismissals {ids}`：持久接受最多 50 个 UUID 到账号隔离的 Redis
  tombstone（30 天 TTL），然后尽力给 iOS 发送 silent APNs。
- `POST /api/device-link/notification-dismissals/query {ids}`：只返回请求集合中已退休的 ID。

旧服务端 404/405 时执行端保留 outbox，本进程同一账号／端点不持续探测。更换账号／端点或
重启后重试。没有新 WS kind、allowlist 或自建 relay 要求；自建中转不调用官方清理接口。

Chat Server 的 `notificationId` 使用消息 UUID。已提交的个人已读推进触发合并后的后台退休提示，
直接收集本次已读事务返回的最多 50 个消息 ID，由独立有界 worker 发送 silent APNs；`POST /v1/push/retired {ids}` 根据当前认证 actor 的
`chat_notice.read_at` 查询准确结果，批量上限 50。没有跨服务 SQL 或共享账号凭证。

## iPhone 与恢复

iOS 原生 subscriber 接受 `recipientId + dismissIds`，保存每个身份的 Keychain tombstone，再
只移除相同账号和 ID 的已展示通知。使用现有通知扩展 Keychain group，独立 service，不读授权
凭证；过期记录在后续清理中回收。扩展交付通知前检查 tombstone，尝试抑制已处理的迟到提醒；
空内容回执的系统展示行为仍须真机验收，已展示的迟到通知也会被前台补偿再次清理。

静默 APNs 没有 alert、sound 或 badge，优先级 5，类型 background；不发送一个新的“已处理”提醒。
系统可能合并、延迟或不唤醒后台，不能承诺强杀后立即清除。手机启动／回前台与有通知时的低频
补偿枚举系统当前通知，只请求这些 ID；普通前台补偿最多每分钟一轮，账号切换使旧响应失效。
新消息不在旧请求集合里，不能被旧清理结果删除。

Android 与旧 iOS 包通过 Expo 逐 ID 做前台补偿；本次后台原生清理只覆盖 iOS，不向旧 Android
发送无法识别的静默数据消息。全新原生模块、后台 remote-notification 模式与扩展检查改变 runtime
fingerprint，不能只用 OTA 交付 iPhone 后台能力。先部署兼容服务端，再发新的 iOS 原生包和执行端；
本地单测与 Swift typecheck 不代表 APNs 真机送达或发布完成。

## 问题通知的结算边界

问题通知只能由本账号执行端账本的 `resolve(sessionId, requestId)` 根据实际结算退休。
Stop 只管理执行轮次和展示状态，不能另立一个按任务清题的入口。请求管理器在停止时取消同步请求、
保留异步问题；关闭会话时才结算剩余请求。这些路径均通过实际的 interaction-dismissed 回执落到同一个入口。
权限执行事件只确认其携带的具体权限请求，不能影响同任务异步问题。

| 事件 | 尚未结算的问题通知 | 已结算的问题通知 |
| --- | --- | --- |
| 查看／已读、恢复空状态 | 保留 | 不重复发送清理 |
| Stop／provider 取消当前轮次 | 保留，只有请求管理器实际取消的请求才逐 ID 清理 | 不变 |
| 回答／撤题／关闭会话的实际请求回执 | 只结算匹配 sessionId 与 requestId；同条通知的全部请求结算后才退休 | 重复回执无操作 |
| 另一请求或另一任务的回执 | 保留 | 不变 |
| Stop 后异步问题才回答 | 仍能按原请求 ID 清理，无需岛面会话还存在 | 重复回执无操作 |

回归使用真实账本接入服务回执：同任务同步请求取消、Stop、异步请求回答按顺序发生；
Stop 后只允许同步通知进入清理批次，异步通知必须等自身回执。这也覆盖 provider 取消共用的 Stop 入口。

## 执行端与镜像端的相同事件

共享 renderer alertEventId（包括 turn 与请求 key）是两端共同的手机事件身份；本机是否能提供
批准／回答按钮只影响 action 字段，不得改写事件身份。只有旧调用方没有共享 alertEventId 时才
使用本机请求 ID／回复 ID 回退；缺少共同身份的旧式代发仍保持保守处理。

| 输入 | 执行端 | 镜像端 |
| --- | --- | --- |
| 相同权限／提问 alertEventId | 同一 eventId，可带本机 action | 同一 eventId，不读取本机同名任务 action |
| 新请求产生新 alertEventId | 新事件身份 | 相同的新事件身份 |
| 完成回复 | 使用回复事件 ID | 使用执行端回复事件 ID |

回归通过真实通知 IPC 入口验证权限与提问的本机／镜像 eventId 一致，及镜像不附带本机按钮。
跨端协议输入变化后，须在干净检出运行 direct-link-runtime 生成脚本及来源校验；嵌套检出上层依赖
可能掩盖产物差异，不能据此把 CI 的生成文件校验判为主分支问题。

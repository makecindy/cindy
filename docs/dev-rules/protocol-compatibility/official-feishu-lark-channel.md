# 官方飞书 / Lark 渠道的协议增量（2026-11-04）

> 通用规则与 Review 清单见[跨端协议兼容](../protocol-compatibility.md)；本文件只记录这一项能力的协议约定。

两仓 `slack-hook-protocol` 同步追加，全部是可选新增：

- `FeishuBotAppInfo.tenantName` 可选追加飞书企业名称（非空字符串或 null），`organization` 保留历史 Cindy 组织标识语义。自建应用卡片显示应用所属企业；商店应用的每条绑定使用各自 `appInfo.tenantName`，不把某个企业名称放在商店应用级标题。旧服务省略字段时隐藏企业名称，旧端忽略新字段，不影响关联或消息派发；不增加客户端请求或轮询。

- `HOOK_PROVIDERS` 追加 `'feishu'`（飞书与 Lark 共用），能力位 `provider:feishu`。与 Telegram／X
  相同，由服务端 welcome 宣告、桌面 hello 声明，双方都有才启用。
- `provider.bind.update`／`state` 新增可选 `bindCode`：一次性短关联码（4–32 位大写字母或数字，
  可含中间连字符），只允许在 `pending` 时非空，缺省等同 `null`；新增 UI 动作提示 `copy_bind_code`。
  `pending` 仍要求 `connectUrl`（飞书为网页授权地址），关联码只是网页授权不可用时的兜底。
- `query.request` 新增可选 `recipient = { scopeId, principalId }`：多个组织共用的服务（官方飞书）发出的查询
  代表哪个应用的哪个账号；带上时两项都须是非空字符串。其它服务不发，旧桌面端忽略。
- 客户端端点清单新增 `feishuHookWsUrl`（`wss:`），登记为跨区域端点：服务只在海外部署一套，
  两份区域清单都指向 `cindy.app`。服务部署并核验后，在两份正式清单同时填写并发布该字段；
  缺省或清空后，重启读取新清单会停止连接；未开启的用户不显示入口，已开启的用户保留卡片并提示
  地址未配置，以便关闭，可用于回滚。dev 使用独立开发服务，配置与发布步骤见
  [端点清单说明](../../../config/README.md)。

飞书群上下文由服务端组装进 `task.dispatch.prompt`（含 `<thread_context>`、引用与当前发言人）；`source.threadContext` 同时供来源卡展示，客户端继续保留服务端完整 prompt，不再从展示元数据重复注入。X 的客户端 prompt 组装只作用于 X，不能据此推断其它渠道丢失上下文。

多设备（2026-11-07）：同一应用下，同一飞书账号可同时保留多个设备的 `confirmed` 绑定；新绑定默认成为工作电脑，重连不改变选择。工作电脑通过机器人菜单 `device` / `/device` 或已绑定电脑的「设为工作电脑」按钮选择，绑定成功后机器人私聊说明用法。服务端内部会话代次、工作目录与偏好按设备绑定隔离，外部 lane 格式仍相同（设备各自存本地任务）。选择仅影响后续消息，运行中任务沿原设备继续；离线 / 繁忙时拒绝，不改派、不补发。`superseded/rebound` 仅表示同一设备的旧账号绑定被替换；其它电脑的绑定不失效。桌面解绑只影响本机。

桌面选择是可选增量：本机 `confirmed` 快照的 `actions` 提供 `select_device` 时，客户端才显示按钮。客户端发 `provider.bind.select { requestId, provider, bindingId }`，服务端按已认证连接的设备核对本机绑定、应用和归属，回 `provider.bind.selection { requestId, provider, bindingId, ok }`；只有匹配的成功回执才能提示「已设为工作电脑」。请求不能创建绑定，不改变其它电脑的绑定状态；服务端从收到请求起限制处理时间，不依赖客户端时钟。断线、解绑、切账号及超时让在途请求失败，不补发。旧服务端不提供动作时隐藏按钮；客户端不持久缓存工作电脑标签；本轮可选的实时展示字段见本文工作电脑展示约定。

客户端接线：desktop 的飞书线 hello 的基础能力是 `provider-bind-v1`、`provider-prefs-v1` 与 `provider:feishu`
（不声明 `telegram-*`；电脑排版的可选能力见[「官方飞书 / Lark 由电脑排版」](official-feishu-lark-desktop-layout.md)），welcome 同样须含这三项才启用。不声明 `session-picker-v1`：飞书服务由多个组织
共用；会话列表查询要双方都声明才回答，服务端单方面宣告不算。飞书线的工作目录 / 模型查询必须带 `recipient`，且与
这条连接上服务端确认过的绑定（`scopeId` / `principalId`，等到绑定快照之后）一致才回答，否则回 `ok:false`。`pending` 的
`connectUrl` 与 `remediationUrl` 在进入设置页快照前按飞书 / Lark 精确主机白名单校验（`feishuDeepLink.ts`），且授权页 `client_id` 必须与当前宣告的 `scopeId` 一致；不一致时转为 `failed/invalid-connect-url`，清除链接与关联码，不向 Renderer 暴露或自动打开；
「打开机器人」的 AppLink 还须指向绑定的应用（`appId` 等于 `scopeId`），否则连同 `open_provider` 一起去掉。

兼容：旧校验器不读取 `bindCode`；不认识 `feishu` 的旧端按未知 provider 拒绝该帧但不断连，也不会
协商到 `provider:feishu`；新客户端连旧服务端收不到飞书帧，连不发 `recipient` 的旧飞书服务端时 `/project`、`/model`
查询失败（两端都未发布，飞书服务端须先于客户端上线）。客户端里协议渠道值进入本地类型的
回调（`onHookReadyForPrefsMirror`）按客户端支持集收窄。没有服务端部署、数据库、环境变量、
Device Link 或自建中转变化；协议包改动会触发服务端全部服务的 CI。

## 飞书组织应用与商店应用并存（2026-11-10，未发布）

两仓协议增加可选 `feishu-multi-app-v1`。新服务端按已验签 Cindy 身份下发允许应用集合；
新客户端只在双方协商后接受 `provider.bind.state.applications` 权威快照，元素为应用名称、品牌、类型、
组织与该应用 confirmed 绑定列表。存在绑定级 appInfo 时，App ID、品牌和应用类型必须与外层应用一致；
可空的名称/组织标签仅用于展示，不参与身份判定。顶层仍投影一个应用，旧端忽略新增字段且继续单应用行为。
新客户端与旧服务端不协商该位，继续原 UI。新 Console 以 `supportsCoexistence` 判定是否显示独立 checkbox。
未配置组织默认官方应用；现有组织选择不变。

关联、打开机器人带可选 scopeId，必须来自当前权威应用集合。自建应用每应用每设备仍只有一个飞书身份，
商店应用继续原关联入口授权后追加；两种 bot 可同时关联。目录和模型配置按同一 Cindy 身份与电脑共享，
设置页按 bot 名称/类型分卡，共用一份配置编辑区，不显示 App ID。任务、历史、授权、工作电脑选择与解绑按应用/身份独立。
同一次双 @ 不去重。无后台搬迁、补偿轮询或自动重放消息。

客户端只展示当前服务端允许集合，隐藏的商店应用不保留独立入口或审核中占位。服务端
`FEISHU_HOOK_STORE_APP_ENABLED` 默认 false；dev 显式开启，正式环境审核通过后再开启。
此开关与全副本升级后才能开启的并存门禁独立，不新增客户端请求或轮询。每个 bot 单独显示
未关联、关联中、失败或已关联账号数，首次关联与商店追加账号使用不同按钮；整体摘要统计
已关联 bot 和账号数。没有关联时先选择 bot，按已有 scopeId 发起关联；配置和已有任务继续共用原流程。

服务端先升级所有实例，再允许组织勾选并存；旧服务端的单应用清理逻辑会撤销另一应用，不能在配置并存后回滚旧版本。
回滚前恢复单应用选择；数据库新增表列保留。客户端可以独立回退为单应用投影。

### 工作电脑展示（2026-11-11，未发布）

Feishu confirmed 状态及 `provider.bind.selection` 成功帧可选追加 `workingDevice: {name: string|null, isCurrent: boolean}`。
这是展示信息，不是绑定、任务或偏好授权。连接快照一次批量读取当前工作电脑（显式选择优先，否则使用最新剩余绑定），
客户端不新增请求或轮询。切换、关联及解绑后沿既有 selection 帧向同一飞书应用/账号的绑定电脑尽力推送；
不补偿、不重放，重连以快照收敛。selection 的 requestId 仍只确认匹配请求；其它成功帧只更新已确认 bindingId 的显示，
不得新增身份、结束另一个授权、写入缓存或触发偏好同步。客户端按行显示名称，本机已选中时隐藏切换按钮；
旧服务端缺字段时显示尚未同步并保留原入口。旧客户端忽略可选字段和不属于其请求的 selection。
服务端先发布可获得完整显示；客户端可独立升级，无 schema、环境变量或 Device Link/自建中转改动。

## 商店飞书应用多账号（2026-11-10，未发布）

两仓 `slack-hook-protocol` 可选新增 `feishu-store-multi-bind-v1`。Desktop 在飞书线 hello 声明，
服务端只有为已验签 Cindy 身份解析到商店应用时才在 welcome 声明；企业自建应用保持原单账号行为。
用户沿用「关联飞书 / Lark」入口，授权结果是新身份就追加，相同应用和 Open ID 则更新原绑定。
不增加选择应用类型或先添加账号的步骤；短码仍是单次使用，追加失败、取消和超时保留已有身份。

协商后，`provider.bind.state` 的可选 `bindings` 是同一 `scopeId` 下的完整 confirmed 列表，
顶层仍投影第一条供旧端读取，校验绑定字段、名称、动作与应用元数据一致；多应用的顶层 bindings 顺序及字段
也必须与所投影应用一致。数组不接受嵌套、重复身份、跨应用行或不一致的顶层投影。
`provider.bind.update.completedAttemptId` 标识完成的准确尝试，不结束另一个正在进行的授权；
可选 `tenantKey` 为商店应用的安装企业标识。初始快照与当前授权完成/撤销交错时合并实时变化；
只有本次活动尝试的完成确认或权威快照才能授予新身份，快照缺失的旧身份视为已撤销。
物理断线终止在途尝试，用户可从原入口重试；丢弃无法归属的迟到确认，不增加服务端补偿、轮询或自动补发。
任务和目录/模型查询只接受本次连接确认过的应用＋身份。
每行独立解绑与选择工作电脑；服务端在关联事务中为新身份复制本机已有绑定已同步的默认偏好，
客户端通过原 `provider.prefs.set` 镜像后续默认偏好，由商店服务端在关联锁内原子更新当前全部身份，
避免遗漏尚未到达客户端的新绑定。次要身份的 IM 偏好不覆盖桌面主默认视图；账号切换清除内存授权。
本机只按 Cindy 账号保存不含凭证的身份展示列表，不以缓存授予执行权限；可空的应用显示名 scopeName 不影响缓存保留或首账号顺序。
同一连接后续的 `provider.bind.state` 仍是权威快照，立即收敛允许应用与绑定；保留仍允许应用的在途授权，
移除应用后终止其授权并拒绝旧身份任务/查询。多应用列表的展示顺序不决定默认账号；快照合并后
将顶层 scopeId 对应应用的绑定稳定置前，偏好读写、推送过滤和首账号缓存沿用该投影。取消与完成交错时仅接受本轮准确 `completedAttemptId` 的服务端确认，
应用或绑定仅因权威快照暂时消失时不记录为主动解绑，后续快照可恢复同一持久绑定 ID。
准确的新关联也可清除同 bindingId 的本地解绑标记；断线、重建和能力丢失会清掉失败/已取消尝试的 ID，迟到回调不获权限。

发布顺序：服务端先完成数据库迁移和全副本升级，再发布支持追加的 Desktop。
旧服务端或自建应用不宣告能力时，Desktop 保留原单账号入口；旧 Desktop 使用首条绑定，
服务端不允许其发起追加。产生多身份数据后不回退到旧服务端，采用兼容版本前滚。
服务端正式 migration 与兼容说明见其 `docs/feishu-hook-server.md`；无新增环境变量。
这是官方 Feishu hook 的独立连接，未改 Device Link 或自建中转的帧、通道与 allowlist，无需中转升级。
原生 Mobile 没有本次绑定设置入口，无原生配置变更。

应用集合允许权威空快照：`applications: []` 必须伴随 `state: none`、null scope/身份、空 actions（提供 bindings 时也必须为空），
不能带 appInfo。客户端立即清空所有绑定及在途授权，拒绝原身份任务/查询，保留显式空应用集合并隐藏关联入口；后续快照可恢复。
这不新增服务端请求；当前服务器配置变更仍可沿既有关闭/重连路径收敛。两仓 parser 同时接受该可选表达。

多应用连接在最后一个账号解绑后，只要权威应用集合仍非空，就保留渠道启用和连接，用户可继续选择允许的 bot 关联。
解绑仅撤回该账号；关闭整个渠道仍由用户显式关闭开关。旧单应用连接的关闭行为保持原样。

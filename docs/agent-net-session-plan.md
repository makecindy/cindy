## 1. 要解决的问题

打开 Agent-Net 后，两台没打通直连、经官方中转通信的电脑，比只用 Device Link 时更容易卡。
一次实测里，小消息从发出到收到确认的中位数是 39 秒，最长 113 秒；同一时段 Agent-Net 连接一直显示正常。

原因在结构上，不在某个参数：

1. **三层可靠传输叠在一起。** Device Link 的可靠传输（序号、确认、2 秒起的计时重发、64 条在途上限、
   确认超时就重置）跑在 Agent-Net 核心的可靠流上；没打通直连时，核心的数据报又装在 443 WebSocket（TCP）里。
   TCP 不丢包只排队，核心把排队当成丢包重发，Device Link 再按自己的计时重发一遍，越堵越多。
   `packages/agent-net-relay/src/datagramQueue.ts` 开头记录了同类事故：Device Link 只有 16 条小消息在等，
   确认却拖了 156 秒。
2. **所有消息排一条队。** 每台对端只有一条普通优先级的流（`packages/agent-net/src/transport.ts:68`），
   接收端 Device Link 又严格按序号交付（`packages/device-link/src/client.ts:3786-3826`）。
   一次点击排在 727 KB 的任务列表结果后面，要等列表全部到齐才会被处理。
3. **看不到真实线路。** 本机模拟的中转（`packages/agent-net/src/portableSocket.ts`）在本机回复
   Device Link 的心跳（`:335`），Device Link 无从知道某台对端的线路已经堵住；
   Agent-Net 核心自己的确认不排队，也认为连接正常。
4. **中转只有 TCP。** 中转服务器的 UDP 端口只回答公网地址查询（`packages/agent-net-relay/src/server.ts:882-895`），
   数据只走 443 WebSocket（`packages/agent-net-relay/src/client.ts:288-291`）。原计划「UDP 被封时才走 443」，
   现在实现的只有兜底这一条路。

## 2. 目标与不做的事

**目标**

- 有人在等的消息（停止、发消息、回答确认、远程输入）不排在大数据后面，线路慢时也只多等一两个往返。
- 送达只由 Agent-Net 核心负责一次；上层不再计时重发，也不会因为确认慢就重置连接。
- 业务按重要程度声明优先级，一路传到核心的发送调度和被控端的执行调度。
- 写操作仍然只执行一次：调用方已判定失败的写请求，之后也不能再被执行。

**范围：全部迁移**

双方都是新版且打开 Agent-Net 时，所有经 Device Link 传输层的业务流量都迁到会话层，不留一部分在旧路径上：

- 同账号的电脑之间、手机与电脑之间的全部请求、结果与推送；
- 跨账号的供应商分享（含供应商组的执行电脑）与共享任务；
- Node Host（`apps/host`）；
- 远程桌面、文件传输的建连信令与中转兜底路径，远程 Agent 与 Orca 的跨设备桥接，插件与词典同步等。

能力台账按 [Agent 网络](product-rules/agent-net.md)「V2 自建与本机中转的完整能力」逐项列出入口、实现与验证结果，
没迁完的明确标记，不能声明「已全部迁移」。

Device Link 只为两类对端保留：还是旧版本的 Cindy，以及没打开 Agent-Net 的设备。这是产品规则
「只更新一端不能让任何功能失效」「关闭即回到原路径」的要求；旧版本退出后是否下线 Device Link，另行裁决。

**不做**

- 不重写近 300 个业务通道和它们的处理函数，业务看到的仍是「调通道拿结果、推送、文字流」。
- 远程桌面画面、文件字节和媒体本来就走 WebRTC 或媒体通道，不在本方案范围。

## 3. 目标结构

```text
业务层：近 300 个业务通道（不改）
  │  调通道拿结果 · 推送 · 文字流
  ├─ 对端支持 agent-net-session-v1 ──▶ Agent-Net 会话层（新）
  │                                     控制流 · 每个请求一条流 · 每个主题一条流
  │                                     优先级、取消、截止时间、只执行一次、线路状况
  │                                       │
  │                                     Agent-Net 核心：每台对端一条加密连接
  │                                     唯一一层送达、重发、拥塞控制，按优先级发送
  │                                       │
  │                                     UDP 直连 → UDP 中转（新增）→ 443 中转（兜底）
  │
  └─ 旧版对端、没开 Agent-Net 的设备 ──▶ Device Link（不变）：经本机模拟的中转跑在 Agent-Net 上，或走旧版中转
```

下文「流」指 Agent-Net 核心里的流；「业务通道」指 `maker:send` 这类远程调用名。

## 4. 优先级分级

按「晚到的后果」分五级。级别只影响发送和执行的先后，不改变权限、超时和重试规则。

| 级别 | 名字 | 判断标准 | 包括 | 单条上限（建议，实测后定） |
|---|---|---|---|---|
| P0 | 关键控制 | 晚到会出安全或正确性问题，或会话本身维持不住 | 会话建立、关闭、撤销；取消请求；允许被控与忙碌状态；订阅的开关；远程桌面租约心跳；远程控制授权确认；Agent-Net 远程切换的确认 | 4 KiB |
| P1 | 交互 | 人刚做了操作，正在等结果 | 发消息、停止任务、插话、继续、重试、移出队列、回答权限确认与提问、停止子任务；通知上的回复与批准；远程桌面经中转时的输入、建连信令与控制；剪贴板粘贴 | 64 KiB |
| P2 | 实时 | 人正看着它持续变化 | 正在查看的任务的主题流（文字流、工具进度、状态、权限请求）；任务列表上的运行状态；重新打开任务时读取待处理确认和输入队列；远程 Agent 与 Orca 的工具往返；远程桌面经中转的兜底画面 | 256 KiB |
| P3 | 前台 | 人打开了页面在等加载，或做了不急的修改 | 任务列表、历史分页、文件浏览与预览、各类列表读取；改模型与设置、排队编辑、定时任务编辑、分叉、回滚；任务列表主题里的其他推送；没在查看的任务的主题流；刚打开的媒体的首个回复 | 不设单条上限 |
| P4 | 后台 | 没人在等 | 现有后台通道（PR 状态、用量、预测下一句、预热等）；定时轮询；插件、词典等同步；远程 Agent 上传、任务复制、迁移快照、伙伴交接等批量传输 | 不设单条上限 |

规则：

1. **通道表定级，接收端封顶。** 每个业务通道在共享 package 的优先级表里登记级别，现有
   `packages/device-link/src/invokePolicy.ts` 的交互、前台、后台三类直接映射到 P1、P3、P4，
   `bypassInvokeScheduling` 里的订阅与租约心跳映射到 P0。发送方按表声明，接收端按同一张表封顶：
   声明高于表里级别时按表执行，旧版本或出错的一端不能把所有消息都标成最高级。
   表按通道名排序，一项一行，新增通道默认 P3（[工程约定](dev-rules/engineering-conventions.md) §9）。
2. **结果和请求同级。** 被控端用请求的级别执行，并用同一级别发回结果。
3. **超出单条上限就降级。** 超过本级上限的部分在同一条流上降到 P3 继续传，不占交互道。
   上限是起点建议，在阶段 3 实测时校准。
4. **可以升降。** 用户切到某个任务，它的主题流升到 P2；离开降回 P3。页面关闭后，还没回来的读请求直接取消。
   核心已经支持给进行中的流调整优先级（`packages/agent-net-core/src/connection.rs:706`）。
5. **不饿死低级别。** 沿用核心现有规则：高优先级连发 15 个分片，就让下一级发 1 个（`stream.rs` 的 `STARVATION_LIMIT`）。
6. **执行也按级别。** 被控端的执行名额按级别分：先沿用现在的 12 个在途、后台最多 4 个、交互额外 2 个
   （`packages/device-link/src/invokeScheduler.ts:12-21`），P0 不占名额。

## 5. 会话层怎么传

### 5.1 三种流

| 流 | 方向与数量 | 级别 | 内容 |
|---|---|---|---|
| 控制流 | 每台对端每个方向一条，长期存在 | P0 | 会话建立与接受、关闭与撤销、取消、在线与忙碌、订阅开关 |
| 请求流 | 每个请求一条（请求方→对端），结果一条（对端→请求方），用请求号对应，用完即关 | 按通道表 | 一次调用的请求和结果 |
| 主题流 | 每个订阅主题一条（被控端→控制端），长期存在，内部有序 | P2 或 P3，可升降 | `session:<id>`、`sessions`、`fs-watch:<dir>` 的全部推送 |

核心的流是单向的（`stream.rs` 开头），所以一问一答各开一条。

**为什么推送不按条拆开。** 运行中任务的文字流是直接往后拼接的，没有序号
（`packages/maker-shared/src/remoteTextStream.ts:24-30`）；同一任务里不同推送之间也靠队列顺序保证
「终态之后不会再冒出文字」（`apps/desktop/src/main/device-link/dispatch.ts` 的事件批收口）。
所以一个主题的推送必须在同一条有序的流里。不同任务的主题流之间互不等待。

### 5.2 结果等主题追上：保持今天的先后关系

今天每台对端只有一条队列，所以「结果发出之前已经发出的推送，一定先于结果到达」。有几处业务依赖这一点：
- 订阅的回复是屏障：被控端先排进断线前的事件批、离线积压和文字快照，最后才回复订阅成功
  （`dispatch.ts:4535-4568`），手机端据此认为之后的推送是完整有序的。
- 读结果与推送的先后：输入队列投影、待处理确认、正在运行的任务、任务行状态等，控制端靠到达顺序判断哪个更新。
  手机端对任务列表有本地变更代次（`apps/mobile/src/session/remoteSessionStore.ts:228-246`），其他几项没有。

推送和结果分到不同的流以后，这个先后关系不再自动成立。会话层自己把它补回来，业务层不加字段、不改判断：

- 被控端的会话层给每条主题流计数：每写进一条推送，计数加一。
- 发出结果时，按通道表查这个结果需要「等」哪些主题，带上这些主题此刻的计数。
  默认等这台控制端订阅的全部主题，和今天一条队列的效果完全一样；通道表可以把确认类写操作（发消息、停止等）
  标记为不用等，它们的结果只是回执。
- 控制端收到结果后先不交给业务，等对应主题流的推送收到这个计数，再交出去。
- 订阅的回复也走这套：它等的就是刚订阅的那条主题流，积压和快照都收到之后才交给业务。

要等的推送只是结果发出之前已经写出的那部分，和今天队列里排在它前面的内容相同；区别是不再挡其他主题和其他请求。

### 5.3 同一请求键的结果按请求顺序交出

手机端读取待处理确认时，依赖「后发的读请求，结果也后到」（`remoteSessionStore.ts` 的待处理确认读取）。
每个请求一条流以后，结果可能乱序。会话层按通道表里的请求键（例如「通道 + 任务」）把同一键的结果按请求顺序交出：
后到的结果等前面同键的请求有了结果再交。不同键之间互不等待。

### 5.4 送达与只执行一次

- **连接活着时**：只靠核心送达，会话层不确认、不重发、不因慢而重置。
- **请求带上**：请求号、业务通道、级别、剩余时限（相对毫秒数，不依赖两端时钟一致）。
- **被控端执行前检查**：这个请求号有没有被取消过；剩余时限减去估计的单程时间后有没有过期；
  请求号去重沿用现有的请求号加内容指纹与结果缓存（`dispatch.ts:3256` 起）。
  已取消或已过期的请求不执行，直接回「已过期」。这取代今天传输层把失败请求替换成跳过占位的做法
  （`client.ts` 的 `dropReliablePendingForRequest`）。
- **调用方超时或不要了**：在控制流发取消。取消是 P0，会越过还在排队的批量数据；如果取消先到，
  被控端记下请求号，请求后到也直接丢弃。
- **连接断了**：
  - 还没写进核心的请求，报「未发出」，可以安全重试（同今天的 `BACKPRESSURE`）。
  - 已写出的请求，报「可能已执行」（同今天的 `INVOKE_TIMEOUT` 且在途）。只读请求按现有可重试名单自动重试一次；
    写请求不自动重试，靠请求号去重和业务自己的幂等号（例如发消息的 `clientId`）。
  - 被控端在断线期间才算完的结果，放进有界的结果待发区，重连后按原请求号补发，不重新执行
    （沿用 [远程与手机适配](dev-rules/remote-and-mobile-adaptation.md) 里「结果不丢、不重跑」的约定）。
  - 主题：重连后控制端重新订阅，被控端照今天的做法补离线积压和文字快照，订阅回复按 5.2 等主题追上后才交给业务。

### 5.5 线路状况

- 不再有业务层心跳，也不再有因确认慢触发的重置。
- 核心按对端提供：连接是否还在、往返时间、最老一段未确认数据已经等了多久（新增统计，见第 7 节）。
- 会话层据此给每台对端三种状态：正常、变慢、断开。变慢只用于界面提示和暂缓新的后台请求，
  不断开、不重发；连接关闭才重建这一台的会话。
- 拓扑页继续使用核心提供的实际路径、往返和真实收发。

### 5.6 授权与安全

- 端到端加密与设备身份不变。会话跑在已认证的 Agent-Net 连接里，消息来源取自连接身份，不信任消息里自带的来源字段。
- 会话建立沿用 `link-open` 的内容：控制端名字、版本、能力、通道表摘要。被控端检查「允许被控」和撤销名单，
  明确接受后才放行需要控制权限的通道。两个控制方向各自独立，关闭一个不影响另一个。
- 撤销和永久关闭走 P0：被控端立即拒绝这个方向的新请求，取消在途请求，释放增量基准；本机镜像缓存清理照旧。
- 今天在建链之前也能用的只读通道（订阅、列表、历史等）保持同样的放行范围（见第 13 节待定）。
- 跨账号会话（供应商分享、共享任务）沿用现有 V2 分享的授权：绑定分享根、资源、成员密钥与委托，
  只放行授权的业务通道，被控端逐条复验，撤销与续期规则不变。来源取自连接身份，不信任消息里的范围字段。

## 6. Device Link 机制的去留

**在新会话层上不再需要**（只为在一条慢 TCP 上撑住）：

- 可靠传输 v1：序号与按序交付、累计确认、2 秒起的计时重发、64 条在途窗口、分片重组、建链确认与缺口修补、
  60 秒放弃。
- `transport-timeout` 瞬时重置、整条中转卡住检测、业务心跳与重连退避。
- 中转拥塞后的冷却与发送预算、socket 水位。
- 单队列下的变通：丢弃可丢前缀让结果先走、链路未就绪时裸帧直发。
- Device Link 直连（WebRTC）与它的租约，V1 自建中转的帧签名与挑战，按路由代次归因中转错误。
- 接收端主动丢弃、靠发送方重发补回的各处（`client.ts:3616-3821` 一带）：新会话层没有这套重组窗口，
  不存在这些丢弃点；解析失败按请求返回错误，不再静默等重发。

**要搬到新会话层，或由新机制取代**：

| 现有机制 | 新会话层的做法 |
|---|---|
| `link-open` / `link-accept` 的身份、版本、能力与明确接受 | 会话建立（控制流） |
| 远程控制开关（两侧都拦）、两个控制方向独立、撤销与永久关闭、释放增量基准 | 控制流消息，语义不变 |
| 会话（重新）建立事件与代次，被控端据此重放订阅 | 会话代次；订阅回复按 5.2 等主题追上 |
| 一条队列带来的先后关系（推送先于其后的结果、同类读结果按请求顺序） | 5.2 结果等主题追上、5.3 同键结果按序交出 |
| 请求配对、「未发出」与「可能已执行」的区分、只读请求断线重试一次 | 见 5.4 |
| 写操作只执行一次：被控端去重 + 传输层作废已失败请求 | 被控端去重 + 剩余时限 + 取消 |
| 调度名额 | 按级别映射，见第 4 节 |
| 可丢弃的事件批与不可丢的终态推送；推送积压信号 | 按主题流各自处理，积压信号取自核心的每级排队字节 |
| 省流量：结果缓存、任务列表增量、历史增量、消息正文复用、标签目录 | 从 `client.ts` 抽成独立模块两边共用；它们自带内容哈希或版本，换流后仍然成立 |
| 在线状态（允许被控、忙碌）、发手机通知 | 控制流 + Agent-Net 名册；通知照旧走中转的通知接口 |
| 跨账号范围：供应商分享、共享任务、按资源单独的分享连接 | 跨账号会话，授权见 5.6 |

上表是会话层（阶段 3）动手前的核对清单，逐项在代码里确认后再删除对应路径。

## 7. Agent-Net 核心要补的通用能力

都是通用的多路流能力，不写入 Cindy 概念，符合 [Agent 网络](product-rules/agent-net.md)「传输核心的边界」。

1. **更多优先级档位。** 现在只有交互、普通、后台三档（`stream.rs` 的 `Priority`）。改成调用方可用的多档
   （例如 0–7），会话层用其中五档；防饿死规则按档位推广。
   **2026-11-19 防饿死已按档计数**（随第 4 项，记录同下）：原来只记一个数，三档都有数据时一直让给中间档，最高档被饿住；
   多档本身还没做。
2. **更多流。** 每条连接最多 64 条流（`connection.rs:196`），每个请求一条流会碰到上限。改为可配置的更高上限，
   结束的流及时回收。
3. **中途取消。** 现在流只能正常结束。增加发送方放弃一条流（未发的不再发、未确认的不再重传），
   以及接收方请求对方停发。
4. **按优先级预留缓冲。** 所有流共用两倍单流上限的发送缓冲（`connection.rs:113`、`:197`；核心默认每条 1 MiB，
   Desktop 的 wasm 每条跟着拥塞窗口在 1–24 MiB 之间，见第 7 项），接收端未读总量上限 4 个窗口。
   两条批量流就能占满，交互消息写不进去。给高优先级保留份额。
   **2026-11-19 已完成（核心与 Desktop 预编译包；手机原生库待下一次原生包）**：比这条流低档的流占着的发送缓冲最多算到
   「共用上限减去半条流的上限」，自己没缓冲的流总能写进一个分片。查的时候发现 Desktop 配置下**只有一条大流也会挡住交互消息**：
   单流上限跟着拥塞窗口走，窗口缩小后大流已经写进来的字节就超过共用上限；模拟的弱网上有大流时 6 秒里约 900 条交互消息
   改前只送到 3–21 条，改后 891–897 条，p99 0.14–0.32 秒；本机回环真实 UDP 上，下载时交互往返 p50 从 21 毫秒降到 1.1 毫秒。
   单连接对比、一阵一阵、起速和共享矩阵逐行相同，大数据夹小请求只有交互列在种子波动范围内变化，见
   [`2026-11-19-priority-buffer`](../packages/agent-net-core/sim/results/2026-11-19-priority-buffer/README.md)。
5. **进展统计。** 增加「最老未确认数据的等待时间」和每级排队字节数，供会话层判断线路状况和推送积压。
6. **两端驱动同步暴露。** Node/WASM 驱动和手机原生模块（`packages/agent-net-native`，依赖同一份核心）都要暴露上述接口；
   改核心后刷新预编译 WASM；手机原生改动属于冷更新。

7. **对抖动不敏感的起速。** 阶段 0 查清了「经中转速度跑不上去」的原因（见基线报告「速度为什么跑不上去」）：
   核心把往返比最低值高出 4–16 毫秒当成排队，判定排队后巡航只发 90%、不再探测余量；抖动估计取相邻样本之差，
   经 TCP 中转时偏小。每秒 1 MB 的线路加上 0–30 毫秒抖动，1 MiB 只用到线路的 5%–18%；没有抖动时，
   每次重新起速的第一次也只有 33%–69%。要让排队判断不把抖动当排队，并让一阵一阵的业务数据起速更快；
   改动按核心规则用模拟器对比 KCP 与现有版本，速度、流量和交互延迟一起报告，并在真实线路上记录往返、最低往返和带宽估计确认。
   Device Link 本身在已起速时只多 7%–18%，不是吞吐的主因。
   **2026-11-14 已完成**：模拟器里查出四个原因并修好（空闲轮次被当成限速证据、零星包结束启动、不乱序的抖动结束启动、
   产品窗口只有 128 个分片），一阵一阵传输的平均线路利用率从 55% / 51% / 39% / 47% 升到 67% / 72% / 83% / 83%，
   原有对比矩阵与共享矩阵持平。记录见 [`2026-11-14-bursts`](../packages/agent-net-core/sim/results/2026-11-14-bursts/README.md)。
   本机没有 C 编译器，这一轮没有重跑 KCP 对照；巡航阶段仍把不乱序的抖动当排队、按九成发，留待后续。
   **同日接着做了自动窗口**（用户要求「按实测带宽×往返动态放大，上限按内存定」）：Desktop 的窗口改成只按内存定的上限
   8192 个分片，实际在途量本来就由拥塞控制按实测「带宽 × 往返」决定；每条流的发送缓冲跟着拥塞窗口放大（两倍，1–24 MiB），
   慢线路上只占约 1 MB。20 MiB 一阵的平均利用率从 82% / 86% / 90% / 90% 升到 84% / 88% / 95% / 95%，千兆线路从 54% 到 95%；
   跨地区线路空闲 5 秒后的 1 MiB 有一格变差，原因在空闲后重新探测的节奏，留到下一轮。记录见
   [`2026-11-14-auto-window`](../packages/agent-net-core/sim/results/2026-11-14-auto-window/README.md)。
   同时试过让 Device Link 在 Agent-Net 积压回落时立即续写、在按序送达的连接上不按定时器重发；用户随后决定 Agent-Net 自建独立的上层
   （10.1 节），这两处 Device Link 改动已撤回，Device Link 保持原样。
   **同日再做长往返起速**：只发过小消息的连接来了一阵数据，开头一串按新连接第一批包的方式快发，用确认间隔一个往返内量出线路速度；
   量出瓶颈后之后几阵按它的 1.25 倍发，不再按启动的倍数冲爆队列；小消息的副本不再算排着的数据。模拟器里跨地区线路第一阵
   1.1 秒 → 0.46 秒，一阵 1 MiB 的平均利用率 57/60/74/72% → 68/70/79/78%，原有矩阵持平。记录见
   [`2026-11-14-ramp`](../packages/agent-net-core/sim/results/2026-11-14-ramp/README.md)。

另外，`packages/agent-net/src/transport.ts:87` 遇到不认识的流类型会关闭整条连接，
所以新的流类型只能在双方确认支持后才打开。

## 8. 中转加 UDP 转发（第一优先）

阶段 0 的对比显示，没打通直连时 Agent-Net 只能把数据报装进 TCP 经中转转发，在每一档线路上都比原来的 Device Link 慢、更不稳
（见基线报告「和原来的 Device Link 对比」）。核心为 UDP 设计的优势只有走 UDP 时才发挥得出来，所以这一项排在最前面，
和提高打洞成功率一起做。

- 中转增加 UDP 数据报转发，443 WebSocket 保留为 UDP 不通时的兜底。
- 设备先经 443 登录，拿到中转签发的 UDP 凭据；之后 UDP 包带上凭据标识，中转据此认定设备号。
  数据报仍是端到端密文，中转只转发。2026-11-14 用户要求「不该被限速」：通过认证的流量不按来源限速，
  靠传输核心自己的拥塞控制；伪造与篡改的包靠密钥校验挡掉。
- UDP 一段时间不通，自动回到 443；恢复后再切回。
- **2026-11-14 已完成（本仓库）**：认证格式、「收得到」位、退回与恢复的时间见
  [协议记录](dev-rules/protocol-compatibility/agent-net-udp-relay.md)。官方中转需服务端仓同步后生效；手机 2026-11-18 随原生库覆盖
  （新安装包生效）；提高打洞成功率没有做。
- 自建中转同一次改动内同步适配：递增 `packages/device-link-relay/src/version.ts` 的版本，让已部署的主人看到升级入口；
  官方服务端仓的内核副本同步同一改动。容量与限速按 [服务器通道审查](dev-rules/server-channel-review.md) 评估。
  官方部署另行授权。

## 9. 和现有路径共存

- **能力协商。** 新能力暂定名 `agent-net-session-v1`，在 Agent-Net 名册的在线能力里声明，会话建立时再确认一次。
  两端都声明才走新会话层；否则这台对端继续走现有 Device Link（经本机模拟的中转，仍然加密），
  旧版和没开 Agent-Net 的设备走旧版中转。行为与今天一致，只更新一端不会让任何功能失效。
- **失败退回。** 新会话建立失败或对端重启成旧版，退回 Device Link over Agent-Net，不退回明文。
- **开关语义不变。** 关闭 Agent-Net 完全回到原路径；「仅使用 Agent-Net」的含义不变。
- **代码位置。** 会话层放在 Agent-Net 一侧（`packages/agent-net` 内或新包），依赖 `@cindy/device-link`
  的协议类型、通道表和优先级表；`device-link` 不反向依赖它，避免成环。`RoutedDeviceLinkClient`
  已经按对端在几条连接之间路由（`packages/device-link/src/routedClient.ts`），新会话层作为另一种对端连接注入，
  业务代码面对的仍是同一个客户端。Desktop 在 `apps/desktop/src/main/device-link/index.ts` 装配，
  手机在 `apps/mobile/src/device-link/agentNetRuntime.ts` 装配，Node Host 在 `apps/host/src/device-link.ts` 装配；
  Host 与 Desktop 共用的业务主体改动后，按架构原则 §5 同时跑 Host 的测试和类型检查。
- **协议记录。** 实现时另写 `docs/dev-rules/protocol-compatibility/agent-net-session.md`，写清流类型、消息形状、错误码、
  旧端与混用、中转（含自建）的互通结果。

### 10.1 Agent-Net 自建独立上层（2026-11-14 用户决定）

用户原话：「你不能独立实现一个上层嘛 上层不要用devicelink 了这样才是最安全的和最解耦的 devicelink 就全走dl agentnet 就全走an」，
并要求「一定要确保完全解耦 不要相互影响」。所以阶段 3 不在 Device Link 上改协议，Agent-Net 自建会话层。

**解耦规则（硬性）**

1. **代码依赖**：会话层（`packages/agent-net/src/session/`）不引入 Device Link 的收发代码（`client`、`routedClient`、可靠传输 `transport`），
   只用业务契约：`@cindy/device-link-protocol` 的类型，以及 `packages/device-link/src` 里不依赖客户端的 `allowlist`、`invokePolicy`、`topics`、
   `invokeTransfer`（按文件路径引入，不经包入口，免得带进客户端）。Device Link 不引入 Agent-Net 的任何东西。
2. **运行时**：两条路不共享连接、队列、计时器和状态。会话层出错只影响走会话层的对端，Device Link 不知道会话层存在。
3. **只在桌面端封装里组合**：`apps/desktop/src/main/device-link/index.ts` 按对端选会话层或 Device Link，业务代码不改。
4. **Device Link 保持原样**：本 PR 早先为 Agent-Net 加进 Device Link 的「积压回落续写」「按序送达不重发」已撤回。
   卡死修复（`reliablePeerTransport`）只服务旧版对端经 Agent-Net 的兼容路径，保留。

**会话层 v1 怎么传**

- **能力**：Agent-Net 节点在发给对端的在线状态里声明 `agent-net-session-v1`，双方都声明以后，才在已有的加密连接上另开会话流
  （新的流类型；旧版节点遇到不认识的流会关连接，所以必须先看到对端声明）。
- **流**：每个方向三条长期流，同一条流内先进先出，核心按优先级发：控制与交互（核心交互级：会话建立、关闭、取消、在线状态、
  第 4 节 P0/P1 的请求和结果）、普通（P2/P3）、后台（P4）。之后按 5.1 拆成每个请求、每个主题一条。
- **消息**：建立与接受（对应今天 `link-open`/`link-accept` 的身份、版本、能力与「允许被控」检查）、请求、结果、推送、关闭、取消、在线状态。
  交给业务的仍是今天的帧形状（`Envelope`），由会话层的适配器生成。
- **先后**：同一条流内天然有序。跨流时，结果带上发出那一刻各条流已发推送的条数，接收端等那几条流追上再交给业务（5.2）；
  同一请求键的结果按请求顺序交出（5.3）。
- **送达**只靠核心：不确认、不计时重发、不因慢而重置；连接断了按 5.4 处理。

动手前核对代码发现的约束，会话层必须照顾到：

- 今天接收端按序号逐条交给业务、等上一条处理完才交下一条。业务依赖的先后不止 5.2、5.3：任务列表主题上带引擎或生命周期字段的
  `local-db:sessions:patched` 是之后任务事件的分界（`dispatch.ts`「事件批收口」），所以推送在 v1 里同一个方向共用一条流。
- 被控端的 `dispatch.ts` 需要：每帧带 `src` 与请求号；`sendLinkAccept` 失败要同步抛错；`sendInvokeResult` 抛 `PAYLOAD_TOO_LARGE`/`BACKPRESSURE`；
  连接代次与链路代次（`getConnectionEpoch`、`getPeerLinkGeneration`）用来丢弃过期的离线事件。
- Device Link 客户端里还替业务做了结果压缩与缓存（`invokeTransfer`）、调用排队（`invokeScheduler`）、入站通道白名单检查；
  会话层要么直接复用这些不依赖客户端的模块，要么照做。
- 手机端的任务状态已有几处代次和新旧比较（输入队列投影、交互修订号、待处理确认），其余仍靠到达顺序。

**顺序**：① Desktop↔Desktop 同账号，默认关，用开关在隔离环境验收；② 手机；③ 跨账号与 Node Host；④ 默认开启（需确认）。
2026-11-16 用户确认先把 ① 跟着「Agent-Net (Beta)」开关打开（不再有单独的开关，Agent-Net 本身仍默认关）；手机、跨账号与 Node Host 不宣告会话能力，照旧走 Device Link。

### 10.2 会话层 v2：Agent-Net 自己的业务传输（2026-11-19 用户确认）

用户目标（原话）：「agent net 完全走自己的业务传输逻辑，最大限度用到 udp 的优势确保传输速度、可恢复性和业务稳定性，
以及避免拥堵风暴，不该再和 devicelink 有任何冗余了」。同时确认：Device Link 不下线、不改；不做 Agent-Net 与
Device Link 之间的自动换路，Agent-Net 默认按正常处理。

**起因（2026-11-18 晚）**：两台同账号电脑经 Agent-Net 官方中转跑远程任务。启动资料 gzip 后约 1.6 MiB，按 64 KiB 切成
26 块，每块等被控端回执才发下一块（`apps/desktop/src/main/remote-agent/controller/runClient.ts` 的 `payload`）；
回程变慢后每块约 1.6 秒，启动等了 41 秒。会话层和核心没有让它变慢的问题，慢在业务协议是照 Device Link 的限制设计的，
原样搬到了 Agent-Net 上。

**还带着 Device Link 形状的地方**（2026-11-19 按源码基线 `1a5ed26727` 核对）

| 位置 | 现在 | 来源 |
|---|---|---|
| 会话消息 | 每条是整段 JSON（`session/lanes.ts`，单条最大 16 MiB），二进制先转 base64；整条收齐才交出 | Device Link 的帧就是 JSON 消息 |
| 交付 | 每个方向 3 条长期流，流内上一条处理完才交下一条；推送共用普通流 | 仿 Device Link 单队列按序交付；5.1 的「每个请求一条流」还没做 |
| 超时 | 按整次请求的总时长算（默认 30 秒，通道表覆盖） | Device Link 的请求计时 |
| 并发与额度 | `InvokeScheduler` 在途 12、后台 4、交互另加 2；被控端每个控制端在途 4 MiB（文件块另有 4 MiB）；会话积压按 Device Link 可靠窗口的含义交给业务 | Device Link 的本地准入 |
| 业务协议 | 远程任务 64 KiB 逐块上传、每次轮询最多回 1.5 MiB（`host/runHost.ts` 的 `poll`）；文件 `stream-read` 每块 256 KiB、4 块在途，附件 1 MiB base64 块、3 块在途（[文件直传记录](dev-rules/protocol-compatibility/agent-net-file-stream.md)、`packages/device-link/src/peerAttachment.ts`）；结果超限压缩、推送超限丢弃（`dispatch.ts`） | 躲开 Device Link 的 2 MiB 帧与 4 MiB 消息上限 |
| 核心 | 第 7 节第 1–5 项没做：只有 3 档优先级、最多 64 条流、流不能中途放弃、发送缓冲共用两倍单流上限（`connection.rs` 的 `send_stream`，两条批量流写满时交互流写不进去）、没有进展统计 | — |
| 手机驱动 | 核心只在 JS 每 8 毫秒一次 `poll` 时收包、回确认、跑计时器（`nativeTransport.ts` 的 `schedule`；原生库没有自己的循环）；每次调用都是 JSON 加 base64；每次 `poll` 最多收 256 个包、发 128 个包、交出 256 KiB（`agent-net-native/src/engine.rs`） | — |

另有一处由代码推断、日志里还没见到的卡死：轮询回包按固定上限组包（base64 后约 2 MB），请求总时限 30 秒；线路低于约
每秒 70 KB、积压又超过上限时，一次回包传不完，超时后按同一游标重拉同样大小，直到 2 分钟后放弃任务。

**原则**：只换「怎么传」，不换「传什么、谁能传、执行几次」。业务通道、载荷形状、授权复核与去重号不变。

**v2 怎么传**

1. **按请求、按主题分流**：落实 5.1。每个请求一条流、它的结果一条流，每个订阅主题一条推送流，控制流不变。
   请求之间、主题之间互不排队。
2. **消息是「头 + 二进制正文」**：头是小 JSON（消息外层、请求号、通道、正文长度与 SHA-256）；正文按原始字节流式写出，
   不转 base64，没有单条上限。接收端按头里的长度先核配额，超过内存阈值的正文写临时文件（遵守
   [凭证与本地存储](dev-rules/credentials-and-local-storage.md)的临时文件规则）。
3. **先后**：同一条流天然有序；跨流沿用 v1 的计数（`p`、`r`、`b`、`o`），粒度从 3 条流细化到每个请求与主题。
   5.2、5.3 和「任务列表补丁是任务事件的分界」都不变。
4. **超时分两段**：传输阶段看进展，核心报告这条流的已确认字节连续 N 秒不动才算失败（N 在 v2-1 实测后定）；
   执行阶段按业务原有时限，从被控端收齐正文起算。
5. **流量控制只在核心**：在途多少由拥塞控制和每条流的接收窗口决定；应用层不设窗口、额度和逐块回执。
   取消就是放弃这条流（第 7 节第 3 项），没发的不再发、没确认的不再重传。
6. **准入按优先级与核心积压**：第 4 节的 P0–P4 映射到核心档位，被控端的执行名额按级别分，不再沿用 Device Link 的数字；
   积压读数取核心每档的排队字节（第 7 节第 5 项）。

**业务协议改用 v2**

| 业务 | v1 | v2 |
|---|---|---|
| 远程任务上传（启动资料、带图消息、大回包） | gzip 后切 64 KiB，逐块等回执 | 一个二进制正文；被控端确认收齐后再发 `open`、`call`、`reply`，不依赖跨流先后 |
| 远程任务事件 | 长轮询，每次最多 1.5 MiB | 被控端往一条事件流里写，发多快由核心流控按控制端读的速度决定；断开后按游标续传 |
| 文件下载与上传 | `stream-read` 256 KiB 块、`stream-rpc` 1 MiB base64 块 | 一个文件一条流，按偏移续传，结束核对哈希 |
| 大结果与历史 | 整段 JSON；超限压缩或报错 | 正文流式；gzip、结果缓存与增量照旧，分页按界面需要保留 |
| 文字流节流 | 按 Device Link 窗口含义的积压读数 | 按核心积压与往返 |

**前置**

- 核心：第 7 节第 1–5 项，先做第 4 项（给交互流预留发送缓冲）和第 5 项（进展统计）。核心改动按
  [Agent-Net 计划](agent-net-plan.md)第 13 节做三层验证。

**发现（主干就有，部分修好）**：xdt-server 这条线路本身只有约 0.7 MB/s（8 MiB 走 WebSocket 与走 UDP 都要约 12 秒，多半是云服务器的出口带宽上限）。
限速线路档（代理排队丢尾）上 UDP 的线路字节只有业务字节的 1.06～1.1 倍；撞上这条真实上限时是 1.7～6.5 倍（1 MiB），8 MiB 时约 2 倍。
在收端进程里逐层计数确认是真丢包：服务器转发了全部数据报，到达本机套接字的只有约三分之一，套接字缓冲加到 4 MiB 也一样（排除本机缓冲）。
也就是核心的拥塞控制在这种限速器上一直超发，跑不出比 WebSocket 更高的速度，只多耗一倍出口流量；自建中转常放在小带宽云服务器上。

2026-11-19 在模拟器里复现并修了两处（[核心验证记录](../packages/agent-net-core/sim/results/2026-11-19-policer-tail/README.md)）：令牌桶放行的一串把带宽估计抬高以后，
一阵数据的尾巴被当成应用空闲、判限速的那一段整段作废；尾巴的重传被成片挡下，又把随机丢包率推到 98%，判限速的门槛超过 100%。
改后 1 MiB 在往返 90 毫秒的限速器上从 9～11 倍降到 4.4 倍，往返 40 毫秒、600 KB 令牌从 6.1 倍降到 5.1 倍，其余矩阵和共享用例基本不变。
往返 10 毫秒这一档（最像 xdt-server）只从 9.1 倍降到 7.5 倍，8 MiB 不变：剩下的是「丢得比送达多时要等 200 毫秒才下结论、宽松上限按被抬高的估计打底」，
六种更早、更紧的认法都弄坏了浅队列共享、断网、有突发的限速器上的现有用例（同一记录「试过、没留下的」），要把判限速这部分重新设计，留作 v2-1 的后续一项。
同日在 xdt-server 上按改后的核心重测（同一记录「公网」一段）：1 MiB 上传线路字节合计 4.32 → 3.65 倍、最坏一次 7.2 → 5.0 倍，8 MiB 1.69 → 1.66 倍，
改前改后都一次没认出限速，延迟和上传用时不变。这条线路上的超发仍在，要等判限速重新设计。

**待定**：v2-5 做不做（不做则推送继续共用一条流）；v2-4 冷更新的发布时机；进展超时 N 与各项阈值在 v2-1 实测后定。

## 11. 验收

- **超过原来的 Device Link。** 用阶段 0 的同一个脚本（`--modes v1,worker`）在每一档线路上对比，
  Agent-Net 的大消息耗时和交互延迟都要优于原来的 Device Link，任何一档都不能卡死；阶段 1、2、3 各自完成时都要报这张表。
- **实验室对照。** 用阶段 0 的同一个脚本和线路档位重跑，对比基线：大消息在途时，
  交互请求的往返不再随大消息时长增长（基线里一直等到大消息传完，每秒 250 KB 档最长 6.9 秒，加抖动的每秒 1 MB 档最长 21.5 秒），
  P0、P1 往返的 p99 不超过空闲往返的两倍加 200 ms；批量吞吐不低于基线。具体数值在阶段 3 实测后确认。
- **真实线路。** 两台经官方中转的电脑，交互消息「发出→开始执行」的中位数和最大值，对比现在的 39 秒与 113 秒。
- **只执行一次。** 超时、取消、断线三种情况下，写请求都不重复执行，调用方已判定失败的请求之后也不执行；
  重连后结果按原请求号补发，不重跑；主题不乱序、不丢终态。
- **故障隔离。** 两个以上控制端共用一台被控端，其中一个静默或不读数据，其余无感；一台对端变慢不影响其他对端；
  中转断开时，已直连的对端不受影响。
- **兼容矩阵。** 新↔新、新↔旧（只更新一端）、只更新手机、Agent-Net 开与关、「仅使用 Agent-Net」、
  官方中转、自建中转、本机中转（阻断官方服务时验证，且不隐式回落官方线路）；
  同账号、供应商分享（含供应商组）、共享任务、Node Host 各自都要覆盖。
- **测试写法。** 按 [工程约定](dev-rules/engineering-conventions.md) §3.2 的价值门槛，优先并入已有测试文件；
  现有互通与重连用例用同一套断言在新会话层上再跑一遍。

## 12. 故障半径三问

| 故障 | 恢复动作 | 不会扩大的原因 |
|---|---|---|
| 单个请求超时或被取消 | 只关这条请求流 | 其他请求和主题各有自己的流 |
| 单台对端变慢 | 标记变慢、暂缓新的后台请求 | 不重置、不重发，不影响其他对端 |
| 单台对端连接断开 | 只重建这一台的会话，补发结果、重新订阅主题 | 补发和续订沿用原级别，不挤占 P0、P1；有界 |
| 中转上行断开 | 只重连中转上行 | 已直连的对端不经过中转 |
| 单台对端连接断开、目录里它还在线 | 拨号一端（设备号小的）1 秒后重拨，失败加倍到 30 秒 | 只拨这一台；对方离线、被拦、本机关闭时不拨；连接活过 30 秒才重新从 1 秒算 |
| 这台电脑换了网络 | 中转连接各 ping 一次，15 秒没回才换；对端连接从新地址发包 | 一次换网每条中转连接只探一次；探测期间照常收发，不先断开 |
| 会话断开时有写请求在途 | 会话回来时走原有重开循环重开链路，在途的写用原请求号再发一次 | 只在请求自己的时限内等；对方去重记忆变了（重启、清空）就不再发；只续本机还在控制的对端，重开循环每次尝试前复查授权 |

重放会不会立刻重造故障：只补发「未执行或可安全重试」的请求和待发结果，主题照今天的做法补积压或发快照，都有上限。

## 13. 风险与待定

1. **架构方向变化。** 本方案替代原计划「`DeviceLinkClient` 不改」的做法，2026-11-13 已确认。
2. **两套并存。** 旧版本退出前，新会话层与 Device Link 要并存，两套都要维护；完全下线 Device Link 另行裁决。
3. **隐含顺序依赖。** 遗漏任何一处，都会出现文字错位或状态回退。会话层按 5.2 默认让结果等全部订阅主题，
   和今天一条队列等价；只对通道表里标为「不用等」的确认类写操作放开，放开的名单逐项核对。
4. **剩余时限估计。** 两端时钟不同，用相对时限加往返估计，估计偏差只会让请求更早被判过期，不会多执行。
5. **优先级表维护。** 新增业务通道要登记级别，未登记默认 P3。
6. **待定：**
   - 建链前就能用的只读通道，在新会话层里怎么放行。
   - 推送压缩是否保留；保留时，压缩失败要能明确「关闭并重新同步」。
   - 会话层能跨重连保留结果后，被控端的结果待发区还需不需要单独存在。
   - 各级单条上限与验收数值，以阶段 0 基线为参照，在阶段 3 实测后确定。

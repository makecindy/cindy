# 原生插件与 Skill 加载排查

> 状态：参考排障说明，描述现有 Desktop 行为，不新增插件准入或执行策略。
> 适用范围：普通本机桌面任务。SSH、设备托管、独立审阅、伙伴隔离配置和本地 Agent API
> 有各自的启动配置，不能直接套用本页结论。

在 Codex 或 Claude Code 中装好了 Superpowers，却在 Cindy 里找不到或不能使用时，
先区分「已安装」「运行时已加载」「界面能找到」「实际调用成功」。这四项并不等价。

## 先确认安装的是什么

| 安装对象 | 由谁执行 | 如何核对 |
| --- | --- | --- |
| Codex / Claude Code 原生市场插件 | 对应引擎的插件运行时 | 核对任务引擎、运行位置和该引擎初始化结果 |
| 单独安装的 Skill（`SKILL.md`） | 当前任务的技能发现与调用入口 | 用确切技能名检查 `/` 和技能管理入口，并做一次显式调用 |
| Cindy `.cindy` 插件 | Cindy 插件宿主 | 在 Cindy 插件页检查安装、启用和授权状态 |

一个包可能同时包含 Skill 和启动钩子。某个 Skill 能调用，不代表整个原生插件及其
启动钩子都已运行；在 Cindy 插件页启用 `.cindy` 包，也不能证明原生市场插件已加载。

## 普通本机 Codex 任务

Desktop 为 Codex 设置 `disableCodexPluginRuntime: true`。本机启动参数因此包含
`--disable plugins --disable remote_plugin`，原生市场插件不会在这条路径执行。
反复重装或同步缓存不会解除这项运行时限制。

Codex 插件缓存和启用配置的同步是另一件事：同步成功只证明文件与配置可用，不代表
本次任务启用了插件运行时。普通 Skill 也有单独的发现路径，不能用 Skill 可调用来
证明原生插件钩子已执行。

依据：[Desktop Codex 装配](../apps/desktop/src/main/maker-host/index.ts)、
[本机 Codex 启动参数](../packages/maker-core/src/agents/codex/index.ts)、
[原生插件同步](../apps/desktop/src/main/maker-host/codex-global-plugins.ts)。
这些结论不用于推断 SSH 远端或本地 Agent API 的 native 模式。

## 普通本机 Claude Code 任务

未托管、未隔离的普通任务会读取 `user`、`project`、`local` 三类设置来源。
先在相同账号、项目和任务类型下新建会话，用确切技能名搜索并显式调用一次。
不要只凭 `/` 中是否可见判断插件是否加载。

若仍失败，开发者可从该次 SDK `system/init` 事件核对目标插件、技能是否列出：

- 初始化未列出目标：核对该任务实际采用的配置目录、项目目录和插件启用范围。
- 初始化已列出，且显式调用成功，但界面搜不到：定位为技能发现或展示的覆盖缺口。
- 初始化已列出，但调用失败：保留这次调用的简短错误，继续排查执行阶段。
- 显式调用成功，但自动启动行为未出现：单独核对对应钩子，不能据此宣布整个插件正常。

依据：[Claude Code 设置来源与启动参数](../packages/maker-core/src/agents/claude-code/index.ts)。
托管、审阅和隔离任务会使用不同设置来源，不适用本节的三来源结论。

## 反馈时提供一个最小失败例子

记录 Cindy 版本、系统、任务引擎及运行位置、安装来源、目标插件或技能名，以及
「期望哪个行为 → 实际结果」。例如：`/` 搜不到目标、找到后调用失败、或启动钩子未触发。
请勿粘贴完整环境变量、授权文件、配置文件或完整会话；初始化核对只需目标是否列出，
执行核对只需成功与否及脱敏错误。

原报告尚未给出具体运行记录，不能据此认定两个引擎存在同一个加载故障。

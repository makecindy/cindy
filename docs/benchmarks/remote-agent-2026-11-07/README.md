# Cindy 远程 Agent 性能方案与受控实测（2026-11-07）

## 最终决定与初轮发现

范围仅为 **Cindy → Cindy**，不引入 SSH 产品入口、ACP 接入或其他客户端。
**最终决定：大载荷并发上传暂不采用，生产继续串行。** 后续真实双端试验证明部分上传可以提速，
也发现控制请求等待增加与较大载荷收益波动，尚不足以支持改变默认行为。
完整权衡与数据见 [大载荷上传实验记录](UPLOAD.md)。本 PR 仅归档文档、原始数据与独立实验脚本。

以下保留初轮受控实验的发现与当时的候选方向，具体上传建议已被上述最终决定取代。

1. **多分片有限并发在受控环境中有收益**：4 MiB 难压缩载荷，在注入 50 / 150 ms RTT 时，
   上传准备阶段分别省约 0.27–0.28 / 0.79 秒。两轮方向一致。小载荷、单分片、近零延迟无明确收益。
2. **启动资料并行采集可作小改，但不是性能重点**：8 / 128 个项目 Skills，分别省约 2.6 / 10–11 ms。
   不值得为此建立通用调度器；若修改，直接保留依赖关系的 Promise 并行即可。
3. **持续推送先保留为候选**：150 ms RTT 下，事件到达延迟中位数约 151–152 → 76–77 ms。
   这是简化推送参照，不是完整可替换协议；需要验证补发、背压和消息数量后才能决定实施。
4. **暂不做持久快照缓存或通用增量同步**：五个任务同时采集同一项目，合并在途读取可省约
   6–40 ms，但大项目两轮波动明显。收益不足以单独支持引入失效、撤权与跨任务隔离机制。

不能把以上数字解释成完整 AI 任务加速比例，也不能据此宣称 Cindy 比 cc-remote 更快或更慢。
本次没有部署或运行 cc-remote；其源码提供了实验方向。

## 方法与证据边界

- 基线：`4538b647a6af841aed5c49f00fa96f581538f7b8`。
- 本机：Apple M5 Ultra，macOS arm64，Node v22.21.1。非独占机器，不清操作系统文件缓存。
- 两次独立完整运行；每项先预热，A/B 顺序交替，记录全部原始耗时与中位数、p95。
- 采集：每种方案 25 次；五任务同项目读取：每种方案 15 次；上传：每种方案、每种载荷、每种 RTT 各 7 次。
- 事件：每种传输方式、每种 RTT 发 100 个事件，间隔 10 ms；这些事件相关，不能当成 100 次独立完整任务。
- 文件采集使用生产 `projectFiles.ts` 公开函数与真实临时文件、真实 Git 检查。调度顺序在实验入口组装，
  **不是 `startRemoteAgentSession` 全流程计时**；没有测 MCP 准备、授权、Agent 进程启动、模型首字。
- 上传使用生产 `RemoteAgentRunClient.payload`，候选在打包时只把串行循环替换为每批最多 4 片。
  其他压缩、阈值、分片大小及编码路径相同；每次都重组、解压、核验内容一致。
  计时包含接收后校验，因此它是含共同校验开销的阶段对比，而不是纯线速测试。
- 上传/事件使用**真实持久 loopback WebSocket**。50 / 150 ms RTT 通过每方向计时器注入；
  0 表示不注入延迟，并不意味着实际耗时为零。包含真实 JSON 编解码、Buffer、gzip 与 socket I/O。
- 使用生产请求解析器校验上传/poll，请求 ID 满足协议；事件使用生产 `RemoteAgentPoller`、
  `EventLog`、`LineSplitter`，并核验 100 个事件完整、有序、无重复。
- **没有经过正式 Device Link 的加密、分帧、限流、分享授权、官方/自建 relay、WebRTC 或供应商组分配**。
  没有模拟带宽瓶颈、丢包或断线，没有真实 WAN、模型、UI，也没有可靠的 CPU/RSS 对比结论。
- 数据为生成的 Skills / 重复文本 / 随机字节；个人配置根显式指向临时空 home，未使用用户凭证或实际项目内容。

原始数据：[第一轮](run-1.json)、[第二轮](run-2.json)。

## 结果

下表均为各轮中位数（毫秒），`前 → 后`。两轮分别列出，避免把波动隐藏在一个平均值里。

| 实验 | 第一轮 | 第二轮 | 判断 |
| --- | ---: | ---: | --- |
| 8 个项目 Skills，串行 → 并行采集 | 14.30 → 11.73 | 12.80 → 10.20 | 稳定但只有约 2.6 ms |
| 128 个项目 Skills，串行 → 并行采集 | 32.76 → 21.45 | 32.77 → 22.33 | 约 10–11 ms，适合小改 |
| 5 个任务、8 个 Skills，各自读 → 共享在途结果 | 17.32 → 11.52 | 16.25 → 10.45 | 约 6 ms，不值得通用缓存 |
| 5 个任务、128 个 Skills，各自读 → 共享在途结果 | 41.97 → 22.24 | 71.73 → 31.35 | 约 20–40 ms，波动明显 |
| 4 MiB 难压缩内容，0 ms RTT，串行 → 4 片窗口 | 101.55 → 100.02 | 109.32 → 109.84 | 无稳定优势 |
| 同上，50 ms RTT | 503.03 → 220.62 | 473.14 → 205.32 | 约少 56–57%，值得推进 |
| 同上，150 ms RTT | 1213.28 → 428.33 | 1207.40 → 421.77 | 约少 65%，值得推进 |
| 事件到达延迟，0 ms RTT，长轮询 → 推送参照 | 0.16 → 0.16 | 0.15 → 0.11 | 绝对差异可忽略 |
| 同上，50 ms RTT | 52.59 → 25.68 | 51.90 → 25.64 | 省约 26–27 ms |
| 同上，150 ms RTT | 151.02 → 76.74 | 151.78 → 75.90 | 省约 74–76 ms |

### 上传收益的条件

生产分片大小为 gzip 后 512 KiB。实验中的 4 MiB 字符串来自 3 MiB 随机字节的 Base64，
压缩后约 3.01 MiB、7 个分片；4 片窗口把确认等待从 7 批缩成 2 批。

对照组不能忽略：

- 32 KiB 内容在 `payload()` 里直接内联返回，约 0.07–0.08 ms，根本没有调用上传。
  **这不是短消息网络延迟**，只是验证窗口改动不影响这一分支。
- 2,160,000 字节重复文本压缩后仅 4,598 字节、1 个分片；150 ms RTT 下两轮
  串行/窗口分别为 167.33/170.77 ms 与 166.48/166.41 ms，没有稳定收益。
- 两组 Skills 采集结果的序列化体积约 45 KB / 722 KB，均不足 1 MiB 内联阈值。
  因此不能把“大载荷上传少 65%”直接套到这两组正常启动资料上。

### 推送收益的代价

当前生产长轮询有数据即返回，不存在固定等满超时的问题。持续事件到达时，上一批响应与下一批请求
之间仍有往返空档；参照推送省去了这部分等待。

第一轮 100 个事件在 50 / 150 ms RTT 下分别约用了 23 / 9 次 poll（包含尾部收口请求），
推送则逐事件发送 100 次。低延迟下约 101 次 poll。不能只看延迟就断定推送更省流量或 CPU：
高延迟下，轮询自然合并了一批事件，而逐事件推送会增加帧数。没有测完整可靠推送、批量推送、
多任务竞争和工具请求往返；这里的结果只是简化参照，不能直接当作实现承诺。

## 可实施方案与验收要求

### A. 多分片上传：已完成真实链路实验，暂不采用

以下是当时的实验约束；双端结果已写入上传实验记录，未覆盖的场景明确保留为证据边界。

- 只改变多片上传；不改小载荷、压缩阈值、授权或分享语义。
- 本实验比较的是串行和每批 4 片；尚未证明 4 是最佳值，正式实现比较窗口 2 / 4。
- 当前接收端按 index 保存片段，支持乱序到达，但真实传输层容量与各任务公平性仍需验证。
- 控制并发在途字节；任一失败或取消后不再调度下一批，已发出的请求收口后不得继续 open/send。
- 真实 Cindy 双端分别走直连与 relay，测上传完成耗时、同时发送短消息/停止指令的延迟、峰值暂存量；
  覆盖弱网、失败、取消、乱序、重复片与旧端兼容。不能通过提高共享通道上限获得漂亮数字。
- 最终决策：**暂不采用**；双端实测及原因见 [实验记录](UPLOAD.md)，生产保留串行上传。

### B. 启动资料并行：低成本时做

- 项目文件、上级说明、上级标记、Git 探测可并行；个人配置仍依赖项目文件，导入解析依赖此前内容。
- 能力握手与本地采集重叠是后续候选，本轮没有测，不在结果中计收益。
- 保持取消检查、错误回退与输出一致；不引入缓存或新调度状态机。
- 决策：**适合顺手的小改，不作为明显改善启动速度的主项目**。

### C. 活跃事件持续推送：暂缓完整改造

- 若推进，复用现有可靠传输与游标，而不是另造协议；保留断线补拉、背压、授权失效与旧端回退。
- 区分工具请求/权限确认等需要低延迟的控制消息和可合并的文本 delta。
- 先验证真实链路、多任务竞争下的事件 p95 和帧数、CPU，再决定是否值得。
- 决策：本轮证明了延迟空间，**尚未证明完整方案的总体收益值得复杂度**。

### D. 合并采集/增量同步：暂缓

- 实验只把同时开始、同一固定 fixture 的 5 次读取合并为一个 Promise，各使用方拿独立克隆。
- 没有实现持久缓存或差量协议，没有测真实修改频率与失效成本。
- 正式复用必须区分账号、权限、项目、Skills 配置和内容代次；`@` 导入会改写结果，不能跨任务共享可变对象。
- 已有托管 Skills 指纹复用应继续保留，不另起重复机制。
- 决策：**目前不新增通用缓存/增量同步**，待真实采集耗时证明其是瓶颈再考虑。

## 复跑

在已执行 `pnpm install` 的此 checkout 中运行：

```sh
node scripts/benchmarks/remote-agent-performance.mjs /tmp/cindy-remote-perf.json
```

脚本不在默认单测中运行。使用唯一临时目录，在 finally 清理；只在最后写指定结果文件。
脚本现从固定基线读取串行上传，在内存中重建归档的 2 片原型；`run-1/2.json` 保留的是早期 4 片原型成绩。
当前候选结果字段为 `candidate`；仅复跑上传可设置 `CINDY_BENCH_UPLOAD_ONLY=1`。
仅复跑事件实验可以设置 `CINDY_BENCH_EVENTS_ONLY=1`。

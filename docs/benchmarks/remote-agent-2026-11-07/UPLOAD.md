# 大载荷上传实验：结果与暂不采用的决定

日期：2026-11-07。范围是 Cindy → Cindy。**最终决定：保留实验记录，生产继续串行上传。**
本 PR 只包含报告、原始数据与手动运行的实验脚本；生产客户端、协议及业务测试没有改动。

## 为什么不采用

原型使用 **512 KiB 分片、每批最多 2 片**，减少等待确认的轮数。
真实链路中，4 MiB 难压缩载荷的中位耗时在两组对比分别下降 **32% / 24%**，
每次省约 **0.30 / 0.22 秒**。10.7 MiB 一组慢约 4%，另一组快约 26%，收益不稳定。

收益没有覆盖已测的常规启动资料：8 / 128 个 Skills 的采集结果约 45 KB / 722 KB，
均可直接内联，不进入分片上传；也没有日常样本证明大载荷确认等待是主要瓶颈。
与此同时，2 片方案的控制请求中位耗时增加约 **20–62 ms**，部分组尾延迟增加约 **100 ms**。
多任务同时大上传时的停止、确认和正常交互尚未实测。这是共享链路上的性能取舍，
不能把单次上传省几百毫秒视为整体体验改善。

因此，当前收益证据不足以支持更改默认行为；也不继续引入分片自适应、全局调度器或优先级机制。
若未来日常数据证明多分片上传经常拖慢任务，再补测多上传竞争与真实交互后重新评估。

## 实验原型与保留方式

- 原型曾修改 `RemoteAgentRunClient.payload`，覆盖 open、call 和反向 reply 的载荷准备。
  JSON 内联阈值、gzip、512 KiB 分片、64 MiB 压缩后上限、请求格式与接收端均保留。
- 原型每批用 `Promise.allSettled` 收口；失败或取消后不发后续片，不继续 open/call/reply，
  不新增重试。已到接收端的失败上传沿用原暂存过期回收。
- 每份上传在途压缩字节由最多 512 KiB 增至 1 MiB，另有编码／传输副本；不是全应用内存上限。
  多任务仍竞争原有共享链路。小消息、压缩后单片内容无稳定收益。
- 生产改动与针对原型增加的业务单测已撤下；不修改协议兼容台账，也不宣称默认功能已经交付。
- [原型生成器](../../../scripts/benchmarks/remote-agent-upload-candidate.mjs)仅供实验脚本导入：
  将固定基线的串行源码在内存中变为 2 / 4 片原型，只编译到独立临时目录，不写生产文件。
  2 片原型可重建与 `upload-live-final.json` 记录相同 SHA-256 的客户端源码。

## 真实双端如何测

发送端是 Mac Studio 上现有开发版 Cindy（版本标记 0.0.0），接收端是 Mac mini 上未改动的
Cindy 0.1.124。数据经过两台机器之间的现有、已认证 Device Link，采样前后及每个有效样本结束时
均报告 direct 可用；没有逐帧抓包，不能排除采样之间的短暂传输回落。
没有关闭直连、强制 relay、重启或替换任一应用。

独立脚本把基线／候选的**真实生产上传函数**打包，再通过本机开发 CDP → 现有 preload IPC →
运行中的 Cindy Main → Device Link → 对方 Cindy 的真实上传接收端调用。
CDP 适配带来共同的本地序列化开销，因此这是实际双端数据路径验收，**不是完整 Agent 启动或模型首字计时**。
未重新编译／安装整个 App，日常任务从未启用该原型。

- 基线：`4538b647a6af841aed5c49f00fa96f581538f7b8` 的串行生产代码。
- 窗口对比：串行、2 片、4 片；最终复跑：串行与当时未变换的候选源码，记录源码 SHA-256；归档脚本现从基线重建同一原型。
- 每种载荷／变体预热一次，正式各测 5 次，轮换顺序，不挑最快的一次。
- 3 / 8 MiB 随机字节编码为 Base64 JSON：源大小约 4 / 10.7 MiB，gzip 后约 3.01 / 8.03 MiB，
  分为 7 / 17 片。同一轮各变体用相同内容；不读取个人文件、凭证或真实对话。
- 第一个分片开始后，每 50 ms 检查是否可启动一对控制探针；上一对未完不叠加。
  探针是同通道 `caps` 和新随机 runId 的无副作用 `close`。最后一对可能在上传完成后收口。
  这测的是控制 RPC 竞争，不是用户可见短消息或正在运行模型的真实停止耗时。
- 每份上传结束后，引用载荷发送故意缺少 `sessionId` 的 open：真实接收端先核对所有分片／长度，
  重组、消费暂存、gunzip CRC 校验、JSON 解析，再由 open schema 返回 `REMOTE_AGENT_INVALID`。
  再次引用返回 `REMOTE_AGENT_EXPIRED: upload is missing or expired`，证明已消费。
  这一步不创建任务、不启动 Agent、不调用模型；不是两端 SHA-256 回显比对。
- 版本、调度优先级、直连标记与全部样本见原始文件；不保存设备 ID、名称或内容。

## 真实数据

单位毫秒。中位数对应每组 5 次上传；p95 只表示本次少量采样的尾部，不能外推成稳定线上 p95。

| 10.7 MiB | 1583.82 | 1652.28 | 1558.96 | 77.72 / 139.24 / 314.72 | 166.05 / 262.74 / 435.68 |

2 片保留部分吞吐收益，同时把每批字节数减到 4 片的一半。它并没有让控制请求与上传完全隔离。

### 2 片原型，独立复跑

| 源载荷 | 上传中位数：串行 → 2 片 | 变化 | 上传 p95：串行 → 2 片 | 控制中位数：串行 → 2 片 | 控制 p95：串行 → 2 片 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 4 MiB | 897.67 → 682.40 | 少 24.0% | 1137.82 → 1205.51 | 96.06 → 126.84 | 467.30 → 251.50 |
| 10.7 MiB | 1962.82 → 1451.58 | 少 26.0% | 2613.81 → 1703.93 | 97.57 → 117.84 | 155.97 → 255.57 |

来源：[最终复跑全量数据](upload-live-final.json)。全部 20 个正式样本通过接收／消费验证，峰值请求数符合串行 1／候选 2。
两次对比的 4 MiB 中位数方向一致，但最终 4 MiB 的尾部没有改善；10.7 MiB 第一组略慢，第二组更快，
表明真实链路带宽与抖动会影响收益。不能只引用最终一组的 26% 并承诺所有大载荷同等加速。

### 高延迟受控补充

使用同一生产基线／2 片原型与 loopback WebSocket，每方向注入半个 RTT；不是实际 WAN。
每组预热一次、交替测 7 次，接收后逐字核验解压 JSON 一致。4 MiB 难压缩载荷结果：

| 注入 RTT | 串行 → 2 片，中位数 | 变化 |
| --- | ---: | ---: |
| 0 ms | 103.98 → 102.96 | 基本持平 |
| 50 ms | 479.10 → 316.85 | 少 33.9% |
| 150 ms | 1198.12 → 729.38 | 少 39.1% |

来源：[最终受控数据](upload-controlled-final.json)。内联小消息约 0.07 ms，单片可压缩文本无稳定收益，
它们是分支对照，不能称为小消息网络加速。机器非独占；不据此报告 CPU／RSS 改善。

## 探索阶段的修正

保留失败与不适合作最终结论的数据：

- [早期探索](upload-exploratory.json)只在开始 150 ms 发探针，大载荷的探针可能落在 gzip 阶段，
  会低估上传时的控制延迟；不能用它判断公平性。
- [小分片未完成实验](upload-small-chunks-partial.json)在 4 MiB 上把 7 次上传增为 25 次，
  没有显示稳定上传收益。进入第二种载荷时出现 `DEVICE_LINK_BUSY`，本轮中止，没有重放写操作。
- 上述探索通过 IPC 显式给了 background 提示；核对生产接线后确认 `remoteBackgroundInvoke` 的
  “background”指建链方式，不等于调用准入的 background hint。正式窗口对比与最终复跑均移除该提示，
  沿用生产的通道默认调度。小分片结果因此只用于排除继续扩展的动机，不能与正式成绩直接混算。

## 原型阶段的历史验证与边界

以下是撤下生产改动前的原型验证记录，不代表本 PR 增加了这些业务用例：

- 自动回归：`roundtrip.test.ts`、`runClientReply.test.ts`、`hostLifecycle.test.ts` 共 **143 项通过**；
  总墙钟 19.59 秒，测试本体 2.98 秒，已有依赖收集 19.33 秒。新增用例并入已有文件，未添加定时等待。
- 测试卫生检查通过（352 个既有基线文件）；文档检查 10 项通过，改动的 TypeScript 文件 ESLint 通过；Desktop 全量 typecheck 通过。
- 新用例验证批次上限、乱序确认、失败时等待同批收口且不继续 open、取消后不发后续片；
  保留压缩期间取消、已关闭拒绝与双片完成覆盖。
- 真实旧接收端、实际认证直连和接收暂存消费已验证。未测跨账号分享授权／供应商组转发、
  强制官方或自建 relay、弱网丢包、多个大上传同时竞争、UI 和真实模型停止。
- 没有声称跨网／所有设备统一加速。2 片的 1 MiB 上限是代码约束，不是实测全进程峰值内存。

## 复跑

需要同一账号的两台已在线 Cindy、已有授权连接，以及发送端开发版的本地 CDP。
用设备发现选择目标 ID；脚本只接收 ID 参数，不读取鉴权文件。目标已有任务不会被探针关闭。

```sh
node scripts/benchmarks/remote-agent-upload-live.mjs \
  --device=<目标设备ID> \
  --baseline=4538b647a6af841aed5c49f00fa96f581538f7b8 \
  --rounds=5 --out=/tmp/cindy-upload-live.json
```

默认 `serial,candidate`，两者均从指定基线取源码，候选只在临时打包时应用归档原型；窗口对比可追加 `--variants=serial,window2,window4`。
多个主窗口时指定 `--target=<CDP目标ID>`；脚本不自动选择模糊目标。
脚本不重放失败写操作；失败输出标记 `completed:false` 并保留已完成样本，不能把部分数据当完整运行。

```sh
CINDY_BENCH_UPLOAD_ONLY=1 node scripts/benchmarks/remote-agent-performance.mjs /tmp/cindy-upload-controlled.json
```

# Memory Search 多词召回与片段：召回、准确率与性能对比

基线 `6686200157`（短语零命中时拆词兜底），修改版 `7ef85bfe57`（多词按覆盖率过滤、片段改多窗口）。
2026-11-21 在同一台 Windows 机器上测试，Node v22.22.3，`better-sqlite3` 内存库。

结论：Top-k 召回基本不变，严格 Precision@5 从 63.5% 升到 87.0%，片段同时含全部查询词的比例
从 7.6% 升到 64.8%；查询延迟和 2000 × 6.4KB 合成语料的多词检索耗时没有系统性回退。

本报告只覆盖检索层 `MemoryFts.search`，不含真实用户记忆内容。查询由固定种子机械生成，用于
版本间对比，不代表线上用户查询的分布。

## 改了什么

- 拆词兜底臂加覆盖率门槛 `max(1, ceil(词数 / 2))`：先按命中词数降序，再按分数排序；全部低于
  门槛时退回未过滤结果，保证不归零。短语 MATCH、整串 LIKE、单词查询不受影响。
- 2 词查询门槛仍为 1，另加相对阈值：部分命中只有质量分不低于最高分 50% 时才保留，全词命中
  永远保留。该策略由本报告的 2 词数据选定。
- SQL 候选池先按 `matchedCount` 排序；粗排与召回统一用 LIKE 语义，大小写不同的高覆盖文档
  不会再在 500 候选截断前被算成低覆盖。
- 多词片段按每个正文命中词各取一段（前 24 / 后 36 字符，间隔小于 20 合并，最多 3 段），
  原文不超过 200 字，含 `<mark>` 不超过 240 字；单词/短语保持原来的 ±60/120 单窗口。
- 去掉 `score *= matched`：命中词数已是独立的第一排序键。

以上数据在 `7ef85bfe57` 测得。同 PR 内随后修掉三处边界，不改变召回架构，未重跑基准：

- LIKE 臂先排除 MATCH 已覆盖的行再按 `limit` 截断：否则靠前的重复行会占满名额，
  LIKE-only 子串命中拿不到「MATCH 满额时预留 1 个名额」。
- 合并窗口保留段内全部命中：缩预算时先压缩上下文，不再以首个命中为锚点截断而切掉
  已合并的关键词。
- 重复词按小写去重后再算覆盖率：`cache CACHE logs` 是 3 个词，不再是 5 个，大小写
  变体不抬高门槛。

## 测试口径

- **语料**：仓库 `docs/`、`packages/`、`apps/` 下的 Markdown，按段落切成 1929 个 800–7000 字符
  片段，平均 3779 字符。标题取首个 `#`，description 取首个非标题、非代码、非表格行。
- **查询**：固定种子 42、7、2026，每个种子 60 条。每条随机取一个源片段，从正文中文连续段里
  截 1–3 个 3–5 字词；词频限制 `df ≤ max(10, 语料数 × 5%)`；互相包含的词对丢弃。
- **期望答案**：查询来源的那个片段。
- **执行**：旧、新实现各自在独立的内存 FTS5 库上 `rebuild` 同一份语料，逐条查询交替先后顺序，
  都使用 `limit: 10`。共 180 条查询，其中 1 词 54 条、2 词 67 条、3 词 59 条。
- **指标**：
  - Recall@k：源片段是否出现在前 k 条；MRR：源片段排名的倒数。
  - Top-1 全词命中：第 1 条是否包含全部查询词。
  - Precision@5（严格）：前 5 条中包含全部查询词的比例。
  - Precision@5（达门槛）：前 5 条中命中词数达到 `ceil(词数 / 2)` 的比例。
  - 片段含全部查询词：返回片段的去标签文本是否包含所有词（只统计多词查询）。
  - 延迟：单条查询墙钟，p50 / p95 取排序后的 50% / 95% 位置。

| Recall@10 | 95.6% | 95.6% | 0 |

| Top-1 全词命中率 | 99.4% | 100.0% | +0.6pp |

## 性能

合成语料 2000 条 × 6413 字符，3 个词都在正文命中，`limit: 5`，新旧交替执行 15 轮取中位数。
另跑 3 组独立轮次观察机器热漂移：

| 场景 | 旧 | 新 |
| --- | ---: | ---: |
| 最小耗时（多轮） | 86.5–91.1ms | 85.6–95.1ms |
| 中位数（多轮） | 90–110ms | 91–124ms |

中位数的轮间波动大于两版差异，最小值基本持平；没有观察到系统性回退。真实混合语料上因为只
为最终返回的少量命中构建片段，p50 / p95 反而略低（50.3 → 49.0ms，85.5 → 82.9ms）。

## 已知限制

- 召回以「查询来源片段」为唯一正确答案。同一文档被切成多个片段时，命中同文档的其他片段也
  记为未召回，因此 Recall@10 的 4.4% 缺口包含这种切分噪声。
- 查询是机械截取的中文词，不是真实用户查询；没有人工相关性标注，严格 Precision@5 衡量的是
  「片段能否自证命中全部关键词」，不是「用户是否觉得相关」。
- 候选池上限 500 的取舍不变：候选之外的长正文高密度文档仍会被放弃。
- 多词片段最多 3 段。4 词以上且各词在正文中分得很散时，片段不保证包含每个词。
- 语料来自仓库文档，规模（1929 条）明显大于日常记忆库；本报告主要用于版本间对比，不代表
  小语料下的绝对表现。

## 复现

基准脚本是一次性 harness，未入库（需要同时导入旧提交的 `fts.ts`）。复现步骤：

1. 分别 checkout `6686200157` 与 `7ef85bfe57`，把旧 `fts.ts` 复制到新工作区并改名为独立模块。
2. 用 `better-sqlite3` 建两个内存库，各自 `MemoryFts.init()` + `rebuild()` 上方语料。
3. 按上文种子与词频限制生成查询，每条交替执行新旧 `search(query, { limit: 10 })`。
4. 用片段正文小写后判断命中词数，按上文公式聚合。

回归验证命令（修改版工作区，`packages/maker-core` 下）：

```bash
../../node_modules/.bin/vitest run src/memory/__tests__/fts.test.ts
../../node_modules/.bin/vitest run src/memory --exclude "**/*git-integration*"
../../node_modules/.bin/tsc --noEmit
../../node_modules/.bin/eslint src/memory/fts.ts src/memory/__tests__/fts.test.ts
```

结果：`fts.test.ts` 62 通过，`src/memory` 161 通过 / 1 跳过（排除既有的 git 集成用例），
`tsc` 与 `eslint` 通过。

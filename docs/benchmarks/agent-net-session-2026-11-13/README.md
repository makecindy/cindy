# Agent-Net 会话层基线（2026-11-13）

[Agent-Net 会话层方案](../../agent-net-session-plan.md) 阶段 0：在改动之前，量出现有 Device Link 经 Agent-Net 中转时，
大消息对小消息的阻塞、吞吐与卡死，并查清「速度跑不上去」的原因。之后的每个阶段用同样的脚本和线路档位对比。

> **勘误（同日）**：第一版数据用的限速器每块数据各用一个 `setTimeout`，在 Windows 上按 15.6 毫秒节拍触发，
> 零散的包每一跳多等 0–15 毫秒、连续的流却不会。这让本机回环的空闲往返从约 4 毫秒变成 62 毫秒，
> 并得出了「经中转吞吐只有 0.3–0.5 MB/s」的错误结论。限速器已改成和核心 Node 驱动一样的计时方式，
> 下文数据全部是修正后重测的；第一版的吞吐数字作废。

## 和原来的 Device Link 对比

同一环境、同样的线路档位，换成原来的 Device Link 中转（生产的自建中转内核 `@cindy/device-link-relay`，
设备不加签名，和经官方中转时一样）。表里是 1 MiB 大消息的耗时，两个方向都算；原来的 Device Link 各 2 轮，
Agent-Net 一列在两档每秒 1 MB 的线路上合并了基线与复测共 4 轮，其他档是基线的 2 轮。
原始数据见 [compare-device-link.json](compare-device-link.json)、[compare-agent-net.json](compare-agent-net.json)。

| 线路 | 原来的 Device Link | 经 Agent-Net 中转 |
|---|---|---|
| 不限速 | 0.04–0.05 秒 | 0.11–0.15 秒 |
| 每秒 1 MB | 1.36 秒 | 1.6–2.3 秒 |
| 每秒 1 MB + 0–30 毫秒抖动 | 1.41–1.46 秒 | 5.9–21.6 秒 |
| 每秒 250 KB | 5.45 秒 | 6.9–7.0 秒 |
| 每秒 64 KB | 21.6 秒 | 2 轮都卡死（卡死修复后 21–39 秒，见下文） |

**现在经中转的 Agent-Net 在每一档线路上都比原来的 Device Link 慢，也更不稳。** 差距最大的是有抖动的线路（慢 4–15 倍），
以及慢线路：原来的 Device Link 21.6 秒传完，没碰到 Device Link 自己 30 秒的确认超时；Agent-Net 更慢，超过 30 秒后触发强制重连并卡死。
小请求排在大消息后面的问题两边都有（原来的 Device Link 也是一条队列），只是原来的大消息传得快，等得短一些。

原因在结构上：没打通直连时，Agent-Net 的数据报装在 TCP（443 WebSocket）里经中转转发，速度上限就是这条 TCP，
再叠上核心自己的拥塞控制（抖动时误判排队，见下文）和 Device Link 的可靠层；原来的 Device Link 只有 TCP 加 Device Link 两层。
Agent-Net 要超过原来，前提是数据走 UDP（直连或 UDP 中转），再把核心的抖动误判和起速修好。

## 结论

1. **小请求要一直等到大消息传完。** 大消息在途时，小请求往返的最大值约等于大消息的总耗时：
   每秒 1 MB 的线路最长 1.9 秒，每秒 250 KB 最长 6.9 秒；空闲时分别是 0.09 秒和 0.21 秒。
2. **线路抖动会让速度掉到线路的一成以下。** 同样每秒 1 MB 的线路，加上 0–30 毫秒的随机抖动后，
   1 MiB 回传要 17–22 秒（只用到线路的 5%–6%），小请求最长等 21.5 秒。绕过 Device Link 直接写 Agent-Net 一样慢，
   问题在核心的拥塞控制，见「速度为什么跑不上去」。
3. **每次重新起速都慢。** 连接上一段时间没有大数据、或者刚在反方向传过大数据，下一次大传输要从很低的带宽估计
   重新爬升；没有抖动时第一次只用到线路的 33%–69%，同一连接接着再传才到 78%–92%。
   Cindy 的大数据（任务列表、历史、附件）本来就是一阵一阵的，几乎每次都落在起速阶段。
4. **慢线路上会卡死且不恢复。** 每秒 64 KB 一档 2 轮全部卡死：1 MiB 回传 180 秒仍未完成，期间 357 个小请求全部失败，
   线路上多传了 87%–90% 的字节；紧接着的上行测试一个字节都没发出。触发过程见「卡死复测」，
   2026-11-14 已修复，见「卡死修复后复测」。
5. **Device Link 不是吞吐的主因，但是「卡」的主因。** 连接已经起速后，经 Device Link 只比直接写 Agent-Net 慢 7%–18%；
   它的问题在于小消息排在大消息后面，以及大结果 30 秒传不完就强制重连。

## 速度为什么跑不上去

`packages/agent-net/bench/throughput-probe.ts` 在同一条限速线路上做对照：同样 1 MiB，经 Device Link 回传，
或绕过它直接作为一帧写进 Agent-Net 连接；每 100 毫秒采样线路字节、核心的往返和带宽估计。汇总见
[probe-summary.json](probe-summary.json)。

**Device Link 影响很小。** 同一连接连续传 4 轮（Desktop 独立线程形态，每秒 1 MB）：

| 走法 | 第一次（起速） | 之后几次 |
|---|---|---|
| 直接写 Agent-Net | 69% | 91%–92% |
| 经 Device Link | 38% | 78%–86% |

**抖动是主因。** 刚在反方向传完 1 MiB，再上传 1 MiB（每种 3 轮）：

| 线路 | 经 Device Link | 直接写 Agent-Net | 核心带宽估计 |
|---|---|---|---|
| 每秒 1 MB | 2.9–3.2 秒（33%–37%） | 2.8–3.1 秒（34%–37%） | 约 320–360 KB/s |
| 每秒 1 MB + 0–30 毫秒抖动 | 5.7–14.4 秒（7%–18%） | 6.1–11.3 秒（9%–17%） | 约 80–200 KB/s |

抖动下卡在低速的一轮（经 Device Link，第 3 轮）：14 秒里核心的带宽估计从 12 KB/s 慢慢爬到 109 KB/s，
一直没有接近线路的约 980 KB/s，实际发送速度约 75 KB/s；往返在 135–163 毫秒之间（基础往返约 83 毫秒）。

**原因（读代码确认）：** 核心把「这一轮的最小往返比最低往返高出一个余量」当成网络在排队
（`packages/agent-net-core/src/congestion.rs` 的 `queue_is_building`）。余量按往返的 1/16 或抖动的 3 倍算，
但限制在 4–16 毫秒之间（`queue_margin_us`）；抖动估计取相邻两个往返样本之差的平滑值。判定排队后：
- 巡航阶段只按估计带宽的 90% 发（`pacing_rate` 里的 `QUEUE_DRAIN_GAIN`）；
- 不认为窗口有余量（`window_has_room`）。

经中转时数据走 TCP，一个包慢了后面的都得等，相邻样本一起变大又一起变小，算出来的抖动偏小；
只要实际抖动超过约 16 毫秒，核心就一直以为在排队，发得越来越保守，带宽估计降到线路的一成左右。
已经起速、连续大流量时影响较小（同一连接连续传时 57%–80%），所以最伤的正是一阵一阵的业务数据。

这一结论来自本机限速代理里的人造抖动（每块数据随机多等 0–30 毫秒，保持先后顺序）。真实网络的抖动形态不同，
会不会同样触发、触发多少，要在真实线路上记录核心的往返、最低往返和带宽估计后才能确认。

## 卡死复测

为看清卡死过程，用 `--log` 在每秒 64 KB 档另跑 3 轮（这一组用的是第一版限速器，卡死的触发与限速器的计时误差无关，
修正后重测同样 2 轮全部卡死）。原始数据见 [very-slow-logged.json](very-slow-logged.json)，日志见
[压测汇总](very-slow-logged.json)。第 2 轮的时间线：

| 时刻 | 事件 |
|---|---|
| 67.0 s | 被控端收到大请求，把 1,051,170 字节的结果排进发往控制端的可靠队列 |
| 96.8 s | 控制端：`reliable transport ACK timeout; forcing reconnect ... seq=11 ... attempts=5 ... ageMs=30088 pending=14`。控制端发出的这条大请求本身很小，但被控端对它的确认排在 1 MiB 结果后面，30 秒内没回来；Device Link 判定超时，强制重连整个 Agent-Net 连接 |
| 96.8–246.7 s | 之后的小请求都没有写出（`firstWrite=none`），到 10 秒超时或报「队列已满」 |
| 246.7 s | 大请求 180 秒超时；控制端 `abandoning 14 stalled reliable frame(s) for peer a-host (link down > 60000ms)` |
| 257–283 s | 上行测试：一个字节都没发出，24 个请求全部报「队列已满」 |

由此可以确定：
- **触发条件是确定的。** 只要大结果在一个方向上 30 秒内传不完，另一方向请求的确认就会超时，触发强制重连。
  起速慢和抖动都会把传输拉长，让这个条件更容易满足。
- **重连之后为什么恢复得慢（2026-11-14 查清）。** 控制端重建的是整个 Agent-Net 节点；被控端还拿着旧连接，
  按「同时拨号只留首选拨号方」的规则拒收控制端的新连接，直到旧连接约 30 秒后超时才接受（复测日志：
  38.8 秒强制重连，68.9 秒被控端判定旧连接断开，69.3 秒立即接上新连接）。其间控制端的请求名额被旧请求占满。
  上面这组日志是对照环境不会自动重新建链时录的，所以拖到 188 秒；加上 Desktop 正式代码在请求前重新建链的步骤后，
  恢复点就是旧连接超时的那一刻。

## 卡死修复后复测（2026-11-14）

修复内容见 [远程与手机适配](../../dev-rules/remote-and-mobile-adaptation.md)「Agent-Net 上单个对端的确认超时」：
Agent-Net 下单个对端确认超时不再重建整个节点，对端仍在送数据时继续等确认；对端换了端点再拨进来时立即换用新连接。
对照环境同时补上了 Desktop 在请求前重新建链的步骤，小请求用生产默认的 30 秒超时（`--prod-timeouts`）。
原始数据见 [stall-fix.json](stall-fix.json)、[stall-fix-regression.json](stall-fix-regression.json)。

| 每秒 64 KB 的线路 | 修复前 | 修复后（3 轮） |
|---|---|---|
| 卡死 | 7 轮里 5 轮卡死，3 分钟内不恢复 | 没有卡死 |
| 回传 1 MiB | 180 秒超时 | 21–39 秒完成 |
| 上传 1 MiB | 一个字节都没发出 | 27 秒完成，全部成功 |
| 小请求 | 全部失败 | 有 2 轮各 13 个排在大消息后面超过 30 秒而超时，其余成功 |

日志里在 38.7 秒记了 `reliable transport ACK delayed behind peer traffic; keeping link`，没有再强制重连。
每秒 1 MB 与每秒 250 KB 的线路各复测 1 轮，结果与修复前相同（1.66–1.91 秒、7.04–7.09 秒）。
小请求排在大消息后面的问题仍在，要靠会话层解决。

## UDP 中转与核心起速后复测（2026-11-14）

两项改动，都按方案的顺序做：

1. **中转走 UDP**（阶段 1，[协议记录](../../dev-rules/protocol-compatibility/agent-net-udp-relay.md)）。
   对照环境新增 `udp-relay` 方式：同样经中转，但中转转发走它的 UDP 端口；本机回环上只交换公网候选地址，不会打通直连。
   每台设备到中转的 UDP 和 TCP 共用同一条限速线路，排不下时尾部丢弃。下表 `udp` 一列确认大消息方向的字节全走了 UDP，
   全程没有尾部丢弃。
2. **核心起速**（阶段 2，[核心验证记录](../../../packages/agent-net-core/sim/results/2026-11-14-bursts/README.md)）：
   空闲后不再误判限速，零星包与不乱序的抖动不再提前结束启动，Desktop 的收发窗口从 128 改为 1024 个分片。

原始数据：只加 UDP 中转时见 [udp-relay.json](udp-relay.json)，两项都做后见 [core-fix.json](core-fix.json)，各 2 轮。
1 MiB 耗时（毫秒，两轮平均，回传 / 上传）：

| 线路 | 原来的 Device Link | Agent-Net 经 TCP 中转（改动前，见上表） | 只加 UDP 中转 | UDP 中转 + 核心起速 | TCP 中转 + 核心起速 |
|---|---|---|---|---|---|
| 不限速 | 61 / 68 | 110–150 | 153 / 135 | 154 / 138 | 164 / 140 |
| 每秒 1 MB | 1371 / 1373 | 1600–2300 | 2265 / 2127 | 1678 / 2055 | 1474 / 1765 |
| 每秒 1 MB + 0–30 毫秒抖动 | 1445 / 1445 | 5900–21600 | 15706 / 13095 | **1811 / 1795** | 1807 / 3022 |
| 每秒 250 KB | 5457 / 5463 | 6900–7000 | 7284 / 6248 | 7303 / **4804** | 6660 / 5381 |
| 每秒 64 KB | 21600 / 21693 | 卡死（修复后 21–39 秒） | 19403 / 23709 | **18389 / 18462** | 18042 / 18358 |

- **只加 UDP 中转，速度没变。** 每秒 1 MB 的线路上仍是 2.1–2.3 秒，抖动线路仍要 13–16 秒：卡速度的是核心，
  和「速度为什么跑不上去」的结论一致。UDP 去掉了 TCP-in-TCP，是核心修好以后才发挥得出来的前提。
- **核心修好后，抖动线路从 13–16 秒降到 1.8 秒**，离原来的 Device Link（1.4 秒）还差约 25%；
  每秒 64 KB 的线路上 18.4 秒，比原来的 Device Link（21.6 秒）快约 15%，两轮都没有失败。
- **还没全面超过。** 每秒 1 MB 的线路上同一种方式两轮之间常差到 1.3 秒对 2.0 秒，慢的那几轮小请求往返中位数约 0.5 秒，
  说明它们排在大消息后面；每秒 250 KB 的回传比原来的 Device Link 慢 1.2–1.8 秒，上传反而快 0.1–0.7 秒。
  这些都在 Device Link 叠在 Agent-Net 上的那一层：所有请求走一条有序队列，加上它自己的确认与重发。
  模拟器里核心本身在同样的线路上跑到 95%（1.1 秒），差距要靠会话层（阶段 3）拿掉。
- **不限速的本机回环上仍慢 2–3 倍**（140–160 毫秒对 61–68 毫秒）。这时没有网络瓶颈，耗时在独立线程、WASM 加密和逐包处理上，
  和线路无关，留待会话层之后单独看 CPU。
- 每格只有 2 轮，单轮之间差别不小，表里的差距在 10% 以内的不能当作结论。

## 自动窗口后全面对比（2026-11-14）

在上一节两项之后又做了两项：

1. **窗口和发送缓冲跟着线路放大**（[核心验证记录](../../../packages/agent-net-core/sim/results/2026-11-14-auto-window/README.md)）：
   Desktop 的收发窗口改成只按内存定的上限 8192 个分片，实际在途量由拥塞控制按实测「带宽 × 往返」决定；
   每条流的发送缓冲跟着拥塞窗口放大（两倍，1–24 MiB）。
2. **积压回落时立即续写**：Device Link 被发送水位挡住的大帧，不再等 250 毫秒到 2 秒的重试定时器。
   （之后撤回：用户决定 Agent-Net 自建独立的上层，Device Link 保持原样，见方案 10.1 节。）

线路档位新增 `wide`（家宽 100 Mbit/s，端到端往返约 32 毫秒）和 `far`（跨地区 50 Mbit/s，往返约 200 毫秒），见「方法」。
三种方式：`v1` 原来的 Device Link 中转，`worker` Agent-Net 经 TCP（443 WebSocket）中转，`udp-relay` Agent-Net 经 UDP 中转。

两张表的所有格子都没有失败、没有卡死；小请求往返的最大值在三种方式下都约等于大消息耗时（还是一条有序队列，阶段 3 的事）。

- **慢线路上已经超过。** 每秒 64 KB 两种 Agent-Net 都比原来快约 15%（1 MiB 18.2–18.7 秒对 21.6 秒，分块利用率 86%–88% 对 75%–76%）；
  每秒 250 KB 的 UDP 中转分块传输 89%–90% 对 85%，1 MiB 上传 4.8 秒对 5.5 秒。
- **每秒 1 MB 追平。** UDP 中转的 1 MiB 两个方向都是 1.33 秒，原来 1.37 秒（上一节 1.7–2.1 秒）；分块利用率从约 64%–74% 升到 87%–88%，
  原来是 95%。抖动线路上 1 MiB 还慢约 25%（1.8 秒对 1.4 秒），和上一节一样。
- **快而远的线路差距最大。** 跨地区线路上 1 MiB 要 1.3 秒，原来 0.47 秒；分块传输只用到 18%–44%。绕过 Device Link 直接写 Agent-Net
  （`throughput-probe.ts`，[probe-far-wide.json](probe-far-wide.json)）同样要 0.72–0.79 秒，理想值约 0.37 秒：卡在核心长往返上的起速，
  不在 Device Link。模拟器里同类线路（50 Mbit/s、往返 200 毫秒）空闲后 1 MiB 也只用到 13%–36%，见核心验证记录「没做的」。
- **这一档对原来的 Device Link 偏宽。** 限速代理对 TCP 是「排满就暂停读取」，不丢包；发送方的 TCP 只和本机代理握手，
  看到的往返是本机回环，不用按 200 毫秒的往返慢启动。真实网络里 TCP 经长往返线路同样要起速，空闲后还会重新慢启动；
  UDP 代理则是排满就丢。远距离、高带宽两档的差距有一部分来自这里，要在真实线路上确认。
- **不限速和家宽两档受 CPU 限制，这一轮不能当结论。** 两台设备、中转和代理都在同一个进程里，Agent-Net 每个包都要加密，
  这一轮测试时机器上另开着游戏和别的任务的类型检查：测完再跑同样的 8 MiB 回环只有 1.9–2.1 MB/s，上午空闲时是 6–7 MB/s。

## 每个包的处理开销（2026-11-14）

在不限速的回环上给会话层的分块传输采样（`node --cpu-prof`，压测进程里跑着两台设备，网络在单独的进程里）：

- **收数据反复拼接**：会话层每收到一片就把还没收齐的帧整个复制一遍，一个 512 KiB 的结果分几百片到，复制量和帧长的平方成正比，
  占了忙碌时间的 18%。改成先存下各片、收齐一帧再拼一次（`session/lanes.ts`；帧落在一片里时不复制）。
- **剩下的都是每个包的固定成本**，和代码写法关系不大。这台机器上每个包：AES-GCM 加密或解密约 3.3 微秒，其中 2.7 微秒是调用本身
  （Node 没有可复用的 GCM 对象，每个包都要新建一个；0 字节也要 2.7 微秒）；Windows 上发一个 UDP 包约 5.7 微秒，几乎全是系统调用，

  三项都没改。核心用 1400 字节的包，已接近普通网络上 UDP 的上限，再靠加大包减少包数的余地不大。

## 两台电脑隔离验收（2026-11-14～15）

Desktop 接入会话层以后（默认关），在两台真实电脑上验收：Windows 测试机用隔离沙箱 `anbench-ml`，macOS 测试机用隔离沙箱
`anbench-xd`，同一账号，都设 `CINDY_AGENT_NET_SESSIONS=1`，代码相同（基线 `b339cf829d` 加本次改动，网络核心校验值一致）。两台不在同一网络，
经中继连接。用户正在用的 Cindy 不参与。Windows 测试机 作为控制端，在界面上打开 macOS 测试机 上的任务、发消息。

| 项目 | 结果 |
|---|---|
| 会话建立 | 两端连上后 39 毫秒会话就绪 |
| 建链 | 经会话层，20–60 毫秒拿到对方接受 |
| 打开远端任务 | 历史、订阅与内容快照经会话层恢复，25–335 毫秒 |
| 发消息 | macOS 测试机 上执行，回复「PONG」与运行事件实时推回，侧栏同时更新；这段时间发往 macOS 测试机 的 Device Link 链路记录为 0 |
| 对方重启 | 会话立即关闭（`DEVICE_OFFLINE`），期间的调用很快返回「对方离线」不卡住；对方回来后 29 毫秒自动经会话层重新建链，内容 134 毫秒恢复 |
| 过夜 | 两端空闲时连接按需收起，00:32 官方中转短暂 502/503/504，约 12 秒后自动恢复，没有卡死 |

验收中发现并修正（都已补回归用例，去掉修正时失败）：

- **几乎从不走会话**：选路原来只要 Device Link 上有在途请求就不换路，而业务一连上就先发列表再建链。改为只在 Device Link 链路就绪、等恢复或有待发消息时不换路。
- **同一对电脑混走两条路**：列表、探测先经 Device Link 发出，对方的 Device Link 还记着之前的可靠链路，把结果放进本机已经没有的链路，
  59 秒后超时、再引发重开。改为会话可用、Device Link 空闲时，建链和所有调用都走会话，一个对端只走一条路。
- **包装层的身份比较**：入口里有「`connectionFor(peer) === client`」这类比较，包一层以后原客户端返回的是它自己，比较全反了
  （影响中继断开时停哪些控制端、传输超时重开、诊断快照）；「`client === routedClient`」让跨账号分享的绑定在开关打开时不执行。
  改为原方法返回它自己时换成包装层，绑定判断和实际交出的对象比。
- **macOS 上开关没生效**：开发版重启脚本在新开的 Terminal 里只转发白名单里的环境变量，补上 `CINDY_AGENT_NET_SESSIONS`。
- **刚连上时的选路空窗**（验收没碰上，按推演补上）：对方刚连上、会话还没就绪的几十毫秒里如果正好建链，会落到 Device Link，
  并一直用到这条链路断开。改为这段时间里 Device Link 上又没有它的链路时先等会话，最多到连接建好后 250 毫秒 + 4 个往返
  （往返未知时 1.5 秒）。补上后再让 macOS 测试机 重启一次：连接经中转建好（22:34:43.143），38 毫秒后会话就绪，再过 47 毫秒建链走会话、
  85 毫秒建好；macOS 测试机 离线期间的建链不等，照旧 27 毫秒报离线。

还没做：
- 反方向（macOS 测试机 控制 Windows 测试机）没在界面上走一遍；两端是同一份代码，被控端这一侧已由 macOS 测试机 验证。
- 远程桌面：macOS 测试机 的隔离开发版回复「不可用」，界面显示「无法连接远程桌面」，走 Device Link 时一样，与会话层无关。

  三到五成，每轮送到的都比估计少一点，估计跟着一轮轮往下掉。不夹小请求、绕过 Device Link 直接写 Agent-Net 连接
  （`--raw`，443 中转）也只有回传 7.9、上传 10.4，核心在这条线路上本身也还没跑满。两件都在核心里做。

## 核心修正后真实网络复测（2026-11-16）

同一对电脑、同一条线路（`--no-line`，夹着小请求，每次 20 MiB），核心里先后做了三件事
（[核心验证记录](../../../packages/agent-net-core/sim/results/2026-11-16-jitter-window/README.md)）。每秒 MB，括号里是小请求最长往返（毫秒）：

|---|---|---|---|
| 改之前（上一节） | 4.9 / 6.5（30） | 5.1 / 7.0（29） | 14.1 / 14.1、2.2 / 1.5 |
| ① 抖动线路上低排队模式不再越发越慢 | 7.3 / 7.3 / 7.5（29） | 7.2 / 5.2 / 6.0（72） | 11.9 / 9.6 / 10.9、2.0 / 12.7 / 1.5 |

| ③ 再加：低排队模式的加速探测连着成功时加大 | **12.2 / 13.6 / 15.9 / 15.2**（35） | **14.6 / 17.5 / 8.3 / 9.9**（35） | （同②） |

原始数据 [real-network-after-core-taps.json](real-network-after-core-taps.json)、
[real-network-after-mtu-taps.json](real-network-after-mtu-taps.json)、[real-network-after-esc-taps.json](real-network-after-esc-taps.json)。
这条线路当天比前一天慢一些（原来的 Device Link 回传 14 → 10.5–13.3）。三件事之后会话层回传快过原来的 Device Link，

- **① 之后带宽估计不再往下掉。** 采样（`--sample`）里带宽估计整段停在每秒 8.3–8.8 MB，不再从 7.3 掉到 2.3。但普通模式
  （不夹小请求）也只有 7.1–7.9，绕过上层直接写 Agent-Net 连接也只有 7.1–7.8：核心在这条线路上的速度到顶了。
- **② 找到另一半：包太长。** 往返随在途量涨到 40–58 毫秒（按利特尔定律，瓶颈约每秒 9 MB），而同一条线路上 UDP 回显
  （1200 字节）每秒 14 MB 往返仍是 10 毫秒。换包长量（每秒 12 MB，往返 p50 / 最长，丢包）：1330 字节 11 / 45 毫秒、0%；
  1350 字节 11 / 29 毫秒、0%；1372 字节 11 / 85 毫秒、0.3%；**1400 字节 184 / 223 毫秒、31.8%**。1400 字节每秒 9 MB 就丢 6%、
  往返 157 毫秒。核心原来每个包 1400 字节，经 UDP 中转还要加 33 字节：隧道里每个包被拆成两片。TCP 由隧道按 MSS 截短，不受影响。

  （[协议记录](../../dev-rules/protocol-compatibility/agent-net-send-packet-size.md)）。
- **③ 起步低了能很快爬回来。** ②之后一次采样里回传到每秒 19.8 MB，但上传那一段启动在每秒 4.1 MB 就结束了，低排队模式每次只加 5%、
  8 轮一次，1.8 秒才到 6.5 MB。改成探测连着成功时 5% → 10% → 20% → 25%，贴着容量时照样只加 5%。

## 方法

- **入口**：生产代码 `AgentNetWorkerSocket`（Desktop 使用的独立线程加 Main 代理）、真正的 `DeviceLinkClient`
  （生产默认计时，不覆盖重发与超时）、本机起的 V2 中转。UDP 关闭，所有数据经 443 WebSocket 中转。
  对照实验另跑当前线程形态（`AgentNetSocket`），能读到核心的完整统计。
- **线路**：每台设备与中转之间插一个限速代理（`packages/agent-net/bench/harness.ts`），按速率排队、加单程延迟；
  排队超过上限时暂停读取，让发送方的 socket 真实堵住。不模拟丢包。

  | 档位 | 每个方向的速率 | 设备到中转的单程延迟 | 抖动 | 排队上限 |
  |---|---|---|---|---|
  | unshaped | 不限 | 0 | 无 | 64 MiB |
  | fast | 1 MB/s | 20 ms | 无 | 256 KiB |
  | fast-jitter | 1 MB/s | 20 ms | 0–30 ms | 256 KiB |
  | slow | 250 KB/s | 50 ms | 无 | 128 KiB |
  | very-slow | 64 KB/s | 100 ms | 无 | 64 KiB |
  | wide | 12.5 MB/s | 8 ms | 无 | 500 KiB |
  | far | 6.25 MB/s | 50 ms | 无 | 625 KiB |

  `wide`、`far` 是 2026-11-14 加的，只用于全面对比；UDP 中转（`udp-relay`）的代理排满时丢掉尾部，TCP 的代理暂停读取。

- **场景**：每轮新建网络，依次跑三种场景。
  - idle：每 500 ms 一个小请求，共 10 个。
  - down：被控端回传一条 1 MiB 结果；同时每 500 ms 一个小请求，直到大消息完成后再多 2 秒。
  - up：控制端发出一条 1 MiB 请求，其余同 down。

  小请求用交互类通道名 `maker:input:stop`，大消息用 `local-db:sessions:list`；被控端只回显，不执行业务。
- **指标**：小请求往返（控制端发出到收到结果）；到达被控端的时间（两端在同一进程，同一时钟）；
  大消息耗时；大消息方向的线路字节除以业务字节。
- **环境**：Windows x64，Node v24.22.1，源码基线 `b339cf829d`，非独占机器。每档 2 轮。

复跑（仓库根目录）：

## 证据边界

- 只在本机回环运行，限速代理模拟接入线路的速率、延迟、排队和人造抖动，不模拟丢包和真实中转的部署位置；
  数字不能直接当作真实网络的指标。真实线路的对比口径见方案第 11 节。
- 每档只有 2 轮（对照实验 3–4 轮），只适合看趋势和现象，不适合看精确值。
- 只覆盖 Desktop 的两种传输形态；手机原生路径、跨账号分享和自建中转没有覆盖。
- 抖动是人造的；真实网络里核心是否同样被拖住，需要在真实线路上记录核心统计后确认。卡死后不恢复的根因尚未定位。
- 测试时这台机器上另有程序占满了虚拟内存的提交额度（物理内存仍有余量）。基准本身运行正常，但不能排除数字受到机器负载影响。
- 限速代理对 TCP 不丢包、暂停读取，发送方的 TCP 不经历长往返上的慢启动；原来的 Device Link 在 `wide`、`far` 两档的数字是理想上限。
- 两台设备、中转和代理在同一个 Node 进程里，CPU 是共享的：不限速和高带宽档位量到的是本机处理能力，不是协议上限。

# Agent-Net 与 Device Link 详细对比（2026-11-16）

[Agent-Net 会话层方案](../../agent-net-session-plan.md) 的总目标：速度和稳定性全面超过 Device Link，并且不再出现消息拥堵。
这一份在网络层改完之后，用同一套压测把三种连法放在一起比：

- **原来的 Device Link**：经官方中转（443 WebSocket，TCP），所有消息排在一条可靠队列里。压测里叫 `v1`。
- **Device Link 经 Agent-Net**：打开 Agent-Net、不开会话层时产品走的路。Device Link 的帧装进 Agent-Net 连接，经 UDP 中转。压测里叫 `udp-relay`。
- **会话层**：Agent-Net 自己的上层（测量时 Desktop 设 `CINDY_AGENT_NET_SESSIONS=1` 才用；2026-11-16 起跟着「Agent-Net (Beta)」开关，
  两台都打开、都是新版就用）。两台节点之间一条加密连接，
  分三条流：控制与交互、普通、后台。压测里叫 `worker-session`，和 Desktop 一样跑在独立线程里。

代码是本轮最终版本：核心指纹 `93a4d821a905`（[核心验证记录](../../../packages/agent-net-core/sim/results/2026-11-16-jitter-window/README.md)），
预编译核心 `prebuilt/core.wasm` 364826 字节。

## 先看结论

| 方面 | 原来的 Device Link | 会话层 | 结论 |
|---|---|---|---|
| 大数据在传时，小请求最长等多久（真实线路） | 0.6–4.7 秒 | 35–41 毫秒 | **拥堵解决了** |
| 大数据在传时，小请求最长等多久（本机慢线路） | 每秒 250 KB 时 9.3–11.5 秒，每秒 64 KB 时 21 秒 | 0.28 秒、0.95 秒 | 只多一两个往返，不再等到传完 |
| 真实线路纯传大数据（回传 / 上传） | 9.2 / 7.1 MB/s | **19.0 / 17.9 MB/s** | 约 2 倍、2.5 倍 |
| 真实线路边传边交互（回传 / 上传） | 9.8 / 4.2 MB/s | **11.3 / 11.1 MB/s** | 回传略快，上传 2.6 倍 |
| 单条 1 MiB（真实线路，回传 / 上传） | 240 / 220 毫秒 | **163 / 176 毫秒** | 快两到三成 |
| 慢线路（每秒 250 KB、64 KB） | 线路的 86%–92%、76%–77% | **92%、87%–91%** | 持平或更快 |
| 快线路（家宽 12.5 MB/s、每秒 1 MB） | 线路的 89%–96% | 89%–93% | 差 3–7 个百分点，主要是每个包多 5% 包头 |
| 跨地区（往返 200 毫秒） | 线路的 83%–84% | 68%（边传边交互）、75%–78%（纯传） | **还落后**，见「还没超过的地方」 |
| 往返很短（本机回环，局域网直连同理），纯传 | 31 / 26 MB/s | 20 / 17.5 MB/s（边传边交互时 34 / 27） | **还落后** |
| 卡死、失败 | 慢线路上大结果 30 秒传不完会强制重连、卡死（已修） | 本轮所有轮次没有失败、没有卡死 | 更稳 |
| 对方正常退出后多久知道（两台已直连） | 经中转，中转马上通知 | 4 毫秒（本轮修复前 30 秒） | 修好了 |
| CPU（同一进程两端合计，每 MiB） | 50–90 毫秒 | 真实线路 93–150 毫秒，每秒 1 MB 时 220–280 毫秒 | **仍比 Device Link 高** |

一句话：**会话层把「小消息被大数据堵住」这件事彻底解决了**，真实线路上的速度是原来的 2 倍以上；
慢线路更快、快线路持平略低；长往返线路和 CPU 还落后。

## 1. 真实线路（两台电脑之间）

中转放在办公室的 macOS 测试机 上（`network-process.ts --listen`，`--no-line` 不加任何限速），两台设备都在家里这台 Windows 电脑的压测进程里，
数据每次都要从家里经公司 VPN 到办公室、再回来：ping 往返 10–24 毫秒，没有丢包，抖动明显。每次 20 MiB、每块 512 KB、同时 4 块
（远程任务上传附件就是这么传的）；三种连法按轮交替，各 5 轮（`--interleave`）。每秒 MB 是中位数（括号里是最低–最高）。

**纯传大数据**（[real-bulk-notaps.json](real-bulk-notaps.json)）：

| 连法 | 回传 | 上传 | CPU 每 MiB（毫秒） |
|---|---|---|---|
| 原来的 Device Link | 9.2（6.0–10.5） | 7.1（2.9–9.8） | 52 / 58 |
| Device Link 经 Agent-Net | 6.9（5.8–7.9） | 3.3（3.2–3.4） | 205 / 193 |
| **会话层** | **19.0（18.1–20.4）** | **17.9（13.6–20.2）** | 98 / 93 |

**边传边交互**：传的同时每 500 毫秒发一个交互类小请求（`maker:input:stop`），看它的往返
（[real-bulk-taps.json](real-bulk-taps.json)；小请求往返是中位数 / 最长，毫秒）：

| 连法 | 回传 | 上传 | 小请求：回传时 | 小请求：上传时 |
|---|---|---|---|---|
| 原来的 Device Link | 9.8（5.6–10.7） | 4.2（1.5–6.9） | 161 / 586 | 528 / 4720 |
| Device Link 经 Agent-Net | 11.8（10.4–12.3） | 1.2（1.0–1.3） | 139 / 262 | 1622 / 4632 |
| **会话层** | **11.3（9.0–13.4）** | **11.1（6.0–17.6）** | **29 / 41** | **29 / 35** |

**单条 1 MiB 与空闲时的小请求**（`session-latency.ts`，每轮三种连法各起一次进程、交替 5 轮，[real-latency.json](real-latency.json)；毫秒）：

| 连法 | 空闲时小请求中位 / 最长 | 回传 1 MiB | 上传 1 MiB | 1 MiB 在途时小请求最长 |
|---|---|---|---|---|
| 原来的 Device Link | 29 / 135 | 240（214–287） | 220（199–414） | 202 / 315 |
| Device Link 经 Agent-Net | 26 / 90 | 191（156–226） | 188（165–362） | 126 / 256 |
| **会话层** | **25 / 97** | **163（127–200）** | **176（135–404）** | **83 / 79** |

空闲时三种的最长值都在 90–135 毫秒，是线路自己偶尔的停顿；会话层在 1 MiB 在途时的最长值不比空闲时高。

- **当天别的时段也是这个比例**：下午几次同一时段交替对比（[driver-timer-ab.txt](driver-timer-ab.txt)）里，原来的 Device Link 纯传回传
  每秒 8.8–11.6 MB、上传 3.4–7.5 MB，会话层回传 17.0–19.3、上传 18.5–19.5 MB（各段的平均）。线路一天里在变：同样的压测，Device Link 的小请求最长
  有的时段是 0.2 秒，有的时段到 0.4 秒，所以只比同一时段交替跑出来的数字。
- **边传边交互时会话层的回传让了速度**：小请求走交互流时，核心进「低排队模式」，只在瓶颈上留很少的队，小请求才能一直是二三十毫秒。
  这条线路抖动大，低排队模式下回传每秒 9–13 MB，不交互时 18–20 MB。Device Link 经 Agent-Net 的回传（普通模式）更快一点，
  代价是小请求要排在队后面（最长 0.26 秒），上传时它的小请求等到 4.6 秒。低排队模式只在用户真的发了交互操作（停止、输入）之后 1 秒内打开，
  平时传大数据走普通模式，就是上面「纯传」那一行。
- **上传以前慢在 Device Link 自己发请求的方式上**：原来的 Device Link 上传通常每秒 3–4 MB，偶尔 9–12 MB，和线路方向无关；
  会话层两个方向一样快。

- **慢线路会话层更快**：每秒 250 KB、64 KB 两档用到线路的 87%–92%，原来的 Device Link 76%–92%；单条 1 MiB 快一到两成。
  小请求最长从 5–21 秒（等到传完）降到 0.3–1.3 秒（一两个往返）。
- **家宽、每秒 1 MB 两档差 3–7 个百分点**：会话层每个包多约 5% 包头（见第 4 节），按线上字节算两者一样满。
  单条 1 MiB 会话层反而快一点（家宽 158 对 165 毫秒，每秒 1 MB 1.2 对 1.4 秒）。
- **不限速一档量的是本机处理能力**：两台设备和中转都在这台电脑上。纯传时会话层 20 / 17.5 MB/s，原来的 Device Link 31 / 26 MB/s；
  边传边交互时会话层 34 / 27 MB/s。普通模式的窗口只按「带宽 × 最小往返」留两倍，本机往返不到 1 毫秒、确认又一批一批地到，窗口先卡住了；
  低排队模式另加了确认成批到达的量。试过普通模式也加：纯传 20 → 24–27 MB/s，家宽、跨地区不变。这一轮没有留：它改的是所有连接的普通模式，
  要重跑核心全部矩阵，而局域网直连还没在两台电脑上测过。
- **跨地区、每秒 1 MB + 抖动两档落后**，见第 5 节。
- **Device Link 经 Agent-Net 的上传在快线路上很慢**（家宽 10%–25%、跨地区 17%–34%，不限速 1–4 MB/s）。这是现在打开 Agent-Net、
  不开会话层时产品走的路；会话层两个方向一样快。

## 3. 稳定性

- **本轮所有轮次没有一次失败**：真实线路 60 次大传输（5 轮 × 3 种连法 × 2 个方向 × 有无小请求）、45 次延迟测试，本机 168 次分块传输、126 次延迟测试，三种连法的请求和小请求都没有失败、没有超时。
- **不再因为大结果传得慢而卡死**：原来的 Device Link 只有一条可靠队列，大结果在一个方向上 30 秒传不完，另一个方向请求的确认就排在后面超时，
  触发强制重连；2026-11-14 之前经 Agent-Net 时每秒 64 KB 的线路 7 轮里 5 轮卡死、3 分钟不恢复
  （[卡死复测](../agent-net-session-2026-11-13/README.md#卡死复测)）。那次修了 Device Link 经 Agent-Net 时的超时处理；
  会话层的确认在核心里、按流各自交付，没有「请求的确认排在大结果后面」这回事，每秒 64 KB 的线路上 1 MiB 照样传完，小请求一直有回音。
- **对方重启、重连**：两台电脑隔离验收时（[记录](../agent-net-session-2026-11-13/README.md#两台电脑隔离验收2026-11-1415)），
  连接建好后 39 毫秒会话就绪；对方重启时会话立即关闭，期间的调用马上返回「对方离线」不卡住；对方回来后 29 毫秒自动重新建链，内容 134 毫秒恢复；
  过夜官方中转短暂 502/503/504，约 12 秒自动恢复。刚连上、会话还没就绪的几十毫秒里建链会先等会话（最多 250 毫秒 + 4 个往返），不再落到 Device Link 上一直用下去。
- **新旧版本互通**：本轮改了发包上限（发包不超过 1350 字节，收包上限仍是 1400），旧版和新版互相能收；核心的模拟器用例覆盖了谁发起、
  换不换网、丢包时校验包恢复满长度分片（[协议记录](../../dev-rules/protocol-compatibility/agent-net-send-packet-size.md)）。
- **两台电脑上新旧互通**（同上两台电脑的隔离沙箱，用户自己的 Cindy 不参与）：本机先换成本轮代码、macOS 测试机 仍是旧版时，重连后 37 毫秒会话就绪，
  建链经会话层 22 毫秒打开；macOS 测试机 也换成本轮代码后，它重启回来 37 毫秒会话就绪，60 毫秒内建链走会话层、13 毫秒打开，离线那段时间的建链马上返回「对方离线」。
  经会话层的调用一来一回正常（远程桌面一项照旧回「不可用」，是隔离开发版的已知情况，走 Device Link 时一样）。
- **反方向验收：macOS 测试机 控制这台**（同上两台电脑的隔离沙箱，经开发版的调试端口在界面上点击、输入、截图；这一轮两台已经打洞直连，往返 9 毫秒）：
  - 在 macOS 测试机 的新建页选「Windows 测试机」（只列出允许它控制的那台，即测试沙箱），发一条消息：这台收到准备请求和新建任务，回复 PONG，工作 3 秒。
    这台处理供应商列表、新建任务各用了 2.0、2.5 秒（刚启动，业务侧的冷启动），网络这一段不慢，走 Device Link 时也经过同样的处理。
  - 上传 4 MiB 附件：这台收到的文件和原文件逐字节相同（SHA-256 一致）。附件本体走产品原有的点对点文件通道，建通道的能力查询和连接信息经会话层，
    连接信息 251 毫秒，4 MiB 约 0.4 秒传完。
  - macOS 测试机 重启后重新打开这条任务，历史（消息、附件、回复）从这台完整加载回来。
  - 这台重启：**修复前 macOS 测试机 过了 30.0 秒才判断它离线**，期间的建链还选了已经断掉的会话。原因是端点关闭时发出关闭包后马上关了套接字，
    UDP 发送还没完成就被取消（Windows、macOS 都是）；之前正向验收时两台经中转连接，中转会通知对端，所以没碰到。修复后同一场景 4 毫秒判断断开，
    界面马上显示「远程设备已离线」，期间的请求 3 秒内返回「对方离线」；这台回来后同一毫秒自动重新建链，新消息照常回复。
    修复与三问见 [远程与手机适配](../../dev-rules/remote-and-mobile-adaptation.md)「Agent-Net 关闭时告诉直连的对端」。
- **跟着「Agent-Net (Beta)」开关**（2026-11-16，两台都不设开发期的环境变量）：开着时建链走会话、发消息回复 PONG；在设置里关掉以后这台改走 Device Link，
  同一条任务照常回复；再打开，不用重启应用，1 秒内重新连上、36 毫秒后会话就绪。关开关时发现 worker 线程被直接结束、关闭包又没发出去，已一并修好
  （见 [远程与手机适配](../../dev-rules/remote-and-mobile-adaptation.md)「Agent-Net 关闭时告诉直连的对端」）。
- **核心的矩阵没有变差**：和上一轮比，单连接对比 64 行用时几何平均不变、没有一行变化超过 1%，共享矩阵三份逐行相同；核心 137 个用例、Agent-Net 67 个用例、Desktop device-link 2350 个用例通过；
  本轮新增的变异全部抓到（[核心验证记录](../../../packages/agent-net-core/sim/results/2026-11-16-jitter-window/README.md)）。

## 4. CPU 与线路开销

**CPU**（压测进程的用户态加内核态时间除以传的 MiB，两台设备和压测本身都在这一个进程里，所以是两端合计）：

| 线路 | 原来的 Device Link | Device Link 经 Agent-Net | 会话层 |
|---|---|---|---|
| 真实线路纯传 | 52–58 | 193–205 | 93–98 |
| 真实线路边传边交互 | 60–73 | 173–226 | 134–149 |
| 本机不限速（边传边交互） | 45–52 | 132–162 | 57–78 |
| 本机家宽（边传边交互） | 49–54 | 220–264 | 157–170 |
| 本机跨地区（边传边交互） | 45–67 | 327–370 | 244–283 |
| 本机每秒 1 MB（边传边交互） | 63–98 | 295–340 | 211–281 |
| 本机每秒 250 KB（边传边交互） | 71–188 | 633–668 | 477–547 |
| 本机每秒 64 KB（边传边交互） | 141–359 | 953–1891 | 720–1078 |

- **Windows 上原来一直空转**：Windows 上 Node 的 `setTimeout` 和 worker 里的 `Atomics.wait` 都要约 15.5 毫秒才醒，
  驱动为了按时发包，把短于一个节拍的等待改成每轮事件循环看一次时间，传输期间一直占满一个核：每秒 1 MB 时每 MiB 1.8 秒，
  每秒 250 KB 时 6.3 秒。现在由核心判断哪条连接等不起（有数据等着发、一个节拍要攒下 64 KB 以上，即每秒 4 MB 以上），其余交给计时器、
  醒来补发攒下的包：每秒 1 MB 时降到 0.2–0.3 秒，速度和小请求往返不变。最初让驱动自己量最近的发送速率再切，真实线路上慢了一到两成
  （量出来之前一阵的开头已经按计时器走完了），所以判断放进了核心。同一时段的对照见 [driver-timer-ab.txt](driver-timer-ab.txt)。
- **还是比 Device Link 高**：真实线路上约 1.7 倍，本机限速线路上 3–5 倍。每个包都要在 JavaScript 里加密、经 UDP 中转签名，而 Device Link 交给 TCP。
  Device Link 经 Agent-Net 更高，因为 Device Link 的帧和 Agent-Net 的包各做一遍。

**线路开销**（数据方向的线路字节除以业务字节，本机线路上量）：原来的 Device Link 1.003，会话层 1.05。会话层每个包约 1350 字节，
其中 UDP 中转加 33 字节（会话号、校验和签名），核心的包头、分片头和加密标签约 30 字节。压测只数 TCP / UDP 载荷：真实网络上 TCP 每个 1460 字节的段还有 40 字节的 IP 和 TCP 头，
UDP 每个包 28 字节，算上之后两者差约 4%。直连（打洞成功、不经中转）时少掉中转那 33 字节。

## 5. 还没超过的地方

- **跨地区（往返 200 毫秒）**：分块传输会话层用到线路的 68%（边传边交互）、75%–78%（纯传），原来的 Device Link 83%–84%；
  单条 1 MiB 684–770 毫秒对 451–456 毫秒。会话层在这档会丢包重传（线路字节比 1.08–1.16）：一阵开头冲过 100 毫秒的队列，丢的要多等一个往返。
  这档对原来的 Device Link 偏宽：限速代理对 TCP 排满时暂停读取、不丢包，发送方的 TCP 不经历长往返上的慢启动；UDP 排满时直接丢掉。
  真实的长往返线路还没在两台电脑之间测过。
- **往返很短的线路**（本机回环，局域网直连同理）：纯传时 20 / 17.5 MB/s 对 31 / 26 MB/s，原因和试过的做法见第 2 节。
- **按字节限速的线路**（家宽、每秒 1 MB）：差 3–7 个百分点，主要是多出来的包头。
- **抖动线路上边传边交互**：真实线路上回传每秒 9–13 MB，和 Device Link 经 Agent-Net 的普通模式差不多、不明显更快；
  本机每秒 1 MB + 抖动一档用到 88%–90%（纯传 91%–92%），原来的 Device Link 95%–96%，单条 1 MiB 1.6–2.0 秒对 1.4 秒。这是低排队模式拿速度换小请求延迟，参数已经贴着核心里几条小请求延迟门槛
  （[核心验证记录](../../../packages/agent-net-core/sim/results/2026-11-16-jitter-window/README.md)「没做的」）。
- **CPU**：见上一节。
- **还没覆盖**：手机端（原生库还没接入会话层，发包上限和计时一起改）、跨账号分享、Node Host、自建中转；两台电脑之间互相控制都在界面上走过，
  但大量数据（20 MiB 这种）只在压测里测过，界面上传的附件走的是点对点文件通道。

## 6. 方法与复跑

- **入口**：生产代码。`v1` 是真正的 `DeviceLinkClient` 加生产的自建中转内核；`udp-relay` 是 Desktop 用的 `AgentNetWorkerSocket` 加 V2 中转的 UDP 转发；
  `worker-session` 是 Desktop 用的会话层（会话跑在 Agent-Net 的 worker 里，Main 拿解好的消息）。被控端只回显，不执行业务。
- **环境**：家里 Windows x64（Node v24.22.1）跑两台设备和压测；真实线路的中转在 macOS 测试机，隔离运行，不碰用户自己的 Cindy。
  非独占机器，数字只适合看趋势。真实线路的速度一天里在变，表里都是同一时段交替跑的。
- **证据边界**：两台设备在同一进程，CPU 是两端合计，不限速档位量到的是本机处理能力；限速代理对 TCP 不丢包（见上「跨地区」）；
  抖动是人造的；真实线路只有一条（家里经公司 VPN），没有测手机网络和跨国线路。

复跑（仓库根目录；真实线路先在中转那台电脑上运行 `node --import tsx packages/agent-net/bench/network-process.ts --listen 47200 --advertise <它的地址>`）：

```sh
pnpm --filter @cindy/agent-net run prepare-core
# 真实线路：纯传、边传边交互
node --import tsx packages/agent-net/bench/bulk-transfer.ts --remote-network <地址>:47200 --no-line --profiles real --modes v1,udp-relay,worker-session --runs 5 --total-mib 20 --interleave --no-taps
node --import tsx packages/agent-net/bench/bulk-transfer.ts --remote-network <地址>:47200 --no-line --profiles real --modes v1,udp-relay,worker-session --runs 5 --total-mib 20 --interleave
# 真实线路：单条 1 MiB 与小请求，每轮每种连法各跑一次（这里交替了 5 轮）
node --import tsx packages/agent-net/bench/session-latency.ts --remote-network <地址>:47200 --no-line --profiles real --modes worker-session --runs 1
# 本机线路：fast,fast-jitter 用 --total-mib 8，slow 用 4，very-slow 用 1；加 --no-taps 是纯传

```

# Cindy Make 上游 PR 查询

查询目标是与用户需求相关、但当前运行的 Cindy 尚未确认包含的 PR，不是全部 Issue，
也不是仅查询未合并或未发布内容。关键词命中只表示可能相关，不保证满足需求。

## 运行版本基准

- Main 构建时将源码 commit 和工作区是否干净注入 bundle；不新增运行期 Git 缓存 JSON。
- 发布包和 Beta 使用正在执行的 bundle 的身份，版本号仅展示渠道，不拿最新 release、
  可移动的 tag、准备好的源码目录或 `origin/main` 替代运行 commit。
- Dev 同样固定在该次 Main 构建的 commit；查询时检查构建源目录是否仍然干净、HEAD
  是否一致。它只用于检测失效，不会把新的 HEAD 当成正在运行的版本。
- Main watch 重编译会重新采集身份。Renderer 单独热更新、未提交改动、查询中切分支、
  缺少构建身份或 Git 检查失败时，保守保留候选并显示“是否包含尚未确认”。
- 发布构建临时改写 `package.json` 的版本号不算源码改动；除此之外的改动不豁免。

## 查询与包含判断

1. 对最多三个关键词分别查询开放 PR 和已合并 PR；Issue 不参与，也不按发布时间过滤。
2. 读取 PR 详情：已合并时使用合并后的 commit（包括 squash/rebase 结果），未合并时
   使用 PR head，不能使用 GitHub 为测试合并生成的 commit。已关闭且未合并的 PR 排除。
3. 优先使用 Dev 的本地 Git 对固定 commit 做只读祖先判断；否则使用 GitHub compare。
   已确认包含的 PR 被排除。确认在当前 commit 之后的 PR 标记“当前运行版本未包含”。
4. 分叉历史、无法证明等价的 cherry-pick、已知 revert、GitHub 不可比较、历史被截断、
   脏构建等情况保持未知，不将“查不到”当成“没有”，也不把未知候选静默移除。
5. 当前运行的是未合并 PR 分支时，也能通过 head 包含关系排除该 PR。

每个关键词/状态最多取十个结果，去重排序后最多核对二十个 PR，最多显示五个。
排除已包含结果后继续补充候选；未核对完时明确显示部分结果提示。查询总超时为 25 秒，
取消/超时不会误报“没有匹配”。详情或比较失败时保留对应候选，包含状态标记未知。

“已合并”不表示“已发布”，也不表示用户当前版本已包含。本查询不核实发布渠道、平台
或可更新版本，因此不会凭 PR 状态声称“升级即可获得”或“尚未发布”。

## 不变的边界

保持既有全局后台流程、源码准备和用户主动选择；不切分支、不合并 PR、不升级客户端。
历史消息中的 Issue 结果与缺少新字段的记录继续可读，新查询只产生 PR。
Main 负责网络和 Git，UI 只消费报告；运行版本摘要在结果详情内，主流程保持紧凑。

## 个人版任务准备

### 文件与分支边界（2026-09-18 用户更新裁决）

用户选择本地提交、合并与 rebase，替代此前只应用文件且永不提交的模型。`main` 只包含
官方提交，永不推送到官方仓。Cindy Make 对远端的写操作只有「个人版 GitHub 同步与提交给官方」
一节列出的几项：推送 `cindy-personal`、同步 fork 的 `main`、推送单项修改的
提交分支并创建 PR，且只写用户自己显式绑定的 fork 与用户逐次确认的 PR（2026-09-22 用户裁决
替代此前“永不推送远端”，2026-09-30 扩展到提交给官方；该节尚未实现）。模型在任务 worktree 修改、验证并回报完成后，宿主在
该任务分支创建带 DCO 签名的本地提交；未成功结束的轮次不提交或生成完成卡。没有新改动
不制造空提交。通用自动保存点仍跳过托管目录，避免在明确完成边界之外提交。

生成个人版直接使用当前 `cindy-personal`，不先同步官方源码（原设置页「生成前同步最新源码」开关
已于 2026-10-01 取消，旧的开启值按关闭读取；同步是唯一会把个人版移到新官方版本的地方）。随后都从这个实际源码目录安装依赖、
检查、构建。临时目录用于检测冲突并形成候选合并提交，不在那里构建。成功合入后的
个人源码工作区保持干净。按 2026-09-20 用户裁决，生成失败／取消时自动撤回尚未生成成功版本的
连续合入，恢复此前个人源码，保留任务分支、每轮修改与已经生成的版本；再次生成会自动重新合入。
恢复前核验分支、提交、文件树和工作区，发现并发修改时保留现场并报告清理未完成，不覆盖用户修改。
撤回过程保留失败提交的本地引用，并持久化待清理记录，确保 Git 已恢复而历史写入失败时可以接着清理。
旧完成记录只有文件树时仍能转换为本地提交。源码存在旧版未提交内容时先保存原 HEAD、
暂存树与文件树；若此前已应用官方文件但分支仍停在旧提交，以已记录的官方基线保存个人
差异，不把大量上游文件误当成个人功能提交。所有旧历史与文件备份通过本地引用保留。

获取官方更新时先固定当前渠道目标、更新本地 main，再在独立分支／worktree 中把个人提交
rebase 到新官方基线（禁止 update-refs 自动改动其他任务分支）。无冲突自动采纳；有冲突
手动同步时先弹窗询问，确认后才创建独立任务并沿用当前模型设置；取消则放弃本次合入、保留个人版。冲突解决并完整结束 rebase、校验个人源码未并发
变化后，才更新 cindy-personal。结果是“最新 main ＋ 个人提交”，不是要求两者 hash 相等；
官方更新不再堆积在未提交列表中。旧版遗留冲突现场仍可完成并迁移，新旧路径均不推送官方仓；
采纳后若已开启 GitHub 同步，由宿主按「个人版 GitHub 同步与提交给官方」一节推送 `cindy-personal`。
实现见 [localHistory](../apps/desktop/src/main/cindy-make/localHistory.ts) 与
[真实 Git 回归](../apps/desktop/src/main/cindy-make/__tests__/upstreamMerge.git-integration.test.ts)。

每次创建制作任务时，在创建任务分支和工作目录之前，必须沿用当前源码渠道重新获取官方目标，
并把 `cindy-personal` 更新到最新官方基线（2026-09-22 用户裁决）。有冲突时进入既有独立
处理任务，源码准备等待冲突解决、采纳与清理完成；同步失败、取消或账号切换均不创建任务
worktree。停止准备会停止本次准备所拥有的冲突任务并清理候选目录，已经完成的官方同步保留。
同步成功后才从更新后的 `cindy-personal` 创建任务分支，因此任务从一开始就在最新个人版源码上
修改。制作任务准备卡在“准备个人项目源码”和“创建任务分支和工作目录”之间单独显示
“正在更新个人版源码”；发生冲突时该步骤保持进行中，直到独立冲突任务完成采纳与清理。
Settings 的「同步」继续可用。创建制作任务前的同步仍为固定流程（同步进行中先等它结束；有冲突留在
处理任务里时不同步，新任务从当前个人版开始）。

生成个人版时把任务修改合入当前个人版基线后直接检查和打包。后续生成失败只撤回未生成成功版本的功能
合入。手机／远程资源沿用主机翻译后的准备状态和既有动作。实现与回归见
[任务准备](../apps/desktop/src/main/cindy-make/taskRuntime.ts)、
[同步运行时](../apps/desktop/src/main/cindy-make/upstreamMergeRuntime.ts) 和
[创建顺序测试](../apps/desktop/src/main/cindy-make/__tests__/taskRuntime.test.ts)。

- 环境、个人版源码、任务分支和工作目录统一由 Main 的 `CindyMakeManager` 管理。
  源码准备／清理、任务工作目录创建／依赖安装、完成后的 Git 写操作共用项目队列，
  不再由 Settings、消息卡片或创建弹窗各自维护后台作业。发送入场与源码清理互斥，
  已进入发送事务或运行中的任务禁止清理源码；清理已开始时拒绝新的发送。
- Settings → Cindy Make 分为“版本控制”和“环境检查”两个页签，版本控制排在首位并默认打开。
  工具检查和 Dev 测试开关归环境检查；个人版源码、我的版本和制作历史归版本控制。
  创建个人版本入口保留在版本控制页签内、概览卡上方，使用纯文字按钮，不显示加号。
  当前使用版本、切换入口和个人版源码合为一张概览卡，下方显示制作历史。切换只改变可见面板，保留检查／准备作业、版本列表展开状态与
  制作搜索内容；进入版本控制时立即重新读取版本、源码与制作历史。后台生成到达成功、失败或取消终态时，
  Main 主动通知设置页重读历史与版本，5 秒轮询只作异常兜底，不作为正常完成反馈。页签支持方向键、Home／End 及独立面板标识。
- 输入 /cindy-make 需求后，在当前页面弹窗检查环境、准备个人版源码并查询上游；
  这段前置流程不创建任务、不创建 worktree；源码准备与 Settings 共用同一流程，
  准备 Git 内容后按锁文件预热依赖缓存，不生成个人分支的依赖目录或执行安装脚本，也不执行 `.pnpmfile.cjs` 等
  pnpm 钩子（预热只是按锁文件取包，正确性由后续安装负责）。
  关闭弹窗不会留下空任务。Settings 的制作入口与侧栏入口复用同一个弹窗。
  前置弹窗通过右上角关闭图标退出，不再单设底部取消；图标、Esc 和遮罩点击均先二次确认，
  提示随当前阶段更新，说明关闭会停止什么、保留什么；环境／源码准备还须说明设置页共享作业也会停止。
  确认框内选择继续查看不打断准备；正在创建制作任务时暂时禁止关闭。
  检查完成后，「继续制作个人版」只显示在弹窗底部，不在报告卡中重复；关闭确认期间暂时禁用。
  实现与确认边界回归见 [CindyMakePreflightDialog](../apps/desktop/src/renderer/components/cindy-make/CindyMakePreflightDialog.tsx)
  及其[测试](../apps/desktop/src/renderer/components/cindy-make/__tests__/CindyMakePreflightDialog.test.tsx)。
- 选择「继续制作个人版」后，先创建带需求标题的任务并保存准备消息，再复核环境和
  个人项目源码；把 `cindy-personal` 更新到最新官方基线并处理完冲突后，才创建任务分支／
  工作目录并安装依赖。历史卡片缺少源码时也先创建任务，
  不让用户等待依赖安装结束才看到任务。首页和 Settings 直接创建这一个制作任务，
  不再为前置检查另建容器任务；已有任务入口继续继承来源任务的运行配置。
- Settings、消息卡片／弹窗和侧栏读取同一个 Main 快照；准备卡显示实际阶段、工具下载量、
  Git 阶段以及 pnpm 的解析／复用／下载／添加数量；安装开始与安装脚本执行另有状态提示，
  不伪造总进度。Settings 和前置弹窗均显示缓存预热的解析／复用／下载数量；
  缓存缺失或版本变化时按需补下载，任务 worktree 再复用缓存独立安装并执行安装脚本
  （来自 GitHub、这台电脑尚未生成覆盖的未验证内容除外，见下文「同步：一个按钮」）。
  Settings 源码准备和更新共用一个状态区域：区分等待其他工程操作、Git 检查、上游版本查询和本地源码检查。
  源码目录直接显示，打开和删除按钮在路径行最右侧对齐，不提供源码详情折叠入口。
  源码准备失败或停止时保留结果和原因，按钮为「重试准备」；更新失败或冲突时显示原因及处理入口。
  源码更新操作共用一个位置：正常显示“同步最新源码”，待处理冲突时替换为“处理冲突”，
  已有处理任务时在同处提供查看入口；底部只显示状态与原因，不重复摆放操作按钮。
  待处理冲突禁止生成个人版，但不阻止切换已经生成的应用版本；版本切换不要求当前没有
  正在执行的任务，切换会正常退出当前进程，目标版本启动后可按既有中断恢复继续任务。制作任务卡
  与设置页均遵守此边界；删除个人版仍保留运行中任务保护。
  更新成功只提示一次，随后显示个人版与 main 的版本差距，不再常驻「源码改动已合入」或
  「个人版源码已准备好」。旧更新回执不遮挡后续源码准备与重试；仍有未处理更新工作区时保留冲突处理入口。
  卡片进入页面即显示，先发布本机保存的源码摘要，再补 Git 版本与联网查询结果；
  不让工具发现或网络查询阻塞整张卡。重新进入保留已有信息，查询失败仍显示本地版本。
  各阶段共用同一刷新代次，迟到的查询不能覆盖之后的准备、清理或较新的查询结果。
  Settings 用「个人版 hash → 本地 main hash」展示本机关系，紧接着说明两者提交差距；
  下一行展示线上目标 hash 和本地 main 相对它的提交差距。不再显示制作分支、当前项目分支或重复的来源 hash。
  当前使用标签与原版／个人版名称使用相同字体、字号和字重；hash 使用等宽字体。
  线上目标版本与已核实的括号内差距使用成功色；省略领先／落后的零值，未知差距保持中性色。
  开发版查询 GitHub 最新 main，
  beta 查询最新已发布 beta 的 tag，正式版查询最新非 beta 发布的 tag；渠道之间不回退。
  能核实时显示本地 main 相对该版本的领先／落后提交数，查询失败不把缓存的 origin/main
  当作最新版本。查询只读、最长等待 10 秒，成功结果在进程内复用一分钟；
  实现与回归见 [latestSourceVersion](../apps/desktop/src/main/cindy-make/latestSourceVersion.ts)
  和[渠道查询测试](../apps/desktop/src/main/cindy-make/__tests__/latestSourceVersion.test.ts)。
  点击重试立即切换到本轮状态，不沿用上一轮错误或进度。
  准备不冒充 Agent 正在执行。
  首阶段检查及源码准备也按 runId 从 Main 读取完整报告；Renderer 重载不退回过时的保存卡片。
  Settings 重新检查后展示新检查，不用上一轮已完成的准备结果覆盖它。
- 准备成功后由 Main 自动发送原始需求，通过既有发送事务继承模型、供应商、推理档位、
  权限、计划模式与 Fast 设置。确认后的任务准备不因切换任务或重载 Renderer 中止，
  也不会丢失首次发送；确认前关闭弹窗则停止该轮前置检查。
- 确认后，完整准备卡替代普通输入区，显示步骤、下载／安装进度及停止／重试操作；
  直接复用输入框的背景和边框，详情限高滚动，操作留在固定底栏。环境、源码和依赖
  准备完成后立即恢复普通输入框，包括第一次自动执行；修改期间沿用普通任务的输入、
  语音、附件及停止操作。该任务自己的准备卡不再重复显示在消息流中，持久报告仍用于
  重载恢复，Settings 与来源任务中的卡片继续保留。Ask Question、Plan 和权限确认
  保持原有优先级。准备失败／取消时从准备卡重试；执行失败或中断使用既有恢复入口。
  已结束的执行记录优先于过时的准备报告，切换页面或重载不会重新锁住输入框。
  见 [CindyMakeComposerMask](../apps/desktop/src/renderer/components/cindy-make/CindyMakeComposerMask.tsx)
  和[生命周期回归](../apps/desktop/src/renderer/lib/__tests__/cindyMakeComposer.test.ts)。
- 每轮修改完成回报落库后，本机制作任务在输入区显示“修改已完成，选择下一步”，沿用输入框
  背景和边框，状态、说明与已核实的文件信息合为一个内容区，不重复显示“修改源码”步骤；
  底栏提供“继续修改”“启动隔离版测试”和“生成个人版”。同一完成记录
  不再重复出现在本机消息流。继续修改需 Main 确认并持久化，重载不恢复已收起的旧卡；
  新的用户消息或下一次完成回报会取代旧结果。提问、计划和权限交互保持原有优先级。
- 点击“继续修改”直接恢复输入框，重新打开任务也不再出现“继续测试／检查并继续”的拦截卡。
  输入框上沿保留“启动隔离测试版”和“生成个人版”两个轻量按钮，修改回复结束但缺少完成回报时也可使用。
  只有点击按钮后，Main 才核对账号、任务、最新回复和托管目录，登记当前源码快照并直接执行所选操作；
  不额外发送 Agent 检查消息，也不增加一次确认。新的快照不继承旧测试或旧生成成功状态，
  原有的源码一致性检查、测试启动检查和生成检查继续执行。新消息、目录变更或账号切换会拒绝过期操作。
  检查失败可重试；打开任务不自动启动测试或生成，运行、排队或等待交互时不抢占原流程。
- 测试必须由用户点击启动。Main 只接受当前账号的本机制作任务及最新完成记录，检查
  工作目录仍属于托管 worktree、没有链接替换、分支与原有 HEAD 匹配，且文件内容与完成
  时的 tree 一致，然后经既有开发版启动器启动独立命名的隔离实例。旧完成记录沿用干净

  历史回执按操作 ID 去重；重启不静默重放写操作。
- 制作历史卡右上角的「重新生成个人版」是全局动作，只构建当前本地 `cindy-personal`，不使用
  某条历史快照，也不自动加入尚未合入的任务，也不访问 GitHub。还没有生成过个人版、但个人版已有可用的
  变化（例如新电脑取回了另一台电脑的修改）时，同一位置显示「生成个人版」。
  筛选「待合入」时（只含未合入与有新改动的记录；已撤销的只能通过它自己的「重新加入个人版」恢复，
  批量制作不会把它加回），工具栏右侧保留「制作个人版」进入多选；支持全选当前搜索列表，
  二次确认按创建时间从老到新列出所选记录。Main 固定已确认的完成记录、commit 与文件树，
  先停止所选记录正在运行的隔离测试，再核验全部选择，逐条合入并且只在全部成功后生成一次。
  合入期间显示当前条目与总数；离开设置不取消流程。冲突或取消停止后续合入与打包，
  待处理的冲突工作区仍依赖已合入的前缀，因此此时保留个人源码基线，待冲突处理后再显式制作；
  没有待处理冲突工作区时，失败清理沿用下述撤回规则。不在重启后重放批量操作。
  每条可测试的待合入记录沿用同一隔离测试控制器；已启动时提供「重新启动隔离版」，
  等待旧进程真实退出后才重新启动，停止失败保留原状态。
  当前完成轮复用任务完成卡的同一生成流程；任务卡点击「生成个人版」时先加入该任务修改再生成。
  已结束的任务可通过待合入多选使用保留的完成快照，无需仍存在的制作工作目录，也不创建虚假的任务。
  生成时在源码锁内记录实际包含的操作，成功后立即刷新版本列表。任务完成卡按钮始终叫
  「生成个人版」，失败后保持同一入口；历史卡的全局入口明确叫「重新生成个人版」。失败或取消自动撤回
  尚未成功生成的合入，保留任务修改与原有应用成品；清理未完成时显示原因，再次生成前继续清理。
  全局重新生成入口仍只构建当前个人源码，不自动加入其它历史任务。检查期间分别显示安装依赖、
  自动测试和类型检查，加载时保留可见按钮文字，失败保留已知原因。旧记录缺少检查子阶段时
  回退到检查中，不改变已有状态含义。
  未声明托管版本启动协议的旧源码仍提供「查看安装包」，不声称可在版本列表中切换。
  完成卡的直接生成同样先走这条合入流程，遇到冲突先处理冲突再生成。
  实现与回归见 [historyRuntime](../apps/desktop/src/main/cindy-make/historyRuntime.ts)、
  [动作准入](../apps/desktop/src/shared/cindyMakeHistory.ts) 与
  [合入／撤销真实 Git 测试](../apps/desktop/src/main/cindy-make/__tests__/featureHistory.git-integration.test.ts)。
- 原「完成制作／删除制作」统一为「结束制作」，不触发合并、提交或生成。无论是否已合入，
  都必须二次弹窗确认，说明会删除工作目录、项目依赖和制作分支，保留归档交流记录；
  未合入时额外提示改动会丢失，合入状态未知时明确提示无法确认。用户确认丢弃即可结束，
  不强制生成个人版。普通归档只停止制作并保留目录，不能代替删除确认；全局清理源码入口独立。
  确认后沿用既有归档与运行时停止流程，再清理该任务的目录和分支，保留已有历史引用。
  合入或生成成功本身不触发清理；生成后可选择「结束制作并清理」。等待冲突处理时不能
  清理关联的制作目录。保留的合入提交和文件树使结束后仍能撤销；如果用户另行清空整个
  托管源码仓库，历史继续可看，但缺失 Git 对象的动作不再提供。
  清理失败不标记完成，cell 保留失败状态，操作区提供原因和「重试清理」；重试也必须弹窗确认。
  目标任务仍在运行或其目录被测试／其它清理占用时，Main 不排队删除，直接返回 busy，
  页面显示“任务仍在运行或目录正在使用”的提示；全局项目队列被其它任务占用时，目标任务若自身空闲，
  仍可结束并清理。
  兼容旧版已删除任务的清理重试，不恢复已删除的交流记录，也不提供恢复入口。
  只操作从合法 runId 派生且由该个人项目 Git 注册的目录，拒绝符号链接／junction 替换、
  仍在使用的目录和账号切换后的旧操作。清理成功后才持久化完成标记。
  Windows 清理启用 Git 长路径支持；Git 移除登记后仍残留目录时，仅确认丢弃的操作允许续清理，
  必须同时匹配持久准备记录中的任务、路径与分支，确认原分支仍在、目录没有 `.git`，
  且该路径和分支都未登记在其它 worktree。删除前重新核验托管根与链接边界；目录删除成功
  才删除分支。残留目录使用 `original-fs` 删除真实文件，避免 Electron 把依赖中的
  `default_app.asar` 当作归档打开后在 Windows 上锁住待删文件；真实 Electron 回归入口为
  `node apps/desktop/scripts/test-cindy-make-cleanup-asar.mjs`。文件占用时在操作区保留原因和重试入口，执行期间按钮显示加载状态。
  清理操作及失败原因由 Main manager 按任务和当前账号持有，通过同一全局快照推送；
  退出设置不取消清理，重进设置或另开窗口继续显示「正在清理」，同一任务的重复请求共用
  在途操作。失败后保留原因直到重试；删除前在原准备卡持久化待清理标记，应用退出中断的
  清理在重启后显示「待清理」，由用户再次确认后重试，不自动重放删除。临时的打开／确认弹窗
  状态才留在 Renderer。旧版 finish 调用仍只清理已合入的内容，不能升级为无条件丢弃。
  实现见 [taskManagement](../apps/desktop/src/main/cindy-make/taskManagement.ts)，
  [真实 Git 回归](../apps/desktop/src/main/cindy-make/__tests__/taskCleanup.git-integration.test.ts)
  覆盖普通归档保留、显式丢弃未采纳改动、忽略目录与分支回收。
- 制作仍由本地 Desktop 执行，拒绝 SSH 任务作为来源。手机的已有任务卡使用通用
  Remote Resource 的任务内 placement 和 session-controls 原语，支持查看准备进度、停止与重试，
  不改变原生配置或 runtime fingerprint。测试／构建占用工作目录时，主机发送入口也拦截修改，
  手机未收到最新进度时同样生效。远端 Desktop 的准备卡保持只读。
- 主机推送资源失效后，手机合并通知并重新读取；前台恢复和重连读取当前主机状态，
  账号、电脑或任务切换后丢弃旧响应。读取失败可重试，操作超时不自动重放写操作；
  前台卡片另有低频读取补偿。故障处理限于本任务的资源请求，不重置设备或共享连接，
  多设备用例验证一个资源读取失败不影响另一设备，不改变 device-link 的传输恢复策略。

## 获取官方更新与解决冲突

- Settings 的单行版本比较右侧仅保留「获取最新」图标，带悬停说明与点击确认框，
  底部不重复放更新按钮；首次准备、失败重试与停止按钮保留。
  确认后重新查询当前运行渠道的最新提交，不复用展示用的缓存。
- Main 拉取固定官方提交，保存个人历史／文件与 main 的备份，再更新 main。
  旧个人目录的未提交修改先转成本地提交；有未结束的 Git 操作或 main 含非目标提交时停止。
- rebase 在托管的独立目录中进行；只重放官方基线之后的个人提交，main 不接收个人提交。
  无冲突自动采纳；冲突时原个人源码保持可用，先弹出二次确认。确认后创建独立任务，
  由 Agent 自动处理并打开该任务；取消则放弃本次合入，不创建任务。重复点击不重复创建。
  个人历史中的 merge 提交若含额外修改／冲突处理结果，普通 rebase 可能漏掉这些内容；
  Main 通过 remerge 差异识别后，即使 rebase 没有文本冲突也先询问，确认后才创建核对任务，保留原个人目录，
  待核对原功能并补回遗漏后再采纳。
- 冲突任务使用独立 source `cindy-make-merge`，归入 Cindy Make 侧栏分组，标题使用
  工作目录的四位标记。它不继承普通制作任务的每轮说明、完成回报工具、隔离测试或
  生成个人版卡片。  首条用户需求由 Main 固定组装，要求理解双方修改、保留本地功能、
  安全解决冲突，并按仓库规则验证。允许暂存并继续现有 rebase，不重新开始、不跳过个人
  提交、不修改其他目录，也不推送；结束后宿主提交必要的附加修复。任务本身永不推送；
  采纳后向 fork 的推送只由宿主按「个人版 GitHub 同步与提交给官方」一节执行。
- 正常执行结束后，Main 核验目录归属、分支身份、原有 HEAD、文件冲突状态及
  `git diff --check`，再应用结果。自动检查不代表功能测试已通过；功能验证由解决冲突的
  任务执行并如实说明。个人版期间发生变化则停止应用并保留现场；中断、失败或
  continuation 边界不应用结果。旧文件合并现场可保留 MERGE_HEAD，解决后由宿主将个人
  差异迁移为本地提交，既有历史保留备份。
- 操作和任务绑定持久化到 userData；重启不静默重放 Git 写操作，重复点击复用任务。
  更新从发起时即绑定账号；确认和取消携带本次操作 ID，旧弹窗不能处置后来的更新。
  离开设置或切换账号时关闭待确认弹窗、保留冲突现场；再次进入可从「处理冲突」重新选择。
  创建任务前先持久化任务 ID；账号切换后不发送旧请求、不暴露另一账号的任务入口。
  已删除或归档的任务由下一次显式解决冲突操作创建新任务，继续使用保留的工作目录。
  未完成的合并禁止清理源码；缺失的合并目录不会被普通恢复流程重建为空目录。
- 取消只适用于尚未创建处理任务的官方更新：核验托管目录及分支归属，退出候选目录中的
  rebase／merge，再正常移除临时 worktree，以原提交值原子删除临时分支。个人源码、
  已获取的官方 main 和恢复备份继续保留。先持久化取消选择，再执行清理；清理失败或中断
  保留原因和「重试取消」入口，重启不会误开解决任务，清理完成前仍阻止后续更新、合入和生成。
  不能强制删除新增文件、被锁定或已由任务使用的目录。取消完成后可再次更新。
- 合并成功并记录采纳结果后，清理对应的临时 worktree 和 `cindy-merge/<ID>` 分支。
  有冲突处理任务时，先归档任务、保留交流记录并等待运行进程退出，再核验目录、分支、
  提交和文件树与采纳结果一致，且没有其他任务占用。清理只删除本次托管目录与精确分支引用，
  新增文件或提交继续保留；个人源码和 `refs/cindy-make/backups/*` 等恢复引用不受影响。
  若打包失败已回退个人源码，只有采纳提交仍被对应的失败构建恢复引用保存时才能补做清理。
  Windows 上 Git 返回移除成功后仍可能留下依赖 junction；必须确认实际目录消失后才删除分支。
  已失去 Git 登记和 `.git` 的旧清理残留（包括分支已删的情况），核验采纳提交仍被保留后，
  只补删 `node_modules` 内的链接和空目录，不跟进链接目标；任何剩余普通文件都保留并等待重试。
  清理失败持久化为待清理，下次显式生成或更新时先完成清理，再建立新的合并目录；重启不会
  自动删除目录。仅支持本机 Desktop，不增加远控调用权限。
- 生成个人版包括合并、处理冲突、清理、检查与打包。发生冲突时，本次生成保持运行，
  完成卡、制作历史和手机任务卡显示「处理冲突」；进度列表与生成记录也保留此步骤。
  冲突处理完成并通过采纳核验后，自动清理临时目录和分支，继续检查与打包，无需再次点击生成。
  生成进度下方直接显示当前执行状态的单行日志，不放“打开处理任务”按钮。检查与打包显示最新一行
  已脱敏的进程输出，长内容省略；尚无输出时显示当前阶段。密集输出合并更新，步骤切换、停止和结束
  不得回放旧日志。手机资源投影沿用同一行状态，阶段记录仍保持可展开查看。处理任务的交流记录
  继续保留，清理目录及归档后从既有任务入口回看，不重建目录。
  在处理任务中点击停止时，立即记录中断并结束本次生成等待；迟到的发送回调、完成事件不能
  恢复处理、另建任务、继续采纳或打包。停止之后发起的新消息被接受后才能继续处理原任务，
  不会恢复已结束的生成。打开任务本身也不恢复运行。重启保留任务绑定和生成记录，不重放 Git。
  正常结束后若同一步仍有未解决冲突，保留原任务并显示检查失败，不反复创建处理任务；
  只有已推进到后续改动的新冲突才自动继续，每一步使用独立的消息标记并留在同一个任务中。
  批量生成等待当前条目完成这套流程，才合入下一项。真正的失败或中断才结束生成。
  「停止制作」在桌面卡片、历史面板和手机上均需二次确认：确认后停止本次关联的冲突任务，
  归档并等待运行进程退出，核验无人借用后丢弃临时冲突修改、移除对应 worktree 与分支，
  再撤回尚未生成成功版本的合入。原制作任务的修改、交流记录与已生成版本保留。
  正在执行的 Git 采纳先完成结果记录，再回退；迟到的任务完成事件不能重新合入或触发打包。
  清理和回退全部完成前保留取消标记，失败后可重试；重启只恢复状态，不自动删除。
  应用退出与处理任务内的停止保留冲突现场，重启不自动续跑，区别于已确认的「停止制作」。
  每次重新生成都按当前源码和修改记录重新计算合并；此前生成失败撤回的合入不会作为可复用的
  合并结果，因此相同改动再次发生冲突属于可能情况。

实现见 [Git 合并](../apps/desktop/src/main/cindy-make/upstreamMerge.ts)、

### 面向普通用户的五条体验目标

1. 可以简单地创建个人版。
2. 同一个 GitHub 账号登录的不同电脑共用同一个个人版：本质是一份代码，打包始终来自
   `cindy-personal` 这一个分支，每台电脑各自生成应用。
3. 个人版的单项修改可以提交给官方（PR）。
4. 个人版的每一项修改都有记录、可查看、可撤销和恢复。
5. 个人版始终与真实线上版本同步：官方发布新版本后，个人版能一键跟上，修改自动保留。

所有面向用户的文案必须让非开发者看懂。主界面不出现 hash、分支、main、提交数、rebase、
合入等词；版本关系统一写成「官方 vX ＋ 你的 N 项修改」；这些技术事实只放在默认折叠的
「技术详情（给开发者）」里。用户看到的词：个人版、原版、修改、待生效、生成个人版、撤销／恢复、
保存位置、你的 GitHub、提交给官方。术语落地前按 `i18n/GLOSSARY.md` 流程登记：「制作历史」改称
「修改记录」、「从个人版移除／重新加入个人版」在列表中简称「撤销／恢复」、新增「提交给官方」
「待生效」「保存位置」。

### 用户裁决（2026-09-30）

- 默认使用官方仓的 fork。`makecindy/cindy` 是公开仓，fork 必然公开，确认卡必须写明修改
  及修改标题在 GitHub 上公开可见。私有仓库（非 fork）作为以后可选项，本轮不做。
- 已在本机使用的用户：自动检测、一次确认、之后全自动。建 fork 属于对外发布，不做完全静默。
- 从 GitHub 取回其他电脑的新修改后，不自动生成个人版，只提示一键生成。
- 提交给官方直接走本仓的 PR 流程（PR 模板、DCO 签名），以作者真实身份署名：预填本机 Git 的
  `user.name`／`user.email`，没有时取 GitHub 公开资料，作者在确认弹窗里可改；不使用 noreply 匿名
  身份（2026-10-01 用户裁决，取代 2026-09-30 的 noreply 署名）。个人版自身的提交照旧由本机 Git

- 个人版只通过用户自己的 GitHub 仓库共享。没有 GitHub 账号的用户本质上不能共享个人版，

- 连接复用 Cindy 已有的 GitHub 连接流程（受管安装 gh ＋ 网页验证码授权，无需用户自己装
  工具）；弹窗说明没有账号可以在 github.com 免费注册。连接成功后进入下文的存量迁移。

### 同步：一个按钮（2026-10-01 用户裁决，已实现）

用户裁决：对用户只有一个「同步」按钮；整个过程要简单到非技术人员也能看懂；需要合并、解决冲突时在流程里自动开任务处理完，只有不确定的取舍才问用户；过程要稳定、可持续、可恢复。有没有 GitHub 账号的体验只在 GitHub 授权初始化和能否多台电脑共用上有区别，其他完全一样，架构上也只有一份逻辑。

- 一条管线（Main [personalSync](../apps/desktop/src/main/cindy-make/personalSync.ts)，接线见
  [personalSyncRuntime](../apps/desktop/src/main/cindy-make/personalSyncRuntime.ts)），每一步都按当前 Git
  事实决定还剩什么要做：
  1. 先把上次没处理完的操作接着做完（重启前留下的、任务准备时留下的也算）：已有任务就等它；真正的冲突
     还没有任务就直接开；没做完的放弃先做完；重放还没开始就被中断的候选目录不开任务（Agent 无从处理），
     等用户「放弃这次合并」。修改记录里有一项修改正在加入或撤销时不开始，说明原因。
     个人版缺少官方基线记录（较早准备的源码）时，先按设置页同样的规则推算一次并记下（只新建、不覆盖）；
     新准备的源码在创建个人分支时就记下基线。
  2. 已保存到 GitHub 时：取回其他电脑的修改；能安全接过的（快进、无冲突自动合并）由 GitHub 同步完成，
     两边都有新修改时在独立目录合并（见下文「拉取与多台电脑」）。GitHub 出错（连接、网络、版本互不相关）
     不挡住这台电脑的官方更新，只在最后说明原因。
  3. 更新到官方版本（规则见下条），从不往回退。
  4. 已保存到 GitHub 时：上传结果；同步期间另一台电脑又上传了，就自动从第 2 步再来一次，仍然如此才提示。
     GitHub 同步的「立即同步」先等已在进行的那次结束，再按当前事实重新判断，不拿旧结果充数。
  没有 GitHub 时跳过 2、4，1、3 完全相同；Settings 与任务卡看到的是同一个状态。同步期间占用源码
  （与手动源码同步同一个占位），生成个人版要等它结束；同步自己的 GitHub 步骤不把这个占位当成「源码忙」。
  源码正忙时如实报告，未生成的修改提示「生成个人版后会自动上传」，都不报成功。
- 冲突：同步发起的合并与官方更新在冲突时直接开 `cindy-make-merge` 处理任务，不再弹确认；任务处理完被采纳后，
  同步自动从下一步继续。Agent 无法同时保留两边功能时在任务里问用户：它带着没解决的冲突结束这一轮时，操作记为
  「在等你回答」（`needsInput`），不报失败；用户回答（新的一轮）后照常继续。
- 不丢修改（[uncarriedChanges](../apps/desktop/src/main/cindy-make/upstreamMerge.ts)）：官方更新与合并两台电脑的
  修改用同一条核对，采纳前被重放一边自己的每个修改都必须在结果里——补丁相同；或这次 rebase 为它产生的提交
  （同作者、同作者时间、同说明，一对一，且该提交本身不与任何被重放的修改补丁相同：任务提交共用 Cindy Make
  身份与说明，作者时间才区分得开，同一秒的两个提交也不会互相作证；并且核对它确实把这个修改的内容留在了结果里：
  改动完全相同、把它再应用到结果上不产生任何变化，或新增的每行文字仍完整在结果对应文件的某一行里且删掉的行确已
  不在——冲突解决把两边改动融进同一行时内容仍在、不误报，只保留了一部分时不会作证）；或另一边自己对它的改写
  （同身份，且去掉
  上下文后的改动完全相同，例如另一台电脑更新官方版本时解决过它）；或把它再应用到结果上不产生任何变化（内容
  已在：Git 2.40 起用 `merge-tree --merge-base`，更旧的 Git（例如 macOS 自带的）改为在候选目录自己的 Git 目录里
  用私有索引核对它能反向应用到结果上）。身份相同的几个待核对修改互相区分不开，只按内容核对。合并提交里额外
  做的修改按「把整个合并再应用一次不产生变化」核对。Git 输出到达捕获上限时一律不信任（数量对不上即视为核对
  失败）。没有冲突的 rebase 若仍漏了修改，候选目录交给处理任务先补回。处理任务结束后仍漏了修改：先在同一个任务
  里提醒一次（列出缺少的提交）；仍缺时停下，由用户在同步状态里选择「仍然使用」（二次确认，说明缺少几项、两边
  原来的版本都留有备份）或「放弃这次合并」。「仍然使用」只对当时核对过的那个结果有效，之后又有变化就重新核对；
  每次失败都只带这次的缺失清单。
- 放弃：等待中的同步可以「放弃这次合并」：停止处理任务、删除候选目录，个人版与 GitHub 上的版本都不变（同步
  发起的操作标记为 `taskOwned`，走与停止制作相同的回收路径）。放弃进行中时显示「正在放弃」，完成后说明「个人版和
  GitHub 上的版本都没有变化」，放弃没能完成时可以再放弃一次。结果正在核对或采纳时不能放弃；没有所属账号的
  操作不会被写成半归属状态。属于其他账号的操作只是不显示，切回该账号后照常继续。
- 等待原因：同步状态按操作的事实说明在等什么并给出对应操作——任务在处理（自动继续）、在等你回答、处理时 Cindy
  被关闭（打开任务说一句「继续」；还没开任务时放弃后再同步）、处理任务不在了（还没开出来、开失败或被删掉：
  「继续处理」用同一个候选目录开新任务）、结果少了 N 项修改（仍然使用／放弃）、处理期间个人版又变了（放弃后
  重新同步）、属于另一个账号（只说明，切回那个账号再处理，同步与放弃都不碰它）、其他失败（打开任务或放弃）。
  等待期间「同步」按钮不可点；同步发起的官方更新若因另一个操作正在进行而没有开始，报告「忙」，不拿那个操作的
  结果当成功。
- 有还没生成的修改时不更新官方版本：官方更新会改写这些修改的提交，生成失败时就撤不回它们，也可能被当成已确定的
  内容上传。此时同步跳过官方更新，提示「先生成个人版，再同步到官方 vX」。
- 两边合不到一起时选一边：基线互不相关（`diverged`），或用户放弃了合并两台电脑的修改之后，同步状态提供「以 GitHub
  上的为准」「以这台电脑的为准」，都需二次确认。以 GitHub 为准：这台电脑的版本留在
  `refs/cindy-make/backups/personal-remote-local/<commit>`，改用 GitHub 的版本与它发布的官方基线。以这台电脑为准：
  一次 `--atomic` 推送先把 GitHub 原来的版本写进用户仓库的 `cindy-personal-backup/<12 位>` 分支（租约要求它
  不存在），再带租约替换；本机还有没生成的修改时照例不上传，提示先生成。之后照常完成同步其余步骤。
- 另一台电脑改写了同一版本：这台电脑自上次同步后没有任何新内容（本机版本就是上次同步确认的版本）而 GitHub 上
  已是另一台电脑改写后的版本（例如它解决了官方更新的冲突，或用户在那边选了「以这台电脑为准」）时，直接取回并
  备份本机版本，同一个冲突只需在一台电脑上处理一次。
- 可恢复：同步本身只记住正在等哪个操作与上次的结果（`source` 旁的 `sync.json`），其余耐久状态都在共享的合并
  生命周期（保留的候选目录、处理任务、重启恢复、取消）和 GitHub 绑定记录里。重启后冲突任务处理完仍会自动继续；
  重启前已采纳的不在启动时擅自继续；任何时候再点一次「同步」都从停下的地方继续。合并操作的归属按账号记录
  （去掉会话代次），同一账号重新登录后仍是自己的操作；旧记录读取时自动换算。
- 创建制作任务前：同步正在进行时先等它结束；整个等待（含等已在进行的那次）最多 120 秒，超时就直接继续
  准备、同步在后台做完，不让新任务在源码更新阶段等上数分钟。有冲突留在处理任务里（任何保留的候选目录）时不做
  源码同步，新任务直接从当前个人版开始，不因那个冲突失败。等待结束后又有同步抢先开始而报「忙」时，再等它
  结束重新判断（至多两次）。
- 任务 worktree 安装依赖时，来自 GitHub、这台电脑还没生成过个人版覆盖的内容不执行生命周期脚本、也不执行
  `.pnpmfile.cjs` 等 pnpm 钩子（`pnpm install --ignore-scripts --ignore-pnpmfile`，并从子进程环境剔除
  `npm_config_*`）：同步会取回 fork 上有写权限者推送的内容，任务创建前的静默安装不得替它执行 `postinstall`、
  pnpmfile 钩子等安装期代码（攻击者只需往根 `package.json` 加一个 `postinstall`，或放一个 `.pnpmfile.cjs`，
  不需要动锁文件）。判定看绑定记录里「取回且未验证」的 tip（`unverifiedRemote`）：任务基线包含它、且没有任一
  已生成个人版本的提交包含它，即视为未验证；读不到这些事实时按未验证处理。官方更新／合并改写了个人提交的哈希时，  未验证身份随改写记录（`rewrites`）传递，不会因换哈希而脱管。生成个人版是用户显式动作（会运行这份内容自己的
  检查并产出用户要运行的应用），它覆盖到该内容后，后续任务恢复正常执行安装脚本。脚本被跳过时写入任务准备
  日志；任务确实需要时由 Agent 在任务里自行安装，那是可见的正常工作。
- 生成个人版不再先同步源码：设置页「生成前同步最新源码」开关已取消，旧版本保存的开启值按关闭读取；同步是唯一
  会把个人版移到新官方版本的地方。
- GitHub 仓库检查：每次与 GitHub 同步先读取保存个人版的仓库（不带凭证跟随重定向）。仓库已删除时提示并在「保存位置」
  提供「重新保存到 GitHub」（停止同步后重新走确认卡）；改了名时按 GitHub 的重定向（只接受指向
  `api.github.com/repositories/<id>` 的地址，跟随一次）找到新名字，且只接受仍属于同一账号的仓库，从不为此新建
  fork；同一名字指向的仓库还必须仍是本账号的官方 fork（fork、归属、上游 `makecindy/cindy` 同样严格校验），否则
  按绑定已失效处理并提示重新保存，绝不向它推送；已归档时说明需先取消归档；没有写入权限时提示重新连接。取回只在源码能移动时进行：还没生成时提示先生成，
  源码正忙时报告「忙」，都不会被误报成「版本互不相关」而引出替换 GitHub 版本的选项。比较两边内容的 Git 输出
  同样有数量核对。以 GitHub 为准同样要求本机内容都已生成（有待撤回的生成时不动）。
- 合并两台电脑修改的合并类型是 `combine`（与官方更新同一套 rebase 生命周期）；进行中时旧版本客户端不认识它，
  会拒绝接手，而不是把它当成官方更新完成并把官方基线设错；完成或取消且没有候选目录后改存为 `rebase`，不让
  旧版本客户端（例如没跟着更新的个人版）因此无法使用源码功能。
- 官方版本（[syncTarget](../apps/desktop/src/main/cindy-make/syncTarget.ts)）：个人版只能在与本机原版
  数据库迁移完全一致时切换，而个人版运行时不会自己更新。因此跟随当前渠道最新发布版，前提是它的
  `apps/desktop/drizzle` 与本机原版的版本一致；不一致时停在本机原版所在的官方版本，并提示「官方 vX 已发布，
  但它更新了数据格式：先切换到原版并更新 Cindy，再同步即可包含」。开发版跟随 main；查不到原版信息时沿用
  旧行为跟随最新；本机原版已知但查不到对比结果时不动（报「暂时查不到官方版本信息」）。目标提交在比较前总会先
  取到本地。创建制作任务前与生成前的源码同步也用同一规则，并且从不把个人版移到比它当前官方版本更旧的版本
  （例如另一台电脑带来了更新的官方版本时保持不动，同步结果提示「个人版已在比这台电脑的 Cindy 更新的官方版本上」）。
  不改更新服务。
- 历史改写记录：每次被采纳的官方更新与合并都记下「这些版本的内容都在这个结果里」
  （`personal-remote.json` 的 `rewrites`，最多 16 条，按完整记录去重，启动时从已持久化的合并结果补记）。上传时，
  即使官方更新解决冲突改变了补丁，只要记录能证明 GitHub 上的版本已被带进本机版本，就可以带租约替换并留备份；
  记录里本地已不存在的提交（例如清理源码后）一律视为「证明不了」，既不会让同步出错，也不会让刚重新准备的
  源码覆盖 GitHub。
- 界面：版本概览卡只有一个「同步」按钮，下面一行白话说明进度、等待的冲突任务、失败原因或「已同步到官方 vX」；
  个人版自上次生成后有了变化（或新电脑取回了修改而从未生成）时，同一行提示「生成后才会在这台电脑上用上」并提供
  「生成个人版」，修改记录标题旁同样提供。旧的「处理冲突」「重试取消」按钮与重复的合并状态提示已移除，所有非修改
  记录的源码操作都在这一行显示与处理。「保存位置」一行只保留连接、在 GitHub 查看、停止同步，不再有单独的
  「立即同步」「合并修改」；两边都改了而这台电脑的还没生成时提示先生成。版本名按个人版实际所在的官方版本显示：
  官方更新采纳后记下新的版本名；基线就是最新发布版时直接用它的名字。

### 身份与凭证

- 使用 Cindy 的 GitHub 连接当前的有效凭证（`ghCliTokenSource`／`githubConnection`），
  token 只在 Main 内存中使用，不写 `.git/config`、remote URL、argv、日志或磁盘。Git 访问 fork
  时用进程环境 `GIT_CONFIG_COUNT/KEY/VALUE` 注入仅限该仓库 URL 的 `http.<url>.extraheader`。
- 绑定的是 `{ login, repository, confirmedAt }` 与存放方式选择，写入托管源码目录旁的
  `userData/cindy-make/personal-remote.json`（非秘密；清理源码不删除它，也不属于「恢复默认」的
  设置项）。每次同步前核对当前登录的 login；不一致时暂停同步并提示，不自动改绑、不推到其他账号。
  运行中的操作只在文件里留运行标记，重启后显示「上次操作被中断」，不自动重放。
- 带凭证的 Git 命令同时覆盖 `core.hooksPath`（指向空设备）与 `core.fsmonitor`，推送加
  `--no-verify --no-follow-tags`：仓库钩子与 fsmonitor 程序不在带凭证的环境中运行，也不会顺带推送标签。
  需要 Git 2.36 以上（2.31 起支持环境变量注入配置，2.36 起支持 `--remerge-diff`），更旧的 Git
  直接提示更新，不静默丢失凭证。
- 需要 `repo` 与 `workflow` 权限。Cindy 自己的登录流程已申请 `workflow`；用户在终端自行
  登录的 gh 可能缺少它，推送含 `.github/workflows` 变化时被 GitHub 拒绝，此时识别该错误并
  引导「重新授权 GitHub」，不改用其他凭证、不跳过这些文件。
- Renderer 只传动作与记录 ID，不传 login、URL 或 token。

### 仓库角色与推送内容

- `origin` 仍指向官方仓，官方代码、渠道 tag、版本查询与冲突处理只读官方仓，逻辑不变。
  新增名为 `personal`、不带凭证的 HTTPS remote 指向用户的 fork。界面只说「你的 GitHub ·
  <login>/<repo>」，不暴露 remote 名。
- 同步 `refs/heads/cindy-personal`，并随同推送 `refs/heads/cindy-personal-base`（个人版所基于的
  官方提交，必须是个人版的祖先，无法证明时不推）；两者用 `--atomic` 一起更新。另一台电脑取回时
  优先用它确定官方基线，没有时退回本机自己的基线；不推送 `refs/cindy-make/personal-upstream` 等
  `refs/cindy-make/*` 自定义引用。任务分支、
  `cindy-merge/*`、`refs/cindy-make/{tasks,features,backups,failed-builds,history-backups}/*`、
  交流记录和生成的应用都不同步；每台电脑自己生成应用。
- fork 上只放「已确定的内容」：生成成功的修改，或官方更新、跨电脑合并的结果。生成失败时
  可能被撤回的合入（`buildRollback` 仍能回退的收据）不推送。
- 推送一律使用显式 refspec 与租约：
  `push personal <commit>:refs/heads/cindy-personal --force-with-lease=refs/heads/cindy-personal:<上次取得的远端值>`；
  租约失败即视为另一台电脑已推送，进入拉取判断，绝不追加 `--force`。
- 推送时机：每次生成结束（失败的生成已先撤回）与每次官方更新采纳后自动检查；迁移时首次推送；
  进入设置页时至多每分钟自动检查一次；创建制作任务前先同步一次（最多等 2 分钟，失败不阻止创建）；
  设置页始终提供「立即同步」。上传前在项目锁内取一次本地快照决定推什么，网络命令都在锁外执行；
  整个同步期间登记为源码读取者，清理源码会被拒绝，但不阻止生成个人版排队。
  仍有生成失败可撤回的收据、待完成的回退记录或 `refs/cindy-make/failed-builds/<commit>` 时一律
  不推。失败只标记「待同步」，不改变本地结果；重启不重放推送。
- fork 是本机上次上传的版本（记录在 `syncedCommit`），而本机历史被官方更新改写时，只有 fork 中
  每个修改在本机都有同样内容（`git cherry` 无 `+`，其中的合入 merge 提交 remerge diff 为空）才替换，替换前在本机留
  备份引用；否则按分叉处理，不覆盖。

### 首次使用与新电脑

- 本机还没有托管源码、也没有记录存放方式时，首次准备前插入「个人版存放方式」：已连接
  GitHub 默认「存到我的 GitHub」，未连接默认「只存这台电脑」并提供「连接 GitHub」。选择即
  构成建 fork 与后续同步推送的授权，不再二次确认；之后在设置页「保存位置」修改。
- 找到或创建 fork：调用创建 fork 接口（已有 fork 时通常应返回已有仓库；不能再建而返回 422 时改为
  定位账号已有的官方 fork 复用），校验它属于当前 login、是 fork 且上游为 `makecindy/cindy`（定位到的
  已有 fork 与创建成功同样严格校验，不会误用别人的或非官方 fork）；账号下已有同名的其他仓库时，GitHub
  会给新副本加后缀，Cindy 不覆盖、不改动已有仓库。轮询到 `ls-remote` 可用后才继续。确认卡显示
  「通常是 <login>/cindy」，实际名称在绑定后显示。重试失败的保存会重新显示确认卡。
- 新电脑：fork 上已有 `cindy-personal` 时，确认卡改为「你的 GitHub 上已有个人版」并说明本机会改用
  它（主按钮「在这台电脑使用」）；托管源码还没准备时先准备源码再继续。照旧从官方仓 clone，本机
  没有自己的修改（只有官方提交）时直接取回 fork 的个人版作为起点；之后提示一键生成，不自动生成、
  不自动切换。

### 已在本机使用的用户：自动迁移

- 检测条件：本机已有个人版源码、已连接 GitHub、未绑定 fork、用户未选择「只留在这台电脑」。
  检测时机：进入设置页版本控制、刚完成 GitHub 连接、下一次创建制作任务或生成个人版前。
  以卡片呈现，不打断进行中的制作、测试或生成。
- 确认卡写明：账号与仓库名、它是官方仓库的公开副本且修改所有人可见、其他电脑可以使用、以后
  可以提交给官方、「这台电脑上的个人版、制作历史和正在进行的制作都不会改变」。操作：「保存到
  GitHub」「只留在这台电脑」。没有「以后再说」：确认卡一直显示，直到绑定成功或用户选择「只留在
  这台电脑」（之后可在「保存位置」重新选择）（2026-10-01 用户裁决）。
- 确认后进入项目队列（与准备、测试、生成互斥，等待时显示「等待其他工程操作」），每步可中断、
  可重试，进度持久化，重启只恢复状态、不自动重放：
  1. 按 `commitPersonalFiles` 把遗留未提交内容转成本地提交，先备份引用；失败则什么都没变。
  2. 找到或创建 fork；纯远端操作，失败只提示原因、可重试。
  3. 添加 `personal` remote，取回远端 `cindy-personal`。
  4. 远端没有个人版：推送本机个人版；本机尚有未生成成功的修改时，等下次生成成功后再推。
     远端已有另一台电脑的个人版：按下文拉取判断合并，确认弹窗显示两边的官方版本与修改数。
  5. 保存绑定，之后自动同步。
- 不重新 clone、不改 `origin`、不动任务分支／worktree／依赖／修改记录／已生成的版本。

### 拉取与多台电脑

- 拉取时机：创建制作任务前（让新任务包含其他电脑的修改）、生成个人版前、官方更新前、进入
  设置页。不做后台轮询。网络失败不阻止本地操作，只显示「GitHub 状态未知」。
- 判断按内容而非 hash（官方更新会改写 hash）：
  - 两边相同：不做任何事。
  - 本机是远端的祖先、本机独有修改都已在远端（`git cherry` 按 patch-id 全部等价），或本机只有官方
    提交：在本机 `refs/cindy-make/backups/personal-remote-local/<旧 commit>` 备份后 `reset --keep`
    到远端，官方基线取 fork 的 `cindy-personal-base`（没有时用本机基线，且必须是远端的祖先）。
    只在源码空闲、工作区干净、当前分支是 `cindy-personal` 且本机内容已确定时取回；否则只报告「GitHub
    上有另一台电脑的新修改」。进行中的任务不受影响，之后照现有流程合到最新个人版上。
    提示「已取回另一台电脑的修改，生成个人版后可用」。
  - 远端已包含本机：推送。
  - 两边都有独有修改（已实现无冲突的情况）：fork 发布的 `cindy-personal-base` 必须与本机官方基线
    完全一致（没有发布基线时不合并：fork 可能已在更新的官方版本上），且本机内容已确定、源码空闲且
    干净时，把本机独有、远端还没有的修改（按 patch-id 判断）从旧到新逐个放到远端版本之上：只用 Git
    对象完成（`merge-tree --write-tree --merge-base` ＋ `commit-tree`，需要 Git 2.40），不检出、不建
    worktree、不运行钩子；作者、作者时间与完整说明从原始提交对象（`cat-file commit`）读取，经环境变量
    写入，不受用户 Git 配置影响，签名不复制。全部无冲突后先带租约快进推送合并结果，成功后再在项目锁内
    确认本机仍停在合并起点、源码空闲干净，才备份本机版本并 `reset --keep` 到合并结果，状态显示「已取回
    另一台电脑的修改，生成个人版后可用」；推送失败时本机完全不变；上传期间本机又有新变化时保留本机、
    记为待同步，下次同步再合并。本机的合入 merge 提交 remerge diff 不为空、任一修改冲突或 Git 太旧时
    什么都不动，只报告。
  - 两边改到同一处或在不同官方版本上（已实现）：自动合并遇到冲突（或 Git 低于 2.40、合入 merge 提交带自有
    修改、两边官方版本不同）时，GitHub 同步只报告「需要合并」，什么都不动，由「同步」接着处理。它与官方
    更新是同一个合并生命周期（`CindyMakeMergeState.remote`，项目锁、保留的候选目录、重启恢复、取消）：
    先核对要合并的正是上次同步取回的 GitHub 版本（`refs/remotes/personal/cindy-personal`）；在官方版本更新的
    一边保持不动，把另一边自己的修改（按共同点之后的提交）在 `merge-worktrees/<ID>` rebase 到它之上，两边都有的
    修改不会重复；无冲突直接采纳，有冲突直接创建 `cindy-make-merge` 处理任务（「同步」即是用户的决定，不再弹
    确认）。任务提示要求同时保留两边的功能，禁止 `rebase --skip`、`reset --hard`、整批
    ours/theirs，无法同时保留时先问用户。采纳前核实 rebase 已完成、GitHub 版本是结果的祖先、这台电脑的
    个人版未被并发修改；官方基线取两边较新的那一个；这台电脑原来的版本留在
    `refs/cindy-make/backups/<ID>/personal`。采纳后由同步自动快进上传，状态显示「已取回另一台电脑的修改，
    生成个人版后可用」（只认这次合并记下的 GitHub 版本，普通上传不会误报）。合并期间与官方更新冲突一样，
    其他源码操作会等它处理完或取消。官方版本互不相关（谁也不是谁的祖先）时只报告，不自动合并。
  - 无法自动处理（基线互不为祖先，或用户放弃了合并）：报告原因，提供「以 GitHub 上的为准」「以这台
    电脑的为准」（已实现，规则见上文「同步：一个按钮」），两者都先备份（以这台电脑为准时把 GitHub 原来的
    版本推到用户仓库的 `cindy-personal-backup/*` 分支）、都需二次确认，都不删除任务分支与已生成的版本。
- 与其他 Git 写操作共用项目队列；候选目录与冲突任务沿用现有清理、取消与重启恢复规则。

### 与真实线上版本保持同步

- 「真实线上版本」指当前渠道最新发布版（正式版取最新正式 tag，测试版取最新 beta tag，Dev 仍
  跟随 GitHub main）。设置页「官方最新」一行显示它，以及个人版是否已包含。
- 数据版本约束：个人版切换要求其数据库迁移集合与本机原版完全一致
  （[versionStore](../apps/desktop/src/main/cindy-make/versionStore.ts) 的 `migrationHash` 核对）。
  现有同步目标取线上最新，而正在使用个人版的电脑上原版不会自动更新；官方新版一旦带来新的
  迁移，基于新版生成的个人版就会被判为不兼容。这是现有流程的缺口，本节一并解决。
- 已取消「生成前同步最新源码」开关（2026-10-01）：按「同步：一个按钮」裁决，生成个人版不再先同步，
  个人版只在用户点「同步」时移到新官方版本；「官方最新」一行与同步状态告诉用户是否已包含。
- 官方发布新版本时，设置页和个人版应用内提示「官方发布了 vX」，并提供一键「更新个人版」：
  1. 后台把个人版同步到 vX 并生成新的个人版，期间照常使用；此时不改动原版和当前个人版。
  2. 新个人版生成成功后提示「重启完成更新」。原版已是 vX 时直接切换；否则按用户已确认的
     更新计划：切到原版 → 由原版既有更新服务更新到 vX 并完成数据迁移 → 自动切到新个人版。
     更新计划持久化并显示进度与停止；任一步失败都停在可用的原版，并说明原因。
  3. 先生成、后更新原版，保证原版更新后一定有可用的新个人版可切换。
- 做官方更新前先看 fork：远端个人版已基于目标版本且本机没有独有修改时，直接采用远端结果，
  不在本机重做，冲突只需在一台电脑上处理一次。
- fork 的 `main`：官方更新采纳后调用 GitHub merge-upstream 接口，只做快进；fork 的 main 有用户
  自己的提交时不动，只在技术详情里提示。Cindy 取官方代码不经过 fork 的 main，这一步不影响正确性。
- 两台电脑原版版本不同：官方基线以较新的一方为准；落后的电脑显示「另一台电脑已更新到官方 vX，
  这台电脑需要先更新」，并走同一「更新个人版」流程；在此之前本机已生成的个人版照常可用。
- 该流程涉及更新服务与版本切换，实施前必须先读 `docs/dev-rules/cindy-updater.md` 并单独确认
  技术方案。

### 修改记录

- 以「修改」为单位列出每次制作（同一次制作的多轮完成算一项），附带系统自动记录（例如「官方更新到
  vX，你的修改已自动保留」）。状态只显示一个：制作中／已生效／待生效／已撤销／官方已采纳；
  PR 状态作为附加标签。筛选：全部、已生效、待生效、已撤销、已提交给官方。
- 「待生效」统一表示已改变个人版源码但尚未生成到应用里的变化（新加入、撤销、恢复、从 GitHub
  取回）。顶部横幅汇总为「有 N 项变化还没生效」，并提供「生成个人版」。
- 撤销／恢复沿用现有反向提交机制，不改写历史；撤销需一次确认，说明「生成后生效、随时可以恢复」。
- 跨电脑：绑定 GitHub 后，Cindy Make 生成的每个提交在说明末尾附加 trailer
  `Cindy-Make-Change: <runId>` 与 `Cindy-Make-Title: <标题>`（官方 rebase 后仍保留）。另一台电脑
  据此在修改记录中显示「在另一台电脑上制作」的条目，可以查看改动、撤销／恢复、提交给官方，不能
  「打开任务」或「继续修改」（交流记录在原电脑上）。标题会随 fork 公开，确认卡已写明。

### 提交给官方

已按以下规则实现（2026-10-01）：

- 入口：修改记录中已完成、有实际改动的单项修改（未撤销、不在进行中），按钮「提交给官方」；已提交过
  的显示「更新提交」，官方未采纳的显示「重新提交」，已被采纳的不再提供。没有把个人版保存到 GitHub
  时弹窗只说明需要先保存到 GitHub，不提供提交。
- 确认弹窗：标题（预填 `feat: <修改标题>`）、说明（按 `.github/PULL_REQUEST_TEMPLATE.md` 预填摘要、
  范围、验证与风险，涉及界面路径时提示补充截图与设计依据，可编辑）、署名名字与邮箱、包含的文件列表、
  「只包含这一项修改」「从你的 GitHub 仓库发起、所有人可见」，以及必须勾选的 DCO 确认（显示将要签名的
  `名字 <邮箱>`）。每一次提交都需要用户逐次确认。
- 执行（全程钉在发起提交的 Cindy 账号作用域上，期间切换账号即中止：不会读到另一个账号的修改、用它的
  身份推送或写它的台账；推送前同样校验保存的仓库仍是本账号的官方 fork，绑定已失效时提示重新保存、不推送）：
  取官方最新 `main` 到 `refs/cindy-make/contribution/main`；在临时索引里以它为底，把这项修改从
  创建基线到最后一轮完成内容的差异用 `apply --cached --3way` 放上去（只含这一项，个人版里的其他修改不
  带上，本机工作区不动）；用作者身份 `commit-tree` 一个提交，说明末尾带同一身份的 `Signed-off-by`；
  带租约推送到 fork 的 `cindy-make-pr/<runId>`（与本机任务分支 `cindy-make/<runId>` 区分；分支已在
  GitHub 上被删除时按「不存在」重新租约推送一次），再在官方仓
  创建 PR（`maintainer_can_modify: true`）。放不上去（与官方最新代码冲突）或官方已包含时说明原因，
  不推送。PR 分支不在本机重新运行检查，说明里如实写「以 CI 结果为准」。
- 再次提交：先读取原 PR 状态（查不到状态时按「不动旧分支」处理），仍开着时更新同一分支与 PR 的标题和说明；
  已关闭或已合并时从一个新的分支新开一个 PR，原 PR 的分支与提交原样保留、绝不改写（新分支按「必须不存在」的
  租约推送，名字被占用就换下一个），不修改维护者已处理的 PR（确认弹窗同样按原 PR 状态说明「会更新」或「会新开」）。
  更新分支成功后立即记下新提交，再改 PR 与写记录；中途失败或切号后重试按新提交租约，不会永久卡死。作者与
  签名身份经环境变量写入，用户 Git 配置里的 `author.name` 等不会改掉它。改了名字或邮箱后需重新勾选 DCO。
- 状态回显：修改记录详情显示「已提交给官方 #N · 等待审核／已被官方采纳／官方未采纳」，并可在 GitHub
  查看；状态每 5 分钟至多查询一次。提交记录保存在按账号隔离的
  `userData/.../cindy-make-contributions.json`，只含 PR 编号、链接、分支与提交，不含凭证。
- 未实现：「官方请你修改」的细分状态；采纳后下一次官方更新时从个人版中移除已被官方包含的该修改提交，
  修改记录显示「官方已采纳，个人版改用官方版本」（自动判断不了时进入既有冲突处理）。

### 设置页呈现（版本控制页签）

- 顶部一张「下一步」横幅，只说一件事、至多一个主按钮，优先级：冲突处理中 → 正在生成或更新 →
  官方发布新版本 → 有变化待生效 → 迁移提示 → 一切最新。
- 概览卡四行，每行一句话、至多一个操作（已实现：正在使用、个人版、官方最新、保存位置四行；「你的 N 项修改」
  按本机修改记录中已在个人版里的项计数，另一台电脑做的修改尚无记录时写「＋ 你的修改」）：
  - 正在使用：个人版／原版，「切换到原版／切换到个人版」。
  - 个人版：「官方 vX ＋ 你的 N 项修改」与「已生效／N 项变化待生效／正在生成」。
  - 官方最新：「vY 正式版（或测试版、开发版日期）」与「个人版已包含／个人版还没包含」。
  - 保存位置：「你的 GitHub · <login>/<repo>」与「已同步／待同步／状态未知／账号不一致」；
    或「只在这台电脑」与「连接 GitHub」。管理菜单：在 GitHub 查看、立即同步、停止同步
    （只断开连接，不删除 fork，也不删除本机个人版）。
- 下方为修改记录，右上角「新增修改」（首次为顶部横幅的「创建个人版」）。
- 最底部默认折叠「技术详情（给开发者）」：个人版分支与 hash、官方基线、本地 main、GitHub 仓库、
  源码目录、打开源码目录、清理源码。
- 本呈现取代 `docs/design-rules/DESIGN.md` 中「Cindy Make source comparison」的豁免条目，实施 UI
  时须同步更新该条并完成 Light/Dark。
- 手机只读显示同步状态与 PR 状态，不新增远控写操作；投影新增字段按
  `docs/dev-rules/protocol-compatibility.md` 保证旧客户端可忽略。

### 简单创建的配套改进

- 上游相关 PR 查询失败不再阻止「继续制作个人版」，改为说明「没能查询官方是否已有类似修改，可以
  继续」。
- 磁盘空间低于 10 GiB 只提示风险、允许继续；低于 2 GiB 或不可写才阻止。
- 缺少系统编译工具时给出面向普通用户的安装引导（打开官方安装页，完成后一键重新检测），仍不代装、
  不执行管理员命令。

### 分期

1. 同步基础：GitHub 身份与绑定、首次选择、存量迁移、推送与拉取（相同／取回／推送三种情况）、
   新电脑使用、提交 trailer、设置页新呈现（横幅、四行概览、修改记录新状态、技术详情折叠）。
2. 与线上同步：官方新版提示与「更新个人版」完整流程、数据版本不一致提示、官方更新复用远端结果、
   fork main 同步、取消「生成前同步最新源码」开关。
3. 多台电脑并发：分叉合并与冲突、兜底操作、另一台电脑修改的撤销／恢复。
4. 提交给官方：PR 流程、状态回显、再次提交（已实现）；采纳后替换（未实现）。

### 不做

- 私有仓库、GitHub 以外的托管平台、同步任务分支与交流记录、自动生成个人版、自动提交 PR。
- 没有 GitHub 账号时的替代共享与提交通道：Cindy 账号／服务端同步、device-link 直传、官方机器人代提交
  修改建议（2026-09-30 用户裁决不做）。

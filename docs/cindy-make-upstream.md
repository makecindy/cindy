# Cindy Make 上游 PR 查询

查询目标是与用户需求相关、但当前运行的 Cindy 尚未确认包含的 PR，不是全部 Issue，
也不是仅查询未合并或未发布内容。关键词命中只表示可能相关，不保证满足需求。

## 运行版本基准

- Main 构建时将源码 commit 和工作区是否干净注入 bundle；不新增运行期 Git 缓存 JSON。
- 发布包和 Beta 使用正在执行的 bundle 的身份，版本号仅展示渠道，不拿最新 release、
  可移动的 tag、准备好的源码目录或 `origin/main` 替代运行 commit。
- Dev 同样固定在该次 Main 构建的 commit；查询时检查构建源目录是否仍然干净、HEAD
  是否一致。它只用于检测失效，不会把新的 HEAD 当成正在运行的版本。
- Main watch 重编译会重新采集身份。Renderer 单独热更新、未提交改动、查询中切分支、
  缺少构建身份或 Git 检查失败时，保守保留候选并显示“是否包含尚未确认”。
- 发布构建临时改写 `package.json` 的版本号不算源码改动；除此之外的改动不豁免。

## 查询与包含判断

1. 对最多三个关键词分别查询开放 PR 和已合并 PR；Issue 不参与，也不按发布时间过滤。
2. 读取 PR 详情：已合并时使用合并后的 commit（包括 squash/rebase 结果），未合并时
   使用 PR head，不能使用 GitHub 为测试合并生成的 commit。已关闭且未合并的 PR 排除。
3. 优先使用 Dev 的本地 Git 对固定 commit 做只读祖先判断；否则使用 GitHub compare。
   已确认包含的 PR 被排除。确认在当前 commit 之后的 PR 标记“当前运行版本未包含”。
4. 分叉历史、无法证明等价的 cherry-pick、已知 revert、GitHub 不可比较、历史被截断、
   脏构建等情况保持未知，不将“查不到”当成“没有”，也不把未知候选静默移除。
5. 当前运行的是未合并 PR 分支时，也能通过 head 包含关系排除该 PR。

每个关键词/状态最多取十个结果，去重排序后最多核对二十个 PR，最多显示五个。
排除已包含结果后继续补充候选；未核对完时明确显示部分结果提示。查询总超时为 25 秒，
取消/超时不会误报“没有匹配”。详情或比较失败时保留对应候选，包含状态标记未知。

“已合并”不表示“已发布”，也不表示用户当前版本已包含。本查询不核实发布渠道、平台
或可更新版本，因此不会凭 PR 状态声称“升级即可获得”或“尚未发布”。

## 不变的边界

保持既有全局后台流程、源码准备和用户主动选择；不切分支、不合并 PR、不升级客户端。
历史消息中的 Issue 结果与缺少新字段的记录继续可读，新查询只产生 PR。
Main 负责网络和 Git，UI 只消费报告；运行版本摘要在结果详情内，主流程保持紧凑。

## 个人版任务准备

### 文件与分支边界（2026-09-18 用户更新裁决）

用户选择本地提交、合并与 rebase，替代此前只应用文件且永不提交的模型。`main` 只包含
官方提交，Cindy Make 永不推送远端。模型在任务 worktree 修改、验证并回报完成后，宿主在
该任务分支创建带 DCO 签名的本地提交；未成功结束的轮次不提交或生成完成卡。没有新改动
不制造空提交。通用自动保存点仍跳过托管目录，避免在明确完成边界之外提交。

生成个人版时先把功能分支的提交合入 `cindy-personal`，再从这个实际源码目录安装依赖、
检查、构建。临时目录用于检测冲突并形成候选合并提交，不在那里构建。成功合入后的
个人源码工作区保持干净；构建失败／取消保留已合入提交与任务，不回退源码。
旧完成记录只有文件树时仍能转换为本地提交。源码存在旧版未提交内容时先保存原 HEAD、
暂存树与文件树；若此前已应用官方文件但分支仍停在旧提交，以已记录的官方基线保存个人
差异，不把大量上游文件误当成个人功能提交。所有旧历史与文件备份通过本地引用保留。

获取官方更新时先固定当前渠道目标、更新本地 main，再在独立分支／worktree 中把个人提交
rebase 到新官方基线（禁止 update-refs 自动改动其他任务分支）。无冲突自动采纳；有冲突
自动创建独立任务，沿用当前模型设置。冲突解决并完整结束 rebase、校验个人源码未并发
变化后，才更新 cindy-personal。结果是“最新 main ＋ 个人提交”，不是要求两者 hash 相等；
官方更新不再堆积在未提交列表中。旧版遗留冲突现场仍可完成并迁移，新旧路径均不推送。
实现见 [localHistory](../apps/desktop/src/main/cindy-make/localHistory.ts) 与
[真实 Git 回归](../apps/desktop/src/main/cindy-make/__tests__/upstreamMerge.git-integration.test.ts)。

- 环境、个人版源码、任务分支和工作目录统一由 Main 的 `CindyMakeManager` 管理。
  源码准备／清理、任务工作目录创建／依赖安装、完成后的 Git 写操作共用项目队列，
  不再由 Settings、消息卡片或创建弹窗各自维护后台作业。发送入场与源码清理互斥，
  已进入发送事务或运行中的任务禁止清理源码；清理已开始时拒绝新的发送。
- Settings → Cindy Make 分为“版本控制”和“环境检查”两个页签，版本控制排在首位并默认打开。
  工具检查和 Dev 测试开关归环境检查；个人版源码、我的版本和制作历史归版本控制。
  当前使用版本、切换入口和个人版源码合为一张概览卡，制作历史紧随其后。切换只改变可见面板，保留检查／准备作业、版本列表展开状态与
  制作搜索内容；进入版本控制时重新读取版本列表。页签支持方向键、Home／End 及独立面板标识。
- 输入 /cindy-make 需求后，在当前页面弹窗检查环境、准备个人版源码并查询上游；
  这段前置流程不创建任务、不创建 worktree；源码准备与 Settings 共用同一流程，
  准备 Git 内容后按锁文件预热依赖缓存，不生成个人分支的依赖目录或执行安装脚本。
  关闭弹窗或选择等待上游不会留下空任务。Settings 的制作入口与侧栏入口复用同一个弹窗。
  实现与确认边界回归见 [CindyMakePreflightDialog](../apps/desktop/src/renderer/components/cindy-make/CindyMakePreflightDialog.tsx)
  及其[测试](../apps/desktop/src/renderer/components/cindy-make/__tests__/CindyMakePreflightDialog.test.tsx)。
- 选择「继续制作个人版」后，先创建带需求标题的任务并保存准备消息，再复核环境、
  个人项目源码、任务分支／工作目录和依赖。历史卡片缺少源码时也先创建任务，
  不让用户等待依赖安装结束才看到任务。首页和 Settings 直接创建这一个制作任务，
  不再为前置检查另建容器任务；已有任务入口继续继承来源任务的运行配置。
- Settings、消息卡片／弹窗和侧栏读取同一个 Main 快照；准备卡显示实际阶段、工具下载量、
  Git 阶段以及 pnpm 的解析／复用／下载／添加数量；安装开始与安装脚本执行另有状态提示，
  不伪造总进度。Settings 和前置弹窗均显示缓存预热的解析／复用／下载数量；
  缓存缺失或版本变化时按需补下载，任务 worktree 再复用缓存独立安装并执行安装脚本。
  Settings 源码卡的底部状态常驻：区分等待其他工程操作、Git 检查、上游版本查询和本地源码检查，
  源码目录直接显示，打开和删除按钮在路径行最右侧对齐，不提供源码详情折叠入口。
  失败或停止时保留结果和原因，按钮为「重试准备」；
  卡片进入页面即显示，先发布本机保存的源码摘要，再补 Git 版本与联网查询结果；
  不让工具发现或网络查询阻塞整张卡。重新进入保留已有信息，查询失败仍显示本地版本。
  各阶段共用同一刷新代次，迟到的查询不能覆盖之后的准备、清理或较新的查询结果。
  Settings 用「个人版 hash → 本地 main hash」展示本机关系，紧接着说明两者提交差距；
  下一行展示线上目标 hash 和本地 main 相对它的提交差距。不再显示制作分支、当前项目分支或重复的来源 hash。
  当前使用标签与原版／个人版名称使用相同字体、字号和字重；hash 使用等宽字体。
  线上目标版本与已核实的括号内差距使用成功色；省略领先／落后的零值，未知差距保持中性色。
  开发版查询 GitHub 最新 main，
  beta 查询最新已发布 beta 的 tag，正式版查询最新非 beta 发布的 tag；渠道之间不回退。
  能核实时显示本地 main 相对该版本的领先／落后提交数，查询失败不把缓存的 origin/main
  当作最新版本。查询只读、最长等待 10 秒，成功结果在进程内复用一分钟；
  实现与回归见 [latestSourceVersion](../apps/desktop/src/main/cindy-make/latestSourceVersion.ts)
  和[渠道查询测试](../apps/desktop/src/main/cindy-make/__tests__/latestSourceVersion.test.ts)。
  点击重试立即切换到本轮状态，不沿用上一轮错误或进度。
  准备不冒充 Agent 正在执行。
  首阶段检查及源码准备也按 runId 从 Main 读取完整报告；Renderer 重载不退回过时的保存卡片。
  Settings 重新检查后展示新检查，不用上一轮已完成的准备结果覆盖它。
- 准备成功后由 Main 自动发送原始需求，通过既有发送事务继承模型、供应商、推理档位、
  权限、计划模式与 Fast 设置。确认后的任务准备不因切换任务或重载 Renderer 中止，
  也不会丢失首次发送；确认前关闭弹窗则停止该轮前置检查。
- 确认后，完整准备卡替代普通输入区，显示步骤、下载／安装进度及停止／重试操作；
  直接复用输入框的背景和边框，详情限高滚动，操作留在固定底栏。环境、源码和依赖
  准备完成后立即恢复普通输入框，包括第一次自动执行；修改期间沿用普通任务的输入、
  语音、附件及停止操作。该任务自己的准备卡不再重复显示在消息流中，持久报告仍用于
  重载恢复，Settings 与来源任务中的卡片继续保留。Ask Question、Plan 和权限确认
  保持原有优先级。准备失败／取消时从准备卡重试；执行失败或中断使用既有恢复入口。
  已结束的执行记录优先于过时的准备报告，切换页面或重载不会重新锁住输入框。
  见 [CindyMakeComposerMask](../apps/desktop/src/renderer/components/cindy-make/CindyMakeComposerMask.tsx)
  和[生命周期回归](../apps/desktop/src/renderer/lib/__tests__/cindyMakeComposer.test.ts)。
- 每轮修改完成回报落库后，本机制作任务在输入区显示“修改已完成，选择下一步”，沿用输入框
  背景和边框，状态、说明与已核实的文件信息合为一个内容区，不重复显示“修改源码”步骤；
  底栏提供“继续修改”“启动隔离版测试”和“生成个人版”。同一完成记录
  不再重复出现在本机消息流。继续修改需 Main 确认并持久化，重载不恢复已收起的旧卡；
  新的用户消息或下一次完成回报会取代旧结果。提问、计划和权限交互保持原有优先级。
- 修改回复结束但缺少新的完成回报，或重新打开待恢复任务时，本机任务复用原有输入区
  流程卡的“继续测试”状态，与输入框互斥，不在输入框上方另建卡片。点击“检查并继续”沿用本任务的正常发送
  流程核对当前修改，检查通过并重新回报后恢复测试／生成个人版卡片，不需要用户输入工具名。
  点击“继续修改”收起当前流程卡并恢复输入，同一结果不立即抢回输入；下一轮结束后再次显示。
  恢复状态不把旧完成记录或一条成功回复当作当前代码已完成的凭据，
  不自动启动测试或生成个人版；发送失败可以重试，运行、排队或等待交互时不抢占原流程。
- 测试必须由用户点击启动。Main 只接受当前账号的本机制作任务及最新完成记录，检查
  工作目录仍属于托管 worktree、没有链接替换、分支与原有 HEAD 匹配，且文件内容与完成
  时的 tree 一致，然后经既有开发版启动器启动独立命名的隔离实例。旧完成记录沿用干净
  HEAD 的核验。PTY 保留启动器的终端语义，
  不另开命令行窗口；环境只保留系统及工具配置，包含 Linux 的 X11／Wayland、桌面会话和
  D-Bus 连接变量，不继承宿主 profile、凭证和 Node 注入；版本切换复用同一白名单。
  测试启动单独注入环境检查已验证的 pnpm 绝对入口，不继承宿主的 `npm_execpath`，
  避免 Windows 的命令包装脚本从任务目录误找 pnpm 安装文件；已有任务的旧启动脚本同样适用。
  只有与目标目录、commit、隔离名及区域匹配的 ready 回执才显示已启动，不能把它当作
  用户验收通过。状态写入该完成记录并沿用消息推送；切换页面不取消启动。
  启动卡片另起一行显示当前步骤：等待启动、环境检查、修改核验、隔离实例准备、依赖、
  运行资源及编译启动。启动期间禁用“继续修改”，Main 同样拒绝此操作；启动完成或失败后
  恢复。失败保留中断步骤和已知错误原因，提供“重试启动”，重试清除上次错误与步骤。
  步骤只记录白名单标识，不保存或展示终端原始输出；旧源码仍从固定阶段前缀读取粗粒度进度。
  设置页历史直接投影同一完成记录的测试状态、步骤与错误，复用任务卡的消息推送和
  Main 启动控制器的重启恢复；失败显示同一重试入口，启动中不开放修改或清理。
  本机主日志的 `cindy-make-test` 记录任务／完成记录标识、阶段、耗时、退出码及白名单启动器
  失败码；失败标记后的跨块 `code=` 也会保留，不记录原始输出、环境或自由文本错误。
  见 [启动控制器](../apps/desktop/src/main/cindy-make/testController.ts) 和
  [完成卡回归](../apps/desktop/src/renderer/components/cindy-make/__tests__/CindyMakeTestCard.test.tsx)。
- “生成个人版”同样由用户点击触发：固定本次完成的提交和文件树，在临时工作目录与
  当前 cindy-personal 合并，无冲突则将本地合并提交采纳到个人版并保存合入记录。
  旧版仅含文件树的完成记录兼容转换为本地提交。随后依赖安装、相关单测、类型检查与打包都在
  `source` 目录的 `cindy-personal` 分支执行，使用既有版本无关打包入口，保留 packaged smoke。
  校验安装包的区域、架构、commit 与 SHA-256，保存到本机专属产物目录后，重新核对任务
  与个人版文件没有变化。冲突不影响个人版原文件；合入后检查／打包失败或取消，
  两个工作目录的源码都保留，重试从已合入记录继续，失败产物不进入版本列表。
  同一源码从合入直到成品保存与清理全程持有项目锁，其他源码操作排队；临时合并目录
  在结束后清理，个人版源码与依赖保留供下次生成复用。除安装包外，将完整可运行
  应用保存成独立快照（Windows 完整目录、macOS 完整 .app），保留签名、执行权限与
  包内相对链接；外部链接拒绝进入快照。成品位于独立的 `userData/cindy-versions`，清理
  源码不删除成品。检查、打包与保存完成后才登记到版本列表，生成不自动启用、安装或发布。
  新源码声明启动协议后，完成卡按钮变成“切换到此个人版”；旧源码／旧完成记录继续保留
  “查看安装包”，不声称不具备协议的旧程序能够接管当前数据。
- 个人版排队、合并、检查、打包及保存期间，完成卡三个操作全部禁用，成功或失败后恢复；
  “继续修改”不作为生成期间的取消入口。继续修改会停止本次测试进程，退出宿主会取消
  构建；文件合入已经开始时完成合入记录并保留源码，成品登记完成时保留成功产物及
  回执。运行与清理完成前保持工作目录占用，避免误删。应用重启不自动重放启动或构建，
  旧在途状态按已中断呈现，可显式重试。手机在已有 Cindy Make 任务中显示同一份准备、测试与生成状态，
  包括测试启动步骤、失败重试、继续修改及缺少完成登记时的“检查并继续”。操作由被控电脑执行；
  手机通过 Remote Resource 通道读取状态、调用已登记操作，不新增业务 invoke 白名单。
  个人版创建入口、成品启用／切换仍在本机 Desktop；远端 Desktop 保留完成记录与输入框。
  设置页制作历史在生成期间收敛为一个状态卡，显示合并、检查（依赖／测试／类型）、打包和保存步骤，
  提供“停止制作”。停止只中止本次构建进程，并清理临时合并目录、未完成安装包、打包输出和构建元数据；
  完成卡与设置页显示同一次构建的身份、进度和停止状态，从任一入口都能停止；
  离开页面不会丢失进度，旧构建的停止请求不能取消重试产生的新构建。

## 获取官方更新与解决冲突

- Settings 的单行版本比较右侧仅保留「获取最新」图标，带悬停说明与点击确认框，
  底部不重复放更新按钮；首次准备、失败重试与停止按钮保留。
  确认后重新查询当前运行渠道的最新提交，不复用展示用的缓存。
- Main 拉取固定官方提交，保存个人历史／文件与 main 的备份，再更新 main。
  旧个人目录的未提交修改先转成本地提交；有未结束的 Git 操作或 main 含非目标提交时停止。
- rebase 在托管的独立目录中进行；只重放官方基线之后的个人提交，main 不接收个人提交。
  无冲突自动采纳；冲突时原个人源码保持可用，自动创建一个独立任务。重复点击不重复创建。
  个人历史中的 merge 提交若含额外修改／冲突处理结果，普通 rebase 可能漏掉这些内容；
  Main 通过 remerge 差异识别后，即使 rebase 没有文本冲突也先创建核对任务，保留原个人目录，
  待核对原功能并补回遗漏后再采纳。
- 冲突任务使用独立 source `cindy-make-merge`，归入 Cindy Make 侧栏分组，标题使用
  工作目录的四位标记。它不继承普通制作任务的每轮说明、完成回报工具、隔离测试或
  生成个人版卡片。首条用户需求由 Main 固定组装，要求理解双方修改、保留本地功能、
  安全解决冲突，并按仓库规则验证。允许暂存并继续现有 rebase，不重新开始、不跳过个人
  提交、不修改其他目录，也不推送；结束后宿主提交必要的附加修复。
- 正常执行结束后，Main 核验目录归属、分支身份、原有 HEAD、文件冲突状态及
  `git diff --check`，再应用结果。自动检查不代表功能测试已通过；功能验证由解决冲突的
  任务执行并如实说明。个人版期间发生变化则停止应用并保留现场；中断、失败或
  continuation 边界不应用结果。旧文件合并现场可保留 MERGE_HEAD，解决后由宿主将个人
  差异迁移为本地提交，既有历史保留备份。
- 操作和任务绑定持久化到 userData；重启不静默重放 Git 写操作，重复点击复用任务。
  创建任务前先持久化任务 ID；账号切换后不发送旧请求、不暴露另一账号的任务入口。
  已删除或归档的任务由下一次显式解决冲突操作创建新任务，继续使用保留的工作目录。
  未完成的合并禁止清理源码；缺失的合并目录不会被普通恢复流程重建为空目录。
- 没有任务的自动合并成功后，仅在候选提交和文件树与已采纳结果一致、提交仍被个人版包含时
  移除临时 worktree，再核对分支没有被其他 worktree 使用，以原提交值原子删除对应的
  `cindy-merge/<ID>` 临时分支；`refs/cindy-make/backups/*` 等恢复引用继续保留。冲突任务的目录和
  分支继续保留，便于查看与继续交流。仅支持本机 Desktop，不增加远控调用权限。

实现见 [Git 合并](../apps/desktop/src/main/cindy-make/upstreamMerge.ts)、
[生命周期](../apps/desktop/src/main/cindy-make/upstreamMergeController.ts)、
[独立任务](../apps/desktop/src/main/cindy-make/upstreamMergeSession.ts)；

覆盖无冲突自动应用、冲突隔离与期间新增未提交个人改动的保护。

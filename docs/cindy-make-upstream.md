# Cindy Make 上游 PR 查询

查询目标是与用户需求相关、但当前运行的 Cindy 尚未确认包含的 PR，不是全部 Issue，
也不是仅查询未合并或未发布内容。关键词命中只表示可能相关，不保证满足需求。

## 运行版本基准

- Main 构建时将源码 commit 和工作区是否干净注入 bundle；不新增运行期 Git 缓存 JSON。
- 发布包和 Beta 使用正在执行的 bundle 的身份，版本号仅展示渠道，不拿最新 release、
  可移动的 tag、准备好的源码目录或 `origin/main` 替代运行 commit。
- Dev 同样固定在该次 Main 构建的 commit；查询时检查构建源目录是否仍然干净、HEAD
  是否一致。它只用于检测失效，不会把新的 HEAD 当成正在运行的版本。
- Main watch 重编译会重新采集身份。Renderer 单独热更新、未提交改动、查询中切分支、
  缺少构建身份或 Git 检查失败时，保守保留候选并显示“是否包含尚未确认”。
- 发布构建临时改写 `package.json` 的版本号不算源码改动；除此之外的改动不豁免。

## 查询与包含判断

1. 对最多三个关键词分别查询开放 PR 和已合并 PR；Issue 不参与，也不按发布时间过滤。
2. 读取 PR 详情：已合并时使用合并后的 commit（包括 squash/rebase 结果），未合并时
   使用 PR head，不能使用 GitHub 为测试合并生成的 commit。已关闭且未合并的 PR 排除。
3. 优先使用 Dev 的本地 Git 对固定 commit 做只读祖先判断；否则使用 GitHub compare。
   已确认包含的 PR 被排除。确认在当前 commit 之后的 PR 标记“当前运行版本未包含”。
4. 分叉历史、无法证明等价的 cherry-pick、已知 revert、GitHub 不可比较、历史被截断、
   脏构建等情况保持未知，不将“查不到”当成“没有”，也不把未知候选静默移除。
5. 当前运行的是未合并 PR 分支时，也能通过 head 包含关系排除该 PR。

每个关键词/状态最多取十个结果，去重排序后最多核对二十个 PR，最多显示五个。
排除已包含结果后继续补充候选；未核对完时明确显示部分结果提示。查询总超时为 25 秒，
取消/超时不会误报“没有匹配”。详情或比较失败时保留对应候选，包含状态标记未知。

“已合并”不表示“已发布”，也不表示用户当前版本已包含。本查询不核实发布渠道、平台
或可更新版本，因此不会凭 PR 状态声称“升级即可获得”或“尚未发布”。

## 不变的边界

保持既有全局后台流程、源码准备和用户主动选择；不切分支、不合并 PR、不升级客户端。
历史消息中的 Issue 结果与缺少新字段的记录继续可读，新查询只产生 PR。
Main 负责网络和 Git，UI 只消费报告；运行版本摘要在结果详情内，主流程保持紧凑。

## 个人版任务准备

### 文件与分支边界（2026-09-18 用户更新裁决）

用户选择本地提交、合并与 rebase，替代此前只应用文件且永不提交的模型。`main` 只包含
官方提交，永不推送到官方仓。Cindy Make 对远端的唯一写操作是「个人 fork 同步」一节
允许的推送：仅 `cindy-personal` 与其官方基线记录，仅推到用户自己显式绑定的 fork
（2026-09-22 用户裁决，替代此前“永不推送远端”）。模型在任务 worktree 修改、验证并回报完成后，宿主在
该任务分支创建带 DCO 签名的本地提交；未成功结束的轮次不提交或生成完成卡。没有新改动
不制造空提交。通用自动保存点仍跳过托管目录，避免在明确完成边界之外提交。

生成个人版是否先同步最新官方源码，由设置页「生成前同步最新源码」控制，默认关闭。开启时先
复用既有官方源码同步流程，同步完成后把功能分支的提交合入 `cindy-personal`；关闭时直接使用
当前 `cindy-personal`。随后都从这个实际源码目录安装依赖、
检查、构建。临时目录用于检测冲突并形成候选合并提交，不在那里构建。成功合入后的
个人源码工作区保持干净。按 2026-09-20 用户裁决，生成失败／取消时自动撤回尚未生成成功版本的
连续合入，恢复此前个人源码，保留任务分支、每轮修改与已经生成的版本；再次生成会自动重新合入。
恢复前核验分支、提交、文件树和工作区，发现并发修改时保留现场并报告清理未完成，不覆盖用户修改。
撤回过程保留失败提交的本地引用，并持久化待清理记录，确保 Git 已恢复而历史写入失败时可以接着清理。
旧完成记录只有文件树时仍能转换为本地提交。源码存在旧版未提交内容时先保存原 HEAD、
暂存树与文件树；若此前已应用官方文件但分支仍停在旧提交，以已记录的官方基线保存个人
差异，不把大量上游文件误当成个人功能提交。所有旧历史与文件备份通过本地引用保留。

获取官方更新时先固定当前渠道目标、更新本地 main，再在独立分支／worktree 中把个人提交
rebase 到新官方基线（禁止 update-refs 自动改动其他任务分支）。无冲突自动采纳；有冲突
手动同步时先弹窗询问，确认后才创建独立任务并沿用当前模型设置；取消则放弃本次合入、保留个人版。冲突解决并完整结束 rebase、校验个人源码未并发
变化后，才更新 cindy-personal。结果是“最新 main ＋ 个人提交”，不是要求两者 hash 相等；
官方更新不再堆积在未提交列表中。旧版遗留冲突现场仍可完成并迁移，新旧路径均不推送官方仓；
采纳后若已开启 fork 同步，由宿主按「个人 fork 同步」一节推送 `cindy-personal`。
实现见 [localHistory](../apps/desktop/src/main/cindy-make/localHistory.ts) 与
[真实 Git 回归](../apps/desktop/src/main/cindy-make/__tests__/upstreamMerge.git-integration.test.ts)。

每次创建制作任务时，在创建任务分支和工作目录之前，必须沿用当前源码渠道重新获取官方目标，
并把 `cindy-personal` 更新到最新官方基线（2026-09-22 用户裁决）。有冲突时进入既有独立
处理任务，源码准备等待冲突解决、采纳与清理完成；同步失败、取消或账号切换均不创建任务
worktree。停止准备会停止本次准备所拥有的冲突任务并清理候选目录，已经完成的官方同步保留。
同步成功后才从更新后的 `cindy-personal` 创建任务分支，因此任务从一开始就在最新个人版源码上
修改。制作任务准备卡在“准备个人项目源码”和“创建任务分支和工作目录”之间单独显示
“正在更新个人版源码”；发生冲突时该步骤保持进行中，直到独立冲突任务完成采纳与清理。
Settings 的手动“同步最新源码”继续可用。创建制作任务前的同步仍为固定流程；另设的
“生成前同步最新源码”开关只控制打包入场，默认关闭。

生成个人版时，若“生成前同步最新源码”已开启，则先把 `cindy-personal` 更新到当前渠道的最新
官方基线；该步骤在进度中单独显示，冲突沿用既有独立处理任务，完成后才继续合入修改和打包。
开关关闭时把任务修改合入当前个人版基线后直接检查和打包。后续生成失败只撤回未生成成功版本的功能
合入。手机／远程资源沿用主机翻译后的准备状态和既有动作。实现与回归见
[任务准备](../apps/desktop/src/main/cindy-make/taskRuntime.ts)、
[同步运行时](../apps/desktop/src/main/cindy-make/upstreamMergeRuntime.ts) 和
[创建顺序测试](../apps/desktop/src/main/cindy-make/__tests__/taskRuntime.test.ts)。

- 环境、个人版源码、任务分支和工作目录统一由 Main 的 `CindyMakeManager` 管理。
  源码准备／清理、任务工作目录创建／依赖安装、完成后的 Git 写操作共用项目队列，
  不再由 Settings、消息卡片或创建弹窗各自维护后台作业。发送入场与源码清理互斥，
  已进入发送事务或运行中的任务禁止清理源码；清理已开始时拒绝新的发送。
- Settings → Cindy Make 分为“版本控制”和“环境检查”两个页签，版本控制排在首位并默认打开。
  工具检查和 Dev 测试开关归环境检查；个人版源码、我的版本和制作历史归版本控制。
  创建个人版本入口保留在版本控制页签内、概览卡上方，使用纯文字按钮，不显示加号。
  当前使用版本、切换入口和个人版源码合为一张概览卡，下方显示制作历史。切换只改变可见面板，保留检查／准备作业、版本列表展开状态与
  制作搜索内容；进入版本控制时立即重新读取版本、源码与制作历史。后台生成到达成功、失败或取消终态时，
  Main 主动通知设置页重读历史与版本，5 秒轮询只作异常兜底，不作为正常完成反馈。页签支持方向键、Home／End 及独立面板标识。
- 输入 /cindy-make 需求后，在当前页面弹窗检查环境、准备个人版源码并查询上游；
  这段前置流程不创建任务、不创建 worktree；源码准备与 Settings 共用同一流程，
  准备 Git 内容后按锁文件预热依赖缓存，不生成个人分支的依赖目录或执行安装脚本。
  关闭弹窗不会留下空任务。Settings 的制作入口与侧栏入口复用同一个弹窗。
  前置弹窗通过右上角关闭图标退出，不再单设底部取消；图标、Esc 和遮罩点击均先二次确认，
  提示随当前阶段更新，说明关闭会停止什么、保留什么；环境／源码准备还须说明设置页共享作业也会停止。
  确认框内选择继续查看不打断准备；正在创建制作任务时暂时禁止关闭。
  检查完成后，「继续制作个人版」只显示在弹窗底部，不在报告卡中重复；关闭确认期间暂时禁用。
  实现与确认边界回归见 [CindyMakePreflightDialog](../apps/desktop/src/renderer/components/cindy-make/CindyMakePreflightDialog.tsx)
  及其[测试](../apps/desktop/src/renderer/components/cindy-make/__tests__/CindyMakePreflightDialog.test.tsx)。
- 选择「继续制作个人版」后，先创建带需求标题的任务并保存准备消息，再复核环境和
  个人项目源码；把 `cindy-personal` 更新到最新官方基线并处理完冲突后，才创建任务分支／
  工作目录并安装依赖。历史卡片缺少源码时也先创建任务，
  不让用户等待依赖安装结束才看到任务。首页和 Settings 直接创建这一个制作任务，
  不再为前置检查另建容器任务；已有任务入口继续继承来源任务的运行配置。
- Settings、消息卡片／弹窗和侧栏读取同一个 Main 快照；准备卡显示实际阶段、工具下载量、
  Git 阶段以及 pnpm 的解析／复用／下载／添加数量；安装开始与安装脚本执行另有状态提示，
  不伪造总进度。Settings 和前置弹窗均显示缓存预热的解析／复用／下载数量；
  缓存缺失或版本变化时按需补下载，任务 worktree 再复用缓存独立安装并执行安装脚本。
  Settings 源码准备和更新共用一个状态区域：区分等待其他工程操作、Git 检查、上游版本查询和本地源码检查。
  源码目录直接显示，打开和删除按钮在路径行最右侧对齐，不提供源码详情折叠入口。
  源码准备失败或停止时保留结果和原因，按钮为「重试准备」；更新失败或冲突时显示原因及处理入口。
  源码更新操作共用一个位置：正常显示“同步最新源码”，待处理冲突时替换为“处理冲突”，
  已有处理任务时在同处提供查看入口；底部只显示状态与原因，不重复摆放操作按钮。
  待处理冲突禁止生成个人版，但不阻止切换已经生成的应用版本；版本切换不要求当前没有
  正在执行的任务，切换会结束当前进程，目标版本启动后按既有中断恢复继续任务。制作任务卡
  与设置页均遵守此边界；删除个人版仍保留运行中任务保护。
  更新成功只提示一次，随后显示个人版与 main 的版本差距，不再常驻「源码改动已合入」或
  「个人版源码已准备好」。旧更新回执不遮挡后续源码准备与重试；仍有未处理更新工作区时保留冲突处理入口。
  卡片进入页面即显示，先发布本机保存的源码摘要，再补 Git 版本与联网查询结果；
  不让工具发现或网络查询阻塞整张卡。重新进入保留已有信息，查询失败仍显示本地版本。
  各阶段共用同一刷新代次，迟到的查询不能覆盖之后的准备、清理或较新的查询结果。
  Settings 用「个人版 hash → 本地 main hash」展示本机关系，紧接着说明两者提交差距；
  下一行展示线上目标 hash 和本地 main 相对它的提交差距。不再显示制作分支、当前项目分支或重复的来源 hash。
  当前使用标签与原版／个人版名称使用相同字体、字号和字重；hash 使用等宽字体。
  线上目标版本与已核实的括号内差距使用成功色；省略领先／落后的零值，未知差距保持中性色。
  开发版查询 GitHub 最新 main，
  beta 查询最新已发布 beta 的 tag，正式版查询最新非 beta 发布的 tag；渠道之间不回退。
  能核实时显示本地 main 相对该版本的领先／落后提交数，查询失败不把缓存的 origin/main
  当作最新版本。查询只读、最长等待 10 秒，成功结果在进程内复用一分钟；
  实现与回归见 [latestSourceVersion](../apps/desktop/src/main/cindy-make/latestSourceVersion.ts)
  和[渠道查询测试](../apps/desktop/src/main/cindy-make/__tests__/latestSourceVersion.test.ts)。
  点击重试立即切换到本轮状态，不沿用上一轮错误或进度。
  准备不冒充 Agent 正在执行。
  首阶段检查及源码准备也按 runId 从 Main 读取完整报告；Renderer 重载不退回过时的保存卡片。
  Settings 重新检查后展示新检查，不用上一轮已完成的准备结果覆盖它。
- 准备成功后由 Main 自动发送原始需求，通过既有发送事务继承模型、供应商、推理档位、
  权限、计划模式与 Fast 设置。确认后的任务准备不因切换任务或重载 Renderer 中止，
  也不会丢失首次发送；确认前关闭弹窗则停止该轮前置检查。
- 确认后，完整准备卡替代普通输入区，显示步骤、下载／安装进度及停止／重试操作；
  直接复用输入框的背景和边框，详情限高滚动，操作留在固定底栏。环境、源码和依赖
  准备完成后立即恢复普通输入框，包括第一次自动执行；修改期间沿用普通任务的输入、
  语音、附件及停止操作。该任务自己的准备卡不再重复显示在消息流中，持久报告仍用于
  重载恢复，Settings 与来源任务中的卡片继续保留。Ask Question、Plan 和权限确认
  保持原有优先级。准备失败／取消时从准备卡重试；执行失败或中断使用既有恢复入口。
  已结束的执行记录优先于过时的准备报告，切换页面或重载不会重新锁住输入框。
  见 [CindyMakeComposerMask](../apps/desktop/src/renderer/components/cindy-make/CindyMakeComposerMask.tsx)
  和[生命周期回归](../apps/desktop/src/renderer/lib/__tests__/cindyMakeComposer.test.ts)。
- 每轮修改完成回报落库后，本机制作任务在输入区显示“修改已完成，选择下一步”，沿用输入框
  背景和边框，状态、说明与已核实的文件信息合为一个内容区，不重复显示“修改源码”步骤；
  底栏提供“继续修改”“启动隔离版测试”和“生成个人版”。同一完成记录
  不再重复出现在本机消息流。继续修改需 Main 确认并持久化，重载不恢复已收起的旧卡；
  新的用户消息或下一次完成回报会取代旧结果。提问、计划和权限交互保持原有优先级。
- 点击“继续修改”直接恢复输入框，重新打开任务也不再出现“继续测试／检查并继续”的拦截卡。
  输入框上沿保留“启动隔离测试版”和“生成个人版”两个轻量按钮，修改回复结束但缺少完成回报时也可使用。
  只有点击按钮后，Main 才核对账号、任务、最新回复和托管目录，登记当前源码快照并直接执行所选操作；
  不额外发送 Agent 检查消息，也不增加一次确认。新的快照不继承旧测试或旧生成成功状态，
  原有的源码一致性检查、测试启动检查和生成检查继续执行。新消息、目录变更或账号切换会拒绝过期操作。
  检查失败可重试；打开任务不自动启动测试或生成，运行、排队或等待交互时不抢占原流程。
- 测试必须由用户点击启动。Main 只接受当前账号的本机制作任务及最新完成记录，检查
  工作目录仍属于托管 worktree、没有链接替换、分支与原有 HEAD 匹配，且文件内容与完成
  时的 tree 一致，然后经既有开发版启动器启动独立命名的隔离实例。旧完成记录沿用干净
  HEAD 的核验。PTY 保留启动器的终端语义，
  不另开命令行窗口；环境只保留系统及工具配置，包含 Linux 的 X11／Wayland、桌面会话和
  D-Bus 连接变量，不继承宿主 profile、凭证和 Node 注入；版本切换复用同一白名单。
  测试启动单独注入环境检查已验证的 pnpm 绝对入口，不继承宿主的 `npm_execpath`，
  避免 Windows 的命令包装脚本从任务目录误找 pnpm 安装文件；已有任务的旧启动脚本同样适用。
  新源码通过仅限开发隔离实例的 `XDT_CINDY_MAKE_TEST=1` 标记识别测试窗口：
  窗口就绪后复用现有主窗口激活路径带到前台，关闭窗口直接退出测试进程，
  不进入托盘／最小化选择。普通开发版和已安装版本保持原有窗口行为；旧源码不识别
  该标记时仍沿用原行为。测试版的登录、设置与持久数据保留在原有隔离目录，
  不随关窗删除；源码、依赖和已生成个人版同样保留。每次启动创建独立临时目录，
  仅对子进程覆写 `TMPDIR`／`TMP`／`TEMP`，让新旧启动器的启动与重启标记集中在其中。
  正常退出、启动失败或停止后回收该目录，目录被替换时拒绝清理；清理失败仅记录固定原因码。
  macOS／Linux 停止 PTY 的进程组，Windows 由 ConPTY 回收所属进程；未收到退出回执时
  不清理仍在使用的临时文件。继续修改和生成个人版等待退出最多 10 秒，超时明确提示先关闭
  测试窗口再重试，仍保留工作目录租约，直到收到真实退出回执；不能假报退出后开始修改或构建。

  用户验收通过。状态写入该完成记录并沿用消息推送；切换页面不取消启动。

  待处理的冲突工作区仍依赖已合入的前缀，因此此时保留个人源码基线，待冲突处理后再显式制作；
  没有待处理冲突工作区时，失败清理沿用下述撤回规则。不在重启后重放批量操作。
  每条可测试的待合入记录沿用同一隔离测试控制器；已启动时提供「重新启动隔离版」，

  已结束的任务可通过待合入多选使用保留的完成快照，无需仍存在的制作工作目录，也不创建虚假的任务。
  生成时在源码锁内记录实际包含的操作，成功后立即刷新版本列表。任务完成卡按钮始终叫
  「生成个人版」，失败后保持同一入口；历史卡的全局入口明确叫「重新生成个人版」。失败或取消自动撤回
  尚未成功生成的合入，保留任务修改与原有应用成品；清理未完成时显示原因，再次生成前继续清理。

  回退到检查中，不改变已有状态含义。

  完成卡的直接生成同样先走这条合入流程，遇到冲突先处理冲突再生成。
  实现与回归见 [historyRuntime](../apps/desktop/src/main/cindy-make/historyRuntime.ts)、
  [动作准入](../apps/desktop/src/shared/cindyMakeHistory.ts) 与
  [合入／撤销真实 Git 测试](../apps/desktop/src/main/cindy-make/__tests__/featureHistory.git-integration.test.ts)。

## 获取官方更新与解决冲突

- Settings 的单行版本比较右侧仅保留「获取最新」图标，带悬停说明与点击确认框，
  底部不重复放更新按钮；首次准备、失败重试与停止按钮保留。
  确认后重新查询当前运行渠道的最新提交，不复用展示用的缓存。
- Main 拉取固定官方提交，保存个人历史／文件与 main 的备份，再更新 main。
  旧个人目录的未提交修改先转成本地提交；有未结束的 Git 操作或 main 含非目标提交时停止。
- rebase 在托管的独立目录中进行；只重放官方基线之后的个人提交，main 不接收个人提交。
  无冲突自动采纳；冲突时原个人源码保持可用，先弹出二次确认。确认后创建独立任务，
  由 Agent 自动处理并打开该任务；取消则放弃本次合入，不创建任务。重复点击不重复创建。
  个人历史中的 merge 提交若含额外修改／冲突处理结果，普通 rebase 可能漏掉这些内容；
  Main 通过 remerge 差异识别后，即使 rebase 没有文本冲突也先询问，确认后才创建核对任务，保留原个人目录，
  待核对原功能并补回遗漏后再采纳。
- 冲突任务使用独立 source `cindy-make-merge`，归入 Cindy Make 侧栏分组，标题使用
  工作目录的四位标记。它不继承普通制作任务的每轮说明、完成回报工具、隔离测试或
  生成个人版卡片。  首条用户需求由 Main 固定组装，要求理解双方修改、保留本地功能、
  安全解决冲突，并按仓库规则验证。允许暂存并继续现有 rebase，不重新开始、不跳过个人
  提交、不修改其他目录，也不推送；结束后宿主提交必要的附加修复。任务本身永不推送；
  采纳后向 fork 的推送只由宿主按「个人 fork 同步」一节执行。
- 正常执行结束后，Main 核验目录归属、分支身份、原有 HEAD、文件冲突状态及
  `git diff --check`，再应用结果。自动检查不代表功能测试已通过；功能验证由解决冲突的
  任务执行并如实说明。个人版期间发生变化则停止应用并保留现场；中断、失败或
  continuation 边界不应用结果。旧文件合并现场可保留 MERGE_HEAD，解决后由宿主将个人
  差异迁移为本地提交，既有历史保留备份。
- 操作和任务绑定持久化到 userData；重启不静默重放 Git 写操作，重复点击复用任务。
  更新从发起时即绑定账号；确认和取消携带本次操作 ID，旧弹窗不能处置后来的更新。
  离开设置或切换账号时关闭待确认弹窗、保留冲突现场；再次进入可从「处理冲突」重新选择。
  创建任务前先持久化任务 ID；账号切换后不发送旧请求、不暴露另一账号的任务入口。
  已删除或归档的任务由下一次显式解决冲突操作创建新任务，继续使用保留的工作目录。
  未完成的合并禁止清理源码；缺失的合并目录不会被普通恢复流程重建为空目录。
- 取消只适用于尚未创建处理任务的官方更新：核验托管目录及分支归属，退出候选目录中的
  rebase／merge，再正常移除临时 worktree，以原提交值原子删除临时分支。个人源码、
  已获取的官方 main 和恢复备份继续保留。先持久化取消选择，再执行清理；清理失败或中断
  保留原因和「重试取消」入口，重启不会误开解决任务，清理完成前仍阻止后续更新、合入和生成。
  不能强制删除新增文件、被锁定或已由任务使用的目录。取消完成后可再次更新。
- 合并成功并记录采纳结果后，清理对应的临时 worktree 和 `cindy-merge/<ID>` 分支。
  有冲突处理任务时，先归档任务、保留交流记录并等待运行进程退出，再核验目录、分支、
  提交和文件树与采纳结果一致，且没有其他任务占用。清理只删除本次托管目录与精确分支引用，
  新增文件或提交继续保留；个人源码和 `refs/cindy-make/backups/*` 等恢复引用不受影响。
  若打包失败已回退个人源码，只有采纳提交仍被对应的失败构建恢复引用保存时才能补做清理。
  Windows 上 Git 返回移除成功后仍可能留下依赖 junction；必须确认实际目录消失后才删除分支。
  已失去 Git 登记和 `.git` 的旧清理残留（包括分支已删的情况），核验采纳提交仍被保留后，
  只补删 `node_modules` 内的链接和空目录，不跟进链接目标；任何剩余普通文件都保留并等待重试。
  清理失败持久化为待清理，下次显式生成或更新时先完成清理，再建立新的合并目录；重启不会
  自动删除目录。仅支持本机 Desktop，不增加远控调用权限。
- 生成个人版包括合并、处理冲突、清理、检查与打包。发生冲突时，本次生成保持运行，
  完成卡、制作历史和手机任务卡显示「处理冲突」；进度列表与生成记录也保留此步骤。
  冲突处理完成并通过采纳核验后，自动清理临时目录和分支，继续检查与打包，无需再次点击生成。
  生成进度下方直接显示当前执行状态的单行日志，不放“打开处理任务”按钮。检查与打包显示最新一行
  已脱敏的进程输出，长内容省略；尚无输出时显示当前阶段。密集输出合并更新，步骤切换、停止和结束
  不得回放旧日志。手机资源投影沿用同一行状态，阶段记录仍保持可展开查看。处理任务的交流记录
  继续保留，清理目录及归档后从既有任务入口回看，不重建目录。
  在处理任务中点击停止时，立即记录中断并结束本次生成等待；迟到的发送回调、完成事件不能
  恢复处理、另建任务、继续采纳或打包。停止之后发起的新消息被接受后才能继续处理原任务，
  不会恢复已结束的生成。打开任务本身也不恢复运行。重启保留任务绑定和生成记录，不重放 Git。
  正常结束后若同一步仍有未解决冲突，保留原任务并显示检查失败，不反复创建处理任务；
  只有已推进到后续改动的新冲突才自动继续，每一步使用独立的消息标记并留在同一个任务中。
  批量生成等待当前条目完成这套流程，才合入下一项。真正的失败或中断才结束生成。
  「停止制作」在桌面卡片、历史面板和手机上均需二次确认：确认后停止本次关联的冲突任务，
  归档并等待运行进程退出，核验无人借用后丢弃临时冲突修改、移除对应 worktree 与分支，
  再撤回尚未生成成功版本的合入。原制作任务的修改、交流记录与已生成版本保留。
  正在执行的 Git 采纳先完成结果记录，再回退；迟到的任务完成事件不能重新合入或触发打包。
  清理和回退全部完成前保留取消标记，失败后可重试；重启只恢复状态，不自动删除。
  应用退出与处理任务内的停止保留冲突现场，重启不自动续跑，区别于已确认的「停止制作」。
  每次重新生成都按当前源码和修改记录重新计算合并；此前生成失败撤回的合入不会作为可复用的
  合并结果，因此相同改动再次发生冲突属于可能情况。

实现见 [Git 合并](../apps/desktop/src/main/cindy-make/upstreamMerge.ts)、

## 个人 fork 同步（2026-09-22 用户裁决，设计稿，尚未实现）

目标：本机检测到可用的个人 GitHub 身份时，个人版源码以用户自己 fork 出来的
`<login>/cindy` 作为「个人版远端仓库」。`cindy-personal` 仍是唯一的个人版分支，仍在本机
记录、合入与生成；区别只是它同时被推送到 fork，换一台机器、同一 GitHub 账号即可取回，
fork 也为日后向官方仓提 PR 留出入口。没有可用身份时，行为与本节之前完全一致。

### 身份来源与凭证边界

- 第一阶段只接受 GitHub CLI 的登录态，复用
  [ghCliTokenSource](../apps/desktop/src/main/git-context/ghCliTokenSource.ts)：`gh` 未安装、
  未登录、超时都视为“没有身份”，源码与生成逻辑走原路径。身份只在「首次选择」一步和
  Settings 的「开启同步」处被询问；不在其他时机弹窗、不自动安装 gh。
  git credential helper、SSH key、粘贴 PAT 与 Cindy 内置 GitHub 登录（OAuth Device Flow）
  都不在第一阶段范围；后者需要仓外注册 OAuth App，用户裁决本轮不做。
- token 只在内存，沿用 ghCliTokenSource 的缓存。Git 访问 fork 时用进程环境
  `GIT_CONFIG_COUNT/KEY/VALUE` 注入 `http.https://github.com/<login>/<repo>.git.extraheader`
  （Basic `x-access-token:<token>`），不写 `.git/config`、不进 argv、不落盘、不进日志；
  不依赖用户是否配置过 `gh auth setup-git`。remote URL 本身不带凭证。
  错误输出沿用 `sourceGit` 的脱敏；主日志只记阶段、结果码与 ahead／behind 数。
- 绑定的是 login，不是 token：确认开启时用 `GET /user` 取 login，连同 fork 仓库名
  写入 `cindy-make-settings.json`（非秘密：`personalRemote: { login, repository, confirmedAt }`）。
  之后每次操作先核对当前 gh 登录的 login 与绑定一致；不一致时停止推送与拉取，Settings 显示
  “当前 GitHub CLI 登录账号与已绑定的 fork 不一致”，不自动改绑、不推到另一账号的仓库。
- Renderer 只传动作与版本 ID，不传 login、URL 或 token；fork 名、URL 与凭证一律由 Main 解析。

### Fork 的发现、创建与确认

- 首次选择（2026-09-22 用户裁决）：本机还没有托管源码、且 `cindy-make-settings.json` 没有
  记录存放方式时，两个会触发首次源码准备的入口（Settings 版本控制页的准备入口、`/cindy-make`
  前置弹窗）在 clone 开始前插入一步“个人版存放方式”，两个选项：
  - 「存到我的 GitHub（`<login>/cindy`）」：gh 已登录时默认选中；说明将使用的账号、fork 名、
    **fork 公开可见**（`makecindy/cindy` 为公开仓，GitHub 不允许其 fork 设为私有，因此个人版
    的修改会公开）、只推送 `cindy-personal` 及其官方基线记录、可随时关闭。
  - 「只存这台电脑」：gh 不可用时默认选中，此时上一项置灰并说明“安装并登录 GitHub CLI
    （`gh auth login`）后可用，换电脑也能取回个人版”，提供「我已配置好，重新检测」按钮，
    重新检测绕过 ghCliTokenSource 的负缓存。
  选择结果持久化后开始准备，之后不再询问；改主意在 Settings「开启／关闭同步」。选择
  「存到 GitHub」即构成建 fork 这一外部写操作的显式授权，不再另设第二个确认弹窗。
  已有托管源码的老用户不经过这一步，只能从 Settings 开启。若准备由其他路径触发而没有记录
  （例如旧版残留状态），按「只存这台电脑」处理。
- 选择「存到 GitHub」或从 Settings 开启后，先 `GET /repos/<login>/cindy`：存在且 `fork === true`
  且 `parent.full_name === 'makecindy/cindy'` 才视为可用；不存在则
  `POST /repos/makecindy/cindy/forks` 并轮询直到可 `ls-remote`；存在但不是官方仓的 fork
  （用户自己的同名仓）则拒绝并说明，不覆盖、不改名，允许用户手填 `<login>/<name>` 指定已有
  fork，同样校验 `parent` 后才绑定。
- 首次选择时若 fork 存在且远端已有 `cindy-personal`（换机器场景），该步直接在「存到 GitHub」
  选项下说明“你的 GitHub 上已有个人版（基于官方 vX、N 个个人提交），将以它作为这台电脑的
  起点”，不再单独弹窗；准备时按下节从 fork 恢复基线。选「只存这台电脑」则按原逻辑从官方
  ref 建基线，之后开启同步时按分叉流程处理。
- 本机已有 `cindy-personal`（此前无 gh 或未开启）、后来从 Settings 开启同步：这是就地
  转换，不重新 clone、不改 `origin`、不动任务分支／worktree／依赖／制作历史／已生成版本。
  步骤与失败语义：① 先按 `commitPersonalFiles` 把遗留未提交内容转成本地提交（旧 HEAD、
  暂存区、文件树先备份到 `refs/cindy-make/history-backups/*`），失败则一切未变；② 检查／
  创建 fork，纯远端操作，失败只提示原因、可重试；③ `remote add personal`；④ fork 上没有
  `cindy-personal` 时按显式 refspec 初始推送本机 tip 与 `personal-upstream`，只向远端追加，
  失败标“待推送”、本地照常可用。fork 上已有另一台机器的个人版时，确认弹窗额外显示两边的
  官方基线与个人提交数，默认操作为「合并并开启同步」，走下节分叉流程（候选目录内 rebase、
  `refs/cindy-make/backups/<ID>/personal` 备份、成功才采纳），冲突则建任务，成功后才推送；
  同时提供「以 fork 为准」「以本机为准」两个备份后覆盖的兜底，均需二次确认。
  确认弹窗须写明现有个人版的官方基线、个人提交数、将被整理的未提交修改数，以及“本机源码、
  任务和已生成的版本不会改动”。开启同步排在项目队列中，与准备、测试、生成互斥，等待时显示
  “等待其他工程操作”。首次选择之后 gh 可用性再变化不主动弹窗，只在 Settings 概览卡出现
  「开启同步」；选过「只存这台电脑」的用户，概览卡保留一行“安装并登录 GitHub CLI 后可将
  个人版同步到你的 GitHub”。

### 本地仓库布局与推送内容

- `origin` 仍指向官方仓，所有官方逻辑（`origin/main` 语义、`clearOnly` 的 URL 校验、
  运行版本查询、迁移基线计算）不变；新增名为 `personal` 的 remote 指向 fork（不带凭证的
  HTTPS URL）。常量放在 `sourcePaths`。清理源码时一并删除 `personal` remote 与
  `refs/remotes/personal/*`；关闭同步只删 remote 与远端跟踪 ref，不删 fork、不删本地分支。
  用户可见的说法始终是“个人版源码仓库 = 你的 fork”，不暴露 remote 名。
- 只推送两个 ref：`refs/heads/cindy-personal` 与 `refs/cindy-make/personal-upstream`
  （推到 fork 的同名 ref）。不推 `main`、任务分支 `cindy-make/*`、`cindy-merge/*`，也不推
  `refs/cindy-make/tasks|features|backups|failed-builds|history-backups/*`——这些是本机的
  工作快照与恢复引用，另一台机器无法复用。
- 推送时机只有三个，都在 `cindy-personal` 已成为**最终状态**之后：
  1. 个人版生成成功并登记到版本列表之后（`buildCindyPersonal` 发布、`onBuildState` 进入
     `ready` 之后），推送该次生成实际使用的 commit（`artifact.commit`），而不是分支当前名下
     可能已经变化的 tip。功能合入采纳的那一刻**不推送**：合入在生成成功前是临时的，检查或
     打包失败会撤回；若此时已推，远端会保留本地已撤回的提交，下次同步会把本机误快进回去。
  2. 官方更新采纳之后（Settings 手动同步或创建制作任务前的自动同步）。官方更新的采纳不参与失败回退，
     属于最终状态，可以立即推送。
  3. 首次开启同步时的一次初始推送。
  推送在项目锁外、当次操作的 Git 采纳与版本登记全部完成后进行，失败不改变本地结果，
  只在状态里记“待推送”，完成卡与 Settings 的生成结果显示“已同步到 fork／未同步”，
  Settings 提供「立即同步」；重启不自动重放推送，下一次让 `cindy-personal` 前进的操作
  入场时作为可见的前置步骤补推。
- 一律以显式 refspec 推送已核验的 commit：
  `push personal <commit>:refs/heads/cindy-personal --force-with-lease=refs/heads/cindy-personal:<refs/remotes/personal/cindy-personal>`
  （`personal-upstream` 同样按 commit 推）。官方更新 rebase 会改写历史，普通 push 必被拒；
  lease 保证不覆盖另一台机器已推送的内容。推送前核验该 commit 仍是本地 `cindy-personal`
  的 tip 或其祖先，否则放弃本次推送并标记待推送。lease 失败即视为分叉，进入下节流程，
  绝不追加 `--force`。

### 多机同步：拉取、快进与分叉（阶段 2）

- 任何让 `cindy-personal` 前进的操作（合入、官方更新、生成、「立即同步」）入场时，若身份可用，
  先 `fetch personal cindy-personal personal-upstream`。网络失败不阻止本地操作，但本次标记
  “远端状态未知、未推送”。
- 比较本地与远端 `cindy-personal`：相同则无事；远端是本地祖先则本地领先，直接推送；本地是远端
  祖先则先 `commitPersonalFiles` 保证工作区干净，再 `reset --keep` 快进本地并采用远端的
  `personal-upstream`，任务 worktree 不受影响。
- 两边分叉时自动处理，复用官方更新的机制（`merge-worktrees/<ID>` 候选目录、`cindy-merge/<ID>`
  分支、`refs/cindy-make/backups/<ID>/*` 备份、同一确认弹窗与 `cindy-make-merge` 任务）：
  1. 先统一官方基线。读取两边的 `personal-upstream`（缺失时以 `merge-base(cindy-personal,
     origin/main)` 代替），取较新者为目标基线；落后的一侧先用既有官方更新 rebase 抬到该基线
     （远端一侧在候选目录内完成，不改动 fork）。两个基线互不为祖先时不自动处理，见下。
  2. 再把本机独有的个人提交 rebase 到远端个人版之上（`rebase --onto <远端 tip> <目标基线>`，
     Git 按 patch-id 跳过两边已相同的提交），`--no-update-refs --signoff` 与官方更新一致。
  3. 无冲突：核验后 `reset --keep` 到结果、更新 `personal-upstream`、推送；有冲突：与官方更新
     相同，先弹窗确认，确认后创建冲突任务，取消则保留本机个人版、本次不推送、远端不动。
- 无法自动处理的情况（基线互不为祖先、远端 `cindy-personal` 不含任何官方提交、fork 不再是
  官方仓的 fork 等）只报告原因，并提供两个明确操作：「以远端为准」把本地 `cindy-personal`
  备份到 `refs/cindy-make/backups/*` 后重置为远端；「以本机为准」先把远端旧 tip 推到 fork 的
  `refs/cindy-make/backups/*` 再强推。两者都要二次确认，都不删除任务分支与已生成版本。
- 同步期间与其他 Git 写操作共用项目队列；分叉处理占用的候选目录与冲突任务沿用现有清理、
  取消与重启恢复规则。手机端只读投影同步状态，不新增远控写操作。

### Settings 呈现

- 版本控制页概览卡在个人版 hash 行下新增一行“个人版远端”：未开启／`<login>/cindy` 已同步／
  待推送／分叉（本机领先 a、远端领先 b）／账号不一致／远端状态未知。状态字段进
  `MakeSourceStatus.personalRemote`，与源码状态同一刷新代次，迟到结果不能覆盖较新状态。
- 操作只放同一处：未开启显示「开启同步」，待推送或分叉显示「立即同步」，已开启时提供「关闭
  同步」；分叉无法自动处理时在此处展开「以远端为准」「以本机为准」。文案走 i18n，术语先查
  `i18n/GLOSSARY.md`（fork、个人版、同步）。

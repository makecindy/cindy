# 飞书受管表单：能力缺口与验收提案

> 状态：待讨论的需求提案，未实现。本文不改变现有产品契约，也不表示修复已部署。

## 用户要完成的工作

用户在飞书收到一张预填资料卡，修改多个字段，选择处理范围并提交；Agent 收到结构化结果，
继续原任务，原卡同步显示已提交。用户不应为这条流程配置第二条机器人长连接或理解内部按钮 ID。

当前已验证的系统选择卡可以返回选项并显示已选状态；直接调用 Open API 发送的自定义表单
可以展示，但发送成功本身不能保证提交结果被宿主接收并交还 Agent。

## 建议的最小能力

优先复用宿主已有问答请求与渠道投递机制，增加通用的结构化表单能力。具体工具名和
schema 由维护者评审后确定。表单内容及后续业务编排由 Agent、Skill 或插件提供。

| 能力 | 最小要求 |
| --- | --- |
| 可发现的表单工具 | 接受稳定字段键、标题、单行文本、多行文本、单选、预填值、必填约束、提交与取消 |
| 宿主登记请求 | 先登记再投递，由宿主生成请求及动作标识；Agent 不手工仿造内置问答协议 |
| 结构化结果 | 返回按字段键组织的值、请求状态及可供核验的来源；操作者与投递标识来自受信通道 |
| 原任务续接 | 结果交给登记请求的任务与伙伴；不依赖 Agent 自建竞争连接或解析任意聊天文本 |
| 原卡状态 | 校验失败保留可编辑状态；成功提交后显示摘要并阻止重复提交；敏感字段不展示 |
| 可诊断投递 | 区分未投递、投递结果未知、已投递待提交、已提交、取消、过期；发送异常后不盲目重发 |

应区分卡片发送回执、用户提交回传、业务写入与业务回读四个结果。表单提交仅表达资料和
处理意图，高风险操作继续走现有授权与确认流程。

## 生命周期与边界

以下均为待实现要求，不描述当前已有保证：

- 请求绑定实际连接、App、任务、伙伴、目标聊天和卡片消息，按现有来源与权限规则核验操作者。
- 群聊和话题分别保留投递位置，不能因为回调缺少话题字段而续接到其他任务。
- 提交内容按已登记 schema 校验，包括字段类型、长度、必填与允许的选项；不得将回调中的
  隐藏字段当作授权、操作者或任务归属的权威来源。
- 重复、并发或延迟提交只产生一次有效结果；取消或过期后不能恢复为有效业务提交。
- 重启后可以恢复等待请求，或明确使旧卡过期，不能长时间保留看似可提交却无人处理的卡片。
- 保留现有系统选择卡和普通权限确认能力，不放宽未知动作分流或操作者校验。
- 密码、令牌等秘密值继续走专用保密输入流程，不进入普通表单结果、模型或日志。
- 表单失败不触发业务写入；业务失败单独报告，不能把原卡显示已提交当作业务完成。

## 分工与待评审问题

按[核心产品原则](../product-rules/core-product-principles.md)，宿主负责可复用的请求、
来源、生命周期、结果回传与跨端一致性；垂直流程及富交互界面留在 Skill 或插件。
实现前需要确认通用表单应扩展现有问答工具，还是通过已有扩展能力提供，并核对普通任务、
伙伴及不同飞书连接架构的覆盖范围。本提案不要求将特定组织流程写入 Core。

持久化、权限和跨端协议如需变更，应另行遵循仓库专项规则并提供迁移、兼容及回滚方案。
本 PR 仅增加提案文档，不修改这些边界。

## 建议验收场景

使用合成资料：显示名称「示例用户」、地区「示例地区」、简介「用于表单验收的合成资料」。
下列场景均待后续实现验收，不计为本提案已执行的测试：

1. 在真实飞书私聊发送含三个文本字段和一个范围单选的表单，核对客户端实际显示和 API 回查。
2. 用户修改每个字段并提交，Agent 收到准确的结构化值，继续原任务，原卡显示已提交摘要。
3. 在群聊及话题分别复测，核对目标、操作者与续接任务；明确谁可提交，拒绝不符合规则的操作。
4. 必填为空、无效选项、超长内容或未知字段不会进入有效结果，用户能修正后提交。
5. 双击、并发回调和回调重放只接受一次；取消、过期及重启后的行为与卡片提示一致。
6. 在桌面发起但缺少飞书投递上下文时，明确报告未投递或要求补全目标，不能将桌面问答显示
   误报为飞书已送达；具备受管投递能力时核对实际目标。
7. 选择处理范围不执行高风险动作；业务写入另有授权与回读证据。
8. 回归现有系统问答、权限确认及已选状态更新，确认行为保持兼容。

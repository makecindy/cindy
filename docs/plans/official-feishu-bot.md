# 官方飞书公共机器人：可行性与实施提案

状态：**提案，未实现、未部署**。2026-11-04，依据客户端 `4b4f3ba1` 核查。
本文不把个人机器人、扫码创建个人应用或插件用户身份发送当作官方公共接入。

## 用户要完成的工作

群里只添加一个 Cindy；成员无需创建应用或填写密钥，可以 @ 它提问、交付工作，
在原群或原话题收到进度、权限确认和成果。普通用户仅连接账号、选择执行电脑；
应用创建、平台审批、凭据和服务运维由运营方承担。与现有官方渠道一样，电脑离线
必须明确提示，不能把官方机器人理解成已包含云端 Agent 托管。

这是通用消息连接、身份和执行路由，归现有官方 Hook 基础设施，不新增一套 Agent Loop。
飞书业务资料查询仍由插件负责，不将其用户 OAuth 凭据借给机器人。

## 已核实的客户端缺口

| 部位 | 当前实现 | 实施时需要补的内容 |
| --- | --- | --- |
| 官方设置 | `HookConnectionsSection.tsx` 只支持 Slack / Telegram / X | 平台能力确认后增加飞书绑定、安装指引、执行电脑及真实状态；不先加空按钮 |
| 连接编排 | `hook-control/manager.ts` 的中性连接只有 Telegram / X | 复用 `NeutralProviderLane`，不要复制一份连接状态机 |
| 客户端及共享协议 | `shared/hookControlIpc.ts` 和 `slack-hook-protocol/src/types.ts` 的 provider 都没有飞书 | 与服务端共同设计增量能力协商，不能仅放宽一个类型 |
| 任务路由 | `hook-control/providerRouting.ts` 只识别现有三个渠道 | 飞书身份、会话、任务、绑定失效与后台结果使用同一个判据，未知来源继续拒绝 |
| 配置与部署 | `config/endpoint*.json` 没有飞书官方 Hook 端点 | 端点由真实部署提供；不猜域名、不借用个人连接、不复用其它平台地址 |
| 个人接入 | `main/im/feishu/adapter.ts` 与 `packages/lizi-im` 已有飞书收发 | 可复用消息编解码和平台呈现；本机凭据与“首个私聊者成为主人”的逻辑不能直接搬给公共机器人 |

上述路径除 `config`、`packages` 外均相对 `apps/desktop/src/`。
官方服务端在独立仓库；本次未核查或修改其实现，不能从客户端缺少端点推断服务端绝无内部原型。
完整现有流程见 [IM 轮次](../dev-rules/im-turn-flow.md)。

相关 [PR #8515](https://github.com/makecindy/cindy/pull/8515) 解决个人机器人扫码绑定，
[PR #7652](https://github.com/makecindy/cindy/pull/7652) 解决个人连接在伙伴间共享，
均不提供本提案的官方多用户服务，不应重复实现它们的个人接入改动。

## 先确认飞书平台路线

“不用每个用户建应用”不等于“一个应用不经审批就能进入所有企业的群”。

| 路线 | 可以追求的体验 | 上线前必须证明的条件 |
| --- | --- | --- |
| 运营方托管企业自建应用，按平台规则对外共享 | 公司先有一个公共入口；普通员工不配密钥，符合条件的外部群可试点 | 企业认证、线上版本与对外共享审批；内部群及真实外部群分别验收；验证群历史和附件权限的实际范围 |
| 商店应用，供不同企业安装 | 面向多企业的标准安装与账号连接 | 企业安装审批、租户凭证隔离；敏感群历史权限与外部群能力不能照搬自建应用的承诺 |

建议先验证第一条的公司试点，但这是**待维护者确认的范围**，不是已经决定更改线上应用。
如果目标是任意企业自助安装，应按第二条单独设计，不能拿试点结果宣称全平台支持。

飞书官方“机器人支持外部群和外部用户单聊”说明对外共享路径不支持商店应用；
历史消息 API 获取群聊消息还要求 `im:message.group_msg`。
现有个人接入帮助将完整群消息敏感权限标为自建应用可用，因此商店路线暂不承诺
“像 Telegram 一样读取此前所有相关群消息”。这些是能力核验点，不是断言任何特殊授权均不可能。
缺少能力时可明确只处理本次 @ 内容及平台实际提供的引用，不通过用户 Token 绕过限制。

平台验收至少确认 `im:message:send_as_bot`、群 @ 消息接收、单聊消息接收、消息资源及
所需群历史权限；是否获批以实际应用的线上版本和接口结果为准，不仅看已申请 scope。
卡片交互还需相应回调；所有事件验签、解密和平台校验挑战在服务端完成。

## 公共服务与账号归属

拟复用的主链路是：飞书事件 → 官方服务验证与去重 → 已授权 Cindy 绑定及执行电脑 →
现有 Hook dispatcher / session runner → 原群或原话题。该链路尚未实现。

- 官方应用密钥、平台访问凭证及事件验证材料只存服务端；桌面仅使用现有 Cindy 登录身份
  连接服务。不能把同一 App Secret 分发给所有电脑，造成多实例抢收事件或泄露。
- 用户绑定通过有期限、一次性的关联流程，同时证明 Cindy 身份和飞书身份，取消、过期、
  重复使用均不能生效；公共机器人不能把第一个私聊的人绑定为全应用唯一主人。
- 身份至少区分平台、应用和租户及用户；群和话题标识也在对应应用/租户内解释。
  对外共享事件的身份边界需用真实事件验证；字段不足时拒绝关联，不猜租户或拼凑另一应用的 open_id。
- 一个公共群可能有多个已绑定 Cindy 用户。首版建议由一位已绑定用户**显式认领群的执行责任**，
  展示将使用的电脑和模型额度，其他成员作为群请求者。无人认领时只引导连接，不随机派给
  最近在线的人。是否采用此规则需产品确认；认领仍受飞书群成员身份核验与授权撤销约束。
- 服务端在派发和发送前检查有效绑定、群归属、账号代次及执行租约。换账号、撤权、解绑或
  卸载后不得继续使用旧授权。未绑定成员不能继承执行责任人的私人任务、记忆或完全访问权限。
- 群工具审批复用 [共同权限决定](../product-rules/im-permission-confirmation.md)，
  同一请求在飞书、桌面和手机只有一个最终结果；不能由任意群成员点击按钮取得主人授权。
  具体交互需遵守既有官方 Hook 的身份策略，不在本提案中另创权限档。
- 当前飞书适配器已区分群主流和真实 `thread_id`；普通引用不自动开话题。官方接入应保留
  提问位置，不复用过时帮助中的“每次都新开话题”描述。输入来源、历史与引用作为不可信内容，
  不把群里别人的话转换成执行责任人的授权。
- 群上下文按实际获得的权限有界取得；缺历史、图片或文件时明确说明。日志不保存完整群正文、
  绑定码、授权 URL 中的秘密值或 Token。群内容保留与撤权清理在服务端范围内明确后才能上线。

## 分阶段提交，避免假可用

1. **平台验证与范围裁决**：运营方确认采用的应用路线，提供授权测试应用与两个真实租户的
   内部/外部测试群；记录实际可接收事件、历史、附件和卡片能力，不改生产业务群。
2. **独立服务端 PR**：在明确授权的服务端仓库实现事件验证、账号绑定、执行电脑路由、
   群认领、撤权、重复事件去重及原位置回传。不能省略服务端，只交客户端按钮。
3. **协议与客户端 PR**：协调维护双方共享的协议包，新增 provider 的能力协商、连接、
   设置及路由；旧端不协商未知 provider，未部署环境不显示“已连接”。沿用已有官方任务执行链。
   涉及凭证、来源、附件、权限与 wire 的具体修改前分别遵守对应专项规则。
4. **联调后发布**：维护者审核、运营方发布飞书应用并部署服务，再按区域开放客户端入口。
   不改写个人飞书的已存配置、凭据或会话；官方与个人连接分别标识并可独立解绑。

本仓的客户端 PR 无法代替第 1、2、4 步。本提案不部署服务、不创建应用、不更改现有企业策略，
也没有授权跨仓修改服务端；下一阶段需明确执行仓库与运营方应用的负责方。

## 必须通过的验收

- **最小成功路径**：没有个人飞书凭据的干净客户端连接公共入口；责任人绑定并认领测试群；
  另一名成员 @ 发出唯一测试请求；目标电脑出现且仅出现一个任务；原位置收到正确结果。
  保存脱敏的消息/请求关联证据，而不是只看接口 200 或设置徽章。
- **能力实测**：内部群和真实外部群分别测文本、引用、历史、图片、文件及已有话题。
  不支持的场景提示真实缺口；不宣称 mock 覆盖了平台许可。
- **隔离与授权**：两个租户/群/绑定用户相同形态的 ID 不串任务；未认领群不派发；
  非主人不能审批；解绑、撤权、切号后旧事件/回调/结果被拒绝；重绑不复活旧授权。
- **生命周期**：同一飞书事件重复投递只执行一次；工作中断线、电脑离线、确认暂停、
  停止及恢复沿用现有语义；发送结果未知时对账，不盲目重发业务结果。
- **混合版本**：新客户端连旧服务、旧客户端连新服务均保持原渠道可用，缺飞书能力明确说明；
  桌面与手机确认同一决定；回滚新功能不丢个人机器人配置及既有任务。
- **工程验证**：依改动范围运行 Hook manager / provider routing / dispatcher / interaction
  回归、各受影响包类型检查；新 UI 做中英文、窄屏及明暗模式检查。以上均是未来验收，
  本文档 PR 未运行这些功能测试，也未声称任何飞书真机流程已通过。

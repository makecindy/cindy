# IM 流式输出初始化失败兜底

## 背景

飞书私聊中出现过这样的交付断层：用户消息已进入 Cindy，Agent 回复也已生成并落库，但初始流式卡片创建失败后，飞书侧没有任何回复或错误提示。Issue #2164 记录了复现证据与代码路径。

现有 #924 / #1160 只处理流式卡片已经创建之后的终态更新失败，不覆盖第一张卡片未能创建的情况。

## 选择的方案

在共享 IM `turnRunner` 中把流式输出面的初始化结果缓存为“handle 或不可用”，并只记录一次脱敏错误。后续文本、工具进度和重试事件继续累积到 Turn 状态，但不重复创建卡片。工具结果中的托管图片无论 handle 是否可用，都先解析并记入 Turn 的媒体账本。Turn 正常或错误收口时，如果没有可用 handle，则安全物化最终 Markdown 中仅由正文携带的托管图片和 `xdt-file` 文件：本地图片和文件都在同一打开句柄上完成大小、inode 与真实根目录复核；SSH 会话中的图片和附件都按 `remoteHostId` 走 remote-file-service 的工作目录限界、`stat` 与分片缓存通道。图片补入同一媒体账本，文件再复制到权限受限的临时目录；后续上传只读取受控副本，并保留 Markdown alt 作为对外展示名。共享 Markdown 扫描会跳过行内代码和 fenced code，识别配对括号，并解析图片及 `xdt-file` 的尖括号/普通 destination 与可选 title；所有真正的内部媒体引用及仍未物化的本机绝对图片目标都从纯文本中清除并保留可读标签，代码示例保持原样且不会触发附件发送。之后通过渠道的纯文本接口发送清理后的最终正文（错误收口会附加错误说明），再通过独立的文件接口逐张补发账本中的媒体，最后清理临时目录。

Markdown 媒体物化只在 rich-card 的无 handle 分支执行；正常流式 handle 继续由渠道自身的 `finalize` 解析正文图片与文件，避免改变正常卡片行为或重复上传。交互卡把一轮回复分段时，流式 handle 会回报已确认随最终卡片落地的工具图片，包含“工具账本图片与正文受管图片为同一路径、正文上传成功”的去重交集；Turn 账本只删除这些明确交付项。Telegram 上传层同样返回逐项确认结果：单图失败和结果不确定的相册不会被误记为已交付。Discord 多批上传会在每批成功后累计路径；后批失败时先保存前批确认，再传播原错误。上传失败、卡片降级丢弃媒体或无法确认的项继续保留，若后续新卡初始化失败则由终态降级重试。这个方案避免每个 delta 重试建卡造成重复消息，同时让飞书卡片 API 故障与普通文本、文件 API 形成独立降级层。媒体逐张发送，单项失败只记录脱敏错误，不阻断其余媒体或 Turn 收口。

## 未采用的方案

- 在每个文本 delta 上重试建卡：可能产生重复卡片和高频请求。
- 只发送“交付失败”占位：会丢失已经生成的短回复，用户仍需回桌面端查看。
- 只在飞书传输层处理：共享编排器才知道 Turn 已经完成以及完整最终正文，传输层无法可靠收口。

## 错误处理

- 初始输出面创建失败：记录脱敏 warning，缓存不可用结果，不产生未处理 Promise rejection。
- 纯文本降级失败：记录脱敏 error，Turn 仍正常收口并释放后续队列。
- 媒体路径解析失败：记录脱敏 warning，继续处理其余图片。
- 最终 Markdown 图片物化失败：记录脱敏 warning，仍清除内部协议引用，不把本地媒体地址发给用户。
- 最终 Markdown 的本机绝对图片路径、`file://` 图片或超出物化上限的图片：不在纯文本中保留目标地址，只保留 alt 标签。
- 最终 Markdown 文件不在工作目录、路径无效、发生最终分量/父目录软链逃逸，或打开后复核的文件标识与路径真身不一致：不发送该文件，仍清除 `xdt-file` 地址并保留可读标签。
- SSH 会话图片与附件：通过 remote-file-service 在远端工作目录内校验并分片取回；远程主机不可用、目录外或超限时不发送且不泄漏路径。
- 图片补发失败或返回失败结果：逐张记录脱敏 error，继续处理其余图片并正常收口。
- 交互前的流式分段成功收口：只清除句柄明确确认已经交付的媒体；逐项失败或无法确认的媒体保留，以便终态降级重试。
- 正常 handle 创建成功：继续使用既有 replace / finalize 流程，不额外发送文本。

## 验证

- 初始建卡失败且有最终正文时，纯文本降级恰好发送一次。
- 初始建卡和纯文本降级都失败时，错误被记录且 Turn 正常完成。
- 初始建卡失败且 Turn 以终止错误收口时，已累积正文、错误说明和未交付媒体仍通过降级路径送达。
- 初始建卡失败且工具产出图片时，正文和图片都通过独立接口各发送一次。
- 初始建卡失败且图片只存在于最终 Markdown 时，发送清理后的正文并补发图片；正常 handle 路径保持原正文交给渠道 finalize。
- 最终 Markdown 图片解析失败时，纯文本中不出现内部媒体 URL。
- 最终 Markdown 含 `xdt-file` 时，仅发送工作目录内经文件描述符复核后生成的私有临时副本；目录外路径、软链逃逸和校验后换文件不发送且不泄漏。
- `xdt-file` 发送时保留 Markdown alt 展示名，不回退暴露本地 basename。
- 交互前已由健康流式卡片交付的媒体，不会在交互后的纯文本降级中重复发送。
- 同一图片同时来自正文受管 URL 和工具账本时，正文上传并随卡片落地后也会清理对应账本项。
- 交互前上传失败或未获明确交付确认的媒体仍保留在账本，交互后的纯文本降级会重试发送。
- Telegram 单图发送失败或相册结果不确定时不确认对应账本图片，已明确成功的同批图片仍可单独出账。
- Discord 多批上传后批失败时，已成功前批仍会从账本出账，失败批次保留供后续降级重试。
- 交互分段 finalize 在部分媒体成功后抛错时，Turn 层仍读取句柄确认并只保留未交付媒体。
- 行内代码或 fenced code 中的 xdt 引用仅作为示例文本保留，不收集、不上传；尖括号 `xdt-file` destination 与 title 按真实附件解析并完整清理。
- 某张图片补发失败时，失败被安全记录且 Turn 正常完成。
- 正常流式回复、空回复、工具结果和排队行为保持既有测试契约。

该修复不修改协议、数据库、凭证、UI 或移动端，也不新增依赖；回滚只需还原 `turnRunner` 与对应测试。
